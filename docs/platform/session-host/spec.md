## 1. Purpose

Every agent session, a worker under the run supervisor or a long-lived head such as the secretary, is placed by one port with five operations: `open`, `launch`, `alive`, `front`, `retire`. There is no single `start`: a controller learns the command it launches only after the slot exists (the run supervisor's gate), so placement is two halves. The facts are in the facts report; this spec fixes the contract. Section 8 adds what sits on top of the port for a head session: starting it, and replacing it before its context fills (rotation).

## 2. Ownership boundary

| Owns | Does not own |
|---|---|
| The five operations and their refusals | Which pane a key runs in, tab grouping, layout (Terminal Control) |
| The terminal adapter over Terminal Control | The attempt lock, cwd lease, containment domain, deadlines, receipts (run supervisor; containment never moves) |
| Head start and head rotation (section 8): the two-step replacement, the lineage files, the rotation lock | Typing an opening or a brief into a pane and detecting that it was taken (`fgos-agent-protocol`, driven by the run supervisor) |
| | Who a session is, its role, whether it holds the role (Identity alone) |
| | Which CLI, model or account (bind(), Seat Binding) |
| | Transporting a head's verbs out of its sandbox and enforcing its grant (run supervisor, head-request contract) |

## 3. Port contract

Machine form: [host-port.v1.json](../../../packages/session-host/contracts/host-port.v1.json).

- `open(request) -> placed(placement, slot?)`: allocates the terminal slot of a key (`groupKey`, `beside`, `groupSize`, `cwd`, `env`, `display`) and starts nothing. A key whose pane is already live answers its placement and allocates nothing.
- `launch(placement, spec) -> launched(identity) | not-started(reason)`: starts a prepared command in that slot through Terminal Control's durable `launched` marker and answers the launched root's process identity. `not-started` keeps the slot and never launches into it again.
- `alive(placement) -> live | gone | unknown`. `unknown` is never turned into `gone`.
- `front(placement) -> fronted | unsupported`.
- `retire(placement, close|retain) -> retired | unknown`.
- Refusals are `unsupported` or `unknown` with a named code: `host-unsupported-here`, `placement-unknown`.

Rules:
1. **Opening text.** Not a port operation. A head's opening is typed visibly as the full text by the run supervisor through the shared delivery step (`fgos-agent-protocol` `adapter_for`, `await_ready`, `deliver_brief`) after it has launched the head's gate; the Session Host never types into a pane.
2. **Idempotent key.** `open` of a key with a live pane answers that placement; it never allocates a second.
3. **Containment.** The port launches a prepared, already-contained command; it never builds containment.
4. **Close discipline.** Only a pane the port opened is closed, never a tab (Terminal Control rule).
5. **Serial per group.** A Node caller that opens many placements serialises per group (`openAsync`, `retireAsync(close)`, one queue per coordinating process): two rounds of one batch never both open the batch's tab, and a close waits behind the earlier opens of its group.

## 4. Adapters

- **terminal**: Terminal Control `allocate` for `open`, `launch` with shell-quoted `launch_line` for `launch`, `inspect` for `alive`, the focus operation for `front` (herdr `tab focus`), `release` for `retire`. Unsupported where the driver declares no pane capability (Windows): answers `unsupported / host-unsupported-here`.
- There is no screenless adapter. A screenless launch (SDK, cloud) is the run supervisor's own, and a head session needs a pane: it answers `host-unsupported-here` on a host without one.

## 5. Paper check against a second host

| Operation | Pane host (Terminal Control + herdr) | Screenless host (Claude Agent SDK or a cloud session) |
|---|---|---|
| `open` | allocate the slot | create the session record; `groupKey`, `beside`, `display` are ignored |
| `launch` | quoted launch into the slot | start the session with the prepared command; identity is the host's handle |
| `alive` | `inspect` of the pane: live, gone, unknown | the host's own session handle |
| `front` | the focus operation: `fronted` | `unsupported` |
| `retire` | `release` close or retain, only a pane the port opened | the host's own stop call; retain keeps the session |
| containment | stays with the run supervisor | stays with the run supervisor |

Both columns fit the five operations with no field the other column cannot fill. No cut that cannot hold was found.

## 6. Layer

Above Terminal Control (L2), below the run supervisor (L4). The dependency is one way: run supervisor → Session Host → Terminal Control. Rust crate `fgos-session-host` (`packages/session-host/rust`) with a thin Node client (`src/session-host/client.mjs`) behind an internal route; no user verb. The head use cases (`src/session-host/head-start.mjs`, `head-request.mjs`, `src/session-rotation/rotate.mjs`) are Node use cases above the client and the run supervisor's session attempt.

## 7. Shared entities

| Entity | Owner | Used here as |
|---|---|---|
| key | Terminal Control key shape | placement key: the attempt id, for a worker and for a head |
| allocation record | Terminal Control | the only pane record; the port writes none of its own |

## 8. Head sessions and rotation

### 8.1 Starting a head

A head (`head:<persona>-<name>`) is one long-lived interactive agent. `startHeadSession` checks the names, fronts the live holder of the role instead of starting a second (by the slot key in the holder's Identity record, `ids.terminal.key`; a record that names no slot is refused `placement-unknown`), and otherwise calls `placeHead`, the one launch path of a head: bind a seat at the persona's tier, launch it as a confined supervised session attempt (run supervisor, sandbox, account lease, private home) with the opening typed visibly, and answer the placement. `startHeadSession` then records the placement in the lineage folder. A head is confined like a worker; what differs is its grant (`grantOf(role)`): writable project paths (a granted directory is bound writable; a granted file, the secretary's `plans/backlog.md`, stays read-only in the sandbox, as does its whole directory, and only `session write` replaces it: Agent Confinement spec, grant `workspace-paths`), `mailbox` (the project's mailbox lock and record writable, grant `mailbox-record`; the secretary's) and allowed verbs. A head reaches the host only through its request socket (`head-request.v1.json`): `session bind session`, `session start`, `session write`, `session rotate`, `session answered`, `session restore role`, and the owner-question verbs `questions list`, `questions ask`, `questions ack`, `questions cancel` (every head, one shared list `QUESTION_VERBS` in `head-grants.mjs`) and `questions answer` (the secretary only). `questions list` is a read the route child answers by running the host's `fgos questions [--answered|--all] --json` (the sandbox cannot open the event store); a confined `fgos questions` (the form the start ritual and the skills use) is mapped to it and prints the reply's data, and the other `questions` sub-commands keep their own doors. The write verbs are served by the host route `fgos internal head-questions --run-dir <attemptDir>` (`apps/fgos/src/wiring/head_questions.rs`, an internal route dispatched in `main.rs` beside `seat-binding`, not in help): `runHeadRequest` only passes the request on, and Rust reads the envelope itself and fills the asker from it (the role from `envelope.session.role`, the session, handle, roles and machine from Identity as the holder of that role, the project from `envelope.cwd`), so no argument can name the asker; it refuses `questions answer` for any head but the secretary and records it with source `secretary`. Inside a head, `fgos questions ask|answer|ack|cancel` send these verbs through the socket when `FGOS_HEAD_REQUEST_SOCKET` is set, retrying a `busy` reply 3 times, 1 s apart; reads go straight to the store. `session write` (`fgos session write <path>`, content on stdin; the secretary's grant) is answered by the head's supervisor itself: the path must be named exactly by the grant's `writes`, a regular file with no symbolic link on the way, and is replaced atomically through the durable-file door, then published by the existing paths land (`fgos_supervision::land`, through the one port `WritePublisher` that `apps/fgos` fills in `wiring/session_write_publish.rs` and passes to `fgos_run_supervisor::route::main` as a parameter; the supervisor crate commits, fetches and pushes nothing). The order: first the land's own catch-up step alone (`land::catch_up`): under the target's merge slot the main checkout is fast-forwarded to the remote tip, and a branch with commits its remote lacks is refused `write-branch-ahead`, a catch-up Git marks Busy (its retryable class: `resource-busy` while a live writer's Git operation is pending, `worktree-admin-held`, `merge-slot-busy`, `main-checkout-busy`, `repo-config-busy`; `LandRefusal.retryable` carries it) is retried with doubling backoff (0.5 s up to 4 s, 45 s of retries and a last attempt that may wait a few seconds per lock, so about 60 s at most; session write has no route child, so the bound is the client's 180 s write reply timeout, not the 60 s verb timeout) and, if still Busy, answered `write-busy` (retryable, naming the last code, nothing written), never `write-catch-up-refused`; any other catch-up refusal `write-catch-up-refused` (detail `<land code>: <detail>`, e.g. `main-checkout-catch-up-refused`); then the path must have no uncommitted change (`write-path-dirty`; `write-path-unreadable` when that cannot be read); then the file must still be the content the write was based on: the request's optional `base` (a git blob id of 40 or 64 lowercase hex digits, anything else is `bad-args`; `fgos session write <path> [--base <oid>]` sends no base when `--base` is not given), else what the file held when the request arrived, and a different blob id after the catch-up is refused `write-base-stale` with both ids in the detail, so an edit built from an older copy never deletes newer rows when the writer passes `--base` = the blob id of the copy it edited (without it only a move during the catch-up is caught; re-read, redo the edit, write again); every refusal so far leaves nothing written. Then the write, and the paths land: only that path is committed (subject `docs(<role>): write <path>`, writer the head's writer id) and the checked-out branch is pushed without force; the reply is `{path, bytes, commit}` and `fgos session write` prints `committed <sha>`. The project's `land.gates` run only for paths their `when` matches, so a configured gate list whose globs match none of the path runs nothing (this repository's gates match only code paths, so a docs, backlog or plans write runs none); gates that do run run inside the request, under the client's 180 s bound, and the head's busy flag is held meanwhile, so the head's other requests are refused `busy` until it ends. A land refusal is a reply, not an error: `{path, bytes, publish: {refusal, detail}}`, nothing is forced, and `fgos session write` ends non-zero with `written, not published: <refusal> <detail>`. A land whose push the remote rejects (it moved after the sync) undoes its own unpublished commit through the Git door (`undo_unpublished_commit`: the branch and index return to the commit's parent, every byte stays) and starts over from a fresh sync, at most 3 more times, then refuses `land-retries-exhausted`; `land-commit-contract-violation` (a hook changed the commit) and a footprint refusal undo the commit the same way. So a refusal never leaves local main ahead of its remote (an undo that itself fails says so in the detail and leaves the commit for a person), and the next write is not refused `write-branch-ahead`; every other land refusal (`land-gate-failed`, `land-gate-missing` when the project configures no `land.gates`, and the others) leaves the file written and uncommitted. **Role bound before the agent exists.** The supervisor registers the attempt in Identity under its role before it tells the gate to go, so a head never runs without its role (the earlier order, register after the agent was bound with any refusal other than `role-held` only logged, let a head's first role-gated requests answer `role-not-held`). Identity's own liveness proof decides: a dead holder is swept and the role taken; a live holder that is not this head's earlier generation refuses the start `head-role-held`; any other Identity refusal is `head-role-not-bound` with its code in the detail. The attempt ends as not started (`start-refused.json`) and `placeHead` throws `HeadStartError` with that code, so `fgos session start` and a rotation report it and a rotation's predecessor keeps the role. **A rotation successor waits for its role.** A successor registers without the role by design (rotation moves it later, at `session answered`), so its role-gated verbs (its questions hook above all) can arrive before the move. When `role-not-held` would be answered and Identity's live holder of the role is the earlier generation of this very head (same persona and name, a lower generation, read from Identity's `head` group), the supervisor answers `role-pending-rotation` instead, naming the predecessor in the detail; a read-only verb in the one list `SUCCESSOR_READ_VERBS` (`head_request.rs`; today `questions list`, since `questions show` is not a socket verb; a Rust test keeps the list inside the verbs `head-request.v1.json` marks `read: true`, and `head-grants.mjs` points at the constant) is the exception: such a successor is answered it, decided by the same Identity fact and nothing from the request args, so its first turn can read the question store (the grant still applies), while every write verb keeps `role-pending-rotation`; every other caller without the role keeps `role-not-held`. Both head request clients (JS `requestHead`, Rust `head_client::request_head`) retry `role-pending-rotation` with doubling backoff (0.5 s up to 4 s) for at most 60 s, then report the code by name; the rotation stop hook asks with no wait (`RotationWait::NONE`). The Rust client keeps the reply `message` on its error, and confined Rust verbs show it. A move that fails stays refused by name (`role-take-failed`, Identity's code in the detail) and the predecessor keeps the role. A refusal of a route child carries the child's text to the client as the reply's bounded `message` (one line, at most 300 characters; the code stays `detail`), so a confined `fgos session start nope` shows `persona-not-found` with the personas it knows.

**One Identity record per head (phase 7e).** The envelope's `session` names the head (`persona`, `name`, `gen`, from `FGOS_HEAD_PERSONA`, `FGOS_HEAD_NAME`, `FGOS_HEAD_GEN` of the launch), and the supervisor registers the attempt in Identity with the `head` group (persona, name, generation) and the `terminal` group (slot key, tab and pane ids, read from the terminal store's allocation record of the slot), so a head cannot report another generation and its pane names it; a bind moves both groups to the agent's session. Its mailbox hook sends `session bind session` (args `{source, value, mailbox?}`: the CLI's own session variable and id, a Codex hook taking the id from its payload, and the mailbox name its hooks bound, `{fgosDir, name}`) the first time it binds the head, and again when that mailbox name changed; the supervisor records the bound session's `cliSession` (for Claude Code the name, messaging socket, pid and start time of `<config dir>/sessions/<agent pid>.json`, read outside the sandbox) and the `mailbox` group; until Identity shows the session bound, every later hook call asks again, except within 5 minutes of this head's own failed bind recorded in the hook outcome (an entry another head wrote, or none, means ask now); the head's supervisor answers the verb itself with the connecting pid (`caller-not-under-head` when that pid does not run under the gate) and has Identity register the agent's own session (cli `claude`, say) on the attempt's gate and move the role to it, so `fgos identity session` inside the head and `--to head:<persona>-<name>` both name that session, not the attempt's `worker` id. A second bind on the same live gate (the CLI started a new session, e.g. after `/clear`) moves the roles to the new session and retires the one bound before. A head messages a peer with `fgos mailbox send`; its sandbox does not reach peer session sockets.

A head runs in the permission mode its persona's invocation declares. The secretary head runs in the leads' mode (bypass), so a peer's message to it is delivered instead of held for approval; it is pinned by `runner.personas.secretary.prefer` in the release standard and runs only inside its required sandbox (Agent Confinement spec 13.4). Every other persona keeps the pane that asks. Only a head's launch may bind a bypass invocation (a capability, role or worker-seat pin of it is refused at bind as `bypass-invocation-not-allowed`), and a project's own `runner.personas.secretary.prefer` replaces the standard's list whole, so an override must keep the bypass invocation entry or the secretary head asks again. Under bypass the paths the grant opens are written without asking.

### 8.2 Rotation: the two-step rule

A head is replaced before its context fills. The replacement is two steps, never one:

1. **Start the successor beside the old session.** The executor (`rotateHeadSession`) writes the handoff, then calls `placeHead` for the next generation with `beside` set to the slot key the role holder's Identity record names (`ids.terminal.key`; none when the record names no slot), so the successor opens in the same tab while the old session still holds the role. The successor registers in Identity without the role only when the live holder is the earlier generation of this very head (same persona and name, lower `gen`) and reads the handoff in its opening.
2. **Move the role only after the successor answered.** The successor's own hook reports its first turn through its request socket (`session answered`): the entry records the answer (`answered.json`: generation, key, Identity session id, last assistant message) only when this lineage's pending rotation waits for that very key and the successor echoes the rotation id exactly (the handoff carries a `Rotation id:` line and `rotation.json` the same id; no fuzzy match, and this entry is the one place the answer is checked); then the successor's own supervisor moves the role to the successor with Identity's `take`. The executor accepts the answer only when Identity lists the successor as the holder, then (the successor now being the role holder, nothing after this point ever ends it; each step that fails writes a `step-failed` incident naming the step and the next step still runs) records the successor's placement and ends the old session by asking its own supervisor to stop it (`cancel-requested.json` in its run directory): the supervisor stops the agent and its release step closes the pane, as at any session attempt's end. The port's `retire(close)` is not used for a live head, because Terminal Control keeps a pane whose foreground is not provably the launched process.

Failure before the successor holds the role (start refused, no valid answer within `sessionRotation.answerWaitMs`): `rotation.json` is removed first (a late `session answered` is then refused), then Identity is asked once. If it already names the successor as holder, the rotation is finished and the incident `rotation-completed` says it was finished after the deadline; if Identity cannot answer nothing is ended and the incident says so; only otherwise the successor is ended the same way. After the ended successor's attempt has closed, Identity is asked who holds the role (invariant: after any outcome exactly one live head holds it): if nobody live does, a take that landed late hit the dead successor, and the old head registers the role again through its own supervisor (verb `session restore role`, registered without `take`, so Identity refuses when any live session holds it) with the incident `role-restored`; if that fails too the incident is `no-live-head` and the executor stops. In that last case the old session stays alive and keeps its placement record, one incident line goes to `incidents.jsonl`, and the reason is returned. Nothing is ever killed with SIGKILL: ending a session is its supervisor's normal stop. The next `session start` fronts whichever session Identity says holds the role.

**An executor that died is resolved on the normal path.** Before `session rotate` takes its normal rotation lock, and before `session answered` records an answer, the pending record's `executor` is judged by the process door (pid and start time, with host/boot/namespace identity). Only a well-shaped executor identity (positive integer pid and non-empty string start time) is judged; malformed or older records are not proven dead. Only `dead` permits orphan recovery. After taking its normal lineage lock, a new rotation is held off only by a proven-`alive` executor; `unknown`, malformed and older records may be replaced without guessing their executors dead. Recovery takes the same lineage lock without waiting and rereads the record. Identity alone then decides: if it names the successor (its head generation, terminal key, or matching recorded answer), placement follows the successor and the predecessor is asked to stop; otherwise the successor is asked to stop and the rotation is abandoned. The predecessor snapshot is saved before launch; the returned successor placement is saved after launch. A crash between launch and that save reads the successor assignment's newest run envelope through the existing assignment-layout reader. Successful resolution removes `rotation.json` and appends one `resolved-orphan` incident with outcome `completed` or `abandoned`; a late answer is then `no-rotation-pending`. If no successor run exists, recovery abandons and removes the record without stopping either session. If Identity does not name the successor, an existing successor run is asked to stop even when its envelope has no placement yet. Only a successor that Identity names and whose run exists but lacks a placement stays pending with `placement-unknown`. An unavailable Identity or an unwritable stop request also retains the record for retry and ends nothing on a guessed holder. A busy recovery lock makes `rotateHeadSession` return `{ rotated: false, reason: 'rotation-in-progress' }`, just like its normal lock. Doctor's `session-rotation-orphans` is one read-only pointer: it counts proven-dead executors within its 250 ms budget (otherwise omits the count), warns, never fails or repairs, and points to the lineage's next rotate or answer.

Authority: Identity alone says who holds the role. The executor owns the replacement and the lineage files. The run supervisor transports and enforces the verbs and moves the role on the one `session answered` verb. `placeHead` starts heads; there is no second launch path.

### 8.3 Requesting a rotation

`requestRotation` is the one entry that asks for a rotation: the request socket's `session rotate` and the unconfined branch of `rotateHead` (which `fgos session rotate` and a hook call) end in it. It checks `{ persona, name, reason: soft|hard|manual, stopFacts }`, writes `request-<id>.json` under the lineage folder, starts the executor as a detached process through the one detach door and returns at once. `soft` and `hard` rotate when the measured fraction of the context window reaches `sessionRotation.soft` or `.hard` (`rotation/decide.rs` in the Session Host crate; `hard` carries the pending question verbatim into the handoff); `manual` is the owner's `/handoff` and carries the old session's last assistant message too (8.8). One rotation at a time per lineage: the executor holds the `session-rotation` lock (holder-lock registry, `<fgosDir>/locks/session-rotation--<persona>-<name>.lock`), a second request finds it held and is a no-op, and `session start` refuses `rotation-in-progress` while it is held.

### 8.5 Recovery evidence and remaining gap

Orphan recovery and refusal of a late answer are owned by `test/session-rotation/rotate.test.mjs`; the read-only pointer and registry wiring by `apps/fgos/src/wiring/doctor/session_host.rs` and `doctor/mod.rs`. Older pending records without executor identity cannot be proven orphaned, but do not block the next rotation once its lineage lock is acquired.

The automatic Stop path still lacks a passing confined-head live proof. On 2026-11-22 the lead `lead-forgent-261122-0118-heads-b52f9` ended a real turn at about 04:00Z, but its trace retained only the 02:14:02Z hand-call line (`no-measure`). Its generation 2 `supervisor.log` identifies real hook requests at 03:32:17.856Z and 03:57:35.683Z refused `bad-measure` (`fraction must be a number of at least 0, or null`). Source diagnosis: the bounded request decoder (`packages/run-supervisor/rust/src/head_request.rs`, `Bounded::visit_map`) treats serde_json's arbitrary-precision decimal number token as an ordinary map. The host enables that feature through Config and Distribution; a decimal such as `0.33` therefore arrives as `{"$serde_json::private::Number":"0.33"}`, not a number, and the rotation boundary correctly refuses it. Integer/null hand calls do not exercise this case. The bounded decoder now reconstructs a `serde_json::Number` from that scalar representation, counting it as one value at its original depth and rejecting extra entries; numeric validation at the rotation boundary stays unchanged. Its owning regression in `packages/run-supervisor/rust/tests/head_request.rs` checks raw route input for decimal, exponent and large-integer numbers (not private maps), and the existing bounds proof now checks integer and decimal values exactly at and beyond the value/depth limits. Run that suite with `--features serde_json/arbitrary_precision` as well as its default features, since the standalone crate does not enable the host's feature unification. The native hook now also attempts one best-effort `stop-failed` incident for a failure after locating the lineage, preserving its error code and detail bounded to 300 characters. Its owning unit proof checks the exact line count, shape and Unicode bound. A confined head's lineage is read-only, so this local write can fail; durable reporting of a failure that never reaches the host still needs a host-writable route. See 8.8.

### 8.6 Configuration and the `/clear` fallback

`sessionRotation` in `core/config-standard`: `soft` (0.4), `hard` (0.7), `keep` (10), `windowSize` (1000000), `answerWaitMs` (120000), `personas.<name>.{soft,hard,reload}`. The context fraction comes from the status line sidecar newer than the Stop hook, else the transcript sum marked one turn stale (spike report).

`/clear` through Terminal Control `send` works (the spike measured 3 of 3, with a SessionStart hook re-injecting a short context) but cannot meet the two-step rule: the old context is gone before the successor answers. It is recorded only as a fallback for a host that cannot open a second session and is never used on the terminal host.

### 8.7 The `fgos session` verb

`fgos session start <persona> --name <name>` and `fgos session rotate <persona> --name <name>` are the owner's door to 8.1 and 8.3 (a live head is fronted by the slot its Identity record names; `fgos identity resolve` with any identifier of the head, its pane, tab, CLI session or role, answers the same record); `fgos session write <path>` is a confined head's door to its granted files. The request socket's verbs carry the same names (`session start`, `session rotate`, `session answered`, `session restore role`, `session bind session`, `session write`), and the `questions ask|ack|cancel|answer` verbs of the owner-question store carry theirs. "Head" stays this component's word for the session kind: Identity's `head:` role, `FGOS_HEAD_*`, `internal head-request` and the `head-request.v1.json` contract keep their names. `fgos head` (dbd26eae6) left no alias and no refusal pointer: it answers unknown verb. The verb is declared once in the command registry (`src/cli/command-registry.mjs`, generated manifest and routes beside it); the host serves its help.

The CLI arm holds no behaviour: `start` calls `startHead` and `rotate` calls `rotateHead` (both in `src/session-host/head-request.mjs`: a confined caller asks through its request socket, anyone else calls `startHeadSession` or `requestRotation`). The project is the worktree root found from the current directory. A CLI rotation is always reason `manual`; `soft` and `hard` come only from the rotation hook, so the verb has no flag for a reason.

Refusals and exit codes (the table `exit-codes.v1.json`):

| Exit | Meaning |
|---|---|
| 0 | started, fronted the live holder, or rotation requested (`rotate` returns at once; the executor runs detached) |
| 2 | precondition: a refusal of the use case or the socket (grant, role, `no-request-socket`, bind or start refused), or a rotation that did not start |
| 3 | `rotation-in-progress` |
| 4 | validation: missing persona or `--name`, `bad-persona`, `bad-name`, unknown sub-verb |

`--json` prints the use case's result (`start`: the placement or the fronted holder; `rotate`: `{ started: true, pid }`). Proof: `test/cli/session-verb.test.mjs`.

### 8.8 The rotation hook

`fgos hook session-rotation --event stop|session-start` is a native subcommand of `hook` (served by the host before the composition root, like `hook mailbox`; code `apps/fgos/src/wiring/session_rotation_hook.rs`). The hook only gathers facts, decides and asks: Identity moves roles and the executor rotates. It does nothing unless `FGOS_HEAD_ROLE` is set, takes the persona and name from `FGOS_HEAD_PERSONA` and `FGOS_HEAD_NAME` (declared by `placeHead` in the session envelope's env; the role string is never parsed), never blocks, prints nothing to the conversation except the session start's one `additionalContext` object, and exits 0 on every path; a failure leaves one line on stderr. Files, environment and payload fields it reads are the contract `packages/session-host/contracts/rotation-files.v1.json`.

- **Stop, successor.** When the lineage's `rotation.json` waits for `FGOS_HEAD_GEN` and no answer is recorded, the stop sends `session answered` (rotation id read from its own handoff, its Identity session id, its first assistant message) over `FGOS_HEAD_REQUEST_SOCKET` and does not measure. No message yet or a refusal: nothing is recorded and the next stop tries again.
- **Stop, any head.** Measure (`rotation/measure.rs`: a status-line sidecar record newer than the hook, else the transcript marked one turn stale), decide (`rotation/decide.rs`, thresholds of the persona), and send `session rotate` at every stop: on soft or hard with the stop facts, otherwise with reason `none` (the host rotates nothing and answers `below-threshold`). The request carries `measure` (fraction, source, stale, decision) and the host appends one line with the request outcome to `<lineage>/stop-trace.jsonl` (the hook runs in the head's sandbox, where the lineage folder is read-only, so only the host can write it). A failure after the hook locates its lineage attempts one best-effort `stop-failed` incident (`at`, `event`, `code`, `detail` bounded to 300 characters) and still reports stderr. A missing `.fgos` has no lineage to write to, and the confined head's read-only lineage can prevent this local incident write. Once a measured Stop reaches `requestRotation` with a valid lineage, a validation or start exception appends a best-effort `stop-failed` incident through the existing host incident writer before propagating; reliable reporting of a failure that cannot reach the host remains a gap. Without a request socket nothing is asked. No lineage state defines a pending owner question yet, so none is reported.
- **Session start.** Prints the latest handoff of the lineage (inline under 10000 characters, else a pointer and the pending question verbatim).
- **What a handoff records.** `- rotation:` in the handoff, `rotate` in `latest.json` and `reason` in `rotation.json` are the real kind: `soft`, `hard` or `manual`. A hard or manual handoff carries the old session's last assistant message and the pending question verbatim (a head batches its open questions in that last message; no structured pending-question source exists yet). The portfolio is the stop facts' list, else `sessionRotation.personas.<persona>.reload` (files or folders, listed as written; an entry the project does not have is left out quietly); the release standard lists the secretary's backlog and discussions folder, so the secretary rereads them after any rotation.
- **A manual rotation's last message.** No Stop hook carries it, so the executor reads it: the session folder the old launch kept or declared (`seatSessionDir`), then the route `fgos internal session-host last-message` (`rotation/last_message.rs`: the newest `<session-id>.jsonl` one level under the folder, read backwards from its end, at most 8 MiB; its last non-sidechain assistant message with text). The turn has ended only when the last user or assistant entry is an assistant `end_turn`; the executor reads again until then (at most 60 s), so the message written after the request is the one handed over. The handoff fences the message (a fence its backticks cannot close, so a heading quoted in it is never read as the pending question) and keeps its last 8000 characters behind `…(earlier text cut)`. A Codex head's rollout transcript is not read: no fixture proves its assistant record, so the section names it as not found. A folder or transcript that cannot be found leaves `(not found: <why>)` in that section and the rotation goes on. Proofs: `test/session-rotation/rotate.test.mjs`, the crate's `last_message` tests, and the route wiring in `test/session-host/client.test.mjs`.
- **Owners.** The frame codec and the client call are the run supervisor's (`go_channel`, `head_client`); measure, decide and the lineage reader are the Session Host crate's (`rotation/`); the wiring only connects them. The hook rows are Claude Code's, in the one hook table; `fgos doctor` reports a missing row through the existing hook row of that CLI.
- **Not built.** No status-line sidecar writer ships (`context-sidecar.jsonl` is optional), so measures are transcript-based and one turn stale until one exists.

### 8.9 The confined door: ticket verbs, `session stop`, `forQuestion`

A confined head reaches every verb below through its one request socket (`head-request.v1.json`); the host hands a confined call (`FGOS_CONFINED=1`) of a verb the contract names to the Node payload, which sends it through `requestHead(verb, args)` (one constant per verb in `head-request-client.mjs`, no second client). The route child (`runHeadRequest`) re-checks every argument, because the arguments come from the sandbox: an unknown key, a mistyped value, or a string that becomes a host argv token and starts with `-` is `bad-args`, and the host argv is built from named fields, never from a free string.

| Verb | Who | Does |
|---|---|---|
| `land` | any head with the grant | Answers a ticket. Exactly one of `branch` and `paths`. A `branch` land is a lead's only (`land-branch-lead-only`) and carries the footprint of its plan as `--footprint` (a plan with no footprint refuses `write-outside-footprint`, the flag is never left out); `tests` go as one `--test <path>` each; `paths` must lie in the caller's grant `writes` (`path-outside-grant`), and a lead's `paths` land that would change the `footprint` of its own `plan.md` against the trunk tip is `footprint-change-refused`. |
| `run` | lead, secretary, supervisor | Answers a ticket. `prompt` (never `unit`: a unit file declares its own writes, which the footprint could not bound, so `unit` is `bad-args`); `writes` the plan footprint does not contain, judged by the repo's write-scope matcher (`matchesWriteScope`), are `write-outside-footprint`, so `src/**` is not contained in `src/*`. The runner starts `fgos run` without `FGOS_DISPATCH_DEPTH`, so a lead's phase run is a top-level seat that takes a lane. The secretary and the supervisor run one unit built from a prompt, read-only unless `writes` lie in a linked `worktree` (`writes-need-linked-worktree`), held to `secretary.run.maxMinutes` and `secretary.run.tier` (`run-ceiling-exceeded` when a request asks for more; `run-one-unit` when it names a unit file); a persona that is no coordinator or lead is `role-mismatch`. |
| `request result` | any head | Reads this role's own tickets: with `id` one (`ticket-unknown` for another role's), without it the role's tickets newest first; `wait` (seconds, at most 50) polls until the ticket leaves `running`. |
| `worktree create` | lead | `fgos worktree create <path> --branch <b> [--base <ref>]`; `branch` is required (a detached worktree is not this door's). |
| `session stop` | supervisor, secretary and any head granted it | `stopHeadSession`: stamps `retiredAt` in its lineage `placement.json` (the head-state source reads `retired` from it) before anything can end the route, then ends the live head the way a rotation ends the old head (its own supervisor is asked to stop it, the attempt's close is awaited), then retires the pane; a plain pane close is refused while an agent is the pane's foreground (8.2). When no stop request can be written the answer is `stop-not-ended` and the stamp is put back; once the request is written the stamp stays, and a head that does not end in time (`stop-not-ended`) or a pane that will not close (`retire-refused`) is reported with the stamp kept. Allowed for a lead or planner lineage of this project, the asker of an answered question (the host's `asker.roles` holds the role; a host failure surfaces with its code), or the caller's own role, else `role-mismatch`; a role no live session holds answers `{stopped: false, reason: "not-live"}`. The secretary and the supervisor may stop any head; a persona that holds no head grant (a hand-started session) is `stop-target-not-head` for them. |
| `supervisor handled`, `supervisor done` | supervisor | The host verbs of the same name, through the envelope's `hostBin`; `handled` takes `events`, one to 50 ids, and marks every one. A `done` that answers `{done: true}` also starts a detached stop of the caller's own role, which waits for the route to exit so the reply is out first, and adds `stopping: true` only once that process started. |
| `supervisor queue`, `supervisor plans`, `slots` | supervisor | Reads the sandbox cannot make itself: the queue is read from the event store, the plans need Identity's project handle and live role holders, the lane view the machine's lock root, and all three sit under masked roots. Not tickets: the route child runs the host verb with `--json` through `hostBin` (the way `supervisor handled` does) and returns its JSON within the 60 s bound. A lead's skill reads only `request result`, so a lead is granted none of them. |
| `supervisor raise` | secretary, supervisor, lead (`LEAD_VERBS`) | Not tickets: the route child runs the host verb with `--json` through `hostBin`. Puts one coordination event on the supervision queue. |
| `supervisor wake`, `watcher tune`, `session read`, `session type`, `metrics record`, `metrics prune` | the two coordinators, per `GRANTS` (`src/session-host/head-grants.mjs`) | Not tickets: the route child runs the host verb with `--json` through `hostBin`. What each does and why is [supervision/spec.md](../supervision/spec.md) 4.1; arguments and refusals are `head-request.v1.json`. `metrics record` accepts `fgos.coordination.*` records only (`kind-not-allowed`). `session type` refuses `target-not-stuck`, `session read` and `type` refuse `session-has-no-pane` or `terminal-refused` when the terminal port cannot serve them. |
| `friction record` | every head (`HEAD_VERBS`: secretary, supervisor, shaper, planner, lead) | Not tickets: the route child runs `fgos friction record ... --json` through `hostBin` outside the sandbox; fail-open (returns its code and exits non-zero if refused or failed). |
| `config patch` | supervisor (`GRANTS`: supervisor only) | Not tickets: the route child runs `fgos config patch <file> --project-only --json` through `hostBin` outside the sandbox; the host stays the only authority on which file a key lives in, and `--project-only` ensures every edit targets the project config file. |

The host verbs' answers are read as one document first (`--json` prints it indented) and line by line only when that fails; a refusal the host prints on stderr as `fgos: <message> [<code>]` keeps its code as the verb's `verb-failed` detail.

A plan is read by one reader, `planOfHead` (`src/session-host/head-plan.mjs`): a `lead-*` or `planner-*` head name is the project handle cut to the prefix limit, `-`, and a prefix of one plan directory that is not `done` or `withdrawn` (`plan-not-found`, `plan-ambiguous`; the limits live in `plan-vocabulary.v1.json`), and its `footprint` is read from `plan.md` at the trunk tip, never from the working file. The project handle is the Identity one (`handle` of `.fgos/project.json`, what `fgos identity project` reports), never the checkout folder's name.

**Tickets.** The socket serves one request at a time and caps a verb at 60 s, so `land` and `run` answer `{ticket, state: "running"}` at once. The request id is the ticket id; `.fgos/runtime/head-tickets/<role>/<id>.json` is created without replacing (`ticket-used`) and a detached runner runs the host verb to its end, then rewrites the file `done` or `failed` (`exit`, `code`; the ticket keeps its `argv`, and a failed one the host's refusal `code` (else `exit-N`), a bounded `message` and `stderrTail`, all returned by `request result`; `land` keeps the host's JSON, `run` only the `unitRunId`, whose outcome stays in `.fgos/assignments/<unitRunId>/` and is read from there by `request result` through the Unit-run readers: present, settled, summary outcome). The runner's process identity is written into the ticket before the reply, so a runner that dies at once reads `failed`/`runner-gone`. The runner outlives the route child (proof: `a_ticket_verb_answers_at_once_while_its_detached_runner_outlives_the_route_child`). A `running` ticket whose runner record is judged `dead` reads `failed` with `runner-gone`; `unknown` stays `running`. Ticket files are runtime scratch.

**Task binding.** A head of a task-bound persona is bound to its task before anything is launched or recorded (`taskOfHead`, `src/session-host/head-plan.mjs`): a `lead` to its live plan (`planOfHead`, `plan-not-found`), a `planner` or `shaper` to the feature directory under `plans/discussions/`, or the later plans discussions home once it exists, whose `DISCUSSION.md` its name spells, with the project handle prefix optional and an exact directory name winning over longer ones (`discussion-not-found`, `task-ambiguous`). The opening then carries a `# Task` section with the exact path and the persona's first step, so a hand start and a supervisor start of the same name type the same text. `secretary` and `supervisor` are bound to nothing and start as before.

**`on_wake`.** A wakeable persona (supervisor, lead, planner) carries an `on_wake` line in `core/agents/<persona>.yaml`; the opening ends with it under `# On wake`. It tells the head to continue in the same turn into its skill procedure and names the done step it must not end before, because nothing types into a live pane after the start ritual (step 3 of which says "then continue"). Secretary and shaper carry none, so their openings are unchanged.

**`forQuestion`.** `session start` takes an optional question id; the opening gains one line telling the new head to write that question's answer back to its origin and then `fgos questions ack <id>` (or `cancel`). The successor holds the asker's own head role, so nothing else changes.
