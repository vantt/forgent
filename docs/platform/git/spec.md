## 1. Purpose and boundary

Git decides what Git state exists, performs typed authorized mutations, and reconciles their interrupted effects. Rust is the live core now; Node transports typed inputs/results and owns no Git policy. There is no public `git(args)` port and no dual-run writer. Workflow, Execution Core, Work, business workflows, setup and Event Store are consumers, not parallel Git cores.

Git owns local object/ref/index/worktree mutations, worktree registration, the local side of fetch/push, and operation recovery. It owns neither business approval nor Work lifecycle, claim/state transaction, reducer, event envelope/union, seal schema, coverage or consumer cache. Holder-lock owns locks/fences; Process owns containment/signals; Session Identity owns writer identity. A read-only request never silently commits, builds, creates a worktree, configures a remote or repairs a repo.

**Projects without Git.** A read-only Unit needs no RepoHandle. When the directory is not a repository, Inspect returns the typed result `notARepository` and Git never turns the absence of a repository into a workflow error; whether a consumer (for example a business workflow, mission #2) proceeds without one is the consumer's decision. A mutation still requires a validated repository.

Required component-boundary row on acceptance: **Git — foundation; owns repository facts, typed Git operations and recovery WAL; consumers Workflow/Execution/Work/Event Store/setup; dependencies holder-lock/process/session-identity; no consumer imports.** Remove “pure git integration” from Workflow's ownership. The signing bundle (2026-10-18) installed this row in `docs/platform/component-boundary.md` and removed “pure git integration” from the Workflow row.

| Mutation layer | Owner / success boundary |
|---|---|
| Local objects/refs | Git; expected-old publication says nothing about checkout or network |
| Local index/worktree/admin | Git; scoped commit/sync/land/restore/create/remove/relocate |
| Remote send/receive | Git transport port; explicit ref mapping and separate remote acknowledgement |
| GitHub API merge | GitHub adapter under consumer authorization; never a local land and never a policy bypass |

A network failure cannot undo local success. API timeout is outcome-unknown until queried; do not blindly issue another merge. GitHub transport must retain consumer approval/Iron Law and record the actual merge commit. This spec authorizes no external send by itself.

Git never imports a consumer. Verify/build/npm/`worktreeSetup.commands` are **not** Git operations (G-030/G-031). Execution provisions after `worktree-create` returns, **outside every Git lock**. Git may spawn only `git` (plus Process containment of those children). Consumer verification evidence is bound by digest; Git does not claim tests ran.

## 2. Shared entities and outcomes

| Entity | Contract |
|---|---|
| RepoHandle | Validated canonical common-dir and trusted main/root identity/topology; never worker `.git` authority |
| WorktreeHandle | Registered gitdir/backlink, canonical path, branch/detached OID, creation identity; revalidated at mutation |
| Oid | Full object-format-aware identifier; validated commit/tree/blob type, no fixed SHA-1 assumption |
| RefName / ExpectedTip | Full validated namespace-qualified **direct** ref; expected `Absent` or exact OID, never wildcard absence. Symbolic refs are refused in owned and mirror namespaces (C1). |
| Scope | Canonical RUL84 entries, matcher version and explicitly expanded generated grants |
| Custody token | The existing `dispatch-cwd` lease (rank 30) on the worktree, held by Execution and extended across the runner commit (owner decision Q2, section 6). Git **validates** the lease descriptor by kernel check and fails closed when it is missing or stale; it does not mint a second lock and there is no Git `Custody` entity. A text session/writer id is not custody. |
| Candidate | Immutable source/target OIDs, exact result tree, parent/mode, **policy evidence digest**, pin |
| OperationId | Repo-scoped idempotency key bound to kind, repo identity, **canonical resource set**, expected values and authority domain; same id with different request digest refused; same id must not bind two disjoint resource sets |
| Receipt | Structured effect receipt (below). Operational evidence, not a consumer event |

Receipt (panelist 1 / C3) — effect is not completion:

```text
operationId, requestDigest,
localEffect {expected, publishedOid?, observedTip, publicationState},
checkout {notApplicable | pending | reconciled | recoveryRequired},
durability {processCrash | stableMedia, capabilityEvidence},
remote {notRequested | acknowledged | unknown | rejected},
consumerSettlement {notOwnedByGit},
attribution {thisInvocationWonCas | effectObservedOnly | uncertain}
```

`publicationState` distinguishes “currently at candidate” from “this invocation's CAS was observed successful.” Seeing `ref == next` after a crash proves the desired state exists; it does **not** prove which actor installed it. Do not manufacture writer attribution from equality. ABA (target returned to expected after a possible successful CAS) does not justify generic retry: a target CAS whose outcome is unknown is never reissued (§10 TargetAttempt rule). The CAS winner is defined per attempt recorded in the WAL, not by OID value over history: exact-old CAS gives at most one successful state-changing CAS per resource within one uninterrupted expected-state generation, and two CASes from the same expected OID across an ABA are both correct Git semantics. OID equality never identifies a generation; per-operation at-most-once is a WAL property, not a CAS property.

Results distinguish `unchanged`, `created`, `committed`, `landed`, `conflicted-open`, `conflict-aborted`, `busy`, `stale`, `refused`, `cancelled`, `failed`, `published-checkout-pending`, `committed-but-contract-violation`, `remote-outcome-unknown`, `recovery-required`, `abandonedBeforeAttempt` (terminal, PublicationCas only, §10 rule 4b: no TargetAttempt, so no target effect), `configApproved` (terminal, ConfigChange only, §10 rule 4c: an effect-free re-approval of existing fetch mappings), `superseded` (terminal, PublicationCas only, §10 rule 4a: a record-only outcome that says nothing about whether the old CAS ran). Include operation id, typed cause, retryability, actual effect/OIDs, exit/signal and bounded redacted stderr. An ancestry query returns yes/no/error; path-at-revision present/absent/error. Corruption, permission and unknown protocol never become “absent”. An ancestry walk that crosses a shallow boundary returns `shallow-history-incomplete` (an error, never “no”), even when both endpoint objects are present: the Git floor proof saw `merge-base --is-ancestor` exit 1 for a true parent after the parent was fetched into a shallow clone. Endpoint presence is not traversal completeness, and cleanup (§11) never treats such an answer as delivery proof. Cancellation after CAS reports the published effect. Local commit, reconciled checkout, remote ack and durable consumer settlement are separate facts.

## 3. Typed operations

All mutations require operation id, validated repository, writer and **declared resource set + existing authority**. No option-bag escape to raw Git args. Reads are bounded/paginated and do not repair. Doctor never mutates.

| Port | Operations and guarantees |
|---|---|
| Inspect | resolveRepo/Ref, status, diff, ancestry, readObjects, pathsAtRevision (batched), listWorktrees, compareContent, snapshotWrites; explicit unknown/error and byte-safe paths; every Inspect call runs with optional locks off (`--no-optional-locks`), because `status` otherwise refreshes the index under `index.lock` |
| Refs | ensureBranch, advanceRef, deleteRef, fastForwardCheckedOut; exact-old CAS, never blind `branch -D`. Exact-old CAS does **not** protect a checked-out branch (`update-ref -d` deleted the current branch in the Git floor proof, and the V-CAS re-check deleted a branch that a worktree registered after the snapshot had checked out): every Refs mutation of `refs/heads/*` takes worktree-admin 40 (§5), and under that one hold revalidates every registered checkout (main and linked; a symbolic HEAD to an unborn name counts as checked out), performs the exact-old CAS, reads back the ref and the registered checkouts, and only then releases 40, so no fgOS worktree registration can come between the check and the effect. An earlier snapshot of checkout membership protects nothing. An in-use ref is refused. No typed operation switches the branch of an existing checkout; one added later takes 40 first. A switch by raw Git or a worker is outside the concurrency guarantee (§9) and is reported as `recovery-required` when that read-back sees it. The one exception is `fastForwardCheckedOut(branch, expectedOld, next)`: fast-forward only, exact-old CAS, the branch is checked out only in a worktree whose verified `dispatch-cwd` lease the caller holds, that checkout is clean, and its tree is updated under that custody; anything else is refused |
| Worktree | create, createDetached, relocate, remove, inspectOrphans, repairRegistration; one admin door, no rm-rf fallback. Git returns after registration/strip of worker `.fgos`; provisioning is Execution. |
| ScopedCommit | preflight/commit; foreign index refusal, custody, literal exact selection, postcommit set/tree proof. A tracked file move is a ScopedCommit with both literal paths (old deleted, new added); failure restores both paths to their immediately pre-commit existence, mode and content before any consumer registry update (a producer move already made before commit remains old-absent/new-present); there is no separate file-move operation |
| Sync | start/inspect/continue/abort; pinned target, scoped resolver, operation-owned merge state |
| Land | prepare/publish/recover; immutable candidate, merge or squash, journalled CAS/checkout. Consumer supplies verification evidence. |
| SafeRestore | preview/apply/recover; full locked checks and durable snapshot before destructive effect. `apply` may carry `reapplyLocalDelta`: after the snapshot and the restore to the new tip, the captured local delta is applied to index and tree; a failed reapply leaves the durable snapshot and returns `recovery-required` (replaces `resyncWorktree`'s `reset --hard` + `apply --index`) |
| Checkpoint adapter | checkpointTrackedFiles; detachable, consumer-selected **non-event** tracked payload only |
| RepositoryConfig | publicationFetchMappings(remote), ensureFetchMapping, ensureHooks, removeOwnedHooksConfig; local config, user settings preserved, provenance |
| Remote | fetchRefs, pushRefs, inspectRemote; explicit mapping, no implicit all-refs or default push-config mutation |
| Recovery | inspectOperation, listPending, reconcile; actual disk/ref checks and idempotent results |
| Publication | restricted plumbing; section 4. Event Store is the only production writer of event refs |

Implementation may collapse ports internally; the appendix maps lessons to this surface. Idempotency is required wherever an effect can repeat.

## 4. Publication port: refs/fgos/*

Event Store's crate-internal driver (event-store spec §3/§20) moves behind this port **without a protocol change**. Node reaches publication through the **combined N-API addon** (below) with **no exception** to the exec guard under the `state` lock. Git is forbidden under state 60. Event Store bounded append/read inside state remains its own in-process/open-log path; no DAG walk or Git call there.

**One Node load: one combined addon (owner decision Q1, topology (a)).** A Node process reaches exactly one in-process instance of `fgos-git`. Two independent Rust cdylib addons cannot share one in-process crate instance, so the Node payload ships **one combined N-API addon** that links both `fgos-event-store` and `fgos-git` and exports both facades. Event Store's seal/sync publication and every Node-reachable Git operation run through that one load. There is no per-operation host-process route (`fgos internal git <op>`) for Git and no JS-bridged second addon; topologies (b) and (c) are not adopted. A second, separate addon load of either crate in the same Node process fails closed, and doctor reports one ABI row for the combined addon. This changes Event Store's packaging (event-store spec §17, §21: its own addon of `fgos-event-store` becomes the combined addon); the signing bundle (2026-10-18) made that amendment, with the Publication port placement in event-store §3, §4 and §20. Rust consumers (observe, `fgos-work-state`) link `fgos-git` in-process. Reversal trigger: if experiment E3 shows the combined addon fails a budget stated before the run, or fails rollback with live processes (P-RELEASE), Q1 reopens.

Operations: writeBlob(bytes), writeTree(literal entries/modes/OIDs), writeCommit(tree, ordered parents, identity/message), readRef/Object, walkCommits(tips,cursor,bounds), compareAndSwap(ref,expected,next,operationId), fetchRefs and pushRefs. No index, worktree, HEAD, main-checkout lock, or consumer semantics.

**C1 — distinct execution policy.** Publication operates on direct namespace-qualified refs. It refuses symbolic refs in owned and mirror namespaces, validates the destination, and uses a backend mode that cannot follow a symbolic ref outside the grant even if the ref changes after preflight. A plain textual prefix check is insufficient. On the Git floor measured (2.53.0) a plain `update-ref` on a symbolic `refs/fgos/*` ref wrote through to `refs/heads/victim`, and `--no-deref` kept the victim unchanged but silently replaced the symbolic ref with a direct one while the expected-old check passed against the dereferenced value. Two separate checks therefore apply: (1) containment, the guarantee: every ref mutation runs in no-dereference mode with the expected OID on the actual update, so it never changes a ref outside `refs/fgos/*` even when the ref turns symbolic after preflight (the P-SYM-HOOK re-check confirmed this on 2.53.0: every `refs/heads/*` ref unchanged across the attack window, while the control without `--no-deref` moved the victim); (2) refusal, best effort: the ref is read as a symbolic-or-direct fact at preflight and again at read-back, and a symbolic ref found at either point is refused or reported as `recovery-required` tamper evidence. Detection of a **transient** substitution is not guaranteed: the same re-check turned a direct ref symbolic between preflight and the CAS, the `--no-deref` CAS overwrote it with a direct ref at the candidate, and both reads saw a direct ref, so read-back cannot recover the overwritten symbolic state. A substitution that is still present at read-back is detected. No detection mechanism for the transient case is claimed until a proof names one. An expected-OID match is never evidence that the ref was direct. Object writes and reads do not enable replace-object or alternate-object authority from worker input, and every identity/type/tree/ancestry/publication read runs with replacement objects disabled (`--no-replace-objects` or its environment equivalent): scrubbing `GIT_REPLACE_REF_BASE` does not disable repository-owned `refs/replace/*`, which made `cat-file` return a different commit for the same OID in the floor proof. Worker-supplied alternate-object, replace-ref and shallow authority (`GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_REPLACE_REF_BASE`, `--reference`-style overrides, config injected through the scrubbed env context of G-001/G-183) is always refused. Repository-owned layout in the trusted common dir (`.git/objects/info/alternates`, shallow, promisor remotes) is a compatibility profile: until E5 establishes which of these configurations `fgos-git` supports, an operation that needs an object unavailable under that layout refuses by name rather than fetching implicitly, and the refusal names the layout feature. Raw Git does not do this by itself: a read of a missing blob in a promisor partial clone spawned a lazy `fetch`, and a missing alternate gave a generic exit 128. So the hardened context sets no-lazy-fetch (`GIT_NO_LAZY_FETCH=1` on the measured floor) for every non-Remote operation (status, diff, read, checkout, merge, not only readObject); shallow, alternates and promisor layout are detected before invocation; a missing object or incomplete traversal becomes a named layout refusal that keeps the actual Git error. Any fetch or deepen is a Remote operation with its own authorization, never an Inspect repair.

Publication's private Git calls **cannot execute repository hooks**, including the **reference-transaction** hook, nor inherit worker-provided external commands. “No hook-running commit porcelain” is not enough: plain `update-ref` ran `reference-transaction` (`prepared`, `committed`) on the measured floor. Every Publication call carries a trusted hook-disabled configuration (`core.hooksPath` set by the backend to an fgOS-owned empty location; `/dev/null` suppressed the hook on 2.53.0) that no repository or worker config can override. This does not disable guards on ScopedCommit or checkout mutations. Transport helpers and credential providers are Remote capabilities, not implicit privileges of writeBlob/readObject/CAS.

Use explicit trusted common-dir plumbing. Validate object types and refs. Event Store provides the seal/merge manifests and parent order; Git never computes event union or business conflict outcomes.

Namespace grants are explicit: own events/local-events/branch-events and authorized one-time legacy import; mirrors only fetch-written; Git operation pins reserved to Git. CAS distinguishes absent from exact OID and returns actual tip on loss. No event segment deletion follows a Git receipt alone: Event Store still verifies coverage and durably records its own sealed receipt.

Required unchanged Event Store protocol:

1. Seal/sync owns event-seal 58; event-append 70 protects rotation only and is released before Git.
2. Write trees/commits, journal intent, CAS `refs/fgos/events/<machine-id>`; retain segments on CAS loss. Event Store retries by its section 10 rules.
3. Walk both parents of a DAG with visited set and bounded continuation. Only Event Store decides certified coverage pruning. Incomplete traversal never claims complete coverage.
4. Fetch `+refs/fgos/events/*:refs/fgos/remotes/<remote>/events/*` and the existing legacy mirror mapping. `+` is allowed only for mirror refresh as Event Store §14 requires. Never overwrite own ref by fetch.
5. Push only own events and authorized legacy ref; never force-push, mirrors, local/branch streams or Git pins. Non-FF triggers Event Store fetch/reconcile using a two-parent commit then ordinary push. No Git-side event reconciliation.

**CAS and pin ordering (V-CAS fold).** A multi-ref `update-ref --stdin` transaction is **not** crash-atomic on the `files` backend: the Git floor proof killed one after the target rename and left target = next, pin = expected and `pin.lock` on disk. Reftable was exercised only for completed transactions. So Git never relies on multi-ref atomicity: the operation pin is written by exact-old CAS and read back as a prepare substep, the prepared WAL record is made durable, the TargetAttempt record of §10 is made durable, and only then is the target moved by a single-ref exact-old CAS. This order is mandatory and has no optimization: Git never puts a target publication in a multi-ref transaction, with the pin or with anything else (the M1 and V-CAS re-checks showed that combining the first pin install with the target publishes before a read-back pin and a durable prepared record). Recovery still admits every observed subset of a multi-ref transaction's effects and any retained native ref lock, because legacy writers and raw Git leave such residue; that admission never authorizes Git to write one. The pin is reachability against GC, not the receipt. The file WAL record remains the authority for intent, phase and attribution, and recovery reconciles target and pin from it (§10).

## 5. Layering and unchanged 4.3-R locks

Reuse Holder-lock's registry, existing paths/ranks, kernel drivers, description borrowing, predecessor domain and fences **unchanged**. No TTL/heartbeat/PID-based authority, inode deletion/recreation or new lock map.

Every mutating request declares a canonical resource set and the **existing** authority required for that set. Normal execution and recovery acquire the same resource authority. Publication of an Event Store stream uses event-seal; branch land uses merge-slot and, where needed, worktree-admin/main-checkout; worktree effects require the applicable admin/main authority and continuous Execution custody. A supervisor recovery lock may serialize the supervisor; it **never** substitutes for these authorities and is not a repository-wide journal mutex. Recovery determines needed resources before acquiring locks. Unsupported or missing authority refuses mutation.

A fresh Rust scope must not hide the Node caller's held locks. Unknown mutation posture fails closed. Holder-lock §9 defines LockScope as a Node object that acquires kernel locks by spawning `fgos internal lock-fd` with the fd in stdio slot 3; it defines no cross-language handle, and none is added.

**LockScope option (a) (owner decision Q1).** For lock-taking operations (commit-scoped, sync, land, worktree, restore), Rust `fgos-git` acquires the ranks it needs (20/40/50) in its **own Rust LockScope**. The Node caller passes, as explicit parameters of the operation, the ranks its scope holds and a descriptor for each held lock the operation relies on (for example the `dispatch-cwd` lease that is the custody token). The Rust scope seeds its rank floor from those held ranks, so the Holder-lock rule "acquire only above every held rank" applies across the N-API boundary exactly as inside one Node scope. A passed descriptor is never trusted as declared: Git verifies it with the three-condition borrower test of holder-lock §5 (named lock, `fstat` `dev:ino` equal to the lock file, `LOCK_EX | LOCK_NB` on that description succeeds) before any effect and again before the irreversible boundary. A held-rank list without a verified descriptor confers no authority, and a set of rank numbers alone is never a lock (no bitmap). The borrower test proves only that the description is usable and exclusive **at the moment of the test**: the model-check probe opened a free lock file, matched name and inode, and `LOCK_EX | LOCK_NB` succeeded because it had just acquired the lock (holder-lock §19 names this case). So a descriptor is accepted only as an acquired handle of the caller's Holder-lock scope in the same process, passed through the combined addon as an opaque handle, never as an fd number or path taken from request input; handles are close-only, a revoked or closed handle is refused, and a successful try-lock never proves continuous custody or a generation handoff (§6). Git children receive a verified lease only through `run_borrowed`. Rust-acquired locks are released by closing their descriptions before the operation returns, so the Node scope never sees a lock it did not take. Publication is unaffected: under seal 58 it never acquires 20/40/50.

## 6. N7 and RUL84

**N7 — ownership and mechanism decided (owner decision Q2).** Execution owns continuous custody from producer start through attempt exit, runner commit, receipt and handoff. Worker exit never releases custody. Git validates it and owns the mutation, not attempt scheduling. Successor producer/reset/sync/remove/commit is refused until current generation handoff is proven. Missing/stale custody fails closed. Read-only workflows require no writable custody.

**Mechanism: the existing `dispatch-cwd` lease, extended across the runner commit.** There is no new Custody entity (design principle 1). The lease Execution already takes on the worktree (rank 30, holder-lock §7, runner RUL101) is no longer released at the end of the assignment; it is held through the runner commit, its receipt and the handoff, and only then released. Contract:

- Execution passes the lease to Git as a held rank plus its descriptor (§5, LockScope option (a)). Git verifies the descriptor by the holder-lock §5 borrower test before any effect and again before the irreversible boundary; a missing, unverifiable or stale lease (wrong `dev:ino`, a description that no longer holds the lock, a worktree whose identity changed) fails closed with a named cause.
- Git children of the operation (commit, hooks) receive the lease through `run_borrowed`, like any other borrowed lock, so a dying Node caller does not free the worktree while git still writes in it.
- Git never acquires, extends or releases the lease; Execution does.
- The change to the run supervisor and to the lease lifetime (closing the gap named in holder-lock §19, "released before the runner commits the Unit's writes") is implementation work owned by the Git plan. This spec states the contract only and does not amend holder-lock §19.
- Predecessor-domain emptiness on Linux/macOS is **not** an existing guarantee (holder-lock §19); that assumption stays currently **false** until the attempt lock exists.

**Successor admission after controller death (M3 / P-CUSTODY fold).** The model check found the shortest violation in two steps, “controller dies → successor acquires free lease”, and reproduced it with a real kernel `flock`: a producer descendant that did not hold the lease description kept writing in the worktree while the successor held the lease. A git child that holds a borrowed description is excluded correctly; a producer process is not, because it holds no copy. So a free `dispatch-cwd` lease is **not** proof of generation handoff. Rule:

- Successor producer, reset, sync, remove or commit on a worktree may start only when the previous custody generation ended by a recorded handoff (lease closed by Execution after the receipt), **or** the previous holder's whole process domain is proven empty by the holder-lock §8 predecessor rule: the custody holder declares the producer's containment domain in the lease's predecessor record before the producer starts, and the successor, after it holds the lease, applies holder-lock §8 steps 2-3 unchanged (kill a non-empty domain at once, then proceed only when Process `domain_is_empty` answers `Empty`; otherwise `held (predecessor-domain-not-empty)`). Execution applies this rule when it acquires the lease for a successor, because it owns custody (Q2); Git still only validates the lease it is handed.
- Where no domain was declared, or the domain kind has no driver that answers `Empty` (today: Linux and macOS until the attempt lock and run-supervisor containment exist; `macos-tree` answers `Unknown`; Linux without a PID namespace is best-effort), admission **fails closed** with `custody-predecessor-unknown`. It never assumes the domain is empty. The worktree and its bytes are preserved and reported by `git-worktree-recovery`; Execution may dispatch the successor in a **new** worktree, so a refused worktree does not stop the item.
- The producer itself never receives the lease description: any copy may `LOCK_UN` (holder-lock §5 rule 6), and a descendant that closes its fds escapes anyway. Inheriting the fd is therefore not the safety mechanism; the domain proof is. Handing the lease to the attempt gate, which runs inside the domain, is the holder-lock §6 lease form and is how the domain proof and the lease coincide once the gate exists.

- **Recorded handoff over a best-effort domain (owner decision 2026-10-19).** After a successful run Execution clears its own predecessor record once the producer's domain is observed empty (holder-lock §8 step 0). For `linux-pgroup` and `macos-tree` that observation cannot see a `setsid` or double-fork escapee, so the handoff does not cover one; on supervised Linux the attempt gate (a subreaper) kills such escapees before the receipt. Refusing to clear best-effort records was rejected: it would strand the worktree after every unconfined Linux or macOS run.

No claim of concurrent commit safety until the lease extension and this admission rule are implemented and V-CUSTODY passes on the implementation. The M3/P-CUSTODY re-check (§19) held only in a finite model and a fixture probe: the old witness is now refused with `custody-predecessor-unknown`.

**RUL84.** The lowest shared **write-scope foundation leaf** owns the grammar/matcher/expansion; Execution owns granted paths; Git enforces them. One Rust implementation and one port; no Node matcher plus a Rust copy. It may initially be a leaf module of the Git package but imports no operations or consumer. Replace `src/runner/dispatch/write-scope.mjs` with a thin facade in the same switch, preserving exports/golden semantics. Packaging (leaf vs independent crate) follows the route decision; it does not give Git ownership of Execution's grant policy.

Preserve grammar: canonicalize declaration trim/dot/separators/consecutive whole `**`; reject absolute/`..`/backslash/NUL/leading colon/embedded `**`. Only `*` within segment and whole-segment `**` glob; all other metacharacters literal; plain entries cover subtree by full segments. Query path bytes are not trimmed; both rename ends are checked. `.fgos` is excluded even by `**`. Generated grants use the same expansion primitive. Byte paths not representable by existing string grammar are refused with lossless encoded path, never lossy-matched.

Honest verification contract (not “nothing unverified is published” via tree equality):

1. Reserve target merge-slot 20; inspect true topology, source/target and target checkout status/index/MERGE_HEAD. Reject foreign state.
2. Create detached operation candidate under admin 40, release admin, construct merge from pinned target. Land conflict aborts candidate only; source and target preserved. Consumer transformations of non-event `.fgos`/decision documents produce declared candidate bytes, not Git-owned state meaning.

4. ## 10. Journal: durability, schema and ownership

**One recovery authority: the file WAL (owner decision Q3).** Location: `<git-common-dir>/fgos/git/operations/<operation-id>/`, outside worktree/runtime scratch, shared by linked worktrees, no config/env override. Operational state for recovering effects under L7, not product event truth. Consumers still publish business history through Event Store. L1/L3 are not changed.

### Driver state root

2026-10-19: the caller-owned trusted driver state root may contain `git-floor-verdict.json`, an optional floor-probe cache, alongside `git-empty-hooks` and temporary probe repositories. It is not WAL or operation evidence. Missing, unreadable, symlinked, inconsistent or differently keyed records cause probing again. The key binds the selected Git binary identity, host package version, probe implementation digest, floor contract, inherited `PATH`, `HOME`/`XDG_CONFIG_HOME`, and config-file identities. System/global paths come from the selected Git's `git var GIT_CONFIG_SYSTEM/GLOBAL` discovery, shared with publication preflight; paths are never guessed from an installation prefix. Any include/includeIf directive disables persistent reuse (including missing or inactive targets), so conditional and included files cannot escape invalidation. The recorded probe names must match the required contract set exactly, without duplicates. A cache write failure only costs a later probe; no setup default, environment switch or doctor prerequisite is introduced.

### Operation evidence

Empty `RemoteFetch`/`RemotePush.targets` is omitted during serialization, preserving historical record digests and previous-digest links. Publication push first advertises the remote tip (one extra network round-trip); its target tuple is keyed by the local publication resource name, with the remote old tip and local next tip. The tuple describes the transfer against that publication resource, not a local ref CAS. Non-event transfers require complete per-target details.

Do **not** run a dual-write protocol. Pins under `refs/fgos/git-operations/<id>/` are reachability only. The pin is written before the target CAS and is not the receipt; a multi-ref transaction is never assumed crash-atomic (§4). E1 decides whether git `core.fsync=objects,reference` would suffice for a **future** ref-only journal (B); the durability proof already showed it is insufficient on its own, because Git does not fsync directories. Failed E1 does not license two authorities “until then.” B itself says failed E1 reopens A.

**C2.** Operation records are **evidence, never lock authority**. Each mutation and its recovery identify the existing serialization resource and pass its live opaque scope/handle. No operation-directory creation, PID, TTL or journal generation constitutes ownership. Same-id requests have one immutable request digest and one transition writer under that context. Concurrent identical request returns busy or the established receipt; different request is refused. The same id cannot be used on two disjoint serialization resources (P-WAL-ID).

**The one-transition-writer primitive (P-WAL-ID fold).** The model check could not test P-WAL-ID because no primitive was named; without one, its negative control reached two transition writers in two steps, and the Refs row of the R30 table takes no registry lock. The primitive is the **no-overwrite install of the next numbered record**; it is evidence ordering, not lock authority (C2 above is unchanged):

1. Id binding: record 0 (Intent, carrying request digest and canonical resource set) is installed no-overwrite. A requester that loses the install reads the installed record 0: same digest returns busy or the established receipt; a different digest or resource set is refused (`operation-id-conflict`). That is also the cross-resource rule.
2. Transition writer: the writer of transition *n* is the one whose record *n* install succeeded. A writer that loses the install of record *n* stops before any effect of that transition, re-reads the chain and returns busy, or continues only as a recovery reader.
3. Effects: only the installer of the immediately preceding record, or a recoverer that holds the operation's own resource authority (§5) and has installed its own next record, performs the next effect. Where an operation has no registry lock (Publication pins and CAS, Remote), its effect must itself be an exact-old CAS. Exact-old CAS alone does **not** make a repeat harmless: after an ABA a second CAS from the same expected value wins again (the M1 and P-WAL-ID re-checks both reached two publications for one operation this way). Rule 4 therefore applies to every effect, with or without a registry lock. An operation kind with neither a registry lock nor an exact-old effect is not exposed through an operation id until it has one. RepositoryConfig.ensureFetchMapping now uses repo-config 80 and native config.lock.
4. **TargetAttempt: no blind re-effect.** Before an irreversible effect (the target CAS of a Land or PublicationCas, a ref delete, a worktree destroy or move, a restore), its performer installs a durable `TargetAttempt` record carrying `priorTargetAttempt: none` and the expected and next values; the effect runs only after that install succeeded. Its outcome (observed success, observed loss with the actual tip) is the next record. A chain that holds a TargetAttempt without an outcome means the outcome is unknown: no recoverer reissues that effect under this operation id, whatever it observes; for a CAS, `ref == expected` is not evidence that the CAS never ran (ABA), and `ref == next` is effect observed, never attribution. It returns `recovery-required` (or completes a receipt as `effectObservedOnly` when the state reached next) and preserves WAL, pins and snapshots. A recoverer may perform the effect only by itself winning the no-overwrite install of the operation's first TargetAttempt record; a valid chain without any TargetAttempt is the WAL evidence that no prior attempt happened. A crash after the TargetAttempt install and before the effect is accepted as unknown, which keeps the effect at most once. An observed loss ends that operation; a retry against the new tip is a new operation id, because the id binds the expected values (§2), and that is how Event Store's §10 retry reaches the port. A recoverer that holds the resource authority also observes the actual effect state named by the payload's recovery observations before deciding; authority, a new transition record, equality, reflog absence, custody or a verification digest is never evidence that an effect did not happen.

4a. **Publication supersession (amendment A1, 2026-10-18).** For a PublicationCas only, a chain that ends at a TargetAttempt without an outcome does not block a **different** operation id on the same ref: a caller holding that ref's publication authority (§5: the stream's event-seal 58, held by the Event Store of that stream's own origin, the only writer of that ref per Event Store §10's chain invariant) may start a new PublicationCas whose expected value is the tip it reads. The old operation is closed with the terminal outcome `superseded` only when all of these hold, observed under that same authority:
   1. **Later winning receipt.** A later PublicationCas of the same ref has a durable receipt whose attribution is `thisInvocationWonCas`, and that receipt's expected value equals the old operation's expected or next value.
   2. **Same authority.** The later operation's Intent carries the same repository identity, the same canonical resource set (that one ref) and the same `authorityBinding` (the same stream writer under the same event-seal) as the old one. A later operation under any other authority (another stream, a legacy-import grant, a mirror fetch, a different repository identity) never supersedes.
   3. **Old domain proven gone.** No process of the old performer can still effect its CAS: no retained native lock artifact of that ref’s backend is observed (`<ref>.lock` for `files`; the shared `tables.list.lock` for `reftable`, which a retained one blocks for every ref until the §11 exact-owned quarantine), and the old performer's process domain is proven empty by the holder-lock §8 predecessor rule, or the old performer's git children ran borrowed under the old event-seal hold (§5 `run_borrowed`) so that the later event-seal acquire through holder-lock, completing the §8/§8.1 predecessor admission, shows no live holder of it (a raw kernel acquire alone is not proof on Windows, where an orphan child can outlive the handle; the model check found a 4-step counterexample). `containment-unproven`, an unknown or unlistable domain, or a live holder keeps the old operation `recovery-required`. **Required so that condition 3 is decidable:** every git child of a PublicationCas runs borrowed under the caller’s event-seal hold (§5 `run_borrowed`), with hooks disabled (§4 C1), so a Publication git child starts no descendant outside that borrow; an event-seal acquire through holder-lock that completes the §8/§8.1 predecessor admission therefore proves the old performer’s domain gone; on Linux and macOS the borrowed description makes that admission immediate once every borrowing child has exited. A Publication route that cannot lend the event-seal to its git children refuses before Intent (`publication-borrow-unavailable`) instead of running unborrowed.

   The `superseded` record is the old chain's outcome record after its TargetAttempt, installed by the no-overwrite primitive of rules 1-2 (one transition writer: a recoverer of the old id that loses the install stops at `EEXIST`; one that wins first leaves the chain under rule 4 and the supersession attempt stops). It names the later operation id and its receipt digest. The old operation's attribution is `effectObservedOnly` when the later expected value equals the old next value, and `uncertain` otherwise; it is never `thisInvocationWonCas`. Supersession is record-only: the old CAS is never replayed, reissued or re-attempted under any id, and the old id stays bound (rule 1) and is never reused. Tip equality without the later durable receipt is never used. A superseded chain is terminal: it is not pending or unresolved for startup checks, doctor's pending count or C5 (§12), its pin may be released, and compaction treats it like any terminal chain. Every other operation kind keeps rule 4 unchanged.

4b. **Abandoned before attempt (clarified 2026-10-18 with the Git phase 01 review).** A chain that ends at Intent or Prepared has no TargetAttempt, so by rule 4 no target effect can have happened. Read-only candidate checks and quiescent admission run before Intent, and no wait separates Prepared from TargetAttempt. Under the same publication authority, with the old performer’s domain proven gone as in rule 4a condition 3, such a chain is closed record-only with the terminal outcome `abandonedBeforeAttempt` (its pin, if any, is reconciled per the recovery table) and becomes compactable; a later operation id on the same ref is never blocked by it. An operation directory that holds no installed record (empty or temporary files only) is not an Intent and is removed under the same authority. A winning PublicationCas sweeps pending same-ref chains under its authority by rules 4a and 4b before returning; a sweep that cannot decide keeps the evidence and reports it.

4c. **Config approved (amended 2026-10-18 with the Event Store phase 05 review).** When every requested mapping already exists, ensureFetchMapping re-approves the observed remote URL by recording ConfigChange Intent followed directly by the terminal outcome `configApproved`. The Intent retains URL and refspec provenance; no target effect, TargetAttempt or Transfer occurs. `configApproved` is valid only for ConfigChange before any TargetAttempt; the operation id stays bound (rule 1). fetchMappingProvenance recognizes this approval alongside successful config installation. No other rule changes.

5. Directory creation, PID, TTL and record age never decide anything in this protocol.

Versioned immutable numbered records carry canonical digest/predecessor digest; write exclusive temp with every byte written and checked (a short write or `EFBIG` leaves a partial temp, which is never a record), fsync file, atomically install **without overwrite**, fsync directory **and parent-dir durability**. Ordinary `rename` overwrites an existing target (the durability proof replaced `old-record` this way), so the install uses `renameat2(RENAME_NOREPLACE)`, or `link(temp, final)` followed by `unlink(temp)` with recovery treating a surviving temp name as an orphan, or the platform's audited no-replace equivalent. Newly created ancestor directories (the operation directory itself) are fsynced, and their parent, before the first record is acknowledged. Parse/hash/version/chain error is corrupt, never empty.

2026-10-19: replaying an already installed Intent syncs its operation directory and WAL operations parent before returning the existing binding, including when a previous creator stopped before syncing either directory. The intact-candidate connectivity fast path trusts history reachable from the expected published tip and walks only the candidate's new reachability, as Git's connectivity check does; failure falls back to the complete type/history checks.

**Directory durability is Git's own job.** Git 2.53.0 never fsynced a parent directory in any traced primitive, even with `core.fsync=all` (the durability proof traced `hash-object`, `commit-tree`, `update-ref --stdin` and `commit`: file fsync then rename, no directory fd). So `core.fsync` is a backend input, never evidence of `stableMedia` by itself, and `fgos-git` itself fsyncs, in this order: every loose-object fan-out directory and `objects/` it wrote into before the WAL `prepared` record and before any ref that references those objects; the directory chain of each ref it created or changed (including new `refs/fgos/...` directories, and `packed-refs`' directory) after the CAS and before the receipt; the WAL directories as above. Until E1 proves a filesystem/backend profile, the receipt advertises `durability.processCrash` only.

Child death/timeout around CAS is unknown until read-back. Startup mutation checks pending entries touching its resources; **bounded scan returning incomplete knowledge is not clearance to mutate** (C4). A pending entry blocks a new mutation of the same resource and always blocks any replay or re-attempt of its own operation id, with one exception: a pending PublicationCas does not block a different operation id on the same ref that holds the same publication authority; §10 rule 4a resolves the pending one. Doctor is read-only. Explicit repair/supervisor uses the same crate/locks; no separate Node repair core.

**What `git-mutation-one-door` and V-GATE detect (source-guard fold).** A Git write is any child process whose resolved binary is `git` or a repository hook, with any argv, unless it runs through the private CLI driver of `fgos-git`. The classification proof found nine real code shapes that a scan for literal `execFile('git', ['<write verb>', …])` misses: argv injected through a callback (verb and spawn in different files), spawn through a non-`child_process` facade (`runBorrowed`), argv held in a variable or mutated after construction, global options before the verb (`-C`, `-c`, `--git-dir`, spread prefixes), wrappers that prepend the verb, a Rust `Command::new` whose binary is a variable, shell strings, non-git spawns that change Git state (direct hook replay, skill text telling an agent to run Git), and read verbs that write (`status` refreshing the index). The guard has two parts, both required: (a) a static scan of every spawn site (`child_process`, `runBorrowed`, `Command::new`, `execSync`/shell) whose binary can be `git` by data flow, including variables and wrappers, with callers of a wrapper counted; (b) a runtime check in the test suite, following the existing `test/state/hot-lock-known-exec-sites.test.mjs` pattern, that records every spawn of `git` or a hook outside the driver and fails on any not on the named allowlist. Shipped skill text is scanned for instructions to run Git writes. Inspect runs with optional locks off (§3), so a read is never a write.
