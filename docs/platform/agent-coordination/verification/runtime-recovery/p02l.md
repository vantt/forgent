   - **1 HIGH**: a stale/superseded controller could re-settle an already-settled Run, overwriting it with stale data.
   - **Structural**: `reconcileCliSpawnRun` (the actual recovery entry point) had zero callers anywhere in `src/` or `bin/` — the whole recovery path was dead code.
   - Plus 7 MEDIUM and several LOW findings.
   - This round needed a continuation session (`p02l-b`) after the original hit its 6-hour wall-time budget, and a cross-session `contextRefs` reference attempt correctly failed closed (a `grantedContextRefs` entry must resolve to an Assignment owned by the SAME `coordinationId` — findings from an earlier session must be inlined as text, not referenced).

## Process findings (added to P00/P01's lists)

- **A per-executor absolute ceiling (`.fgos/config.json`'s global `timeoutMs: 2100000` = 35 minutes) is a real, separate bound from `aggregateBounds.wallTimeMs`** — it is not overridable per coordination request (the schema has no field for it). A recheck task broad enough to require a full suite sweep plus multiple real repro scripts on a large cell can exceed it even when the session's own wall-time budget is nowhere near exhausted. When this happens, split the task into a narrower, explicitly time-boxed one (name the exact 1-2 tests/repros that matter most) rather than repeating the same broad ask.
- **`grantedContextRefs`/`contextRefs` cannot cross coordination sessions.** `authorizeDeclaredOperation` refuses a ref that resolves to an Assignment not owned by the current `coordinationId`. A continuation session inheriting findings from an earlier (wall-time-exhausted) session must inline the needed detail as objective text, not try to reference the old session's assignment ids.
- **A session can legitimately auto-close to `status: "completed"` once every required actor's slot has one clean recorded completion** — this happened for both `p02l-b` and `p02l-c` here, in contrast to P00/P01/P04 where an earlier messy multi-attempt history (mixing failed and successful attempts for the same role) appears to have prevented it. Once a session reports `completed`, no further `authorize`/`operation`/`disposition` step can be dispatched into it (refused: "session is not active") — treat that as the cell's own closure record rather than trying to force an explicit close disposition.
- **A self-reported "18/18, 484/484, PASS" from a doer should be treated as a claim, not evidence** — this cell is the starkest example yet in this track: the claim was comprehensively false, and both independent reviewer and red-team caught it immediately with concrete reproductions.
