**Critique — vnflow (architecture critic)**

**Attack 1 — on the System Shaper's primary recommendation (DAG dependency). Decision-changing if it lands.**
The System Shaper's core structural fix is to pull Intraday's EOD lake read into Intraday's DAG so that `AssetRunner`'s dependency blocking will manage staleness and decode failures. This assumes Intraday and EOD share a single temporal schedule where standard DAG blocking is valid. They do not. EOD runs after market close (16:30); Intraday polling runs during the session (until 15:00). If Intraday's DAG declares a strict upstream dependency on EOD's output for the *same* `run_date`, Intraday will permanently deadlock waiting for an EOD run that won't happen for hours. Intraday *must* read a previous session's data (hence the 7-day lookback). Therefore, the read cannot be resolved by standard same-date `AssetRunner` DAG edges. The System Shaper's primary mechanism is structurally incompatible with the domain's timing.
*What would settle it:* Check the domain scheduling rules. If EOD strictly follows Intraday chronologically, `AssetRunner`'s same-date dependency resolution will paralyze the Intraday pipeline.

**Attack 2 — on the shared alert cap coupling (Alternative Shaper & Constraint Advocate). Weakens both proposals.**
Both the Alternative Shaper and Constraint Advocate cite the shared alert dataset as a critical, silent runtime coupling, assuming EOD alerts bleed into and exhaust Intraday's daily cap. The Alternative Shaper even anchors their "no-build path" trigger on this ("revisit... the first time a critical Intraday alert is swallowed... because the EOD run exhausted the shared cap").
This contradicts the temporal reality of the system. Because Intraday stops polling at 15:00 and EOD runs at 16:30, EOD runs *after* Intraday finishes. EOD alerts cannot exhaust Intraday's cap during normal operations because Intraday consumes its capacity before EOD even starts. The coupling they are guarding against only occurs if someone manually triggers an EOD backfill *during* trading hours. The chronic production risk they are solving is a phantom.
*What would settle it:* Read `src/vnflow/application/signals/alert_dispatch_intraday.py` (lines 17-23), which explicitly documents this exact timing separation and confirms the cap only overlaps during rare manual intraday EOD runs.

**Attack 3 — the suspicious unanimity on "don't restructure". Weakens the packet.**
All three proposals conclude that the pipeline abstractions shouldn't change, pivoting entirely to fixing data dependencies and schemas. This looks like independent convergence, but it is actually the shared scout report anchoring them all. The scout report pointed to four specific data/schema seams, and the shapers simply solved those seams.
However, the user's prompt is that *"evolution* is becoming difficult," not operations. The upcoming 2026-07-05 audit requires porting ATR entry planning and RVOL scoring into Intraday. If evolution is painful, it is likely because of the friction of mapping these domain features across two different contexts (like the breadth gate bypass). All three shapers essentially ignored the forward-looking evolution pressure to fix the operational bugs highlighted by the scout, silently reframing "evolution is difficult" into "the data boundaries are unsafe."
*What would settle it:* Review the commit history of the sole maintainer to see if the recent friction was caused by invisible data pipeline breaks or by the sheer cognitive overhead of threading new domain logic across the two execution paths.

**Attack 4 — on the falsification criteria (System and Alternative Shapers).**
The System Shaper's FC #3 ("If the maintainer's actual pain is about readability...") and the Alternative Shaper's FC #3 ("If Intraday and EOD are destined to merge...") are unfalsifiable theater. One requires telepathy with the sole maintainer about their internal emotional state, and the other requires clairvoyance about future business pivots. Neither can be checked by looking at code, logs, or current evidence. They are opinions dressed as rigorous criteria.
*What would settle it:* Discard them. A true falsification criterion must be observable in the present system state.

**Attack 5 — on the Constraint Advocate's severity/timing estimate. Does not change recommendation.**
The Constraint Advocate estimates "4-7 focused maintainer days" to deliver these four explicit contracts. This is an asserted number designed to make the proposal look serious. The fixes themselves — adding a string discriminator column, surfacing a bypassed argument in `evaluate_buy_gate`, and adjusting a polars read in `signal_engine_intraday_loaders.py` — touch a handful of lines in three well-defined files. For the sole maintainer of a 1-month-old codebase, this is a 1-day task, not a week-long expedition.
*What would settle it:* Count the lines of code required for the proposed changes.

**Attack that failed, reported.**
I attacked the Constraint Advocate's claim (Constraint #1) that "Runner checks execute AFTER the asset function, so a post-execution check alone cannot protect a notification already sent." I expected the `AssetRunner` might have a pre-flight data quality step that could catch the missing breadth gate before execution. The code in `src/vnflow/application/asset_runner.py` (`_materialize`) proves the advocate right: it explicitly executes `fn_result = spec.fn(ctx)` and only then evaluates `check_results = self._run_checks(...)`. Since the asset function itself dispatches the alert, a data quality check on the pipeline cannot intercept the Telegram message. The structural vulnerability is real, and I concede the attack.
