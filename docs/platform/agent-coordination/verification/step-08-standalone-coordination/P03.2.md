## Coordinator's independent source review (before dispatching Reviewer)

Read the 3 new lock-held `store.mjs` checks (`maxAssignmentsForSession`,
`maxRoundsForSession`, `maxConcurrencyForSession`) and confirmed: all
three are positioned inside `withEventsLock`, strictly after the
`taskClaimPath` resume-check (which returns/self-heals early -- so a
resume is never double-counted against any of them) and strictly before
`claimAssignmentId(...)` (the actual write). `manifest` is read fresh at
the very top of the SAME lock acquisition (`readManifestRaw(manifestPath)`,
first line of the `withEventsLock` callback) -- not a stale/earlier read.
`maxConcurrencyForSession` additionally takes its own fresh
`readEvents(eventsPath)` inside the same critical section. This matches
P03.1's own established, Red-Team-verified pattern exactly.

Read `assertWithinWallTimeBudget`/`assertWithinTaskDepth`
(session-engine.mjs) and confirmed the Doer's own concurrency-safety
reasoning holds: wall-time is a pure function of real time
(`Date.now() - manifest.createdAt`) with no shared mutable counter to
race; task-depth walks a REAL, immutable, already-on-disk
`parentAssignmentId` chain (never a caller-asserted number), with a
cycle guard. Neither needs lock-held enforcement -- both are legitimately
pre-lock and authoritative by construction, not merely advisory (unlike
P03.1's own pre-lock `maxRounds` fast-fail, which its own Red-Team proved
WAS merely advisory for a genuinely shared, racing counter).

Read `recordConsultDisposition`'s new foreign-evidence/actor-impersonation
guard in full: requires `manifest.definitionRef` (a deliberate, documented
scope tightening -- previously worked for ANY session), then requires a
REAL declared topology edge (`edge.from === requesterActorId && edge.to
=== consultantActorId`) between the two actors, using the on-disk
`assignment-created` event's own recorded `actorId` for each Assignment
(never a caller-asserted actor identity). Without this fix, a caller could
disposition ANY already-linked, already-a-session-member Assignment
(including, degenerate case, the requester's own) as if it were the
specialist's settled advice -- confirmed by reading the code BEFORE this
fix (P03.1's version) had no such check at all.

## Review

Independent Reviewer dispatched with all 3 flagged items plus a
mandatory empirical stress test on `maxConcurrencyForSession`. Result:
clean across every item.

### `maxConcurrencyForSession` empirical stress test: 0/40 violations across real cross-process racing

Mirrored P03.1's own Red-Team methodology exactly (genuinely separate
`node` OS processes via `child_process.spawn`, synchronized to a shared
busy-spin target timestamp, ground truth read from `events.jsonl`/
`session.json` on disk after every trial, never process exit codes
alone): cap=2/5-callers (15 trials), cap=1/8-callers (15 trials,
most aggressive pressure tried), cap=3/3-callers-at-boundary (10 trials,
confirms no false-rejection at the exact cap). **0/40 violations total.**
Unlike P03.1's `maxRounds` bug, this check was correctly positioned
inside the lock from the start -- no fix needed.

### Item 2 (recordConsultDisposition's new definitionRef requirement): SAFE, confirmed

Reviewer diffed the P03.1-committed version of the function directly
(`git show 8fc3130a:...`) and confirmed it had NO topology/definitionRef
check at all previously -- every existing call site (in both P03.1's own
tests and this cell's) exclusively targets a declared-protocol session;
the function's own module header establishes it as declared-path-only by
design since its first commit. No legitimate non-declared caller exists
anywhere in this codebase for this tightening to break.

### Item 3 (R7 comparator): non-vacuous, correctly scoped

Confirmed the comparator strips only legitimately-expected-to-differ
fields (ids, timestamps, provenance scope labels, role vocabulary) and
keeps exactly the confidence-rule fields R7 requires identical; the test
explicitly asserts the STRIPPED fields genuinely differ between modes
before asserting the KEPT fields match -- proving the pass isn't
coincidental/vacuous.

### Live-proof spot-check: genuine

Cross-checked the narrative log against raw `claude-step2-request-live.stdout.log`
(real persisted RunResult JSON matches verbatim) and
`coord2-final-{session.json,events.jsonl}` (event count/shape matches the
"9 events, no duplicates" claim exactly). The Attempt-3 self-inflicted
false-fail is kept as honest, traced evidence, not hidden.

### assertWithinTaskDepth off-by-one: correct, no bug

Hand-traced against the R5 test's own `maxTaskDepth: 2` fixture
(request-consult depth 1, provide-consult depth 2 both succeed,
disposition at depth 3 correctly rejected) -- matches.

**Coordinator disposition: cell CLOSEABLE.** Given this is the second
concurrency-sensitive extension to this exact file in two consecutive
cells, and given the first (P03.1) genuinely needed an empirical fix,
this cell's clean 0/40 empirical result (not just a clean code read) is
the correct bar to accept against -- matches this track's own established
practice of never accepting a concurrency claim on code-reading alone
once a real instance of this bug class has been found in a file.
