1. **Governance bypass risk.** `assignment-policy.mjs:251`'s

### HIGH — `findDuplicateOverrideFlag()` silently misses a duplicate whose second occurrence is the very last argv token

The Fix Evidence section describes the helper as counting "only an
occurrence that has a following value string." That is not what the code
does. The actual loop:

```js
for (let i = 0; i < rest.length - 1; i += 1) {
  if (rest[i] === name) count += 1;
}
```

excludes exactly one index — `rest.length - 1`, the literal last element of
`rest` — regardless of whether that occurrence "has a following value."
Reproduced live: with `--cwd` placed *before* the flags under test (so the
duplicate genuinely lands last in `rest`, not shielded by a trailing
`--cwd`), `execute --contract <file> --executor named_executor --executor`
(second `--executor` bare, at the very end) exits **0** and dispatches
successfully through `named_executor` — no rejection, no stderr message.
Contrast with the same duplicate placed mid-array (the Fixer's own two new
tests, and my own control case with a value after both `--executor`
occurrences): correctly rejected. The practical blast radius is narrow
(`flagValue`'s `indexOf` still picks the first occurrence, so the *wrong*
executor is never silently substituted), but this is a real, live,
un-guarded gap against R9's literal text ("reject duplicate ... flags ...
before launch") on both doors, and the Fix Evidence's own description of the
mechanism is inaccurate — it describes value-aware counting the
implementation never performs.

Evidence: `redteam-probe.mjs` "ATTACK (a)" — exit code 0, full RunResult
JSON printed, `.fgos/assignments/` gained a real directory for a request
that R9 requires to be rejected before launch.

Smallest fix direction: iterate the full `rest` array (drop the `- 1`
bound) and count occurrences by name alone, exactly as `flagValue`'s
`indexOf` already treats flag identity — position in the array should never
change whether a flag counts as "present."

### MEDIUM — the same helper produces a false-positive rejection when a flag's own value literally equals another flag's name string

`findDuplicateOverrideFlag()` scans raw token equality with no concept of
"this token is a value, not a flag name." Reproduced live:
`--contract <file> --tier --executor --executor named_executor` (a
malformed `--tier` with no value, immediately followed by a genuine,
single, well-formed `--executor named_executor`) is rejected with
`duplicate flag "--executor" -- pass it at most once before launch`, even
though `--executor` was only ever typed once as an actual flag — the first
occurrence is the accidental *value* consumed by `--tier`'s missing
argument, not a second `--executor` invocation. This confirms the
red-team's original concern: `flagValue()` and `findDuplicateOverrideFlag()`
use different, disagreeing notions of "what counts as a flag occurrence" —
`flagValue` never inspects raw token position for this, but the duplicate
checker does pure string-equality across the whole array regardless of
role. Narrow (requires a value that happens to collide with a real flag
name), but it is a genuine robustness gap in the exact validation logic R9
required.

Evidence: `redteam-probe.mjs` "ATTACK (c)" — exit code 1, the literal
false-positive stderr message.

### MEDIUM — a third, previously-unflagged `deriveProviderFamily`-family bug, live-reproduced in the glm-cli proof log's own quoted evidence

The Reviewer's R11 section quotes the glm-cli proof log's stderr banner
verbatim: `provider=claude model=z-ai/glm-5.2 tier=lightweight` — but never
explains why `provider` reads `claude` when `.fgos/config.json`'s glm-cli
entry declares `providerModel: "z-ai"` and the same run's own
`dispatch-plan.json` correctly records `governance.providerFamily: "z-ai"`.
Traced the root cause: `src/runner/dispatch/transport.mjs:163`
(`resolveExecutorCommand`'s return) computes this display/RunResult
`provider` field independently of `governance.providerFamily`:

```js
provider: executor.provider ?? executor.command,
```

`executor.provider` reads a config field named `provider` — distinct from
`providerModel`, the field every real executor entry in this repo actually
uses. Confirmed via direct read of `.fgos/config.json`: **zero of the 12
registered executors set `provider`** — it is dead schema. So this
expression always falls through to `executor.command`, the literal
resolved binary name. For any executor whose real command happens to be a
Claude CLI command but whose real provider family (`providerModel`) is
something else — `glm-cli` is the live, currently-configured example — the
banner and RunResult misreport the provider as `claude`, even though the
correctly-derived value (`deriveProviderFamily(executorEntry,
executor.command)`, resolve.mjs:429) is already sitting on the very same
`executor.governance.providerFamily` a few lines above in the same object,
unused by this line. This is a third, distinct call site in the same
provider-derivation bug family already flagged HIGH above (which covered
only `assignment-policy.mjs:201` vs `resolve.mjs:429`) — not previously
enumerated in either the Doer's or Reviewer's `deriveProviderFamily`
call-site grep (both counted exactly 2 call sites; there are 2 call sites
of `deriveProviderFamily` itself, but this is a *third, independent* wrong
derivation feeding the same class of governance-facing field from a
different, unrelated code path).

Blast radius, checked directly (not assumed): confined to (a) the
human-facing stderr banner printed on every dispatch, and (b) the bare
`dispatch execute <executorId>` third door's own top-level RunResult
`provider`/`command` fields (via `buildDispatchResult`,
`result-ladder.mjs:41`). Traced `assignment-runner.mjs`'s handling of
`rawResult` (used by both R9 doors, `--assignment` and `--contract`): it
never reads or forwards `rawResult.provider`/`rawResult.command` into the
persisted `result.json` — confirmed directly against a real result.json on
disk (no top-level `provider`/`command` keys present). So R11's specific
proof-required RunResult fields for the two R9 doors are **not** corrupted
by this bug, and it is not a P00.3-scope regression (`transport.mjs` is
absent from this cell's diff, confirmed via `git diff --stat`). It is real,
live, and currently misleads any operator reading the dispatch banner for
`glm-cli` (and would misreport the third door's own RunResult for the same
executor) — worth folding into the same P00.4 follow-up as the already-

(provider-family derivation bypassing `governance.providerFamily`) and the
smallest fix is the same shape: read `executor.governance.providerFamily`
here instead of the dead `executor.provider` field.

**2026-09-01 — Red-Team round-2 fixes (HIGH #1 off-by-one, MEDIUM #2 false
positive) — fixed.**

Both findings lived in the same `findDuplicateOverrideFlag()` helper
(`src/runner/dispatch/cli.mjs`, immediately after the `flagValue` closure).
The prior version's loop bound (`i < rest.length - 1`) skipped the last
index of `rest` entirely (HIGH #1: a trailing bare duplicate went
unrejected), and its raw string-equality scan had no notion of "this
position is a flag name" vs. "this position is a flag's value" (MEDIUM #2:
a flag name that only appeared as a preceding flag's dangling value slot
was miscounted as a real occurrence).

Replaced the whole helper with a single left-to-right walk over `rest` that
mirrors `flagValue()`'s own convention — the token immediately after a
recognized flag name is that flag's value and is never itself re-examined
as a flag position:

```js
const findDuplicateOverrideFlag = () => {
  const flagNames = new Set(['--executor', '--model', '--tier']);
  const counts = new Map();
  let i = 0;
  while (i < rest.length) {
    if (flagNames.has(rest[i])) {
      counts.set(rest[i], (counts.get(rest[i]) ?? 0) + 1);
      i += 2;
    } else {
      i += 1;
    }
  }
  for (const name of ['--executor', '--model', '--tier']) {
    if ((counts.get(name) ?? 0) > 1) return name;
  }
  return null;
};
```

This fixes both findings in one pass: every index of `rest` is now
reachable (no `- 1` bound), so a trailing bare duplicate counts; and a
token is only ever counted as "an occurrence of flag X" when it is read at
a flag position, not consumed as a preceding flag's value slot, so the
duplicate-checker and `flagValue()` never disagree about what counts as a
flag occurrence. Both doors (`--assignment` and `--contract`) call the same
helper, unchanged.
