## R8: STOP GATE #4 (objective, plan-named, independently confirmed)

**Plan's own stop gate #4**: "a required live CLI executor/provider is
absent, unconfigured, lacks the exact required tier, or fails

### Root cause (independently verified by the Coordinator, not just the Doer's report)

`resolveAssignmentDispatchPolicy` (`src/runner/dispatch/assignment-policy.mjs:92`):
```js
let effectiveTier = opPolicy.minTier || 'standard';
```
This is an UNCONDITIONAL floor -- `cliOverride`/`work.tier`/governance can
only RAISE it (`resolveStrongerTier`), never lower it below `'standard'`.
`opPolicy` is `assignment.policy`. Traced `buildInlineAssignment`
(`src/runner/dispatch/assignment.mjs`, ~line 481 onward): `contract.policy`
is populated ONLY when a domain harness seam fires
(`...(harnessPolicy ? { policy: harnessPolicy } : {})`), which itself
requires a resolvable `domain` off a Work object with a `.stage` --
standalone CoordinationSession dispatch (agent-led AND declared, this
entire track's whole subject) never attaches a Work/stage, so
`harnessSeam` never fires, so `contract.policy` (and therefore
`assignment.policy`/`opPolicy`) is NEVER populated for ANY coordination
dispatch, ever. Confirmed independently: `grep -n "policy" src/runner/dispatch/execution-contract.mjs`
and `INLINE_ASSIGNMENT_PARAM_WHITELIST` in `assignment.mjs` both show no
`policy` field exists on the inline-contract surface at all.

**Consequence**: every coordination dispatch (agent-led or declared,
Phase 01 through this cell) has always resolved to AT LEAST `'standard'`
tier, unconditionally. The real `.fgos/config.json` only configures
`lightweight` for `gemini`/`openai-codex`/`z-ai` (confirmed, unchanged
since P00.4/P03.2's own discovery of this same config shape) -- meaning
NONE of them can ever satisfy the unavoidable `'standard'` floor. This
reframes P00.3's and P03.2's own prior "codex-cli/glm-cli live-executor
timeout / config-tier gap" findings: the real root cause was always this
SAME architectural floor, not merely an incomplete `modelPolicies`
config (a config change alone cannot fix this -- the floor is
unconditional in code, not a missing config value).

## P04.2b — stop gate resolution (maintainer-approved fix)

The maintainer reviewed the stop-gate report above and explicitly
authorized the narrow fix direction already recorded: add exactly one
new legal field, `contract.policy = {minTier}`, to the inline-contract

### Fix

- `src/runner/dispatch/execution-contract.mjs`: `'policy'` added to
  `ACCEPTED_CONTRACT_FIELDS`; new `ACCEPTED_POLICY_FIELDS = new
  Set(['minTier'])`; a validation block requires `contract.policy` (when
  present) to be a plain object carrying EXACTLY `minTier`, one of
  `MODEL_POLICY_TIERS` -- enforced via the existing
  `assertOnlyAcceptedFields` gate (rejects `preferExecutor`/
  `preferPersona`/`model`/`visibility`/`fallbackExecutors` individually).
- `src/runner/dispatch/assignment.mjs`: `buildInlineAssignment` merges
  the domain harness's own `policy` (if any) with `contract.policy.minTier`
  via `resolveStrongerTier` (reused, never reimplemented) -- never-weaken,
  matching `resolveAssignmentDispatchPolicy`'s own invariant; every other
  harness field passes through unchanged.
- `src/runner/coordination/session-engine.mjs`: `buildReadOnlyContract`
  gained an optional `minTier` param (absent for every pre-existing
  caller, byte-identical default). `dispatchDeclaredOperation` threads
  the composed policy stack's `minTier` through this NEW channel only
  when it resolves STRICTLY BELOW `'standard'` -- the Fixer found and
  fixed a genuine provenance regression here during this cell's own
  work: threading it unconditionally collapses
  `resolveAssignmentDispatchPolicy`'s strict `>` tie-check between
  `opPolicy.minTier` and `cliOverride.minTier`, misattributing
  provenance to the wrong scope. At-or-above-`'standard'` continues to
  reach the resolver via the pre-existing `cliOverride.minTier` channel,
  unaffected.

requiring EMPIRICAL verification, not code-reading alone:

1. **Prototype-pollution safety**: SAFE, empirically confirmed. A genuine

   form) is cleanly REJECTED by `assertOnlyAcceptedFields`'s

   \"__proto__\""`) before `minTier` is ever inspected. Confirmed this
   differs structurally from the earlier `schema.mjs`/`baseStepMap` bug
   (P02.1) that motivated the check: that bug was dynamic bracket-key
   assignment onto a bare `{}` (a write-time hazard); this path is
   read-then-whitelist-check (a safe shape). `Object.freeze({

   this shape (`CopyDataProperties`, not `[[Set]]`) -- moot anyway since
   validation runs first and throws before this line is ever reached
   with malicious input.
2. **Governance independence**: CONFIRMED, traced end to end through
   `resolveAssignmentDispatchPolicy`'s real body. Executor/provider
   resolution (governance-gated) is computed entirely independently of
   `effectiveTier`/`opPolicy.minTier`; tier only selects which MODEL to
   use for an already-fixed provider. Since `ACCEPTED_POLICY_FIELDS`
   permits only `minTier` (never `preferExecutor`), this new channel
   structurally cannot influence which executor/provider is selected,
   so a lower reachable tier can never let a governance-blocked
   candidate through.
3. **Above-'standard' declared-operation tier still works**: PROVEN by
