## Review

### MEDIUM — `buildCandidateInventory`'s defensive invariant crashes the whole planner for a legal agentType-only executor shape

`resolveExecutorConfig` (resolve.mjs) has a third command-resolution
fallback the module's own `resolvedCommand` computation never replicates:
an `agentType`-only executor entry (no own `command`/`invocations`)
resolves via `buildAgentTypeExecutor(cfg.executor, effectiveAgentType)`,
whose command is the GLOBAL `cfg.executor.command` -- not `'claude'`.
`buildCandidateInventory` passes `resolvedCommand: undefined` to
`deriveProviderFamily` for this shape, which defaults to `'claude'`,
disagreeing with `resolveExecutorConfig`'s correctly-derived family
whenever the global executor's command isn't a Claude CLI command. The
thrown `CohortPlanningError` is not a `RunnerConfigError`, so the
surrounding try/catch re-throws it uncaught -- this aborts the ENTIRE
inventory build, not just one candidate, the moment any single
`agentType`-only entry exists alongside a non-Claude global executor.

**Coordinator's own independent reproduction** (not trusting the
Reviewer's claim alone):
```
buildCandidateInventory({ executor: { command: 'pi', ... }, executors: { 'agent-x': { kind: 'agent', agentType: 'some-agent' } }, ... })
→ THREW: CohortPlanningError validation buildCandidateInventory: internal provider-family disagreement for executor "agent-x" (own derivation: "claude", resolveExecutorConfig: "pi")
```
Matches the Reviewer's report exactly. Does not trigger against the
current committed `.fgos/config.json` (every `kind:"agent"` entry there
has its own `invocations`, global executor is `'claude'`) -- no
regression today, but `agentType`-only executors are a real, documented
shape (`buildAgentTypeExecutor`, D1/D2 tsk-3sw) this planner will
encounter the moment one is registered.

**Coordinator disposition: ACCEPTED, fixing.** A confusingly-worded
"internal invariant violated" crash for a legal config shape is a real
correctness bug, not a hypothetical -- matches this track's own
established practice of fixing genuine reproducible bugs even when the
currently-committed config doesn't trigger them (the exact posture taken
for every prior cell's Fix Evidence in this track). Fix direction:
`buildCandidateInventory` must replicate `resolveExecutorConfig`'s full
command-resolution fallback chain (including the `agentType` branch) when
computing its own `resolvedCommand`, so the two derivations genuinely
read the same input and the invariant's "should never fire" premise
becomes actually true, rather than degrading the invariant's fail-loud
posture.

### MEDIUM — R4 handoff's Proof Matrix/docstring overclaim "governance" coverage

Phase-04 R4's own text: "Resolver revalidates executor/provider/model/
tier AND governance." `verifyPlannedAllocationAgainstCurrentConfig` calls
`resolveAssignmentDispatchPolicy` with no `options`, and by its own
docstring deliberately never calls `resolveExecutorConfig` (the actual
cross-provider governance gate) "since it resolves a real spawnable
command." A candidate governance-eligible at planning time that becomes
ineligible before dispatch would pass this handoff with `abort: false`.

**Coordinator disposition: ACCEPTED as a documentation-accuracy gap,
NOT a functional fix this cell.** The function's own design rationale
(avoid a spawn-adjacent resolution call inside a cell whose whole point
is "never spawns anything") is sound and deliberate -- P04.2's real
dispatch wiring is expected to call `resolveExecutorConfig` for real at
actual spawn time, which DOES enforce governance, so the real safety
invariant (never dispatch to a governance-ineligible executor) still
holds end-to-end once P04.2 lands. The problem is purely that this
cell's own docstring/Proof Matrix currently overclaim what THIS function
alone proves, which could mislead a P04.2 implementer into skipping the
real governance re-check on the false assumption this handoff already
covers it. Fix: correct the docstring to explicitly disclose the gap
("does not re-verify governance eligibility -- a real dispatch caller
MUST independently re-run resolveExecutorConfig's governance gate before
spawn") -- documentation-only, does not touch behavior.
