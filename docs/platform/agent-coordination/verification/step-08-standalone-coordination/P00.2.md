## Requirements

- R5 Tier bridge: direct resolver for `lightweight|standard|creative|analytical|critical`
  against `runner.modelPolicies.<provider>`, preserving Work-tier
  `light|standard|heavy -> policy tier` behavior and existing `modelForTier()`

  compatibility projection for current callers; no protocol scopes yet
  (Phase 03).
- R8 Provider capability validation: runner config accepts partial provider
  policy-tier maps; pure `supportsPolicyTier` query; invalid model
  strings/absent provider tables reject at config load or resolve; never
  probes credentials or infers support from executable availability.

**F1 (MEDIUM) — R6(b) exemption reproduces H2a for unregistered `claude`/default-command executors, contradicting R6's literal wording; the exempted branch itself is untested**

File: `src/runner/dispatch/assignment-policy.mjs:154-166`, `:169`
Requirement violated: Phase-00 R6 — "provider family from that executor's
configured `providerModel` (**explicit `claude` default only for a
registered executor without the field**)."

The exemption (`isImplicitDefaultExecutor`) lets `primaryExecutor` skip the
registry-membership check when it equals the literal string `'claude'` or
`runnerConfig?.executor?.command`, **even when neither is actually present
in `runnerConfig.executors`**. In that branch `registeredExecutorEntry` is
`undefined`, so at line 169 `resolvedProvider = registeredExecutorEntry ?
deriveProviderFamily(...) : primaryExecutor` falls to the `: primaryExecutor`
arm — `providerModel` becomes the raw executor-id string again, not a value
derived from any registered entry's `providerModel` field. This is the exact
H2a shape (`providerModel = executor id`) for this one carve-out, and it
directly contradicts R6's own parenthetical, which conditions the `claude`
default on the executor being *registered* ("...only for a registered
executor without the field"), not merely on the id matching a magic string.

Evidence this is untested: grepped `test/runner/assignment-policy.test.mjs`
for `isImplicitDefaultExecutor`/`hasExecutorRegistry`/a case combining
`runnerConfig.executors = {...}` (a real, non-empty registry) with
`preferExecutor` left at its `'claude'` default or explicitly set to
`'claude'` where `'claude'` is *not* a key in that registry — no such case
exists. The two closest tests either register `claude` itself
(`assignment-policy.test.mjs:304-321`, `executors: { claude: {...} } }`,
which exercises the throw path, not the exemption) or omit `executors`
entirely (`:323-339`, which exercises `hasExecutorRegistry === false`, a
different branch). The exact scenario the Doer says forced this fix — a real
`.fgos/config.json` registering `pi` but not `claude` — has zero regression
coverage.

Mitigating factors (why MEDIUM, not HIGH): this narrows an existing, wider
hole rather than opening a new one — before this cell, *no* executor id was
ever validated against a registry, so today's exemption is strictly less
permissive than yesterday's total bypass. In the common case the executor id
literally is `claude`'s own provider family, so the wrong-shaped value is
usually also the right value by coincidence. But it is a coincidence, not a
derivation, and the literal R6 wording is violated for this path.

Smallest fix direction: either (a) only exempt when `registeredExecutorEntry`
truthy (i.e., drop the exemption, accept that this machine's `.fgos/config.json`
needs `claude` added to `executors{}` — arguably the more honest fix per
R6's literal text), or (b) keep the exemption but restrict its effect to
skipping *only* the throw, not the provider-family derivation — i.e. still
compute `resolvedProvider` via `deriveProviderFamily` against a synthetic
`{ command: runnerConfig?.executor?.command }`-shaped entry so the "id vs.
family" derivation stays consistent even on the exempted path, then add a
test that pins the exempted branch's actual `providerModel` output.

**F2 (HIGH) — Governance gate checks only the resolved provider family, not the selected executor as a distinct field; `disallowedProviders` semantics silently shifted from executor-id-keyed to provider-family-keyed, with zero test coverage of a registered executor whose id and family differ**

File: `src/runner/dispatch/assignment-policy.mjs:206-211`
Requirement violated: Phase-00 R6 — "governance checks the resolved provider
family **and selected executor as distinct fields**."

Before this cell, `resolvedProvider = primaryExecutor` always (H2a's own
bug), so `options.disallowedProviders` was, in practice, keyed by executor
id. After this cell, for a *registered* executor, `resolvedProvider =
deriveProviderFamily(registeredExecutorEntry)` — which can differ from the
executor id (that's the whole point of R6a/H2a). The governance gate at line
208 still does exactly one check: `disallowedProviders.includes(resolvedProvider)`.
It never also checks `primaryExecutor`/`effectivePolicy.executorId` against
anything. Concretely: an executor registered as
`{ 'glm-cli': { providerModel: 'z-ai' } }` used to be blockable via
`disallowedProviders: ['glm-cli']` (the id); after this cell the same config
value no longer blocks it — only `disallowedProviders: ['z-ai']` (the
family) does. Any existing deployment that configured `disallowedProviders`
by executor id (the only semantics that ever existed before this cell) has
its governance block silently stop working for any executor whose
registered `providerModel` differs from its id, with no warning, doc note,
migration test, or `disallowedExecutors` counterpart added to catch the
executor-id case going forward.

This is exactly the scenario the dispatch prompt flagged for scrutiny (item
5), and the pre-existing test `governance gate rejects disallowed
egress/provider` (`test/runner/assignment-policy.test.mjs:135-152`) does not
catch it — it passes no `runnerConfig` at all, so `hasExecutorRegistry` is
false, `registeredExecutorEntry` stays undefined, and `resolvedProvider`
falls back to the raw `primaryExecutor` string — the *old* code path,
unchanged in behavior. No new test anywhere in this cell's diff constructs a
registered executor with a `providerModel` distinct from its id and then
exercises `options.disallowedProviders` against it.

R6's "as distinct fields" phrasing reads as intent for governance to be able
to act on *both* fields independently, not for one field's semantics to
silently absorb the other's prior meaning. As written, there is now no way
to block a specific executor entry by id when its declared provider family
is otherwise trusted.

Smallest fix direction: add a `disallowedExecutors` (or equivalent) governance
option checked against `primaryExecutor`/`executorId` independently of
`disallowedProviders` against `resolvedProvider`, and add a test with a
registered executor whose id and `providerModel` differ, asserting
`disallowedProviders` matches the family and (if added) `disallowedExecutors`
matches the id. At minimum, document the semantic shift in the R10/R6 gap
notes so operators upgrading `disallowedProviders` configs know to review
them.

**F3 (LOW) — Provenance `source.scope` vocabulary doesn't match the FlowDefinition/CoordinationSession contract's documented scope names; "matches ... verbatim" overstates what matches**

Files: `src/runner/dispatch/assignment-policy.mjs:82,102,115-121,129-133,154-166,170-172,178-196,204,211`;
`docs/architect/agent-coordination/contracts/flow-definition.md:195-208`

The contract's PolicyPatch provenance section documents `scope` as naming
"the layer that won (`runner`, `definition`, `node`, `operation`, `role`,
`actor`, `assignment`, `cli`, `governance`)." The implementation instead uses
`opPolicy`, `cliOverride`, `work`, `default`, `registeredExecutor`,
`runnerConfig`, `assignment`, `governance` — only `assignment` and
`governance` match the documented vocabulary; `opPolicy`/`cliOverride`
clearly correspond to the doc's `operation`/`cli` but under different
strings, and `work`/`default`/`registeredExecutor`/`runnerConfig` have no
documented counterpart at all.

This is **not a hard R7 violation**: ADR-009 Decision 6 explicitly says "the
exact scopes implemented in a given phase are a roadmap concern, not this
ADR's," and R7 itself allows "an equivalent versioned machine-readable
form." So the `{field: {value, source: {scope, id}}}` object shape — which
is what R7 actually pins down — does match verbatim, confirmed field-by-field
against `flow-definition.md:199`. But the Doer's report and the Proof Matrix
both say provenance shape "matches ADR-009's FlowDefinition PolicyPatch
provenance contract verbatim" without qualifying that only the shape (not
the scope vocabulary) matches — worth correcting the claim's precision, and
worth reconciling the scope strings to the documented vocabulary (or
formally extending it) before Phase 03 wires protocol-level scopes, so two
independently-evolving scope vocabularies don't have to be reconciled later
under more time pressure.

Smallest fix direction: no code change required for this phase; either
rename `opPolicy`→`operation` and `cliOverride`→`cli` now (cheap, no current
consumer reads `provenance.*.source.scope` besides this cell's own tests),
or add one line to R7's Doc Updates / Gaps section naming the scope strings
actually in use so Phase 03 has a starting reconciliation list instead of
rediscovering the drift.

**RT1 (HIGH) — F2's `disallowedProviders`/`disallowedExecutors` governance
gate silently reverts to H2a's exact defect (`providerModel = executor id`,
never the true provider family) whenever `runnerConfig.executors` is absent —
a fully schema-valid config shape, not a malformed edge case — defeating the
entire governance mechanism F2 was written to fix, with zero test coverage
of `providerModel`/governance in that state**

Files: `src/runner/dispatch/assignment-policy.mjs:157-169` (`hasExecutorRegistry`
/ `registeredExecutorEntry` / `isImplicitDefaultExecutor` / registration
throw), `:183-190` (`resolvedProvider`/`providerSource` derivation),
`:234-239` (governance checks), `:257-258` (`provenance.provider`).

Requirement violated: Phase-00 R6 — "Provider family comes from that
executor's configured `providerModel`... **not from executor id**" (no
carve-out conditioned on whether an `executors` registry happens to be
present) — and its own governance clause, "Governance checks the resolved
provider family and selected executor **as distinct fields**." Also
undermines R7 (`provenance.provider.value` reports the false family) and the
Coordinator's own F2 disposition ("`disallowedProviders` names a provider
family, never a raw executor id, per its own option name").

**Root cause**: `resolvedProvider`'s three-way ternary
(`registeredExecutorEntry ? deriveProviderFamily(...) : isImplicitDefaultExecutor
? deriveProviderFamily({command: ...}, primaryExecutor) : primaryExecutor`)
falls to the bare `: primaryExecutor` arm whenever `registeredExecutorEntry`
is `undefined` AND `isImplicitDefaultExecutor` is `false`. `registeredExecutorEntry`
is *unconditionally* `undefined` whenever `hasExecutorRegistry` is `false`
(`runnerConfig.executors` absent entirely — `config.mjs` makes this an
OPTIONAL field, not a required one; a project that configures only
`executor` + `modelPolicies` is fully valid per `validateRunnerConfigShape`).
So for ANY `preferExecutor` value that is neither `'claude'` nor
`runnerConfig.executor.command` (e.g. a workflow's `opPolicy.preferExecutor`
or a human's `cliOverride.preferExecutor` naming a real, working executor id
like `'glm-cli'`), when no `executors` registry exists, `resolvedProvider`
falls straight to the raw id — the exact H2a shape the whole R6/F2 pass
exists to eliminate. Critically, the fail-closed registration throw
(`:167-169`) is *also* gated on `hasExecutorRegistry`, so this path throws
NOTHING — it silently succeeds with a false `providerModel`.

hypothetical):

loud) outcome whenever a project's `modelPolicies` happens to be keyed by
raw executor id rather than true provider family (plausible for any project
that hasn't adopted the `executors` + `providerModel` convention this repo's
own `.fgos/config.json` uses) — confirmed live: `preferExecutor: 'glm-cli'`,

`providerModel: 'glm-cli'` and `provenance.provider.value: 'glm-cli'`, both
false, and `disallowedProviders: ['z-ai']` again does not block it.

**Why this was missed**: every one of the Fixer's new F1/F2/F4 tests (and
the pre-existing "never validates preferExecutor registration when
runnerConfig declares no executors registry at all" test at
`assignment-policy.test.mjs:323-339`, which already exercises exactly the
`hasExecutorRegistry === false` branch this bug lives in) either supplies a
populated `executors` registry, or — in the one existing test that *does*
omit `executors` — only asserts `effective.executorId`, never
`effective.providerModel` or governance behavior in that state. F2's own new
test (`:370-412`) always registers `glm-cli` in `runnerConfig.executors`, so
it only proves the fix works when a registry is present — never the
registry-absent config shape this finding exploits.

**Mitigating factors (why HIGH, not CRITICAL)**: `options.disallowedProviders`/
`disallowedExecutors` are not wired to any live caller in this repo today
(`grep` finds zero production call site setting them — only this file's own
doc comments and tests reference the names) and this repo's own tracked
`.fgos/config.json` does populate a full `executors` registry, so there is
no live exposure through this repo's actual dispatch path right now. But R6/
F2 exist precisely so a *future* governance caller can trust
`disallowedProviders` as provider-family-truthful — that promise is false
for any config lacking an `executors` registry, a config shape
`validateRunnerConfigShape` fully permits and this same test suite already
exercises (just not for `providerModel`/governance).

**Smallest fix direction**: don't let the registry-absent case share the
bare `: primaryExecutor` fallback that also serves the "genuinely nothing to
validate against" registration-throw exemption — those are two different
concerns (whether to fail-closed on an *unrecognized id*, vs. how to
*derive the provider family*) that collapsed onto the same variable. Either
(a) extend F1's own synthetic-entry pattern
(`deriveProviderFamily({ command: runnerConfig?.executor?.command },
primaryExecutor)`) to the registry-absent case too — this at least stops
misreporting `providerModel` as silently trustworthy by deriving it the same
declared way every other path does (though note: with no registry entry,
there is still no way to *learn* a true family divergent from the id — the
data simply doesn't exist in this config shape, so this only fixes the
reporting/coincidence risk, not the fundamental absence of truth), or (b)
treat "governance options are present but there is no `executors` registry
to verify `resolvedProvider`/`primaryExecutor` against" as its own fail-closed
condition — throw rather than silently apply governance against an
unverifiable value, so an operator who sets `disallowedProviders` gets a
loud config error instead of quiet non-enforcement. (b) is more faithful to
this file's own "fail closed, never swallowed" invariant stated at the top
of the file.
