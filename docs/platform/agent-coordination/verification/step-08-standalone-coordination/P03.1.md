**One item flagged for the Reviewer/Red-Team, not self-dispositioned —
a plausible TOCTOU on `maxRounds` enforcement:**

`dispatchDeclaredOperation`'s round-cap check (`roundsAlreadyUsed >=
maxRounds`, around line 971-980) reads `events` (via `replaySession`,
already computed earlier in the function) and compares against the
CURRENT count of `assignment-created` events for the target actor —
BEFORE `createAndExecuteSessionTask` runs its own atomic
`dispatch.claim`-guarded creation. For two concurrent calls to
`dispatchDeclaredOperation` requesting the SAME new round number (same
`taskKey`), this is provably safe: both collapse onto the same
deterministic `assignmentId` (via `hashTaskKey(taskKey)`), and
P01.2's already-proven `dispatch.claim` exclusive-create guard inside
`createAndExecuteSessionTask` rejects the second concurrent caller —
no round-cap bypass there. But for two concurrent calls requesting
DIFFERENT round numbers (e.g. caller A dispatches `round: 1`, caller B
concurrently dispatches `round: 2`, `maxRounds: 1`) — since `roundsAlreadyUsed`
is read from `events` BEFORE either caller's own `assignment-created`
event is appended, BOTH calls could observe `roundsAlreadyUsed === 0`,
both pass the `0 >= 1` check (false), and both proceed to create
DISTINCT Assignments (different `taskKey`s -> different `assignmentId`s
-> the P01.2 claim-file guard does not collide between them) — resulting
in 2 rounds actually created against a `maxRounds: 1` edge. This is the
exact "check-then-act across the atomic-claim boundary" bug CLASS that
was found and fixed 3 separate times in P01.2 (rounds 1-3 of that cell),
just manifesting in a NEW piece of state (the round-count read) that sits
outside any lock, unlike P01.2's already-hardened Assignment-creation
path itself. No test in this cell's own suite exercises concurrent
`dispatchDeclaredOperation` calls with different round numbers — the
existing `maxRounds` test (`R2: maxRounds: 1 is enforced...`) is
single-caller/sequential only.

Given this exact bug class's track record in this session (P01.2 found
one new race per Red-Team round, 3 rounds in a row, all in this same
file), this is not a theoretical nitpick — it is exactly the shape of bug
this track has repeatedly found real. Sending to an independent
Reviewer/Red-Team to attempt reproduction and adjudicate severity, rather
than the Coordinator guessing or silently accepting it as fine.

### HIGH — `maxRounds` topology cap is bypassable under genuine cross-process concurrency (CONFIRMED, empirically reproduced 15/15)

`dispatchDeclaredOperation`'s round-cap check (`roundsAlreadyUsed >=
maxRounds`, session-engine.mjs:966-981) reads `assignment-created` events
via an **unlocked** `replaySession()` call, entirely separate from
`createSessionAssignment`'s own atomic, cross-process-locked write
(`withEventsLock` in `state/events.mjs`). The existing `dispatch.claim`/
`taskClaimPath` guard (P01.2's hardening) only protects same-`taskKey`
collisions -- two DIFFERENT round numbers produce different `taskKey`s
(and thus different `assignmentId`s), so they never collide on that
guard at all.

**Reviewer's reproduction, independently reasoned through by the
Coordinator and found sound:**
- Single-process `Promise.all` race: does NOT reproduce (0/N) -- the
  Reviewer traced the entire call chain from `dispatchDeclaredOperation`'s
  top through `createSessionAssignment`'s event-append and confirmed
  ZERO `await` exists anywhere in that span (the first `await` in the
  whole chain is `await executeAssignment(...)`, which runs AFTER the
  Assignment already exists) -- so within one Node process, call A's
  entire round-check-through-commit sequence runs to completion,
  uninterrupted, before call B's synchronous prefix even starts, even
  under `Promise.all`.
- Two real, separate `node` OS processes racing the same session: **15/15
  reproductions**. Both calls succeed, both create real Assignments,
  `manifest.assignmentRefs` and `events.jsonl` durably contain TWO
  `assignment-created` events for the same `consultant-actor` against a
  `maxRounds: 1` topology edge -- a genuine, persisted governance
  violation on disk, not a transient artifact.

**Coordinator disposition: ACCEPTED, HIGH, blocking -- dispatching a
Fixer.** This is squarely inside R2's own stated scope ("Enforce...
declared intent, direction, context visibility, and **one-round cap**"),
not deferred to R5/P03.2's later session-bounds-enforcement cell. It
matches this exact file's established bug class from P01.2 (check-then-
act across an unlocked boundary, 3 separate real instances found and
fixed there) -- multi-process concurrent dispatch against one session is
a realistic scenario this track has repeatedly treated as in-scope (not
"nobody would ever do that"), since real automated agent callers
(including this track's own multi-subagent Coordinator pattern) can
legitimately race. Fix direction (per the Reviewer's own recommendation,
confirmed sound): move the round-cap check INSIDE the same
`withEventsLock` critical section `createSessionAssignment` already
holds for its own event-append -- mirroring P01.2's own precedent
exactly (`bindActor`'s `opts.primaryActorId` extended that function's
existing lock to cover a second invariant, rather than adding a new,
separate, unlocked check).

## Fix Evidence

`createSessionAssignment` (store.mjs) extended with an opt-in
`opts.maxRoundsForActor`, mirroring `bindActor`'s `opts.primaryActorId`
precedent exactly: when supplied, checks "actor `actorId` has fewer than
`maxRoundsForActor` prior `assignment-created` events" on a FRESH
`readEvents(eventsPath)` taken INSIDE the function's own `withEventsLock`
critical section, placed strictly AFTER the existing `taskClaimPath`
resume-check (which returns/self-heals early) and strictly BEFORE
`claimAssignmentId(...)` (so a rejected check writes nothing at all).
Undefined by default -- every pre-existing caller (agent-led
`proposeConsult`/`dispatchPrimaryTask`, every existing test) sees
byte-identical behavior. `dispatchDeclaredOperation` (session-engine.mjs)
forwards `maxRoundsForActor: incomingEdge.maxRounds ?? Infinity`
unconditionally whenever a topology edge governs the dispatch (not gated
on its own, now-advisory-only, pre-lock `isResumeOfThisRound` guess) --
`createAndExecuteSessionTask` already forwards arbitrary `opts` straight
through to `createSessionAssignment` unmodified, confirmed by the
Coordinator directly in source, so no further plumbing was needed.

**Coordinator's own independent verification** (not trusting the Fixer's
