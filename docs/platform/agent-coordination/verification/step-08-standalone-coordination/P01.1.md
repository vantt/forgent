  fail-closed manifest/event store rooted at `.fgos/coordination/<id>/`,
  exactly matching `docs/architect/agent-coordination/contracts/coordination-session.md`.

  remove `.fgos/missions/` shapes entirely; no migration/compat/detection

### HIGH — Crash-then-retry after an interrupted `assignment-created` write can duplicate the Assignment for one logical task, violating the contract's Required Negative Test #3

`coordination-session.md`'s Required Negative Tests names one scenario with two halves: "Replaying `events.jsonl` after an interrupted `assignment-created` write (crash between event append and `assignmentRefs` append) does not fabricate a completed Assignment reference, **and does not duplicate the Assignment on retry**." The first half is genuinely proven (`replay.mjs`'s dangling-ref-direction-2 check, tested by `coordination-replay.test.mjs`'s "detects a dangling ref the other direction" test). The second half is not proven, and is demonstrably false against the current implementation.

Trace of `createSessionAssignment` (`store.mjs:288-347`), inside the held `withEventsLock` critical section:
1. `claimAssignmentId` → `mkdirSync` claims the Assignment directory, `buildAssignment` computes the Assignment.
2. `assignment.json` is written to `.fgos/assignments/<id>/assignment.json`.
3. `assignment-created` is appended to `events.jsonl` (`appendEventLocked`).
4. `manifest.assignmentRefs` is updated and `session.json` is rewritten (`writeManifestRaw`).
5. `tasks/<taskKey>.json` claim record is written.

A crash between step 3 and step 4 leaves exactly the state `coordination-replay.test.mjs`'s "dangling ref the other direction" test constructs by hand: `assignment-created` event present, `assignmentRefs` entry absent, and — critically — the taskKey claim file from step 5 also never written (it comes after step 4). On process restart, a caller retrying the same logical task calls `createSessionAssignment` with the same `coordinationId`/`taskKey` again. That function checks `fs.existsSync(taskClaimPath)` (`store.mjs:304`) — false, since step 5 never ran — and falls straight through to `claimAssignmentId(...)` again, which computes a **new** `assignmentId` (via `createAssignmentId`'s existing-directory scan) and creates a **second** Assignment for what was meant to be one logical task. Nothing in `createSessionAssignment` consults `events.jsonl` or runs `replaySession` before proceeding, so the orphaned `assignment-created` event from the crashed attempt is never seen. `readManifestRaw` (used here) only validates the manifest's own shape — it does not detect the dangling event.

This is real and reachable exactly the way the contract's own negative test describes it, not a hypothetical. The Doer's own report (P01.1.md Gaps, store.mjs's `createSessionAssignment` doc comment) discloses the limitation honestly and frames it as "R7's scope, P01.2's" — but `coordination-session.md` is the contract this cell was instructed to implement exactly ("implement exactly this, do not invent a divergent shape," current-cell.md), and this specific scenario is one of that contract's own Required Negative Tests, not an R5-R8 concept (dynamic consult, engine, live proof). Non-Goals' "resume reconciliation logic beyond what R1-R4 requires for replay correctness" is arguably satisfied (replay itself is correct — it fails closed rather than fabricating), but the contract's negative test explicitly asks for more than replay correctness: it asks that a retry not duplicate. That half is unmet.

Smallest fix direction: before calling `claimAssignmentId`, have `createSessionAssignment` scan `events.jsonl` (or a lighter-weight per-taskKey marker) for an existing `assignment-created` event whose `assignmentId` has no corresponding `assignmentRefs` entry — i.e., detect the interrupted-write shape itself before creating a second Assignment, or land the taskKey claim record write (step 5) inside the SAME atomic step as the event append (steps 3+4+5 as one write-before-any-visible-effect unit) rather than after it. Either closes the gap without pulling in the rest of R7's resume-reconciliation scope. At minimum, this should be named plainly as an open contract gap in the Gaps section (it already is, but framed as "R7 scope" rather than "a specific named contract negative test not yet met").

### MEDIUM — Only `replaySession` checks `schemaVersion`; every mutating store operation (`createSessionAssignment`, `bindActor`, `linkResult`, `transitionSessionStatus`) reads the manifest via `readManifestRaw`, which never compares `schemaVersion` against the running `SCHEMA_VERSION`

Recovery Rule #4 says "A schema/version mismatch... fails recovery with a named reason; it never silently reinterprets the old shape." `replay.mjs`'s `readManifestForReplay` wraps `store.mjs`'s `readManifestRaw` with exactly that check (`replay.mjs:30-39`) — but every store mutator (`createSessionAssignment` `store.mjs:299`, `bindActor` `store.mjs:222`, `linkResult` `store.mjs:360`, `transitionSessionStatus` `store.mjs:384`) calls `readManifestRaw` directly, not `readManifestForReplay`, so none of them would refuse to keep mutating a session whose persisted `schemaVersion` no longer matches the running contract's `SCHEMA_VERSION`. Low practical severity today (`SCHEMA_VERSION` is a hardcoded `'1'` with no version-2 shape yet to reinterpret), but it is a real gap against the Recovery Rule's literal text, and becomes live risk the moment a schema bump ships without every mutating door re-checking it. Smallest fix: have the four mutators call the same schemaVersion-checking wrapper `replaySession` uses (or inline the one-line comparison) instead of the bare `readManifestRaw`.

### HIGH — The accepted HIGH fix's own retry fast-path returns a "successful" Assignment that is never actually added to the session (no `assignment-created` event, no `assignmentRefs` entry), permanently, with no self-heal — reopening the exact contract requirement it was dispatched to close

`coordination-session.md`'s Required Negative Test #3 requires that replaying/retrying after an interrupted `assignment-created` write "does not duplicate the Assignment on retry." The Coordinator's accepted fix (Fix Evidence section above) reorders `createSessionAssignment` so the `tasks/<taskKey>.json` claim record is written immediately after `claimAssignmentId` reserves an id, and added a fast path: if the claim record exists and `assignment.json` exists for the claimed id, return that Assignment (`store.mjs:320-328`). This does stop a literal second `assignment.json`/directory from being created. But it does **not** re-check or complete the two writes that make the Assignment an actual session member — the `assignment-created` event append and the `manifest.assignmentRefs` update. If a crash lands after `assignment.json` is written but before those two writes complete (exactly the "interrupted `assignment-created` write" window the Required Negative Test names), the fast path on **every** subsequent retry returns a frozen, well-formed Assignment object that looks like a successful, completed session Assignment — but `manifest.assignmentRefs` never gains this id and no `assignment-created` event is ever appended. Nothing in the fast path detects or repairs this; it is a bare `return Object.freeze(existing)`.

Reproduced independently (script, not the shipped regression test — see below for why the shipped test misses this):

```
BEFORE retry:
  manifest.assignmentRefs = []
  events = [ 'session-opened' ]

AFTER retry, returned assignmentId = asgn_writer_1_op_001
  manifest.assignmentRefs = []
  events = [ 'session-opened' ]

linkResult THREW: validation - assignment "asgn_writer_1_op_001" is not a member of session "coord_verify" -- cannot link a result to it
```

The caller of `createSessionAssignment` gets back what looks like a fully successful call (no thrown error, a real frozen Assignment with a valid `assignmentId`) and has no way to know from that return value alone that the session's own bookkeeping was never completed. The failure only surfaces later, confusingly, at `linkResult` (or never, if the caller never tries to link a result). Because the fast path is unconditional and permanent — every future retry for this `taskKey` takes the identical shortcut — there is no store.mjs door that ever repairs this: the Assignment is stuck as a phantom, forever invisible to `replaySession` too (since neither the event nor the ref exists, it doesn't even trip a `dangling-ref` — it's simply absent, exactly like the pre-existing "harmless orphan" case store.mjs's own crash-point tests treat as acceptable, except here the caller was actively told this Assignment belongs to the session).

This is the same crash window the Coordinator's disposition explicitly named this fix as closing ("Fix direction: reorder `createSessionAssignment` so the `tasks/<taskKey>.json` claim record is written IMMEDIATELY... Once the claim file exists, a retry always resolves to the SAME `assignmentId`... an acceptable, honest outcome for that narrow crash window, not a silent duplicate"). "Resolves to the SAME assignmentId" is true, but incomplete: the disposition (and the Fixer's doc comment, and both new regression tests) only checked that the *identity* returned on retry is stable, never that the *session membership* the caller is relying on was actually completed. The two shipped regression tests (`coordination-store.test.mjs`, "crash after claim-record + assignment.json written, before event/ref") assert only `retried.assignmentId === orphanId` and that exactly one Assignment directory exists — neither asserts `readManifest(...).assignmentRefs` nor `readSessionEvents(...)`, which is exactly why this gap shipped through Doer → Reviewer → Fixer without being caught.

Smallest fix direction: in the fast-path branch (`store.mjs:320-328`), after confirming `existing` (the on-disk Assignment) is present, also check whether `manifest.assignmentRefs.includes(claim.assignmentId)`; if not, complete the atomic write this retry detected as interrupted — validate and append the `assignment-created` event, update `manifest.assignmentRefs`, and persist the manifest — using the same `eventPayload`/`assignmentId` the original attempt would have used — before returning. This makes the retry itself the self-healing mechanism the Recovery Rule's "one atomic write" language implies, instead of a shortcut that silently abandons the second half of that atomic write forever.

### MEDIUM — `sanitizeTaskKey`'s lossy sanitization lets two textually-distinct `taskKey`s collide onto the same claim file, silently dropping the second logical task's Assignment instead of creating it

`sanitizeTaskKey` (`store.mjs:240-243`, via the shared `sanitizeToken`) lowercases and replaces every non-`[a-z0-9]` character with `_` before using the result as the `tasks/<sanitized>.json` claim-file name. Two different `taskKey` values that differ only in case or in which non-alphanumeric separator they use (e.g. `"primary-round-1"` and `"primary_round_1"`) sanitize to the identical claim-file name `primary_round_1.json`. Reproduced independently:

```
a.assignmentId = asgn_writer_1_op_001 objective= A
b.assignmentId = asgn_writer_1_op_001 objective= A
same? true
manifest.assignmentRefs = [ 'asgn_writer_1_op_001' ]
```

The second `createSessionAssignment` call (a genuinely distinct logical task, different `objective`/`contract`) silently takes the "already claimed" fast path and returns the *first* task's Assignment instead of creating its own — no error, no warning, and the second task's Assignment is never created at all. This is a real correctness gap in the idempotent-claim mechanism itself (distinct from the HIGH finding above, which is about a crash-interrupted single task): `taskKey` uniqueness is only guaranteed up to sanitized-form equality, not literal string equality, and nothing in `store.mjs`, its doc comments, or the R2 proof matrix names this as an accepted constraint on callers. Whether this is exploitable in practice depends entirely on which `taskKey` conventions the not-yet-built session engine (R5/P01.2) chooses — but the store module itself provides no guard rail today. Smallest fix direction: either hash the raw (unsanitized) `taskKey` into the claim-file name instead of a lossy character-substitution, or detect a collision (sanitized name already claimed by a different raw `taskKey`) and throw a named `CoordinationError` instead of silently aliasing.

Required Negative Test (replay must never accept a duplicated Assignment
ref) while closing this one. Caught this by re-tracing the inner-retry

Fixed by making `completeAssignmentRegistration`'s event append itself

(the `assignmentId` there is always freshly claimed via

correctness guard on that path, not a behavior change. With this in

appends nothing, and completes only the still-missing `assignmentRefs`
