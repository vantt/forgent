# P03.1 — Role Execution Policy Readiness (Phase 03, R1-R8)

Cell: P03.1. Track: step-09-mvp3-to-mvp5. Base: 52a1db76.

## Requirements (verbatim)

- **R1 Capability audit.** Read current runner config and dispatch policy. Record
  how `standalone-master-coordination-loop` operations resolve today for Doer,
  Reviewer, Red-Team, Fixer, and Recheck.
- **R2 Explicit capability surface.** If role operations cannot resolve
  intentionally, add minimal capabilities such as `coordination-doer`,
  `coordination-review`, `coordination-red-team`, `coordination-fix`, and
  `coordination-recheck`, or the smallest equivalent supported by current
  dispatch config.
- **R3 Tier floors, not model pins.** Fixture/protocol code declares
  capabilities and `minTier`; project config maps to concrete executors and
  provider/model policies. Portable fixture files must not hardcode literal
  provider/model names.
- **R4 Cost-quality defaults.** Doer/Fixer may default to standard or the
  cheapest capable coding executor. Reviewer/Recheck default to analytical
  read-only execution. Red-Team defaults to analytical and escalates to critical
  for invariant, security, concurrency, dispatch, session/replay/schema, or
  Work-boundary cells.
- **R5 Read-only review executor.** Reviewer, Red-Team, and Recheck should prefer
  a read-only-capable executor when available. They must not need git-write
  grants to produce their own RunResult/report.
- **R6 Escalation without default overspend.** Opus/Sol-class or equivalent
  critical reasoning is used by policy escalation or manual coordinator
  decision, not as the default for every review.
- **R7 Config discipline.** Any new config default, env var, runtime-read file
  location, or infrastructure assumption is registered with setup/doctor in the
  same phase.
- **R8 Dispatch proof.** `decide` or equivalent dispatch tests prove every role
  resolves to the intended mechanism/executor/tier, and missing critical-tier
  support fails closed when critical is required.

## R1 Audit Findings (before this cell's changes)

Baseline confirmed by reading the fixture directly: `core/coordination-protocols/standalone-master-coordination-loop.yaml`
declared **no `policy`/`capabilities` on any of its 6 operations or 4 actors**, and no
`spec.policy` (definition-scope). Confirmed no live caller yet passes per-role
policy either: `src/verbs/coordination/launch-master-loop.mjs`'s

**global** `cliExecutor`/`cliModel`/`cliTier` (`launchMasterLoopUseCase`,

Tracing `dispatchDeclaredOperation` (`src/runner/coordination/session-engine.mjs:1368-1785`)
with that baseline:

   `runner`/`definition`/`operation`/`role`/`actor`/`assignment`/`cli` — from
   `runnerPolicy`/`definition.spec.policy`/`operation.policy`/`rolePolicy`/
   `actorEntry.policy`/`assignmentPolicy`/`cliPolicy`. With nothing declared

   `executeAssignment`'s `cliOverride` param. With `opPolicy = assignment.policy

### R2: why no `capabilities[]` was added

R2's own conditional is: "**if** role operations cannot resolve intentionally,
add minimal capabilities ... or the smallest equivalent supported by current
dispatch config." The R1 audit found operations *can* resolve intentionally —
via `policy.minTier`, the mechanism this cell actually wired in
(`resolveAssignmentDispatchPolicy` reads `opPolicy.minTier`/`cliOverride.minTier`,
confirmed live by the R8 dispatch tests below). Given `capabilities[]` is
confirmed inert for this fixture's own (non-cohort) dispatch path — R8's own
Bug Taxonomy explicitly warns against "claiming R8's dispatch proof passes by
reading config statically instead of actually exercising the real resolution
path," and a `capabilities` declaration would have nothing real to prove —
adding invented capability names (`coordination-doer` etc.) to either the
fixture or `.fgos/config.json`'s `capabilities` catalog would be inert
scaffolding with zero functional effect today. `policy.minTier` is "the
smallest equivalent supported by current dispatch config" R2 itself names as
the acceptable alternative. Declared: `spec.operations[*].policy.minTier` only.
See the fixture's own new top-of-`operations:` comment for the same reasoning
inline.

### R4/R6: Red-Team's escalation path is a real, already-wired mechanism — not a schema gap

R4/R6 ask for Red-Team to "default to analytical and escalate to critical for
[named high-risk categories]." This is a *per-round, content-dependent*
judgment (which specific round's subject matter touches an invariant/security/
concurrency/etc. concern) — not a static property the FlowDefinition schema
could express as a single fixed value on the `red-team-candidate`/
`red-team-recheck` operation template (a static `critical` pin there would
raise the floor for *every* round, defeating "analytical by default" and R6's
"not as the default for every review").

This is **not a genuine schema gap** requiring new plumbing. The existing
`assignment`/`cli` policy scopes in `dispatchDeclaredOperation`'s own scope
stack (`session-engine.mjs:1664-1673`) are explicitly *exempt* from
`PORTABLE_POLICY_SCOPES` (`session-engine.mjs:718`, `assertNoPortableExecutorPin`)
— they are the trusted, per-dispatch-call scope flow-definition.md's own
PolicyPatch section describes: "a trusted request/CLI actor preference may
still select concrete infrastructure." `mergePolicyStack`'s monotonic-raise
rule (`definitions/schema.mjs:217-243`, reused unmodified) means a caller
passing `assignmentPolicy: { minTier: 'critical' }` on one specific
`dispatchDeclaredOperation({ operationId: 'red-team-candidate', ... })` call
can only ever *raise* the fixture's own `analytical` floor for that one round,
never lower it. **Proven live** by the R8 escalation test below (real dispatch,
real `RunnerConfigError`-free resolution to `critical`/`opus`-tier model).

Whoever *drives* this fixture (today: `launch-master-loop.mjs`'s MVP4 launcher,
which composes zero per-step policy at all — see R1 above) is the natural place
to expose this as a per-round option, but extending that launcher's own
request composition is outside this cell's Files list (`src/verbs/coordination/
launch-master-loop.mjs` is not in Phase 03's Files, and is Phase 04/05
territory — the live proof this phase only makes *possible*, per the Goal's
own "before Phase 04's live proof runs them for real"). **Recommendation for
Phase 04**: when a round genuinely touches an invariant/security/concurrency/
dispatch/session-replay-schema/Work-boundary cell, pass
`assignmentPolicy: { minTier: 'critical' }` on that specific
`dispatchDeclaredOperation` call for `red-team-candidate`/`red-team-recheck` —
already legal, already tested, requires no further schema/session-engine
change.

### R5: read-only-capable executor — a real gap, with a real, already-registered fix available

"Read-only-capable executor" has no literal flag in this repo's dispatch
vocabulary — `isReadOnlyMode`/`mutation: 'read-only'` (see R1 finding #3
above) governs *assignment intent*, not *which executor* runs it; the actual
tool-permission boundary (dropping the git-write grant) lives in an
**executor's own CLI args**. This repo's committed `.fgos/config.json` already
has exactly this executor, built for exactly this purpose in a prior cell:

```
executors.claude-reviewer: {
  kind: "agent",
  description: "Claude Code CLI, scoped for a READ_ONLY_ROLES ... Assignment
    ... identical to executors.claude except it drops the git-write grant
    ... and the --allowedTools flag entirely",
  invocations: [{ via: "cli", command: "claude", args: [... no --allowedTools ...] }]
}
```

However: `preferExecutor` **cannot** be declared at the fixture's own
operation/role/actor/definition scope (`assertNoPortableExecutorPin`,
confirmed by the R3 static test and by the pre-existing
`coordination-declared-consult.test.mjs` "R1: dispatchDeclaredOperation rejects
a definition/operation/role/actor-scoped literal preferExecutor pin" test).
This is a real, structural limit of the current design — **not a defect**
(Non-Goals explicitly bar treating this as a session-engine bug; it is the
deliberate portability boundary the PolicyPatch contract documents) — so R5
cannot be fully closed by a fixture-only change in this cell.

The mechanism that *can* close it already exists two layers up:
`src/verbs/coordination/schema.mjs`'s `kind:"declared-protocol"` request
schema already accepts a trusted per-actor override —
`ACTOR_ALLOWED_KEYS = ['id', 'persona', 'executor', 'model', 'tier']`
(`schema.mjs:122`), which `run.mjs`'s `actorPolicyFields`
(`run.mjs:74-83`) threads into `dispatchDeclaredOperation`'s `cliPolicy`
per actor. **Recommendation for Phase 04**: when composing a
`standalone-master-coordination-loop` request, name
`actors: [{ id: 'reviewer', executor: 'claude-reviewer' }, { id: 'red-team',
executor: 'claude-reviewer' }]` — already legal, already validated,
requires no further schema change. `launch-master-loop.mjs`'s own composer
does not yet expose this (confirmed in R1: it composes `steps[]` only, no
`actors[]`) — extending it is explicitly out of this cell's Files list.

The already-structural read-only guarantee (R1 finding #3: `isReadOnlyMode:
true`/`mutation: 'read-only'` for every operation, every role, unconditionally)
is proven live by the R8 dispatch tests below, without needing the
`claude-reviewer` executor pin — Reviewer/Red-Team/Recheck already "must not
need git-write grants to produce their own RunResult/report," structurally,
today.

## Gaps

- R5 is not fully closed by this cell alone: `preferExecutor` cannot legally
  be declared at the fixture's own portable scope (by design, not a defect),
  so routing Reviewer/Red-Team/Recheck to the already-registered
  `executors.claude-reviewer` requires Phase 04's live-proof driver to pass
  `actors: [{ id: ..., executor: 'claude-reviewer' }]` on the coordination

  (out of this cell's Files list). The structural read-only guarantee
  (`isReadOnlyMode: true`/`mutation: 'read-only'` for every role, every
  operation) already holds today regardless, proven live in R8 test 2.
- R4/R6's critical-escalation trigger ("does this round touch an
  invariant/security/concurrency/dispatch/session-replay-schema/Work-boundary
  cell?") is a per-round judgment call for whoever drives the session
  (Phase 04's coordinator), not something this cell's static fixture can
  encode — documented above as the intended mechanism (`assignmentPolicy`/
  `cliPolicy.minTier: 'critical'`), proven live, but the *judgment itself* is
  explicitly out of scope here (this phase makes the mechanism available; it
  does not build the judgment logic — that's Phase 04's live proof).
- `launch-master-loop.mjs` (the current MVP4 driver for this fixture) does not
  yet expose either of the above per-round/per-actor overrides in its own
  request composition — a real, named follow-up for whichever cell builds
  Phase 04's live proof, not something this cell should force through
  (`src/verbs/coordination/launch-master-loop.mjs` is not in Phase 03's Files
  list).

requirement above is either closed outright (R1, R2, R3, R7, R8) or closed with
