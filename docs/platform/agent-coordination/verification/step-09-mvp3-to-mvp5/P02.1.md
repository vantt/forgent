## 1. Requirements (verbatim from phase-02-mvp4-thin-surface-launcher.md, R1-R4 slice)

- **R1 Surface shape.** Prefer a command/request-file helper first. A skill or
  slash launcher may wrap that command later, but only as a thin caller. The
  surface accepts a plan/artifact path and creates a validated coordination
  request for `standalone-master-coordination-loop`.
- **R2 Runtime authority.** The launcher calls the coordination runtime and
  then reads the session/evidence surface. It does not choose hidden actors,
  authorize undeclared operations, synthesize final truth, or bypass
  FlowDefinition/session validation.
- **R3 No prompt runtime.** The launcher must not paste or load the Master
  Prompt as product runtime logic.
- **R4 Request validation.** Bad file path, unknown fixture id/version, Work
  fields, missing objective, invalid bounds, or forbidden context ref fails
  with an actionable error.

## 2. Surface Shape Decision

Chose a NEW CLI sub-verb, `fgos coordination launch-master-loop`, registered
in the same `case 'coordination':` switch in `bin/fgos.mjs` that already
dispatches `run`/`show` (mirroring that exact pattern — same
`repoRootForCoordination` resolution, same `requireField`/flags convention),
plus a matching entry in `src/cli/command-registry.mjs`. Behind it, a new
module `src/verbs/coordination/launch-master-loop.mjs` exports two functions:
`buildMasterLoopRequest(ctx, params)` (pure request composer — no runtime
call) and `launchMasterLoopUseCase(ctx, params)` (composes, then calls the
existing `runCoordinationUseCase`). This is the smallest change that
satisfies R1's literal text ("Prefer a command/request-file helper first"):
it is a genuinely thin, single-purpose command (not a generic multi-fixture
launcher, not a skill/slash file — Non-Goals explicitly forbids the latter in
this cell) that reuses the EXACT existing CLI registration pattern rather
than inventing a new one, and reuses the EXACT existing runtime door
(`runCoordinationUseCase`) rather than forking dispatch logic. The module is
also directly importable/testable without going through a subprocess, which
is what most of this cell's own test suite exercises.

## 3. Design Decisions Worth Recording

- **Only the fixture's REQUIRED first pass is composed** (`produce-candidate`
  / `review-candidate` / `red-team-candidate`) — never an `authorize`/
  `disposition`/`revise-candidate`/`reviewer-recheck`/`red-team-recheck`
  step. All three optional bindings are `activation: {mode:
  driver-authorized}` (confirmed in the shipped fixture YAML and frozen in
  `P00.1.md` §3); authorizing one is a driver decision made after reading
  this run's own evidence, never something this composer infers or
  defaults. This is the load-bearing choice that satisfies R2's "does not
  choose hidden actors, authorize undeclared operations" and the cell's own
  Bug Taxonomy warning against "a well-intentioned default."
- **The plan/artifact path travels in `objective` free text, never as a
  `contextRefs` entry.** `schema.mjs`'s `assertSafeRefOrId` restricts every
  context ref to `[A-Za-z0-9_-]+` or a `$ref:` placeholder — an arbitrary
  filesystem path (slashes, dots) cannot legally be a context ref today.
  `objective` (top-level and per-step) has no charset restriction, only a
  length cap, so the plan path is folded into the produce step's own
  objective text instead. This is also exactly why "forbidden context ref"
  is testable at all: a caller who tries to pass a raw path as an EXTRA
  context ref (this module's optional `contextRefs` param) hits the same
  existing charset check.
- **`targetActorId` is omitted on every step.** This fixture binds exactly
  one actor per role at the first-pass graph positions, so the engine's own
  `resolveDeclaredOperationActor` resolves it from the declared
  FlowDefinition — reading declared content, not choosing it. (Carried-
  forward Gap #2 in `P00.1.md` §4 — actor ambiguity at two graph positions —
  does not apply here: the first pass has no such position.)
- **`protocolRef.id` is a pinned constant** (`MASTER_LOOP_PROTOCOL_ID`), not
  a caller-facing parameter — this launcher targets ONE fixture by design
  (the phase title itself: "MVP4 thin surface launcher" for "the declared
  Master Coordination fixture"). "Unknown fixture id" is therefore not a
  launcher-owned check; it is proven by mutating the composed request's
  `protocolRef.id` after composition and showing the SAME
  `loadCoordinationProtocol` call `run.mjs` already makes (line 214) refuses
  it identically — defense-in-depth proof, zero duplicated logic.
- **`expectedFixtureVersion` is the one genuinely new check.**
  `schema.mjs`'s `PROTOCOL_REF_ALLOWED_KEYS` is `{'id'}` only — no version
  field exists anywhere in the request schema, and `openDeclaredProtocolSession`
  pulls whatever version happens to be registered without comparing it to
  anything. This is the one gap `schema.mjs` genuinely cannot cover (it has
  no notion of "expected" version), so `buildMasterLoopRequest` adds exactly
  one new check: if the caller names an expected version, `loadCoordinationProtocol`
  is called up front and the actual `metadata.version` must match, or the
  call fails before composing anything.
- **Bad file path is the other genuinely new check** — `schema.mjs` never
  touches the filesystem, so plan/artifact path existence is checked here
  via `fs.existsSync` against the path resolved from `ctx.cwd`.
- **R3 (no prompt runtime):** confirmed by construction — this module never
  imports, reads, or references
  `docs/architect/agent-coordination/playbooks/prompts/master-coordinator.md`
  anywhere; the free-text `objective` strings it builds are short, mechanical
  ("Review the candidate produced from <path>.") and carry no product/
  synthesis logic.

## 5. What Reuses `schema.mjs` vs. What Is New

schema at all). No engine-level (`src/runner/coordination/*.mjs`) file was
touched.
