## R4 — the resume gap, confirmed, and the fix

### The gap, confirmed by reading before assuming

Per this cell's own dispatch (`current-cell.md`), `resumeSession`
(`session-engine.mjs:376`) was checked before being trusted:

```js
export function resumeSession(coordinationId, opts = {}) {
  return replaySession(coordinationId, opts);
}
```

Confirmed: literally a `replaySession` re-export, read-only, not a
dispatch-continuation door.

The real gap, confirmed by reading `src/verbs/coordination/run.mjs` before
this cell's edit: `runCoordinationUseCase` unconditionally called
`openStandaloneSession`/`openDeclaredProtocolSession` at the top of every
request. `openSession` (`store.mjs:178`) claims `coordinationId` via an
exclusive `fs.mkdirSync`; on `EEXIST` it throws
`CoordinationError('validation', 'coordination session "<id>" already
exists')`. Reproduced live before any fix (the pre-existing test this cell
replaced, `coordination-run-live-proof.test.mjs`'s old "re-running the same
live request file is refused at session open" case): a second real
`fgos coordination run --file <same request, same coordinationId>`
invocation failed at exit code 4 with exactly that message, before ever
reaching a dispatch/authorize/disposition call.

### The fix — confirmed safe before writing it

Before building on it, confirmed (not assumed) that `dispatchDeclaredOperation`
and `authorizeDeclaredOperation` are genuinely session-state-driven, not
call-sequence-driven: both open with `const manifest = readManifest(coordinationId,
opts)` — a fresh disk read on every call, keyed only by `coordinationId`.
Neither has any in-memory state that persists across separate
`runCoordinationUseCase` invocations, and neither cares whether the session
was opened in this process or a prior one. This is the exact assumption the
cell brief asked to be verified before building on it; it held.

Given that, the fix is a small, surgical surface-layer branch in
`src/verbs/coordination/run.mjs`, not new engine plumbing:

```js
function findExistingManifest(coordinationId, engineOpts) {
  if (coordinationId === undefined) return undefined;
  try {
    return resumeSession(coordinationId, engineOpts).manifest;
  } catch (err) {
    if (err instanceof CoordinationError && err.category === 'not-found') return undefined;
    throw err;
  }
}
```

...used at both existing open call sites:

```js
manifest =
  findExistingManifest(request.coordinationId, engineOpts) ??
  openStandaloneSession({ ...openParams, primaryRole: request.primaryRole }, engineOpts);
// and, symmetrically, for declared-protocol:
manifest =
  findExistingManifest(request.coordinationId, engineOpts) ??
  openDeclaredProtocolSession({ ...openParams, definitionId: request.protocolRef.id }, engineOpts);
```

`resumeSession` is used rather than reaching into `replay.mjs` directly —
its own doc comment says it exists precisely "so callers have one obvious
'resume' door on this module rather than reaching into `replay.mjs`
directly." This is the FIRST real caller of that door for its stated
purpose. `resumeSession(...).manifest` is byte-identical in shape to what
`openStandaloneSession`/`openDeclaredProtocolSession` themselves return
(both ultimately read/write the same `session.json` via
`readManifestRaw`/`writeManifestRaw`), so nothing downstream in `run.mjs`
needed to change: `manifest.coordinationId`, `.definitionRef`, `.objective`
are read identically either way.

Only an EXPLICIT `request.coordinationId` is ever treated as a resume
candidate — an auto-generated id (the default, `coordinationId` omitted)
always opens fresh, since by construction it cannot already exist. A
`not-found` `CoordinationError` (session genuinely does not exist yet) opens
a new session, unchanged. Any OTHER error (corrupt log, schema-version
mismatch, dangling/foreign/out-of-order ref) is re-thrown as-is — a corrupted
existing session is never silently treated as "new" and never gets a second
`mkdirSync` attempted over it.

**Bug-taxonomy check (this cell's own "reaches the SAME doors, not a
parallel path"):** resume adds zero new dispatch/authorize/disposition call
sites. Every step in a resumed request's `steps[]` array reaches the exact
same `dispatchDeclaredOperation`/`dispatchResearchFanOut`/
`authorizeDeclaredOperation`/`recordDriverDisposition` calls a fresh-open
request already used — confirmed by inspection: the only change in
`run.mjs` is which of two producers `manifest` comes from, nothing in the
step-processing loop below it changed.

### Why this doesn't reopen the concurrency risk P03.2's Red-Team already closed

P03.2's Red-Team target 1 proved "concurrent `openSession`, same
`coordinationId`" resolves to exactly 1 winner (53/53 real trials). This
cell's fix does not touch `openSession`'s own atomicity — a genuine RACE
between two processes (`findExistingManifest` sees `not-found` in both,
both call `openSession`, one wins the `mkdirSync`, the other gets `EEXIST`
and now throws unhandled, since `findExistingManifest` is only consulted
BEFORE the open attempt, not wrapped around it) still resolves the same way
it did before this cell: one throws "already exists," the loser's whole
`runCoordinationUseCase` call fails. What's NEW is only the SEQUENTIAL case
— a second call that starts AFTER the first one's `openSession` has already
returned sees the session via `resumeSession` and continues it instead of
refusing. A genuinely concurrent RESUME (two processes racing to resume and
dispatch into the SAME already-open session at the same time) is a new
concurrency shape this cell did not stress-test with real multi-process
trials — flagged explicitly in Gaps below as a Red-Team target, matching
this track's own division of labor (Doer proves correctness/idempotency
mechanics; Red-Team hammers concurrency).

## R4's live proof — two real CLI invocations, same coordinationId

### Commands

Full request-file content, split point, and CLI invocations, reproduced
both as an executable test (`coordination-run-live-proof.test.mjs`, new
test named below) and as a standalone script outside the test runner
(same pattern P03.2's own trace used):

```bash
FGOS_DISABLE_OPPORTUNISTIC_CHECKS=1 node standalone-resume-proof.mjs
```

**Split point.** The 11-step Master Loop request is split after step 4
(`authorize-revision`), BEFORE `revise` ever dispatches:

- Call 1 (`part1.json`): `produce`, `review`, `red-team`, `authorize-revision`.
- Call 2 (`part2.json`), SAME `coordinationId`: `revise`,
  `reject-first-pass`, `authorize-reviewer-recheck`, `reviewer-recheck`,
  `authorize-red-team-recheck`, `red-team-recheck`, `accept-revision`.

This split point is deliberate, not arbitrary: `evaluateSessionQuorum`
requires every required actor (`doer`, `reviewer`, `red-team`, `fixer`) to
have at least one completed Assignment before `closeSessionByQuorum` can
succeed. Splitting any LATER than this (e.g. after `revise`) would let Call
1 alone satisfy quorum (all 4 actors done) and close the session to
`completed` before Call 2 ever runs — turning the "resume" test into a
"resume-a-terminal-session" test by accident. Splitting here proves the
session is genuinely still `active` (quorum missing exactly `[fixer]`) when
Call 2 starts.

**No `$ref:` label survives a call boundary** — `run.mjs`'s `labels` map is
created fresh (`Object.create(null)`) once per `runCoordinationUseCase`
call. Call 2's steps therefore name Call 1's own Assignment ids LITERALLY,
substituted from Call 1's real reported output — `resolveRef`'s own
documented "already safe-charset-checked id, an advanced/resume use case"
path, exercised live for the first time by this cell.

**A related question the cell brief specifically asked to check:** does
resume open a NEW identity-bypass on ordinary (non-driver-authorized)
`operation`/`fan-out` steps — i.e. could a SECOND request supply a
DIFFERENT `writerId` than the session's own `provenanceRoot.writerId` and
still dispatch new required-first-pass work into someone else's session?
Checked by reading `dispatchDeclaredOperation`'s body: the `writerId`
parameter is used ONLY to stamp the new Assignment's own `caller.writerId`
provenance field — it is never compared against `manifest.provenanceRoot.writerId`
anywhere in that function. **This is not a NEW gap resume introduces**: no
identity check on ordinary dispatch existed BEFORE this cell either — it
was simply unreachable, since a single request always supplied the SAME
`writerId` for both `openParams` and every dispatch call by construction
(one object, one call). `assertDriverIdentity` (the ONLY writerId-equality
gate in the whole module) has always been scoped to `authorize`/`disposition`
only, by design — `thin-launcher-surface-readiness.md`'s own hole #4 ("no
driver handoff... a launcher run by a different operator cannot authorize
anything in it... a product decision to make before it becomes load-
bearing, not a bug to route around") already names this exact asymmetry as
an accepted, pre-existing architectural property, not a defect. Recorded
here rather than silently assumed; no new test written, since there is
nothing resume-specific to prove — the property (or lack of one) is
identical with or without resume. Flagged in Gaps below as worth a future
product decision if a driver-handoff/multi-operator story is ever built on
top of resume.
