### MED-1 — provenance companion fields never checked against the authorization they name

`assertAuthorizationSpendable` verified `authorizationId` names a real,
unconsumed `operation-authorized` event, but never checked that the
`operationId`/`nodeId`/`invocationKey`/`contextGrant` riding alongside it
**match** that event — reproduced: a write naming a real `authorizationId`
while lying about all four companion fields was accepted, replay stayed
clean. Partially defeated R5's key-reuse guard (name an unused key) and left
R6's on-log `contextGrant` unverified against the real grant.

**Disposition: FIXED.** `assertAuthorizationSpendable` (`store.mjs`) now
compares every present provenance field against the `issued` event's own
payload and refuses on any mismatch, naming the mismatched field(s).
Regression: `coordination-store.test.mjs` "assertAuthorizationSpendable
refuses provenance whose operationId/nodeId lie about the authorization they
name" (nodeId mismatch, contextGrant.refs mismatch). Side effect, not a
regression: the pre-existing R5 test for a double-spent `invocationKey` could
previously only reach that check via a provenance whose `invocationKey` did
not match its own `authorizationId`'s real event — MED-1 now refuses that
exact shape one check earlier, for a more precise reason; the test was
updated to assert the new (earlier, correct) refusal rather than weakened
(see its updated in-line comment).

### MED-2 — binding invocation cap enforced on only ONE of two writing branches

`assertWithinBindingInvocationCap` was called only on the genuinely-new-
taskKey path in `createSessionAssignment`; the crash/self-heal branch never
ran it. Reproduced: cap 2, two invocations spent, a crash-produced
unregistered claim for a third self-healed past the cap — 3 Assignments
materialized at a cap of 2. This is P02.1's own HIGH-1 bug class (a check
missing from one of two writing branches) recurring in the R7 layer, and the
phase's Acceptance criteria ("`activation.maxInvocations` is enforced...")
carries no carve-out for self-heal.

**Disposition: FIXED, in this cell** (Coordinator ruling: this repeats a
named HIGH-severity bug class and the Acceptance criteria requires the cap
enforced with no exception; deferring it would ship this cell's own R7
non-compliant). The self-heal branch now calls
`assertWithinBindingInvocationCap` with the same `authorizationProvenance`
MED-1 has already verified belongs to the authorization being completed;
the cap's existing `ownAuthorizationId` exclusion means completing an
interrupted registration never double-counts against itself, while a cap
already exhausted by OTHER invocations still refuses. Regression:
`coordination-store.test.mjs` "the binding invocation cap gates the
self-heal writing branch too, not only the genuinely-new-taskKey path"
(control on the new-taskKey path + the self-heal path, both refused
identically). This also makes the ORIGINAL Proof Matrix claim — "an
authorization forged past that door through the raw store door still has
its dispatch refused by the lock-held count" — true unconditionally, where
before it held only on the new-taskKey path.

**NOT fixed, and explicitly out of this cell's scope:** the four
PRE-EXISTING session-wide caps (`maxAssignmentsForSession`,
`maxRoundsForSession`, `maxConcurrencyForSession`, `maxRoundsForActor`) sit
below the SAME claim branch and share the identical gap (Reviewer confirmed
this empirically for `maxAssignmentsForSession`). Fixing the binding cap
alone while leaving these four siblings unfixed is a real, named
inconsistency — recorded as a forward gap in `index.md`, same treatment as
`cohort-planner.mjs`'s disambiguation gap, rather than silently expanding
this cell's blast radius onto four checks it does not own.

### MED-3 — default taskKey makes a second authorized invocation a silent no-op

With no explicit `taskKey`, `dispatchDeclaredOperation`'s default derivation
(`declared:${operationId}`, no incoming topology edge) carries no
per-invocation discriminator: reproduced end-to-end through real doors — a
second `authorizeDeclaredOperation` + `dispatchDeclaredOperation` call
silently returned the FIRST call's Assignment (`resumed: true`), and the
second authorization was never consumed, with no error. This is exactly the
shape `coordination-session.md`'s "Recheck Is Not Retry" clause names as
forbidden, and it made this cell's own R7 feature (`maxInvocations > 1`)
unreachable through the default path.

**Disposition: minimal guard FIXED in this cell, full fix deferred to
Phase 03 per Non-Goals** (Coordinator ruling: implementing recheck-aware
`taskKey` derivation IS recheck semantics, out of this cell's Non-Goals; but
silently returning success while discarding a real authorization is a
correctness defect independent of recheck, worth closing now). Added: when a
dispatch would resolve to an existing Assignment via taskKey collision WHILE
a fresher, unconsumed authorization sits on the log for the exact same
binding, `dispatchDeclaredOperation` now refuses loudly instead of resuming
silently — inventing no new taskKey-derivation behavior, only converting a
silent wrong result into a correct, informative error. A genuine idempotent
resume (no unconsumed sibling authorization pending) is unaffected.
Regression: `coordination-driver-authorization.test.mjs` "a fresh
unconsumed authorization is refused rather than silently discarded by a
same-DEFAULT-taskKey resume" plus its control ("a genuine
idempotent resume with no fresh authorization pending is unaffected by the
silent-discard guard").
Phase 03 forward gap recorded in `index.md`: derive the default `taskKey`
from `invocationKey`/`authorizationId` so a second invocation reaches a NEW
Assignment rather than needing a caller-supplied `taskKey` or hitting this
guard.

### MED-4 — same-session scope check was whole-string-prefix-anchored, not segment-based

`assertRefsOwnedBySession`'s `/^asgn_/`/`/^coord_/` tests matched only when
the REF ITSELF started with that prefix, so a path-form ref into another
session's directory (e.g. `.fgos/coordination/sessions/coord_other/
events.jsonl`) matched neither pattern and passed both the write-time check
and the dispatch-time gate. The contract clause is unconditional ("Cross-
session grant authority is out of scope — no design intent for it exists
anywhere in the substrate proposal").

**Disposition: FIXED, together with L1** (Coordinator ruling: this track has
been rigorous everywhere else in this cell — disk-fresh counting,
session-scoped keys, now provenance consistency — a driver-trust reading
that leaves an unconditional contract clause enforceable only against a
naive bare-id spelling would be the odd one out; Reviewer's own open
question 1 is resolved this way). `assertRefsOwnedBySession` now scans each
ref by PATH SEGMENT (split on `/`/`\`), so a foreign `coord_`/`asgn_`
segment anywhere in a path-form ref is caught the same as a bare id.
Regression: `coordination-driver-authorization.test.mjs` "a
PATH-FORM grantedContextRefs entry into a different session is rejected the
same as a bare id".

### R7 ruling — the two counting layers are intentionally asymmetric, and the issuance layer is stricter than the contract's literal wording

Confirmed as the Doer's Gaps text intended, with one correction: the
ISSUANCE layer (`store.mjs`) counts every `operation-authorized` event for
the binding, spent or not — stricter than `flow-definition.md`'s literal
"the binding's *consumed*-invocation count is counted fresh from the on-disk
`operation-authorized` events" wording, which only the DISPATCH layer
matches exactly. Concrete consequence: an authorization burned by a dispatch
that failed before materialization permanently consumes binding budget; a
plain retry (same `authorizationId`) is unaffected, only a genuinely-new
authorization is blocked. Accepted as deliberately fail-closed — no code
change — but recorded here as asymmetric-by-design rather than two readings
of one ambiguous phrase, correcting the Doer's Gaps framing.

### R8 ruling — accept the comparison as implemented; do NOT record R8 as closed

`authorizedBy.id === manifest.provenanceRoot.writerId` is accepted as the
maximal step this codebase supports, and it does close what P02.1 recorded
(no caller can name an arbitrary driver id anymore). But what shipped is
exactly the `writerId`-alone case R8's own escape clause names ("`writerId`
alone is not enough if the existing API cannot distinguish an arbitrary
event writer from the driver") — the API still cannot make that
distinction, so the clause is triggered, not satisfied. **R8 status:
satisfied-modulo-a-named-follow-on, not closed.** No stronger comparison is
available anywhere in this codebase today (every identity is the same
self-declared string at every entry point), and building attestation would
be inventing contract semantics rather than implementing the accepted
text — correctly refused by the Doer. Behavioral consequence recorded as a
forward gap in `index.md`: driver handoff is now structurally impossible (a
session opened by writer A can only ever be authorized by A; Phase 03's
`driver-disposition-recorded` will inherit the same pin).

## Gaps

### Interpretations recorded for review

- **R8: what "matching the session's driver identity" means, exactly.** The
  accepted contract gives `authorizedBy` as
  `{type: "driver", id: <driver-identity>}` and says only that "the driver is
  not a `spec.actors[]` worker"; the manifest gives `provenanceRoot` as the
  "Caller identity that opened the session (writer identity)". Nothing in the
  accepted text names a third identity, and this codebase has no identity
  registry, attestation, or signing layer of any kind. **Implemented
  comparison: `authorizedBy.id === manifest.provenanceRoot.writerId`,**
  checked lock-held in `store.mjs`'s `authorizeOperation` — the one door every
  authorization passes through. This is the phase file's "tied to session
  driver/provenance root" read literally, using the only durable driver
  identity a CoordinationSession actually persists.
  **What this does and does not buy, stated plainly**, because R8's own text
  anticipates exactly this ("`writerId` alone is not enough if the existing
  API cannot distinguish an arbitrary event writer from the driver"):
  - It DOES close the gap P02.1 recorded — "any caller able to reach
    `authorizeDeclaredOperation` can name an arbitrary driver id" is no
    longer true. The id is now pinned to a value the session itself
    recorded at open time and cannot be chosen freely.
  - It does NOT make the identity unforgeable. `writerId` is a
    self-declared string at every entry point in this codebase
    (`openDeclaredProtocolSession({writerId})`,
    `dispatchDeclaredOperation({writerId})`, `caller.writerId` on every
    Assignment), so a caller that knows which identity opened the session can
    still present it. Distinguishing an arbitrary event writer from the
    driver *cryptographically* would require an authentication/attestation
    primitive that does not exist anywhere in this repo, and inventing one
    would be new contract semantics rather than implementing the accepted
    text — so it is deliberately NOT done here. **Recommend Review/Red-Team
    rule explicitly on whether pinning-without-attestation satisfies R8, or
    whether a follow-on phase owes a real writer-identity primitive.**
- **Existing fixture updated, as the cell anticipated.**
  `coordination-store.test.mjs`'s `issueAuthorization` helper wrote
  `authorizedBy: {type: 'driver', id: 'driver-1'}` against sessions opened
  with `provenanceRoot: {writerId: 'writer-1'}` — a synthetic id that no
  identity check could ever have passed. Changed to `'writer-1'` (one line,
  plus a comment saying why). This is the "existing test fixtures need
  updating to use a real, checkable driver identity" case the Bug Taxonomy
  named as expected and fine. No assertion was weakened, and the three tests
  that use the helper still assert exactly what they asserted before.
- **R6: what "resolve to an artifact/ref owned by this same
  `coordinationId`" means for a ref that resolves to nothing.**
  `assertRefsOwnedBySession` reuses `validateConsultProposal`'s EXISTING rule
  verbatim rather than inventing a second one: a ref naming a real, on-disk
  Assignment that is not a member of this session is refused; a ref naming a
  different `coord_*` session is refused; a string that merely resembles an
  id but resolves to nothing on disk is left alone. This codebase has no
  artifact registry to resolve a non-Assignment ref against (the shipped
  fixtures grant things like `artifact:candidate@2`), so rejecting
  unresolvable strings would mean policing naming conventions rather than
  catching a foreign-state leak — and would diverge from the sibling rule
  this file already applies one function away. Flagged rather than assumed.
- **R6: which base context stays legal.** The contract allows the granted
  refs "plus whatever base session context is always legal for that
  Assignment (its own declared inputs)". The one such ref in this runtime is
  the mediated-visibility upstream request under a declared topology edge,
  where `resolvedContextRefs` is `[fromAssignmentId]` **by construction** —
  there is no parameter path for caller-supplied refs to reach that branch at
  all, and the id is already validated to belong to the edge's declared
  `from` actor. Everything else on a driver-authorized dispatch is
  caller-supplied and must be named by the grant. R6 is implemented as a
  CEILING, not an injection: a grant permits reads, it does not add refs to
  the contract the caller did not ask for (phase file: "may receive only ...").
- **R7: `maxInvocations` is forwarded regardless of activation mode.** The
  binding cap is counted from `operation-authorized` events, which a
  `required` binding never has, so declaring `activation: {maxInvocations: 3}`
  without `driver-authorized` stays inert rather than quietly meaning
  something else. The existing "explicit activation.mode required" test
  (which declares `maxInvocations: 2`) still dispatches unchanged.

### Genuinely open after this cell

Nothing in R5-R8 was deferred. Two things a Red-Team should probe rather than
take on trust, since both are the class this track's history says sequential
tests miss:

1. **Concurrency.** Every new check is lock-held on a fresh from-disk read

   check was deliberately folded into `assertAuthorizationSpendable` — the

   carries that same tension. Worth an explicit ruling that this reading is
   the intended one.
