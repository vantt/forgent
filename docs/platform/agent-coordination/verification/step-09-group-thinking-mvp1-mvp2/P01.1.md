### HIGH-1 — `cohort-planner.mjs`'s actor-keyed operation resolver is *already* broken by this fixture's shape; this cell's Gaps section names the adjacent `activation` gap but not this concrete, already-live landmine

- **Location:** `src/runner/coordination/cohort-planner.mjs:307-316`, function `resolveActorOperation(definition, actorId)`:
  ```js
  function resolveActorOperation(definition, actorId) {
    for (const node of definition.spec.graph.nodes) {
      for (const opRef of node.operations) {
        if (opRef.actor === actorId) {
          return definition.spec.operations.find((op) => op.id === opRef.ref);
        }
      }
    }
    return undefined;
  }
  ```
  This resolves "the operation wired to `actorId`" by scanning `graph.nodes` in array order and returning the **first** match — exactly the failure mode the substrate proposal's own §9 gap table names verbatim: *"Materialization must select the exact node-operation/edge binding, not just the first incoming edge for an actor. One actor may receive first-pass and recheck operations from different sources."* (`docs/architect/proposals/step-09-group-thinking-substrate.md` §9, "Edge disambiguation" row).

- **Why this fixture is the trigger, not a hypothetical:** `standalone-master-coordination-loop.yaml` is the **first** fixture in this repo where a single actor id is bound to two *different* operation ids at two different graph nodes: actor `reviewer` is bound to `review-candidate` in `phase-first-pass` (line 107) **and** to `reviewer-recheck` in `phase-recheck` (line 119); actor `red-team` is bound to `red-team-candidate` in `phase-first-pass` (line 109) **and** to `red-team-recheck` in `phase-recheck` (line 121). Confirmed by reading both sibling fixtures (`declared-consult.yaml`, `independent-research-fan-out-fan-in.yaml`): every actor in both appears bound to exactly one operation id throughout the whole graph (`independent-research-fan-out-fan-in.yaml`'s two researcher actors are each bound once, to the *same* op id `independent-research`, not two different op ids — a different, order-irrelevant shape that `resolveActorOperation` handles fine since `find` on operations by a single shared `op.id` returns the same operation regardless of which node position matched first). So `resolveActorOperation(definition, 'reviewer')` against this new fixture will **always** return `review-candidate` (whichever node comes first in `graph.nodes` array order), and there is no way to ever obtain `reviewer-recheck` through this function — not an edge case, a structural impossibility as written.

- **This is not merely Phase-02-scoped speculation — the vulnerable function is already live, wired, and tested today:** `cohort-planner.mjs`'s `planCohort()` (which calls `resolveActorOperation` once per actor, per its own docstring at line 369: "resolve its wired operation (role/tier/capabilities)") is imported and called by `src/runner/coordination/session-engine.mjs:1631` inside `dispatchResearchFanOut`, and is exercised by a real, passing test suite (`test/runner/cohort-planner.test.mjs`, `test/runner/coordination-research-fan-out.test.mjs`). `planCohort` is generic over any validated `CoordinationProtocol` FlowDefinition, not fan-out-specific by name or by any code-level restriction — nothing in `planCohort`/`resolveActorOperation` limits it to fixtures shaped like `independent-research-fan-out-fan-in.yaml`. The natural, most-reused path for a future phase to allocate doer/reviewer/red-team/fixer to real executors before dispatching this new fixture's operations is to reuse `planCohort` exactly as-is, because it already exists, is already tested, and is exactly what its docstring describes doing. The moment that happens, `reviewer`'s and `red-team`'s cohort allocation will silently use `review-candidate`'s/`red-team-candidate`'s role/tier/capability requirements for **every** allocation decision involving those actors, including the recheck round — a **silent wrong-value substitution**, not a thrown error, which is worse than a crash because nothing will flag it.
- **Why this fixture's current field values mask the bug today (and why that masking will not last):** in the shipped fixture, `review-candidate`/`reviewer-recheck` (and `red-team-candidate`/`red-team-recheck`) happen to declare identical `role` and no `policy`/`capabilities` fields at all, so `resolveActorOperation` picking the wrong one of the pair currently has zero observable effect if `planCohort` were run against this fixture today. But that is a coincidence of the current field values, not a structural safeguard — the whole point of a "recheck" operation (per the substrate's own §9 "Recheck distinct from retry" row) is that it is expected to eventually diverge from the first-pass operation (e.g. a stricter `policy.minTier` for a recheck pass, or different `capabilities`). The first time a future cell gives `reviewer-recheck` its own `policy`/`capabilities`, this resolver will silently allocate against the wrong operation's requirements.
- **Disposition:** correctly out of scope to *fix* in this cell (`src/runner/coordination/**` is Do-Not-Touch here, and R1 requires zero `src/` diff — confirmed still true). This is a **documentation/trace finding**, not a fixture defect: the fixture itself is a faithful, correct rendering of the substrate's target MVP1 shape (verified against §6 verbatim, per the existing CLEAN Review point 4), and *should* have this shape — the bug is entirely in `cohort-planner.mjs`'s pre-existing resolver, which this cell did not write and is not required to fix. The finding is that this cell's own Gaps section discusses the schema-level `activation` gap (adjacent, but distinct — that gap is about materialization *authorization*, this one is about materialization *selection*) without naming this concrete, already-instantiated instance of the substrate's own named "Edge disambiguation" gap, even though this cell is the one that introduced the first fixture shape capable of triggering it.
- **Smallest fix direction (for whoever picks this up, likely Phase 02/03, not this cell):** add a Gaps entry here (or a forward-pointer in Phase 02's own cell doc) naming `cohort-planner.mjs:307` `resolveActorOperation` explicitly, and require it be re-keyed by the exact `(nodeId, operationId, actorId)` triple — mirroring `session-engine.mjs:809-824`'s `resolveDeclaredOperationActor`, which already disambiguates correctly today because it is keyed primarily by `operationId` (an explicit parameter), not by `actorId` alone — before `planCohort` is ever pointed at this fixture (or any future fixture reusing one actor across multiple distinct operations).
