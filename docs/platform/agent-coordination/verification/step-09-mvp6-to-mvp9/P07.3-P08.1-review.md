### 1.1 Terminal-transition authority is genuinely retained (P07.3 priority 1)

`validateSessionAggregation` (`src/runner/coordination/session-engine.mjs:3061-3182`)
performs exactly one write: `recordAggregationValidation` at line 3161. It
never calls `transitionSessionStatus`, `transitionSessionStatusLocked`, or
`closeSessionByQuorum`. I confirmed this by reading the whole function body,
not only by trusting the static test.

The static test itself is real, not name-only. `test/runner/coordination-aggregation.test.mjs`
slices the engine source between `export function validateSessionAggregation(`
and `\nexport async function retrySessionTask(`, asserts the slice contains
no transition primitive, and asserts it *does* contain
`classifyAggregationOutcome(` — so it fails if the evaluator call is ever
removed, not just if a transition is added. It also asserts `end > start`,
so a reorder fails loudly instead of silently scanning an empty string.

The consumption side is genuinely refuse-only. `closeSessionByQuorum`
(lines 2827-2871) reads the validated record from `replayed.aggregations`

test proves that by leaving a real `no-consensus` aggregation on the log and
closing `completed` anyway.

### 1.2 The partial-cohort bypass is genuinely fixed in the shipped code (priority 2)

I reasoned through the current code rather than the described bug. The
all-of rule holds at both levels in `validateSessionAggregation`:

- Level 1 (`:3106-3117`): `resolveOperationOutcome` computes
  `satisfied: branches.every(b => b.satisfied)` (confirmed at
  `session-engine.mjs:1260`). When false, the loop `continue`s — the
  operation contributes **no** source, and each unsatisfied branch is named
  into `missingActors`/`failedActors`.
- Level 2 (`:3124-3134`): every branch is mapped to a pinned source first;
  `built.some(entry => entry.pinned === null)` then discards the **whole**
  operation, naming every branch into `unresolvedContributionRefs`. Pinned
  siblings cannot cover for an unpinned one.

I could not construct a half-answered cohort reaching `consensus`. Any
discarded operation is absent from `sources` while still present in
`sourceOperationRefs`, so `classifyAggregationOutcome`'s own source-coverage
check fails and forces `no-consensus`. The runtime test confirms this
empirically at the observable level that matters: with researcher-b never
run, `sourceResultRefs.length === 1` (only `review` survives) and
`missingSourceOperationRefs === ['research']` — researcher-a's *satisfied,
pinned* result contributed nothing. That is the corrected behavior, not the
described bug.

This also makes the invariant replay depends on true by construction:
`consensus ⇒ missingActors/failedActors/unresolvedContributionRefs all
empty`.

## Part 2 — Findings

### F1 — MEDIUM — The aggregation terminal gate is opt-in and currently unreachable in production; this makes the trace's headline residual over-weighted

**File/line:** `src/runner/coordination/session-engine.mjs:2856` (the
`if (aggregationId !== undefined)` guard); `src/verbs/coordination/run.mjs:458`.

**Evidence (grep, run by me):** the only production caller of
`closeSessionByQuorum` is `src/verbs/coordination/run.mjs:458`, which calls
`closeSessionByQuorum(manifest.coordinationId, {}, engineOpts)` — no
`aggregationId`. `validateSessionAggregation` has **zero** callers outside
`session-engine.mjs` itself and the new test file. No committed fixture under
`core/` declares `completion.aggregation`.

**Failing scenario:** a protocol declares `completion.aggregation`, no one
ever validates it, and the session closes normally. Nothing notices.
`closeSessionByQuorum` does not hold the FlowDefinition, so it cannot know an
aggregation was declared and skipped.

**Requirement bearing on it:** phase-07 Exit — "Completion eligibility,
cognitive validation, and terminal authority remain separate" is satisfied;
but "Agent Coordination may use a validated cognitive outcome as terminal
input" is proven only at the API level, never as an enforced protocol
property.

**Why this is a review finding and not just a deferral:** the Doer disclosed
this honestly as Gap #4, and CLI wiring is explicitly P07.4's job, so the
*scope* is fine. What is not fine is the weighting in the trace. The trace
spends its entire "Concern" headline and a full section on the forged
`consensus` residual, when the gate's opt-in nature makes that forgery
**strictly unnecessary**: a driver who wants an unjustified close does not
need to forge an `aggregation-validated` event at all — it can simply omit
`aggregationId`. The forgery buys the attacker nothing the plain path does
not already give them. This makes the residual materially *less* severe than
P06's raw-door stamp forgery (which granted context visibility that
otherwise would not exist), not the same severity as the trace states.

**Smallest fix direction:** none in this cell. P07.4 should (a) make
`closeSessionByQuorum` definition-aware enough to refuse a close when the
protocol declares `completion.aggregation` and no validated aggregation
exists, and (b) correct this weighting when it promotes the contract text.

### F2 — MEDIUM — P08.1's "real Assignment/Run provenance" is presence-only, and the gap is not disclosed

### F4 — LOW — A source operation with zero declared bindings yields an unexplained `no-consensus`

**File/line:** `src/runner/coordination/session-engine.mjs:3096-3117`.

**Failing scenario:** a declared `sourceOperationRefs` entry whose operation
has no binding actors. `resolveOperationOutcome` returns
`satisfied: [].every(...) === true` (vacuous), so the `!outcome.satisfied`
branch never runs and no actor is named. `built` is `[]`, `built.some(...)`
is false, and the push loop adds nothing. The operation silently contributes
zero sources.

**Impact:** **not** a consensus bypass — I checked. The evaluator's
source-coverage check still fails the operation (it is in
`sourceOperationRefs` but absent from `sources`), forcing `no-consensus`; and
if it is the *only* source operation, the `sourceResultRefs.length === 0`

event carries `outcome: no-consensus` with no `missingActors`,
`failedActors`, or `unresolvedContributionRefs` explaining why, which
undercuts the "named, never dropped" property the surrounding comments claim
for every other discard path.

**Smallest fix direction:** treat `outcome.branches.length === 0` as its own
named condition rather than letting it fall through the vacuous-satisfied
path — e.g. record the operationRef into a reason field, or reject the
declaration at definition time if a declared source operation has no bindings.

## Part 4 — On the Doer's own disclosed gap (priority 8)

The disclosure is **accurate as far as it goes, and the mechanism is
correctly diagnosed.** I confirmed it independently: the session's own driver
can call `recordAggregationValidation` with `outcome: 'consensus'` and
`sourceResultRefs` drawn from `manifest.assignmentRefs`. Every store-door
check passes (payload shape, `status === 'active'`, `assertDriverIdentity`,
assignment ownership), and every replay check passes (driver identity matches
`provenanceRoot.writerId`; each ref has an earlier `result-linked`; the
consensus-consistency check is satisfied by simply omitting the three
explanatory fields). No `classifyAggregationOutcome` call is needed.

The structural reason given is also correct: `replay.mjs` imports nothing
from `src/runner/definitions/`, so it cannot know which operations were
declared sources and cannot re-derive the evidence set. The trace's dismissal
of an inputs-hash as theatre is sound — anyone who can write the event can
compute the hash.

**Where I differ from the trace:** it characterizes this as "the *same*
unmediated-store-door trust boundary Phase 06 already named… nothing here
narrows or widens it." It is the same **class**, but it is materially **less
consequential**, for the reason in F1: because the aggregation gate is
refuse-only *and* opt-in, a forged `consensus` grants the forger nothing.
Under P06, forging the reserved `protocol-operation:` stamp through the raw
`createSessionAssignment` door produced context visibility that would not
otherwise exist — a real capability gain. Here, a driver who wants an
unjustified close just omits `aggregationId` and the close proceeds
unexamined. The forgery is a strictly harder route to an outcome already
available for free.

So: not worse than P06/P06.3 anticipated, and not different in kind — but
the trace's framing overstates it, and in doing so under-weights the
mechanism that *does* matter (F1: nothing requires an aggregation). I would
ask P07.4 to correct that emphasis when it promotes the contract text, rather
than carry the current framing into `coordination-session.md`.

One point in the trace's favor that I want on the record: the design choice
that `validateSessionAggregation` takes **no `outcome` parameter** is the
real defense here, and it holds. Everything the verdict depends on is derived
inside the engine — declared sources from the definition, answering
Assignments via the stamp-verified `resolveOperationOutcome` (not actor or
claim-key matching), and each artifact's pin from `settleReports[].sha256`
recomputed against the file **located by derivation from the validated
`assignmentId`/`runId`, never by joining the stored `path` string**. That
last detail correctly avoids re-opening the traversal class R6 closed for
`runId`, and I verified it in the code (`session-engine.mjs`'s
`aggregationSourceFrom`). The mediated door genuinely cannot be talked into a
favorable verdict; what is unproven is that it was used at all.

### New residual — the definition is pinned by id + version, never by content

Not a regression, and not a reason to block; recording it because P07.4 will
read this trace as a statement of what the mediated door guarantees.

The manifest pins `definitionRef.{id, version}`. Nothing pins the *body*. Two
reproduced consequences:


**Why this is not a finding against this fix:** I checked whether the
exposure is specific to the aggregation door or shared with the four sibling
precedents it was told to copy. It is shared — `authorizeDeclaredOperation`
authorizes a binding that exists *only* in an attacker-supplied
`packageRoot` definition:

```
honest packageRoot                  REFUSED ("not wired into this protocol's graph")
attacker packageRoot (sibling door) ACCEPTED
```

So this is a pre-existing, repo-wide property of every definition-consuming
door, and the fix brought `validateSessionAggregation` to parity — exactly
what the disposition asked for. The capability it needs is also not new:
variant E requires write access to the same `.fgos/` tree the already
disclosed raw-store-door residual writes `events.jsonl` into, so it buys an
attacker nothing they did not already have; variant H2 requires control of
`opts`, the workspace locator, which is the hosting process's own trusted
configuration rather than session input.

the same class as, and belongs beside, F1's opt-in-gate gap.
