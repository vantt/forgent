## Findings

### HIGH — Fan-out visibility-window sources open on the FIRST contributor only, not all (P06.2)

**File/line:** `src/runner/coordination/session-engine.mjs:1052-1077`
(`resolveOperationOutcome`), called from `deriveVisibilityWindowState`
(`:1095-1109`).

**Failing scenario:** a visibility window's `opensAfter.operationRefs[]`
names an operation that is wired to MULTIPLE actors in the graph (fan-out —
one operation template, several independent contributors). `resolveOperationOutcome`
calls `resolveDeclaredOperationActor(definition, operationId)` with no
`targetActorId`, which (per `resolveDeclaredOperationActor`,
`session-engine.mjs:799-814`) returns only `matches[0]` — the FIRST node/actor
pairing found while iterating `spec.graph.nodes`. The window's `open` verdict
(`sources.every((s) => s.satisfied)`, `:1107`) is therefore computed from
ONE fan-out contributor's outcome, never all of them. Once that one actor's
result links, the window opens even if every other fan-out sibling never
dispatched, is still pending, or failed.

**Requirement violated:** this is a textbook instance of the cell's OWN Bug
Taxonomy line 1: *"A partial-window bypass (accepting a ref because SOME but
not all sources are linked)."* It also contradicts Acceptance: "Window
legality is a genuinely separate, additive gate" is undermined when the gate
silently checks only a subset of the actual contributors for a fan-out
source.

**Why this is not hypothetical:** the P06.2 trace itself names "P00.1's
paradigm case" for visibility windows as *"private-first-pass vs.
post-independent-pass"* — i.e. exactly a fan-out research cohort feeding a
synthesis gate. This repo's own real, already-committed protocol
`core/coordination-protocols/independent-research-fan-out-fan-in.yaml`
implements precisely that shape today: `independent-research` is bound to
BOTH `researcher-a` and `researcher-b` at one node (`graph.nodes[1].operations`,
two entries sharing `ref: independent-research`). If this exact, real
protocol were to declare a `post-research-window` gating
`synthesize-findings` on `opensAfter.operationRefs: ['independent-research']`
(the natural, single-entry way to express "wait for the whole cohort," since
`opensAfter.operationRefs[]` names *operation* ids, not actor-qualified
ones), the window would open as soon as ONE of the two researchers reports —
defeating the feature's own headline use case.

**Test coverage:** none. The cell's own fixture
(`test/runner/coordination-driver-authorization.test.mjs:1565-1624`) avoids
this exact shape by giving `research-a`/`research-b` each their OWN
operation id and OWN actor — i.e. it tests "multiple entries in
`operationRefs[]`" (which correctly requires all-of), never "one entry bound
to multiple actors" (fan-out), which is a materially different code path
(`resolveDeclaredOperationActor`'s `matches[0]` branch vs. its
`targetActorId`-supplied branch).

**Disclosure:** P06.2.md's Gaps section does name "Fan-out source operations
are not disambiguated," but frames it as an unproven edge case ("not proven
against a fan-out fixture by this cell's own tests") rather than as a
partial-window-bypass — its own cell's highest-named Bug Taxonomy risk. The
severity is understated relative to what the code actually does.

**Smallest-fix direction:** `deriveVisibilityWindowState`/`resolveOperationOutcome`
would need to resolve ALL actor bindings for a fan-out `operationRef` (every
`{node, ref}` match in `resolveDeclaredOperationActor`'s own `matches[]`
array, not just `matches[0]`) and require every one of them satisfied before
that source counts — the same "every entry, not just one" logic
`deriveVisibilityWindowState` already correctly applies across
`opensAfter.operationRefs[]` itself, extended one level deeper. This can
likely reuse `resolveDeclaredOperationActor`'s existing `matches` computation
without new schema surface, staying inside this cell's own stated scope
(P06.1 schema untouched).

### HIGH — Source resolution matches by actor id alone, not actor+operation, so an actor active on more than one operation can cross-satisfy an unrelated window source (P06.2)

**File/line:** `src/runner/coordination/session-engine.mjs:1061`
(`resolveOperationOutcome`'s `events.find(...)` call).

**Failing scenario:** `resolveOperationOutcome` finds the source Assignment
via
```js
const createdEvent = events.find((event) => event.type === 'assignment-created' && event.payload.actorId === effectiveActorId);
```
— a match on `actorId` ALONE, with no `operationId` filter. This is not a
shortcut the Doer could easily have avoided: verified in
`src/runner/coordination/store.mjs:376`,
`assignment-created`'s payload for a non-driver-authorized (`required`)
dispatch is `{assignmentId, actorId}` only — `operationId` is populated only
via `authorizationProvenance`, which exists solely for `driver-authorized`
bindings (confirmed in P06.2.md's own Design Notes, and independently in
`store.mjs`). So there genuinely is no `operationId` on the event to filter
by for the paradigm "required-source-operation" case this cell targets.

The consequence: if ONE actor is bound to more than one DIFFERENT operation
in the graph — and dispatched for more than one of them in the same session
— `events.find` returns whichever `assignment-created` for that actor
happens to appear FIRST in the log, regardless of which operation a
window's `opensAfter.operationRefs[]` entry actually names. A window source
naming operation A can be satisfied by that actor's unrelated, earlier (or
simply first-in-log) Assignment for operation B.

**Requirement violated:** this is the same failure shape as the cell's own
Bug Taxonomy line 5 — *"an `actor-replaced` path that lets a NEW unrelated
operation ref piggyback on someone else's satisfied obligation"* — except it
requires no `actor-replaced` event at all; ordinary actor reuse across
operations is sufficient. It also breaks the derivation's own documented
intent ("classify exactly the way the operation named in `opensAfter` is
resolved," P06.2.md Design Notes) since the wrong Assignment can be picked.

**Why this is not hypothetical:** the same real, committed fixture cited
above, `independent-research-fan-out-fan-in.yaml`, already has `coordinator-actor`
bound to TWO different operations (`dispatch-research` at `phase-fan-out`,
`synthesize-findings` at `phase-fan-in`) — i.e. "one actor, multiple
operations" is an established pattern in this exact protocol family, not an
invented edge case. It does not trigger in THIS specific fixture only
because `coordinator-actor` is never itself named as a window source in
today's shape — but nothing in the schema or this cell's code prevents a
future protocol from doing so.

**Test coverage:** none — the P06.2 fixture gives every actor exactly one
operation, so this path is never exercised.

**Disclosure:** not named anywhere in P06.2.md's Gaps section. The only
related gap named is the reverse direction (one operation, many actors —
finding above), which is a different code path.

**Smallest-fix direction:** since `assignment-created` carries no
`operationId` for required dispatches, and P06.1's schema is out of this
cell's scope to change, the least invasive fix is likely to also require
`taskKey` on the match — the caller's default derivation is
`declared:${operationId}` (`session-engine.mjs` `dispatchDeclaredOperation`,
resolvedContextRefs/taskKey block) — but `taskKey` is not currently recorded
on the `assignment-created` event either, only mapped indirectly through the
`tasks/<hash>.json` claim file (`peekClaimedAssignmentId`). A real fix likely
needs either (a) resolving the source Assignment through the same
claim-file/taskKey lookup `dispatchDeclaredOperation` already uses for its
own resume path, keyed by the SAME default `declared:${operationId}` taskKey
convention, rather than a bare event-log `actorId` scan, or (b) recording
`operationId` on `assignment-created` for required dispatches too (a
store.mjs schema change, likely out of this cell's declared scope). Either
way this needs a decision, not a silent default, before P06.3 proof/promotion.

## Finding 1 (fan-out partial-window bypass) — CONFIRMED-RESOLVED

Reproduced with my own fan-out shape, deliberately wider than the Fixer's
two-actor test: **one** operation (`research-a`) bound to **three** actors at
one node, each branch dispatched under `research-branch:<actorId>` (the real
`dispatchResearchFanOut` convention), window gating on the single
`operationRefs: ['research-a']` entry.

| Cohort state | `open` | branches |
|---|---|---|
| 1 of 3 settled | `false` | — |
| 2 of 3 settled | `false` | `[[researcher-a,true],[researcher-b,true],[researcher-c,false,missing]]` |
| 3 of 3 settled | **`true`** | all satisfied |
| 2 settled + 3rd **failed** | `false` | `[[…,true],[…,true],[researcher-c,false,failed]]` |

`authorizeDeclaredOperation('synthesize')` is refused at 1/3 and 2/3 and
succeeds only at 3/3. Both directions verified: the negative (partial cohort
never opens) **and** the positive (a fully-settled cohort does open — i.e. the
fix is a real resolution, not a blanket refusal that would have made the
paradigm use case permanently unopenable). Replay parity independently
re-checked on a partial cohort: two independently-taken `replaySession()`
results produce byte-identical `sources`.

## Finding 2 (cross-operation actor reuse) — CONFIRMED-RESOLVED for the reported shape

Reproduced with a **harder** shape than either original report: the unrelated
operation is dispatched **first in event order** (exactly what the old
`events.find(actorId === …)` latched onto) and goes through the **real
declared dispatch path**, so it carries a genuine `declared:unrelated-op`
taskKey *and* a genuine contract stamp — just for the wrong operation.

- `research-a` never dispatched, `unrelated-op` completed first by the same actor → `research-a` = `{satisfied:false, reason:'missing', assignmentId:null}`, window **CLOSED**, authorization refused.
- Positive control: the *same* multi-operation actor completing the *real* `research-a` → window **opens**. No false negative introduced for the legitimate multi-op-actor case.

## `actor-replaced` piggyback — CONFIRMED-RESOLVED, both directions

Tested at a higher bar than the Fixer's regression test, which used a raw
store-door assignment with an obviously-unrelated taskKey and no stamp:

- **Strongest piggyback**: the replacement's unrelated work carries **both** a legitimate `declared:` taskKey **and** a legitimate `protocol-operation:…#unrelated-op` stamp → `research-a` still `missing`, window CLOSED, and `actorId` still resolves to `researcher-a-v2` (lineage followed; it is the *work* that fails to qualify).
- **Door-3-only positive**: replacement work under a completely arbitrary taskKey (`handoff-batch-77`) carrying the correct `#research-a` stamp → **satisfied**, window opens, authorization succeeds. The replacement's *actual correct work* does still discharge the obligation.
- **Near-miss stamps** (`#research-b`, `@9.9.9#research-a`, `#research-`) → all refused; door 3 is exact-match, not substring.
- **Near-miss taskKeys** (`declared:research-a-extra`, `declared:research`, `xdeclared:research-a`, `declared:research-ab`) → all refused; the `declared:<op>` / `declared:<op>:` prefix boundary holds.

## NEW — MEDIUM: door 2 is reachable through the sanctioned dispatch API, and a contradicting stamp cannot veto it

The Fixer's residual disclosure frames the taskKey door as *"trust-equivalent
to the raw store door itself: a caller that can choose taskKeys can assert
operation identity."* Accurate in principle, but it understates the reach:
`taskKey` is an ordinary, documented parameter of `dispatchDeclaredOperation`
itself (`@param {string} [params.taskKey] Overrides the default …`,
`session-engine.mjs:1642`) — not the raw store door. Nothing validates that an
explicit taskKey belongs to the operation being dispatched.

Reproduced (PROBE E). Actor bound to both `research-a` (window source) and
`unrelated-op`. `research-a` is **never dispatched**. `unrelated-op` is
dispatched through the normal, sanctioned API with
`taskKey: 'declared:research-a'`:

```
PROBE E open: true  {"operationRef":"research-a","satisfied":true,"reason":null,
                     "assignmentId":"asgn_coordinator_1_op_001", ...}
PROBE E authorize: AUTHORIZED (window treated as open)
```

The window opens and `authorizeDeclaredOperation('synthesize')` succeeds
without `research-a` ever being performed — the same shape as Finding 2, via
a deliberate explicit taskKey rather than event ordering.

What makes this specifically worth fixing rather than merely documenting: the
assignment **carries the correct contradicting evidence on disk**. Its own
contract stamp reads `…#unrelated-op`. The three doors are OR'd and door 2 is
tested before door 3 ever loads the assignment, so a positive-but-wrong stamp
can never veto a matching taskKey.

**Smallest fix direction:** make door 3 a *veto when present and
contradicting*, not merely a third alternative proof — if the assignment
carries any `protocol-operation:<thisDefinition>@<version>#…` constraint and
none names `operationId`, refuse regardless of taskKey. This is safe for
every legitimate shape: a real declared dispatch always stamps the operation
it is for, and a raw-store-door assignment (which the actor-replaced
re-attempt path depends on, including the Fixer's own regression test) carries
no stamp at all, so the veto never fires there. Confirmed against the Fixer's
own test: its `declared:research-a:replacement` assignment passes
`constraints: []`.

**Not a regression** — the old actor-only code opened this window too. It
means Finding 2 is substantially, not completely, closed: the accidental and
first-in-log paths (the realistic ones) are shut; a deliberate contradictory
taskKey still passes.

## NEW — LOW: an operation bound at two different nodes to two different actors is now permanently unopenable

`declaredOperationBindingActors` scans **all** graph nodes and requires
**every** distinct bound actor to settle. For a genuine fan-out cohort at one
node that is exactly right. But the same all-of rule now also applies across
*mutually exclusive* graph paths. Reproduced (PROBE D3): `research-a` bound at
`phase-primary` to `researcher-a` and at `phase-fallback` to `researcher-b`,
only the primary path ever traversed:

```
PROBE D3 branches: [["researcher-a",true,null],["researcher-b",false,"missing"]]
PROBE D3 open: false
```

The window can never open, because the fallback node's actor is never
dispatched by design. This **fails closed** (a liveness bug, never a bypass),
and no protocol committed to this repo has that shape today. The Fixer's Gaps
section names the adjacent *same-actor-at-two-nodes* case but not this
*different-actors-at-two-nodes* one; it should be named with the same honesty
before P06.3 promotes any contract text, since "bound at two nodes" is not
inherently "a cohort."

## NEW — LOW (informational): mixed role-only + actor-bound binding changes the error behavior

`declaredOperationBindingActors` filters on `ref.actor` truthiness before its
zero-match fallback, so an operation bound role-only at one node and
actor-bound at another now resolves through the actor-bound node
(PROBE D4: `open: true`), where the previous single-binding resolver would
have picked `matches[0]` — the role-only node — and thrown the named
`role-only` `CoordinationError`. Not a security loosening (positive
operation proof is still required), but the function's own doc comment claims
the fallback preserves *"the exact message a caller has always seen for those
shapes"* — that holds only when **all** bindings are actor-less. Worth a
one-line correction to the comment.

### R3-L1 (LOW, documentation): the stamp-reader comment states a wrong reason

`session-engine.mjs:1146-1149` asserts that a boxed `String` that dodges the
writer's `typeof` guard "dodges this too" at the reader. It does not — it
JSON-round-trips into a plain string and would match `.includes(stamp)`

accept a boxed-String forgery. Replace the parenthetical with the real
dependency, and name `execution-contract.mjs`'s `isStringArray` as the layer
that guarantees `constraints` is a plain string array by the time the reader
sees it.

## Does the structural fix close the whole defect class?

Yes, in my own assessment, and for a reason independent of the four attacks.

The defect class was never "actor identity is forgeable" or "taskKey is
forgeable." It was: *the gate answered "which declared operation completed?"
from channels that doors other than the one performing the operation could
write*, and each round removed one such channel while the enumeration stayed
incomplete. Round 3 does not remove a fourth channel — it removes the
enumeration. The question now has exactly one answer source, that source is a
reserved namespace, the namespace has a writer-side refusal for caller input
and a reader-side exact-equality test, each independently tested, and the only
way to write into it is an internal parameter that appears twice in the entire
repository and is not on any caller-facing signature, schema allow-list, or
CLI surface. Crucially the default inverted: a door now has to *do something*
to satisfy a window, rather than *remember something* to not satisfy one. A
predicate that fails closed for every door that has not opted in cannot be
beaten by finding a door nobody thought of.

The residual surface is one door — the raw `createSessionAssignment` import —
and it is a categorically different trust level: no CLI reachability, no
request-file field, no exported engine signature; a caller must already be
inside the process importing `store.mjs`, at which point it can append
arbitrary events anyway. Round 3 makes that door the *intended* declaration
mechanism for engine-internal callers (it is how the actor-replaced fixtures
work), which is a coherent design rather than a leftover. It is correctly
recorded in the trace's Gaps list.

I could not construct an attack this round that the previous two rounds' style
would have found, and the one novel mechanism I did find (JSON round-trip of a
non-string that serializes as a string) is closed — though by a layer the code
comment misattributes.
