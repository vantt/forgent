## 1. Requirements (from phase-08.md's P08.1 bullets + current-cell.md's Goal/Acceptance/Bug Taxonomy)

- Define the CLOSED MVP8 contribution-type enum: `proposal | objection |
  response | clarification | rank | specialist-request`.
- Build a typed lineage validator in a NEW, isolated module.
- Require immutable artifact backing and real Assignment/Run provenance for
  every contribution.
- Reject: undeclared contribution types, dangling anchors, dangling
  responses, cycles (a response chain that loops back), foreign-session
  refs, and operation/type mismatch (a type not declared in that
  operation's `contributions.allowedTypes[]`).
- Do NOT add: recipient, delivery, unread, mutable status, or an arbitrary
  free-form body field.
- Tests First: one test per rejection case, plus a positive test proving a
  well-formed contribution with real provenance validates. Prove
  immutable-artifact-backing is actually enforced.

## 3. Design Notes

### Module path choice

`src/runner/deliberation/schema.mjs`, matching current-cell.md's own
suggestion and this repo's `src/runner/<concern>/` convention
(`src/runner/team-cognition/`, `src/runner/coordination/`). No existing
`deliberation` directory or references existed anywhere in the repo before
this cell (`grep -ril "deliberation" src/ test/` returned nothing prior to
this change), confirming this is a genuinely new, unclaimed boundary.

### Component-authority-boundary-map.md check

Read the full document (`docs/architect/proposals/component-authority-boundary-map.md`).
It does NOT name a dedicated "Deliberation Memory" or "contribution-ledger"
authority row anywhere in §6 (Authority Ownership) or §9 (Coding Domain
Responsibility Map) — the closest analog is the **Team Cognition Engine**
row, whose "Must not own" list (CoordinationSession terminal transitions,
context-grant authority, Assignment dispatch, RunResult confidence
upgrades) is the same discipline `team-cognition/schema.mjs`'s own header
already draws on. This module follows that same discipline by construction
even though no row names it directly: it is a pure data-shape/lineage
validator with zero fs/network/session/dispatch access (proven by
deliberation-static.test.mjs), so none of those forbidden authorities are
reachable from it. If/when the boundary map is promoted, a "Deliberation
Memory" row analogous to Team Cognition Engine would be the natural
addition — noted as a Gap below, not something this cell should invent
unilaterally.

### Pattern precedent followed (team-cognition/schema.mjs)

Mirrored one boundary over, same discipline:
- `DeliberationError` (category, message) exactly parallels
  `AggregationError`.
- `fail(category, reason)` helper, `isPlainObject`/`isNonEmptyString`
  duplicated locally rather than imported — self-contained module, no
  import from `team-cognition/` or `coordination/`, so this boundary never
  inherits session-runtime or aggregation authority by accident (same
  reasoning `team-cognition/schema.mjs`'s own header gives for not
  importing `coordination/schema.mjs`).
- Whitelist-first field validation (`assertOnlyAcceptedFields`), fail-closed
  on first violation.
- `revision` required as a non-empty string on every contribution — same
  immutability-pin convention as `AggregationSource.revision`: an
  `artifactRef` without a `revision` pin is not immutable backing.

### Contribution shape chosen

Fields: `contributionId`, `sessionId`, `operationRef`, `type`,
`assignmentId`, `runId`, `artifactRef`, `revision`, `anchors` (optional
array), `respondsTo` (optional string), `roundKey`, `visibilityWindowRef`,
`ts`. This maps directly onto phase-08.md's Candidate Contract sentence:
"contribution type, Assignment/Run/artifact provenance, anchors, response
lineage, round key, visibility-window provenance, and timestamp." No
`recipient`/`delivery`/`unread`/mutable `status`/free-form `body` field
exists (grep-verified, §5).

`visibilityWindowRef` is carried as a required opaque provenance string
only — this cell does not interpret, enforce, or resolve visibility-window
legality (that MVP6 enforcement is explicitly out of scope here; only P08.2
"Session Ledger, Replay, And Visibility" wires real enforcement). Treating
it as a required non-empty string keeps the shape honest (every
contribution really did happen inside some declared window) without this
module pretending to own window semantics it has no access to validate.

### Context-based validation (no store access)

Following `aggregation-evaluator.mjs`'s own precedent for
`currentRevisions` (a pure-function input standing in for real store
access, since P07's evaluator "still has no session/store access"), this
module's `validateContributionLineage(contribution, context)` takes a
caller-supplied `context = {sessionId, declaredOperations,
knownContributions}` rather than resolving anything itself:
- `declaredOperations: {[operationRef]: {allowedTypes: string[]}}` — stands
  in for the real FlowDefinition `contributions.allowedTypes[]` declaration
  P08.1's Non-Goals explicitly left open ("your call whether the minimal
  schema surface belongs here"). This cell's call: keep it OUT — no
  `src/runner/definitions/*` schema wiring was added (Do Not Touch
  respected), and the caller (P08.2 or later) supplies the resolved map.
- `knownContributions: Map<contributionId, {sessionId, respondsTo?}>` —
  stands in for a real session ledger read. A caller-supplied entry may
  legitimately carry a `sessionId` different from the session under
  validation; that is precisely how a foreign-session ref is distinguished
  from a dangling one (`resolveRef`'s two-step check: not-found = dangling,
  found-but-wrong-session = foreign-session-ref).

### Cycle detection

Implemented as a bounded graph walk (`validateResponseLineage`): starting
from the candidate's `respondsTo` target, follow each node's `respondsTo`
pointer through `knownContributions`, tracking visited ids (seeded with the
candidate's own `contributionId`). Revisiting any id — including the
candidate's own id, or a loop entirely among already-known nodes — is a
cycle. The walk is capped at `knownContributions.size + 1` steps so even a
pre-existing corrupt/cyclic chain in the caller-supplied map can never spin
the validator forever; an overrun is itself treated as a cycle, since a
well-formed acyclic chain can never need more steps than there are known
nodes. Both a direct self-loop (`A` responds to `A`) and a 3-node loop
(`A->C->B->A`) are covered by tests.

### `response` type requires `respondsTo`

Added one shape rule beyond the letter of the six rejection cases: a
contribution of `type: 'response'` MUST set `respondsTo` (enforced in
`validateContributionShape`, category `validation`). A "response" with
nothing to respond to is not a response — this directly serves the Bug
Taxonomy's "a 'response' that can target a nonexistent... contribution"
concern by making the omission itself a rejection, not just a dangling-ref
edge case.

## 4. Design Notes — what was deliberately NOT built

- No FlowDefinition/`src/runner/definitions/*` schema wiring for
  `contributions.allowedTypes[]` declaration itself — `declaredOperations`
  is a plain caller-supplied object; a future cell (likely P08.2) resolves
  it from the real definition.
- No session ledger, append, replay, or visibility-window enforcement —
  P08.2's scope per current-cell.md's own Non-Goals.
- No `recipient`/`delivery`/`unread`/mutable `status`/free-form `body`
  field, and no code path that could construct one (whitelist rejects any
  unknown field outright).

## 6. Gaps

- `component-authority-boundary-map.md` has no dedicated Deliberation
  Memory / contribution-ledger authority row yet; this cell followed the
  Team Cognition Engine row by analogy (see §3) but the boundary map itself
  was not edited (out of this cell's scope/Do Not Touch).
- `declaredOperations`/`knownContributions` are caller-supplied stand-ins
  for real FlowDefinition/session-ledger data — P08.2 must decide their
  exact real-data source and shape when it wires session integration; this
  cell's shapes are a reasonable but non-binding proposal.
- No test proves behavior under a very large/pathological `knownContributions`
  map (performance), since P08.1's scope is correctness of the validator,
  not scale — left for whichever later cell does load/perf proof, if any is
  ever needed.
- **Anchors are resolved, never walked.** `validateAnchors` checks each
  `anchors[]` entry for existence and same-session membership, but does not
  traverse the anchor graph, so an anchor cycle (`a` anchors `b`, `b` anchors
  `a`) validates, and a contribution may anchor itself if its own id is
  already in `knownContributions`. Degenerate rather than dangerous here —
  anchors are a reference set, not a traversed chain, and nothing in this
  module follows them — but P08.2 builds append/replay on this validator and
  will traverse them, so it is named here explicitly as a **P08.2
  ledger-layer obligation**, not an accepted permanent limit.
- **Duplicate contribution ids are not rejected.** A candidate whose
  `contributionId` already exists in `knownContributions` validates. This
  module has no ledger to check uniqueness against; the repo's own precedent
  puts that check on the replay walk (`replay.mjs`'s `aggregationIds`
  duplicate check is the pattern). Also a **P08.2 ledger-layer obligation**
  — P08.2 must not assume this validator covered it.
- Assignment/Run/artifact *existence* still cannot be verified by this module
  itself (no store access, by design). The `knownAssignments` channel added
  in the Fix Round declares how a caller supplies that truth; **populating it
  is P08.2's job**, and until a caller does, provenance reality is unchecked
  and the Proof Matrix says so.

### 4 (MEDIUM) — `knownAssignments`: a channel for provenance reality, plus a free `runId` binding

Red-Team confirmed four accepted-today forgeries: foreign-session provenance,
a fabricated Assignment/Run, a traversal-shaped `runId` suffix, and "right
type, wrong operation" (an `operationRef` unbound to what the Assignment
actually did). Two independent fixes:

**(a) `runId` must belong to its claimed Assignment — no new context needed.**
`schema.mjs:95-110` adds `assertRunIdBelongsToAssignment`, mirroring
`coordination/store.mjs:1277 assertValidRunIdForAssignment`: the full shape
`run_<assignmentId>_<digits>`, never a prefix-only check, because a prefix
check accepts a same-prefix malicious suffix. Called from
`validateContributionShape` at `schema.mjs:154`, category
`foreign-provenance`. This alone closes the traversal-shaped case and the
plain `runId`/`assignmentId` mismatch. Test: `rejects a runId that does not
have the shape of a Run of the claimed Assignment`, covering
`not-even-a-runid-shape`, a different Assignment's runId, and
`run_asg_001_../../../../tmp/evil-marker`.

**(b) the optional `knownAssignments` context channel.** `schema.mjs:280-323`
adds `validateAssignmentProvenance(contribution, knownAssignments,
sessionId)`, wired into `validateContributionLineage` at `:347` immediately
after the operation/type check. `context` now accepts an optional
`knownAssignments: Map<assignmentId, {sessionId, operationRef}>`. When
supplied, three things must hold, each closing a different accepted forgery:
the `assignmentId` resolves at all; it belongs to the session under
validation; and it carries the claimed `operationRef`.

The channel is declared **here** rather than left to P08.2 for the reason
Red-Team gave: P08.2 cannot add it later without changing this module's
public signature. It is **optional** because this module has no store access
by design — Assignment existence can only ever be known to a caller that has
one. Populating it stays P08.2's job, and until a caller does, provenance
reality is unchecked; §2 and §6 both say so plainly rather than claiming
otherwise.

Tests: `knownAssignments is optional -- omitting it leaves provenance
presence-checked only`, `validateContributionLineage accepts a contribution
whose Assignment resolves, is in-session, and answered the claimed
operation`, `... rejects a fabricated Assignment once knownAssignments is
supplied`, `... rejects an Assignment belonging to a different coordination
session`, `... rejects "right type, wrong operation" -- the Assignment
answered another operation`, `knownAssignments must be a Map when supplied`.

### 5 — Proof Matrix row corrected

The single row "Real Assignment/Run provenance required | `rejects a
contribution missing assignmentId/runId/artifactRef provenance`" overclaimed
— that test only proved *presence*. §2 now carries three rows instead: field
presence (all three fields actually exercised), the `runId`-belongs-to-its-
Assignment shape check, and the `knownAssignments`-gated reality check with
its "only when a caller supplies `knownAssignments`" qualifier stated in the
row itself.

### 6 (LOW) — `allowedTypes` may not be inherited

`schema.mjs:186` — `Object.hasOwn(declaredOperations, operationRef)` instead
of a plain property read, so a `declaredOperations` built with
`Object.create(proto)` can no longer legalize types declared only on the
prototype. Test: `an allowedTypes declaration reachable only through the
prototype chain does not legalize a type`.

### 9b — test hygiene

`rejects a contribution missing assignmentId/runId/artifactRef provenance`
only ever deleted `assignmentId`. It is now
`rejects a contribution missing any one of the assignmentId/runId/artifactRef
provenance fields` and loops over all three, each with its own assertion
message. The shared fixture's `runId` was also corrected from `run_001` to
`run_asg_001_01` — it never matched its own `assignmentId`, which fix (a)
above made visible.

### 10b — Gaps

§6 now names, explicitly as **P08.2 ledger-layer obligations**: anchors are
resolved for existence and session but never walked for cycles (so an anchor
cycle, or a self-anchor, validates); duplicate contribution ids are not
rejected; and Assignment/Run/artifact *existence* remains unverifiable from a
pure module, with `knownAssignments` naming how a caller supplies it.
