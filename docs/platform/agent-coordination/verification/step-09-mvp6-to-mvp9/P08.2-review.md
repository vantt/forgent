`assertDispositionRefOwnedBySession` (`store.mjs:1012` pre-change) asks two

### MEDIUM-1 — A bare (unprefixed) contribution id is accepted as a disposition target, is reported by `show` as session-owned even when it names ANOTHER session's contribution, and silently resolves nothing

**File/line:** `src/runner/coordination/store.mjs:1024-1033`;
`src/verbs/coordination/show.mjs:55-62`; `src/runner/coordination/replay.mjs:290`.

**Failing scenario (reproduced, PoC 1):** session A links `contrib_mine`;
session B in the same workspace links `contrib_theirs`. A's driver records two
dispositions with bare targetRefs.

```
own bare id at write door       : ACCEPTED
FOREIGN session bare id at door : ACCEPTED
openContributionIds             : [ 'contrib_mine' ]
resolvedContributionIds         : []
show targetRefOwnedBySession    : [ [ 'contrib_mine', true ], [ 'contrib_theirs', true ] ]
```

**Requirement violated:** the trace's own claim that "a bare contribution id …
can never target a contribution. That is deliberate" is true of *resolution*
but leaves two consequences unstated. First, `show` reports
`targetRefOwnedBySession: true` for a ref that names another session's
contribution — the read-side mirror asserts ownership over a foreign
contribution id, which is the appearance the Bug Taxonomy entry ("a
disposition able to target a contribution from a DIFFERENT session") exists to
prevent. Second, a driver who writes `contrib_mine` instead of
`contribution:contrib_mine` gets a disposition that is accepted, rendered, and
resolves nothing — the contribution stays `open` forever with no error
anywhere. There is no production caller yet (P08.3 will be the first), which
is exactly when a naming trap like this gets baked in.

**Evidence:** PoC 1 above; `replay.mjs:290` gates resolution on
`targetRef.startsWith(CONTRIBUTION_REF_PREFIX)`.

**Smallest fix:** in `assertDispositionRefOwnedBySession`, after the prefixed
branch, refuse an unprefixed ref that exactly equals a member of
`contributionIds` with a message naming `contribution:<id>`. That closes the
silent no-op without imposing any id-shape convention (which the Doer
deliberately avoided, correctly). The foreign-id case then remains an opaque
ref, which is honest.

### MEDIUM-2 — Replay's open/resolved derivation is order-blind: a disposition appended BEFORE the link marks the contribution resolved, a state the write door refuses

**File/line:** `src/runner/coordination/replay.mjs:288-292` (collect) and
`:506-513` (filter).

**Failing scenario (reproduced, PoC 2):** a `driver-disposition-recorded`
event naming `contribution:contrib_future` is appended raw, then

```
write door on the same ordering : REFUSED (dangling-ref)

replay resolvedContributionIds  : [ 'contrib_future' ]
```

**Requirement violated:** current-cell.md Tests First — "Open/resolved views

resolution ordering the write door refuses. This is not the same class as the

the contributions linked *before* that disposition.

**Smallest fix:** in the `driver-disposition-recorded` branch, add only when
`contributionIds.has(suffix)` — i.e. the contribution has already been walked.
One condition, and it makes the replay-time derivation agree with the write
door exactly.

- The bare-ref case (MEDIUM-1) is where `show` and the write door *agree* and

**Off-by-one (`<` vs `<=`).** `linkedEvent.seq === windowOpenedAtSeq` is
admitted. In any ordinary protocol the two events belong to different

self-referential declaration — a window whose `opensAfter.operationRefs`

ACCEPTED, and the Run admitted is the one that OPENED the window, so it
demonstrably saw nothing the window admits. `<=` would be the strictly correct
comparison. Severity **INFO** — it requires a nonsensical protocol document and
nothing validates against it today, but if P08.3 or a definition-schema cell
adds a self-reference check, `<=` is the cheaper half of the same fix.

**Two false-negative / false-positive probes were productive. Both trace to one
root cause:** `visibilityWindowOpenedAtSeq` and the backing-run comparison both
use a `result-linked` event's `seq`, which is a **link** position, not a
**reasoning** position. Wherever those two diverge, the check answers the wrong
question.

3. `recordRunRetry(...)` declares a retry (seq 9), the retry executor runs and

4. `research`/`researcher-b` settles (seq 11). Window OPENS.

**Severity MEDIUM**, same class as the original 4c, with materially narrower
reachability: it needs a crash/kill inside a specific window, whereas the
original needed only "settle now, link later". Red-Team's warning that this must
not be left for P08.3 to build round semantics on applies unchanged to the
residual.

**Fix direction (smallest correct one).** Compare against when the Run *started*,
not when its result was *linked*. The log already carries that lower bound: a
first Run is bounded below by its `assignment-created`, a retry Run by the
`run-retried` event that authorized it. Requiring that position to be at or
after `windowOpenedAtSeq` is definition-independent, needs no new state, and
closes NEW-1 and the `<=` INFO above at the same time.

#### NEW-2 (LOW-MEDIUM, new) — a legitimate link is refused, with a factually wrong error, after any retry of a window SOURCE

The mirror image of NEW-1, and reachable through the ordinary mediated retry
path with no crash at all.

`visibilityWindowOpenedAtSeq` uses `lastEventFor(events, 'result-linked', ...)`
per source branch. Retrying an already-satisfied window source appends a second
`result-linked` for it, moving the computed "opened at" position **forward**,
even though Red-Team 4b established that windows are monotone closed→open and
never re-close. Reproduced:

```
before retry: link ACCEPTED   (window opened seq 8, deliberate settled seq 10)
after  retrySessionTask on the window source researcher-a (new result-linked at seq 13):
  REFUSED -- assignment "...op_003" settled at log position 10, before visibility window
             "post-research" opened at log position 13
```

The deliberate Run genuinely did reason under an open window, and the message
asserts the window opened at 13, which is false — it opened at 8 and stayed
open. This is fail-closed (a liveness/UX defect, not a soundness hole), but the
error text will send a driver to "re-run the operation under the open window"
for a Run that already was.

Note the Fix Round's own justification is correct about the *backing* Assignment
("deliberately uses the LAST `result-linked` ... so a legitimate re-run after
the window opened links normally") but is silent about the **source** side,
where LAST is the wrong choice. The doc claim at `session-engine.mjs:3267-3272`
("the log `seq` at which `windowState`'s LAST source became satisfied") does not
hold once any source has been re-linked.

**Fix direction:** for each source branch, take the EARLIEST `result-linked`
whose run classified as satisfied, not the latest. Satisfaction is sticky
(`resolveBindingOutcome`), so the earliest satisfying event is when the branch —
and therefore the window — actually opened. `lastEventFor` remains correct for
the failed-then-retried direction only, which the earliest-satisfying rule also
handles.
