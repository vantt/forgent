## 1. Design Notes — the classification decisions, and why

### 1a. The contribution-lineage finding: investigated concretely, not assumed

**The question**, per current-cell.md: does closing "the pack gate's closed
step vocabulary never reaches `linkSessionContribution`" require a genuinely
NEW kernel-level mechanism (shared missing primitive), or does it require
only EXTENDING the pack's own existing step vocabulary to add a new step
kind that forwards to the already-existing, already-proven
`linkSessionContribution` door (implementation bug, fixable in-scope)?

**Investigation, before writing any code:**

1. Read `linkSessionContribution`'s full signature and body
   (`src/runner/coordination/session-engine.mjs:4013-4200`). It is a
   COMPLETE, self-mediating door: the caller supplies only
   `contributionId`/`type`/`assignmentId`/`roundKey`/`linkedBy`/
   `anchors`/`respondsTo`; every window/provenance/lineage check (operation
   stamp, actor binding, visibility-window legality, reasoning-time-vs-link-
   time ordering, artifact revision pin, closed-type-enum narrowing) is
   derived internally from the session's own event log and bound
   FlowDefinition. This is the SAME test the plan's own text applies to the
   contribution-lineage decision ("does the underlying capability already
   exist and is it proven?") — yes, fully, since P08.2/P08.3.
2. Read `run.mjs`'s existing `authorize`/`disposition` step handlers
   (`src/verbs/coordination/run.mjs`). Both are thin, request-boundary-only
   forwards into their own mediated doors (`authorizeDeclaredOperation`,
   `recordDriverDisposition`), deriving `driverIdentity` internally, never
   accepting it from the caller. A `contribution` step is structurally the
   SAME shape — a fifth thin forward, not a new mechanism.
3. Checked whether a `contribution` step could reopen any of P10.1's five
   verified pack bypasses (§5, re-verified P10.5). None of the five concern
   contribution linking: three (validate-aggregate, authorize-specialist,
   close-directly) are refused because `run.mjs`'s vocabulary never exposes
   them at all — a `contribution` step doesn't touch any of those three
   doors; the other two (switch-protocols, bypass-grants) are unaffected
   since `linkSessionContribution` independently re-derives every grant/
   window check from the session's own real state, exactly like every
   sibling mediated door already does — a `contribution` step adds no new
   trust surface.
4. Confirmed the actual code location is `src/verbs/coordination/{run,
   schema}.mjs` — the APPLICATION/use-case layer this whole Phase 10 lives
   in, not `src/runner/**` (the kernel boundary `session-engine.mjs` alone
   occupies, which P10-KERNEL-FIX was uniquely authorized to touch). No
   kernel file needed touching at all — confirmed empirically after the
   fact too: `git diff --stat -- src/ core/` shows exactly
   `src/verbs/coordination/{run,schema}.mjs` changed, zero files under
   `src/runner/**` or `core/`.

**Conclusion: implementation bug, in-scope pack-layer wiring gap.** The
underlying capability already existed and was already proven
(`linkSessionContribution`, P08.2/P08.3); the gap was narrowly that the
pack's own request vocabulary never reached it. Closing it required no new
kernel mechanism, no new trust decision, and no kernel-file edit — a small,
additive, structurally-identical-to-two-existing-siblings change to the
application layer Phase 10 already owns. This does NOT trigger phase-10.md's
"leave Step 09 open with a named proposal" consequence, which is reserved
for a genuine capability gap not fixable as a scoped patch.

### 1b. The `run.mjs:236`/`aggregationCloseParams` finding: confirmed small and scoped, PLUS one earlier sibling instance found

Investigated per current-cell.md's own steer ("most likely 'implementation
bug,' scoped and small — a symmetric try/catch matching the pattern
`classifySessionQuorum` itself now uses"). Confirmed: `classifySessionQuorum`
(`session-engine.mjs:3289-3319`) already establishes the exact pattern —
`try { resolved = loadCoordinationProtocol(...) } catch { resolved = null }`,
then an explicit `CoordinationError` refusal at the CLOSE-time enforcement
point (`opts.enforceDefinitionVersion`), never a raw crash.
`aggregationCloseParams` (`run.mjs`) had no such guard on its own
`loadCoordinationProtocol` call. Fixed by mirroring the pattern exactly.

**A second, earlier instance of the identical failure class was found while
investigating this one, not named by P10-KERNEL-FIX.md's own §5 Gap text**
(which named only the `aggregationCloseParams` call): `runCoordinationUseCase`
(`run.mjs`, the `else` branch, `kind: 'declared-protocol'`) resolves
`request.protocolRef.id` via an ALSO-unguarded `loadCoordinationProtocol`
call to validate `request.actors[]` membership — this runs FIRST,
unconditionally, on EVERY declared-protocol request (open or resume),
before the steps loop or `aggregationCloseParams` are ever reached. Fixed
the same way, but thrown as `StoreError('validation', ...)` rather than
`CoordinationError`, matching this specific block's own sibling "actors[].id
not declared" refusal two lines below it (a request-validation concern,
distinct from `aggregationCloseParams`'s own close-time refusal — nothing
has been dispatched yet when this earlier check runs, so there is nothing
yet to give a soft `closed: false` "refusal to close" for; a hard request
failure is the honest, correctly-scoped outcome).

**Consequence for testability, found empirically, not assumed:** because
this earlier check resolves `request.protocolRef.id` on EVERY
declared-protocol call, and `loadCoordinationProtocol` always does a FULL
directory scan across all tiers before filtering by id (any malformed
sibling file in the first-scanned tier fails the whole call, regardless of
target id), a "broken sibling file" registry corruption ALWAYS trips the
earlier check first, making `aggregationCloseParams`'s own catch
effectively unreachable through the public request door for that specific
failure shape. Proven by first writing a test for the naive "broken
sibling" scenario, watching it hit the earlier check instead (not a test
bug — a real, confirmed code-path fact), then redesigning the
`aggregationCloseParams`-specific regression test to isolate it correctly
(a second, independently-resolvable "decoy" protocol satisfies the earlier
check; the session's OWN bound protocol file is instead deleted outright —
a `not-found` failure, not a "malformed sibling," which does not break the
decoy's own resolution). Both fixes are real, correct, and kept — the
earlier one is reached far more often in practice; the later one remains
correct defense-in-depth at the exact point current-cell.md named.

## 3. Implementation (the two in-scope fixes)

### 3a. `src/verbs/coordination/schema.mjs`

- New `contribution` step type in `validateSteps` (fifth kind, alongside
  `operation`/`fan-out`/`authorize`/`disposition`).
- `validateContributionStep`: validates `contributionId` (safe-id charset,
  matching every other id field in this file), `contributionType` (closed
  MVP8 enum, imported from `../../runner/deliberation/schema.mjs`'s
  `CONTRIBUTION_TYPES` — a legal use-case→infra import per
  `docs/architecture-manifest.json`'s own layer ranking, confirmed before
  adding it), `assignmentId` (`$ref:`-or-literal, matching every other
  Assignment reference in this file), `roundKey` (bounded free text,
  matching the engine's own "opaque grouping label" treatment — not
  charset-restricted, matching `rationale`/`objective`), optional
  `anchors[]`/`respondsTo` (literal contribution-id-shaped strings, matching
  `linkSessionContribution`'s own native parameter shape — NOT `$ref:`-
  resolved, since they reference contribution ids, not assignment ids).
- `assertNoLinkedBy`: a new guard, mirroring the existing
  `assertNoAuthorizedBy` exactly, rejecting a caller-supplied `linkedBy` —
  driver provenance is always derived from the session's own `writerId`.
- Unknown-step-type message updated to name all five kinds.

### 3b. `src/verbs/coordination/run.mjs`

- New `else if (step.type === 'contribution')` branch: resolves
  `step.assignmentId` via the existing `resolveRef` (so `$ref:<label>` works
  exactly like every other step), forwards into `linkSessionContribution`
  (newly imported from `session-engine.mjs`) with `linkedBy: driverIdentity`
  (the SAME derived identity `authorize`/`disposition` steps already use),
  reports the real persisted result (`appended`, `anchors`, `respondsTo`
  included). No `labels[step.as]` entry — a contribution step materializes
  no Assignment, matching `authorize`'s own precedent.
- `aggregationCloseParams`: `loadCoordinationProtocol` wrapped in
  try/catch; on failure, throws `CoordinationError('validation', ...)`
  mirroring `classifySessionQuorum`'s own resolution-failure message —
  caught by the existing `catch (err) { if (err instanceof
  CoordinationError) closeRefusalReason = ... }` block, so a resolution
  failure now surfaces as `closed: false` with an honest
  `closeRefusalReason`, never a raw crash.
- The `else` branch's own `request.protocolRef.id` resolution (actor-
  membership check): same try/catch pattern, throws
  `StoreError('validation', ...)` on failure (matching this block's own
  sibling refusal two lines below, a genuine request-validation failure,
  distinct in kind from `aggregationCloseParams`'s soft close-refusal).

**Zero kernel files touched** (`git diff --stat -- src/ core/` shows only
the two files above); zero files under `src/runner/**` or `core/` modified.
