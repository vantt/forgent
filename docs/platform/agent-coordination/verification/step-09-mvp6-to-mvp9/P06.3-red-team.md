### FINDING 1 (Medium) — a raw `actor-replaced` event collapses the cohort and opens the window on half the work

`deriveVisibilityWindowState` → `buildActorReplacementMap`
(`session-engine.mjs:1067-1073`) consumes **every** `actor-replaced` event in
the log with no acceptance check. `resolveBindingOutcome` then follows that
lineage to an effective actor before collecting Assignments. So if
`researcher-a` is declared replaced by `researcher-b` — a *sibling in the
same cohort at the same node* — both graph bindings resolve to the same
effective actor, and researcher-b's single genuine Assignment satisfies both
branches.

Reproduced against the committed fixture (`/tmp/rt-p063/attack.test.mjs`,
ATTACK 1; end-to-end in `attack3.test.mjs`, ATTACK 5):

```
before: open=false  [["researcher-a",false,"missing"],["researcher-b",true,null]]
  recordActorReplacement(cid, {oldActorId:'researcher-a', replacementActorId:'researcher-b'})
after:  open=true   [["researcher-a",true,null,"asgn_coordinator_1_op_002"],
                     ["researcher-b",true,null,"asgn_coordinator_1_op_002"]]
authorizeDeclaredOperation → SUCCEEDED (auth_rt_1)
dispatchDeclaredOperation('synthesize-findings') → done, reading ["asgn_coordinator_1_op_002"]
```

Both branches carry the *same* `assignmentId`. Only one of the two
independent research passes was ever performed, yet the
`post-independent-pass` window opened and the synthesis ran — which is
exactly the guarantee this fixture exists to demonstrate.

Three things make this worse than the residuals already named:

1. **No stamp forgery is involved.** researcher-b's Assignment is genuine,
   engine-stamped, produced by `dispatchDeclaredOperation`. The reserved-stamp
   defense is fully intact and buys nothing here, so "the stamp is the
   enforcement primitive" does not cover this shape.
2. **The codebase already classifies this as a bug.** The mediated
   `replaceSessionActor` door refuses the identical shape
   (`session-engine.mjs:3156-3166`), and its own comment says so verbatim:
   *"this is exactly the shape that lets one actor's real result get silently
   double-counted to cover two required slots (the bug this check exists to
   close)"*. I confirmed the refusal empirically (ATTACK 1b: `REFUSED —
   newActorId "researcher-b" is already bound … with its own independent
   activity on record`). The window derivation simply does not re-apply that
   check, and `replay.mjs:211-217` explicitly declines to enforce any
   cross-event rule on `actor-replaced`.
3. **The promoted text implies a check that does not exist.** It says the
   derivation follows *"any **accepted** `actor-replaced` lineage"*
   (`flow-definition.md:270-271`). Nothing accepts or validates the event at
   read time. A reader takes "accepted" to mean the mediated door's
   guarantees hold; they do not.

Scope note, offered honestly: the *runtime* half of this belongs to
`session-engine.mjs`, which is on this cell's Do Not Touch list, so the Doer
was right not to patch it. The *documentation* half is squarely P06.3's own
deliverable, and P06.3's Bug Taxonomy names this failure mode directly
("promoting contract text for behavior that isn't actually implemented").

**Smallest fix direction (this cell):** add a third residual to
`flow-definition.md`'s residual paragraph naming the unmediated
`recordActorReplacement` store door as the same class of trust boundary as
the unmediated `createSessionAssignment` one, and drop or qualify the word
"accepted" so it does not imply a read-time check. **Follow-up cell:** have
`buildActorReplacementMap` ignore (or fail closed on) a replacement whose
`replacementActorId` is itself a distinct declared binding of the same source
operation — i.e. re-apply `replaceSessionActor`'s own collision rule at read
time.

## Attack 2 — is Limitation 3 ("runtime-inert for `required` bindings") true?

**HELD — the claim is correct and I could not find a second path.**

Static: `contextAccess` is read at exactly two sites in all of `src/`
(`session-engine.mjs:1410` and `:1958`), both inside driver-authorized gate
paths, both of which only ever *refuse*. No other consumer exists; schema
validation (`schema.mjs:646-650`) merely carries the field through.

Empirical (`attack.test.mjs`, ATTACK 4): I built two definitions differing
*only* by the presence of `contextAccess.visibilityWindowRef` on a `required`
binding, and drove both at an ungranted sibling ref with the window shut.
Both dispatched to `done` reading that ref. Behaviour is identical; the ref
grants nothing extra. (The tool printed "DIVERGENT" — that is my comparison
comparing per-session assignment ids, not a behavioural difference.)

Worth stating plainly so nobody misreads Limitation 3 as reassuring: a
`required` binding has no `legalContextRefs` check at all (that block is
inside `if (isDriverAuthorized)`), so it can read any session-owned ref.
That is pre-existing, unrelated to windows, and unchanged by this cell — but
"runtime-inert" means *the window ref changes nothing*, not *the binding is
constrained*. The promoted text's phrasing is accurate; I flag it only
because a skimmer could invert it.

## Attack 3 — the promoted text's specific factual claims

### FINDING 2 (Low–Medium) — "the sole door" / "satisfy no window source at all" is contradicted by the file's own residual 40 lines later

`flow-definition.md:274-279`:

> It is written by `dispatchDeclaredOperation` — **the sole door that
> materializes a declared operation** — and the shared read-only contract
> constructor refuses any caller-supplied constraint in that namespace, so a
> door that does not stamp produces Assignments that **satisfy no window
> source at all**, whatever their actor, claim key, or provenance.

Then `:311-314`:

> the unmediated `createSessionAssignment` store door can write the reserved
> stamp itself …

Both cannot be true. I confirmed the second empirically (ATTACK 2): a
`createSessionAssignment` call with `taskKey: 'anything-at-all:rt'`, an
objective of "Not research at all", and a hand-written
`protocol-operation:<id>@<version>#independent-research` constraint opened the
window and got `authorizeDeclaredOperation` to succeed. Note this is not the
benign case the residual describes (a replacement actor discharging its
obligation) — it is arbitrary non-research work.

Within the mediated module the claim *is* true, and I verified that
carefully: of the four `buildReadOnlyContract` call sites (`:473`, `:700`,
`:2047`, `:2292`), only `:2047` passes `protocolOperationRef`, and
`assertNoReservedOperationStamp` plus the snapshot-once discipline at
`:150-180` close the caller-supplied and TOCTOU-container variants. There is
no fifth mediated dispatch door. So the mechanism is sound; the sentence is
just over-absolute.

**Smallest fix:** qualify "the sole door" as "the sole *mediated* door", and
move the trust-boundary caveat from the trailing "for completeness" sentence
into the same paragraph as the "satisfy no window source at all" claim, so a
skim cannot pick up the guarantee without the boundary.

## Attack 6 — would the promoted text mislead a P07.3+/P08+/P09+ implementer?

### FINDING 3 (Low, but it is a factual inversion) — a Required Negative Test asserts the opposite of the behaviour

`flow-definition.md:415-419`:

> an Assignment carrying no reserved `protocol-operation:` stamp for a listed
> source operation **satisfies it** regardless of that Assignment's actor or
> claim key; and an Assignment belonging to a different CoordinationSession
> **satisfies it not at all**

The middle clause is missing its negation. As written, the contract's own
required-negative-test list states that an *unstamped* Assignment **does**
satisfy a window source — the exact inverse of the mechanism, and the inverse
of the test that proves it. The parallel third clause ("satisfies it not at
all") shows the intended construction. A future implementer reading this list
as the spec for their own negative tests would encode the wrong assertion.

**Smallest fix:** "…satisfies it not at all, regardless of that Assignment's
actor or claim key".

### Not overclaimed (checked, and I expected to find problems here)

- **Replay determinism.** The text claims only "replay reaches the same
  verdict from the same disk state with no cached or latched answer in
  between". That is exactly what the parity test proves — a second,
  independently-*taken* `replaySession()` fed to the *same* function. It does
  not claim an independent second implementation, and it should not. Correctly
  scoped.
- **Grant-scope precision.** Limitation 1 states plainly that `permits.*` is
  validated structural intent and not a per-ref runtime filter, and gives the
  reason. I could not find anywhere in the promoted text that implies
  per-ref filtering. Correct.
- **"Concrete authority … stays where it already was."** Verified against
  `authorizationProvenance` at `session-engine.mjs:1988-1994`, which does set
  `contextGrant.refs`. Accurate.
- **"A raw-store-door authorization does not get through."** True: the
  dispatch-time re-derivation keys off the *binding's* activation mode, not
  the authorization record, so a forged `operation-authorized` still meets the
  gate. Accurate.
- **Deferrals.** No anonymization, aggregation, transformation, or
  partial-window concept appears in the schema, the runtime, the fixture, or
  the promoted text. `sources.every(satisfied)` and `branches.every(satisfied)`
  are the only rules. Confirmed independently.
