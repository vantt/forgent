## Design Notes

### The gate lives at the request door, because that is where the definition is

`closeSessionByQuorum` holds no FlowDefinition at close time — it works from
the manifest and the event log — so it structurally cannot notice that the
bound protocol declared an aggregation. `run.mjs` is the ONE place both the
interactive CLI and the headless adapter reach a close. So the declaration is
turned into an enforced property there, in `aggregationCloseParams`, and
nowhere else.

**Corrected in the Fix Round below.** As first written, this note said the
gate could reuse the definition `run.mjs` already loads for the actor
membership check. That was the bug: that definition is the one the *request*
names. `aggregationCloseParams` now resolves its own definition from
`manifest.definitionRef` with a version-drift refusal and takes no definition
parameter at all. See Fix Round item 1.

The split of authority is preserved exactly as P07.3 designed it:

- `run.mjs` decides **which** validated aggregation speaks for the session;
- `session-engine.mjs` decides, inside its own close lock and from its own
  replay of the event log, **whether that outcome permits a close**.

The negative test for a `no-consensus` verdict asserts on the *engine's* text
(`validated as "no-consensus", not "consensus"`), which is what proves the
surface forwards an id rather than reimplementing the judgment.

### Selection rule: the most recently validated aggregation

`aggregation-validated` carries no `outputOperationRef`, so a record cannot be
matched back to the declaration's declared output operation without inventing
a join this contract does not define. The rule chosen is the **latest**
validated record on the log, because that is exactly the remedy
`closeSessionByQuorum`'s own refusal message prescribes ("resolve the
aggregation and validate a new one"): a later validation supersedes an earlier
verdict. Fail-closed in both directions — validating a `no-consensus` after a
`consensus` re-closes the gate.

Stated precisely rather than overstated: the selection happens outside the
engine's close lock and the engine re-checks only the id it is handed, so a
`no-consensus` validated *between* those two reads does not supersede the
already-selected `consensus`. Both writes need the same driver identity and an
active session, so this is a narrow same-driver race, not a cross-actor
exposure. Named in the contract; not closed here (Fix Round item 11).

`ignoredAggregations` is deliberately not consulted: a post-terminal record
cannot inform a close that already happened.

### The gate never fires for a protocol that declares nothing

`aggregationCloseParams` returns `{}` when the session's own bound definition
declares no `completion.aggregation`, and returns `{}` immediately for every
agent-led session (`manifest.definitionRef` is `null`). That covers every shipped
protocol under `core/` (verified by grep, Commands #5) and every existing test
fixture — which is why the whole pre-existing coordination suite is untouched
by this change rather than merely happening to pass.

### `show` renders absence explicitly

`renderAggregation` normalizes every optional list to `[]` and every optional
scalar to `null`, so the rendered object always carries the same 15 keys. The
test asserts that key set literally rather than spot-checking fields, which is
the check that would catch the Bug Taxonomy's "show rendering that silently
drops a dissent/failure field" if a later edit stopped mapping one.

Post-terminal records go to `ignoredAggregations` rather than being hidden —
the same "neutralize, don't hide" posture `show` already applies to
authorizations and dispositions.

### The parity test exercises two genuinely different doors — for `run`

Door 1 is a spawned `node bin/fgos.mjs coordination run --file` /
`coordination show` subprocess reading its runner config from
`.fgos/config.json`. Door 2 is `runCoordinationHeadless` called in-process with
an in-memory request object and `ctx.runnerConfig`. Two separate initialized
workspaces, the same fake executor registered identically in both, the same
request objects, the same three-phase scenario.

**Scoped honestly (Fix Round item 9).** That "two genuinely different doors"
claim holds for the two `run` comparisons only. The third comparison, over
`show`, is weaker and is no longer claimed otherwise:
`runCoordinationHeadless` exposes no `show` surface of its own, and the CLI's
`show` is a thin wrapper over the same `showCoordinationUseCase` the headless
side of the test calls directly — so that `deepEqual` compares one function
against itself plus the CLI's `--json` envelope round-trip. It still proves
the two workspaces reached identical rendered state and that the envelope
drops nothing; it is not a second implementation of `show`. The test's own
comment now says exactly this.

All three payloads (first run,
resumed run, `show`) are compared with `deepEqual` after mapping `asgn_…`
tokens to placeholders in first-appearance order and collapsing ISO
timestamps — nothing else is normalized away, so a different refusal, a
different quorum, or a dropped field would still fail.

### "Never upgrades confidence" is proved against disk, not against a return value

The evidence is `result.json` on disk for every run of every Assignment in the
session, snapshotted before validation and compared after validation AND after
the terminal transition. This is stronger than asserting on
`validateSessionAggregation`'s return value, which never claimed to touch a
RunResult in the first place; the question worth answering is whether anything
downstream of a `consensus` verdict rewrites the evidence, and nothing does.

### 1 (HIGH) — `aggregationCloseParams` resolves the SESSION's definition

authorize), so the drifted state was already terminal for the session in every
