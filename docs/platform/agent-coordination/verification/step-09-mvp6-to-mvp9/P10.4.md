## 1. The protocol's real shape

Private round-1 proposals -> a mediated, non-contribution aggregate artifact
-> bounded round-2 ("next-round") proposals anchored to round 1.

`metadata.id: core.coordination-protocol.group-thinking-delphi-feedback-lite`
-- checked against every existing `core/coordination-protocols/*.yaml`
metadata.id (`grep -rn "  id:" core/coordination-protocols/*.yaml`, 8 files,
none named `group-thinking-*`); genuinely unique, no collision with Phase
08's `deliberation-delphi-chain` (a different id) or with anything P10.2/
P10.3 would plausibly name (their own text was read per current-cell.md's
Must-Read list before picking this).

- **No claim of strong anonymity**: every input's provenance is traceable
  through this session's own event log/replay (the MVP6 context-grant
  mechanism) -- never information-theoretically hidden from the driver, who
  has full ledger visibility by design across this whole track. Same
  discipline P08.3's own Nominal-Group section already established.
- **No claim of statistical convergence**: `aggregate` is a plain declared
  operation (no `contributions` field -- none of the six closed MVP8
  contribution types names "aggregate") that produces ONE mediated artifact
  from the round-1 proposals. No vote, rank, or formal consensus method is
  declared or implied. `completion.aggregation` (MVP7's
  `evidence-preserving-synthesis` session-close gate) was deliberately NOT
  declared -- see §3 for why.
- **Bounded next-round proposals**, via a REAL enforced ceiling: see §2.

## 2. Real, testable ceiling: `topology.edges[].maxRounds`, not graph absence

Phase 08's own `deliberation-delphi-chain.yaml` bounds rounds purely
structurally -- there is no round-3 graph node, so a round 3 is
undispatchable only because nothing names it. This definition uses a
DIFFERENT, genuinely enforced mechanism instead:
`topology.edges: [{from: facilitator-actor, to: panelist-a, maxRounds: 2},
{from: facilitator-actor, to: panelist-b, maxRounds: 2}]` -- the same
`maxRounds` primitive `declared-consult.yaml` already uses (`maxRounds: 1`),
applied here for the first time to a two-round deliberation shape.

`dispatchDeclaredOperation`'s edge lookup
(`incomingEdge = topology.edges.find(edge => edge.to === actorId)`,
`session-engine.mjs`) matches by ACTOR alone, never by operation id. Both
`propose-round1` and `propose-round2` are bound to the same panelist actor,
so dispatching EITHER counts one round against the SAME shared cap. The
round-bound test (`test/runner/coordination-delphi-feedback-lite.test.mjs`,
3rd test) proves a THIRD invocation for panelist-a -- targeting
`propose-round2` again, a genuinely new taskKey, a real `fromAssignmentId`,
structurally identical in every other respect to the legal round-2 call --
is refused by the engine itself with `"...allows at most 2 round(s)..."`,
and that the refused attempt creates zero additional Assignments (asserted
against `replaySession`, not the dispatch return value alone). This is the
Acceptance criterion's own "real round-bound negative test."

Round ORDER (round 2 cannot be linked as a durable contribution before
`aggregate` settles) is enforced independently, by the SAME MVP6
visibility-window mechanism `deliberation-delphi-chain.yaml` already proved
-- reused, never reimplemented: `round1-open` is vacuously open from session
start; `round2-open` opens only once `aggregate` settles. The 2nd test
proves this: a round-2 Assignment is dispatched (and settles) BEFORE
`aggregate` ever runs -- the edge doesn't care, since `fromAssignmentId`
only needs to name any Assignment belonging to the edge's `from` actor, and
`convene` qualifies -- but the LINK is refused with
`/visibility window "round2-open" to be open/`, and the refused link writes
nothing (`replayed.contributions.length === 0`).

**Bound and order are therefore two independently enforced properties, from
two different mechanisms, proved by two separate negative tests** -- not one
mechanism doing double duty.

## 3. Design decisions, and two real findings from empirical failures

- **`completion.aggregation` (MVP7 evidence-preserving-synthesis) was
  considered and deliberately not used.** The phrase "evidence-preserving"
  in this cell's own Goal bullet is satisfied by the Deliberation
  Contribution Ledger alone (P08.2's own contract text: "evidence-PRESERVING
  ... every input's provenance is traceable through the session's own
  replay/ledger"), matching P08.3's precedent (a plain `aggregate`
  operation, no session-close gating). Adding `completion.aggregation` would
  have required a `requiredDisclosures[]` design, a `sourceOperationRefs[]`
  choice spanning two differently-shaped round operations, and session-close
  wiring this cell's Acceptance criteria never asked for -- avoided as
  unbounded scope creep (YAGNI), not an oversight.
- **Two distinct operation ids (`propose-round1`/`propose-round2`), not one
  operation id reused at two graph nodes.** My first draft reused a single
  `propose` operation id bound to `panelist-a`/`panelist-b` at both
  `phase-round1` and `phase-round2` (reading the Activation contract's
  "the same operations[].id may be declared required at one graph position
  and driver-authorized at another" as license for this). **This is a real
  engine constraint, found empirically, not a style preference**:
  `resolveDeclaredOperationActor` (`session-engine.mjs`) matches
  `{operationId, targetActorId}` against the FIRST node in graph order whose
  binding's actor agrees -- there is no node/round discriminator parameter
  anywhere in `dispatchDeclaredOperation`'s signature. Every round-2
  dispatch silently resolved to the round-1 binding (wrong
  `contextAccess.visibilityWindowRef`, `round1-open` instead of
  `round2-open`), which is why my first test run showed a round-2
  contribution linking successfully with NO refusal at all (the
  round-order negative test failed with "Missing expected exception").
  Confirmed the root cause by reading `resolveDeclaredOperationActor`
  directly (`matches.find(...)`/`matches[0]`, `session-engine.mjs:1002`)
  before redesigning, not assumed. Fixed by giving round 1 and round 2
  their own operation ids, matching Phase 08's own precedent shape -- but
  now I know WHY that shape is required, not merely that it was chosen
  before.
- **Actor-scope `minTier` set above `standard`, not at `standard`, on
  purpose.** My first draft set both panelist actors' `spec.actors[].policy.
  minTier` to `standard`. `resolveAssignmentDispatchPolicy`'s own hardcoded
  default floor is ALSO `standard`
  (`effectiveTier = opPolicy.minTier || 'standard'`), and its
  provenance-update comparison is a STRICT `strength(cliTier) >
  strength(effectiveTier)` -- a tie never updates attribution. The resolved
  VALUE was correct (`standard`), but the persisted `RunResult.policy.
  provenance.tier.source` stayed `{scope: 'default'}` instead of
  `{scope: 'actor', id: 'panelist-a'}` -- confirmed by a standalone debug
  script reading the real `runResult.policy` object before concluding this
  wasn't my test's own bug. Fixed by raising panelist tier to `analytical`
  (above the default floor) and facilitator to `critical` -- both now
  provably actor-scope-attributed, not merely coincidentally correct in
  value. This is a genuine, narrow, documented (in-code comment, since it
  wasn't previously written down anywhere I found) engine behavior any
  future protocol author declaring an actor-scope `minTier: standard` should
  know about.

## 5. Per-actor provider/tier requirement -- explicitly NOT built here, with a real finding why

**I did not build a per-actor EXECUTOR/provider dispatch demonstration in
this cell.** A real, empirically-confirmed kernel constraint makes the
FlowDefinition-level channel the cell's own hint text pointed at
non-viable: `assertNoPortableExecutorPin` (`session-engine.mjs:779`) throws
whenever ANY portable policy scope -- and `PORTABLE_POLICY_SCOPES` is
`{runner, definition, operation, role, actor}`, `actor` included -- declares
a literal `preferExecutor`. Declaring `spec.actors[].policy.preferExecutor`
in this definition would make every real dispatch against it throw at the
policy-resolution gate, not merely be a no-op or get silently ignored.
Confirmed by reading `session-engine.mjs:777-788` directly, not assumed from
the contract prose alone (the flow-definition.md PolicyPatch section's
"Literal executor/model names in policy are trusted session/human/project
overrides, not portable framework defaults" already implies this, but the
kernel-level THROW, not merely a documented convention, is the harder fact).

**What I built instead, which IS legal and IS proven live**: real
`spec.actors[].policy.minTier` usage on both roles (facilitator: `critical`,
panelists: `analytical`), proven end-to-end in the first test via two real
dispatches asserting `runResult.policy.provenance.tier.value` AND
`.source === {scope: 'actor', id: '<actor-id>'}` for both a facilitator and
a panelist Assignment -- a real, distinguishable, actor-scoped POLICY
demonstration, just not the PROVIDER-routing half of the cell's own hint.

**Where real per-actor provider/tier selection actually lives, per P10.1's
own already-proved mechanism**: the REQUEST's own `actors[].executor` field
(`ACTOR_ALLOWED_KEYS`, `src/verbs/coordination/schema.mjs`), resolved
through `actorPolicyFields`/`run.mjs`, exactly as P10.1's own mid-flight
addendum (§3a of P10.1.md) already proved live with two genuinely different
registered executors dispatching as two different actors in one session.
That mechanism is session/request-time, not a portable FlowDefinition field,
and it is protocol-agnostic -- it works identically whichever of P10.2/
P10.3/P10.4's protocols a request names. **I am stating plainly, per this
cell's own instructions, that I did not additionally re-prove that
mechanism against THIS specific protocol** -- P10.1 already proved it
generically and executor-id-agnostically, and re-proving it per-protocol
would duplicate P10.1's own test rather than add new coverage. The
Coordinator should check whether P10.2 or P10.3 covers the executor-routing
half explicitly; if neither does, the honest state is: the mechanism is
proved generically (P10.1) and known to be reachable by any protocol
(nothing in `group-thinking-pack.mjs`'s gate reads or filters
`requestObject.actors`, per P10.1 §3a), but no cell in Phase 10 has proved
it AGAINST one of the three new Lite protocols specifically.
