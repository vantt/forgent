## HIGH-1 — The close-time aggregation gate reads the definition from the REQUEST, not from the session. Bypassable through the public request door.

**File/line:** `src/verbs/coordination/run.mjs:219-235`
(`aggregationCloseParams`), called at `run.mjs:500`; the `definition` it
receives is bound at `run.mjs:317`
(`definition = loadCoordinationProtocol(request.protocolRef.id, ...)`).

**Requirement violated:** `current-cell.md` P07.4 Goal bullet 1 and
`P07.4.md`'s own Requirement 1 — *"a definition declaring
`completion.aggregation` with no validated aggregation REFUSES the close."*
Also `coordination-session.md`'s promoted text (*"A protocol that declares
`completion.aggregation` … may not close on quorum alone"*) and
`flow-definition.md`'s (*"the request door refuses the close until an
aggregation has been validated for that session"*).

**Failing scenario.** The gate consults whichever protocol document *the
current request names*, never the protocol the session is actually bound to.
`findExistingManifest` (`run.mjs:130-146`) resumes an existing session on
`coordinationId` + `writerId` alone — it never checks that
`request.protocolRef.id` matches `manifest.definitionRef.id`. So the session's
own driver, holding nothing but the driver identity it legitimately has, can
resume a declared-aggregation session under a *different* `protocolRef` that
declares no aggregation, and the gate returns `{}`.

**Evidence — executed against this worktree, not argued.** Two project-tier
protocols, structurally identical, differing only in `completion.aggregation`;
one session opened under the aggregation-declaring one, then resumed under the
other with a single `disposition` step (which never touches `definition`):

```
FIRST  closed= false  reason= coordination run: protocol "…agg-bypass" declares
       completion.aggregation, but session "coord_bypass_probe" has validated
       no aggregation -- refusing to close …
manifest.definitionRef = {"id":"test.coordination-protocol.agg-bypass","version":"1.0.0"}

SECOND closed= true   reason= undefined
manifest.status = completed
reported definitionRef = {"id":"test.coordination-protocol.agg-bypass","version":"1.0.0"}
```

The session closed to `completed` with **zero** validated aggregations, and the
returned payload still reports the aggregation-declaring `definitionRef` — the
close looks, from the outside, exactly like a legitimate one. No `.fgos` raw
write, no forged event, no store-module access: the ordinary CLI request door.

I probed the sibling vector too — resuming with a `kind: "agent-led"` request
so `definition` stays `null` — and it is **blocked** by the engine
(`dispatchPrimaryTask: session … has no "primary" actor bound`). The
`protocolRef`-swap is the live one.

**Why this is the same bug the previous commit just fixed.** `7263a15c`, one
commit before this cell's base, is titled *"pin aggregation validation to the
session's own bound definition"*, and its message reads: *"validateSessionAggregation
accepted a FlowDefinition as a caller parameter instead of resolving it from
the session's own `manifest.definitionRef`, so a caller could hand the mediated
door a definition … and reach a favorable consensus verdict the real protocol
would refuse."* P07.4 reproduced that exact shape one layer up, at the close
door, on the same feature, in the same wave.

**Smallest fix.** Resolve the definition inside `aggregationCloseParams` from
the session, exactly as `validateSessionAggregation`
(`session-engine.mjs:3078-3092`) now does — read
`readManifest(coordinationId, engineOpts).definitionRef`, return `{}` when it
is `null`, otherwise `loadCoordinationProtocol(definitionRef.id, …)` with the
same version-drift refusal — and stop passing the request-loaded `definition`
into it at all. That also removes the `let definition` hoist at `run.mjs:285`,
restoring the original block-scoped binding. Add the regression test the
scenario above describes: a declared-aggregation session refuses to close when
resumed under a different `protocolRef`.

## MEDIUM-2 — P09.1: a `specialistSlots[].id` may collide with a declared `spec.actors[].id`, defeating the "never routable" guarantee in one direction and false-rejecting a legal edge in the other.

**File/line:** `src/runner/definitions/schema.mjs:545-576` (the slot/edge
cross-check) and `:365-400` (`validateSpecialistSlot` — `id` is only checked
for non-emptiness; nothing asserts it is disjoint from any other id space in
the definition).

**Requirement violated:** `current-cell.md` P09.1 Goal bullet 4 — *"Reject
explicit runtime edges naming a slot (slots are declarative capacity, not a
routable topology node) and reject undeclared slot expansion."* The Acceptance
line is stronger still: *"Topology class and operation legality remain fully
predeclared/static."*

**Failing scenario, both directions.** With `specialistSlots[0].id` set to
`'actor-1'`, which is also a declared `spec.actors[].id` (executed):

```
# with edges: [{from:'actor-1', to:'actor-2'}]
REJECTED: spec.profile.topology.edges[0].from "actor-1" references a declared
          specialist slot id -- slots are declarative capacity, never a
          routable topology edge endpoint
# without that edge
ACCEPTED (no edge). graph actor = actor-1 | slot id = actor-1
```

1. **False positive:** a perfectly legal edge between two real actors is
   rejected, because one actor's id happens to match a slot id.
2. **False negative:** `graph.nodes[].operations[].actor: 'actor-1'` validates
   — it resolves against `spec.actors[]`, as the new docstring at `:929-944`
   correctly says — so the declared slot id *is* now reachable as a routable
   graph binding. The docstring's conclusion ("a graph operation binding can
   never statically expand into an undeclared (or any) specialist slot") holds
   only while the id spaces are disjoint, and nothing enforces that.

FlowDefinitions are portable protocol content, not operator-authored trusted
data (`verbs/coordination/schema.mjs`'s own `writerId` comment draws exactly
that line), so "an author wouldn't do that" is not the applicable standard.

**Smallest fix.** In the `specialistSlots` block, after `seenSlotIds` is built,
reject any slot id that appears in `spec.actors[].id` (and, for the same
reason, `spec.roles[]`, `spec.operations[].id`, and `graph.nodes[].id`). The
existing `roleSet`/`operationIds`/actor sets needed for that are already
computed in `validateSpec` at `:1003-1005`, so the check can sit alongside
`assertSpecialistSlotsReferenceRealEntities` rather than in the profile pass.
Add the two negative tests above.

## MEDIUM-3 — The forged-aggregate residual is recorded as "structural"; a cheap mitigation is in fact on the table, one layer below where the trace looked.

**File:** `src/runner/coordination/store.mjs:1149-1186`
(`recordAggregationValidation`); asserted as structural in
`coordination-session.md` § "Named limitations, not omitted" item 1 and in
`P07.4.md`'s Gaps.

**This is the coordinator's top-priority question, answered directly.**

*Is the residual still within the same accepted trust-boundary class?* **The
class is unchanged, but the framing built on top of it is wrong.** P07.4's
Gaps argue: *"with the declaration enforced, a driver who wants an unjustified
close can no longer simply omit the id — forging the event is now the cheapest
route."* HIGH-1 shows the premise is false. The declaration is **not**
enforced against the session, so the cheapest route to an unjustified close is
neither omitting the id nor forging an event — it is naming a different
`protocolRef` on the resume request, which needs no `.fgos` write access, no
store-module access, and no forgery at all. The forged-aggregate residual's
significance therefore has **not** risen the way the trace describes; it is
still strictly the more expensive of the two routes, and the cheaper one sits
*above* the trust boundary rather than below it. Fix HIGH-1 first; only then is
the "forgery is now cheapest" analysis even the right analysis to be doing.

*Is a cheap mitigation being left on the table?* **Yes — one, and it is the
same fix shape `7263a15c` already applied.** The trace calls the residual
structural on the grounds that *"replay is definition-blind by design."* That
is true of replay, but the forgery does not enter through replay — it enters
through `recordAggregationValidation`, an exported store door that accepts
`outcome` as a plain caller parameter (`store.mjs:1149-1175`) and appends it
after shape/identity/active-session checks that never look at what the evidence
would actually classify to. That door is *not* definition-blind: it already
reads the manifest and validates every `sourceResultRef` against the session's
own Assignments. Removing `outcome` from its parameter list and deriving it
there — exactly as `7263a15c` removed `definition` from
`validateSessionAggregation`'s parameter list one commit earlier — closes the
careful forgery for every caller that is not a raw file append.

The two mitigations the cell brief floated are correctly *not* on the table,
and should be recorded as rejected rather than left open:
- **an audit-log requirement** adds nothing — the event log *is* the audit log,
  the forged event is already in it, and `show` already renders it (P07.4's own
  work); a forged record is indistinguishable from a real one in any log,
  which is the problem, not the absence of a log;
- **requiring the validating `writerId` to differ from another actor**
  contradicts the design as built: `replay.mjs:170-176` *refuses* any
  `validatedBy` that is not the session's driver, because a validated
  aggregation is defined as driver-authored session state. Changing that needs
  a new identity concept, which is not cheap and not this phase's.

**Smallest fix direction.** Out of P07.4's scope (`store.mjs` is Do Not Touch),
so no change here. But the residual should be rewritten in
`coordination-session.md` and in the trace as *"not closed in MVP7; the store
door accepts `outcome` as a caller parameter and could derive it instead —
same fix shape as the definition pin"*, rather than as *structural*. Recording
a fixable exposure as structural is how it stops being scheduled.

## LOW-1 — The "latest validated aggregation supersedes" rule is not enforced atomically; the narrow race fails open.

**File/line:** `run.mjs:221` (`resumeSession` read) vs.
`session-engine.mjs:2862-2875` (the engine's own replay, inside its close lock).

`aggregationCloseParams` picks the last validated aggregation outside the close
lock and hands the engine an *id*. If a `no-consensus` record is validated
between the two reads, the engine re-checks only the id it was handed — the
older `consensus` — and permits the close, even though the design note's own
rule ("a later validation supersedes an earlier verdict … fail-closed in both
directions") says it should not. Narrow (both writes need the same driver
identity and an active session) and not a new exposure, but the design note
overstates the guarantee. Either pass the selection rule into the engine or
soften the note.

### Item 7, the replay consistency check — CONFIRMED-PRESENT, and exactly what it does and does not catch

`replay.mjs:214-236`, inside the existing `outcome === 'consensus'` block.

**What it catches** (both executed): a `consensus` with `artifactRevisionRefs`
absent or empty, and one whose length differs from `sourceResultRefs.length`.

**What it does not catch — it is a COUNT check, never a CONTENT check.** I built
forged consensus records through the real store door and replayed them:

```
T3 [junk strings, right count]                 -> store ACCEPTED, replay ACCEPTED, outcome=consensus
T3 [duplicated single pin]                     -> store ACCEPTED, replay ACCEPTED, outcome=consensus
T3 [pins naming a NON-EXISTENT artifact]       -> store ACCEPTED, replay ACCEPTED, outcome=consensus
T3 [empty strings, right count]                -> REFUSED (payload.artifactRevisionRefs must be an
                                                  array of non-empty strings — the pre-existing
                                                  event-schema rule, not the new check)
```

So `artifactRevisionRefs: ['x','y']` against two sources passes; so does the
same pin repeated twice; so does a pin naming an artifact that does not exist.
Nothing resolves a pin against the session's real Assignments, artifacts, or
revisions. The bar a forger must clear is one line of arithmetic. Note the
project's own test fixture is itself in this category — `storePayload` emits
`artifact://<assignmentId>@rev-<i>`, a synthesized string.

This is not a defect: the disposition asked for exactly a count/non-zero check
in the definition-blind loop, and that is what landed. The docs are accurate —
`coordination-session.md` says "absent/empty or do not number exactly one per
cited `sourceResultRefs` entry", and its Named Limitation 1 says a forger
"mirroring that shape exactly, matching pin counts included" still wins. I flag
it only so nobody later reads P07.4.md's "only a forger who mirrors the full
shape of a real validation still wins" as a higher bar than it is: mirroring the
shape means matching a count.

### New this round

**NEW-1 (LOW-MEDIUM, documentation accuracy — not a code block). A
same-`{id, version}` in-place edit dropping `completion.aggregation` bypasses
the gate completely. Reproduced.**

The drift check compares versions, so an edit that leaves the version alone
passes it, and the now-absent declaration takes the `return {}` early exit:

```
C/phase1                       closed=false status=active  aggregations=0
C/phase2(edit, SAME version)   closed=true  status=completed aggregations=0
```

The session closed to `completed` with zero validated aggregations. Reachable
without touching the original file at all, since the loader lets a project-tier
document shadow a domain/core one by id (`protocol-loader.mjs:202-209`).

**Why this is not a BLOCK, and not a defect in this fix.** The exposure is
already disclosed, as `coordination-session.md`'s pre-existing Named Limitation
2 — *"The definition is pinned by `{id, version}`, never by content … Every
sibling definition-consuming door in the engine shares this exposure"* — and the
close gate is now exactly such a sibling. The disposition mandated copying
`validateSessionAggregation`'s pattern verbatim rather than re-deriving it; the
Fixer complied, and inheriting the pattern's residual is the consequence of the
instruction, not a lapse. It also sits at a different, higher-cost trust
boundary than the HIGH did: it needs `.fgos` write access, exactly like the
already-accepted forged-aggregate residual, whereas the HIGH needed only an
ordinary request.

**What I would change, one sentence.** Limitation 2's illustration is *"could
still swap in a same-`{id, version}` document declaring a different cohort"*.
At this door the consequence is categorically larger: it does not alter a
parameter, it silently switches off the single enforced property this cell
exists to add, and the resulting close is externally indistinguishable from a
legitimate one. Naming that consequence where the limitation is stated would
make the promoted text fully honest. A real fix (a content digest on
`definitionRef`) is a whole-engine change and correctly not this round's.

**NEW-2 (LOW). The slot-id disjointness check omits one id space:
`visibilityWindows[].id`. Reproduced.**

```
T4 [slot id == visibilityWindows[].id] -> ACCEPTED
```

`assertSpecialistSlotIdsAreDisjoint` enumerates four spaces — actors, roles,
operations, graph nodes. Disposition item 3 named exactly those four, so the
Fixer delivered the accepted scope in full and this is out-of-scope rather than
incomplete. But the window id space is a slot's *own* reference space (a slot
declares `allowedVisibilityWindows[]`), which makes it the one remaining space
where the function's own stated rationale — *"Disjointness is what makes 'a slot
id is never in the actor id space' a property rather than an assumption"* —
still rests on an assumption. Inert today (nothing resolves a slot by id at
runtime), and the fix is one array entry using `windowIds`, a set already
computed in `validateSpec`. Worth taking before P09.2 resolves anything against
slot ids.

**OBS (no action). The accepted "a drifted definition can no longer close even
with no aggregation declared" consequence is real but close to unreachable.**
`aggregationCloseParams` now throws on drift before the opt-out early return, so
in principle a no-aggregation session that would previously have closed can be
refused. In practice the window barely exists: a close is attempted on every
run, so a quorum-satisfied session closes on the run that satisfies it; and once
a definition has drifted the session can no longer dispatch or authorize either
(`session-engine.mjs:1367`, `:1734`, `:2425`). The Fixer's own reasoning
("the drifted state was already terminal for the session in every respect but
this one") is sound, and the explicit opt-in regression test still passes.
