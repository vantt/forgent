## 1. The central decision, re-derived from first principles

I read `linkSessionContribution`
(`src/runner/coordination/session-engine.mjs:4013-4216`) in full. The Doer's
"complete, self-mediating door" claim is accurate, and I can name exactly
why:

- the FlowDefinition comes from `manifest.definitionRef` (never the caller),
  with a version-drift refusal;
- `operationRef` is read off the backing Assignment's reserved
  `protocol-operation:` stamp — an Assignment that merely shares an actor
  can back no contribution;
- `visibilityWindowRef` is read off that operation's own node binding
  (`contextAccess.visibilityWindowRef`), so a caller cannot choose which
  window rule its contribution is judged against;
- open-state is re-derived from a *fresh* `replaySession` via
  `deriveVisibilityWindowState`, not trusted from the dispatch-time gate;
- a reasoning-time-vs-window-open ordering check compares log positions
  (`runAuthorizedSeq <= windowOpenedAtSeq` refuses);
- the artifact revision pin is re-checked against the file's current bytes;
- `validateContributionLineage` runs with `declaredOperations` built from
  the definition's own `contributions.allowedTypes`.

The caller supplies only ids, `type`, `roundKey`, and lineage claims — each
of which is checked against the real ledger. **Reaching this door creates no
new kernel-level trust decision.** That is the substance of the
"implementation bug vs. shared missing primitive" test, and it lands on
"implementation bug."

I hunted specifically for a door-side gap that the pack's new `contribution`
step fails to close, since finding one would flip the classification. I found
none. I also confirmed the fix is structurally reachable for *all three*
protocols, not only the one tested end to end: every contribution-declaring
operation in `group-thinking-nominal-group-lite.yaml` (and in the other two)
declares `contextAccess.visibilityWindowRef`, which is the door's hard
prerequisite.

## 2. P10.1's five bypasses — none reopened

`linkedBy` is **quadruply** defended; no caller-supplied value can ever reach
it:

1. `schema.mjs`'s new `assertNoLinkedBy` rejects the field at the request
   boundary (mirrors the existing `assertNoAuthorizedBy` exactly);
2. `run.mjs:547` hardcodes `linkedBy: driverIdentity` — a literal, never a

   `manifest.provenanceRoot.writerId` inside `recordContributionLink`;
4. `run.mjs`'s `findExistingManifest` refuses any resume whose request
   `writerId` differs from `provenanceRoot.writerId`.

Each of the five bypasses, checked against the real code:

| # | Bypass | Why the `contribution` step does not reopen it |

| 1 | Switch protocols silently | The door loads the definition from `manifest.definitionRef`, never from the request, and refuses on version drift. |
| 2 | Bypass grants | Window ref derived from the binding; open-state re-derived fresh from `replaySession`. No grant is caller-supplied. |

| 4 | Authorize a specialist | The branch never calls `authorizeSpecialistSlot`/`recordSpecialistAuthorization`. |
| 5 | Close a session directly | `recordContributionLink` refuses a non-active session; the door never transitions status. If anything this strengthens #5. |

Every window/provenance/lineage check inside `linkSessionContribution` runs
unchanged regardless of how it is invoked — confirmed by reading the function
body, not by trusting the claim.

One structural note: P10.1 §5's *argument form* for bypasses #3/#4 ("the

## Findings

### MEDIUM-1 — bare `catch {}` discards the real cause (user-visible diagnosability regression)

Both new guards use `catch {` with no error binding, so the underlying
`FlowDefinitionError` message is thrown away. The updated R4 test in
`test/verbs/coordination-launch-master-loop.test.mjs` documents the loss
directly: it previously asserted `no CoordinationProtocol definition found for
id`, and now asserts only a generic `could not be resolved`.

Worse, the two failure shapes are now indistinguishable, and one is actively
misleading: on a malformed *sibling* protocol file, the message blames the id
the user asked for rather than naming the broken file, because
`loadCoordinationProtocol` scans the whole tier before filtering by id. A user
who typos a protocol id and a user with one corrupt file in the registry get
the same unhelpful message.

The project's own root instructions list "useful errors" as a core rule. The
fix is one line per site, with no behavior change:

```js
} catch (err) {
  throw new StoreError(
    'validation',
    `coordination request: protocol "${request.protocolRef.id}" could not be resolved: ${err.message}`,
  );
}
```

(and the symmetric change for the `CoordinationError` in
`aggregationCloseParams`).

### MEDIUM-2 — inaccurate claim in promoted canonical contract text

`docs/architect/agent-coordination/contracts/coordination-session.md`'s new
"Five bypasses, verified structurally impossible" paragraph reads:

> (2) bypass grants, (3) validate its own aggregate, (4) authorize a
> specialist — `run.mjs`'s public request vocabulary never exposes any of
> these three as caller-invokable actions at all

That is false for #2, and it contradicts `P10.1.md` §5, which deliberately
separates the two reasons: *"three (validate-aggregate, authorize-specialist,
close-directly) because `run.mjs`'s public request vocabulary never exposes
them at all, and two (switch-protocols, bypass-grants) because this gate's own
explicit-selection checks run before, and add nothing to, `run.mjs`'s existing
enforcement."*

An `authorize` step **does** exist and **is** caller-invokable. It is safe
because it is correctly mediated through `authorizeDeclaredOperation`, not
because it is absent from the vocabulary. As written, the promoted text
overstates the guarantee's shape in a canonical contract document that future
readers will rely on.

only for RFC-Review-Lite. Delphi-Feedback-Lite got a negative (refusal) proof;
Nominal-Group-Lite got only an expected-message-text update.

This matters because P10.7's own Acceptance criteria ("private rank CAPTURE"

One positive `rank`-contribution test through the pack gate for
Nominal-Group-Lite would close this and make the pack-wide claim fully
evidence-backed.

### MEDIUM-4 — an unreported, unnamed test flake

Re-running the Doer's own combined-focused command four times, I observed
`fail 2` in two runs and `fail 1` in two runs. The extra failure is:

`test/runner/coordination-store.test.mjs` →
*"two concurrent creators racing DIFFERENT logical tasks under one session
never lose an assignmentRefs append (both land)"*

It passes 5/5 when the file is run in isolation, and fails roughly half the

**This is not caused by this cell** — I confirmed

### LOW-5 — test count overstated

§4 claims "7 new unit-level request-boundary tests" in
`test/verbs/coordination-run-driver-steps.test.mjs`. I count 6 new tests plus
1 updated. Trivial, but the report's own discipline is exact counts.

### LOW-6 — plan IDs in code comments

The new comments in `run.mjs`/`schema.mjs` lead with `// P10.10 (Promotion And
Closeout): ...`, which conflicts with this repo's own
`.claude/rules/review-audit-self-decision.md` § "Stable Code Artifacts" ("Do
not put plan IDs, phase numbers, audit labels, or finding codes in code
comments"). The comments themselves are good — they explain the invariant and
the why, not just the what. There is also heavy existing precedent in these
same files (`P08.2`/`P08.3`/`MVP8`/`R6`/`R7` references throughout), so this is
written-rule-vs-established-practice rather than a defect introduced here.
Flagging for consistency; not blocking.

### LOW-7 — request boundary is stricter than the engine door on contribution ids

`schema.mjs`'s `assertSafeId` enforces `^[A-Za-z0-9_-]+$` on `contributionId`,
`anchors[]`, and `respondsTo`. The engine's own `assertContributionIdShape`
(`store.mjs:1307`) is looser — it rejects only path separators, `..`, and the
`contribution:` prefix, so it permits dots and colons.

The direction is safe (the boundary can only narrow, never widen). But a
contribution created through a direct engine call with a dotted or colon'd id
could never be named as an `anchor` or `respondsTo` through the pack gate.
Worth one sentence in the promoted contract text so the narrowing is
disclosed rather than discovered.
