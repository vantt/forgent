Independent, zero-prior-context attack pass. No fixes applied. Every claim
below is backed by an actual command run against the live worktree

## Summary

P06.2's visibility-window runtime gate has a **HIGH severity** real bypass:
`resolveOperationOutcome()` in `session-engine.mjs` resolves "did the
required source operation settle" by matching `assignment-created` events
on **actor id alone**, never cross-checking that the matched assignment
was actually for the operation being resolved. Confirmed exploitable
through two independent, concretely reproduced attack paths (multi-op actor,
actor-replaced piggyback). This defeats the entire purpose of the gate: an
attacker (or an innocent scheduling coincidence) can open a window without
the actually-required operation ever settling successfully.

P07.2's aggregation-outcome classifier held against every attack attempted
(hidden dissent, malformed disclosure value shapes incl. nested
objects/arrays/whitespace, stale/missing/wrong-typed `currentRevisions`,
consensus-with-unresolved-dissent, duplicate-dissentRef shadowing,
`__proto__`-shaped keys, input mutation, and a grep for hidden
scoring/threshold logic). One design-boundary observation is noted (not a
break of the stated invariant).

**Overall verdict: BLOCK** (on P06.2's HIGH finding; P07.2 is clean).

## P06.2 — Visibility Runtime Enforcement

### Finding P06.2-1 (HIGH): window-source resolution ignores `operationId`, matches by `actorId` alone

**Code**: `session-engine.mjs`, `resolveOperationOutcome()` (new in this
diff, around the `deriveVisibilityWindowState` block added after line 995):

```js
const createdEvent = events.find((event) => event.type === 'assignment-created' && event.payload.actorId === effectiveActorId);
```

This is the ONLY check used to decide whether the required source
operation (e.g. `research-a`) has an `assignment-created` event to chain
into `result-linked`/RunResult classification. It never checks that the
matched `assignment-created` event was actually created **for the
operation being resolved** — it accepts the FIRST assignment (in event
order) the resolved actor was ever given, for ANY operation.

The Doer's own trace file (P06.2.md, Design Notes) acknowledges this is
necessary because `assignment-created.operationId`/`nodeId` are populated
ONLY for driver-authorized bindings, and defends the actor-only match by
citing it as "the SAME resolver... already uses" and analogous to
`classifySessionQuorum`/`synthesizeResearchFanIn`'s own actor-only
`.find()`. That precedent is real (confirmed at
`session-engine.mjs:1619`, `:2381`), **but those callers' own design
assumes one actor performs exactly one operation/branch role in the
session** (`synthesizeResearchFanIn`'s `branchActorIds` are dedicated
fan-out branch actors). Visibility windows carry no such guarantee — the
codebase's OWN existing test fixture
(`coordination-driver-authorization.test.mjs:10-13`) explicitly documents
and exercises the opposite shape: "ONE actor... bound to TWO DIFFERENT
operations at TWO DIFFERENT graph nodes... so an authorization matched by
actor alone... is provably wrong" — the exact defect class this cell's
own gate reintroduces for the window-legality check specifically.

### Attack 1 — multi-operation actor bypass (CONFIRMED BROKEN)

**Attack**: Bind actor `researcher-a` to TWO operations in the graph:
`research-a` (a required window source) and an unrelated `noise-op` at a
different node. Dispatch and successfully complete `noise-op` only.
**Never dispatch `research-a` at all.**

**Evidence** (full repro script:
`/tmp/claude-1000/.../attack1-actor-multiop.test.mjs`, run with
`FGOS_DISABLE_OPPORTUNISTIC_CHECKS=1 node --test`):

```
WINDOW STATE: {
  "open": true,
  "sources": [
    {
      "operationRef": "research-a",
      "satisfied": true,
      "reason": null,
      "actorId": "researcher-a",
      "assignmentId": "asgn_coordinator_1_op_001",   <-- this is noise-op's assignment
      "runId": "run_asgn_coordinator_1_op_001_01"
    },
    ...
  ]
}
*** CONFIRMED VULNERABLE: research-a reported satisfied via an unrelated assignment ***
```

`deriveVisibilityWindowState` reports the window **OPEN** and
`authorizeDeclaredOperation('synthesize', ...)` would succeed, even though
`research-a` — the operation the window is supposed to gate on — was never
dispatched, let alone completed. `assert.equal(state.open, false, ...)`
fails: `true !== false`.

### Attack 2 — actor-replaced piggyback (CONFIRMED BROKEN)

**Attack**: `research-a` is bound to `researcher-a`. `research-a` is
**never dispatched at all** (stronger than a failed attempt — zero
`assignment-created` for `researcher-a` ever exists). `researcher-a` is
then replaced by `researcher-a-v2` via `replaceSessionActor` (a
legitimate, independently-valid operation this codebase supports for
reassignment). The replacement (`researcher-a-v2`) is given a
**completely unrelated** ad-hoc assignment ("File quarterly expense
report") via the raw store door (`createSessionAssignment`/`linkResult`,
the exact pattern the Doer's own actor-replaced test fixture uses for a
replacement's attempt) and it succeeds.

**Evidence** (full repro script:
`/tmp/claude-1000/.../attack2-actor-replaced-piggyback.test.mjs`):

```
WINDOW STATE: {
  "open": true,
  "sources": [
    {
      "operationRef": "research-a",
      "satisfied": true,
      "actorId": "researcher-a-v2",
      "assignmentId": "asgn_coordinator_1_op_002",   <-- the unrelated expense-report task
      ...
    },
    ...
  ]
}
*** CONFIRMED VULNERABLE: research-a satisfied by an UNRELATED task completed by its actor-replaced lineage ***
```

This is a materially worse variant of the same root cause combined with
the `actor-replaced` lineage-following the cell added specifically for
this scenario (`buildActorReplacementMap`): a global (session-wide,
unscoped-to-operation) actor replacement lets a replacement satisfy an
obligation it never actually worked on, as long as it did *something,
anything* that succeeded.

### Why this passes all 155/323 of the Doer's own tests

Every one of the Doer's own 11 new tests uses a fixture where the
resolved actor is bound to **exactly one** operation
(`researcher-a`→`research-a`, `researcher-b`→`research-b` only) and never
receives any OTHER assignment before or during the scenario. The bug is
invisible under that fixture shape by construction — the `.find()` always
happens to land on the "right" event because there is no "wrong" one to
find. Independently confirmed: running the full glob the Doer's trace file
cites (`coordination-session-engine`, `coordination-replay`,
`coordination-driver-authorization`, `flow-definition*`,
`coordination-schema`) plus `team-cognition*` — **256/256 pass**, zero
regressions — proving these two attacks are a genuine gap the existing
suite does not cover, not a regression this red-team introduced.

### Smallest-fix direction

`resolveOperationOutcome` needs the `assignment-created` event lookup to
additionally verify the assignment was actually for `operationId` — but
per the Doer's own Design Notes, `assignment-created.operationId` is only
populated for driver-authorized bindings, so a pure `event.payload.operationId
=== operationId` filter would not work for the paradigm case (research
operations are NOT driver-authorized). The fix likely needs to key off
`taskKey` (which IS deterministically derived from `operationId` at
dispatch time — see `taskKey = explicitTaskKey ?? \`declared:${operationId}...\``
at `dispatchDeclaredOperation`) rather than `actorId` alone, or by
resolving through the task-claim mechanism (`assertRefsOwnedBySession`'s
sibling primitives) that already maps a taskKey to its assignment. This is
a design decision for the Doer/Coordinator, not made here.

### Attacks that held (not broken)

- **Cache/latch bypass**: confirmed NOT exploitable. Both
  `authorizeDeclaredOperation` and `dispatchDeclaredOperation` call
  `deriveVisibilityWindowState` with a freshly-taken `replaySession()` (authorize)
  or the call's own once-memoized-per-call `replayOnce()` (dispatch) — no
  state survives across separate `authorizeDeclaredOperation`/
  `dispatchDeclaredOperation` invocations. Verified by direct code read
  (`session-engine.mjs:1230`, `:1554`, `:1778`).
- **Ownership-check regression**: confirmed NOT present. Read both call
  sites in full: `assertRefsOwnedBySession` (authorize: line ~1200;
  dispatch: line ~1743) runs and can throw BEFORE the new window-legality
  block in both functions — no early-return/short-circuit skips ownership.
- **Determinism/replay parity**: not independently broken by my own
  probing beyond the Doer's own replay-parity tests, which pass. Given
  Attack 1/2 above, note that replay would reach the SAME (wrong) verdict
  the live path reaches, since both call the identical pure function — the
  bug is in the derivation itself, not a live/replay divergence.

### Not exploited further (documented gaps, not attacked to a concrete break)

- `permits.sourceOperationRefs[]` per-ref filtering gap (Doer's own
  documented Gap #1) — not independently exploited; the Doer's own
  reasoning for why it's out of scope (no existing ref→producing-operation
  primitive for non-`asgn_`-shaped refs) is sound and this red-team did not
  find a way to force an illegitimate ref through the binding-level gate
  beyond what a window-open bypass already grants wholesale.
- Fan-out disambiguation (Doer's own documented Gap #2) — subsumed by
  Attack 1/2 above (that gap's stated failure mode is a strict subset of
  the actor-id-only matching defect confirmed here).

### Observation P07.2-1 (informational, not a break): "hidden dissent" only covers *disclosed*-but-unsurfaced dissent, not *never-disclosed* dissent

**Attack 5**: A source with `disclosures: {confidence: 'high'}` (no
`dissent` key at all) and `requiredDisclosures: ['confidence']` (dissent
not required) reaches `outcome: 'consensus'` even though nothing prevents
a real, undisclosed objection from existing.

This is **not a violation of the stated cell requirement** — the cell's
own wording is "reject a claimed consensus outcome when a disclosed
dissent/objection exists that the aggregation input doesn't surface,"
which is specifically about a disclosure that exists in `disclosures` but
is missing from `dissentRefs`. A dissent that is never disclosed at all is
outside what a pure, store-free evaluator can ever detect (there's no
independent ground truth to check against) — the Doer's own trace file
does not claim otherwise. Flagging only because the plain-English name
"hidden dissent" invites a reader (a future P07.3 integrator) to assume a
broader guarantee than what's actually implemented; worth a one-line
callout in the trace file or contract text when P07.3 promotes this, so
callers know they MUST include `dissent` in `requiredDisclosures` for the
guarantee to mean anything in practice. No code change recommended by
this red-team.

## Verdict

**BLOCK.**

P06.2-1 (HIGH) is a genuine, concretely-reproduced defeat of the runtime
enforcement gate this cell exists to add: a visibility window can be
opened without the operation it's gating on ever actually succeeding, via
either (a) the resolved actor being bound to more than one operation in
the graph — a shape this exact codebase's own test suite elsewhere calls
"the hardest case" and deliberately exercises — or (b) an `actor-replaced`
lineage whose replacement does unrelated work. Both are realistic,
not-contrived shapes given what else this codebase already supports
(multi-operation actor bindings, session-wide actor replacement). This
should not proceed to contract promotion (P06.3) or be treated as DONE
until `resolveOperationOutcome` cross-checks the matched assignment
against the operation actually being resolved, not actor id alone.

P07.2 has no blocking findings; the one observation is a documentation
note for future integration, not a code defect.

## NEW Finding P06.2-2 (HIGH): doors 2 and 3 are caller-forgeable through the SAME public dispatch API the original attack used

The fix's own stated invariant is "three independent doors, any one of
which is proof; **nothing else counts, so an unrelated Assignment fails
CLOSED**". Two of the three doors are plain caller-supplied input on
`dispatchDeclaredOperation`'s own public parameter list, with no
engine-only provenance separating an engine stamp from a caller string.

**Door 3 (contract constraint) — `session-engine.mjs:1988-1993`:**

```js
const contract = buildReadOnlyContract({
  ...
  constraints: [
    ...constraints,                                            // <-- caller-supplied (params.constraints)
    `protocol-operation:${definition.metadata.id}@${definition.metadata.version}#${operationId}`,
  ],
```

`assignmentServesOperation` (`:1128`) then tests
`constraints.includes('protocol-operation:...#<operationId>')` — an
`Array.includes` over a list the caller contributed to. It cannot tell an
engine stamp from a caller-written string.

**Door 2 (taskKey namespace) — `:1642`:** `params.taskKey` is a documented
public override (`@param {string} [params.taskKey] Overrides the default
declared:<operationId>[:round-N] taskKey`), written verbatim into the claim
record `readTaskClaimsByAssignment` reads back.

**Attack RT-A (door 3 forgery), CONFIRMED BROKEN.** Same fixture and same
public API as the original Attack 1. `researcher-a` is bound to both
`noise-op` and window source `research-a`. `research-a` is NEVER
dispatched. `noise-op` is dispatched with one extra parameter:

```js
constraints: [`protocol-operation:test.attack.multiop-actor@1.0.0#research-a`]
```

```
RT-A window open: true | research-a: {"operationRef":"research-a","satisfied":true,
  "reason":null,"actorId":"researcher-a","assignmentId":"asgn_coordinator_1_op_001",
  "runId":"run_asgn_coordinator_1_op_001_01","branches":[{"boundActorId":"researcher-a",
  "satisfied":true,...}]}
*** RT-A CONFIRMED VULNERABLE: forged contract constraint opened the window ***
✖ AssertionError: window must stay closed -- research-a was never performed  (true !== false)
```

**Attack RT-B (door 2 forgery), CONFIRMED BROKEN.** Identical, with
`taskKey: 'declared:research-a'` on the `noise-op` dispatch instead:

```
RT-B window open: true | research-a: {"operationRef":"research-a","satisfied":true,...,
  "assignmentId":"asgn_coordinator_1_op_001",...}
*** RT-B CONFIRMED VULNERABLE: forged taskKey opened the window ***
```

**Why this is not out of threat model.** Neither attack touches the raw
store door. Both go through `dispatchDeclaredOperation` — the exact
function the original, accepted Attack 1 used, at the exact same trust
level. The Fix Round's Scope Decision explicitly reasons about door 2
("trust-equivalent to the raw store door itself: a caller that can choose
taskKeys can assert operation identity") but that equivalence does not
hold: choosing a taskKey requires only an ordinary declared dispatch, not
store-level access. And the Fix Round makes no such caveat at all for door
3 — it describes the stamp as something `dispatchDeclaredOperation`
"stamps onto EVERY declared dispatch it builds", i.e. as engine-controlled
evidence. It is not; the caller's own `constraints` land in the same array
and are read back by the same `.includes()`.

This is the original root cause narrowed, not eliminated: the gate still
answers "did operation X settle?" from evidence the dispatch caller
controls. An attacker who wants the window open without performing
`research-a` now needs one extra parameter, not zero.

**Smallest-fix direction** (design decision for the Fixer/Coordinator, not
made here): no caller anywhere in the repo legitimately supplies a
`protocol-operation:` constraint — `grep -rn "protocol-operation:" src/
test/ bin/ core/` returns only the stamp site (`:1992`) and the reader
(`:1128`). So the stamp can be moved off the caller-shared `constraints`
array into a field the caller has no parameter path to, or
`dispatchDeclaredOperation` can reject a caller-supplied constraint
carrying the `protocol-operation:` prefix. Door 2 needs the symmetric
treatment (reject a caller `taskKey` in another operation's
`declared:<otherOperationId>` namespace).

## NEW Finding P06.2-3 (MEDIUM): door 2's prefix match cross-satisfies a sibling operation whose id begins with `<source>:` — no forgery, no attacker

`assignmentServesOperation` (`:1122`) accepts
`taskKey.startsWith('declared:' + operationId + ':')`. Operation ids carry
**no character restriction** — `definitions/schema.mjs:518` validates only
`op.id must be a non-empty string`. So an operation legally named
`research:deep` produces the default taskKey `declared:research:deep`,
which matches window source `research`'s prefix door.

**Attack RT-G, CONFIRMED BROKEN.** Two ordinary declared operations,
`research` (the window source) and sibling `research:deep`, both bound to
`researcher-a`. Only `research:deep` is dispatched, through the ordinary
public API with its own default taskKey — no forged parameter, no raw
store door, no adversary at all:

```
RT-G open: true | sources: [["research",true,null,"asgn_coordinator_1_op_001"]]
*** RT-G CONFIRMED VULNERABLE: sibling operation cross-satisfied the source, no forgery needed ***
✖ AssertionError: window must stay closed -- operation "research" was never dispatched
```

This is a pure accident path — an innocent naming choice silently opens a
window whose source never ran. No committed protocol in
`core/coordination-protocols/` currently uses a colon in an operation id
(checked all four), which is why severity is MEDIUM rather than HIGH, but
nothing in the schema prevents one. Fix direction: constrain operation ids
at the schema layer, or make the claim-key namespace check exact against
the closed set of discriminators `dispatchDeclaredOperation` itself
appends (`:round-N`, `:auth:<id>`) rather than an open prefix.

## Verdict

**BLOCK.**

The original Finding P06.2-1 is genuinely resolved as literally framed —
both accepted repros now fail, the fan-out all-of rule is correct end to
end, the actor-replaced lineage now transfers the obligation rather than a
licence, and the declared residual gap fails closed. No false negative was
found against any legitimate shape, including every binding shape the four
committed protocols actually use.

But the fix's own load-bearing invariant — "nothing else counts, so an
unrelated Assignment fails CLOSED" — does not hold. Two of its three
proof doors read caller-supplied input through the same mediated dispatch
API the original accepted attack used (P06.2-2, HIGH, two live repros),
and the third accepts an open prefix over an unconstrained id space
(P06.2-3, MEDIUM, one live repro, no attacker required). The window can
still be opened without the operation it gates on ever running. Both fixes
are small and local — the stamp needs a channel the caller cannot write,
and the namespace check needs to be exact.

P07.2 is unchanged by this round (no code touched) and its Wave 2 APPROVE
stands.

Status: DONE_WITH_CONCERNS

## NEW Finding P06.2-5 (MEDIUM): stamp-only turns claim-key squatting from a bypass into a permanent, silent liveness denial

Under Round 2, seizing a declared operation's claim key through
`dispatchPrimaryTask` *satisfied* the source (that was RT-H). Under stamp-only
it does the opposite, and the opposite is not harmless.

`dispatchDeclaredOperation` resumes an existing Assignment by claim key
(`peekClaimedAssignmentId`, `session-engine.mjs:1817`). If an unstamped
Assignment already holds `declared:research-a`, the legitimate declared
dispatch **resumes it** instead of creating a stamped one — and reports
success.

**Attack RT-O, CONFIRMED.** Stock fixture, two ordinary public calls, no raw
store door:

```
RT-O squat: CREATED asgn_coordinator_1_op_002        (dispatchPrimaryTask, taskKey 'declared:research-a')
RT-O legit dispatch: assignment asgn_coordinator_1_op_002 resumed=true constraints=[]
RT-O window open after legit work: false
     [['research-a', false, 'missing'], ['research-b', true, 'null']]
```

`dispatchDeclaredOperation('research-a')` returns successfully. The operator
has every reason to believe `research-a` completed. The window can now
**never** open for the life of the session: the only Assignment that claim key
will ever resolve to carries no stamp, and no mediated door will create a
second one. There is no error, no warning, and no diagnostic anywhere that
names the cause.

Severity MEDIUM, not HIGH: it is a denial, not an authorization bypass, and it
carries RT-H's own precondition (an actor named `primary`, or one
`replaceSessionActor` call to create one). But it is silent, permanent, and
newly introduced by this round's design — under Rounds 1–2 the resumed
Assignment would have satisfied the source. Fix direction: either have
`dispatchDeclaredOperation` refuse to resume an Assignment that carries no
stamp for the operation it is dispatching (fail loudly rather than silently
succeed), or reserve the `declared:` claim-key namespace against the
non-declared doors the way the constraint namespace is reserved.
