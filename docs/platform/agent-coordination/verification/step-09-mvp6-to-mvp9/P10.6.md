## 1. Design Notes — what this cell proves, and a real structural finding it surfaced

P10.2 already proved RFC-Review-Lite's full chain (independent objections,
controlled reveal, response, disposition, chat-history-free replay) via
DIRECT engine calls (`authorizeDeclaredOperation`/`dispatchDeclaredOperation`/
`linkSessionContribution` called directly). This cell's job, per
current-cell.md, was to prove the SAME properties reachable through the
REAL public pack gate (`runGroupThinkingRequest`,
`src/verbs/coordination/group-thinking-pack.mjs`) specifically — the surface
an actual user/skill invocation goes through, not a test author's direct
internal access — plus resume, which P10.2 never covered.

**A genuine, structural finding surfaced while building this, verified by
direct code read before a single assertion was written around it, never
assumed:** `run.mjs`'s entire request step vocabulary is closed to four
kinds — `operation` | `authorize` | `disposition` | `fan-out`
(`runCoordinationUseCase`'s own step-loop, read in full). **None of the
four ever calls `linkSessionContribution`** (session-engine.mjs) — grepped
every call site of that function across `src/`: the only callers anywhere
in this codebase are test files (P08's and P10.2's own suites). This means
the CONTRIBUTION-typed ledger records themselves (`proposal`/`objection`/
`response`, with `anchors`/`respondsTo` lineage) — the specific artifacts
P10.2's own replay assertions read — can only ever be created by a direct
`linkSessionContribution` call. There is no request-step shape anywhere in
`schema.mjs`/`run.mjs` that reaches that door.

This is genuinely out of this cell's May-Touch scope to fix: `run.mjs` and
`schema.mjs` are not on this cell's May-Touch list (only new test files and
`P10.6.md` are), and adding a new step kind to the one shared request door
every parallel cell/user ultimately depends on is exactly the kind of
shared, kernel-adjacent change current-cell.md's Do-Not-Touch text says to
**report as a blocking finding, never patch silently**. So it is reported
here, and — more importantly — proven **empirically**, not merely narrated:
`test/verbs/coordination-group-thinking-rfc-review-lite-pack-conformance.test.mjs`'s
own first test asserts `replayed.contributions.length === 0` after driving
the protocol's ENTIRE window-gated chain end to end purely through the pack
gate.

**What the gap does NOT block, verified by direct code read**:
`deriveVisibilityWindowState`/`resolveBindingOutcome`
(session-engine.mjs:1411-1490) derive every visibility window's open/closed
state purely from `assignment-created` + Run-settlement events — never from
`deliberation-contribution-linked` events. So the real REVEAL privacy gate
(the actual property RFC-Review-Lite exists to prove — "independent
objections before controlled reveal") is **fully** reachable and provable
through the pack gate; only the separate, CONTRIBUTION-typed deliberation
ledger (the specific record shape P08/P10.2's direct-call tests use to
express lineage) is not.

**A second real finding, also verified empirically, not assumed**:
`classifySessionQuorum` (session-engine.mjs:3104) requires every actor
DECLARED on the manifest to have completed something — not every
"required" operation. RFC-Review-Lite declares exactly 4 actors
(coordinator/proposer/objector-a/objector-b), and `respond` is
driver-authorized (never required, per P10.2's own Design Notes), so the
SAME moment objector-b settles — the only moment "reveal" can legally
open — is ALSO the moment quorum is met, and `closeSessionByQuorum`
(called unconditionally at the end of every request) closes the session
automatically at the end of THAT SAME call. There is structurally no
window in which "authorize granted in one call, a genuinely later separate
call still finds the session open to re-authorize it" can occur for this
specific protocol's actor topology. This cell's second test proves "no
re-authorization of an already-settled step" two ways instead, both
verified live: a same-call repeat of the identical authorize step is a
truthful idempotent no-op (`run.mjs`'s own documented idempotent-authorize
read-back path, lines 433-446), and a genuinely separate, later call
attempting the same re-authorization after the session has naturally
closed is refused outright by the engine's own active-session guard —
never a silent second grant either way.

**Resume, proven across FOUR separate `runGroupThinkingRequest` calls, not
one shot** (the first test): call 1 opens the session and settles
convene/propose/objector-a only (the interrupt point — one objection
settled, `closed:false`). Call 2, still through the pack, attempts the
SAME reveal-gated authorization P10.2 proved refused via direct engine
calls — refused identically through the pack gate, zero new events. Call 3
attempts a real, protocol-specific instance of P10.1's Fix Round 1
cross-check (already re-verified generically by P10.5 against a bare,
disposition-only session): resuming THIS cell's own richer, real,
mid-chain RFC-Review-Lite session under Nominal-Group-Lite — refused, zero
new events, the session's real bound protocol untouched. Call 4 is the
real resume: objector-b settles, the SAME authorization refused in call 2
now succeeds (mixing a literal ref carried over from call 1 with a fresh
`$ref:` label from call 4 — `resolveRef`'s own documented "advanced/resume
use case"), the proposer responds, and the driver dispositions the
response's own real, session-owned assignment (`$ref:respond` — the real,
artifact-backed target reachable without a contribution record). NO
re-dispatch of convene/propose/objector-a: replay confirms objector-a was
dispatched exactly once across the whole chain.
