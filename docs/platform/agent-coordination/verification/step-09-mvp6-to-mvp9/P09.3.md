## 3. Design Notes

### Why item 3 ("slot use in isolation fixtures") needed one real test, not zero

`current-cell.md` named this as "almost certainly" R7 (read-only isolation
from Work/git/coding mutation). Tracing `dispatchDeclaredOperation`
(`session-engine.mjs`) confirms there is exactly ONE
`buildReadOnlyContract(...)` call site inside that function (line ~2427),
reached identically regardless of whether `resolveDeclaredOperationActor`
resolved `actorId` via a static `actor` binding or via a live
`specialistBindings` lookup for a `specialistSlotRef` binding — the
specialist-binding branch only ever changes WHICH `actorId` gets dispatched,
never HOW the contract that `actorId` is dispatched under gets built. The
pre-existing R7 static param-scan test
(`coordination-r7-work-isolation.test.mjs:153`) already names
`dispatchDeclaredOperation` by function name, so it already structurally
covers this — no gap there. But nothing before this cell had exercised a REAL
specialist-dispatched Assignment and asserted its `mutation` field, so the
new behavioral test (`assignment.mutation === 'read-only'`, dispatched
through the real fixture in `coordination-specialist-binding.test.mjs`)
closes that specific evidentiary gap with an actual dispatched Assignment,
not just a structural argument.

The dynamic forbidden-export-name scan
(`coordination-r7-work-isolation.test.mjs:94`) already covers every new
P09.2 export automatically (it walks `src/runner/coordination/**` at test
time, not a hardcoded list) — zero changes needed there. What it did NOT
cover is `src/runner/definitions/**` (P09.1's own schema-only scope), since
the original Phase 06 R7 scan had no reason to look there before MVP9 added
binding-shaped surface to that directory. Extended with a sibling test,
matching the existing test's own pattern exactly (same
`listModuleFiles`/`extractExportedNames`/`FORBIDDEN_EXPORT_NAME_SUBSTRINGS`
helpers, reused not forked). One real false positive surfaced immediately
(`mergePolicyStack` — legitimate PolicyPatch scope-layer merging, unrelated
to git/Work "merge"), named and excluded explicitly with a one-line
allowlist and reasoning, not silently widened or narrowed away.

### Why the crash-recovery tests are shaped the way they are

P09.2's own Design Notes (confirmed by direct code read of
`recordSpecialistAuthorization`, `store.mjs:1066-1136`) establish that
`specialist-authorized` is written by exactly ONE `appendEventLocked` call
inside a SINGLE `withEventsLock` critical section — every check (session
active, driver identity, idempotency-on-`specialistAuthorizationId`,
`maxBindings` cap) runs inside that same lock, before the one append. There
is therefore no on-disk INTERMEDIATE state to construct a fixture for
between "authorized" and "bound" — they are the same write. This matches
current-cell.md's own framing exactly ("this cell's own authorization+binding
write is a SINGLE `appendEventLocked` call... the crash points to actually
test are: (a) before vs. after that one write commits... (b) between a
successful `specialist-authorized` write and the FIRST Assignment for that
specialist being created").

Given that, the two real, distinguishable crash points are caller-visible
retry scenarios, not internal on-disk half-states — matching
`coordination-recovery-and-quorum.test.mjs`'s own established house style
("construct the exact durable on-disk state a crash would leave, then prove
the SAME real call resumes cleanly," never a literal process kill), applied
here at the granularity this mechanism's actual atomicity allows:

- **(a)** The caller crashed and does not know whether its
  `authorizeSpecialistSlot` call durably committed. Retrying with the SAME
  `specialistAuthorizationId` must resume idempotently. This extends the
  pre-existing idempotency test (`coordination-specialist-binding.test.mjs:490`,
  which only asserted the event count) with the crash-point framing PLUS two
  additional assertions the original test did not make: the LIVE binding
  (`resolveLiveSpecialistBindings`) is unaffected by the retry, and a full
  end-to-end dispatch still succeeds normally afterward — proving genuine
  recovery, not merely "no duplicate event."
- **(b)** The caller crashed and does not know whether its dispatch request
  ever materialized an Assignment for the newly-bound specialist. Retrying
  the IDENTICAL dispatch request (same `operationId`/`targetActorId`, no
  explicit `taskKey`) must resume the SAME Assignment — proven via the
  existing, pre-P09.2 `createSessionAssignment` idempotent-taskKey-claim
  mechanism (`store.mjs`, unchanged by P09.2), which the specialist path
  reaches through the exact same `dispatchDeclaredOperation` ->
  `createAndExecuteSessionTask` -> `createSessionAssignment` chain every
  other dispatch path uses. The new test asserts `resumed: true`, the SAME
  `assignmentId`, and exactly one each of `specialist-authorized`/
  `operation-authorized`/`assignment-created` after the retry.

Both are real calls through the real engine doors against a real temp-dir
fixture — no mocked I/O, matching the repo's own established discipline for
this class of test.

  `a worker-typed identity (not merely a wrong driver id) cannot
  authorize a specialist into a slot`, mirroring
  `coordination-recheck-disposition.test.mjs:471`'s identical proof for
  the sibling `disposition` event kind. File now 22/22 (was 21/21).
- **[LOW/INFO, not fixed here, named honestly]** The static

  shaped like a forbidden verb would evade it), and even the whole-text

  dynamically-assembled name would evade it). Confirmed via grep: no such
  evasive construction exists in the current diff — theoretical, not
  exploited today. Red-Team confirmed this is a PRE-EXISTING methodology
  property of Phase 06's own original R7 scan pattern, faithfully
