## Finding 1 — Immutability claim does not hold for two of the four exported functions (P07.1)

**MEDIUM.**

`aggregation-evaluator.mjs` exports four functions: `validateSourceCoverage`, `validateRequiredDisclosureCoverage`, `evaluateAggregationCoverage`, and (from `schema.mjs`) the shape validators. The trace claims, unqualified: *"Result is immutable (never a mutable verdict a caller could accidentally alter and re-trust) ... reinforcing 'never rewrites evidence' at the API surface, not just in the module's own body."* The module header similarly states generally: *"it returns a validation result"* with no scoping to one function.

Empirically, only `evaluateAggregationCoverage`'s return value is frozen (`Object.freeze` at every level, verified: mutation attempts throw `TypeError: Cannot assign to read only property` / `Cannot add property, object is not extensible`). `validateSourceCoverage` and `validateRequiredDisclosureCoverage` — both exported, both directly unit-tested, both legitimate public API — return a **plain, unfrozen object** with a **mutable array** (`missingSourceOperationRefs`) and, in `validateSourceCoverage`'s case, a **mutable `Map`** (`bySourceOperationRef`).

Reproduced: pushed a fabricated entry into `missingSourceOperationRefs` (succeeded), overwrote `cov.ok` to `'CORRUPTED'` (succeeded), overwrote a `Map` entry (succeeded), and — most concretely — overwrote `disc.ok = true` on a `validateRequiredDisclosureCoverage` result that legitimately failed (`missingDisclosuresBySource` still shows the real missing disclosure underneath, but `.ok` now lies). All of this happens silently, no throw, because ES-module strict mode only prevents mutation of *frozen* objects — these two return values were simply never frozen.

**Failing scenario:** any future caller (most plausibly the P07.3 integration this skeleton is explicitly built for) that calls `validateSourceCoverage`/`validateRequiredDisclosureCoverage` directly instead of going through the combined entry point gets a verdict object it can mutate and then re-trust — exactly the failure mode "never rewrites evidence" / "never a mutable verdict" was meant to close off, just one call-path short of full coverage.

**Smallest-fix direction:** freeze the return values of `validateSourceCoverage` and `validateRequiredDisclosureCoverage` the same way `evaluateAggregationCoverage` already freezes its own combined output (same pattern, one `Object.freeze` per nesting level), or — if the two sub-functions are meant to be internal-only — stop exporting them and narrow the module header's immutability claim to name only the combined entry point.

Evidence: `/tmp/redteam/attack-team-cognition.mjs`, output transcript in this session.

### Verified the fix does not introduce a new input-mutation bug

`freezeSourceSnapshot` builds a snapshot via `{ ...source, disclosures:

frozen-in-place reference to the caller's object. Confirmed empirically
(escalation 3): mutating the caller's **original** `sources[]` object
after the call succeeds without throwing (`original.revision =
'mutable-by-owner'` succeeds, `Object.isFrozen(original)` is `false`), and
the returned snapshot's value stays at its old value regardless —
proving the two are decoupled copies, not the same object with only one
of them frozen. This matters because the alternative fix shape (freezing
the caller's own object in place) would itself have been a new violation
of "never mutates its own input" — the Fixer's trace named this trade-off
explicitly and chose correctly.

Also confirmed the two `Reflect`-based attempts I first logged as "NOT
BLOCKED" were a false alarm in my OWN test harness, not a real gap:
`Reflect.set`/`Reflect.deleteProperty` return `false` on a frozen target
instead of throwing (per spec, unlike plain assignment in strict-mode ESM,
which throws) — my first pass only checked for a thrown exception. Rerun
checking the actual resulting value
(`/tmp/redteam-recheck/attack3b-reflect-verify.mjs`) confirms no mutation
actually occurred in any of the three cases: `entry.revision` stayed
`'rev1'`, the `revision` key was not deleted, and `entry.disclosures.d1`
stayed `'v1'`. `Object.defineProperty` against the frozen object also
throws (`Cannot redefine property`), as expected. Logged here so the
record does not overstate a bypass that isn't real.

### New residual gap — one level short: disclosure VALUES that are themselves objects/arrays are only shallow-frozen

`freezeSourceSnapshot`'s `Object.freeze({ ...source.disclosures })` freezes
the `disclosures` object's own keys (blocks adding/removing/reassigning a
disclosure id), but does not deep-freeze a disclosure's **value** when
that value is itself an object or array. Reproduced
(`/tmp/redteam-recheck/attack3-fixround2.mjs`, "ESCALATION 1"):

```
entry.disclosures = { d1: 'v1', nested: { level: 'deep', arr: [1,2,3] } }
entry.disclosures.nested.level = 'TAMPERED-NESTED'  -> succeeds, no throw
entry.disclosures.nested.level after attempt = TAMPERED-NESTED
entry.disclosures.nested.arr.push(999)              -> succeeds, no throw
entry.disclosures.nested.arr after attempt = [1, 2, 3, 999]
```

Both mutations land on the snapshot object itself (not merely the
caller's original — confirmed the caller's `original.disclosures.nested`
reference is the SAME object the snapshot's shallow copy points at, since
`{ ...source.disclosures }` only copies the `disclosures` object's own
top-level keys, not the values recursively — so this also reaches back
into the caller's original object, the same class of leak as the
already-fixed `revision` case, just one level further down for this one
field shape).

**Why this is lower severity than the original finding, not a repeat of
the same MEDIUM:** `schema.mjs`'s `validateAggregationSource` only checks
`isPlainObject(source.disclosures)` — it never constrains what a
disclosure's individual *value* looks like, and `P07.1.md`'s own Gaps
section already documents this as open, undefined territory ("disclosures
values are checked for presence... not for their own shape/type per
disclosure id... left open... a later cell that defines disclosure
semantics owns that shape"). Every disclosure value exercised by this
cell's own fixtures and tests today is a primitive (a string like
`'high'`), so this gap has no live trigger in shipped code or tests — it
only bites a future disclosure value that happens to be non-primitive,
a shape this cell explicitly declines to define yet.

**Smallest-fix direction (for whichever cell eventually defines disclosure
value shape):** either recursively deep-freeze each disclosure value in
`freezeSourceSnapshot` (a small `deepFreeze` helper, same idea already
used in this repo's own test file for a different purpose at
`team-cognition-aggregation-evaluator.test.mjs:203-207`), or document
explicitly that only string-shaped disclosure values are covered by this
snapshot's immutability guarantee until a later cell locks the value
shape down.
