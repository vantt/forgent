Reviewer: independent Red-Team (no prior context, did not see any Reviewer findings)
Diff under attack: `9b81427c..20a3b604` | Date: 2026-09-04
Verdict: **APPROVE WITH CONCERNS**

**Headline first: the recurring bug class did NOT recur.** The attack this track
shipped three times — a session-integration function taking a
FlowDefinition/config from its caller for a legality decision —
is genuinely absent. `linkSessionContribution` has no `definition`, no
`visibilityWindowRef`, no `operationRef`, no `revision`, and no
`declaredOperations` parameter; every one is derived from `manifest.definitionRef`
or from the session's own log, and a static signature test locks it. I tried to
find a caller-supplied path into the window decision and there is none.

What I did find: **six issues, three of them MEDIUM**, none HIGH. Two of the
three MEDIUMs are about the *window legality* property this cell's Acceptance
rests on — not about how the definition is resolved, but about *when* and
*against what content* the window verdict is computed. The third is a
replay-hardening asymmetry the cell introduced by making an
already-weakly-checked event kind newly load-bearing for derived state.

All PoCs below were run against this worktree at `20a3b604`. Scratch scripts in
`/tmp/rt-p082/`.

## Attack 1 — The new `contribution:` ownership check, directly

### 1a. Contribution-shaped `targetRef` WITHOUT the reserved prefix — **HELD (fail-safe)**

The menu's sharpest question. A bare `contrib_1` still sails through
`assertDispositionRefOwnedBySession` unchecked, exactly as it did before this
cell — the Doer says so explicitly and it is true. But it buys nothing:
`replay.mjs:348` only harvests `resolvedContributionIds` from refs that
`startsWith(CONTRIBUTION_REF_PREFIX)`, so an unprefixed ref resolves **nothing**.
The bypass direction is toward "stays open", never toward "wrongly resolved".
Write door and replay agree on the same exact-prefix test, so there is no
shape one recognizes and the other does not.

Variants tried, all fail-safe for the same reason: `Contribution:contrib_1`
(case), `/contribution:contrib_1` (leading slash), `" contribution:contrib_1"`
(leading space). Each falls to the opaque-segment path at the write door and is
ignored by replay's harvest.

### 1b. Mixed prefix with a foreign contribution id embedded — **HELD**

`contribution:<other-session-id>/asgn_x`, `contribution:../../other-session/x`,
and `contribution:` + a contribution id belonging to a second real session in
the same workspace are all refused: the check is exact set membership
(`contributionIds.has(suffix)`) against ids harvested from *this* session's own
lock-held `readEvents`, not a segment scan. The early `return` that skips the
directory/`asgn_` scan is safe precisely because membership is exact.

The fail-closed default (`contributionIds = new Set()`) is correct and load-bearing:
`recordContributionLink` calls the same helper for `artifactRef` without passing
a set, so a `contribution:`-prefixed `artifactRef` is refused rather than skipped.

### 1c. `contributionId` has no shape constraint at all — **BROKE (LOW)**

`contributionId` is validated only as a non-empty string, at both doors. So this
is accepted end to end and both the write door and `show.mjs`'s mirror report it
as **owned by this session**:

```
contributionId = '../../../../etc/passwd'
targetRef      = 'contribution:../../../../etc/passwd'   -> accepted, resolves the contribution
```

PoC output (`/tmp/rt-p082/poc2.mjs`):
```
C path-shaped contributionId accepted: true | resolved: ["../../../../etc/passwd"]
C2 prefix-shaped contributionId accepted: true    (contributionId = 'contribution:ghost')
```

**Not exploitable today** — I grepped every consumer of `contributionId` /
`targetRef` outside `src/runner/coordination/` and `src/runner/deliberation/`
and found no path-join sink; the value is only ever compared and rendered. But
it is a deviation from this codebase's own R6 discipline, which gave `runId` a
full-shape check (`assertValidRunIdForAssignment`, applied in this very
function two lines earlier) for exactly this reason, and it lets a caller mint
a ref whose *text* claims cross-session reach while the ownership check calls it
local. Severity **LOW** (latent).

**Smallest fix:** an id-shape assertion on `contributionId` at
`recordContributionLink` — at minimum "no `/`, no `\`, no `..`, does not itself
start with `contribution:`". The Doer's stated reason for adding no constraint
("P08.1 leaves contribution ids free") justifies leaving the *namespace* free,
not leaving path separators and the reserved prefix legal inside it.

## Attack 2 — `linkSessionContribution`'s definition resolution

### 2a. Caller-supplied definition/window/operation — **HELD, and this is the cell's strongest result**

There is no parameter to attack. Verified by reading the signature
(`session-engine.mjs:3325-3329` destructures only
`{contributionId, type, assignmentId, roundKey, linkedBy, anchors, respondsTo}`),
the version-drift refusal at `:3345`, the binding-derived window at `:3384`, the
stamp-derived operation at `:3365`, and the definition-derived
`declaredOperations` at `:3434`. The cell's own static signature test asserts it
rather than resting on inspection. This is the right shape.

### 2b. Same-`{id, version}` definition CONTENT swap defeats the window gate entirely — **BROKE (MEDIUM)**

The definition is pinned by `{id, version}` and never by content. The Doer
discloses this verbatim as inherited P07.3 parity. The mechanism is indeed
inherited; **the consequence here is materially worse than P07.3's and the trace
does not say so.**

PoC (`/tmp/rt-p082/poc3.mjs`): a real dispatched session, honest protocol, only
`researcher-a` settled so window `post-research` is genuinely closed. Then the
protocol document on disk is rewritten in place — `metadata.id` and
`metadata.version` byte-identical — with the window's own
`opensAfter.operationRefs` repointed at an operation that has already settled:

```
baseline (honest definition): REFUSED, window closed — correct
after same-version content swap: BROKEN — linked with visibilityWindowRef = post-research
   replay accepts it: true
```

The version-drift check passes (same version), `deriveVisibilityWindowState`
faithfully evaluates the *swapped* window rule, and the resulting immutable
ledger record asserts `visibilityWindowRef: "post-research"` — a window
provenance claim that was false when written and that replay, being
definition-blind, can never re-check. In P07.3 the same swap changed which
evidence a verdict was derived over; here it deletes the entire MVP6
window/context legality property that is this cell's named Acceptance criterion,
and launders the result into a permanent record.

Severity **MEDIUM**: disclosed mechanism, undisclosed escalation of consequence,
requires `.fgos/coordination-protocols/` (or `opts.packageRoot`) write access —
the same capability the already-named raw-store-door residual needs.

**Smallest fix direction (not for this cell):** pin `manifest.definitionRef` by
content hash alongside `{id, version}`, once, for all five
definition-consuming doors. Short of that, the trace's parity caveat should say
plainly that for THIS door the swap does not degrade a verdict — it removes the
gate.

## Attack 3 — Content-freedom

### 3a. Named content/mailbox fields — **HELD**

The payload whitelist makes `body`/`content`/`text`/`recipient`/`delivery`/
`unread`/`status`/`resolved`/`sessionId` unrepresentable, and the runtime test
greps the raw `events.jsonl` for the report prose. Confirmed independently.

### 3b. `roundKey` is an unbounded verbatim string channel into the immutable ledger — **BROKE (LOW-MEDIUM)**

`roundKey` is a required field validated only by `isNonEmptyString`. It is
caller-supplied at the *mediated* door (`linkSessionContribution` passes it
straight through), persisted verbatim, and projected back onto the replay
record. `contributionId` is the same.

PoC (`/tmp/rt-p082/poc2.mjs`):
```
D artifact prose inside the event log via roundKey: BROKEN (content persisted verbatim)
   projected back onto the replay record: true
```

The Doer's defense — "roundKey is on the same footing as `reason`/`rationale`
elsewhere in this file" — is the part I'd push back on, because **the file does
not actually treat free text that way**. `recordConsultDisposition`, the sibling
mediated door in the same module, caps its free text:

```js
// session-engine.mjs:2172
const DISPOSITION_RATIONALE_MAX_LENGTH = 2000;
```

So the established precedent one function away is "the mediated door bounds
caller free text"; the new mediated door bounds nothing. The Bug Taxonomy entry
"stores artifact CONTENT instead of a ref+revision pin" is therefore closed
against *field names*, which the tests prove, and open against *field volume*,
which nothing checks. A driver wanting the artifact body in the ledger does not
need a `content` field; it needs a long `roundKey`.

Severity **LOW-MEDIUM** (requires driver identity; no confidentiality boundary
crossed; but it defeats the stated discipline and there is a two-line precedent
for the fix).

**Smallest fix:** apply a `DISPOSITION_RATIONALE_MAX_LENGTH`-style bound to
`roundKey` (and `contributionId`) in `linkSessionContribution`.

## Attack 4 — Window/context legality reuse

### 4a. Is `deriveVisibilityWindowState` called correctly, with fresh state? — **HELD**

`deriveVisibilityWindowState(definition, visibilityWindowRef, replayed, fgosDir)`
at `session-engine.mjs:3391` receives: the manifest-resolved definition, the
binding-derived window id, and a **fresh** `replaySession()` taken in this call
(`:3353`) rather than a state handed in or cached. Correct arguments, correct
order, no reimplementation. I could not construct a stale-state variant.

### 4b. TOCTOU (window closes between derivation and append)? — **HELD, structurally**

The window verdict is computed outside the lock and the append happens inside
it. Not exploitable: `open = sources.every((s) => s.satisfied)`
(`session-engine.mjs:1306`) and `resolveBindingOutcome`'s satisfied state is
sticky ("a satisfied attempt settles the binding"). Windows are monotone
closed→open, so no interleaving can flip `open` to false after the check.

### 4c. The window is checked at LINK time, not at REASONING time — **BROKE (MEDIUM)**

This one is proven by the Doer's own green test, no PoC needed. Read the
sequence in `runtime: a contribution is linked only once its binding's
visibility window is open…`:

1. `research`/`researcher-a` dispatched and settles.
2. `deliberate`/`coordinator-actor` **dispatched, executed, and settled here** —
   window `post-research` is CLOSED, and the dispatch gate does not fire because
   the binding is `activation.mode: required` (the pre-existing MVP6 residual
   the Doer correctly identifies).
3. Link refused. Correct.
4. `research`/`researcher-b` settles → window opens.
5. **The same link now succeeds**, pinning the artifact produced at step 2.

The `deliberate` Run never re-ran. Its reasoning demonstrably could not have
seen `researcher-b`'s output, because that output did not exist yet. Yet the
ledger now carries an immutable record asserting
`visibilityWindowRef: "post-research"`, and the event's own doc comment reads
"a contribution records the window its reasoning was legal under"
(`session-engine.mjs:3388`). It records no such thing. It records the window
that was open when the driver got around to writing the link.

This is the **combination the attack menu asked about** (item 6): the MVP6
`required`-binding dispatch residual plus this cell's new code is strictly worse
than the residual alone. Before this cell, an ungated `required` dispatch was an
unrecorded hole. After it, the same hole produces a durable, replay-accepted
record that *affirmatively claims* window legality. The Doer argues the residual
"raises rather than lowers" the link-time check's value; that is true of the
check's usefulness and untrue of the record's honesty.

A related scope observation, stated once rather than scored separately: the cell
contract's requirement reads "Enforce MVP6 window/context legality **when a
later Assignment receives a contribution artifact**." This cell gates *writing
the link*, not *receiving the artifact*; there is no delivery path here at all
(the Doer's own "No CLI/`show` surface" gap). The receiving half of that
sentence is unimplemented, which is defensible as P08.3 scope but should not be
read as satisfied.

Severity **MEDIUM**.

**Smallest fix direction:** at link time, additionally require that the backing
Assignment's `result-linked` event appear **at or after** the log position where
the window's `opensAfter` sources all became satisfied — i.e. compare event
`seq`, which replay already has. That turns "the window is open now" into "the
reasoning was produced under an open window", which is what the field claims.

## Attack 5 — The "no mutable status" claim

### 5a. No stored status field; derivation is real — **HELD**

Grep-confirmed: no `status`/`resolved` key on any contribution record;
`openContributionIds`/`resolvedContributionIds` are computed after the walk; the
whitelist makes such a field unrepresentable. The append-only assertion in the
test (byte-prefix stability across the disposition) is a good check and it holds.

### 5b. Forging open→resolved: through the mediated/store door — **HELD**

`recordDriverDisposition` pins `authorizedBy.id` to
`manifest.provenanceRoot.writerId` via `assertDriverIdentity` and resolves the
`contribution:` ref against a lock-held read. I could not get a resolution
through it without being the session driver and naming a real contribution.

### 5c. Forging open→resolved on the log: **replay never checks the resolving disposition's driver identity** — **BROKE (MEDIUM)**

This is my primary finding. `replay.mjs`'s new contribution branch correctly
refuses a foreign linker:

```js
// replay.mjs:~291
if (linkedBy.id !== manifest.provenanceRoot.writerId) { throw ... }
```

Six lines below, the branch that **flips a contribution from open to resolved**
performs no equivalent check:

```js
// replay.mjs:348
if (!terminalSeen && event.payload.targetRef.startsWith(CONTRIBUTION_REF_PREFIX)) {
  resolvedContributionIds.add(event.payload.targetRef.slice(CONTRIBUTION_REF_PREFIX.length));
}
```

`validateEventPayload` only requires `authorizedBy.type === 'driver'` and a
non-empty `id` — it is shape-only by design, and says so. The session-scoped
identity question is answered at the write door and, for
`aggregation-validated` and `deliberation-contribution-linked`, independently at
replay. For `driver-disposition-recorded` it is answered **only** at the write
door.

PoC (`/tmp/rt-p082/poc1.mjs`) — one raw-appended event, `authorizedBy.id` set to
a worker identity:

```
before: {"open":["contrib_1"],"resolved":[]}
after : {"open":[],"resolved":["contrib_1"]}
RESULT: BROKEN -- a foreign-identity disposition flipped open->resolved at replay
```

Why this matters more than "it's just the raw-append boundary": the trace's own
claim at `replay.mjs:118-119` is *"no write path exists that could flip it"*,
and `schema.mjs`'s new comment says *"a hand-written log is exactly what replay
exists to refuse."* Against that stated threat model — the one this cell adopts
for its own event, and for which it wrote three replay refusals — the derived
state it introduces is unguarded. The asymmetry is the finding: the cell
hardened replay for the event it added and not for the event it made
load-bearing.

Severity **MEDIUM** (requires `.fgos` write access, same as the disclosed
raw-store-door class; but unlike that class this one is a one-line omission
against a check the same function already performs twice).

**Smallest fix:** in the `driver-disposition-recorded` branch, refuse when
`event.payload.authorizedBy.id !== manifest.provenanceRoot.writerId`, or at
minimum skip the `resolvedContributionIds.add` for such an event. Copy the
contribution branch's own check verbatim.

### 5d. A disposition that PRECEDES the contribution still resolves it — **BROKE (LOW)**

`resolvedContributionIds` is accumulated during the walk with no ordering
constraint, then intersected with `contributions` at the end. The same branch
applies a strict out-of-order refusal to the contribution's own backing
assignment (`linkedCountByAssignment` must be non-zero *before* the link) but
none to the disposition→contribution edge.

PoC (`/tmp/rt-p082/poc2.mjs`), disposition at seq 4, link at seq 5:
```
B ordering: BROKEN -- resolved by a disposition that came BEFORE the link existed
```

Unreachable through the write doors (which refuse a `contribution:` ref for an
unlinked id), so hand-written-log only — same class as 5c, smaller consequence.
**Smallest fix:** move the `resolvedContributionIds.add` behind a
`contributionIds.has(...)` guard, so a disposition can only resolve something
already walked.

### 5e. Any disposition string resolves — **INFO**

`DISPOSITION_VALUES = {accepted, rejected, partially-accepted}` is enforced only
in the mediated `recordConsultDisposition` (`session-engine.mjs:2228`), not in
the raw `recordDriverDisposition` door nor in the event schema. So on the raw
path a `disposition: "deferred"` (or any string) marks a contribution resolved.
Even on the honest path, `rejected` and `partially-accepted` both count as
resolved — a defensible modeling choice, but it is a choice the trace does not
state, and "partially-accepted closes the contribution" is the one I would want
written down before P08.3 builds round semantics on it.

Scored under Attack 4c rather than duplicated here.

`knownStampedAssignments` and `operationRef` are derived from the same stamp, so
`validateAssignmentProvenance` cannot fire. The Doer names this and correctly
declines to claim the channel as proof. Verified, no finding.

#### NEW-1 (MEDIUM, new) — item 4's property is bypassable through `retrySessionTask`'s documented crash self-heal

Reachable through mediated doors only. No hand-written log, no raw
`appendEvent`, no `.fgos` forgery beyond writing a run result the executor

`retrySessionTask` (`session-engine.mjs:3616-3623`) self-heals the documented
crash window — executor settled on disk, process died before `linkResult` — by
calling `linkResult({allowSupersede: true})` **later**. That appends a
`result-linked` at a NEW, high `seq` for a Run that executed long before.

1. `research`/`researcher-a` settles. Window `post-research` CLOSED.
2. `deliberate` dispatches and settles — reasoning produced under the CLOSED

4. `research`/`researcher-b` settles (seq 11). Window OPENS.

**Fix direction (smallest correct one).** Compare against when the Run *started*,
not when its result was *linked*. The log already carries that lower bound: a
first Run is bounded below by its `assignment-created`, a retry Run by the
`run-retried` event that authorized it. Requiring that position to be at or

#### NEW-2 (LOW-MEDIUM, new) — a legitimate link is refused, with a factually wrong error, after any retry of a window SOURCE

The mirror image of NEW-1, and reachable through the ordinary mediated retry
path with no crash at all.

`visibilityWindowOpenedAtSeq` uses `lastEventFor(events, 'result-linked', ...)`
per source branch. Retrying an already-satisfied window source appends a second
`result-linked` for it, moving the computed "opened at" position **forward**,
even though Red-Team 4b established that windows are monotone closed→open and
never re-close. Reproduced:

```
before retry: link ACCEPTED   (window opened seq 8, deliberate settled seq 10)
after  retrySessionTask on the window source researcher-a (new result-linked at seq 13):
  REFUSED -- assignment "...op_003" settled at log position 10, before visibility window
             "post-research" opened at log position 13
```

The deliberate Run genuinely did reason under an open window, and the message
asserts the window opened at 13, which is false — it opened at 8 and stayed
open. This is fail-closed (a liveness/UX defect, not a soundness hole), but the
error text will send a driver to "re-run the operation under the open window"
for a Run that already was.

Note the Fix Round's own justification is correct about the *backing* Assignment
("deliberately uses the LAST `result-linked` ... so a legitimate re-run after
the window opened links normally") but is silent about the **source** side,
where LAST is the wrong choice. The doc claim at `session-engine.mjs:3267-3272`
("the log `seq` at which `windowState`'s LAST source became satisfied") does not
hold once any source has been re-linked.

**Fix direction:** for each source branch, take the EARLIEST `result-linked`
whose run classified as satisfied, not the latest. Satisfaction is sticky
(`resolveBindingOutcome`), so the earliest satisfying event is when the branch —
and therefore the window — actually opened. `lastEventFor` remains correct for
the failed-then-retried direction only, which the earliest-satisfying rule also
handles.
