## 3. Design Notes

### The schema field: local enum, not an import

`contributions.allowedTypes[]` lands on `spec.operations[]` in
`src/runner/definitions/schema.mjs`, whitelisted via a new
`OPERATION_CONTRIBUTIONS_FIELDS = new Set(['allowedTypes'])` and a new local
`CONTRIBUTION_TYPE_VALUES` frozen array duplicating
`../deliberation/schema.mjs`'s `CONTRIBUTION_TYPES` enum values verbatim,
rather than importing them. This follows the file's own established
precedent: `AGGREGATION_METHOD_VALUES` is a local copy, not an import from
`team-cognition/schema.mjs`, for the reason the file's own header states —
`definitions/schema.mjs` is a zero-dependency pure kernel ("this module does
not import from coordination/schema.mjs, and coordination/schema.mjs does
not import this one either"). Importing `CONTRIBUTION_TYPES` would have been
the more DRY choice but would have broken that stated zero-import discipline
for the first time; duplication was the judgment call, matching the file's
own prior answer to the identical question for aggregation.

An empty `allowedTypes: []` is accepted as legal, not rejected as
degenerate — unlike `completion.aggregation.sourceOperationRefs` (required
non-empty elsewhere in this same file), an empty and an absent
`contributions` key are meant to converge on the SAME runtime meaning
("declares no allowed types"), so the schema must accept the shape the Bug
Taxonomy explicitly requires testing.

### Closing the vacuous gate: one line, real consequences

P08.2's Gaps named the fix precisely: replace
`Object.fromEntries(definition.spec.operations.map((operation) => [operation.id, { allowedTypes: [...CONTRIBUTION_TYPES] }]))`
with a real per-operation read. The actual change
(`session-engine.mjs`, `linkSessionContribution`'s `declaredOperations`
synthesis):

```js
const declaredOperations = Object.fromEntries(
  definition.spec.operations.map((operation) => [
    operation.id,
    { allowedTypes: operation.contributions?.allowedTypes ? [...operation.contributions.allowedTypes] : [] },
  ]),
);
```

Both "no `contributions` key" and "`allowedTypes: []`" produce the identical
representation (`{ allowedTypes: [] }`), which
`validateOperationDeclaresType` (P08.1's own module) already treats as
reject-everything — no change needed there, confirming P08.2's own claim
that "the wiring is already in place and pointed at the right place."

This line's real consequence is larger than the diff: it retroactively
narrows every EXISTING contribution-linking runtime test that never declared
the field. `coordination-deliberation-ledger.test.mjs`'s own `protocolDoc()`
fixture (P08.2's) declared `deliberate` with no `contributions` key and
linked `proposal`/`objection` contributions through it in several tests —
all of which started failing the moment this line changed, for the EXACT
reason the vacuous-gate regression exists to catch. The fix was to give the
fixture the real declaration it always should have had
(`contributions: { allowedTypes: ['proposal', 'objection'] }`) rather than
loosen the new check — the fixture was built against a stub this cell was
explicitly assigned to remove, and the file's own 31 tests are green again
with the honest declaration in place. No other line in that file changed.

The `CONTRIBUTION_TYPES` import in `session-engine.mjs` (previously used only
by the removed vacuous spread) was dropped as dead.

### Fixture design: three real, committed, opt-in protocols

Modeled on the P06.3 precedent
(`independent-research-fan-out-fan-in-gated.yaml`): a separate file per
concept, `topology.edges[]` omitted (this track's own simpler
`coordination-deliberation-ledger.test.mjs` precedent — an operation bound
to more than one actor at one graph node needs no declared edge, and I
dispatch every binding with an explicit, actor-scoped `taskKey` rather than
relying on the edge-derived default), and every contribution-bearing
operation binds to a real `contextAccess.visibilityWindowRef` (required —
`linkSessionContribution` refuses to link through an ungated binding at
all).

**A real, load-bearing correctness finding, not a design preference: a
contribution can never be gated by a window that opens only after that SAME
operation's own cohort settles.** My first draft of the Nominal-Group and
Delphi fixtures used exactly that self-referential shape (private-propose's
own binding required the `reveal` window, which opened after
private-propose's own cohort settled) on the theory that Run SETTLEMENT and
CONTRIBUTION LINKING are independent events (true, and P08.2's own design
note). It is structurally impossible under P08.2 Fix Round 2's actual check:
`linkSessionContribution` compares `runAuthorizedAtSeq` (the Run's
AUTHORIZATION/dispatch position) against `windowOpenedAtSeq`, and an
operation's own authorization always precedes the settlement a
self-referential window would need to wait for — so the comparison
`runAuthorizedSeq <= windowOpenedAtSeq` is true, and the link is refused,
100% of the time, for every self-gated operation. I found this empirically
(all three fixtures' first drafts failed their own runtime tests with the
EXACT Fix-Round-4 refusal message), traced it to the real cause by reading
`runAuthorizedAtSeq`/`visibilityWindowOpenedAtSeq` rather than assuming a
test-fixture bug, and redesigned rather than working around it:

- `deliberation-rfc-chain.yaml` was never affected — `rfc-open` opens after
  a genuinely earlier, different operation (`convene`), so `propose`/
  `object`/`respond`'s authorizations correctly follow it.
- `deliberation-nominal-group-chain.yaml`: `private-propose` now binds to a
  vacuously-open window (`private-open`, `opensAfter.operationRefs: []` —
  the schema's own documented degenerate "open from session start" case),
  so each participant's own private reasoning is always free to record.
  `reveal` (the real gate, opens after BOTH `private-propose` settle) now
  governs `clarify` and `private-rank` — genuinely different, later
  operations, so the reasoning-time check holds honestly.
- `deliberation-delphi-chain.yaml`: `propose-round1` now binds to
  `round1-open` (vacuous, same reasoning). `round2-open` (real, opens after
  `aggregate`) was ALREADY correctly non-self-referential and needed no
  change — it gates `propose-round2`, a different operation from
  `propose-round1`.

### The Nominal-Group privacy proof takes the Bug Taxonomy's OR-clause, deliberately

Bug Taxonomy: "a proposal contribution linked before the reveal window opens
must be rejected **or provably not visible to other participants' context**"
(emphasis mine). Given the structural finding above, the FIRST branch
(rejecting the proposal's OWN link) is impossible by construction for any
protocol that wants private-then-revealed semantics — so this cell takes the
second, and proves it with the SAME MVP6 mechanism the phase's own Exit
bullet calls for, never a new one: `clarify` is made `driver-authorized`
(the only activation mode the window/context-grant gate enforces at dispatch
time, per the FlowDefinition contract's own documented limitation), and the
test shows `authorizeDeclaredOperation` refuses to grant the facilitator
read access to EITHER private proposal while only one participant has
settled, then succeeds once both have. This is not a weaker proof than the
literal first branch — it demonstrates the actual product property
("provably not visible to other participants' context") more directly than
a link-time refusal would have, since a link-time refusal only proves the
PROPOSER's own record can't enter the ledger yet, not that anyone else is
blocked from reading it.

### RFC and Delphi lineage shape

RFC anchors the objection to the proposal (`anchors: [proposalId]`) and has
the response answer the objection (`respondsTo: objectionId`), then a driver
disposition resolves the response via the `contribution:` ref namespace
P08.2 added. Delphi anchors each round-2 proposal to BOTH round-1 proposals
(`anchors: [round1A, round1B]`), modeling "next-round proposal" building on
the mediated aggregate without the aggregate itself being a contribution —
none of the six closed MVP8 types names "aggregate", and this cell does not
invent a seventh; `aggregate` is a plain declared operation whose settling
opens `round2-open`.

### `dispatch()`'s actor-scoped `taskKey`, and why the assignment lookup drops the operationId filter

Every dispatch in the new test file passes an explicit, actor-scoped
`taskKey` (`declared:<operationId>:<targetActorId>`): the default derivation
(`declared:<operationId>`, no actor discriminator for a `required` binding
with no incoming edge) would collide across the two actors bound to the same
operation at one node — `dispatchDeclaredOperation`'s own comment names this
exact hazard. The assignment lookup after dispatch (`dispatch()`'s
`replayed.assignments.find(...)`) filters by `actorId` alone, matching
`coordination-deliberation-ledger.test.mjs`'s own precedent: a `required`
binding's `assignment-created` event carries no `operationId` field at all
(that field is `driver-authorized`-only, per the CoordinationSession
contract's own Event Log row), so filtering on it silently matched nothing
in my first draft. Correct because every call site reads back the
just-created assignment immediately, before any later dispatch for the same
actor.
