## The headline finding: a real credential-leak regression (HIGH), caught and fixed

Red-team's retry (op_095) discovered that the initial migration's new
`prepareBwrap` logic in `src/runner/dispatch/confinement/drivers/bwrap.mjs`
copied the host's OpenAI Codex credential file into **every** `private-home`
sandbox resource, keyed only on the resource *type*, never on which executor
was actually being confined. Because the new `host-write-denied` policy grants
`private-home:read-write` broadly to `advise`/`code:review`/`code:debug`
capabilities, this meant `claude-bwrap` and `agy-bwrap` (Claude and Gemini
agents with no relationship to Codex) also received a copy of the Codex
credential inside their own sandbox on every dispatch — a credential they
never had access to under the OLD hardcoded argv, which mounted that specific
credential file only into `codex-bwrap`.

Red-team proved this live and structurally (no raw secret value reproduced
here, per this session's own credential-handling policy): the copied file
inside `claude-bwrap`'s sandbox was byte-identical to the real host
credential, discoverable from inside the sandbox via `/proc/self/mountinfo`
and a filesystem search, readable, and — since network egress defaulted to
open — exfiltratable to an external address in a live test. A full
read-plus-exfiltrate chain, default-on, on this operator's own machine, the
moment the migration landed.

This is exactly the class of finding this entire track's reviewer/red-team
discipline exists to catch, and it worked as intended — it just took a
second red-team attempt (after the first `codex-herdr` attempt died with zero
output, unrelated to the finding itself) to surface it.

**Fix** (fixer, commit `569f72d3`): the credential copy is now gated on an
explicit `executorId` allowlist scoped to `codex-bwrap` only (not just the
resource type), matching the file's own "never branch on provider, resolve a
real resource" architectural principle by making the credential a properly
scoped resolved input rather than a blanket copy. A new regression test
asserts `claude-bwrap`/`agy-bwrap`'s own prepared `private-home` never
contains a Codex credential, while `codex-bwrap`'s own `private-home` does —
and the fixer proved the test itself was non-vacuous by temporarily reverting
the gate and confirming the test then fails.

**Independent re-verification (twice)**:
- Reviewer (op_097): dispatched a real `claude-bwrap` task and confirmed its
  `private-home` contained no credential file, no Codex environment variable,
  and no Codex bind in the prepared bwrap invocation — while a real
  `codex-bwrap` dispatch still correctly received its own credential,
  authenticated, and ran successfully (no functional regression).
- Red-team recheck (op_098, fresh coordinationId after the original session's
  wall-time budget expired): independently re-ran the same exploit chain
  against the fixed commit and confirmed it now fails for `claude-bwrap`,
  `agy-bwrap`, and any other non-`codex-bwrap` executor id, while
  `codex-bwrap` itself remains fully functional. Explicit final verdict:
  **"Safe to merge."**

**Post-fix hygiene**: three leftover temporary directories from *before* the
fix (created during earlier live-falsification probes) still held real
byte-for-byte copies of the leaked credential on disk under
`/tmp/fgos-confinement/`. The Lead deleted these three directories directly

## M-1 disposition

The undocumented `FGOS_DISPATCH_NO_LOCK` environment variable (added so the
Doer's own nested live-falsification sub-dispatches could run under a
coordinator already holding the main-checkout dispatch lock) was **removed
entirely** rather than documented — the fixer judged it was only a testing
convenience, not a genuine production need, and `executeExecutorCli` now
unconditionally acquires the lock again. Confirmed zero references remain
across `src`/`test`/`docs`/`.fgos`.

## Structural finding: a pane-management mistake, and its lesson

Mid-cell, the Lead closed herdr pane `wS:p2BN` believing it was a *finished*
reviewer pane, based solely on its terminal title text ("Implement
confinement authority") — it was actually the *still-running* red-team pane
for op_094. This is very likely what turned op_094 into a genuine
zero-output timeout (the herdr-spawn adapter's own harvest mechanism —
typing an exit command, reading a completion sentinel, then auto-closing the
pane itself — depends on the pane staying open until it decides to close it).

**Lesson for every future Lead in this track**: never infer an assignment's
completion from a pane's title text alone. Always read that specific
assignment's own `run.json` file directly first and confirm its `status` is
not `"running"` before closing any pane, with no exceptions — regardless of
how obvious the title looks. This is now a standing, absolute rule for pane
management in this track, distinct from (and stricter than) the general
"only close panes you created yourself" scoping already established in P00.
