## The R1 decision: `runner.confinement.strict` stays `false`

The Doer (op_083, `agy-herdr`, commit `fbff7630`) decided to KEEP strict mode
false, not flip it. Both reviewer and red-team independently re-derived and
confirmed this decision is correct, though red-team caught that one of its two
stated justifications was reasoned backwards (see HIGH-3 below):

- **Justification #1 (holds):** only 3 of 7 canonical capability slots ship with
  an explicit confinement policy by default (`DEFAULT_CAPABILITY_SLOTS` in
  `src/setup/registrations.mjs`); on a clean install, enabling strict today would
  make `config.mjs`'s load-time check throw immediately. Live-verified by all
  three roles (Doer, reviewer op_090, red-team op_091) by constructing a copy of
  the real config with `strict:true` and confirming it throws.
- **Justification #2 (corrected mid-cell):** originally stated as "P04's M-3
  anchor-inheritance overclaim is a reason to keep strict disabled" — red-team's
  live probe proved this backwards. `strict` has **zero runtime effect** anywhere
  in `src/runner/dispatch/confinement/**`, `cli.mjs`, or `resolve.mjs` — its only
  effect is the load-time throw in justification #1. Since that throw requires
  every capability to have its OWN explicit confinement, it would make
  `request.mjs`'s anchor-inheritance branch (where M-3 lives) **unreachable** for
  any capability strict mode would actually allow to load. M-3 is therefore an
  argument **for** eventually enabling strict, not against it. The DECISION was
  not changed — justification #1 alone is sufficient — only the flawed reasoning
  in #2 was corrected.
