### Primary scrutiny target — the "## Split" heading narrowing: HIGH finding

**The general design principle is correct; the specific regex implementing
it is not.** Verdict on the four numbered sub-questions:

1. **Does `split-and-child-specs.md` establish "## Split" as a documented
   heading convention?** No. Read
   `domains/coding/skills/fgos-coding-planning/references/split-and-child-specs.md`
   directly — it says only "If one piece is honestly enough, there is no
   split, and the item proceeds as itself. Say so plainly in `plan.md`;
   `fgos-coding-validating` reads that as its pass-through verdict." There is
   **no heading name, no "##" prefix, no "Split" keyword requirement**
   anywhere in that doc. The literal "## Split" family heading is the Doer's
   own invention, not a cited repo convention — the code comment's framing
   ("confirmed against real examples in this repo's own history") overstates
   what the reference doc itself says (the reference doc says nothing about
   headings at all).

2. **Is there a real, currently-active regression risk, or purely
   theoretical?** Real, not theoretical. I surveyed all 606
   `docs/history/*/plan.md` files for level-2 headings mentioning "split"
   (case-insensitive):
   - `^## Split` (Doer's regex) matches 195/606 files.
   - `## No split` — 32 files, **zero overlap** with the "## Split"-matching
     set — the regex's own `^##[ \t]+Split\b` requires "Split" as the
     heading's first word, so "## No split" fails to match
     (`SPLIT_HEADING_PATTERN.test("## No split\n...")` → `false`, verified
     by running the actual regex from
     `src/intake/plan-verdict-from-plan-md.mjs`).
   - `## Decide the split` — 19 more files, also zero overlap, also
     unmatched (`false`, same check).
   - Also present in the corpus but unmatched: `## Shape: no split`,
     `## Không split` (Vietnamese), `## Quyết định split` (Vietnamese),
     `## Implementation plan (single item, no split)`,
     `## No further split beyond the 3 children below`.
   - At minimum **51 real files (32 + 19, before counting the smaller
     variants) plainly declare "no split, one piece" in exactly the prose
     style `split-and-child-specs.md` asks for** ("No split — one piece.",
     "One honest piece, not split into children.", "No split. This is one
     coherent piece...") and would return `null` from
     `planVerdictFromPlanMd`, not `{verdict:'pass-through'}`.
   - This is **not a stale/legacy convention**: `git log -1 --date=short`
     on a sample of "## No split"-only files shows commits as recent as
     2026-08-26 (5 days before this cell) and 2026-08-24/08-19/08-18/08-17;
     "## Decide the split" samples show 2026-08-24, 08-17, 08-12. Both
     headings are in live, ongoing use, not artifacts from an old
     convention that "## Split" superseded.
   - Caveat matching the reviewer brief's own framing: `docs/history/*`
     entries are terminal (already executed), so none of these specific
     files will be re-swept by R4 today. The finding is about **prevalence
     of the real convention going forward** — the next plan.md written the
     same way real authors have been writing them for weeks will silently
     no-op on the Assignment/runner path, which is exactly R4's stated
     purpose to avoid.

3. **Does this violate ADR-006/007 or the plan's acceptance criteria?** No.
   Grepped both ADR files for "split" — zero hits in either
   `ADR-006-assignment-provenance-and-contract-snapshot.md` or
   `ADR-007-domain-harness-seam-and-non-driving-inline-evidence.md`; neither
   ADR specifies plan.md's split-detection syntax. Read
   `plans/260831-1637-step07-inline-assignment-mvp/plan.md`'s Phase 1 exit
   criterion ("`planVerdictFromPlanMd()` lands with READY+split-children
   test green") and plan-level Acceptance Criteria (npm test green modulo
   named baselines) — both are satisfied literally; no heading convention is
   mandated at the plan level. Confirmed genuinely out of ADR scope, not
   assumed.

4. **Is "fail toward null" actually safe, or does it make R4 a no-op for the
   common case?** Both, in different senses. The FAIL-SAFE PRINCIPLE (never
   infer a real queue-mutating verdict from mere silence, because the
   Cell 6.1/6.2 fixtures rely on staying at `stage: planning` across passes)
   is correct and is not what I am flagging — I independently traced
   `resolvePlan` (`src/intake/plan.mjs` ~596-645) and confirmed the tiny/
   small skip-and-advance branch and the explicit-`callerVerdict` branch are
   genuinely different code paths with different gate exposure (heavy-risk/
   blast-radius gates apply to the latter, not the former) — so returning
   `null` instead of an eager pass-through for tiny/small IS the right call,
   verified against the actual code, not just the Doer's comment. But the
   SPECIFIC signal chosen to represent "Step 4 was reached and plainly
   declared no split" — a heading whose first word is literally "Split" — is
   measurably narrower than what real authors in this exact repository
   write, undermining R4's stated purpose ("derive a plan verdict from
   plan.md deterministically... and wire it into the planning sweep") for a
   meaningful share of genuinely one-piece, already-decided plans.

**Smallest-fix direction:** broaden `SPLIT_HEADING_PATTERN` in
`src/intake/plan-verdict-from-plan-md.mjs:65` from
`/^##[ \t]+Split\b.*$/im` to something matching "split" as a whole word

reality-gate/feasibility-matrix note with no mention of "split" anywhere,

actually in use.

**Test that would catch this today:** none — `test/intake/plan-verdict-from-plan-md.test.mjs`

split` or `## Decide the split` verbatim (both are real, common headings, not

**Severity: HIGH** (blocks close as filed; not a crash/data-corruption risk —
fails toward the pre-existing safe no-op, so nothing breaks silently in the
data-integrity sense — but it is a real, currently-active, non-theoretical
