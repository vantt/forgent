### Implementation deviation from the pre-researched fix shape (found during Tests First, not a re-design)

current-cell.md's exact fix shape says to add `mutatedDirtyBeforeFiles` only to the `evidenceData` object written to `evidence.json` (~L924-936). Doing only that leaves the fix inert: `findLatestAssignmentRunResult` never reads `evidence.json` -- it parses **`result.json`** into the `runResult` variable it reads (`runResult.evidence?.changedFiles` etc. all resolve against `result.json`'s own, separately-constructed `evidence` sub-object at ~L967-978, not `evidenceData`). `changedFiles` already works cross-pass today only because `assignment-runner.mjs` independently writes the same `changedFiles` value into **both** objects. Mirroring that exact precedent for `mutatedDirtyBeforeFiles` therefore requires adding it to both: `evidenceData` (evidence.json, ~L931, alongside `dirtyBefore`/`dirtyAfter`) AND `runResult.evidence` (result.json, ~L977, alongside `changedFiles`). Verified by first running the Tests First battery with only the `evidence.json`-side edit applied -- the new positive cross-pass test failed (derived `no-evidence` instead of `failed`, exactly the silent-downgrade bug described below) -- then adding the `result.json`-side field, after which the same test passed. Both files stay within this cell's named File Ownership (`assignment-runner.mjs`, `operation-choice.mjs`); no other line in either object changed.

- **R6 safety reasoning (Bug Taxonomy's "reason this through carefully" requirement):** documented below; conclusion is "safe, and additionally this cell fixes a real correctness bug beyond the taxonomy's stated security question."

### Safety reasoning (Bug Taxonomy step 3)

**Question posed:** is `mutatedDirtyBeforeFiles` in `evidence.json`/`result.json` -- attacker-writable post-settle, with no hash-binding of its own (unlike `runId`/`claimSha256`) -- a NEW way to flip a genuinely failed/no-evidence run into a false success, beyond what the already-accepted `changedFiles` trust model allows?

**Answer: no new attack surface, and the fix additionally closes a real (non-security) correctness bug.** Reasoning, read against `classifyRunEvidence`'s actual branches (`assignment-runner.mjs` ~L365-443):

1. `hasExternalEvidence = changedFiles.length > 0 || hasDirtyBeforeMutation` (L393) is an OR -- `hasDirtyBeforeMutation` can only ever WIDEN `hasExternalEvidence`, never narrow it, exactly as the taxonomy note assumes.
2. `findLatestAssignmentRunResult` has exactly one live call site (`chooseStageOperation`'s planning-stage branch, ~L731), and it is invoked only for `resultKind: 'gate-verdict'` (validate-plan) -- a **read-only** operation by construction. For read-only operations, `hasExternalEvidence === true` hits the fail-closed branch FIRST (L402-404, before any claim/report logic): `if (isReadOnlyOperation && hasExternalEvidence) return { status: 'failed', confidence: 'failed' }`. So for the one real call site today, a forged/inflated `mutatedDirtyBeforeFiles` can only ever push the derived verdict TOWARD `failed`, never toward `done`/`reported`/`verified`. It structurally cannot manufacture a false success in this call site -- the opposite of the taxonomy's feared direction.
3. For a hypothetical future MUTATING-operation call site, `hasDirtyBeforeMutation: true` alone (with `changedFiles` empty) could contribute to `done/inferred` (no claim) or `done/verified` (claim present) -- the same class of upgrade `changedFiles` alone already provides today with no additional hash-binding. This is equivalent-in-kind to the accepted `changedFiles` trust model, not a new vector: both are advisory, attacker-writable, settle-time facts already subject to the same tamper-detection ceiling (claim-bytes binding, settle-report binding, plan-hash binding) that gates everything else in this function; neither field is itself hash-bound, by design, same as `changedFiles`.
4. Beyond the taxonomy's stated security question, this fix closes a real correctness bug found while building the Tests First positive case: WITHOUT persisting `mutatedDirtyBeforeFiles`, a genuinely-settled `failed/failed` read-only-dirty-mutation verdict recorded with **no `agentClaim`** (worker crashed/killed before writing `agent-result.json`) re-derives cross-pass to `no-evidence/no-evidence` instead of `failed/failed` -- because `hasExternalEvidence` hardcoded to `false` skips the fail-closed branch, and the `agentClaim === null` short-circuits the done/blocked branches too, falling through to the generic `no-evidence` default. `no-evidence` and `failed` both correctly refuse to advance Work, so this was never an advance-Work exploit, but it silently misreports WHY a run failed (masking a read-only contract violation as "just no evidence"). See the new `R6/G3: cross-pass re-derivation...` test in `operation-choice.test.mjs`, which fails against the pre-fix hardcoded-`false` shape and passes after persisting the field into `result.json`'s `evidence`.

**Conclusion:** proceed as implemented -- no new tamper vector; ship.
