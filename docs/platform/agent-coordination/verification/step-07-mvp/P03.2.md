## Requirements

- R3: `src/runner/dispatch/cli.mjs`'s `execute` subcommand gains `--contract
  <file>` (path to a JSON file). Mutually exclusive with `--for` and
  `--assignment` — rejected up front, before any parse/build/dispatch work
  happens. The file IS the execution contract (ADR-006 §4's flat field
  list); an optional top-level `caller` key is pulled out separately and
  never passed to `execution-contract.mjs`'s field validator.
  `caller.writerId` is auto-resolved via `resolveWriterIdentity()`
  (`src/util/session-identity.mjs`) only when the file does not already
  supply a non-empty one — a file-supplied value always survives verbatim.
  Builds an inline Assignment via the real public `buildAssignment()`
  (`provenance: { kind: 'inline', contract, caller }`), the same call
  shape `mission-lite.mjs`'s `createMissionAssignment` already uses.
  Accepts `--work <id>` (reusing the existing `decide --work` lookup,
  `listWork(fgosDir).work[workIdArg]`) to attach the contract to a real
  Work at a declared Stage, which is what lets ADR-007's domain harness
  seam (landed in P03.1) actually fire for this door. A mutating contract
  exits non-zero before any executor is invoked, by construction:
  `buildAssignment()`'s inline path throws `RunnerConfigError`
  synchronously via `execution-contract.mjs`'s `validateExecutionContract`,
  and this throw happens before `executeAssignment()` is ever called.
  Does not hand-roll a write of `assignment.json` — the built (not yet
  persisted) Assignment is passed straight to `executeAssignment()`, which
  already lazily writes it on first run. Output matches the existing
  `--assignment` branch's convention (`JSON.stringify(result)` on stdout).
  `bin/fgos.mjs` needed no change (confirmed: the dispatch subcommand
  wiring there passes argv through unmodified; no per-flag declaration
  exists for any other `execute` flag either). `CHANGELOG.md` gained one
  `### Added` line under `## [Unreleased]`.

## Design Decisions (per current-cell.md Watch-Fors)

- **JSON file shape**: the file IS the contract directly (flat, ADR-006
  §4's field list), with one carved-out top-level `caller` key — not a
  `{ contract: {...}, caller: {...} }` wrapper. Simplest for a caller (human
  or agent) to hand-author from the ADR-006 §4 field list alone; the
  `caller` carve-out is necessary because `caller` is provenance, never one
  of `execution-contract.mjs`'s `ACCEPTED_CONTRACT_FIELDS`, and would
  otherwise be rejected by the generic field validator.
- **`caller.writerId` resolution**: only when the file does not already
  supply a non-empty string. A file-supplied value (e.g. a proof record
  wanting a stable, reproducible writer id) always wins. This mirrors
  `resolveWriterIdentity`'s existing role across the codebase — it fills a
  gap, it does not override an explicit value.
- **No pre-flight `decideExecutorCli` call** in the `--contract` branch:
  mirrors mission-lite's own real call site (`mission-lite.mjs`'s
  `runMissionAssignment`), which never calls it either.
  `executeAssignment()` already runs the identical governance gate
  (`compileDispatchPlan`) internally before spawning an executor, so a
  second, earlier call would only duplicate that check under a different
  error message. `isMissionLite: true` is passed unconditionally, the same
  condition the `--assignment` branch already applies whenever
  `provenance.kind === 'inline'` (ADR-006 R8).
- **`guardCwdRepoRootDivergence`**: not called in the `--contract` branch,
  matching the existing `--assignment` branch's own cwd/root resolution
  (`cli.mjs:861-869`), which also does not call it. Consistent with the
  closest existing precedent rather than adding an unrequested check.

### HIGH — a second `--contract` invocation against the same Work/writer silently discards the caller's new contract and re-executes the stale first one

- **File/line**: `src/runner/dispatch/cli.mjs`, the `--contract` branch's
  `buildAssignment({ ...(work ? { work } : {}), provenance: {...} })` call
  (around line 1046 in the current working tree; the block starting
  `let assignment; try { assignment = buildAssignment({`). No `options` key
  is passed at all — specifically, `options.assignmentsDir` is never
  threaded through.
- **Failing scenario**: run `execute --contract c1.json --work tsk-X`, then
  run `execute --contract c2.json --work tsk-X` again (a second, distinct
  contract file, same Work). Both invocations silently produce the identical
  `assignmentId` (`asgn_tsk-X_op_001`), and the second call's own contract
  content — objective, contextRefs, expectedOutputs, everything — is **never
  actually run**. `executeAssignment()`'s lazy-write in
  `assignment-runner.mjs:581-601` sees `assignment.json` already exists
  from run 1, takes the read-back branch, and silently re-executes run 1's
  stale, already-persisted Assignment instead — while stdout still reports
  `{"status":"done",...}` as if the caller's actual (second) request had run.
  This is a false-success result: the CLI exits 0, the JSON on stdout looks
  legitimate, and there is no error anywhere in the chain telling the caller
  their contract was ignored.
- **Empirically verified** (not just read from code) with a standalone
  repro script driving two real `node src/runner/dispatch.mjs execute
  --contract ... --work tsk-repro` subprocess calls against a live `.fgos`
  store:
  ```
  RUN 1 assignmentId: asgn_tsk_repro_op_001
  RUN 2 assignmentId: asgn_tsk_repro_op_001
  assignmentId collision: true
  run2 actually persisted objective: FIRST invocation objective — should be run 1
  ```
  The same bug reproduces for the no-`--work` path too (fallback id keys off
  `caller.writerId`, which is stable whenever the writer id comes from an
  explicit file-supplied `caller.writerId` or from `resolveWriterIdentity`'s
  env-session branch across repeated invocations in the same agent session —
  not just a PID that happens to change per process).
- **Root cause**: `createAssignmentId` (`assignment.mjs:128-178`) only avoids
  a collision by scanning `assignmentsDir` for existing entries sharing its
  computed prefix — and that scan is entirely gated on the caller passing
  `options.assignmentsDir` (`if (assignmentsDir && fs.existsSync(assignmentsDir))`
  and the final `while (fs.existsSync(...))` retry loop are both skipped
  outright when `assignmentsDir` is falsy). `mission-lite.mjs`'s own real
  call site (`createMissionAssignment`, `mission-lite.mjs:286-328`) knows
  this and explicitly passes `options: { assignmentsDir }` — its own comment
  block (`mission-lite.mjs:330-346`) documents this exact failure mode
  ("silently let the second writer's real content lose with no error
  anywhere in the chain") as a HIGH bug it fixed for its own call site, and
  additionally layers an atomic exclusive-create (`wx`) claim loop on top for
  the concurrent-collision case. This CLI door is the SECOND real call site
  ADR-006 R4 anticipated, and it reintroduces the exact defect the first real
  call site already had to fix.
- **Violated requirement**: current-cell.md's Requirements section
  ("Persistence... Confirm this by reading `executeAssignment` yourself,
  don't assume from this note alone") — the Doer read `executeAssignment`'s
  lazy-write but the read did not surface that the lazy-write's correctness
  depends on `buildAssignment()` receiving a collision-free id, which itself
  depends on `assignmentsDir` being threaded through. Also directly
  undermines this cell's own stated purpose: current-cell.md says "This is
  the door Phase 03's own two live proofs (R4/R5, next cell P03.3) will run
  through" — R5 attaches to a Work via `--work`, and any retry or repeated
  legitimate use of the door against the same Work (very plausible for a
  harness-seam consult that a caller wants to re-run) silently no-ops on the
  caller's actual new request.
- **Smallest-fix direction**: pass `options: { assignmentsDir: path.join(fgosDir,
  'assignments') }` into the `buildAssignment(...)` call in the `--contract`
  branch, mirroring `mission-lite.mjs:306-308` exactly. This alone restores
  correct sequence-number scanning and fixes the sequential/retry case
  reproduced above. Note this does NOT close the narrower concurrent-race
  window (two truly simultaneous invocations under the same identity could
  still compute the same candidate id before either directory exists) — see
  the MEDIUM finding below for that.

### MEDIUM — no exclusive-create claim for the built Assignment (concurrent-race variant of the HIGH above)

- Even after the HIGH fix above restores directory scanning,
  `buildAssignment()`+`createAssignmentId()`'s scan is still check-then-write
  (`fs.existsSync` then later `fs.writeFileSync` in
  `assignment-runner.mjs:583-584`), not an atomic claim. Two genuinely
  concurrent `execute --contract` invocations under the same writer identity
  or the same `--work` id (e.g., two roles in a debate-style flow, or a
  retry racing a slow first run) can still both pass the `!fs.existsSync`
  check before either has written, then one silently loses its content —
  the same class of bug `mission-lite.mjs`'s `createMissionAssignment`
  fixed for its own call site with an exclusive `wx`-flag open-and-retry
  loop (`mission-lite.mjs:367-386`). This CLI door has no equivalent.
  Lower severity than the HIGH above because it requires true concurrency to
  trigger, not just sequential reuse, but it is the same underlying
  provenance-integrity guarantee ADR-006 R4 implies for every inline-build
  call site. Smallest-fix direction: either call
  `createMissionAssignment`-style exclusive-create logic here too, or (KISS)
  factor `mission-lite.mjs:347-392`'s claim loop into a small shared helper
  both call sites use — a decision for the Coordinator/Doer to make, not
  this Reviewer.

### Red-Team Fix Round

Implemented the smallest-fix direction Red-Team named, adapted for R3.5:
factored an atomic id-CLAIM step into a new exported helper,
`claimAssignmentId(buildCandidate, assignmentsDir)`

`createAssignmentId`), used only by `cli.mjs`'s `--contract` branch.

- **Mechanism verified before committing to it**: `fs.mkdirSync(dir)`
  (no `{ recursive: true }`) is atomic at the OS level — it throws `EEXIST`
  if the directory already exists, so it doubles as the claim. On success
  the id is genuinely reserved; nothing is written inside the directory by
  this helper (R3.5 stays true — the branch still hands the built,
  un-persisted Assignment straight to `executeAssignment()`). Confirmed by
  reading `assignment-runner.mjs:575-584` that `executeAssignment()`'s own
  lazy-write path tolerates the directory pre-existing: it does
  `fs.mkdirSync(runsDir, { recursive: true })` first (a no-op success when
  `assignmentDir` already exists, since `recursive: true` mkdir never
  throws `EEXIST` on an existing directory), then checks
  `!fs.existsSync(assignmentJsonPath)` — `assignment.json` itself, not the
  directory — which is still false right after a bare claim, so the write
  proceeds normally into the pre-created directory. `mission-lite.mjs`'s
  own loop (`mission-lite.mjs:367-368`) already relies on the identical
  "pre-existing directory is a supported precondition" behavior for its
  own `fs.mkdirSync(assignmentDir, { recursive: true })` call before its
  `wx` open, confirming this precondition is already exercised code, not a
  new assumption.

  `assignment.mjs` — see "mission-lite non-refactor" below for why this
