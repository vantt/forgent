### MEDIUM 1 — Top-level confidence-gate tightening makes the deeper per-branch reason strings unreachable for any real Assignment, and this new production-relevant behavior is untested

File: `src/runner/dispatch/operation-choice.mjs:1653-1660` (top-level gate)
vs. `:1974-1994` (`fix-verify-red`/`scoped-subtask` branch bodies, left
verbatim).

The Gaps section frames the deeper per-branch `confidence !== 'verified'`
re-checks as "redundant-but-harmless defense-in-depth ... the exact reason
strings a caller reaching them still needs." This is not accurate for the
real production path. `EVIDENCE_REQUIRED_BY_OPERATION` in
`assignment-normalizer.mjs:65-72` stamps `evidence.required: 'verified'`
for `fix-verify-red`, `scoped-subtask`, AND `implement-item` unconditionally
— there is no declared operation for which these three ops' `evidence.required`
is ever anything other than `'verified'`. That means for ANY real
`buildAssignment`-produced Assignment reaching these branches, the new
top-level gate (`evidenceRequired === 'verified' ? confidence === 'verified' : ...`)
is *strictly stricter or equal* to, and always evaluated *before*, the
branch's own re-check — so the branch-level re-check, and its distinct
`${operation}-requires-verified-evidence` reason string / explicit
`canProceed: false` field, can now only ever be reached via a bare `choice`
with no stamped Assignment at all (i.e. only from the two direct-unit-test
call sites the Gaps section itself names). Verified empirically (not
assumed): built a real Assignment via `buildAssignment({ operation:
'scoped-subtask', ... })` and `buildAssignment({ operation: 'fix-verify-red',
... })`, fed each into `interpretAssignmentRunResult` with `confidence:
'reported'` — both return `reason: 'assignment-<op>-insufficient-confidence'`
(the top-level reason) with **no `canProceed` field at all**, never
`'<op>-requires-verified-evidence'` / `canProceed: false` (the branch-level
shape). Same reproduction for `implement-item` (which has no branch of its
own): pre-cell, a real Assignment with `confidence: 'reported'` fell through
every branch to `assignment-implement-item-unsupported-operation`; post-cell
it now stops one step earlier at `assignment-implement-item-insufficient-confidence`.
The Gaps section's claim that `implement-item` is "unchanged by this cell"
is only true for its catch-all destination, not for this specific
confidence/reason-string combination.

Impact: not a functional regression (no code anywhere branches on the
specific reason string, and `canAdvanceEdge`/`stop` land the same both
ways — grep-confirmed, `reason:` string is never matched by callers outside
this file and its own test file), but it is a real, silent shape/behavior
change on the actual production dispatch path (`executeDriverOperationChoice`
always builds a real Assignment) that ships with **zero test coverage** —
every existing/new test that reaches the `fix-verify-red`/`scoped-subtask`
branch bodies does so either via a bare `choice` (no assignment) or with
`confidence: 'verified'` (where both gates agree and it's moot). This is
exactly the "missing negative test" class the review brief asks to hunt
for: the code path that the R5 confidence-gate change actually altered in
production is the one path nothing exercises.

Violated: current-cell.md's own acceptance bar ("Golden battery ... passes
with zero outcome changes for any existing test" is true, but doesn't cover
this new-behavior path at all) and the Bug Taxonomy's "dispatch-key change
silently altering which branch fires ... behavior drift disguised as 'just
changing the condition'" — this is that exact class of drift, just in the
confidence gate rather than the resultKind dispatch key.

Fix: add one test per operation (`fix-verify-red`, `scoped-subtask`,
`implement-item`) that builds a real `buildAssignment`-produced Assignment
and asserts which reason string/shape actually surfaces for `confidence:
'reported'`, so this behavior is pinned rather than incidental; and correct
the code comment/Gaps framing (it is not "defense in depth" for real
dispatches — it is dead code for that specific confidence value on the
production path, which is fine, but should be described accurately).

Repro:
```js
import { buildAssignment } from './src/runner/dispatch/assignment.mjs';
import { interpretAssignmentRunResult } from './src/runner/dispatch/operation-choice.mjs';
// seed domains/coding/task-specs/scoped-subtask.md, then:
const assignment = buildAssignment({ workId: 'x', stage: 'executing', operation: 'scoped-subtask', options: { repoRoot: tempDir } });
interpretAssignmentRunResult({ choice: { operation: 'scoped-subtask', assignment }, runResult: { status: 'done', confidence: 'reported' }, repoRoot: tempDir });
// => { canAdvanceEdge: false, stop: true, reason: 'assignment-scoped-subtask-insufficient-confidence' }
// NOT { ..., reason: 'scoped-subtask-requires-verified-evidence', canProceed: false } as the branch body alone would produce.
```

### MEDIUM 2 — `onAdvance` wiring is internally correct but not consumed by its one real caller; loop.mjs keeps its own separate, pre-existing plan.md-verdict derivation, so this requirement changes no observable production behavior yet

`executeDriverOperationChoice` is called from exactly two places, both in
`loop.mjs` (grep-confirmed, no other caller in `src/`: lines ~909 and
~1523). Grep-confirmed across all of `loop.mjs`: `outcome.verdictPayload`

The only `verdictPayload` reads in `loop.mjs` are `options.verdictPayload`

requirement's real-world value is actually realized and the duplicate logic

### MEDIUM 3 — Compound `resultKind && operation` guard: verified genuinely forced by current stamped granularity, but confirms R5's ADR-006 §3 intent ("replacing `operation === ...` branches") is only 2/6 realized

File: `src/runner/dispatch/assignment-normalizer.mjs:65-77` (evidence/
resultKind tables) vs. `operation-choice.mjs:1811,1910,1974,1985`.

Independently verified the Doer's claim by tracing `EVIDENCE_REQUIRED_BY_OPERATION`,
`RESULT_KIND_BY_OPERATION`, and `classifyDeclaredMutation` for all four
affected operations: `scout-blast-radius` and `resolve-question` both
resolve to `mutation: 'read-only'`, `evidence.required: 'reported'` (one
via explicit map entry, the other via the read-only default — same value),
`resultKind: 'advisory'` (both via the same mutation-derived default, no
explicit map entry for either) — every currently-stamped field is byte-
identical between the two. Same result for `fix-verify-red`/`scoped-subtask`:
`mutation: 'mutating'`, `evidence.required: 'verified'` (both explicit map
entries, same value), `resultKind: 'work-product'` (both via the same
default). No combination of currently-stamped fields can distinguish either
pair — the compound guard is a genuine, verified-not-assumed consequence of
P02.1's stamped granularity, not a missed opportunity within this cell's
own scope (instruction was explicit: preserve branch bodies, only change
the guard).

This is a legitimate design gap, not a defect: ADR-006 §3's stated goal is
"replacing `if (operation === ...)` branches" — as implemented, 4 of 6
branches still use `operation` as the deciding secondary key inside their
resultKind bucket, so the operation string has not actually been retired
from interpretation dispatch for the mutating/advisory groups, only
narrowed. Flag for Coordinator: whether a follow-up cell should widen
P02.1's `RESULT_KIND_BY_OPERATION`/`EVIDENCE_REQUIRED_BY_OPERATION` tables
(e.g. distinct resultKind values per operation, or an added disambiguating
field) so R5's intent is fully realized, or whether the compound guard is
accepted as the permanent shape. Per `assignment-normalizer.mjs`'s own "Do
Not Touch" status for this cell, no code change is recommended here now —
this is a decision to route to Coordinator, not something to fix inline.

### LOW 1 — `findLatestAssignmentRunResult`'s `resultKind` parameter is more general than its one real call site, and that generality is unsafe if ever reused

File: `src/runner/dispatch/operation-choice.mjs:100,729`.

The function accepts an arbitrary `resultKind` and filters on it, but has
exactly one caller (`chooseStageOperation:729`), which always passes the
literal `'gate-verdict'` — the one resultKind value that happens to be
unique to a single operation (`validate-plan`). Per MEDIUM 3, `'advisory'`
and `'work-product'` are each shared by two operations; if this function is
ever called with either of those values by a future caller, its filter
would silently accept a stored run result from either sibling operation
(e.g. a `resolve-question` result read back for a `scout-blast-radius`
lookup) with no operation-level disambiguation, unlike
`interpretAssignmentRunResult`'s own compound guard. Not exploitable today
(single caller, single safe value) — flag the constraint in the function's
own doc comment so a future caller doesn't reuse it unsafely.

### LOW 2 — `onAdvance`'s `opts.repoRoot ?? opts.cwd` fallback is untested and would resolve the wrong content root if ever exercised

File: `src/runner/dispatch/operation-choice.mjs:2128-2129`.

`repoRootForPlan = opts.repoRoot ?? opts.cwd` assumes `opts.cwd` is a valid
repo root when `opts.repoRoot` is absent. At `loop.mjs:909-916` (the
non-sweep dispatch call site), `opts.cwd` is `wt.path` — a worktree
checkout, not the true repo root — while `opts.repoRoot` is always also
supplied there today, so the fallback is currently dead. Every test caller
also always sets both to the same value. If a future caller ever omits
`repoRoot` while passing only a worktree-style `cwd`, `resolveContentRoot`
would run `git worktree list` from the wrong directory and could resolve an
incorrect content root for the onAdvance plan.md read. No test exercises
this branch. Low priority given it is unreachable via any current caller,
but worth a comment noting the assumption, or removing the `?? opts.cwd`
fallback in favor of requiring `repoRoot` explicitly.

### LOW 3 — `fallbackResultKindForOperation`'s try/catch is unreachable defensive code

File: `src/runner/dispatch/operation-choice.mjs:1591-1598`.

`classifyDeclaredMutation` (`assignment-normalizer.mjs:94-98`) always
returns `'read-only'` or `'mutating'` for any string `operation` (its final
branch is an unconditional `return 'mutating'`), so `stampDeclaredAssignment`
can never actually throw `RunnerConfigError` for a valid string operation —
the `mutation !== 'read-only' && mutation !== 'mutating'` guard inside it is
already dead code by construction. The `try/catch` around it here is
defensive-paranoia over an unreachable path (AI-assisted-code risk lens:
catch-and-swallow around code that provably cannot throw for the inputs
this function actually receives, since it's gated by `typeof operation !==
'string'` first). Not a bug; cosmetic.
