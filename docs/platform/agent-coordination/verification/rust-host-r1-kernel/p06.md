## Round 1 (session `rust-host-r1-kernel--p06`)

Doer's commit `a00e7578` implemented the six-stage `InvocationService`
pipeline, `CallerAdmission`/`ProviderGrant` two-stage authority gates, and
the builtin echo provider. Review + red-team against it found:

- **HIGH-1** — `CallerAdmission`'s policy check only refused when
  `allowed_policies` was `Some` and didn't contain the operation's
  `authority_policy_id`; when `allowed_policies` was `None` (i.e.
  `CallerAdmission::default()`), the check was skipped entirely —
  fail-open, not deny-by-default. **Fixed**: added
  `CallerAdmission::allow_catalog_policies(catalog)` (the correct
  minimal-R1 default, wired into `InvocationService::new`) and changed the
  check itself to `policy_satisfied = allowed_policies.as_ref().is_some_and(...)`
  then refuse `if !policy_satisfied` — `None` now denies, never skips.
- **MEDIUM-1** — `ProviderGrant::grant` had a `"*"` wildcard capability
  that bypassed intersection entirely. **Fixed**: removed.
- **MEDIUM-3** — `dispatched` was set `true` before three earlier
  fast-path early returns (provider-not-registered, fast-path-cancel,
  fast-path-deadline) that never actually dispatched anything. **Fixed**:
  `dispatched` starts `false`, flips to `true` immediately before the real
  `provider_instance.invoke(...)` call.
- **MEDIUM-4** — no `Parked` terminal state; a parked outcome fell through
  to the generic `Succeeded` arm. **Fixed**: added
  `InvocationTerminalState::Parked`, recorded distinctly, with an
  end-to-end test.
- **MEDIUM-6** — `cancellation_txs` had no removal path anywhere —
  unbounded growth for a long-running host. **Fixed**: RAII
  `CancellationTxGuard` pruning the entry on every `invoke_internal` return
  path, with a regression test
  (`cancellation_tx_pruned_after_terminal`).
- **LOW-2** — `two_projectors_same_outcome` didn't prove both projectors
  reached the same provider. **Fixed**: both shims now return
  `(output, provider_id)` via `invoke_with_record`, test asserts both
  `provider_id`s match and are `Some`.
- **LOW-3** — `admission_refused` didn't check the absence of
  selection-stage markers. **Fixed**: added assertions that
  `invocation.selection-refused` was never recorded and `stage: select`
  never entered.

Also rejected/no-action: none in round 1 — all findings were real and fixed.

Disposition rationale for the fix approach: HIGH-1's fix (an explicit
catalog-derived default) was chosen over leaving `CallerAdmission::default()`
itself deny-everything, because the constructor `InvocationService::new`
needs a working default out of the box for every existing test and caller
to keep functioning — see Round 2 below for why this default is still not
the end of the story.

Verified (Lead, clean tree): `cargo test -p fgos-host-runtime` (32 lib +

fgos-host-runtime --all-targets -- -D warnings` (clean), `cargo fmt --all

## Round 2 (session `rust-host-r1-kernel--p06-review`, against `bc6f23e8`)

Reviewer independently re-ran every verification command from a clean
tree, confirmed all seven round-1 fixes genuinely implemented (not just
claimed), and confirmed Phase 05's `catalog.rs`/`operation_provider_router.rs`/
`registry.rs` byte-identical to the P05 close commit (no drift). Findings:

- **MEDIUM-1-residual-on-HIGH-1** — `allow_catalog_policies` builds its
  allow-set as `{op.authority_policy_id for op in catalog}`, and `admit()`
  looks up `op_desc` from that SAME catalog, so the policy check is
  tautological: it can never refuse any catalogued operation.
  `InvocationService::new` is the only composition this crate offers
  today, so the *effective* runtime authorization posture for any real
  invocation is unchanged from before HIGH-1's fix — proven by the
  reviewer with a temporary adversarial integration test (written, run,
  deleted) admitting a privileged operation under a never-configured
  policy. Reviewer's own explicit recommendation: **"Do not close HIGH-1
  outright; carry it as a named Phase 08 composition-root obligation --
  the real composition root supplies an explicit externally-sourced
  allow-list, or `InvocationService::new` stops defaulting the admission
  and callers must pass one."**
- LOW-1 — default composition can never grant any capability (harmless
  today: every in-tree provider declares `capabilities: &[]`).
- LOW-2 — principal check's `caller_principal` fallback conflates caller
  identity with the per-call invocation id (pre-existing, not introduced
  by round 1).
- LOW-3 — park-then-resume record semantics undefined for a future
  re-invocation reusing the same id (no re-invocation machinery exists in
  R1; nothing broken today).
- LOW-4 — `CancellationTxGuard::drop`'s `.lock().unwrap()` could abort the
  process if it ran during an unwind on a poisoned mutex.
- INFO-1 — terminal-state set now exceeds R5's literal six-state list
  (strictly more precise; `Parked` is required by MEDIUM-4).

Red-team, working independently, confirmed the same tautology and found a
second, distinct MEDIUM:

- **Concurrent duplicate invocation IDs collide and orphan cancellation.**

## Round 2 fix (Lead-only, commit `32835b8b`)

- **LOW-4** — fixed: `CancellationTxGuard::drop` and `cancel()` now use
  `.lock().unwrap_or_else(|poisoned| poisoned.into_inner())` instead of
  `.unwrap()`.
- **Red-team's concurrent-duplicate-id MEDIUM** — fixed in two layers,
  the second discovered by the Lead's own regression test while proving
  the first:
  1. First pass: generation-tagged `CancellationEntry { generation, tx }`
     + `CancellationTxGuard` carrying its own `generation`, so a guard's
     `Drop` only removes the map entry if it still holds that exact
     generation — fixes premature removal when a later registration
     reuses the same id.
  2. Writing a dedicated regression test
     (`concurrent_duplicate_invocation_id_cancellation`) that spawns two
     genuinely concurrent invocations sharing one caller-supplied id
     exposed a SECOND, worse bug the first pass didn't touch: the map's
     single-slot `insert()` silently dropped the earlier invocation's
     `watch::Sender` when the later one registered, and
     `invoke_internal`'s cancellation watch treats a closed channel
     (sender dropped) identically to an explicit cancel — so the earlier
     invocation was being spuriously cancelled the instant a second one
     shared its id, with nobody ever calling `cancel()`. Fixed by changing
     `cancellation_txs` from `HashMap<String, CancellationEntry>` to
     `HashMap<String, Vec<CancellationEntry>>`: every concurrent
     registration under an id keeps its own sender alive independently;
     `cancel()` now signals every live registration sharing an id (not an
     arbitrary pick); each guard drop removes only its own generation from
     the `Vec`, removing the `Vec` itself once empty.
- **MEDIUM-1-residual-on-HIGH-1** — not solved in code, per the round-2
  reviewer's own explicit recommendation (quoted above): a real fix needs
  a policy source independent of "whatever operations exist in the
  catalog", which this phase has no R1 mechanism to supply.
  `allow_catalog_policies`'s doc comment in `authority_gate.rs` was
  strengthened to state the tautology plainly and name the Phase 08
  composition-root obligation explicitly, rather than reading as a solved
  HIGH.

Round 2 fix disposition: closed at Lead-level verification, not a third
dispatched review round. Rationale — the concurrent-duplicate-id fix is
proven correct by a regression test that reproduces the exact attack
red-team described (two invocations, one caller-supplied id, one finishing
before the other) and asserts the previously-broken behavior (spurious
cancellation of the survivor, or orphaned cancellation reachability) no
longer occurs; `cargo clippy -p fgos-host-runtime --all-targets -- -D
warnings` and `cargo fmt --all -- --check` are both clean on the change;
and the round-2 reviewer already explicitly recommended deferring
MEDIUM-1-residual rather than re-reviewing it. Per the fix-round cap (max
3 fix rounds per cell), this is fix round 2 of 3 — closing here rather
than spending a third dispatched round on a finding the reviewer itself
called "not a regression."

Verified (Lead, clean tree, commit `32835b8b`): `cargo test -p

`cargo test -p fgos-host-runtime -- --list` — all round-1 tests present
