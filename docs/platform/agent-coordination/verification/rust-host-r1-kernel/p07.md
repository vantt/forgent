## Round 1 red-team findings (against `c831811f`, confirmed independently by the Lead)

- **HIGH — selector parser skips a leading dash-prefixed token.**
  `apps/fgos/src/main.rs`'s selector-search loop ignored every argv token
  starting with `-` while searching for the first non-dash token, so
  `fgos --made-up version` picked `version` as the selector instead of
  rejecting `--made-up` per R1/R3. **Fixed**: the first `cli_args` token is
  now always the selector, unconditionally.
- **HIGH — absolute manifest entry escapes the active release path.**
  `resolve_payload_path` joined `components.legacyNode.root`/`.entry` via
  `Path::join` without rejecting an absolute component; `Path::join`
  replaces its base entirely when the joined component is itself
  absolute, so an absolute `entry` silently escaped
  `FGOS_ACTIVE_RELEASE_PATH` and executed. **Fixed**: reject an absolute
  `root`/`entry` up front, and additionally canonicalize both the release
  root and the resolved payload path and require the latter to stay under
  the former (also catches `../` traversal and symlink escapes, beyond
  the literal bare-absolute case red-team demonstrated).
- **MEDIUM — resolution silently falls back when both active-release env
  vars are unset**, discovering a manifest relative to `current_exe`
  instead. **Investigated further, NOT removed** — see "Round 2 correction"
  below; this fallback turned out to be required by R9's own Verification
  command.
- **MEDIUM — the recursion marker can be cleared by the spawned payload**
  before it re-invokes the host, since it is a single inherited env var
  the child fully controls. **Documented, not fixed**: `bin/fgos.mjs` is
  first-party, source-controlled code (accidental-recursion threat model,
  per R5), not an adversary evading its own host's trap; no purely
  env-var-based signal can survive a child that deliberately strips it,
  and a stronger mechanism (e.g. an ancestor-process check) is outside R5's
  asked-for scope.

Also fixed in the same pass: added regression tests for both HIGH fixes
(`test_leading_unlisted_option_does_not_bypass_selector_validation`,
`test_absolute_manifest_entry_is_rejected`).

## Round 2 correction (empirical, same fix commit `3bf88771`)

The Lead's first pass at the current_exe-fallback MEDIUM removed it
entirely, reasoning it matched R4's "never PATH, never cwd, never a
hardcoded path" language literally. Running the full Node test suite
(`FULL_TEST`'s first step) afterward showed no regression there, but a
**separate, explicit R9 Verification command**
(`FGOS_HARNESS_ENTRY=bin:<built binary>`) failed with 82 of the coverage
floor's ~84 cases newly broken — `test/rust-host/harness.mjs` (a Phase
01-03 lease this phase may run but never edit) invokes the binary
directly with **neither** `FGOS_ACTIVE_RELEASE_PATH` nor
`FGOS_ACTIVE_MANIFEST_PATH` set, relying entirely on the fallback to be
self-sufficient. Since the harness cannot be edited and R9's command is
explicit and required, the fallback was restored — verified this was the
correct call per the Verified Decisions rule (new empirical evidence: a
real, concrete test failure against a hard, listed phase requirement).
The confinement fix (absolute-path rejection + canonicalized containment
check) applies regardless of how `active_release_path` was determined, so
red-team's HIGH finding stays fixed either way.

## Round 3 (session `rust-host-r1-kernel--p07-review3`, against `3bf88771`)

Red-team: **clean, no findings** — explicitly re-attempted the selector
bypass, the confinement escape, and looked for a new issue in the
restored fallback; none succeeded.

Reviewer confirmed both HIGH fixes genuinely closed and R9's exact command
passes with exactly the expected 6 by-design `version`-selector failures.
Findings, all about proof strength / documentation rather than the fixed
code itself:

- **MEDIUM-1** — R9's own Verification command sets only
  `FGOS_HARNESS_ENTRY`, which makes `harness.mjs`'s `entryB` default to
  `entryA` — the documented command was a Rust-vs-Rust self-comparison,
  not the claimed Node-vs-Rust differential. **Fixed**: corrected the
  phase doc to set `FGOS_HARNESS_ENTRY_A`/`_B` explicitly.
- **MEDIUM-2** — running the corrected, true differential surfaces **two
  more** failing cases beyond the six `version` ones:
  `coverage-unknown-verb` and `coverage-exit-category-stderr-status`.
  Exit codes agree (`4`) on both hosts; stderr text does not (Node prints
  its full verb list plus writes an `invocation-faults.jsonl` record; the
  Rust host prints a short usage line and writes no fault record). R3
  only specifies the exit code, and reproducing Node's fault-logging side
  effect is real new scope this phase doesn't ask for. **Disposition**:
  accepted as a documented divergence, not fixed in code — recorded in
  `CHANGELOG.md` per `AGENTS.md`'s user-visible-behavior gate, and named
  explicitly in the phase doc's Verification block.
- **MEDIUM-3** — the current_exe fallback's own successful resolution in
  R9's command depends on a gitignored `dev-manifest.json` artifact that
  neither R9's command nor `FULL_TEST`'s own first step produces on a
  genuinely clean tree (it's written as a side effect of
  `apps/fgos/tests/cli_tests.rs`'s own `ensure_dev_manifest()`, or by
  `scripts/run-rust-dev-host.mjs`). **Fixed**: documented this precondition
  explicitly in the phase doc's Verification block.
- **LOW-1** — the current_exe fallback is a boundary interpretation made
  inside this cell rather than escalated, since `plan.md` names the two
  env vars specifically. **Disposition**: ratified explicitly by the Lead
  here (this doc) rather than reversed, given round 2's empirical finding
  that removing it breaks R9's own required verification; flagged that
  P09 may remove the fallback once a staged release always sets
  `FGOS_ACTIVE_*` itself.
- **LOW-2** — `test_absolute_manifest_entry_is_rejected`'s outside-payload
  fixture used CommonJS `require()` inside a `.mjs` file, which Node's
  ESM loader rejects before the fixture's own marker-write/exit-37 logic
  ever runs — two of the test's three assertions were passing vacuously
  regardless of whether the confinement fix actually worked. **Fixed**:
  switched to an ESM `import`; verified the test still passes with all
  three assertions now real (would fail if the confinement fix were
  reverted).
- **LOW-3** — the fallback's probe order (checks 3-levels-up before
  2-levels-up from the binary) could select the wrong release root for a
  staged-release directory layout. **Deferred to P09/P11**, when the
  staged release layout actually lands — latent today, only reachable
  with both env vars unset.
- **LOW-4** — the phase doc named the wrong build-output path for the
  binary (a per-crate path; the workspace emits it at one shared
  repo-root location), and the doer's `.gitignore` edit touched
  Phase 04's own build-output ignore section. **Doc path fixed.**
  `.gitignore` itself: **investigated empirically, left unchanged** —
  removing either the "redundant" bare `node_modules` line or the
  "redundant" per-crate build-output line reintroduced a real
  untracked-file regression on this exact worktree (the linked worktree's
  `node_modules` is a symlink, which the trailing-slash-only
  `node_modules/` pattern does not match on its own; `apps/fgos`'s own
  build-output directory genuinely gets created by some invocation paths,
  confirmed present on disk at the time of review). Ratified as correct,
  not reverted.
- **LOW-5** — R7's text claimed the P02 harness sets
  `FGOS_INVOCATION_RECORD_PATH` itself; it doesn't — only
  `apps/fgos/tests/cli_tests.rs` does. **Fixed**: corrected in the phase
  doc.
