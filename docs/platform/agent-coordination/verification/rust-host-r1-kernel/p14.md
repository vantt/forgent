## Round 1 (doer's own test hang, discovered independently twice)

The doer's `test/install/install-sh.test.mjs` used `spawnSync` to run
`install.sh` against an in-process `node:http` fixture server. `spawnSync`
blocks the entire Node event loop for the child's whole lifetime — but
that same event loop is what the fixture server needs to answer
`install.sh`'s own `curl` requests back to it. The result is a guaranteed
self-deadlock: `install.sh` waits on a response the test process can never
send while it's frozen inside `spawnSync`. The doer's own background test
run hung for the same reason and never got to report before the ceiling
hit. The Lead diagnosed this independently (constructing an isolated
`spawnSync`-vs-`spawn` reproduction) and fixed it by converting all test
cases to async `spawn` + a completion promise, matching the pattern this
track's own `fgctl-stage.test.mjs`/`fgctl-init.test.mjs` already use for
real concurrent-process races. The session's own reviewer, working
independently against the same pre-commit worktree state, found and
diagnosed the identical bug (its own report: "the checked-in test
deadlocks by design and can never pass") — two independent confirmations
of the same root cause.

Lead takeover, first commit `b68946c0`: async-spawn fix, README's `##
Install` section rewritten per R8 (curl \| sh path first, `fgctl init`
next, the npm path kept below with a sentence on why it still exists),
work committed. Second commit `90c41a65` fixed the reviewer's remaining
LOW findings: `grep -F` on `SHA256SUMS` could select a sibling entry
whose name was a superstring of the real tarball's name (fixed to an
exact filename-field match via `awk`); the atomic-install temp file
wasn't covered by the cleanup trap (fixed); no test coverage for the
already-implemented root refusal (added, including the
`FGCTL_ALLOW_ROOT=1` override path).

## Round 2 (red-team's first pass, against `90c41a65`)

Reviewer: clean, confirmed all six items from round 1 closed. Red-team,
running for the first time on this cell: 2 MEDIUM.

- Unbounded `curl`/`wget` downloads: no timeout flags at all, so a server
  that connects but never finishes responding hangs the script
  indefinitely.
- A tarball whose `fgctl` entry is a symlink to an arbitrary external path:
  `-f`/`cp` both follow symlinks transparently, so that target's bytes get
  installed instead of the checksum-verified binary.

Fixed as commit `bda65d3d`: added `--connect-timeout`/`--max-time` to
every curl call and `--timeout=` to every wget fallback call; explicitly
refuse an extracted `fgctl` entry that is a symlink rather than letting
`-f` silently accept it. Added a symlink-payload regression test (external
secret file, confirmed never installed) and a static source-regex test
proving every download/resolution call site carries the shared timeout
args.

## Round 3 (reviewer, against `bda65d3d`)

Reviewer: symlink finding fully closed; the curl timeout path fully
closed (measured live: a 120s-drip and a 15s-connect-blackhole server both
failed within the expected window). New MEDIUM: the wget *fallback* path
remained effectively unbounded in practice — `--timeout` is an idle
timeout that resets on every byte received, not a total wall-clock cap,
and wget retries a failed transfer up to 20 times by default. A
slow-drip server could keep the fallback path alive far longer than
intended even with the flag set.

Fixed as commit `663afed9`: added `--tries=1` to stop the retry
multiplication, and wrapped every curl/wget invocation with the external
`timeout` command (when available) as a genuine wall-clock backstop that
doesn't depend on either tool's own timeout semantics. Strengthened the
Case 6 static test to also assert `--tries=1` and the `HARD_TIMEOUT_CMD`
wrapper's presence at all four call sites.

## Round 4 (reviewer only, narrowly scoped, final, against `663afed9`)

Confirmed clean: hid `curl` from `PATH` to force the wget fallback path,
repeated the slow-drip attack against it, and confirmed the script now
fails at exactly the `timeout` wrapper's ~130s ceiling (measured), with a
control run (hiding `timeout` too) staying alive past 200s — proving the
wrapper is genuinely the operative bound, not a coincidence. One
informational LOW: without coreutils `timeout` on `PATH`, a byte-drip
server still defeats wget's own idle timeout — not a defect, since
`timeout` is coreutils and present on the only supported target
(`x86_64-unknown-linux-gnu`), and a silent/no-response server (as opposed
to a slow-drip one) remains bounded at 120s by wget's own read timeout
regardless.

## Deferred findings (not resolved in this cell)

- LOW (round 3) — `test/install/install-sh.test.mjs`'s Case 6 is a static
  source-regex assertion, not a live behavioral timing test; it cannot
  catch a semantically-equivalent-but-differently-worded timeout gap, and
  its ceiling isn't independently configurable for a true behavioral test.
  Accepted: a live 120s+ hang reproduction in the committed test suite
  would slow every future test run for the whole cell; the reviewer's and
  red-team's own live reproductions (this session's own evidence trail)
  already prove the behavior once, which is what matters for this fix.
- LOW (round 3) — symlinked-directory and hardlink archive-escape variants
  are refused by GNU tar 1.34's own extraction behavior, not by anything
  `install.sh` itself does. Accepted as an environment-dependent property,
  not a defect of this script; not portable to a hypothetical future
  target whose `tar` behaves differently, but V1 ships only
  `x86_64-unknown-linux-gnu`.
- INFO (round 3) — a tarball with both a top-level `fgctl` symlink AND a
  nested real `fgctl` file installs the nested one (the `find -type f`
  fallback correctly skips the symlink and finds the real file elsewhere
  in the tree). Documented behavior, not a vulnerability: only
  archive-internal bytes are ever installed in this case.
- INFO (round 4) — without coreutils `timeout` on `PATH`, a byte-drip
  server can still defeat wget's own idle-only timeout indefinitely (a
  silent/no-response server remains correctly bounded at 120s regardless).
  Not fixed: `timeout` is coreutils, present on the only target this
  track ships (`x86_64-unknown-linux-gnu`); worth a second look only if a
  future target without coreutils is ever added.
