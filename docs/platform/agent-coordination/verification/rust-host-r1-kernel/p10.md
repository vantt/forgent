every doc's own prose. This was included directly in the doer's dispatch
as Part B, alongside R1-R8's Part A.

## Round 1 (reviewer + red-team, against the doer's commit `a7db8864`)

Both independently re-verified everything (herdr-plugin 224/224, all
component test files, `npm run build:skills` producing an empty diff,
an explicit old-vs-new byte-identical-fallback control comparing 7
absence/no-fixture cases). Reviewer: "no HIGH... the doc-prose class
deferred from P00 is closed for the brief's scope." Findings:

- **HIGH (red-team) / MEDIUM M1 (reviewer) — Node tier-0 resolution had
  no executability check.** Shell's `-x` and Herdr's `mode & 0o111`
  checks both correctly fall through to tier 1 when the tier-0 candidate
  isn't executable; Node's `resolveWorkspaceInstallationBin` only checked
  `existsSync && isFile()`, so a mode-644 file was selected as tier 0 and
  handed to a caller that would exec it directly and fail with EACCES.
  **Fixed**: added `fs.accessSync(candidateBin, fs.constants.X_OK)`,
  falling through to tier 1 on failure.
- **HIGH (red-team) / LOW L1 (reviewer) — lexical containment accepted a
  symlink escaping the release root.** The round-0 (doer's own)
  containment check confirmed the manifest's `entries.fgos` stayed under
  the release root as a *string*, but never resolved symlinks — a
  lexically-confined entry that was itself a symlink whose real target
  escaped (`entries.fgos: "bin/fgos-link"` → `/bin/sh`) still resolved as
  valid tier 0. **Fixed**: resolve the real path via `fs.realpathSync`
  when the target exists and re-confirm containment against the release
  root's own real path too.
- MEDIUM M2 — `src/runner/dispatch/cli.mjs`'s `BIN_FGOS_PATH` resolves
  tier 0 against the *module's own* checkout root (evaluated once at
  import), not the caller's dispatch root — under this track's
  linked-worktree topology, a dispatch CLI running from a worktree can
  never see a tier-0 installation even when the main checkout has a real
  one. R4's own literal text ("route the constant through
  `resolveFgosBin`") is satisfied either way, and the fallback preserves
  today's exact behavior. **Lead decision, ratified**: accept for this
  phase, documented in the code comment as a named limitation the cutover
  track can resolve (per-call resolution against the dispatch root
  instead of module-import-time resolution).
- MEDIUM M3 — the doer's own report had several factual inaccuracies
  (claimed an X_OK check that didn't exist yet, wrong "Old" column verbs
  in the doc-prose disposition table, a phantom helper-function edit
  claim, omitted the full Node suite from its own verification). **Not a
  code issue** — the Lead re-derived every fact in this trace doc from
  the diff directly, not from either report.
- MEDIUM M4 — the full Node suite (which the doer never ran, only 4
  component files) has one pre-existing failure
  (`test/runner/cohort-planner.test.mjs:478`, unrelated to P10, tracked
  the same way across this whole track). **Documented, not fixed** — not
  P10's file, not P10's regression.
- Six more LOW findings (stale doc prose in two files; phase/requirement
  labels in three code comments, against this repo's own
  stable-code-artifacts convention; a `Result` that can never be `Err`;
  duplicate exec-branch logic between two Node callers; an informational
  note about `retro-next/SKILL.md` now depending on bare `fgos`). Two
  (stale prose, phase labels) **fixed** in the same pass as the two HIGH;
  the rest **deferred**, documented below.

Fixed as commit `e36fcc86`: X_OK check, realpath symlink confinement, two
new regression tests, two doc-prose corrections, phase-label comment
cleanup. Two existing test fixtures (`registrations.test.mjs`'s tier-0
fixture, `bin-discovery.test.mjs`'s shared `writeStub` helper) had never
set the executable bit on their synthetic tier-0 binaries — harmless
before the X_OK fix, would have failed spuriously after it since they
represent a *real* tier-0 binary (always executable); fixed alongside.

## Round 2 (session `rust-host-r1-kernel--p10-review`, against `e36fcc86`)

Reviewer: clean — independently reproduced both closed HIGH findings with
its own fixtures (including directory-symlink and `releasePath` variants),
confirmed both new regression tests are real (fail against the pre-fix
resolver), confirmed the fixture-mode change broke no other assertion.
Three LOW findings, all about *this same commit's own* leftover
phase/round labels (including one genuinely wrong round-number citation
in a new test comment) plus one comment that had become factually
inaccurate given red-team's own finding below — all three **fixed**.

Red-team, working independently, found one real HIGH the reviewer's pass
didn't cover:

- **HIGH — shell and Herdr accept an escaping tier-zero symlink chain
  Node now correctly refuses.** Shell's `-x` test and Herdr's
  `metadata()`-based executability check both follow a symlink chain
  transparently with no containment check on the real target — an
  executable tier-0 shim that is itself a symlink escaping the
  installation root was accepted and executed by both runtimes, even
  after round 1's fix made Node correctly refuse the identical input. All
  three runtimes disagreeing on the same manifest is exactly the failure
  class this phase exists to prevent. **Fixed**: `scripts/fgos-shell-
  integration.sh` now resolves both paths via `readlink -f` (GNU
  coreutils, present on the only approved reference target) and requires
  containment before executing; `herdr-plugin/src/fgos.rs` gained
  `is_confined()` using `Path::canonicalize()` (component-aware
  containment, not a naive string prefix) wired into `resolve_fgos()`.
  Added a symlink-escape regression test to both runtimes' own test
  suites (Node already had one from round 1).

Fixed as commit `23560b6c`.
