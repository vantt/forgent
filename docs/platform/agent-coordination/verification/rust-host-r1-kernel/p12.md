## Round 1 (reviewer + red-team, against the doer's commit `8e6961c2`)

Reviewer: no HIGH. 2 MEDIUM — M1 (a tracked `.fgos/distribution.json` pin
silently overridden by a `--from` of a different digest, pin left
inconsistent) and M2 (a same-digest re-run still ran the full
`stage_release` — install.lock + candidate copy — before the idempotent
check, rather than skipping it outright). 10 LOW, including a numeric-pid
lock-liveness divergence from the real `main-checkout-lock.mjs` semantics
(L1), a missing digest assertion on non-pin-only arms (L7), and an orphaned
`activation.json.tmp.*` on crash never cleaned up (L8).

Red-team, independently: 3 HIGH, all downstream of one root cause —
`init_workspace` acquired the release-store `install.lock` only for
staging, then released it; there was no separate workspace-scoped lock
covering capsule writes, the activation.json publish, and the install
transaction record. Two concurrent `fgctl init` processes against the same
pre-staged pinned workspace both exited 0, each writing a distinct
completed transaction, with activation left pointing at whichever wrote
last. A pinned-but-unstaged digest with no `--from` was refused rather than
reconciled per docs/architect/packaging-distribution/runtime-identity-and-
activation.md §3's "acquire/stage the pinned release" language (V1's only
real acquisition source being `--from`, per that same doc's §13).

Fixed as commit `fbecde3a`: a create-exclusive `.fgos/installation/
activation.lock` (mirroring Phase 11's `install.lock` pattern) acquired
before any workspace-visible write and held through the R8 tail; `--from`
now reconciled against an existing pin (staged, digest asserted to match;
refused clearly on mismatch, never silently overriding the pin); the
idempotent check reordered ahead of staging; the numeric-pid lock check
corrected to match the real `pidLive && withinTtl` semantics in
`main-checkout-lock.mjs` (the phase file's own R5 prose had paraphrased
this imprecisely); the pin-path digest assertion added; stale
`activation.json.tmp.*` cleanup added.

## Round 2 (reviewer-only recheck, against `fbecde3a`)

Confirmed items 2–6 closed but found a genuine new **HIGH**: `Activation-
LockGuard` had no content (`{pid, ts}`) recorded on the first fix pass, so
a SIGKILL between acquire and the RAII `Drop` (which never runs on
SIGKILL) left the lock file behind forever — every later `fgctl init`
refused with `activation-lock-held` with no path to recovery, and item 6's
own tmp-file cleanup could never even run since the lock blocked every
attempt to reach it. Two MEDIUM: a pre-publish TOCTOU (the `current_
activation` snapshot used to decide `previousArtifactDigest` and the
idempotent-skip path was read *before* the activation lock was acquired,
so a slower initializer could republish over a faster concurrent one using
stale state), and the digest assertion from round 1 only running on the
pin-only arm, leaving the pin+matching-`--from` and no-pin-`--from` arms
trusting `releases/<digest>/` by directory name alone when `stage_release`
took its `NoOp` path.

The session hit its 1-hour `aggregateBounds.wallTimeMs` budget before
red-team's own recheck of the original three HIGH findings could be
dispatched — a hard, non-negotiable session-level bound, not a retryable
failure.

Fixed as commit `e7c94134`: `ActivationLockGuard` now records `{pid, ts}`
and reclaims a stale lock under the same `pidLive && within DEFAULT_TTL_MS`
rule `lock.rs` already applies to the main-checkout lock (one reclaim
attempt, never a retry loop); `activation.json` is re-read once more
immediately after the lock is acquired and treated as authoritative (the
pre-lock read is now only a fast-path optimization to skip wasted staging
work in the uncontended case); the digest assertion moved to run once,
after the candidate manifest is read, covering all three resolution arms.

## Round 3 (fresh session `-recheck2`, reviewer + red-team together, against `e7c94134`)

Reviewer confirmed round 2's three items closed, then found **F1 (HIGH)**:
`ActivationLockGuard::try_create` used `OpenOptions::create_new` followed
by a *separate* `write_all` call — a real window where the lock file
exists but is empty, which the staleness check's "unparseable content is
stale" rule then reclaimed as if the genuinely live holder had crashed.
Reproduced deterministically via `strace`-injected write delay, and
spontaneously in 2 of 15 un-injected barrier races. Red-team, recovering
its original three HIGH attacks against the fully-fixed code for the first
time, found the identical bug class via its own concurrent race (H1).

Fixed as commit `ccb12c38`: `try_create` now writes the lock's complete
`{pid, ts}` content to a uniquely-named temp file first, then `hard_link`s
it onto `activation.lock` — atomic, fails `AlreadyExists` on collision
exactly like `O_EXCL`, but never exposes partial content — mirroring
`main-checkout-lock.mjs`'s own `writeAtomicCreate` for the identical
reason. The stale-reclaim path also gained a re-read-immediately-before-
unlink guard (mirroring that same module's own reclaim safety check), so a
fresh holder that replaces a lock mid-staleness-check is never unlinked
out from under itself. Bumped the existing 8-process concurrency test to
24 processes (the empty-lock window only showed up probabilistically, not
via a fixed small process count) and added two new dedicated tests: a
dead-pid orphaned-lock reclaim (the exact HIGH repro) and a live-pid lock
correctly refusing reclaim.

## Round 4 (fresh session `-recheck3`, reviewer + red-team together, against `ccb12c38`, final)

Reviewer: F1 and the reclaim-unlink guard both confirmed closed — ~20
million tight-loop reads of the lock file during concurrent creation
observed zero empty/partial states; 34 separate race-loop runs (up to 32
truly concurrent processes) all produced exactly one winner with zero
reclaims. One new **MEDIUM (F2)**: the *sequence* of re-read-then-unlink in
the stale-reclaim path is still two separate syscalls, not one atomic
operation — under `strace` injection specifically targeting that narrow
window, two concurrent reclaimers of the *same* crash-orphaned lock could
both eventually call `remove_file` before either's `try_create` retry,
letting both "win". Reviewer's own report notes this is the identical
residual window already present in `src/runner/main-checkout-lock.mjs`
itself (`tryAcquireOnce`'s own stale branch, lines 306–319) — the reference
implementation this phase was explicitly told to mirror carries the same
limitation, and closing it for real needs a structurally different
mechanism (an `flock` held on an open file descriptor, or a rename-to-
tombstone reclaim) rather than another re-read. Never reproduced
spontaneously (10×16-process pre-placed-stale-lock runs: 0 hits). Red-team,
independently: **clean, 0 findings** — direct and delayed-`linkat`
16-process races both produced exactly one completed transaction, no
ENOENT race, no dual winner.

**Not fixed** — closed at the fix-round cap (3 Lead-authored fix commits:
`fbecde3a`, `e7c94134`, `ccb12c38`) with F2 and the accompanying LOW notes
documented as deferred below.

## Deferred findings (not resolved in this cell)

- MEDIUM F2 (round 4) — the stale-reclaim path's re-read-then-unlink
  sequence is two syscalls, not one atomic operation; under deliberate
  `strace` injection, two concurrent reclaimers of the same crash-orphaned
  lock could both eventually unlink and recreate it. Identical residual
  window already present in the reference `main-checkout-lock.mjs` module
  this phase mirrors; never reproduced without injection. Closing it for
  real needs `flock` on an open fd or a rename-to-tombstone reclaim
  mechanism, a genuinely different design, not a further patch on the
  current approach — worth a dedicated look if P13's upgrade/repair path
  ends up sharing this lock file's contention profile.
- LOW L-C (round 4) — a `SIGKILL` timed precisely between the reclaim
  path's own `hard_link` and its temp-file unlink leaves an
  `activation.tmp-<pid>-<ms>` leftover that `cleanup_stale_activation_tmp_
  files` doesn't sweep (it only matches `activation.json.tmp.*`). Cosmetic;
  does not block any future init.
- LOW L-D (round 4, informational) — the temp lock filename can repeat
  within the same millisecond across a failed create and its own
  post-reclaim retry; harmless since each is unlinked immediately after
  use, but the reference module adds a random suffix for defense in depth.
- LOW INFO-1 (round 4, informational) — an `ENOENT` on the lock's re-read
  step (the holder released between our failed create and the read)
  refuses with `activation-lock-held` instead of retrying once, per the
  reference module's own `retry` status for that exact case; one spurious
  refusal on an otherwise-clean concurrent path, self-heals on the next
  invocation.
- LOW L-A (round 1, carried) — a string-identity `activation.lock` is
  never reclaimable (this crate's own writer only ever records a numeric
  pid, so the path is unreachable in practice; documented in the code
  comment rather than fixed).
- LOW L-B (round 1, carried) — `test/rust-host/fgctl-stage.test.mjs`'s
  usage string changed mechanically in the doer's original commit
  (`<stage|status>` → `<stage|status|init>`) as a side effect of adding the
  `init` subcommand; no coverage lost, record only.
- LOW L2–L6, L9, L10 (round 1, from the very first review pass) — a
  non-atomic shim rewrite on every activation (R7 doesn't require
  atomicity there); the `stateSchemas: null` reporting for a Phase 09
  manifest that doesn't yet emit it (correct mapping, not a defect);
  duplicate keys in the `version --runtime-json` envelope's `data` object;
  a byte-for-byte test comparison that normalizes `generated_at`
  (intentional); an `i64`→`i32` pid truncation in the lock-liveness probe
  (fail-closed, not exploitable); linked-worktrees collapsing to one
  `workspaceId` (an inherent consequence of R1's own resolution rule, not
  a bug). None fixed, none regressed across all three fix rounds.
