# Why auto-decompose children now carry `action` + `read_first` directive prose

`tsk-3xd` fixed a real gap: `src/intake/plan.mjs`'s auto-decompose
dispatched children with an empty directive — the executor only got
`title` + `refs` + `verify`, no prose saying what to do, which files to
read first, or which locked decision it had to obey. Children were
stamped straight to stage `executing` (`stageForStep(domain, 'Execute')`)
with no `clarify`/`decompose` gate to backfill missing context, so they
ran blind.

## The bug had three layers, not one

- **Layer 1** — the judge-scout LLM prompt never asked for directive
  prose at all. The schema it requested was
  `children: [{title, verify, kind, ...}]` — no field for instructions.
- **Layer 2** — `normalizeChild` kept only `title`, `verify`, `kind`,
  `risk`, `refs`, `footprint`, `rawDeps`. Even if the model had returned
  prose anyway, this function discarded it before it ever reached a
  child record.
- **Layer 3** — `addWork` never passed `description` through to the new
  child, even though both worker prompt templates
  (`worker-prompt-default.txt`, `worker-prompt-skill-pointer.txt`)
  already interpolate `{description}` — the templates were ready to
  receive prose that nothing upstream ever supplied.

## Why this is a contract gap, not a model-quality problem

`buildDecomposeChildrenVerdict` — the function both the LLM auto-
decompose branch and the native, caller-supplied `fgos plan
--children` branch call (`tsk-27y` D1) — uses the same `normalizeChild`.
That means even a live session with full context, reasoning through its
own split by hand, had no path to hand real directive prose down to the
children it created. The problem wasn't the model producing weak
instructions; there was no field for instructions to travel through at
all, on either path.

## The fix: two new fields, generated in the same LLM call, mechanically checked

D1 adds two new optional fields — `action` and `read_first` — rather
than reusing the existing `description` field, mirroring bee's own cell
shape (`action`, `read_first`, `must_haves` in
`upstreams/bee/skills/bee-planning/references/planning-reference.md`).
Both are additive-optional under the existing `SCHEMA_VERSION` (3,
unchanged) — the same precedent `footprint`/`domain` already set when
they were added without a version bump. `read_first` needed no new
mechanism at all: `footprint` was already kept by `normalizeChild`, just
never interpolated into the worker prompt templates — wiring
`{footprint}` into both templates was the entire `read_first` fix, zero
LLM cost, zero schema risk.

`action` is generated by the LLM in the *same* judge-scout verdict call
(extending Layer 1's prompt schema — no extra model round-trip), and is
**required to cite a real locked-decision D-ID** from the parent's own
`CONTEXT.md`. `normalizeChild` mechanically checks the cited D-ID
actually exists in the parent's decision table, reusing the same pattern
`findUncoveredLockedDecisions` already uses for footprint coverage. A
child whose `action` is missing, or cites no real D-ID, is invalidated —
the same discipline an item with a missing `verify` already gets.

### Why the two rejected alternatives were rejected

- **Freeform LLM-generated prose with no citation requirement** — there
  would be nothing to mechanically check the prose against, so a vague
  or wrong `action` could pass silently, defeating the point of adding
  the field at all.
- **Mechanical extraction from the parent's `plan.md`** — rejected as
  brittle: there's no guaranteed 1:1 mapping between a child and a plan
  phase, and it breaks outright for `tiny`/`small` mode items that never
  produce a phased `plan.md` in the first place.

Requiring a real D-ID citation, checked mechanically, was the option
that kept the prose grounded without either failure mode.

## Scope: fixes both decompose paths, deliberately excludes `fgos add --parent`

Because both the auto-decompose LLM path and the native `fgos plan
--children` path share `normalizeChild`/`addWork`, fixing `decompose.mjs`
alone covers both for free. The manual `fgos add --parent` CLI path is a
separate surface with zero description-shaped flag today — confirmed by
reading its full parameter list — and was left explicitly out of scope
here; that gap already belongs to `tsk-535`'s own stated scope.

## Ordering against `tsk-535`, and why it isn't a supersede

A sibling item, `tsk-535`, looks at the same code from a *data-loss*
angle: 53 of 187 items are missing `description` entirely, and a planned
title re-derive mechanism (`tsk-4zg`) would overwrite a real title with
"Untitled submission" once it ships. `tsk-535`'s original proposed fix
was `description = title` for those items.

**`tsk-3xd` does not make `tsk-535` redundant, and `tsk-535` is not
superseded.** `tsk-3xd` only patches forward — it never touches the 53
already-broken items, and never touches the `fgos add` path at all
(`bin/fgos.mjs` only sets `description` inside the `submit` branch;
`--description` exists only for `edit` and `tool register`). Copying a
title into `description` would satisfy `tsk-535`'s own literal claim,
but would **not** fix what `tsk-3xd` cares about: a title-copied
`description` is still an empty-meaning prompt to the executor, just one
that now looks superficially non-empty.

**Locked order: `tsk-3xd` lands first, no hard dependency** — recorded
via `fgos edit tsk-535 --merge-after tsk-3xd` (`mergeAfter` only orders
at merge time; it never blocks either item's `clarify`/`planning`
dispatch, so both can run in parallel). Reasoning: `tsk-3xd` patches
40 of the 53 description-missing items via real prose through the
decompose path, shrinking `tsk-535` down to two smaller remaining
pieces (`fgos add` missing `--description` for 13 root items, plus
backfilling the other already-broken items). If `tsk-535` landed first
with `description = title`, those 40 child items would *look* fixed
while still being an empty-meaning prompt to the executor — masking the
exact symptom `tsk-3xd` exists to catch, with nobody noticing `tsk-3xd`
itself wasn't done yet.

The data-loss risk `tsk-535` names is not live yet, either: the title
re-derive function is called from exactly one place today, with no
migration or re-derive verb anywhere in source — it only fires once
someone actually ships that mechanism, which doesn't exist yet. The real
hard constraint is that both `tsk-3xd` and `tsk-535` must land before
that future re-derive ships — but since the item that ships it doesn't
exist yet, there's nothing to attach a dependency to today.
