# Why "register a finished item into the merge list" needs no new code

A natural first instinct, when asked to make a finished worktree item
"commit, then register into the merge list — skipping if it's already
registered," is to go build a registration mechanism: some list, some
idempotency check, some new state. That instinct is wrong here, and the
reason why is worth writing down so it doesn't get rebuilt by accident.

## The existing lifecycle already does this

`fgos return <id>` (`bin/fgos.mjs`'s `case 'return'`) already is that
mechanism, in full:

- It requires `item.status === 'doing'` before it will do anything
  (`bin/fgos.mjs:1373-1375`). An item that has already been registered —
  i.e. already moved past `doing` to `proposed` — cannot be "returned"
  again; the verb rejects with `"is 'proposed', not 'doing' — nothing to
  return"`. That rejection *is* the "check if already done, skip if so"
  behavior. There is no separate check to write, because the state machine
  itself only allows the transition once.
- It requires the working tree clean and HEAD advanced past the commit
  recorded at claim time before it will register anything — so "commit"
  is already a hard precondition of the same call, not a separate step
  that could be skipped or forgotten.
- On a passing verify, it moves the item to `status: proposed` — the
  documented run-complete rung of the completion ladder (L9,
  `docs/platform-foundations.md`): "worker chạy xong + verify xanh TRÊN
  NHÁNH — 'đã làm' nhưng CHƯA vào main." `proposed` *is* "registered,
  waiting to merge." There is no second, parallel list an item needs to
  land on.

## Where this showed up

This surfaced concretely while building out `tsk-4j9`'s merge-ordering
work (`docs/history/merge-standardization/`). The item's own decompose
step split off a child specifically to build "auto-commit + register
merge-list entry, idempotent" — restating the same thing `CONTEXT.md`'s
D1 had already locked as needing no new code. Rather than build a second,
parallel mechanism to satisfy a title that outran its own locked decision,
the conflict was surfaced and confirmed directly:

> Xác nhận: no-op, đóng theo D1. fgos return \<id\> đã đủ, không cần code
> mới.
>
> ("Confirmed: no-op, closed per D1. `fgos return <id>` is already
> enough, no new code needed.")

## The general shape of the mistake being avoided

A title generated by decomposing a feature into pieces can drift from
what the feature's own already-locked decisions actually call for —
especially when the decomposition step and the decision-locking step are
different passes (one model-driven, one person-approved) that don't
automatically cross-check each other. When an `executing`-stage item's
own scope contradicts a decision already locked in its feature's
`CONTEXT.md`, the correct move is to surface the conflict and confirm
with a person, not to build whatever the title implies. Implementing a
second registration mechanism here would have produced two competing
"is this merge-ready" signals — `status: proposed` (real) and whatever
the new mechanism tracked (redundant) — for no offsetting benefit.
