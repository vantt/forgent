## Gaps

- **A SECOND, sibling R8-class bug, found only by running the real test
  suite (not by grep alone).** `store.mjs`'s `resolveCoordinationPaths` had
  a fallback chain `root = resolveMainCheckoutRoot(cwd) ??
  resolveMainCheckoutRoot(process.cwd()) ?? process.cwd()`. Before this
  cell's R8 fix, `root` was computed but never actually consumed by
  `fgosDir` (dead for that purpose), so this bug was fully latent. Once R8's
  fix made `fgosDir` depend on `root`, this fallback became live and broke
  ~10 pre-existing tests that dispatch against a plain, non-git temp
  directory (every one of them omits `git init`) -- `resolveMainCheckoutRoot(cwd)`
  correctly returns null for a non-git cwd, and the fallback then resolved
  `root` against the TEST RUNNER PROCESS's own cwd (this repo's real git
  checkout) instead of the caller's own workspace. Fixed by anchoring the
  fallback to `cwd` itself (`resolveRepoRoot(cwd, {strict:true})`, which
  never shells out and just returns `cwd`), matching
  `dispatch/assignment-runner.mjs`'s own already-correct fallback shape
  exactly. Full reasoning and diff in the Doer's report.
- **Two pre-existing tests asserted the exact OLD, now-intentionally-
  superseded invariant** ("dispatchPrimaryTask/dispatchDeclaredOperation/
  recordConsultDisposition accept NO mutation parameter at all" /
  "buildReadOnlyContract hardcodes mutation: 'read-only' as a literal") in
  `test/runner/coordination-r7-work-isolation.test.mjs` (that file's OWN
  "R7" is Phase 06's work-isolation R7, unrelated to this Phase's R7).
  Updated both tests (and the file's own header comment) to assert the NEW,
  correct, narrower invariant: `dispatchPrimaryTask`/`recordConsultDisposition`
  still accept no mutation parameter (unchanged); `dispatchDeclaredOperation`
  now destructures `mutation = 'read-only'` (a default, not a hardcoded
  literal); `buildSessionContract` (renamed) defaults the SAME way. The
  file's header comment also now names, honestly, a genuinely NEW and
  currently-OPEN question this cell's own R1-R9 scope never asked and does
  not answer: could two DIFFERENT `dispatchDeclaredOperation` calls (two
  actors) target the SAME linked-worktree `cwd` concurrently, both
  mutating? R3 only ever refuses the MAIN CHECKOUT; it says nothing about
  two mutating dispatches sharing one worktree. Flagged for whichever
  cell/ADR next addresses multi-actor workspace allocation -- not decided
  here, and no speculative fix attempted (Non-Goals: "no speculative fix...
  unless investigation proves it's genuinely reachable" -- this is a
  genuinely open design question, not a proven-reachable bug in this
  cell's own R1-R9 surface).
- **`src/verbs/coordination/run.mjs` was NOT touched.** R1's schema.mjs
  change (`assertMutationAllowed`, `validateOperationStep` now returns
  `mutation` on its normalized shape) and `dispatchDeclaredOperation`'s new
  `mutation` parameter are both real and tested directly at the engine
  level, but nothing in `run.mjs` currently reads `step.mutation` and
  forwards it into `dispatchDeclaredOperation`'s call -- so `fgos
  coordination run`'s own CLI-driven request path cannot YET actually
  dispatch a mutating step end-to-end. `run.mjs` is not listed in this
  cell's own "Files: may touch," and this cell's Non-Goals explicitly
  disclaim "No CLI-layer change of any kind (that is P02.1's lease)." This
  wiring gap is real, is the natural next step, and is Phase 02/03's own
  scope to close, not silently assumed done here.
- **One test failure in the full-suite run is NOT one of the 4 named
  baseline failures, but IS confirmed pre-existing** (via `git stash`
  against the untouched worktree): `test/runner/coordination-static.test.mjs`'s
  "imports no Work lifecycle, merge, worktree, transport-spawn, or
