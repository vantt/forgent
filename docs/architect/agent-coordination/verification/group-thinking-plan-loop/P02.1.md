### MEDIUM

**M1 — R4's "zero write-side function calls (verified, not asserted)" claim
overstates what the static check actually verifies; it is evadable by a
namespace or dynamic import, not just named imports.**
`test/verbs/coordination-chain.test.mjs`'s `importedNamesFrom` (lines
291-305) matches ONLY the `import { a, b as c } from '<path>'` named-import
syntax via `/import\s*\{([^}]*)\}\s*from\s*['"]([^'"]+)['"]/g`. A write-side
call reachable through `import * as store from '../../runner/coordination/store.mjs'`
followed by `store.openSession(...)`, or through a dynamic `await
import('../../runner/coordination/store.mjs')`, would produce zero matches
for this regex and the check would report "no write-side import found" even
though the module now calls a write-side function. `chain.mjs`'s own
current source only uses named imports (verified by reading the full file:
`import { resolveCoordinationPaths, readManifest } from
'../../runner/coordination/store.mjs'`; `import { showCoordinationUseCase }
from './show.mjs'`), so THIS diff is not currently violating R4's
substance. But the check also inspects only `chain.mjs`'s own file text —
it never verifies that `show.mjs` (the module `chain.mjs` calls into) stays
write-free; if a future change to `show.mjs` added a write-side call,
`chain.mjs`'s own test would stay green with no signal at all, since it
never inspects `show.mjs`'s imports. `test/architecture.test.mjs` has no
general "read-only module never calls write function" check either
(confirmed: its only checks are manifest/layer/domain-siloing, none
of them name write-vs-read). Net effect: the acceptance criterion "verified,
not asserted" is true only for the exact syntactic shape this regex
recognizes, not a real guarantee against every import shape or transitive
regression.
- Smallest fix direction: either (a) extend `importedNamesFrom` to also
  flag any `import *` or dynamic `import(...)` whose specifier matches the
  guarded module fragments (fail closed on an unrecognized import shape
  rather than silently passing), or (b) note this as a named, accepted
  limitation in the Gaps section rather than claiming the check has "real
  teeth" against every write-side reachability path.
- Test: add a second deliberately-broken PoC using `import * as store from
  '../../runner/coordination/store.mjs'; store.openSession(...)` and assert
  the check still trips (it currently would NOT, if run against today's
  `assertNoWriteSideImports`).

**M2 — one corrupt/unreadable session's manifest crashes the WHOLE chain
view, not just that one cell's row.**
`renderCell` (chain.mjs:77-92) calls `readManifest(sessionId, engineOpts)`
directly and unguarded. `readManifest`/`readManifestRaw` throws a raw
`CoordinationError` for a missing or schema-mismatched/corrupt manifest
(store.mjs's own documented categories: `not-found`, `corrupt-log`,
`schema-version-mismatch`). `show.mjs`'s own `showCoordinationUseCase`
wraps its own `readManifest` call in a try/catch that turns a `not-found`
into a friendly `StoreError` and re-throws everything else — but that
wrapping is `show.mjs`'s own single-session behavior; `chainCoordinationUseCase`
does not catch anything around either its own `readManifest` call or its
per-session `showCoordinationUseCase` call, so ONE bad/corrupt session
anywhere under the matched track's sessions throws out of the whole `.map()`
in `chainCoordinationUseCase` (chain.mjs:112-114), which means the CLI
returns nothing at all for the WHOLE track — including every other,
perfectly healthy cell in it. This directly undercuts the phase's own
stated objective ("give the external Lead a real way to see 'what's done,
what's next' across a WHOLE chain of cell-sessions") for exactly the
degraded-state scenario a status tool exists to survive. Not one of the 9
"Tests First" items, so not a literal requirements violation, and not
named in the Gaps section either.
- Smallest fix direction: catch per-session in `renderCell`'s caller and
  render a degraded row (e.g. `{ cellId, sessionId, status: 'unreadable',
  error: err.message }`) instead of letting one session's read failure take
  down the whole track's view.
- Test: seed a track with two healthy closed sessions plus one session
  directory whose `session.json` is truncated/invalid JSON; assert `chain`
  still returns the two healthy cells (today it throws instead).

### MEDIUM — the R4 "chain.mjs never imports a write-side export" static check has no teeth against three common bypass shapes

**Attack performed**: extracted the exact `assertNoWriteSideImports`
regex-based checker from `test/verbs/coordination-chain.test.mjs`

source strings that a future edit to `chain.mjs` (or a less careful

1. `import * as store from '../../runner/coordination/store.mjs'; store.openSession(...)` (namespace import)
2. `const { openSession } = await import('../../runner/coordination/store.mjs')` (dynamic import)
3. A write call reached through a THIRD helper module chain.mjs imports normally (i.e. chain.mjs's own source never mentions `store.mjs`/`session-engine.mjs` at all — the check only scans for those two literal path fragments)

**Actual result**: all three PASS the check silently (`assertNoWriteSideImports` does not throw for any of them) — confirmed by direct execution, not by reading the regex. The check only recognizes the single literal syntax shape `import { a, b } from '<path containing the fragment>'`.

**Current-diff impact**: NOT exploitable today — `chain.mjs` as written
uses only plain named imports of `resolveCoordinationPaths`/`readManifest`
(store.mjs) and `showCoordinationUseCase` (show.mjs, which the check does
not even scan, though it is independently confirmed genuinely read-only by
manual inspection above). This is a verification-method gap, not a live
defect in this cell's diff.

**Requirement violated**: R4's acceptance line — "`chain`'s own
implementation contains zero write-side function calls (**verified**, not
asserted)" — and Test 7's own framing ("the write-side-import check above
has real teeth"). The check has real teeth against exactly the one shape

against three other equally plausible shapes. "Verified" is doing more
work than the check actually performs; R4 is asserted-with-a-test, not
fully verified, for any future edit that doesn't happen to use plain named
imports.

**Smallest fix direction**: either (a) extend `importedNamesFrom` to also
flag any `import *` or dynamic `import(` referencing the two guarded
paths (cheap, closes 2 of 3 bypasses), or (b) note the gap explicitly as a
named limitation in the check's own comment so a future reader doesn't
over-trust "real teeth" against shapes it was never tested against. Not a
blocker for THIS diff's actual content, since the current source is clean
by direct inspection — but the test's own claim of "real teeth" is
broader than what it delivers.
