## Round 1 (reviewer + red-team, against the doer's commit `a19e559f`)

Reviewer: 0 HIGH. 1 MEDIUM (**M1**) — R1's digest assertion in
`scripts/ci-external-consumer.sh` passed only through an undocumented
manifest-digest fallback; the actual `SHA256SUMS` comparison was dead
code in practice. 9 LOW, mostly doc/polish notes (missing `Step failed:`
naming on some `set -e` exits, `FGCTL_ALLOW_ROOT=1` exported
unconditionally, no `CHANGELOG.md` entry, etc.).

Red-team, independently: **HIGH** — the same root cause, demonstrated
live: a run with the `fgos-*.tar.gz` `SHA256SUMS` record replaced by 64
zeroes still exited 0, because the digest assertion's manifest-fallback
branch (comparing the reported `artifactDigest` against `manifest.json`
extracted from the very same, unverified archive) always passes
regardless of tampering — a tautology, not a check. **MEDIUM** — the
local static asset server used `fs.statSync`/`fs.createReadStream` on a
basename-derived path, both of which follow a symlink placed in the
assets directory (loopback-only binding limited real exposure).

Root cause, once inspected (`packages/distribution/rust/src/verify.rs`,
`scripts/build-rust-distribution.mjs`): `artifactDigest` is a canonical
hash of the release *manifest/tree content*, never of the compressed
`.tar.gz` archive's own bytes — the two hash spaces cannot be equal by
construction. The doer's fallback conflated them, and because both
sides of the fallback comparison were derived from the same
unauthenticated archive, no external tampering could ever be detected by
it.

Fixed as commit `393e2365`: split the digest assertion into two
sequential, non-substitutable gates. Gate 1 recomputes the tarball's own
`sha256sum` and requires it to exactly match the asset's `SHA256SUMS`
record (the only check able to detect a tampered/corrupted archive) —
failing this exits 1 immediately, before any content extracted from the
archive is trusted. Gate 2 then compares the reported `artifactDigest`
against `manifest.json` extracted from that now-verified archive — a
legitimate tree-content check once Gate 1 has already proven the bytes
are authentic. Also switched the asset server from `statSync` to
`lstatSync` so a symlink entry in the assets directory is refused
(`isFile()` is false for a symlink's own lstat record) rather than
followed.

One self-inflicted regression caught before commit: an apostrophe inside
a single-quoted `node -e` string (`archive's`) broke the shell's own
quoting and produced a syntax error; caught by an `sh -n` syntax check
and a live run before the fix was ever dispatched for recheck, fixed by
rewording.

  already extracted/staged the archive; moving it earlier would make the
  script's own "before any extracted content is trusted" comment
  literally true end-to-end, and fail faster. Not a correctness gap
  today (`fgctl init`'s own staging is independently digest-verified by
  Phase 11/13's release-store logic; the consumer script's own assertion
  still runs and still gates before declaring success).
- LOW (round 2) — the phase file's own R1 prose ("the reported digest
  matches the `SHA256SUMS`-recorded digest") describes the pre-fix,
  architecturally-impossible single-gate design; worth a documentation
  pass to the two-gate wording, not a behavior change.

  has no dedicated unit test (only the refusal path is tested).
- INFO (round 1, carried) — R5's real prerelease tag cut (the Lead's own
