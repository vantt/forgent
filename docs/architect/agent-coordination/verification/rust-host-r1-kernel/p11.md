## Process note: `partialPolicy.allowedOmissions` blocks the authorize+operation fix-round flow

The initial `open.json` declared `partialPolicy: {"allowedOmissions":
["fixer"]}`. Once doer+reviewer+red-team's quorum was satisfied, the
session closed itself to `status: "partial"` immediately — before the
Lead could issue an `authorize` step for `revise-candidate`. Attempting
`fgos coordination run` with an `authorize`+`operation` pair against that
same `coordinationId` was refused: `authorizeOperation: session
"rust-host-r1-kernel--p11" is not active (status: "partial") -- cannot
authorize a new operation once new materialization has stopped`. The
skill's own fix-round template (`fgos-plan-loop/SKILL.md` §3) never
declares `partialPolicy` on `open.json` for exactly this reason. Lesson
recorded: never declare `allowedOmissions` for `fixer` (or any role) on
the initial `open.json` if a fix round might follow — the session must
stay `active` past first-pass quorum for `authorize` to have anywhere to
land. Worked around the same way P09/P10 did: the Lead applies the fix
directly and opens a fresh, narrowly-scoped session for the recheck.

## Round 1 (reviewer + red-team, against the doer's commit `1bb4feac`)

Reviewer: no HIGH; independently re-ran every Verification command,
proved the concurrent-lock race with its own 6-process fixture,
constructed its own corruption/re-signed-digest fixtures, confirmed
`FGOS_STATE_HOME` fully contains every store path (checked the real
machine store was untouched before/after). Findings:

- MEDIUM M1 — a SIGKILL mid-stage leaves a 0-byte `install.lock` with no
  owner identity; every later stage call fails `stage already in
  progress` with no mechanically-provable stale-recovery path. R6 does
  not require crash recovery, so **not fixed in this phase**; flagged for
  P12/P13, which will need owner identity in the lock format.
- MEDIUM M2 — `__FGCTL_STAGE_LOCK_DELAY_MS`, a test-only env-var sleep
  hook, was compiled into the production binary on the lock-acquisition
  path. **Fixed**: removed entirely (not just disabled) — the reviewer's
  own 6-process race already proved the lock correct without it.
- Eight LOW findings (dot/empty path segments not normalized before the
  collision check; extraction failure leaking a `.stage_tmp_*` dir;
  `status`'s sort/cross-check gaps; `mode` not verified/applied; the
  no-op path copying the full candidate before reading the digest; a
  wrong error-variant display string; undeclared extra files staged by
  design; `verify.rs` duplicating `canonical.rs`'s own output). Two
  (dot/empty segments, temp-dir leak) **fixed** alongside M2; the rest
  **deferred**, documented below.

Red-team, working independently: no HIGH. All symlink/absolute/traversal/
case-collision manifest attacks were already refused (matching P09's and
P10's own confinement discipline). One real finding:

- MEDIUM — a `.tar.gz` containing a valid release plus one
  path-traversing (`../../archive-traversal-sentinel`) member staged
  successfully; `tar::Archive::unpack` silently sanitized the entry
  rather than the whole archive being refused, violating R7's intended
  trust boundary. **Fixed**.

Fixed as commit `c68a657b`: removed the lock-delay hook (concurrency test
rewritten to fire 8 truly concurrent processes instead); added a
read-only, two-pass `extract_tar_gz` that validates every archive
entry's path and type (absolute/empty/`..`/non-regular-file all refused)
before extracting anything; wrapped the temp-directory preparation phase
in a closure that removes the temp dir on any failure, not just
success/quarantine; refused `.`/empty path segments in
`canonical.rs` (the canonicalization table defines only NFC +
`/`-separator normalization, nothing that collapses these segments, so
refusing rather than silently normalizing was the conservative
reading). Added 2 new canonical.rs unit tests, 5 new extract.rs unit
tests, and 4 new Node integration tests (traversal-archive refusal,
symlink-archive refusal, dot-segment collision, rewritten N-process
concurrency race).

## Round 2 recheck, reviewer half (`rust-host-r1-kernel--p11-recheck2`, against `c68a657b`)

Clean: 0 HIGH, 0 MEDIUM. Independently reproduced all four fixes with its
own fixtures (Python `tarfile`-built hostile archives distinct from the
fix's own construction method; its own re-signed `./bin/fgos` manifest;
its own 12-process×3-round lock race). Confirmed the diff stays inside
`packages/distribution/rust/**` + the one test file, and that M1/L3–L8
were correctly left untouched. Two new LOW findings, both explicitly
called out as non-blocking and non-security:

- L-new-1 — a pax *global* extended header (`git archive`'s own output,
  `tar --pax-option`, Python `tarfile(pax_headers=…)`) is now refused as
  a disallowed entry type, a format-compatibility regression (GNU
  default, `--format=ustar`/`posix`, and Python's default PAX local
  headers all still stage fine). **Deferred** — not produced by this
  track's own pipeline; noted for P15 if an asset-tarball producer using
  pax global headers is ever chosen.
- L-new-2 — `extract_tar_gz` opens the archive path twice (validation
  pass, then extraction pass); a same-user writer swapping the file
  between passes would have the second pass extract unvalidated bytes.
  Same trust domain, not exploitable across a boundary. **Deferred** as a
  defense-in-depth note (open once + `seek(0)`, or an inode/size check,
  would close it).

## Round 2 recheck, red-team half (`rust-host-r1-kernel--p11-recheck3`, against `c68a657b`)

Delayed by the red-team executor (`codex-herdr`) hitting its own usage
quota mid-task (see the infra note below); once dispatched, found:

- MEDIUM — `..\..\outside` (backslash traversal) and `C:\outside\pwn`
  (Windows drive-letter path) archive entries were accepted and staged
  as literal filenames rather than refused. They did not escape the
  store on this Linux host (backslash isn't a path separator here), but
  the check was inconsistent with this same crate's own
  `canonical::normalize_release_path`, which already normalizes
  backslashes to `/` for manifest-declared paths per the canonicalization
  table's "Path separator: always `/`, including on Windows" rule.
  **Fixed**.

All other probes (hardlink, device/fifo, deep traversal, trailing-slash,
exact `..`, symlink chain, 16-process lock race, hidden-subcommand
probes) were already refused/correct — no other findings.

Fixed as commit `7e79dd20`: `validate_entry` now normalizes backslashes
to `/` before the absolute/traversal check (mirroring `canonical.rs`) and
refuses any entry whose normalized path starts with an ASCII-letter +
`:` drive prefix. Added 2 new unit tests plus 2 new full-archive tests.

- LOW L-new-2 (round 2) — `extract_tar_gz` opens the archive by path
  twice (validate, then extract); a same-user TOCTOU is theoretically
  possible but not exploitable across a trust boundary.
