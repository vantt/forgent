## Round 1 (session `rust-host-r1-kernel--p05`, red-team half; reviewer deferred to session 2)

- Red-team: 1 HIGH — `RegistrySnapshot.providers` is `&'static
  [ProviderDescriptor]`, not R1/R3's literal `&'static [&'static dyn
  OperationProvider]`. **Disposition (first pass): investigated and
  rejected** as a false positive, cited against the canonical kernel doc's
  own Router signature (`host-invocation-provider-routing.md` §6: Router
  returns `ProviderDescriptor`, not a provider object) and Phase 06's own
  plan (`OperationProvider` trait defined fresh in `invocation_service.rs`,
  not `contracts.rs`; Phase 06 treats Phase 05's `select()`/`RegistrySnapshot`
  shape as fixed, calls it read-only). Documented in place (commit
  `128823db`) rather than changing the design. **This rejection's own
  reasoning was itself found partly wrong in Round 2 below (R3-M1) and
  corrected — the conclusion (design unchanged) held, the stated reason did
  not.**

## Round 2 (session `rust-host-r1-kernel--p05-review`, against `d3de434d`)

## Round 3 (session `rust-host-r1-kernel--p05-review2`, against `b14beee5`, and the Lead's own final fix)

- Reviewer: independently re-verified the canonical doc and Phase 06's plan
  themselves (not just trusting the doc comments) and found Round 1/2's M1
  rejection reached the right OUTCOME through a technically wrong
  INTERMEDIATE claim: `fgos-host-runtime` "cannot hold real `dyn
  OperationProvider` objects even in principle" because it "never depends
  on a provider crate" is false as a general Rust fact — a `&'static dyn
  Trait` field needs no dependency on any implementing crate. The real,
  correct reason is R7: this phase is explicitly forbidden from defining
  the trait body at all, so no trait declaration exists yet to form the
  `dyn` type from. Also flagged that calling R1/R3-vs-R7 a "false positive"
  undersold it — it is a genuine contradiction inside the phase spec,
  correctly resolved in R7's favor, which deserved recording as a
  contradiction rather than dismissal. 4 LOW (M2's deferral has no owner in
  the plan corpus beyond a source comment; L1's stated justification isn't
  the real one — `SNAPSHOT_FOR_TESTS` is same-crate, `pub(crate)` would
  serve it; `OperationId::from_static` is public and unvalidated, and M4's
  new test only covers `CATALOG`, not Phase 06/08's own future
  constructions; a link-time catalog-membership check at `build_snapshot`
  could complement M3 without adding a second runtime enforcement point —
  a Phase 08 suggestion).
- Red-team: re-confirmed M2 independently (no new information beyond
  Round 2's own M2), rest held clean.
- **Disposition:** the rationale correction — **fixed** (commit
  `151ca63d`): rewrote the doc comment to cite R7 (no trait declaration in
  scope) as the real blocker, dropped the "never depends on a provider
  crate" claim entirely, stopped calling it a "false positive" in favor of
  "genuine contradiction, resolved in R7's favor", and stated the real
  downstream cost for Phase 06/08 (two registration tables to keep in sync
  instead of the one canonical §6 sketches) explicitly. The four new LOW
  findings (M2-owner, L1-reason, `from_static` validation reach, link-time
  catalog check) are **accepted as real, deferred** — fix-round cap reached
  (3: the initial M1 doc fix, the M4/M5/L2 fix, this rationale correction),
  and none blocks R1: M2's owner gap and the catalog-check suggestion are
  both explicitly Phase 06/08 concerns already flagged in this same trace
  doc; L1's reason is corrected right here rather than in source, since the
  behavior itself (pub fields) is not changing; `from_static`'s validation
  reach is speculative work against phases not yet written.
