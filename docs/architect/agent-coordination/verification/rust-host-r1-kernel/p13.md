## Round 1 (reviewer + red-team, against the doer's commit `a21f100b`)

Reviewer: 0 HIGH. 2 MEDIUM — **M1**, a quarantine recovery dead end: once
`fgctl verify` quarantines the active release, neither `fgctl repair`
(the release directory it needs is gone) nor `fgctl init [--from]`
(Phase 12's idempotent-skip compared digest only, never status) could
ever recover the workspace through either documented door. **M2**,
upgrading away from a quarantined activation recorded its own (now-moved)
digest as `previousArtifactDigest`, so a later `fgctl repair` rollback
would target a release directory that no longer exists. 9 LOW, mostly
duplication/DRY notes and pre-existing-scope observations (`build-
rust-distribution.mjs`/`cli_presenter.rs` touched to carry `stateSchemas`
into the digest and the runtime-json envelope — accepted as a deliberate,
reasonable consequence of adding the field, not scope creep).

Red-team, independently: **HIGH** — `verify_workspace` read the current
activation and moved the release directory to quarantine *before*
acquiring the activation lock, then published that stale in-memory record
*after* acquiring it; a concurrent `fgctl upgrade` that published a
different activation in the race window would have been silently
overwritten by the stale quarantine record. **MEDIUM** — `fgctl repair`
of a tampered active release (no `previousArtifactDigest` to roll back
to) refused correctly but never quarantined the tampered payload, leaving
known-bad content sitting under `releases/<digest>/`. **LOW** — a
same-digest `fgctl upgrade --from` wasn't idempotent, minting a fresh
`activationId` with a self-referential `previousArtifactDigest`.

Fixed as commit `3ac50db7`: `verify_workspace` now re-reads
`activation.json` fresh once the lock is held and only publishes the
quarantine status if it still names the digest being quarantined;
`init_workspace`'s four idempotent-skip checks now exclude a quarantined
current activation, so `fgctl init --from <matching source>` genuinely
re-stages/re-verifies/re-publishes instead of silently no-op'ing;
`upgrade_workspace`'s `previousArtifactDigest` computation now chains past
a quarantined current activation to whatever it itself pointed at;
`repair_workspace`'s no-`previousArtifactDigest` branch now quarantines a
verification failure the same way `fgctl verify` does; `upgrade_workspace`
gained the same same-digest idempotent-skip fast path `init_workspace`
already had.

## Round 2 recheck (fresh session `-recheck1`, reviewer + red-team, against `3ac50db7`)

Reviewer: reproduced all five round-1 fixes broken on the pre-fix binary
and passing on the new one — but found a genuine **regression**: the
MEDIUM fix's new quarantine branch inside `repair_workspace` published the
*pre-lock* `current_activation` snapshot after acquiring the lock, the
exact same stale-overwrite pattern the HIGH fix had just closed in
`verify_workspace` — the Lead's own fix, applied to a second call site,
forgot to carry the pattern with it. Also found a second missed spot for
M2's chaining rule: `init_workspace`'s *own* `previous_artifact_digest`
computation (a different line from the idempotent-skip check already
fixed) still recorded a quarantined activation's digest verbatim. One LOW
(the new `upgrade_workspace` idempotent-skip fast path wasn't re-checked
under the lock, the same class of race `init_workspace` already guards
against with its own two-phase pattern).

Red-team, independently: a distinct MEDIUM — a process killed by `fgctl
verify` between moving a release to `quarantine/` and publishing
`status: "quarantined"` leaves `activation.json` falsely reading `"ready"`
for a digest whose release directory no longer exists; the round-1 fix's
own status-based exclusion (`current.status != "quarantined"`) can't
detect this exact window, so a same-digest `fgctl init --from` had no way
to recover it.

Fixed as commit `8527120a`: `repair_workspace`'s quarantine branch now
re-reads `activation.json` under the lock the same way `verify_workspace`
does, publishing the quarantine status only if the fresh read still
matches; `init_workspace`'s own `previous_artifact_digest` computation now
applies the same quarantine-chaining rule already used in
`upgrade_workspace`; all four `init_workspace`/`upgrade_workspace`
idempotent-skip checks now also confirm the release directory genuinely
exists on disk (`is_release_staged`) before trusting a digest-and-status
match, closing the falsely-ready crash window across every recovery door;
`upgrade_workspace`'s same-digest fast path gained the authoritative
post-lock re-check `init_workspace` already had.

## Deferred findings (not resolved in this cell)

- LOW (round 3) — the MEDIUM-1 init-door quarantine-chaining fix has no
  dedicated regression test, though its `upgrade_workspace` twin does
  (round-2 fix commit added the twin's test but not this one). Coverage
  gap, not a correctness defect; the fix itself is deterministic and was
  independently reproduced broken/fixed by both reviewer rounds.
- INFO (round 3) — a `previousArtifactDigest` recorded as valid at write
  time can later itself become quarantined by an unrelated `fgctl verify`
  run; the next `fgctl repair` correctly refuses with a clear "previous
  release not found" message rather than silently rolling back to bad
  content. Safe by construction, left alone.
- INFO (round 3) — the repair/verify re-read-under-lock guard compares by
  `artifact_digest`, not `activationId`; a sub-millisecond window exists
  where a concurrent `fgctl init --from <same digest>` re-stage between
  the release move and the lock acquisition could still receive the
  quarantine status meant for a different activation of the identical
  digest. Not reproduced even under `SIGSTOP`-based injection (two
  concurrent admin operations on the exact same digest, one-command
  recovery available either way); comparing `activationId` instead would
  close it structurally. Worth a look if P15/P16 surface any related
  concurrency requirement, not urgent enough to justify a third fix round
  here.
- LOW/L2–L9 (round 1, carried) — mostly DRY/duplication observations
  (pre-publish gate sequence repeated across init/upgrade/repair;
  `workHistoryRoot` path hand-built in three places; `verify_workspace`
  reading activation and renaming the release directory before acquiring
  the lock, though the lock-acquisition itself is now race-safe per the
  round-2/3 fixes; a rollback via `repair` clearing
  `previousArtifactDigest`, an intentional design choice not documented
  inline; `status --json`'s shape depending on cwd; a refused upgrade
  candidate remaining staged under `releases/` by design). None fixed,
  none regressed across both fix rounds.
