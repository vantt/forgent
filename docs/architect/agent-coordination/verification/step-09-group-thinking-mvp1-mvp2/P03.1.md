### MEDIUM-1 — a keyless repeat dispatch could silently return the WRONG invocation's Assignment/RunResult

`resolveTaskKeyAuthorization`'s fallback picked the MOST RECENT consumed
authorization when no fresh one was pending. With ≥2 authorizations already
spent at one binding, a keyless repeat call always derived the LAST
invocation's key and silently resumed the LAST invocation's Assignment —
`resumed: true`, no error — regardless of which invocation the caller
meant. New behavior from this cell: before it, both invocations shared the
unsuffixed default key, so the second dispatch was loudly refused by
P02.2's silent-discard guard and this state was unreachable. Reviewer rated
this the same class as P02.2's Red-Team fan-out MEDIUM ("silently
substituting one actor's Assignment/RunResult for another's").

**Disposition: FIXED**, per the Reviewer's own recommendation and suggested
direction. `resolveTaskKeyAuthorization` now returns the single consumed
authorization when exactly one exists (the genuine idempotent-resume case,
unaffected), and `null` when more than one does and none is fresh — an
ambiguous repeat the caller must resolve with an explicit taskKey. `null`
correctly cascades to the existing "no unconsumed operation-authorized
event" refusal already covered by other tests, so no new error path was
invented. Regression: `coordination-recheck-disposition.test.mjs` "a
keyless dispatch with TWO already-consumed authorizations and none pending
is refused, not silently resolved to the most recent" — Coordinator
mutation-verified (reverting to "most recent" fails exactly this one test).

### MEDIUM-3 — R4's "recheck lineage" claim exceeds what replay actually reconstructs

The Proof Matrix and this cell's own test describe replay as answering
"which recheck followed which original", but the implemented join
(`assignments[].authorizationId → authorizations[].targetArtifactRef`) only
names an artifact-revision link, and only when `targetArtifactRef` is
supplied (it is OPTIONAL on `operation-authorized`, per the accepted
contract's field table — omit it and replay carries no link at all). There
is no actual original-Assignment → recheck-Assignment pointer in the
reconstructed shape; the test's stand-in assertion
(`originalRecord.actorId === recheckRecord.actorId`) is a same-actor
coincidence check, not lineage.

**Disposition: documentation corrected, no code change** (Coordinator
ruling, choosing between the Reviewer's two options). Adding an explicit
predecessor-ref field would mean extending the `assignment-created` or
`operation-authorized` event shape beyond what the accepted contract
specifies — exactly the kind of contract extension this cell's own brief
says to STOP and report on rather than do unilaterally. The accepted text
names WHAT replay must answer, not a specific field to carry it, so this is
correctly a scope decision, not a bug. Ruling: **replay's recheck-lineage
capability is artifact-revision-scoped and best-effort — present only when
a driver supplies `targetArtifactRef`, absent otherwise — not a guaranteed
original→recheck edge.** Recorded as a named precondition on P03.2's
`show.mjs` work in `index.md`'s forward notes (below), since that is the
next consumer of this return shape and needs to know not to assume a
stronger guarantee than what exists. If a future phase genuinely needs a
hard predecessor edge, that is a new contract decision, not this cell's or
P03.2's to make unilaterally.

### MEDIUM-1 — `recordDriverDisposition`'s idempotency was JSON key-order sensitive on the caller-supplied `authorizedBy`

`store.mjs`'s idempotency check compared raw `JSON.stringify(payload)`.
Top-level key order was safe (payload is rebuilt in fixed order), but
`authorizedBy` is a caller-supplied nested object stored verbatim, and
`JSON.stringify` is key-insertion-order sensitive — two calls describing
the IDENTICAL decision with `authorizedBy`'s two fields in a different
order compared unequal and appended twice, silently making the "reject
then recheck then accept" history (the actual MVP2 loop shape) ambiguous.
Reproduced sequentially, no concurrency needed. A real divergence from the
`authorizeOperation` pattern this door claims to mirror (which keys
idempotency on `authorizationId` alone, with no equivalent exposure).

**Disposition: FIXED.** Comparison now canonicalizes `authorizedBy` to its
two schema-validated fields before comparing, rather than relying on raw
JSON key order. Regression: `coordination-recheck-disposition.test.mjs`
"R3: idempotency compares a CANONICAL shape, not raw JSON -- a repeated
disposition with authorizedBy's fields in a different key order is still a
no-op". Coordinator mutation-verified (reverting to raw `JSON.stringify`
comparison fails exactly this one test).

### MEDIUM-2 — `session.json` was written non-atomically, so an unlocked reader could throw `corrupt-log` against a healthy session

**Pre-existing code, not in this cell's own diff** — reported because it
was reproduced end-to-end for the first time in this track (three
independent reproductions, up to ~2.45M read attempts, one realistic-rate
trial genuinely aborting a legitimate dispatch), is a DIFFERENT mechanism
from the already-recorded `dangling-ref` read-ordering race (different
error, different — scarier — category, and hits `readManifest`, the first
statement of every dispatch, not only `replaySession`), and is live on the
exact concurrent-dispatch path P03.2's R5 live proof will exercise.
`writeManifestRaw` used a plain `writeFileSync` (O_TRUNC then write) while
every reader reads outside the events lock by design (the same
pre-lock-advisory split this whole track relies on) — a window in which a
concurrent reader could observe a truncated file mid-write.

**Disposition: FIXED**, in-cell rather than deferred, despite being
pre-existing (Coordinator ruling: `store.mjs` is within this cell's own
file scope, the fix is small and well-established — same same-directory
temp-file-plus-`renameSync` idiom `src/state/events.mjs`'s own lock
acquisition already uses — and it is a direct, specifically-named
prerequisite for the very next cell rather than a general future concern
like the four session-wide caps). `writeManifestRaw` now writes to a
same-directory temp file and atomically renames it into place; POSIX
`rename` within one directory guarantees a concurrent reader always
observes either the complete old file or the complete new one, never a
partial write. No dedicated stress test added to the committed suite
(Coordinator judgment: a timing-dependent torn-read window is not
reliably, deterministically reproducible in a fast unit test without
flakiness risk to CI; the fix is a well-known-correct idiom already used
elsewhere in this codebase, and Red-Team's own adversarial reproduction —
recorded here — is the evidence of record). Full suite re-verified green
after the fix (5134 tests, exactly this track's baseline).

## Gaps

### Interpretations recorded for review

- **R2: which disjunct of the contract's "MUST incorporate" was implemented.**
  The clause allows the new artifact/evidence revision OR the authorizing
  `invocationKey`/`authorizationId`. **Implemented: `authorizationId`**, as
  `declared:<operationId>[:round-N]:auth:<authorizationId>`. Reason for
  preferring it over `targetArtifactRef`: `authorizationId` is already
  refused-if-duplicated by `authorizeOperation` and is REQUIRED on every
  authorization, whereas `targetArtifactRef` is optional — keying on an
  optional field would leave the guarantee absent exactly when a driver omits
  it. `invocationKey` would work identically (it is 1:1 with
  `authorizationId` by R5's own uniqueness rule); `authorizationId` was chosen
  because it is what `assertAuthorizationSpendable` and the binding cap
  already count by.
- **R2: how the taskKey's own authorization is selected, and why a resume
  still works.** The key must exist BEFORE a claim record can be looked up,
  so the authorization is resolved first, by a rule deliberately different
  from the gate's: prefer an UNCONSUMED authorization for the binding (that
  is the invocation being spent), else fall back to the most recent
  ALREADY-CONSUMED one (that is a repeat/crash resume, which must land on the
  key its own invocation first claimed). The dispatch gate below then
  re-resolves exactly as before, with the resulting `resumedAssignmentId` in
  hand — unchanged. Consequence worth a ruling: when a FRESH authorization is
  pending, a repeat call now dispatches that new invocation rather than
  resuming the previous one. That is the intended recheck semantic (a new
  authorization is a new invocation), and the previous behavior in that
  situation was P02.2's loud refusal, never a successful resume, so nothing
  that used to succeed now fails.
- **Two P02.2 guard tests were re-pointed from the default taskKey to an
  explicit one, and a companion test added.** The two silent-discard guard
  tests ("...same-DEFAULT-taskKey resume" and the FAN-OUT one) drove their
  collision by OMITTING a taskKey — a shape this cell makes structurally
  impossible, which is precisely the root-cause fix P02.2 deferred to Phase
  03. Both tests now pass an explicit shared `taskKey`, which is the one
  remaining way to reach that collision, so the guard keeps exactly the
  coverage the Reviewer and Red-Team mutation-verified (both still fail under
  a guard mutation). Nothing was weakened: a NEW test
  ("a FAN-OUT dispatch with no explicit taskKey no longer collides at all")
  proves the default path now succeeds where it used to be refused. Net
  driver-authorization file count: 41 → 42 tests.
- **R3: `disposition` is validated as a non-empty string, not a closed enum.**
  The contract's field table says "e.g. `accepted | rejected`" — "e.g." is
  open, and the same section describes disposition as also "closing a round."
  `schema.mjs` therefore enforces shape only. Note the divergence from
  `session-engine.mjs`'s pre-existing `DISPOSITION_VALUES`
  (`accepted|rejected|partially-accepted`), which governs the UNRELATED
  consult-disposition Assignment path (Phase 04 R4) — that is a different
  mechanism (a worker Assignment recording a requester's judgement of
  specialist advice), not this event. Flagged rather than assumed: if Review
  wants a closed vocabulary on the driver event, it is a one-line addition.
- **R3: no session-scope check on `targetRef`/`evidenceRefs`.** Nothing reads
  a disposition's refs into a contract, a prompt, or a gate — it is inert
  ledger state — so this is the same "close it when it is read" posture
  P02.2's Red-Team LOW-1 applied to `targetArtifactRef` (and which this cell
  now closes for that field, exactly because R1/R2 started reading it). If a
  future cell renders dispositions into any worker-visible context, the same
  `assertRefsOwnedBySession` call belongs there first. Recorded, not deferred
  silently.
- **R3: post-terminal dispositions are refused at WRITE time but not
  neutralized at READ time**, unlike `operation-authorized`. Deliberate
  asymmetry: Recovery Rule point 5's read-time neutralization exists so a
  post-terminal authorization "can never satisfy the dispatch gate" — a
  disposition has no gate to satisfy and can materialize nothing, so throwing
  away a durable driver decision found on the log would lose information for
  no safety gain. Written-time refusal mirrors `authorizeOperation`/
  `recordRunRetry` exactly.
- **R3: idempotency is byte-identical-payload, not per-target.** A repeat of
  the exact same decision (same ref, disposition, rationale, evidence) is a
  no-op — the crash-resume discipline every other store door uses. Two
  genuinely different decisions on ONE ref (a `rejected` first pass, an
  `accepted` after the recheck) both append and both replay, in order; that
  is asserted by test, since it is the actual MVP2 loop shape.
- **R1: no new artifact primitive was added, deliberately.** The phase file's
  own named risk is "treating artifact production as repo mutation." Artifact
  refs already exist end to end (`runResult.evidence.artifacts`, produced by
  `assignment-runner.mjs` and returned to every caller through
  `dispatchDeclaredOperation`'s own result), so R1 needed exposure and
  linking, not storage. The only code this cell added for R1 is the
  `targetArtifactRef` scope check. If Review expects a first-class
  artifact-ref reader on the session surface, that is P03.2's `show.mjs`
  work, with this cell's `replaySession` shape already carrying everything it
  needs to join.
