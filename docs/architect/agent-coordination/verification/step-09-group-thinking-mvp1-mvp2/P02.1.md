### Recovery Rule point 5 atomicity — independently confirmed genuine

Re-derived from source rather than from the trace. `withEventsLock(logPath, fn)`
(`src/state/events.mjs:404`) acquires a cross-process on-disk mutex at
`path.dirname(logPath)/events.lock`; a session's `eventsPath` is
`<sessionDir>/events.jsonl`, so the lock file is `<sessionDir>/events.lock` for
all three of:

- `authorizeOperation` — `store.mjs:722`
- `createSessionAssignment` — `store.mjs:510`
- `transitionSessionStatus` — `store.mjs:1047`

It is the same on-disk mutex, not a similarly-named or adjacent one, and
`transitionSessionStatusLocked` (`store.mjs:1017-1034`) performs its status
check, terminal-event append, and manifest write entirely inside it. The race a
check-then-act shape would leave open, re-derived independently: T1 reads
manifest (`active`) → T2 acquires the lock, appends `session-cancelled`, writes
the manifest, releases → T1 acquires the lock and appends `operation-authorized`
*after* a terminal event. In the shipped shape the manifest read at
`store.mjs:723` is inside the same held lock, so a concurrent transition can
only be wholly-before (loser re-reads the winner's manifest and refuses) or
wholly-after. The Doer's discriminating-by-mutation argument is sound and I
concur; the test at `coordination-driver-authorization.test.mjs:425` genuinely
discriminates, because the worker holds the identical lock via `withSessionLock`
and only transitions *inside* it, so a pre-lock manifest read would still see
`active`.

### Ruling on the interpretation call: "ignored" is CORRECT — endorsed

The contract's own words are "invalid/ignored", which offers both readings; the
requirement it actually imposes is that such a record can never authorize a
dispatch. `replay.mjs` satisfies that by construction — the record is excluded
from `authorizations`, and `authorizations` is the only list
`resolveBindingAuthorization` ever consults — and it is not silently dropped:
it is surfaced on `ignoredAuthorizations`. A hard throw would be strictly
worse, and not marginally: `replaySession` is on the read path of every
dispatch, every resume, and every inspection, so throwing would render a
session that is *already terminal* permanently unreadable over a record that
by construction can no longer do anything.

I checked specifically for a scenario where "ignored" masks something a throw
would surface, and found the dangerous combination is already a throw: an
`assignment-created` naming a post-terminal authorization fails
`dangling-ref`, because `authorizationById` is built only from the valid
`authorizations` list. So the case where a post-terminal authorization
actually *did* materialize work still fails closed. The residual is
observability only (see LOW-2), not safety. **No change requested.**

### Findings

**MED-1 — the `(nodeId, operationId, targetActorId)` triple is under-tested;
the Proof Matrix overstates the evidence.**
Reference: `resolveBindingAuthorization`, `session-engine.mjs:884-892`; the
16-test file `test/runner/coordination-driver-authorization.test.mjs`.
The R4 Proof Matrix row says the triple is "**Proven by** 'an authorization
for (phase-recheck, reviewer-recheck, reviewer) does NOT authorize the SAME
actor at a DIFFERENT binding'". I mutation-tested that claim in an isolated
copy of `src`/`test`/`core`, running the full 16-test file against four match-key
mutations:

| Mutation of the match predicate | Result |
|---|---|
| drop `record.nodeId === nodeId` | **16/16 still pass** |
| drop `record.operationId === operationId` | **16/16 still pass** |
| drop `record.targetActorId === targetActorId` | **16/16 still pass** |
| keep `targetActorId` only (the literal cohort-planner shape) | 15/16, 1 fail |

Only the degenerate actor-only shape is caught. The disambiguation fixture
puts each operation at its own node with its own operation id, so `operationId`
alone already separates the two bindings and no single component of the triple
is independently load-bearing under test. The implementation is correct — this
is an evidence gap, not a defect — but it is precisely the gap the cell's Bug
Taxonomy was written to close, and as written the row's "Proven by" claim is
not supported.
*Smallest fix:* two additions to the existing fixture — (a) one node hosting
two driver-authorized operations for the SAME actor (makes `operationId`
load-bearing), and (b) one operation template bound to two different actors at
ONE node, the `independent-research-fan-out-fan-in` cohort shape the function's
own doc comment cites as motivating (makes `targetActorId` load-bearing). Each
needs one added assertion that an authorization for one does not authorize the
other. `nodeId` cannot be made load-bearing without MED-2.

**MED-2 — `nodeId` validates but never selects; the contract's blessed
"same operation id, different activation at different graph positions" case is
unreachable at runtime when both positions bind the same actor.**
References: `resolveDeclaredOperationActor`, `session-engine.mjs:825`
(`const picked = targetActorId !== undefined ? matches.find((m) => m.ref.actor === targetActorId) : matches[0];`)
and `authorizeDeclaredOperation`, `session-engine.mjs:963-969`
(`const { actorId, node, binding } = resolveDeclaredOperationActor(definition, operationId, targetActorId); if (nodeId !== undefined && nodeId !== node.id) { throw ... }`).
`flow-definition.md`'s Activation section states: "The same `operations[].id`
may be declared `required` at one graph position and `driver-authorized` at
another." I confirmed empirically that such a definition validates (probe
against the real `validateFlowDefinition`: two nodes, one `review` operation,
one `reviewer` actor, node B `driver-authorized`, node A default → VALIDATES
OK, both bindings normalized with distinct activation). At runtime, however,
`dispatchDeclaredOperation` exposes no node selector, and
`resolveDeclaredOperationActor` returns the FIRST graph-order match for the
actor — so node B's binding is never resolved, its `driver-authorized`
activation never gates anything, and `authorizeDeclaredOperation({nodeId:'B'})`
throws a misleading "does not host" error because `nodeId` is only checked
against the first match, never used to select it. Notably the cell's own new
schema test "the same operation id may be required at one graph position and
driver-authorized at another" uses `actor-1` at BOTH positions, so it asserts
the shape is *representable* while the runtime cannot honor it.
Not a gate bypass — the resolved binding's own declared mode is always
honored, and this first-match behavior predates this cell (Phase 04 R5) — but a
silent-misconfiguration trap on a configuration the contract names explicitly.
*Smallest fix direction:* thread an optional `nodeId` into
`resolveDeclaredOperationActor` as a third disambiguator (and accept it on
`dispatchDeclaredOperation`), so `authorizeDeclaredOperation`'s existing
`nodeId` parameter selects rather than merely validates. If that is out of
scope here — reasonable, given `dispatchDeclaredOperation`'s signature is a
shared surface — the alternative is to reject at validation a duplicate
`(ref, actor)` pair appearing at more than one node, which today
`validateGraph` does not do (`definitions/schema.mjs:559-594` tracks duplicate
node ids only). Either way this belongs in Gaps for P02.2/Phase 03 rather than
being left undiscovered.

**LOW-1 — replay does not fail closed on two `assignment-created` events
consuming one `authorizationId`.**
Reference: `replay.mjs`, the consumption loop —
`for (const [id, event] of createdIds) { ... record.consumedByAssignmentId = id; }`.
The second consumer silently overwrites the first. Demonstrated empirically:
a session with one `operation-authorized` (`A1`) and two `assignment-created`
events both carrying `authorizationId: 'A1'` replays without error and reports
`consumedByAssignmentId = asgn_x_002`. The write path treats "one authorization
materializes at most one Assignment" as an invariant and enforces it lock-held
(`store.mjs:557-567`), and `replaySession` mirrors every *other* cross-event
invariant at read time (duplicate `assignment-created`, duplicate
`operation-authorized`, dangling authorization ref) — this one is the
exception. I traced the self-heal fast path (`store.mjs:517-548`, which passes
`authorizationProvenance` while skipping the consumption check) as the only
non-hand-crafted candidate and satisfied myself it is not reachable: the
pre-lock gate would already have refused, since the authorization it needs is
by then consumed and `resolveBindingAuthorization`'s fallback requires
`consumedByAssignmentId === null`. So this is defense-in-depth / read-time
invariant parity, not a live bug.
*Smallest fix:* one branch in that loop — throw `duplicate-ref` when
`record.consumedByAssignmentId !== null`.

**LOW-2 — the gate's refusal message does not surface
`ignoredAuthorizations`.**
Reference: the `no unconsumed "operation-authorized"` throw in
`dispatchDeclaredOperation`. Given the endorsed "ignored" reading, an operator
whose authorization landed post-terminal sees only "no authorization exists",
never "one exists but was neutralized as post-terminal". `replaySession`
already returns the list; naming a non-zero count in the error message would
close the only observability cost of the ignored-vs-throw choice. Cosmetic.

**LOW-3 — note, no action requested.** `store.mjs`'s exported
`authorizeOperation` validates shape and session status only; binding existence
is checked exclusively by `session-engine.mjs`'s `authorizeDeclaredOperation`.
This split is explicitly documented in the function's own doc comment and is
the right layering (store.mjs holds no definition awareness). A direct-store
authorization naming a nonexistent binding is inert — its triple can never
match a real dispatch. Confirmed no consumer outside
`src/runner/coordination/**` imports either door.

### HIGH-1 — the self-heal path double-consumes one authorization and then bricks the session

**Where.** `store.mjs`: the lock-held "one authorization materializes at
most one Assignment" check lives at `store.mjs:557-567`, *after* the
`if (fs.existsSync(taskClaimPath))` branch at `:517` has already returned
or self-healed. The self-heal branch (`:532-546`) forwards
`authorizationProvenance` into `completeAssignmentRegistration` (`:354-367`),
which appends the consuming `assignment-created` — with no consumption check
on that path at all. The check therefore guards only the genuinely-new-taskKey
path.

**Why the pre-lock gate does not save it.** `dispatchDeclaredOperation`'s
gate (`session-engine.mjs:1358-1400`) resolves the authorization from an

`createSessionAssignment`. Two processes can both pass that unlocked gate on
the same authorization — which is precisely why the lock-held check exists.
One of the two branches inside the lock is missing it.

**Reproduced end to end with NO file surgery** (a real `SIGKILL` produces the
crash state, then two real OS processes dispatch the same driver-authorized

### Attack 4 — `nodeId`'s non-load-bearing status IS safe as shipped (independent conclusion)

Two facts hold at once, and separating them matters more than the Fix Round's
table implies:

1. **`nodeId` can never be independently discriminating through the engine
   doors, by construction.** `authorizeDeclaredOperation`
   (`session-engine.mjs:963-983`) ignores the caller's `nodeId` for selection
   and writes `node.id` from the SAME deterministic
   `resolveDeclaredOperationActor(definition, operationId, targetActorId)`
   call the gate uses. `nodeId` is a pure function of the other two
   components, so two records agreeing on `(operationId, targetActorId)`
   always agree on `nodeId`. No fixture can make it discriminate — which is
   why the mutation sweep cannot catch dropping it, and why no additional
   test short of MED-2's change ever will. The Fix Round's remaining
   "evidence gap" is therefore not closable by testing; it is a property of
   the design.
2. **It is nevertheless load-bearing at runtime.** Proved empirically: an
   authorization written through the raw `store.authorizeOperation` door with
   the real `operationId` + real `targetActorId` but the WRONG `nodeId`
   (`phase-first-pass` instead of `phase-recheck`) reaches the log, and the
   dispatch is **refused**. Review LOW-3's "a direct-store authorization
   naming a nonexistent binding is inert" depends on this comparison.

The MED-2 shape itself is fail-safe, confirmed empirically: one operation
bound to one actor at two nodes (`required` at A, `driver-authorized` at B)
validates; `authorizeDeclaredOperation({nodeId: 'node-b'})` is refused
("that binding lives at node node-a"); the dispatch resolves node A's
`required` binding and dispatches with no authorization. Node B's activation
never gates anything, but nothing is *wrongly* authorized — the binding the
runtime actually resolved had its own declared mode honoured. No
authorization for one binding can authorize another today.
**Recommendation (docs only, no code change):** record reason (1) beside
`resolveBindingAuthorization`, so a future cleanup does not delete the
`record.nodeId === nodeId` comparison as "proven non-load-bearing by mutation
testing".

## Gaps

### Deliberately deferred to P02.2 (R5-R8) — the boundary, so P02.2 need not rediscover it

- **R5 `invocationKey` idempotency.** `invocationKey` is threaded end to end
  (authorize → `operation-authorized` payload → `assignment-created`
  provenance → replay's derived record) but its UNIQUENESS is not enforced
  anywhere. Two `operation-authorized` events may carry the same
  `invocationKey` under different `authorizationId`s today, and each will
  authorize its own dispatch. The contract's "a second `operation-authorized`
  (or the Assignment dispatch it would trigger) reusing an already-consumed
  `invocationKey` is rejected", and its session-scoped uniqueness rule, are
  P02.2's.
- **How much idempotency P02.1 DID have to build** (so the double-dispatch
  hole named in this cell's Bug Taxonomy is not left undocumented): exactly
  one invariant, `authorizationId` is consumed at most once. It is enforced
  in TWO places — advisory pre-lock in `dispatchDeclaredOperation`'s gate
  (`consumedByAssignmentId === null`), and AUTHORITATIVELY lock-held inside
  `createSessionAssignment` (fresh `readEvents` under the held events lock,
  on the genuinely-new-taskKey path only, so a resume is never counted as a
  second consumption). Consumption is derived from disk, never in-memory:
  an authorization is consumed by the one `assignment-created` event carrying
  its `authorizationId`. A resume of the same `taskKey` deliberately prefers
  its OWN already-consumed authorization
  (`peekClaimedAssignmentId` → `resolveBindingAuthorization`) so an idempotent
  retry never spends a second authorization. What this does NOT cover: a
  crash between `authorizeOperation` and `createSessionAssignment` leaves an
  unconsumed authorization that a later, DIFFERENT `taskKey` can legitimately
  spend — correct under R4 alone (nothing was dispatched), but R5's
  `invocationKey` rule is what will make that resume-identical rather than
  merely safe.
- **R6 context-grant enforcement.** `grantedContextRefs` is recorded on the
  authorization and copied onto `assignment-created` as
  `contextGrant: {refs: [...]}`, but it is NOT enforced at dispatch: the
  dispatched contract's `contextRefs` are still built exactly as before, and
  nothing filters or validates them against the grant. The contract's
  "may read only the refs listed in that authorization's
  `grantedContextRefs`, plus … its own declared inputs", and its
  "every `grantedContextRefs` entry must resolve to an artifact/ref owned by
  this same `coordinationId`" clause (currently unchecked at authorize time
  too), are both P02.2's.
- **R7 bounds interaction.** `activation.maxInvocations` is validated by the
  schema and carried on the normalized binding, but NOTHING reads it at
  dispatch yet — a binding cap neither narrows nor is checked. Existing
  `aggregateBounds` enforcement is untouched and unregressed (no new bounds
  logic was added, per this cell's Non-Goals). P02.2 owns "binding caps
  narrow, never widen" plus the freshness rule that the consumed-invocation
  count is counted from the on-disk `operation-authorized` events for that
  exact binding.
- **R8 driver authority.** `authorizedBy` is validated for SHAPE only
  (`{type: 'driver', id: <non-empty>}`). Its `id` is not tied to the
  session's `provenanceRoot` or to any writer identity, so any caller able to
  reach `authorizeDeclaredOperation` can name an arbitrary driver id. This is
  the exact gap R8 names ("`writerId` alone is not enough if the existing API
  cannot distinguish an arbitrary event writer from the driver").

### Interpretation recorded for review

- **"invalid/ignored" for a post-terminal `operation-authorized`.** The
  accepted contract's Recovery Rule point 5 says replay must treat one
  appearing after a terminal event as "invalid/ignored". This cell implements
  **ignored**: such a record is excluded from `replaySession().authorizations`
  (the only list the R4 gate consults, so it can never authorize anything) and
  reported separately as `ignoredAuthorizations` rather than silently dropped.
  It is deliberately NOT a throw: the contract anticipates such an event
  reaching disk despite the write-path lock ("regardless of write-time
  ordering"), and throwing would make the whole session permanently
  unreadable over a record that can no longer authorize anything. The safety
  property is identical under either reading. If Review prefers a hard
  failure, the change is one branch in `replay.mjs`.
- **`ts` is not a payload field.** The contract's `operation-authorized` field
  table lists `ts`, but `state/events.mjs`'s `appendEventCore` stamps `ts` on
  every event automatically, and `coordination/schema.mjs`'s `EVENT_SPECS`
  already excludes `ts` from every other event kind for exactly that reason.
  `operation-authorized` follows the same existing convention rather than
  introducing a second, hand-supplied timestamp.
- **Test fixture placement.** No shipped fixture was edited. The driver-
  authorized fixtures are written into each test's own temp
  `<cwd>/.fgos/coordination-protocols/` — `protocol-loader.mjs`'s REAL
  project tier — as JSON (so they parse without the optional `yaml`

### HIGH-1 — the self-heal path no longer double-consumes an authorization

The consumption check and MEDIUM-1(a)'s issuance check are now ONE lock-held
helper, `assertAuthorizationSpendable`, called from BOTH of

```js
function assertAuthorizationSpendable({ eventsPath, coordinationId, authorizationProvenance, ownAssignmentId }) {
  const authorizationId = authorizationProvenance?.authorizationId;
  if (authorizationId === undefined) return;
  const events = readEvents(eventsPath);
  const issued = events.some((e) => e.type === 'operation-authorized' && e.payload?.authorizationId === authorizationId);
  if (!issued) throw new CoordinationError('validation', `... names no "operation-authorized" event in this session ...`);
  const alreadyConsumedBy = events.find((e) => e.type === 'assignment-created' && e.payload?.authorizationId === authorizationId);
  if (alreadyConsumedBy && alreadyConsumedBy.payload.assignmentId !== ownAssignmentId) {
    throw new CoordinationError('validation', `... was already consumed by Assignment "..." -- one authorization materializes at most one Assignment`);
  }
}
```

The self-heal branch passes `ownAssignmentId: claim.assignmentId`; the

`undefined` and ANY existing consumer still throws — the pre-existing check's
behavior and its exact message are preserved, not weakened. The exemption
matters only where it should: a genuine idempotent resume of its OWN
authorization.

Category and phrasing match the sibling check verbatim (`validation`, "one
authorization materializes at most one Assignment"), so no existing assertion
on that message text moved.
