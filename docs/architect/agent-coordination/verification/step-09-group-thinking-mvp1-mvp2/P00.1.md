### HIGH — Recheck could silently collapse onto the original Assignment via the existing taskKey/idempotent-claim precedent

- File/reference: `coordination-session.md`, "Recheck Is Not Retry" section,
  and the Recovery Rule's point 2-3 plus the Storage Layout's
  `tasks/<hash>.json` line.
- Evidence (verbatim): Recheck Is Not Retry says a recheck "is a NEW
  Assignment created against a new artifact/evidence revision ... never a
  retry of the original reviewing Assignment. The original Assignment's
  RunResult and verdict are never superseded, rewritten, or deleted by a
  recheck — both ... remain readable." The Recovery Rule (point 2) says each
  `assignment-created` event is written atomically "following mission-lite's
  existing `wx` claim precedent," and the Storage Layout names
  `tasks/<hash>.json` as "internal idempotent-claim record, one per
  `taskKey` (hash of the raw taskKey)." Point 3 of the same Recovery Rule:
  "any Assignment already present in `assignmentRefs` is treated as already
  issued and is never re-created."
- Exploit scenario: this idempotent-claim mechanism exists precisely to
  make re-dispatch of "the same logical task" a no-op that resumes the
  existing Assignment rather than creating a duplicate — that is its whole
  purpose, reused verbatim by this cell's own `invocationKey` idempotency
  rule for `operation-authorized`. Nothing in the new text says a recheck's
  `taskKey` (the hash key that this exact machinery uses to decide "already
  issued, don't recreate") must incorporate the new artifact/evidence
  revision, the triggering `authorizationId`, or the `invocationKey`, so as
  to differ from the original reviewing Assignment's own `taskKey`. If a
  future implementer derives a recheck's `taskKey` the same way as the
  original binding's `taskKey` (e.g., keyed by `nodeId`+`operationId`+
  `actorId` only, which is exactly the binding identity this contract's own
  Activation section anchors `activation` to), the idempotent-claim
  mechanism will read that as "already issued" and resume/reuse the
  ORIGINAL Assignment id instead of creating a new one — turning a recheck
  into exactly the retry this section says it must never be, without any
  bug: the implementer would be faithfully following the accepted `wx`
  claim precedent this same contract cites as authority.
- Which requirement it violates: directly defeats the Required Negative
  Test "A recheck creates a NEW Assignment ... without rewriting,
  superseding, or deleting the original Assignment's RunResult or verdict;
  both remain readable after the recheck" — not through implementation
  error, but through literal application of a mechanism this contract
  itself endorses elsewhere.
- Smallest fix: add one clause to "Recheck Is Not Retry" stating that a
  recheck's `taskKey` (or whatever idempotent-claim key gates Assignment
  creation) MUST incorporate the new artifact/evidence revision (or the
  authorizing `invocationKey`/`authorizationId`), so it is never
  claim-collision-equal to the original reviewing Assignment's own
  `taskKey`.

### MEDIUM — `invocationKey` uniqueness scope is never stated

- Evidence (verbatim): "Each `invocationKey` is consumed exactly once per

  this binding/`nodeId`," not "globally across all sessions."
- Exploit scenario: storage layout (`events.jsonl` is per
  `sessions/<session-id>/`) makes session-scoped enforcement the practical
  default, but the contract never says so in prose, unlike
  `aggregateBounds`, which gets an explicit "recomputed fresh from the

  in the same file. A future implementer could just as legally read

  `operation-authorized` events carry `nodeId`) rather than per-session,
  and check only that binding's own prior events — silently permitting two
  DIFFERENT bindings in the same session to reuse the identical
  `invocationKey` string, each independently "consumed once" under that
  narrower reading. Whether cross-binding reuse should be legal or
  forbidden is exactly the kind of question the contract should answer and
  currently doesn't.
- Which requirement it violates: R1 faithfulness/precision — the
  "exactly-once consumption" acceptance criterion is stated without a
  scope, so two structurally different implementations (session-scoped
  vs. binding-scoped) both satisfy the literal text while producing

- Smallest fix: one clause — "`invocationKey` uniqueness is scoped to the

  concern" (or the alternative scope, if binding-scoped was actually

### MEDIUM — No atomicity/ordering guarantee for `operation-authorized` vs. a concurrent terminal-status transition

- File/reference: `coordination-session.md`, Required Negative Tests list:
  "An `operation-authorized` event issued after a session has left `active`
  (any terminal status) is rejected," compared with the Recovery Rule's
  explicit atomic-ref rule for `assignment-created`
  ("Each `assignment-created` event and its corresponding `assignmentRefs`
  append happen as one atomic write") and `aggregateBounds`'s explicit
  "never bypassable by process restart (every bound is recomputed fresh
  from the on-disk manifest/event log on every call, never from in-memory
  state)" guarantee.
- Exploit scenario: "issued after a session has left active" describes an
  outcome, not a mechanism. The contract is silent on whether checking
  "is this session still active" and appending the `operation-authorized`
  event must happen as one atomic/serialized operation with respect to a
  concurrent `transitionSessionStatus` call moving the session to a
  terminal status. A future implementer could legally read this as a plain
  check-then-act (read status, see `active`, then append) with no lock
  or single-writer serialization against the terminal-transition path —
  under concurrent access (e.g. a driver authorizing an operation in one
  process while a quorum/timeout path concurrently closes the session in
  another), the check could pass a beat before the terminal write commits,
  and the resulting `operation-authorized` event would land in
  `events.jsonl` a line after the terminal event, which replay would then
  have to interpret. Nothing says whether that is rejected retroactively
  at replay time either. This is exactly the class of guarantee the
  contract already calls out by name for the two adjacent cases
  (`assignment-created` atomicity, `aggregateBounds` freshness) but omits
  here.
- Which requirement it violates: the terminal-and-absorbing invariant
  ("once `transitionSessionStatus` moves a session out of `active` ... no
  further transition ... is ever legal") is about `status` transitions
  specifically; it does not, by its own text, cover a same-instant
  `operation-authorized` append racing a terminal write, and the
  Bug-Taxonomy-adjacent invariant this cell exists to protect
  (driver-gated dispatch must never be bypassable) is left dependent on an
  implementation detail the contract never commits to.
- Smallest fix: one sentence in the `operation-authorized` subsection (or
  a Recovery Rule addendum) requiring the active-status check and the
  `operation-authorized` append to be part of the same atomic/serialized
  write path used for `assignment-created`, and stating that replay must
  treat any `operation-authorized` event appearing after a terminal event
  in `events.jsonl` as invalid/ignored regardless of write-time ordering.

  guarantees no single logical invocation double-dispatches across a

  `maxInvocations` purposes is recomputed from the on-disk

- Which requirement it violates: the acceptance criterion "the

  logically prior guarantee — that the binding cap itself is durably and

  the on-disk `operation-authorized` events for that exact binding (never
