### Assertion 1: Mode-Selection Rule (R2)

- **Source References:**
  - [`docs/architect/agent-coordination/verification/code-panel-multicell-facade/index.md#L48`](file:///home/vantt/projects/code-panel-multicell-facade-p00/docs/architect/agent-coordination/verification/code-panel-multicell-facade/index.md#L48) (Ownership Boundary table, Mode Selection row)
  - [`plans/260915-code-panel-multicell-facade/plan.md#L12-L21`](file:///home/vantt/projects/code-panel-multicell-facade-p00/plans/260915-code-panel-multicell-facade/plan.md#L12-L21) (Mục tiêu section: execution target vs citation/context/edit-target)
  - [`plans/260915-code-panel-multicell-facade/phase-00-contract-and-baseline.md#L13-L18`](file:///home/vantt/projects/code-panel-multicell-facade-p00/plans/260915-code-panel-multicell-facade/phase-00-contract-and-baseline.md#L13-L18)
  - [`plans/260915-code-panel-multicell-facade/phase-01-two-mode-facade.md#L11-L16`](file:///home/vantt/projects/code-panel-multicell-facade-p00/plans/260915-code-panel-multicell-facade/phase-01-two-mode-facade.md#L11-L16)
- **Contract Specification:**
  1. **Direct Single-Cell Selection:**
     - Any request for a concrete code change without a plan execution target selects `direct-single-cell`.
     - **Passing Citation:** A request that merely cites or references a plan or phase path in passing (e.g. *"fix the bug described in plans/260915-foo/plan.md"*) without an execution-target verb directed at the plan is NOT multi-cell; it STAYS `direct-single-cell`.
     - **Plan File as Edit Target (Red-Team Finding A1):** A request like *"fix the typo in plans/X/plan.md"* cites the plan file as the thing being EDITED, not as an execution target — this stays `direct-single-cell`. Matching the rule on the track branch: *"yêu cầu mà plan.md/phase-NN-*.md LÀ execution target (bare path, hoặc có verb run/resume/execute trỏ thẳng vào chính plan/track đó): giao việc cho fgos-plan-loop. Một request chỉ CITE plan path làm context/edit-target (sửa nội dung file plan, hoặc chạy/resume việc khác mà plan chỉ được nhắc tới để cung cấp bối cảnh) vẫn là direct-single-cell — citation không tự động nâng thành execution target"*.
     - **Run/Resume Verb Not Directed at Plan (Red-Team Finding A2):** Requests like *"run the focused tests listed in plans/X/phase-01.md against src/x.mjs"* or *"resume my work on src/auth.mjs, context in plans/X/plan.md"* have a run/resume verb AND cite a plan path, but the verb's actual OBJECT is something else (tests, a source file); the plan is only background context. These stay `direct-single-cell`. Planned mode strictly requires the run/resume/execute verb to be directed AT the plan/phase artifact itself, not merely co-occurring with a plan path while directed at something else.
  2. **Planned Multi-Cell Selection:**
     - Planned mode requires the plan or phase path (`plans/<name>/plan.md` or `plans/<name>/phase-NN-*.md`) to be the **actual execution target** of the request (e.g. bare path `plans/260915-foo/plan.md`), OR
     - The request contains an **explicit run/resume/execute instruction directed AT the plan/phase artifact itself** (e.g. *"run this implementation plan: plans/260915-foo/plan.md"*, *"resume track plans/260915-foo/plan.md"*, *"execute this code implementation track"*).
  3. **Anti-Guessing / Ambiguity Refusal:**
     - Genuinely unresolved or ambiguous user intent (e.g. contradictory directives or multiple unresolvable targets) MUST be refused or prompt the user for clarification.
     - The system must NEVER silently guess or default to either mode.
- **Concrete Expected Outcomes & Tests for Phase 01:**
  - `classifyCodePanelRequest("implement fix for auth bug in src/auth.mjs")`
    - Expected: `{ mode: "direct-single-cell", target: "src/auth.mjs" }`
  - `classifyCodePanelRequest("fix the bug described in plans/260915-foo/plan.md")`
    - Expected: `{ mode: "direct-single-cell", target: "plans/260915-foo/plan.md", role: "passing-citation" }`
  - `classifyCodePanelRequest("fix the typo in plans/260915-foo/plan.md")`
    - Expected: `{ mode: "direct-single-cell", target: "plans/260915-foo/plan.md", role: "edit-target" }` (edit-target test: does not enter planned mode)
  - `classifyCodePanelRequest("run the focused tests listed in plans/260915-foo/phase-01.md against src/x.mjs")`
    - Expected: `{ mode: "direct-single-cell", target: "src/x.mjs", context: "plans/260915-foo/phase-01.md" }` (verb directed at tests, plan is context: stays direct-single-cell)
  - `classifyCodePanelRequest("resume my work on src/auth.mjs, context in plans/260915-foo/plan.md")`
    - Expected: `{ mode: "direct-single-cell", target: "src/auth.mjs", context: "plans/260915-foo/plan.md" }` (verb directed at source, plan is context: stays direct-single-cell)
  - `classifyCodePanelRequest("run this implementation plan: plans/260915-foo/plan.md")`
    - Expected: `{ mode: "planned-multi-cell", planPath: "plans/260915-foo/plan.md" }` (verb directed AT plan itself)
  - `classifyCodePanelRequest("resume track plans/260915-foo/plan.md")`
    - Expected: `{ mode: "planned-multi-cell", planPath: "plans/260915-foo/plan.md" }` (verb directed AT track/plan)
  - `classifyCodePanelRequest("plans/260915-foo/plan.md")`
    - Expected: `{ mode: "planned-multi-cell", planPath: "plans/260915-foo/plan.md" }` (bare path as execution target)
  - `classifyCodePanelRequest("maybe do something with plans/260915-foo/plan.md or fix bar")`
    - Expected: Refusal / throws `AmbiguousIntentError` / prompts for clarification.

### Assertion 2: Delegation Boundary

- **Source References:**
  - [`domains/coding/skills/fgos-code-panel/SKILL.md#L24-L74`](file:///home/vantt/projects/code-panel-multicell-facade-p00/domains/coding/skills/fgos-code-panel/SKILL.md#L24-L74) (Code-panel ownership and non-goals) and [`domains/coding/skills/fgos-code-panel/SKILL.md#L378-L555`](file:///home/vantt/projects/code-panel-multicell-facade-p00/domains/coding/skills/fgos-code-panel/SKILL.md#L378-L555) (Code-panel single-cell lifecycle steps)
  - [`core/skills/fgos-plan-loop/SKILL.md#L21-L52`](file:///home/vantt/projects/code-panel-multicell-facade-p00/core/skills/fgos-plan-loop/SKILL.md#L21-L52) and [`core/skills/fgos-plan-loop/SKILL.md#L97-L510`](file:///home/vantt/projects/code-panel-multicell-facade-p00/core/skills/fgos-plan-loop/SKILL.md#L97-L510) (Plan-loop track coordination loop)
- **Contract Specification:**
  1. When in `planned-multi-cell` mode, `fgos-code-panel` MUST delegate track execution to `fgos-plan-loop`'s driver **exactly once** per track invocation.
  2. `fgos-code-panel` MUST NOT contain or execute any multi-cell track orchestration logic (such as auditing track-level preconditions, looping across multiple cells with `chain.mjs`, or sequencing cell transitions); all multi-cell progression belongs exclusively to `fgos-plan-loop`.
  3. In `planned-multi-cell` mode, `fgos-code-panel`'s responsibility is strictly bounded to:
     - Recognizing user input and selecting `planned-multi-cell` mode.
     - Materializing the 3-tier coding test-policy overlay (`FOCUSED_TESTS`, `AFFECTED_TESTS`, `FULL_TEST`, `FULL_TRIGGERS`).
     - Invoking `fgos-plan-loop` with the plan target and policy overlay.
  4. `fgos-plan-loop` remains the sole, generic owner of multi-cell track execution and contains no coding-domain branches (`trackKind: code`).
  5. In `direct-single-cell` mode, `fgos-code-panel` legitimately executes its single-cell coordination cycle once directly through `CoordinationSession`.
- **Concrete Expected Outcomes & Tests for Phase 01:**
  - Delegation Test 1: In `planned-multi-cell` mode, execution spy on `fgos-plan-loop` verifies it is invoked with `{ planPath, testPolicyOverlay }` exactly once.
  - Delegation Test 2: In `planned-multi-cell` mode, spy on coordination CLI doors (`fgos coordination run`) verifies that zero multi-cell orchestration requests originate from `fgos-code-panel`.
  - Delegation Test 3: `fgos-plan-loop` accepts the coding policy overlay without requiring changes to generic plan schemas.

### Assertion 3: No-Duplication Rule (Red-Team Finding B1)

- **Source References:**
  - [`domains/coding/skills/fgos-code-panel/SKILL.md#L378-L565`](file:///home/vantt/projects/code-panel-multicell-facade-p00/domains/coding/skills/fgos-code-panel/SKILL.md#L378-L565) (Legitimate single-cell coordination steps)
  - [`core/skills/fgos-plan-loop/SKILL.md#L97-L510`](file:///home/vantt/projects/code-panel-multicell-facade-p00/core/skills/fgos-plan-loop/SKILL.md#L97-L510) (The canonical multi-cell track driver loop)
  - [`test/architecture.test.mjs`](file:///home/vantt/projects/code-panel-multicell-facade-p00/test/architecture.test.mjs) (Architecture invariant enforcement)
  - [`test/setup/skill-wrappers.test.mjs`](file:///home/vantt/projects/code-panel-multicell-facade-p00/test/setup/skill-wrappers.test.mjs) (Skill projection and wrapper consistency)
- **Discriminator Rationale (Invalid Token Ban Replaced):**
  - Prohibiting individual tokens such as `disposition: "cell-closed"`, `type: "authorize"`, `open.json`, `fix-*.json`, or `close.json` is **invalid**: `fgos-code-panel`'s legitimate `direct-single-cell` mode already contains all of these (`domains/coding/skills/fgos-code-panel/SKILL.md:544` and ~15 other occurrences), because single-cell code-panel dispatches through the exact same underlying `CoordinationSession` engine and `standalone-master-coordination-loop` protocol once for its single code change.
  - A test built on "these tokens must never appear" either fails on the unmodified baseline or can never detect a real violation.
  - The true architectural boundary is **multi-cell track sequencing**: driving more than one cell in a loop of code-panel's own (e.g. code-panel's own source containing a loop or iteration construct over multiple `fgos coordination chain`, `activeCell`, or "next cell" resolutions within a single `fgos-code-panel` invocation). That is the unique signature of reimplementing `fgos-plan-loop`'s cell-sequencing engine.
- **Contract Specification:**
  1. A static architecture test MUST fail if `domains/coding/skills/fgos-code-panel/SKILL.md` (or any generated projection under `.agents/`, `.claude/`, or `plugins/`) grows a duplicate copy of `fgos-plan-loop`'s multi-cell sequencing loop.
  2. Prohibited multi-cell orchestration constructs in `fgos-code-panel` source:
     - Any loop or iteration construct over multiple `fgos coordination chain`, `activeCell`, or "next cell" resolutions within a single `fgos-code-panel` invocation (the actual signature of reimplementing `fgos-plan-loop`'s own cell-sequencing logic).
     - Defining a multi-cell iteration template or state-machine loop that sequences from a closed cell to open a successor cell.
     - Parsing track-level `plan.md` cell lists or phase tables to manage multi-cell progression.
  3. Preserved single-cell usage:
     - Single-cell mode executes exactly one cell lifecycle for a standalone change, legitimately using coordination run doors once (`open.json`, `fix-*.json`, `close.json` with `disposition: "cell-closed"`, `authorize`).
- **Concrete Expected Outcomes & Tests for Phase 01:**
  - Static Test 1: Architecture test parses `domains/coding/skills/fgos-code-panel/SKILL.md` and asserts absence of multi-cell looping constructs (e.g. regex/AST verification ensuring no while/for loops over `fgos coordination chain` or `activeCell` cell transitions exist).
  - Mutation Test 2: Mutation test verifies that injecting a multi-cell cell-sequencing loop (e.g. a `while` loop re-invoking `fgos coordination chain` and opening successor cells upon cell close) into `domains/coding/skills/fgos-code-panel/SKILL.md` causes `npm test` / `test/architecture.test.mjs` to fail with:
    `MultiCellSequencingDuplicationError: fgos-code-panel must delegate multi-cell orchestration to fgos-plan-loop, not loop over coordination chain/cells`.
    Conversely, the unmodified baseline containing legitimate single-cell coordination steps (`open.json`, `disposition: "cell-closed"`, `authorize`) passes cleanly without false positives.
