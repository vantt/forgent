- **Contract Specification:**
  1. **Direct Single-Cell Selection:**
     - Any request for a concrete code change without a plan execution target selects `direct-single-cell`.
     - **Passing Citation:** A request that merely cites or references a plan or phase path in passing (e.g. *"fix the bug described in plans/260915-foo/plan.md"*) without an execution-target verb directed at the plan is NOT multi-cell; it STAYS `direct-single-cell`.
     - **Plan File as Edit Target (Finding A1):** A request like *"fix the typo in plans/X/plan.md"* cites the plan file as the thing being EDITED, not as an execution target — this stays `direct-single-cell`. Matching the rule on the track branch: *"yêu cầu mà plan.md/phase-NN-*.md LÀ execution target (bare path, hoặc có verb run/resume/execute trỏ thẳng vào chính plan/track đó): giao việc cho fgos-plan-loop. Một request chỉ CITE plan path làm context/edit-target (sửa nội dung file plan, hoặc chạy/resume việc khác mà plan chỉ được nhắc tới để cung cấp bối cảnh) vẫn là direct-single-cell — citation không tự động nâng thành execution target"*.
     - **Run/Resume Verb Not Directed at Plan (Finding A2):** Requests like *"run the focused tests listed in plans/X/phase-01.md against src/x.mjs"* or *"resume my work on src/auth.mjs, context in plans/X/plan.md"* have a run/resume verb AND cite a plan path, but the verb's actual OBJECT is something else (tests, a source file); the plan is only background context. These stay `direct-single-cell`. Planned mode strictly requires the run/resume/execute verb to be directed AT the plan/phase artifact itself, not merely co-occurring with a plan path while directed at something else.
     - **Negation Honored (Finding CE2):** Negation must be accounted for before matching any verb. A request like *"don't run plans/X/plan.md yet, just fix src/foo.mjs"* is `direct-single-cell`, not planned-multi-cell, even though a naive 'run/resume verb + plan path' match would misfire.
     - **Non-Execution / Inspection Verbs at Plan (Finding CE4):** A plan or phase path with a read-only or inspection verb (e.g. *"review plans/X/plan.md"*, *"explain plans/X/plan.md"*, *"summarize plans/X/plan.md"*) and no run/resume/execute verb stays `direct-single-cell` (`code-panel` treats it like reading any other file), and does not need `plan-loop`.
  2. **Planned Multi-Cell Selection:**
     - **Plan/Phase Path as Execution Target:** Planned mode requires the plan or phase path (`plans/<name>/plan.md` or `plans/<name>/phase-NN-*.md`) to be the **actual execution target** of the request (e.g. bare path `plans/260915-foo/plan.md`), OR the request contains an **explicit run/resume/execute instruction directed AT the plan/phase artifact itself** (e.g. *"run this implementation plan: plans/260915-foo/plan.md"*, *"resume track plans/260915-foo/plan.md"*, *"execute this code implementation track"*).
     - **Track Referenced by Name Without Path (Finding CE1):** A track referenced BY NAME with no path at all plus a run/resume/open verb (e.g. *"resume the <track> track"*, *"open the next cell for <track>"*) IS `planned-multi-cell`. The track name resolves to `plans/<name>/plan.md` or a registered coordination track. (Closes the gap where the rule previously had no legal output for pathless track names).
     - **Plans Outside `plans/` Directory (Finding CE5):** The `plans/<name>/plan.md` path-shape heuristic is a fast-path convenience, not the sole test: an explicit run/resume/execute instruction naming ANY `plan.md` or `phase-NN-*.md`-shaped file, wherever located (e.g. *"run this plan: docs/platform/packaging-distribution/code-panel-rollout-plan.md"*), is `planned-multi-cell`. Only a BARE, unqualified file reference with no run/resume/execute verb needs the `plans/` path-shape to be treated as an implicit execution target (reconciling with the bare-path rule).
     - **Phase Path Target Interaction with Chain (Finding CE3):** When a request names a specific PHASE path as execution target (e.g. *"run phase-01 of plans/X"*), the phase selection must NOT be silently dropped when handing off to `fgos-plan-loop`. Because `fgos-plan-loop`'s own chain-based entry point always resolves to 'the lowest phase with no merged row' regardless of what phase was named, the rule derives the track from the phase path and lets plan-loop determine the real next phase, **refusing (not silently overriding)** if the named phase disagrees with what `chain` would actually open next.
  3. **Anti-Guessing / Ambiguity Refusal:**
     - Genuinely unresolved or ambiguous user intent (contradictory directives, unresolvable targets, or named phase disagreement under CE3) MUST be refused or prompt the user for clarification.
     - The system must NEVER silently guess or default to either mode.
