## `tsk-1bh` fix (commit `9af6362c`)

Two sub-bugs in `src/runner/coordination/session-engine.mjs`, both
confirmed live in this track's own history:

1. **`resolveBindingAuthorization`** always returned the OLDEST unconsumed
   authorization for a binding. An earlier authorization orphaned by a
   refused dispatch (e.g. a `contextRefs` grant violation, before
   `createSessionAssignment`) stayed unconsumed forever, so every future
   dispatch attempt at that binding kept resolving back to the same dead
   authorization — a corrected retry (a fresh authorization) was
   permanently unreachable. Fixed: prefer the newest unconsumed
   authorization (`findLast` instead of `find`).
2. **`classifySessionQuorum`'s ungated-actor fallback** classified an
   actor's completion by the FIRST `assignment-created` event alone. A
   later, genuinely successful re-attempt at the same binding (after a
   failed/no-evidence first attempt, under a fresh authorization) could
   never un-stick a `failed` classification, so `closeSessionByQuorum`
   refused forever even after real, verified work landed. Fixed: walk
   every attempt in event order, crediting the first satisfied one.

## Review round 1 recheck (dispatched against commit `aa328e70`)

Independent recheck (`op_005` reviewer, `op_006` red-team). Both
confirmed the fix and both surfaced ONE further real finding each:

- **Reviewer**: confirmed all three recheck items by real execution and
  mutation testing (reverting `findLast`→`find` on each function
  independently reproduced the exact pre-fix failures); 838/838 pass. One
  NEW residual **MEDIUM**, explicitly flagged as pre-existing (not
  introduced by this cell): an orphaned authorization is never retired —
  once its newer siblings are all consumed, it becomes the SOLE unconsumed
  authorization again, so a keyless re-dispatch with no fresh authorization
  spends the stale orphan and mints a duplicate Assignment instead of
  idempotently resuming the last consumed one. **Dispositioned `deferred`**
  in `close.json`'s rationale (see below) — real, correctly diagnosed, but
  outside this cell's scope and not a blocker; filed for a future engine
  cell, recommended direction: treat a newer already-consumed authorization
  as superseding any older unconsumed sibling, in both resolvers.
- **Red-team — NEW HIGH**: `classifySessionQuorum`'s fallback scoped
  same-binding retries by raw `assignment-created.payload.operationId`/
  `nodeId` equality, reasoning "only `dispatchDeclaredOperation` ever
  writes them." **That reasoning was wrong**: `createSessionAssignment`
  (store.mjs) is an exported raw door that accepts a caller-supplied
  `authorizationProvenance` object directly, and only verifies its fields
  MATCH a real, already-issued, unspent authorization — never that the
  call passed through `dispatchDeclaredOperation`'s own gate. A caller
  holding a genuine, freshly-authorized `(nodeId, operationId)` for a
  binding could spend it through the raw door with an entirely unrelated
  inline contract, complete it, and have the fallback credit that
  unrelated result as the retry.

**Fixed in commit `7b0af304`**: the fallback now scopes same-binding
retries through `assignmentServesOperation` (the same reserved
`protocol-operation:` contract-stamp predicate `resolveBindingOutcome`
already uses for the gating path), never raw payload-field equality. That
stamp is written unconditionally on `dispatchDeclaredOperation`'s own
common path, and `assertNoReservedOperationStamp` refuses any
caller-supplied entry in that reserved namespace on every door, including
the raw one — so the raw-door attack can still forge the EVENT payload
fields and legitimately spend a real authorization, but can never produce
an Assignment carrying the actual reserved stamp. A new regression test
reproduces the red-team's exact attack sequence (raw
`createSessionAssignment` spending a real, matching, fresh authorization
for the same binding with an unrelated task), independently confirmed to
fail against the pre-fix payload-field check.
