existing, already-proven-live 1:1 consult protocol from Phase 03/P04.2b),
dispatched through both doors with distinct `coordinationId`s: the real
CLI (`node bin/fgos.mjs coordination run`, a genuine subprocess) and the
headless adapter (`runCoordinationHeadless`, in-process). Full envelope
+ full on-disk persisted state (manifest, events.jsonl, every Assignment/
Run/RunResult/evidence file) diffed with an explicit, individually-
justified allowlist of volatile fields (timestamps/durations/pid,
positionally-normalized ids, the events-log hash-chain field, ambient
git-dirty snapshot, live-report-content sha256 — with the adjacent
`path` field on the same entry deliberately left un-normalized and
confirmed to match exactly). Result: **`diffCount: 0`**. A negative case
(unknown-field request) through both doors produced byte-identical
`StoreError` message + exit-category before any state was persisted on
either side. A real friction (non-canonical `agent-result.json` status)
hit identically on both doors — reported honestly as shared,
door-independent friction, never hidden or fabricated as success.

**Round 1 gap (Reviewer, MEDIUM) → Round 2 fix (Fixer, re-verified by
both the Coordinator and Red-Team):** the original `timeoutMs`
volatile-field allowlist entry referenced a nonexistent "notes below"
justification and was broader than the actual data required — every
`timeoutMs` value observed in the captured run was a static, config/
fixture-derived value (never a live-computed deadline), so it should
diff exactly like `aggregateBounds` already correctly did. Fixed by
removing it from the allowlist entirely; re-diffing against the
already-captured state still yields `diffCount: 0`, now via genuine
non-normalized equality (values `300000`/`2100000` on both doors,
neither the executor's own `900000` hardcoded fallback) rather than an
unexplained exemption. Red-Team additionally traced the diff algorithm
itself on paper and confirmed no presence-asymmetry or type-coercion
blind spot could mask a real mismatch.
