## R8: STOP GATE #4 (objective, plan-named, independently confirmed)

### Root cause (independently verified by the Coordinator, not just the Doer's report)

`resolveAssignmentDispatchPolicy` (`src/runner/dispatch/assignment-policy.mjs:92`):
```js
let effectiveTier = opPolicy.minTier || 'standard';
```
This is an UNCONDITIONAL floor -- `cliOverride`/`work.tier`/governance can
only RAISE it (`resolveStrongerTier`), never lower it below `'standard'`.
`opPolicy` is `assignment.policy`. Traced `buildInlineAssignment`
(`src/runner/dispatch/assignment.mjs`, ~line 481 onward): `contract.policy`
is populated ONLY when a domain harness seam fires
(`...(harnessPolicy ? { policy: harnessPolicy } : {})`), which itself
requires a resolvable `domain` off a Work object with a `.stage` --
standalone CoordinationSession dispatch (agent-led AND declared, this
entire track's whole subject) never attaches a Work/stage, so
`harnessSeam` never fires, so `contract.policy` (and therefore
`assignment.policy`/`opPolicy`) is NEVER populated for ANY coordination
dispatch, ever. Confirmed independently: `grep -n "policy" src/runner/dispatch/execution-contract.mjs`
and `INLINE_ASSIGNMENT_PARAM_WHITELIST` in `assignment.mjs` both show no
`policy` field exists on the inline-contract surface at all.

**Consequence**: every coordination dispatch (agent-led or declared,
Phase 01 through this cell) has always resolved to AT LEAST `'standard'`
tier, unconditionally. The real `.fgos/config.json` only configures
`lightweight` for `gemini`/`openai-codex`/`z-ai` (confirmed, unchanged
since P00.4/P03.2's own discovery of this same config shape) -- meaning
NONE of them can ever satisfy the unavoidable `'standard'` floor. This
reframes P00.3's and P03.2's own prior "codex-cli/glm-cli live-executor
timeout / config-tier gap" findings: the real root cause was always this
SAME architectural floor, not merely an incomplete `modelPolicies`
config (a config change alone cannot fix this -- the floor is
unconditional in code, not a missing config value).

### Why this is not fixable within this cell (or without a maintainer decision)

The only fix path (recorded by the Doer, independently assessed as
correct by the Coordinator): add a `policy` field to
`execution-contract.mjs`'s inline-contract field whitelist and
`assignment.mjs`'s `INLINE_ASSIGNMENT_PARAM_WHITELIST`, so a declared
CoordinationProtocol operation's own `spec.operations[].policy.minTier`
can populate `assignment.policy` and lower the floor below `'standard'`
for a genuinely `lightweight`-only provider family. **Both files have
been in this entire track's "Do Not Touch" list for EVERY cell across
all 4 phases so far** -- this is a deliberately protected, high-blast-
radius surface (the inline-contract whitelist is precisely what prevents
e.g. arbitrary executor/model pinning from an inline dispatch). Widening
it is a real, cross-cutting schema/security-relevant decision this track
has never delegated to a cell's own "routine implementation choice"
scope, and touching it here would be exactly the kind of silent scope
expansion into a locked-down file this whole track's discipline has
consistently avoided (every prior cell that considered touching a
protected file stopped and reported instead, e.g. P03.1/P03.2's explicit
"if you find you need to touch X, stop and report" instructions, which
