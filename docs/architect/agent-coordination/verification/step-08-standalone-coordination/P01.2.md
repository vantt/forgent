# Cell P01.2 — Session engine, dynamic consult, resume, live proof (Phase 01 R5-R8)

## Requirements

- R5 Session engine: one entry point accepting a validated standalone
  request, creating/resuming a session, materializing bounded inline
  contracts, calling only `buildAssignment()`/`executeAssignment()`,
  recording canonical refs/results. Injected executor in tests; governed
  Assignment runner in production, never direct spawn.
- R6 Dynamic consult: primary actor proposes exactly one specialist actor
  plus one consult task while running. Foundation validates role,
  objective, read-only mutation, evidence requirement, context visibility,
  aggregate bounds, `parentAssignmentId`, one request/response round —
  before creating it. No protocol id or predeclared graph required.
- R7 Resume/idempotency: on restart, reconstruct pending/completed logical
  tasks from persisted refs; never duplicate a claimed Assignment or rerun
  a completed result. Created-without-ref crash reconciled by exact
  claimed logical task/Assignment identity, not timestamp. Ambiguous
  foreign state fails closed with a recoverable diagnostic.
- R8 Agent-led proof: interactive coordinator + real `cli-spawn` workers,
  primary-investigator read-only session requesting one bounded
  reviewer/specialist consult. Record manifest/events/Assignment/Run/
  RunResult/evidence; prove no Work, Workflow, Stage, TaskSpec, protocol,
  Mission, direct executor call, or repository mutation exists.

### HIGH — `proposeConsult`'s "exactly one specialist actor, ever" invariant is a TOCTOU race across two processes: two different specialists can both be bound and both dispatched to the same session, silently

R6 (and this module's own header comment, `session-engine.mjs:20-26`)
states the invariant in absolute terms: "one request/response round = at
most ONE specialist actor, ever, bound to a given session." The Doer's own
report frames the sequential case (a third actor proposed *after* the
first specialist completes) as "the single most important thing" this
cell fixed, and that sequential case is genuinely correct — traced
`validateConsultProposal` (`session-engine.mjs:364-379`): `existingSpecialists`
is read, and `conflictingSpecialist = existingSpecialists.find(actor =>
actor.id !== specialistActorId)` correctly rejects ANY specialist id other
than one already bound, at any time after that binding exists, including
after the session's only specialist Assignment has completed. No bug there.

But the check that enforces this ("no specialist bound yet, or the SAME
one resuming") and the mutation that actually binds a new specialist
(`bindActor`, called later in `proposeConsult`, `session-engine.mjs:470-473`)
are NOT one atomic critical section. `validateConsultProposal` reads state
via an unlocked `replaySession()` call; the eventual `bindActor()` call is
a *separate*, later `withEventsLock`-protected write whose own atomicity
check only guards against re-binding the *same* actor id
(`store.mjs:225-227`: `existingActors.some((a) => a.id === actor.id)`) —
it never re-checks "does any OTHER non-primary actor already exist" under
the lock. Two callers (realistically: two separate OS processes/
coordinators both driving the same on-disk session — a real, supported
scenario per this repo's own out-of-process dispatch model, not a
contrived one) proposing consults for two *different* `specialistActorId`
values can both pass `validateConsultProposal` before either has bound
anything, then both successfully call `bindActor` for their own distinct
id. Nothing anywhere downstream catches this either: `schema.mjs`'s
`validateManifest` only rejects a *duplicate* actor id, never a second
non-primary actor (confirmed by reading `schema.mjs`'s actor-validation
block, `schema.mjs:200-206` — no count/role-arity check exists), and
`aggregateBounds.maxAssignments` defaults to 20 (`schema.mjs`'s
`DEFAULT_AGGREGATE_BOUNDS`), far above the 3 Assignments (primary + 2
consults) this scenario produces, so it never trips either.

Reproduced directly (not hypothetically) using only the module's own
exported functions, manually interleaving the two callers' operations in
the exact order two racing processes would produce (open a session,
dispatch the primary, then call `validateConsultProposal` for
`specialist-A` and `specialist-B` back-to-back — both pass — then
`bindActor` for both back-to-back — both succeed):

```
--- Step 1: both callers validate BEFORE either binds ---
validateConsultProposal(A) passed
validateConsultProposal(B) passed -- BOTH validations passed with no specialist bound yet
--- Step 2: both callers now bind their own actor id ---
bindActor(A) succeeded
bindActor(B) succeeded
--- Final manifest.actors ---
[
  { "id": "primary", "role": "researcher" },
  { "id": "specialist-A", "role": "reviewer" },
  { "id": "specialist-B", "role": "reviewer" }
]
BUG CONFIRMED: more than one specialist actor bound to the session
```

Because each specialist id has its own distinct `taskKey`
(`consult:specialist-A` vs `consult:specialist-B`), this is not merely a
phantom actor-registry entry — a real second `proposeConsult` call for
`specialist-B` would proceed straight through `createAndExecuteSessionTask`
and genuinely dispatch a second, independent consult Assignment/Run, fully
violating "primary actor proposes exactly one specialist actor plus one
consult task" end to end, with no error raised anywhere.

Note this is *not* reachable via same-process `Promise.all` concurrency —
`validateConsultProposal`, `readManifest`, and `bindActor` are all
synchronous (no internal `await`; `withEventsLock`'s own retry loop uses a
blocking `sleepSync`, confirmed in `state/events.mjs:361-390`), so within
one Node process the entire check-then-bind sequence for one
`proposeConsult` call runs to completion before the event loop can hand
control to a second concurrent call. The race is real only across two
separate processes/executors — which is exactly the shape a resumed/
retried coordinator (R7's own scenario) or two independent supervisors
driving the same `coordinationId` would produce.

Smallest fix direction: make the "no conflicting specialist" check part of
the SAME locked critical section as the bind, mirroring how
`createSessionAssignment` already re-checks state under its own
`withEventsLock` before writing. Concretely: give `bindActor` (or a new,
specialist-specific atomic door) an optional invariant check that runs
against the freshly-read, lock-held manifest immediately before the
`existingActors.some(...)` duplicate-id check — e.g. reject if any
existing non-primary actor id differs from the one being bound — so the
"only one specialist ever" rule is enforced at the one place that
actually mutates `manifest.actors`, not only at an earlier, unlocked read.
Add a regression test that manually interleaves two `proposeConsult`
callers for different `specialistActorId`s the same way this reproduction
does (real concurrency is not required to prove the fix — the interleaved-
call-order technique above is sufficient and deterministic).

### MEDIUM — a genuine cross-process race on the SAME `specialistActorId` silently substitutes the winning caller's role/objective/contract for the losing caller's, with no `CoordinationError`, when the fix's own doc comment says this exact case "is rejected"

`session-engine.mjs`'s module header (lines 19-26) and
`validateConsultProposal`'s own inline comment (lines 364-371) both state
the resume rule in absolute terms: "a resume that names the same actor id
but a DIFFERENT role is a genuine conflict, not a retry, and is rejected."
That rejection is real for a SINGLE process calling `proposeConsult` twice
(each call re-runs `validateConsultProposal` fresh, line 467, which does
catch a stale role). It is NOT real across two processes, because
`proposeConsult`'s own body (`session-engine.mjs:449-499`) does two
SEPARATE unlocked reads of session state before deciding whether to call
`bindActor` at all:

1. `validateConsultProposal(...)` (line 467) — reads via `replaySession()`.
2. `const manifest = readManifest(...)` (line 469) — a second, independent,
   unlocked read, used only to compute `alreadyBound`
   (`session-engine.mjs:470`).

If read #1 (for caller C, proposing `specialistActorId: 'specialist'`,
`role: 'advisor'`) happens to run BEFORE another process, caller A, commits
its own full `proposeConsult('specialist', role: 'reviewer')` sequence, but
read #2 happens AFTER A's commit, then: C's `alreadyBound` is `true`, so
`session-engine.mjs:470-471` SKIPS `bindActor` entirely — the exact door
this cell's own HIGH fix protects. C proceeds straight to
`createAndExecuteSessionTask` → `createSessionAssignment`
(`store.mjs:392-477`) with the SAME `taskKey` (`consult:specialist`) A
already claimed. `createSessionAssignment`'s taskKey-collision path
(`store.mjs:409-439`) does not compare the caller's freshly-built
`contract`/`actorId` against what is already claimed at all — for ANY
caller, race or not — it simply returns the FIRST caller's existing
Assignment unchanged. So C's own `proposeConsult('specialist', role:
'advisor')` call returns SUCCESSFULLY (no thrown error, `resumed: true`)
with an Assignment whose actual bound role is `"reviewer"`, not the
`"advisor"` C asked for — and C has no signal anything went wrong.

This is the identical bug CLASS as the already-fixed HIGH (unlocked
read-then-decide, raced by a second real process, with the fix scoped to
`bindActor` only) but reaches a DIFFERENT, unprotected code path: whenever
`alreadyBound` is already `true` by the time `proposeConsult` checks it,
`bindActor` — and therefore the HIGH fix's new invariant check — is never
called at all.
