## What R1-R4 implement

- **R1**: `fgos coordination run --file <request>` (synchronous in V1)
  and `fgos coordination show <id> --json` (read-only), one registered
  verb with two sub-verbs, mirroring `merge`'s existing sub-verb
  dispatch. Both return the SAME `fgos.v1` envelope every other real
  verb uses (`src/state/envelope.mjs`'s `wrapEnvelope`, not a parallel
  shape) and the SAME `EXIT_CODES`/`categoryOf` contract. Global trusted
  `--executor`/`--model`/`--tier` apply unless a per-actor override is
  declared in the request file. Two real engine constraints discovered
  and correctly surfaced as explicit refusals (never silently dropped):
  `--model` has no channel for `kind:"declared-protocol"` dispatch
  (`dispatchDeclaredOperation`'s `cliOverride` carries no `model` field);
  fan-out-branch actors accept no per-actor policy override
  (`dispatchResearchFanOut` accepts no caller policy at all — cohort
  planner owns allocation exclusively).
- **R2**: `validateCoordinationRequest` — every reject category from the
  phase text has its own dedicated check: unknown fields at every
  nesting level (`assertAllowedKeys`), portable concrete infra
  (`protocolRef` may only carry `{id}`), unregistered actor overrides,
  actor-role rewrites (hard `if ('role' in actor)` rejection),
  undeclared actor multiplicity (`Set`-based duplicate detection at both
  the top-level `actors[]` and per-fan-out-branch level), mutation
  forced to `'read-only'` everywhere, a recursive Work-lifecycle-key
  scan over the whole raw request before any narrowing, a path-escape
  charset guard reusing the same pattern `session-engine.mjs`'s
  `assertSafeCoordinationId` already established, and CLI/file conflicts
  on `executor`/`model`/`tier` with a distinct, named message.
- **R3**: real command registry entry (`touchesState`/`externalEffect`
  flags, JSON-Schema params, examples — `--help --json` works
  generically once registered), a real doctor check
  (`coordination-example-requests-valid`, registered via `registerCheck`,
  validating the 4 published examples), 4 real example request files
  built from the real, already-committed protocol yamls, an end-user
  how-to registered into the real docs index generator (not
  hand-edited), and minimal targeted diffs to the architecture manifest/
  reading map/runner spec/distribution spec/io-contract/CHANGELOG.
- **R4**: `runCoordinationHeadless` calls `runCoordinationUseCase`
  DIRECTLY — the exact same function the CLI's own dispatch calls, never
  a forked copy. Proven two ways: a runtime reference-identity assertion
  and a static test that reads the adapter's actual source, extracts the
  import specifier, and resolves it to confirm it's literally the same
  file (mirroring `coordination-static.test.mjs`'s own precedent for
  proving "one execution core").

## Review history

**Doer → Reviewer**: the Reviewer genuinely attacked the R2 trust
boundary with 12 distinct adversarial constructions (nested Work-
lifecycle keys inside arrays-of-arrays, unknown fields at every nesting
level, duplicate actor ids at both top-level and per-branch, `..`/
`%2f`-encoded/backslash path-escape attempts in every id-shaped field,
`__proto__` as an actor id, forward-referencing `$ref:` to an
undispatched step, and both documented engine-constraint refusals) and
**found no bypass** — independently re-verified by the Coordinator
reading the exact validated functions and the `$ref` scoping logic
before accepting the clean result. This is the first cell since Phase 06
opened where a genuine adversarial pass found the underlying trust-
boundary CODE already correct on the first attempt.

The Reviewer did find and precisely root-cause a real, confirmed content
defect (not a security bug): every `expectedOutputs` entry across all 4
published example request files named ONLY `agent-result.json` content,
never a companion report artifact — and `classifyRunEvidence`
(`assignment-runner.mjs`, pre-existing, unrelated-to-this-cell logic)
requires exactly such a companion artifact for a read-only operation to
ever reach `confidence: 'reported'`. This meant all 4 examples would
deterministically produce `no-evidence` and never close against ANY
real, honest, fully-compliant executor — not the "live-executor
non-determinism" both the Doer and the Coordinator had assumed from an
earlier live-run observation. Independently re-verified by the
Coordinator: read `classifyRunEvidence`'s exact companion-artifact
requirement, confirmed all 4 files' `expectedOutputs` content directly.
Also flagged 3 real trust-boundary checks (declared-protocol
unregistered-actor-override, fan-out per-branch policy-override refusal,
fan-out-branch duplicate-actor-id) that were genuinely enforced but had
zero dedicated negative-test coverage.

**Fixer**: added a companion `agent-report.md` instruction to every
read-only step's `expectedOutputs` across all 4 example files (reusing
the exact phrasing convention already proven live in P01.2's own live-
proof driver script), and added the 3 missing negative tests. Live
re-ran 3 of the 4 examples against real executors: `evidence.json`
confirmed the companion artifact is now genuinely produced in every
case (the original no-evidence failure mode is gone); a separate,
orthogonal, pre-existing issue surfaced instead on some runs — a real
executor occasionally writes a non-canonical `agent-result.json` status
string (e.g. `"success"` instead of `"done"`), which `classifyRunEvidence`
correctly fails closed on (`claimInvalid` → `{status:'failed',
confidence:'failed'}`) rather than silently accepting — this is the
same class of live-executor output-format friction already documented
elsewhere in this track (P05.2's own Gaps section) and is explicitly
out of this cell's scope to chase further.

**Coordinator's own independent close-out verification**: read the
fixed `agent-led-request.json` directly (confirmed the companion-
artifact string was added correctly); live re-ran
`declared-consult-request.json` myself against the real engine —
`evidence.json` for the one step that settled `failed` confirms BOTH
`agent-report.md` and `agent-result.json` were genuinely produced
(`artifacts: [...both valid: true...]`), with `agentClaim: null`
matching the exact `claimInvalid`-fail-closed path (the same orthogonal
vocabulary issue the Fixer already found, not a re-manifestation of the
original bug). Cleaned up the live-test session artifacts afterward (no
tracked file was touched by the live runs — confirmed via `git status`
before writing this file).

**Disposition: no separate Red-Team round dispatched for this cell.**
Reasoning: the actual trust-boundary CODE (schema.mjs/run.mjs/headless-
adapter.mjs) already received a genuine, thorough adversarial pass from
the Reviewer and held clean — that is the exact rigor level every
Phase 06 cell needed a dedicated Red-Team round to reach only after 1-2
Fixer rounds. The Fixer round in THIS cell touched only JSON content

to any file the Reviewer's adversarial pass already covers. This matches
