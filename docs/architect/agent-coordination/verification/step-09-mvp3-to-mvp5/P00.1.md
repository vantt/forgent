### Assignment provenance shape (recheck-as-new-Assignment `taskKey` derivation)

- Contract text (`coordination-session.md:232-241`, "Recheck Is Not
  Retry"): a recheck's `taskKey` "MUST incorporate the new artifact/
  evidence revision or the authorizing `invocationKey`/`authorizationId`,
  so it can never collide with... the original reviewing Assignment's own
  `taskKey`."
- Implementation (`index.md` P03.1 CLOSED, lines 258-266): "recheck as a
  genuinely new Assignment via a ROOT-CAUSE fix to the default `taskKey`
  derivation (`declared:<op>[:round-N]:auth:<authorizationId>`, both
  taskKey branches), closing the gap P02.2 deliberately deferred."
- Known residual edge (`index.md:568-578`, P03.1's Red-Team Target 3,
  carried forward as a P03.2 precondition, not fixed): a caller who
  deliberately supplies the literal unsuffixed default key
  (`declared:<operationId>`) via an explicit `taskKey` can still cause a
  later keyless ambiguous-repeat call to land on that claim. Reachable only
  when a caller supplies that exact string; `src/verbs/coordination/
  run.mjs` forwards an optional `step.taskKey` — later phases must not
  reuse that literal string as a "default" sentinel.

### Context grant behavior (enforcement point, scope-check semantics)

- Contract text (`coordination-session.md:205-217`, "Context-Grant
  Enforcement"): "A dispatched worker for a driver-authorized operation may
  read only the refs listed in that authorization's `grantedContextRefs`...
  Every `grantedContextRefs` entry must resolve to an artifact/ref owned by
  this same `coordinationId`."
- Implementation (`index.md` P02.2 CLOSED, lines 207-213): "context-grant
  enforcement as a real gate inside the dispatch path (not advisory)."
- Fix history worth knowing: the grant-scope check was originally

  again by Red-Team from a naming-CONVENTION check to an existence-based
  check mirroring the `asgn_` half (index.md:232-244, MEDIUM-2).

### Artifact ref behavior (linked-not-copied; recheck-lineage limitation)

- `index.md` P03.1 CLOSED (line 258-259): "Artifact refs linked (not
  re-stored) through the existing RunResult/evidence path."
- Contract scope statement (`coordination-session.md:27-31`): the contract
  "does not add any field to Assignment, Run, or RunResult... Assignment
  stays session-blind" (ADR-008).
- **Exact limitation to quote, not paraphrase**
  (`index.md:491-500`, P03.1's Review MEDIUM-3, carried forward
  verbatim as a P03.2 precondition and still true — nothing in P03.2 or
  later extended this): "recheck lineage in `replaySession`'s return shape
  is artifact-revision-scoped and best-effort, not a guaranteed
  original→recheck edge... The
  `assignments[].authorizationId → authorizations[].targetArtifactRef`
  join is the only link replay reconstructs, and `targetArtifactRef` is
  OPTIONAL on `operation-authorized` — omit it and replay carries no link
  at all. There is no actual original-Assignment → recheck-Assignment
  pointer in the shape." `thin-launcher-surface-readiness.md:84-88`
  restates the same limitation for any future renderer: "A renderer must
  not present it as one."

### Bounds behavior

- `activation.maxInvocations` (`flow-definition.md:104`): "Optional
  per-binding invocation cap. It only NARROWS usage at that one binding —
  it can never widen `aggregateBounds.maxAssignments`,
  `aggregateBounds.maxRounds`, or `aggregateBounds.maxConcurrency`... The
  binding's consumed-invocation count is counted fresh from the on-disk
  `operation-authorized` events for that exact binding (never from
  in-memory state)." As frozen above, no binding in the shipped fixture
  currently declares this field.
- Session-wide `aggregateBounds` (`coordination-session.md:69`): hard
  limits `{wallTimeMs, maxAssignments, maxConcurrency, maxRounds,
  maxTaskDepth}`, "enforced uniformly... never bypassable by which entry
  point a caller uses, and never bypassable by process restart."
- **Known self-heal-branch gap, still open** (`index.md:434-452`, P02.2's
  Review, upgraded by Red-Team with real-concurrency evidence):
  `maxAssignmentsForSession`, `maxRoundsForSession`,
  `maxConcurrencyForSession`, and `maxRoundsForActor` are "checked only on
  the genuinely-new-taskKey path, below the same claim-file branch the
  binding invocation cap used to skip too... Red-Team's real 2-process
  reproduction against `maxAssignmentsForSession: 1` materialized TWO
  Assignments in **12 of 20 genuine concurrent trials**." P02.2 fixed only
  the per-binding invocation cap (its own R7 scope); these four session-wide
  siblings are unresolved.
