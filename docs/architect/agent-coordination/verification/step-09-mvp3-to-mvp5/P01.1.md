## 1. Requirements (verbatim from phase-01-mvp3-recheck-lineage-and-disposition.md)

- **R1 Handoff-first review.** Compare the implemented MVP1/MVP2 handoff against
  this phase before editing source. If a requirement is already implemented and
  proved, record acceptance in the trace instead of redoing it.
- **R2 Recheck lineage.** A recheck records a new Assignment linked to the
  artifact revision/evidence ref it evaluates and the prior finding/verdict it
  is rechecking.
- **R3 Retry separation.** Recheck must not use `run-retried`, must not
  supersede a previous RunResult, and must not erase or rewrite the first-pass
  review/red-team verdict.
- **R4 Disposition event.** `driver-disposition-recorded` records target ref,
  disposition, rationale, evidence refs, timestamp, and driver provenance.
- **R5 Driver-only authority.** Worker Assignments may produce findings and
  recommendations, but cannot record final disposition or close truth.
- **R6 Replay.** Session replay reconstructs recheck lineage and dispositions
  deterministically from the event log.
- **R7 Artifact authority.** Coordination stores refs to artifacts/results; it
  does not copy produced artifacts into a second authoritative store.
- **R8 Negative semantics.** Recheck for unknown target, stale/nonexistent
  artifact ref, missing authorization, terminal session, or reused invocation
  key fails closed.

### 4a. Why "terminal session" has no door-level test

`src/verbs/coordination/run.mjs`'s `runCoordinationUseCase` opens a session
once (`openStandaloneSession`/`openDeclaredProtocolSession`, unconditional —
`P00.1.md` Gap #17, "No resume door") and closes it exactly once, via
`closeSessionByQuorum` called AFTER the entire `for (const step of
request.steps)` loop finishes (`run.mjs:391-401`, confirmed by direct read).
There is no step type that transitions the session to a terminal status
mid-loop (the four step types are `operation`/`fan-out`/`authorize`/
`disposition`, `schema.mjs:420-423` — none of them closes the session), and a
second `runCoordinationUseCase` call naming the same `coordinationId` is
itself refused at session-open before any step runs
(`test/verbs/coordination-run-driver-steps.test.mjs:526`, "re-running a
request that names an existing coordinationId is refused"). So within one
request there is no way to reach terminal status and then attempt a further
authorize/disposition step in the SAME already-open session through the
door — the capability that would let a door-level test exist is exactly the
resume door `P00.1.md` already tagged "04 (MVP5)" and explicitly out of this
phase's scope (`current-cell.md` Non-Goals references Phase 04 gaps only by
number, but Gap #17 itself is the direct blocker here). This is not a defect
introduced or left by this phase — the engine-level refusal is real,
lock-held-atomic (`coordination-driver-authorization.test.mjs`'s "the
active-status check and the operation-authorized append share ONE held
events-lock critical section" test), and reachable from every CLI/request
authorize or disposition step that exists today.
