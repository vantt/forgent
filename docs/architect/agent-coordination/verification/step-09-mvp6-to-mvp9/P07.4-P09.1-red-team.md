## Attack 1 — the close gate itself: **BROKE (HIGH)**

The gate (`src/verbs/coordination/run.mjs:219`) reads
`definition?.spec?.profile?.completion?.aggregation`, where `definition` is
whatever `loadCoordinationProtocol(request.protocolRef.id, …)` returned at
`run.mjs:317` — **the protocol the *request* names, resolved live off disk,
unpinned by version**. It is never checked against `manifest.definitionRef`.
`findExistingManifest` (`run.mjs:130`) validates only `writerId` on a resume.

### 1a. Protocol-swap on resume — reproduced

A session opened against a protocol that declares `completion.aggregation`,
then resumed with `protocolRef.id` naming a *different*, aggregation-free
protocol and a single `disposition` step (which needs no operation, so no
dispatch door is reached):

```
PHASE1 closed= false | refusal= ... declares completion.aggregation, but session
       "coord_rt09_swap" has validated no aggregation ...
PHASE1 manifest.definitionRef= {"id":"test.proto.with-agg","version":"1.0.0"}
PHASE2 (resume naming the AGGREGATION-FREE protocol) closed= true | refusal= none
PHASE2 manifest.status= completed
PHASE2 definitionRef still= {"id":"test.proto.with-agg","version":"1.0.0"}
PHASE2 validated aggregations on log= 0
```

The session stays bound to the aggregation-declaring protocol on its own
manifest, and reaches `completed` with **zero** validated aggregations.

### 1b. Same id, definition edited in place — reproduced

Cheaper still: no second protocol needed. Drop `completion.aggregation` from
the bound protocol's own file between the two runs (and bump its version, to
show the version pin is absent too):

```
VARIANT-B PHASE1 closed= false
VARIANT-B PHASE2 (same id, edited file, version 1.0.0 -> 9.9.9) closed= true | refusal= none
VARIANT-B manifest.status= completed definitionRef= {"id":"test.proto.with-agg","version":"1.0.0"}
VARIANT-B aggregations on log= 0
```

### Why this is worse than the forgery residual P07.4.md discloses

- **Cheaper than the raw-store-door forgery.** No `.fgos/events.jsonl` write,
  no hand-built event, no driver-identity copying. A normal `fgos coordination
  run --file` request does it.
- **Reachable by accident, not only by an attacker.** An operator resuming
  with a copy-pasted request that names the wrong `protocolRef.id` gets a
  silent unjustified close. This is a correctness bug first, a trust-boundary
  bug second.
- **Both promoted contract statements are false as written.**
  `coordination-session.md`: *"The request door … reads the bound definition"*
  — it does not; it reads the requested one.
  `flow-definition.md`: *"A session bound to a definition that declares
  `completion.aggregation` may not close on quorum alone"* — reproduced above
  that it may. This is exactly the P07.4 Bug Taxonomy entry "promoting
  contract text for behavior not implemented".
- **It is inconsistent with every sibling door in the same phase.**
  `validateSessionAggregation` (`session-engine.mjs:3086-3092`) and
  `dispatchDeclaredOperation` (`session-engine.mjs:1735-1740`) both resolve
  from `manifest.definitionRef` **and** refuse version drift. The new gate is
  the only definition-consuming door in the coordination layer that does
  neither. `coordination-session.md`'s own named limitation #2 asserts "The
  validation door resolves the definition from `manifest.definitionRef` and
  refuses version drift" as if it covered this path; it does not.

### Smallest fix

In `aggregationCloseParams`, ignore the request's definition. Resolve from
`manifest.definitionRef` and refuse version drift, copying
`validateSessionAggregation`'s existing four lines verbatim. (An acceptable
narrower alternative is to reject, at `run.mjs:317`, any resume whose
`request.protocolRef.id` differs from `manifest.definitionRef.id` — but that
still leaves 1b open, so the manifest-resolution fix is the real one.)

Add a regression test for both variants; the existing parity test cannot catch
either, because both doors share `run.mjs` and therefore share the bug.

## Attack 2 — raw-store-door forgery through the new gate: **BROKE as disclosed, plus an ignored cheap signal (MEDIUM)**

Reproduced exactly as `P07.4.md` predicted. `recordAggregationValidation` with
a hand-picked `outcome: 'consensus'`, one legitimately `result-linked` source
ref, and the session's own driver identity is accepted by the store door and by
replay, and the new gate then closes the session:

```
FORGED event accepted by store door
replay accepted? aggregations= 1 outcome= consensus | artifactRevisionRefs= null
PHASE2 close through NEW P07.4 gate: closed= true | refusal= none
manifest.status= completed
```

`P07.4.md` is right that this became the cheapest *forgery* route once the gate
closed — though Attack 1 is cheaper than forging at all.

### The cheap signals a real validation leaves that nothing checks

Control run, a genuine `validateSessionAggregation` on the same protocol:

```
CONTROL real consensus: outcome= consensus | sourceResultRefs= 2
                        | artifactRevisionRefs= 2 | method= evidence-preserving-synthesis
```

Two structural invariants hold for **every** record a real validation can emit,
and neither replay nor the gate checks either:

1. **`artifactRevisionRefs.length === sourceResultRefs.length`, and non-zero on
   a `consensus`.** `validateSessionAggregation` pushes exactly one
   `artifactRef@revision` pin per surviving source (`session-engine.mjs:3173-3181`),
   and a `consensus` requires full coverage, so a real consensus can never carry
   zero pins or a count mismatch. The forgery above carried **none** and was
   accepted. This is the same class of check replay already performs for
   `missingActors`/`failedActors`/`unresolvedContributionRefs`/
   `unboundSourceOperationRefs` (`replay.mjs:208-218`) — it is one more field in
   that same loop, needs no definition, and costs nothing.
2. **Every `sourceResultRefs` entry belongs to a binding of a declared
   `sourceOperationRefs` operation.** The forgery above cited the
   *coordinator's `review` assignment* — an operation that is not a declared
   source of the aggregation at all. Replay is definition-blind so it cannot
   check this, but `aggregationCloseParams` (which, once fixed per Attack 1,
   holds the bound definition) can.

Neither closes the residual completely — a forger who mirrors the shape still
wins — but signal 1 is free and strictly narrows the gap between "any
consensus-shaped event" and "a record a real validation could have produced".
`P07.4.md`'s Gaps section should not claim the residual is unnarrowable while
these are unread.

## Attack 3 — `show.mjs` render: **HELD**

Fed `show` two hand-built edge-case records (a `no-consensus` with empty
dissent but non-empty `unresolvedContributionRefs` and a non-empty
`unboundSourceOperationRefs`; a `qualified` with `dissentRefs` set,
`artifactRevisionRefs: []`, `missingActors: []`, and no output assignment) and
diffed the rendered record against the raw event payload field by field.

Every field present on the event round-tripped byte-identically. Every absent
field rendered as `[]`/`null` per the documented contract, and the 15-key set
was stable across both. Nothing dropped, nothing misrepresented. `qualified`
renders correctly. Post-terminal records land in `ignoredAggregations` as
claimed.

Two surface observations, not defects:

- `show` reports the aggregation records but never says **which** one gated the
  close, nor whether the bound protocol declares an aggregation at all. On a
  session with several records an operator cannot tell from `show` alone which
  one spoke. Worth one field once Attack 1 is fixed.
- The absent-vs-present-but-empty distinction is collapsed. Harmless today —
  `validateSessionAggregation` only ever emits these fields when non-empty —
  but it means `show` cannot distinguish a real record from a hand-written one
  that spelled the empties out.

## Attack 5 — P09.1's cross-referential checks: **MOSTLY HELD, two real gaps**

Ran 25 crafted definitions through `validateFlowDefinition` (`attack5.mjs`).

### Held

- **Prototype-pollution-shaped ids.** Slot ids `__proto__`, `constructor`,
  `toString`, `hasOwnProperty` are accepted as ordinary strings and correctly
  deduplicated (`duplicate slot id "__proto__"`). Every id set in the new code
  is a `Set`, never an object literal — no pollution surface.
- **Declaration-order independence of the edges check.** Slot-naming edges are
  rejected whether `specialistSlots` is written before or after `edges`, on
  both `from` and `to`.
- **Workflow-profile rejection** — structural, via `spec.profile has unknown
  field "topology"`.
- **Cap typing** — `'3'`, `true`, `null`, `Infinity`, `1.5`, `0`, `-1` all
  rejected.
- **Dangling role / operationRef / capability / visibility-window refs** — all
  rejected as the trace claims.

### Gap 5a (MEDIUM) — `slot.role` incoherent with its own `operationRefs[]` is accepted

```
ACCEPTED | slot.role "coordinator" but operationRefs ["research"]
           (a researcher-only operation)
```

The runtime already enforces exactly this invariant — `dispatchDeclaredOperation`
refuses `actorEntry.role !== operation.role` (`session-engine.mjs:892-895`). So
the schema accepts a slot that is **statically impossible to fill and dispatch**:
any specialist of the slot's declared role is refused at dispatch for every
operation the slot lists. This is the track's recurring "declared capability,
wrong operation" bug class, in a cell whose Acceptance bullet is precisely
"topology class and operation legality remain fully predeclared/static".

Smallest fix: in `assertSpecialistSlotsReferenceRealEntities`
(`schema.mjs:948`), pass `operations` rather than only `operationIds` and
assert `operation.role === slot.role` per `operationRefs[]` entry. Six lines,
no runtime surface, no binding logic.

Related, lower severity and *documented* by the Doer as deliberate:
`requiredCapabilities[]` resolving against a definition-wide union means a slot
may require a capability declared only on an operation it may never perform
(reproduced: slot performs `research`, requires `audit`, accepted). The Doer's
reasoning is stated and defensible; I flag it only because 5a shows the same
"declared X, wrong operation" shape and 5a is *not* documented anywhere.
Similarly, `allowedVisibilityWindows[]` may name a window scoped to an operation
outside the slot's `operationRefs[]` — undocumented, same class, lower stakes.

### Gap 5b (LOW-MEDIUM) — a slot that bounds nothing is accepted

```
ACCEPTED | operationRefs:[] requiredCapabilities:[] allowedVisibilityWindows:[]
```

This contradicts the Doer's own stated rationale for making all seven fields
required (`schema.mjs:366-375`: "a slot missing any of them is not partially
declared, it is unbounded, which defeats the whole point of a slot"). An empty
array satisfies `assertStringArray` and delivers exactly the unboundedness the
requirement exists to prevent. The sibling precedent in this same file rejects
it: `completion.aggregation.sourceOperationRefs` must be non-empty, with the
reasoning "an aggregation with no declared sources is self-validated"
(`schema.mjs:433-434`).

Smallest fix: require `operationRefs.length > 0` at `schema.mjs:386`. Whether
`requiredCapabilities`/`allowedVisibilityWindows` may legitimately be empty is
a product call — but it should be *stated*, not fall out of `assertStringArray`.

### Minor observations (no fix demanded)

- `maxBindings: 1e21` and `Number.MAX_SAFE_INTEGER` are accepted — integral and
  positive, so a "narrowing cap" that narrows nothing. Matches the letter of
  the requirement.
- Duplicate entries inside one slot's `operationRefs[]` are accepted, where
  `completion.aggregation.sourceOperationRefs` rejects duplicates
  (`schema.mjs:436`). Inconsistent, cosmetic today.
- **No cross-namespace uniqueness for slot ids.** A slot id may equal a declared
  actor id, operation id, or graph node id (all reproduced as ACCEPTED). Today
  this is inert. It does soften P09.1.md's Req-8 "structural closure proof":
  the claim "a slot id is never in `actorIds`" holds only while the id spaces
  happen to be disjoint, and nothing enforces that they are. Worth a uniqueness
  check, or an explicit note, before P09.2 resolves anything against slot ids.

### Liveness finding (MEDIUM) — an enforced gate makes `partialPolicy` unreachable

Not in the attack menu, found while probing whether the gate "becomes mandatory
in a way that breaks a definition" (P07.4's own Bug Taxonomy). Reproduced
(`attack4.mjs`): a session with an explicit `partialPolicy:
{allowedOmissions: ['researcher-b']}` — i.e. a close the contract says is
legal — where `researcher-b` is bound to a declared `sourceOperationRefs`
operation:

```
PHASE1 closed= false  (no aggregation validated yet)
validated outcome= no-consensus | missingActors= ["researcher-b"]
PHASE2 closed= false | refusal= aggregation "agg_partial" validated as
       "no-consensus", not "consensus" -- refusing to close
manifest.status= active
CONTROL (no aggregation declared) closed= true | status= partial
```

The omission the policy explicitly permits is precisely what forces
`no-consensus` (an unsatisfied binding makes its whole source operation
contribute nothing). No re-validation can ever produce `consensus` while the
actor stays missing, so the session can **never** close. `grep` confirms no
`cancelSession` caller exists in `src/verbs/`, `bin/fgos.mjs`, or the headless
adapter — there is no other terminal door on the request surface. The same
holds for a permanent `qualified` (unresolved dissent), which the gate also
refuses.

This may be the intended reading of "terminal input is refuse-only", but it is
a real product consequence of *enforcing* the gate that neither `P07.4.md`'s
Gaps nor the promoted contract text names. The contract says only that an
aggregation "never relaxes `partialPolicy`" — it does not say that declaring
one makes `partialPolicy` unreachable and the session unclosable. Name it, or
give the gate a declared escape (a driver disposition that records why the
aggregation cannot be resolved).

### Item 7, the replay consistency check — CONFIRMED-PRESENT, and exactly what it does and does not catch

`replay.mjs:214-236`, inside the existing `outcome === 'consensus'` block.

**What it catches** (both executed): a `consensus` with `artifactRevisionRefs`
absent or empty, and one whose length differs from `sourceResultRefs.length`.

**What it does not catch — it is a COUNT check, never a CONTENT check.** I built
forged consensus records through the real store door and replayed them:

```
T3 [junk strings, right count]                 -> store ACCEPTED, replay ACCEPTED, outcome=consensus
T3 [duplicated single pin]                     -> store ACCEPTED, replay ACCEPTED, outcome=consensus
T3 [pins naming a NON-EXISTENT artifact]       -> store ACCEPTED, replay ACCEPTED, outcome=consensus
T3 [empty strings, right count]                -> REFUSED (payload.artifactRevisionRefs must be an
                                                  array of non-empty strings — the pre-existing
```

So `artifactRevisionRefs: ['x','y']` against two sources passes; so does the

project's own test fixture is itself in this category — `storePayload` emits
`artifact://<assignmentId>@rev-<i>`, a synthesized string.

This is not a defect: the disposition asked for exactly a count/non-zero check

`coordination-session.md` says "absent/empty or do not number exactly one per

it only so nobody later reads P07.4.md's "only a forger who mirrors the full

### New this round

**NEW-1 (LOW-MEDIUM, documentation accuracy — not a code block). A
same-`{id, version}` in-place edit dropping `completion.aggregation` bypasses
the gate completely. Reproduced.**

The drift check compares versions, so an edit that leaves the version alone
passes it, and the now-absent declaration takes the `return {}` early exit:

```
C/phase1                       closed=false status=active  aggregations=0
C/phase2(edit, SAME version)   closed=true  status=completed aggregations=0
```

The session closed to `completed` with zero validated aggregations. Reachable
without touching the original file at all, since the loader lets a project-tier
document shadow a domain/core one by id (`protocol-loader.mjs:202-209`).

**Why this is not a BLOCK, and not a defect in this fix.** The exposure is
already disclosed, as `coordination-session.md`'s pre-existing Named Limitation
2 — *"The definition is pinned by `{id, version}`, never by content … Every
sibling definition-consuming door in the engine shares this exposure"* — and the
close gate is now exactly such a sibling. The disposition mandated copying
`validateSessionAggregation`'s pattern verbatim rather than re-deriving it; the
Fixer complied, and inheriting the pattern's residual is the consequence of the
instruction, not a lapse. It also sits at a different, higher-cost trust
boundary than the HIGH did: it needs `.fgos` write access, exactly like the
already-accepted forged-aggregate residual, whereas the HIGH needed only an
ordinary request.

**What I would change, one sentence.** Limitation 2's illustration is *"could
still swap in a same-`{id, version}` document declaring a different cohort"*.
At this door the consequence is categorically larger: it does not alter a
parameter, it silently switches off the single enforced property this cell
exists to add, and the resulting close is externally indistinguishable from a
legitimate one. Naming that consequence where the limitation is stated would
make the promoted text fully honest. A real fix (a content digest on
`definitionRef`) is a whole-engine change and correctly not this round's.

**NEW-2 (LOW). The slot-id disjointness check omits one id space:
`visibilityWindows[].id`. Reproduced.**

```
T4 [slot id == visibilityWindows[].id] -> ACCEPTED
```

`assertSpecialistSlotIdsAreDisjoint` enumerates four spaces — actors, roles,
operations, graph nodes. Disposition item 3 named exactly those four, so the
Fixer delivered the accepted scope in full and this is out-of-scope rather than
incomplete. But the window id space is a slot's *own* reference space (a slot
declares `allowedVisibilityWindows[]`), which makes it the one remaining space
where the function's own stated rationale — *"Disjointness is what makes 'a slot
id is never in the actor id space' a property rather than an assumption"* —
still rests on an assumption. Inert today (nothing resolves a slot by id at
runtime), and the fix is one array entry using `windowIds`, a set already
computed in `validateSpec`. Worth taking before P09.2 resolves anything against
slot ids.

**OBS (no action). The accepted "a drifted definition can no longer close even
with no aggregation declared" consequence is real but close to unreachable.**
`aggregationCloseParams` now throws on drift before the opt-out early return, so
in principle a no-aggregation session that would previously have closed can be
refused. In practice the window barely exists: a close is attempted on every
run, so a quorum-satisfied session closes on the run that satisfies it; and once
a definition has drifted the session can no longer dispatch or authorize either
(`session-engine.mjs:1367`, `:1734`, `:2425`). The Fixer's own reasoning
("the drifted state was already terminal for the session in every respect but
this one") is sound, and the explicit opt-in regression test still passes.
