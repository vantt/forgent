## Requirements (phase-09-mvp9-bounded-specialist-binding.md, P09.1 cell + current-cell.md's fuller phrasing)

1. Add `topology.specialistSlots[]` to `FlowDefinition`, restricted to the
   `CoordinationProtocol` profile (same structural mechanism as
   `visibilityWindows`): `id`, `role`, `operationRefs[]`,
   `requiredCapabilities[]`, `allowedVisibilityWindows[]`, `maxBindings`,
   `maxAssignments`.
2. Reject a dangling `role` (must resolve to a declared `spec.roles[]` id).
3. Reject a dangling `operationRefs[]` entry (must resolve to a declared
   `spec.operations[]` id).
4. Reject a dangling `requiredCapabilities[]` entry (must resolve to a
   capability declared on at least one `spec.operations[]` entry anywhere
   in the definition).
5. Reject a dangling `allowedVisibilityWindows[]` entry (must resolve to a
   declared `spec.profile.topology.visibilityWindows[]` id).
6. Require `maxBindings`/`maxAssignments` to be positive integers — reject
   zero, negative, or non-integer values.
7. Reject an explicit `topology.edges[]` entry naming a declared specialist
   slot id as its `from`/`to` (slots are declarative capacity, never a
   routable topology edge endpoint).
8. Reject a graph node operation binding (`actor`) that references an
   undeclared specialist slot id — proven as a structural closure property:
   no field anywhere in the schema resolves `actor` against slot ids, so
   any such reference is already rejected by the pre-existing "actor not
   declared in spec.actors" check, with zero new binding/expansion code
   path introduced.
9. Reject `specialistSlots` on a `Workflow`-profile definition.
10. A definition with no `specialistSlots` stays byte/behavior-identical to
    pre-change validation (regression).

## Design Notes

**Field placement and cross-referential check split.** `specialistSlots[]`
is parsed for shape only inside `validateProtocolProfile` (`role`,
`operationRefs[]`, `requiredCapabilities[]`, `allowedVisibilityWindows[]`,
`maxBindings`, `maxAssignments` are all required — a slot missing any of
them is not partially declared, it is unbounded, which defeats the whole
point of a slot). Cross-referential checks (`role` vs `spec.roles[]`,
`operationRefs`/`requiredCapabilities`/`allowedVisibilityWindows` vs
`spec.operations[]`/capabilities/`visibilityWindows[]`) run afterward in
`assertSpecialistSlotsReferenceRealEntities`, called from `validateSpec`
right after `operations` and `windowIds` are computed — the exact same
split `visibilityWindows` already uses, for the exact same reason
(`validateProtocolProfile` runs before `spec.operations[]` exists in
`validateSpec`'s `profile -> roles -> actors -> operations -> graph`
order). `windowIds` computation was hoisted a few lines earlier in
`validateSpec` (it was previously computed only for `validateGraph`'s
`contextAccess` check, right before that call) so it can also feed the new
`specialistSlots` check without duplicating the derivation.

**`requiredCapabilities[]` resolves against a definition-wide union, not a
single operation.** The candidate contract says a capability reference must
be to "something real elsewhere in the definition" — capabilities are
declared per-operation (`spec.operations[].capabilities[]`), and a slot's
required capability is a property of the specialist filling it, not of any
one operation it may perform, so the legal target set is the union of every
declared operation's `capabilities[]` across the whole definition
(`capabilityIds = new Set(operations.flatMap((op) => op.capabilities ?? []))`),
not a per-operationRef intersection. No narrower reading was asked for, and
a per-operationRef intersection would be new binding-shaped logic this cell
is explicitly not supposed to introduce.

**Edges-vs-slots check reads: "reject explicit runtime edges naming a
slot" literally, for any declared slot id, regardless of position in the
source document.** `topology.edges[]` and `topology.specialistSlots[]` are
both parsed inside the same `validateProtocolProfile` function, into local
`topology.edges`/`seenSlotIds` variables, before either is frozen onto the
final `topology` result — so the new check (`edge.from`/`.to` must not be a
declared slot id) runs there directly, with no need for a second
post-`validateSpec` pass. This mirrors how `visibilityWindows`' shape check
and duplicate-id check both happen inline in the same function, before any
cross-`operations` referencing.

**"Undeclared slot expansion" needed zero new code for the
graph-operation-binding half.** Reread literally, current-cell.md's clause
is: "reject undeclared slot expansion (a binding/operation referencing a
slot id not declared in `topology.specialistSlots[]`)." The only existing
schema surface where a graph node operation binding references an id at
all is `graph.nodes[].operations[].actor`, and that field has only ever
resolved against `spec.actors[]` ids (`validateNodeOperationRef`,
unchanged by this cell). A slot id — declared or not — is never added to
that `actorIds` set, so *any* attempt to use a slot id as an operation's
`actor` is already rejected today, with the existing "actor not declared in
spec.actors" message. Rather than inventing a new dual-namespace `actor`
resolution (which would start to look like the binding/authorization logic
P09.2 owns, explicitly called out in this cell's Bug Taxonomy as the
mistake to avoid), this cell proves the closure property with a dedicated
test instead of new production code: a graph operation binding can never
statically "expand into" a slot, declared or not, until P09.2 adds real
authorization. This reading is also the only one consistent with the
Acceptance bullet "Topology class and operation legality remain fully
predeclared/static" — inventing a new slot-resolution path on `actor` would
itself be new runtime-adjacent surface, not proof of staying static.
