Adversarial review of P10.10 (Promotion And Closeout): the "implementation
bug vs shared missing primitive" classification, the new `contribution`
step (`src/verbs/coordination/{run,schema}.mjs`), and the two
resolution-failure fixes.

**On the classification: I agree with the normal-closure path.** The
contribution-lineage finding is correctly classified an implementation bug.

Five findings below. None blocks closure. Two (M1, L1) are defects this cell

## 1. Attacks that FAILED — the classification survives

Every attack the dispatch asked for was built and run as a real probe. All
four core attacks failed to find a hole.

### 1a. Can the pack-gate path reach `linkSessionContribution` with a shape its P08.2/P08.3 proof never covered? NO.

The new path is a **strict narrowing**, not a widening. `run.mjs`'s
`contribution` branch supplies exactly seven fields, and every one is either
derived or narrower than the direct-call path:

| Field | Where it comes from | vs. direct call |
|---|---|---|
| `linkedBy` | `driverIdentity` = `{type:'driver', id: request.writerId}`, and `findExistingManifest` (`run.mjs:140`) hard-refuses a `writerId` that is not the session's `provenanceRoot.writerId` | derived, never caller-supplied |
| `type` | closed `CONTRIBUTION_TYPES` enum | direct call accepts any string |
| `contributionId` | `assertSafeId` (`/^[A-Za-z0-9_-]+$/`) | direct call only forbids `/`, `\`, `..` |
| `assignmentId` | `assertSafeRefOrId` + `resolveRef` | same shape `disposition.targetRef` already uses |
| `roundKey` | non-empty, ≤2000 | same bound the engine enforces |
| `anchors`/`respondsTo` | `assertSafeId` each | stricter than engine |

Every window/provenance/lineage check (`stampedOperationRefOf`,
`deriveVisibilityWindowState`, reasoning-time-vs-link-time ordering,
revision pin, `validateContributionLineage`) runs unchanged inside the same
function. There is no field the request boundary can set that skips one.

### 1b. `linkedBy` forgery — five angles, all refused, at TWO independent layers

Probe A (`probe-a-linkedby.test.mjs`, 5/5):

```
A1 raw linkedBy key   -> coordination request: steps[0] (type "contribution") declares "linkedBy" ...
A2 linkedBy: undefined -> same refusal ('linkedBy' in step catches a present-but-undefined key)
A3 linkedBy on the PROTOTYPE (in-memory requestObject door) -> same refusal ('in' walks the chain)
A4 JSON "__proto__" smuggling -> ownKeys: [...,'__proto__'], 'linkedBy' in step: false
                              -> unknown field "__proto__" in steps[0] (type "contribution")
A5 DIRECT engine call, schema layer bypassed entirely:
   recordContributionLink: authorizedBy.id "evil-forged" is not the driver identity of
   session "rt_a5" (its provenanceRoot.writerId is "rt-driver")
   contributions on ledger after: 0
```

A5 is the important one: even with the whole request boundary removed, the
**store layer** (`assertDriverIdentity`, `store.mjs:1427`) independently
refuses a forged `linkedBy`. `assertNoLinkedBy` is defence-in-depth, not the
only defence. The claim holds and is stronger than the report states.

Smuggling a driver identity through `anchors`/`respondsTo`/`roundKey`/
`contributionId` is not reachable either: none of those fields is ever read
as an identity — `linkedBy` is the only identity input and it is overwritten
unconditionally.

### 1c. `resolveRef`/`assignmentId` — no asymmetry vs `authorize`/`disposition`

`contribution` uses the identical `assertSafeRefOrId` + `resolveRef` pair
`disposition.targetRef` and `operation.fromAssignmentId` already use, and
both drop `mutation` from the normalized output the same way. A literal
(non-`$ref`) assignmentId is accepted by all three — that is required for
resume and is not new.

Confinement is enforced by the engine, twice: `lastEventFor(events,
'assignment-created', assignmentId)` in `linkSessionContribution`, and
`manifest.assignmentRefs.includes(assignmentId)` in `recordContributionLink`.

Probe B1 — link session B's assignment into session A, same driver, same
workspace:

```
B1: REFUSED [foreign-ref] linkSessionContribution: assignment "asgn_rt_driver_op_004"
    was never created in session "rt_b1_a" -- a contribution may only be backed by
    this session's own work
B1 sessionA contributions: 0
```

### 1d. Unguarded `loadCoordinationProtocol` left in `run.mjs`? NO — exactly two, both guarded

Probe C3, source scan of every call site:

```
line 252  definition = loadCoordinationProtocol(manifest.definitionRef.id, ...)   guarded: true
line 380  definition = loadCoordinationProtocol(request.protocolRef.id, ...)      guarded: true
```

No third site exists. The report's claim is accurate.

### 1e. The "a naive test cannot isolate `aggregationCloseParams`" claim — TRUE, verified

Probe C2 ran the naive scenario the Doer describes (open a session, then
drop a malformed sibling into the project registry, then resume):

```

   "core.coordination-protocol.group-thinking-rfc-review-lite" could not be resolved ...
```

The request-boundary guard fires first, exactly as claimed. The decoy /

Fails closed; pre-existing `protocol-loader` behaviour; out of scope. Noted
because it is the mechanism behind the whole decoy discussion.

## 2. Findings

### M1 — MEDIUM (introduced by this cell): both new catches discard the original error, and the request-boundary one actively misattributes

`run.mjs:379-386` and `run.mjs:251-258` both use a bare `catch {`. The
original `FlowDefinitionError` — which names the exact file that failed and
the parse position — is discarded with no `cause`.

Probe C2, measured:

```
message:   coordination request: protocol "core.coordination-protocol.group-thinking-rfc-review-lite"
           could not be resolved -- refusing the request rather than crashing with an
           unresolvable-definition error
err.cause: UNDEFINED (original error discarded)
```

The actual fault was `zz-broken.json`. The protocol named in the message is
perfectly healthy. An operator is pointed at the wrong artifact, with no
thread back to the real one.

Severity is raised by three things, not one:

1. This is the **hottest path in the file** — line 380 runs unconditionally
   on every declared-protocol request, open and resume alike.
2. Before this change the raw error was *correct and specific*. This is a
   net loss of diagnosability introduced by a fix whose stated purpose was
   "an honest, correctly-attributed refusal."
3. `test/verbs/coordination-launch-master-loop.test.mjs` was updated to
   *stop* asserting the specific upstream message and assert the generic one
   instead — the regression is now locked in by a test.

The `classifySessionQuorum` precedent the report cites has the same flaw
(`session-engine.mjs:3296`, `catch { resolved = null }`). Mirroring it
faithfully is defensible; propagating it onto a hotter path without noticing
is the finding.

**Fix (in-scope, one line each):** add `{ cause: err }` to both `throw`s, and
ideally append `err.message` to the wrapped text. Neither test needs to
change.

### M2 — MEDIUM (pre-existing, unnamed, and now load-bearing): the base door does not cross-check a resumed session's protocol; the pack gate does

Probe B4 ran the same resume request through both doors:

```
B4 base runCoordinationUseCase: ACCEPTED closed=false
B4 pack gate: REFUSED [validation] group-thinking pack: session "rt_b4" is already bound
   to protocol "core.coordination-protocol.group-thinking-rfc-review-lite", not the
   explicitly selected "core.coordination-protocol.group-thinking-nominal-group-lite"
```

`runCoordinationUseCase` validates `request.actors[]` against the **claimed**
`protocolRef.id`, never against the resumed session's real
`manifest.definitionRef.id`. P10.1 added exactly this cross-check — to
`group-thinking-pack.mjs` only. `fgos coordination run --file` and the
headless adapter go through `run.mjs` directly and do not get it.

Practical consequence: the `actors[].id is not declared by protocol ...`
narrowing can be sidestepped on resume by claiming a protocol that declares
the actor you want to attach a policy override to. Impact is bounded — the
engine still refuses a dispatch to an actor the *real* definition does not
declare, and mounting it needs write access to the protocol registry — so
this is not a privilege escalation. It is a genuine door asymmetry.

Two things make it worth naming now rather than later:

- **§1c's 21-item sweep does not contain it.** No cell in P10.1-P10.9 or
  P10-KERNEL-FIX names it either (grepped). For a closeout artifact whose
  Acceptance #1 is a complete residual classification, that is a real hole in
  the list, even though §1c only claimed to sweep *named* Gaps.
- **P10.10's own new test depends on the gap.** The decoy technique in
  `coordination-aggregation-surface.test.mjs` works *because* call 2 can
  claim `decoyId` while the session stays bound to `PROTOCOL_ID`. If anyone
  later hardens `run.mjs` with the pack gate's cross-check — the obvious
  fix — that test breaks, and the only proof isolating fix #2 evaporates.
  The Doer's inline comment notes the asymmetry but does not flag the
  coupling.

**Recommended:** add it to §1c as a 22nd residual (implementation bug,
deferred, no live exploit), and add one sentence to the decoy test warning
that the technique is coupled to it.

### M3 — MEDIUM (factual correction to §1d/§1c item #5): the definition-pinning gap IS worsened by Phase 10's own work — proven, not argued

§1c item #5 states the pinning gap is "not something Phase 10's own
pack/skill introduced, **worsened**, or could have hidden." The word
"worsened" is demonstrably false. Probe D:

```
D real propose.contributions.allowedTypes = ["proposal"]
D forbidden type chosen: rank
D baseline (unswapped): REFUSED: linkSessionContribution: ... deliberation: operation
  "propose" does not declare "rank" in its contributions.allowedTypes[]
D after shadow (same id@version, project-tier file, widened allowedTypes):
  resolved core.coordination-protocol.group-thinking-rfc-review-lite@1.0.0,
  propose.allowedTypes=["proposal","objection","response","clarification","rank","specialist-request"]
D after content swap: ACCEPTED appended=true -- PINNING GAP EXPLOITED THROUGH THE NEW STEP
D contributions on ledger: [["c_swapped","rank"]]
```

A contribution type the canonical protocol forbids is now on the immutable
deliberation ledger, linked through the public request door, with the version
check passing. Note also that a **project-tier file silently shadows a
core-tier protocol at the same `id@version`, with no warning.**

What this does and does not change:

- **Does not change the classification.** It is still a shared missing
  primitive (content-addressed pinning exists nowhere), still pre-existing
  (identical exposure has governed `dispatchDeclaredOperation`,
  `authorizeDeclaredOperation`, `validateSessionAggregation` and the direct
  `linkSessionContribution` path since MVP6-8), and mounting it needs write
  access to a workspace the driver already fully controls. It is not a
  privilege escalation and it does not block a literal Exit Contract bullet.
- **Does change the record.** Phase 10's `contribution` step moves this
  decision class — *which contribution types are legal*, and *which
  visibility window gates the reasoning that may enter the ledger* — from
  "reachable only by a direct engine call from a test file" to "reachable
  from the CLI / pack gate / skill." That is a materially larger surface,
  and it is exactly the question the classification decision turns on.

**Recommended:** strike "worsened" from item #5, and replace it with the
concrete statement above plus this probe as evidence. The conclusion
(non-blocking, normal closure) is unaffected — a closeout artifact just
should not carry a claim its own new code disproves.

### L1 — LOW (introduced by this cell): `anchors: []` vs omitted breaks idempotent repeat

Probe B3: link `c_anch` with `"anchors": []`, then repeat the byte-identical
request without the `anchors` key.

```
B3 repeat-without-anchors: REFUSED [duplicate-ref] recordContributionLink: contributionId
   "c_anch" in session "rt_b3" was already linked with different content -- a contribution
   link is immutable; record a new contributionId instead
```

Two semantically identical requests ("no anchors") produce a hard
`duplicate-ref` instead of the documented idempotent no-op. Root cause is in
the new `validateContributionStep`, which preserves the
explicit-empty-vs-absent distinction that `recordContributionLink`'s
`canonicalize` then reads as different content. This defeats the
crash-resume self-heal path for any client that emits `anchors: []`.

**Fix:** normalize an empty `anchors` to `undefined` in
`validateContributionStep` (one line).

### L2 — LOW (pre-existing, newly user-facing): wrong field name in a contribution-link refusal

Probe A5:

```
recordContributionLink: authorizedBy.id "evil-forged" is not the driver identity of session ...
```

`assertDriverIdentity` is shared, and hardcodes `authorizedBy` in the
message. For a contribution link the field is `linkedBy`. Harmless before —
contribution links had no public door. The new step makes this message
reachable from the request surface.

## 5. Verdict

**APPROVE WITH CONCERNS.**

**On the classification, plainly: I agree with normal closure. This should
NOT trigger "leave Step 09 open."** The contribution-lineage finding is an
implementation bug. `linkSessionContribution` was a complete, self-mediating,
already-proven door; the gap was purely that `run.mjs`'s request vocabulary
never reached it. Closing it required no kernel mechanism, no kernel file,
and no new trust decision — the new step is a strict narrowing over an
existing door, verified by probe, not by reading the report's prose. The
`shared missing primitive` consequence clause is reserved for a capability
gap not fixable as a scoped patch; this was fixable as a scoped patch, and
was.

I also agree the definition-pinning residual (§1c #5) does not force the
track open — but §1d's supporting prose needs the M3 correction before it
goes into the record.

Recommended before the track-closing declaration:

1. **M1** — add `{ cause: err }` to both new `throw`s. One line each.
2. **L1** — normalize empty `anchors` to `undefined`. One line.
3. **M3** — strike "worsened" from §1c item #5; record probe D's result.
4. **M2** — add the base-door resume asymmetry as a 22nd residual, and note
   the decoy test's coupling to it.
5. **L2** — optional; `assertDriverIdentity`'s message field name.

None of these is a blocker. 1, 2 and 5 are code one-liners; 3 and 4 are
record corrections.
