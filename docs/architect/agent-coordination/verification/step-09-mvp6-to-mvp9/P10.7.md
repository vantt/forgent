## 3. Finding #1 -- the pack gate has no channel for contribution linking, at all

Read directly, before writing a single test (per this repo's own read-first
discipline): `run.mjs`'s request `steps[]` vocabulary is closed to exactly
four kinds -- `operation` | `authorize` | `disposition` | `fan-out`
(`schema.mjs`'s own `validateSteps`, `OPERATION_STEP_ALLOWED_KEYS` has no
contribution field of any kind). `linkSessionContribution`
(session-engine.mjs) -- the ONLY door that turns a settled Run into a
durable `proposal`/`clarification`/`rank` ledger entry -- has no
corresponding step type, and is never called anywhere in `run.mjs`. This is
proven empirically, not just argued from a static read: a request with a
`type: 'link'` step is refused by the real schema with its own exact
message ("steps[1].type must be \"operation\", \"fan-out\", \"authorize\",
or \"disposition\""), and the real, persisted event log of a full chain
driven through the pack gate never once contains a
`deliberation-contribution-linked` event.

**Consequence for this cell's Acceptance text.** "Private rank CAPTURE" and
"chat-history-free replay reconstruction... of the full lineage", read
literally as P10.3 proved them (contribution records with `anchors`
lineage), are **not reachable through the pack gate** -- for this protocol
or any other pack member, since the gap is in the SHARED `run.mjs`/
`schema.mjs` request vocabulary, not this protocol's own definition. What
IS reachable and IS proven (§4): the four-phase ASSIGNMENT/AUTHORIZATION
lineage -- which actor dispatched which operation, and which
authorization's `grantedContextRefs` gated which later operation --
reconstructed purely from `replaySession(...)` alone, with no appeal to
this test's own local step-order memory. This is a materially narrower,
but still real and honestly-scoped, "chat-history-free reconstruction"
claim than P10.3's.

This is a genuine shared missing primitive, per the phase-10 exit
contract's own text ("If a shared missing primitive is proven, do not hide
it in the Protocol Pack or skill."). It is NOT this cell's to fix
(`run.mjs`/`schema.mjs` are outside this cell's May-Touch list, and

they are the SAME closed, hardened, "physically/authoritatively outside the

## 5. Finding #2 -- `closeSessionByQuorum`'s per-actor model auto-completes a multi-phase session early (blocks the literal "after share, before clarify" resume scenario)

Building the FIRST draft of the resume test exactly as current-cell.md's
own example describes it ("interrupt mid-chain (e.g. after share settles,
before clarify)") failed with a real, reproducible error on the SECOND
call: `authorizeOperation: session "..." is not active (status:
"completed")`.

Root cause, traced directly in `session-engine.mjs`
(`classifySessionQuorum`, called from `run.mjs`'s own UNCONDITIONAL
end-of-every-request `closeSessionByQuorum` call -- P10.1.md/P10.5.md's own
bypass-#5 note): quorum classification iterates `manifest.actors[]` and, for
EACH declared actor id, looks for the FIRST `assignment-created` event
naming that actor and checks only THAT ONE assignment's latest
`result-linked` outcome. It is a **per-actor** model ("has this actor
dispatched and settled at least once, anywhere in the graph"), never a
per-graph-node one ("has the WHOLE graph been traversed").

Nominal-Group-Lite declares 4 actors. The facilitator's FIRST operation is
`share` (phase 2 of 4); each participant's FIRST operation is
`private-propose` (phase 1). The instant `share` settles, all 4 declared
actors already have one settled assignment each -- so `run.mjs`'s automatic
end-of-request close call succeeds and the session transitions to
`completed`, TWO WHOLE PHASES (`clarify`, `private-rank`) before the graph
itself is done. A second `runGroupThinkingRequest` call attempting to
continue is then refused outright by the engine's own terminal-session
guard -- not by the pack gate's own resume cross-check (P10.1's fix), which
would have named a protocol mismatch instead. Confirmed directly on the
FIRST call's own returned result (`closed: true`, `status: 'completed'`),
not merely inferred from the second call's failure.

**This is a shared kernel gap, not a defect in this protocol's own
definition or the pack gate.** `classifySessionQuorum` is protocol-agnostic
(keyed only by `manifest.actors[].id`); it is at risk for ANY declared
protocol where one actor is bound to more than one operation across the
graph. Read directly (not run, out of this cell's own scope) for the other
two group-thinking-lite protocols:

- RFC-Review-Lite (`group-thinking-rfc-review-lite.yaml`): `proposer-actor`
  performs both `propose` (phase 2) and `respond` (phase 4) -- same
  at-risk shape. P10.5's own resume test never hit this because it only
  ever advanced as far as `coordinator-actor` + `proposer-actor`'s FIRST
  operation each (2 of 4 actors settled after 2 calls) -- well short of
  `proposer-actor`'s SECOND operation.
- Delphi-Feedback-Lite (`group-thinking-delphi-feedback-lite.yaml`):
  `facilitator-actor` performs both `convene` and `aggregate`; each
  `panelist` performs both `propose-round1` and `propose-round2` -- also
  at-risk.

This cell did not run P10.6/P10.8's own protocols to confirm the failure
live (out of scope, separate isolated worktrees) -- named here as a
structural hypothesis backed by direct code + YAML reads, for P10.10 to
verify and promote/track.

**What this cell proved instead, honestly, rather than hiding the gap:**

- Test (A): a genuinely successful resume, split at a point that avoids
  the trap (interrupted mid-`private-propose`, before the facilitator's
  first-ever dispatch) -- the second call completes the ENTIRE remaining
  chain (`propose`, `share`, `clarify`, `private-rank` x3) correctly, with
  no duplicate propose dispatch and the no-tally check still holding at the
  natural end.
- Test (B): the literal scenario current-cell.md's own example names,
  proven to fail for the REAL, now-understood reason (session already
  `completed` after call 1), not a mystery error -- confirmatory
  `assert.rejects` on the second call's own exact engine message.

mechanism is a genuine, protocol-agnostic completion-correctness defect

"no double-grant" sense P10.6 tested, but P10.6's own test always
bundled the final settling actor's completion and the driver-authorized
step into the SAME call — exactly the shape that hides this bug. A
genuinely separate later call to `respond` (RFC-Review-Lite's own normal
"objections raised now, proposer responds later" flow) is silently,
permanently refused. This is no longer a per-protocol nuance for P10.10
to casually classify — it is a live, reproducible defect already present
