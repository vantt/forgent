## 2. `protocol-loader.mjs` reused, not forked or duplicated — stated explicitly

Confirmed by direct read of `src/runner/definitions/protocol-loader.mjs`
(full header + both exports) before writing any code: it already implements
project/domain/core tiered discovery, `metadata.id@version` identity, and
duplicate/precedence handling exactly as `current-cell.md`'s central design
question predicted. `group-thinking-pack.mjs` imports and calls
`loadCoordinationProtocol` from that exact module for every real protocol
resolution (`resolvePackProtocol`'s only non-registry-file read) — it never
re-implements discovery, never re-validates a FlowDefinition document, and
never assigns a protocol a second id. The pack registry's own `{id,
version}` pairs are references to that canonical identity, never a
competing one: `resolvePackProtocol` refuses outright when the pack's
pinned `version` disagrees with what `loadCoordinationProtocol` actually
resolves (proved by the "pack-pinned version has drifted" test).

**Why the pack registry file lives OUTSIDE `core/coordination-protocols/`,
not inside it.** `protocol-loader.mjs`'s `scanTier('core', ...)` scans
`core/coordination-protocols/*.{yaml,yml,json}` NON-RECURSIVELY and
requires every file there to be a valid `CoordinationProtocol`-profile
FlowDefinition (`scanTier`'s own `spec.profile.kind !== 'CoordinationProtocol'`
rejection, `protocol-loader.mjs:180-185`). A pack-registry `.json` file
placed inside that directory would be picked up by that same scan and
rejected as a malformed document (or, worse, silently misread as an
attempted protocol) — this is not a stylistic choice, it is a real
collision `core/protocol-packs/` (a sibling, never-scanned directory)
avoids structurally. JSON (not YAML) was chosen for the registry itself
specifically because it needs zero dependency: `protocol-loader.mjs`'s own
header comment documents that its `yaml` package resolution is best-effort
(`.yaml`/`.yml` files silently skip when the package is unavailable) — a
JSON-only registry has no such failure mode.

## 3. Public request adapter and replay renderer boundary

**Adapter (`runGroupThinkingRequest`):** exactly one gate, then a straight,
unmodified forward into `runCoordinationUseCase` (`run.mjs`) — the same
door `fgos coordination run --file`/the headless adapter already call.
Verified by reading `run.mjs` in full before writing this module: its
request vocabulary is closed to four step kinds
(`operation`/`authorize`/`disposition`/`fan-out`, confirmed against
`src/verbs/coordination/schema.mjs:420-424`'s own step-type dispatch), and
`runCoordinationUseCase` always attempts `closeSessionByQuorum` as its own
final, automatic step. Nothing in `group-thinking-pack.mjs` adds a step
kind, a second close path, or a second validation pass —
`validateCoordinationRequest` (`schema.mjs`), called exactly once inside
`runCoordinationUseCase`, remains the single source of request-shape truth
(the gate's own pre-flight peek at `kind`/`protocolRef.id` is documented in
code as I/O-only, no schema validation of its own). Resume is inherited for
free: a request naming an existing `coordinationId` reaches `run.mjs`'s own
`findExistingManifest` path unchanged (proved by the "resuming through the
pack gate" end-to-end test).

**Renderer:** deliberately NO wrapper function. `fgos coordination show
<id> --json` is read-only and passive — a session opened under a
pack-approved protocol was already gated at RUN time; adding a gate on
`show` would narrow the existing public replay surface for no benefit and
contradicts "renders public replay" (Phase 10's own phrasing implies the
FULL existing replay, not a filtered subset). The skill's own step 5 calls
`fgos coordination show` directly, unmodified — zero new code for the read
side (YAGNI).

## 3a. Mid-flight addendum (2026-09-04): per-actor provider/tier is preserved, not collapsed

The Coordinator relayed a user-driven hard requirement mid-flight: this
cell's own request-adapter boundary must not collapse a group-thinking
session onto one hardcoded provider — at minimum Claude/Codex/agy must be
able to collaborate within one session under the real `cli-spawn` model.
Checked against the actual design (§3 above), not assumed compliant:

**Where a caller expresses "actor A uses provider X, actor B uses provider
Y":** in `actors[]` on the request object itself — `{id, executor?,
model?, tier?, persona?}` per actor (`ACTOR_ALLOWED_KEYS`,
`src/verbs/coordination/schema.mjs:122`), exactly the same field a
hand-authored `fgos coordination run --file` request already uses.

**Why it reaches `run.mjs`'s real per-actor resolution unchanged:**
`runGroupThinkingRequest` never reads, validates, filters, or reconstructs
`requestObject.actors` at all — confirmed by reading its own source
(`group-thinking-pack.mjs`): the ONLY fields it peeks are `kind` and
`protocolRef.id` (`peekRequest`, used solely for the explicit-selection
gate, §5 #1 below); everything else, including `actors[]`, is forwarded
byte-for-byte into `runCoordinationUseCase(ctx, { requestPath,
requestObject, ...runOptions })`. `run.mjs` then resolves each operation
step's actor policy exactly as it would for any hand-authored request:
`actorPolicyFields(actorEntry, ...)` where `actorEntry =
step.targetActorId ? findActor(request.actors, step.targetActorId) :
undefined` (`run.mjs`) — this cell's gate sits entirely outside that path
and cannot narrow it, because it never touches it.

**Proof, not assertion:** `test/verbs/coordination-group-thinking-pack.test.mjs`'s
new test ("a request naming a DIFFERENT executor per actor reaches
run.mjs's real per-actor actorPolicyFields resolution unchanged...")
registers TWO real, distinct executors in a fake `runnerConfig.executors`
map (same registered-executor shape
`test/runner/coordination-visibility-window-fixture.test.mjs`'s own
`fakeCohortRunnerConfig` uses for its real 3-provider-family fixture — not
invented for this cell), assigns one to each of `declared-consult.yaml`'s
two actors via `actors: [{id: "requester-actor", executor:
"exec-actor-a"}, {id: "consultant-actor", executor: "exec-actor-b"}]`,
dispatches through `runGroupThinkingRequest` end to end, and asserts the
two resulting steps carry DIFFERENT `executor`/`provider` values
(`exec-actor-a`/`family-a` vs. `exec-actor-b`/`family-b`) — confirmed live
in the dispatch log itself (`dispatch ... executor=exec-actor-a
via=cli-spawn provider=family-a ...` then `executor=exec-actor-b
via=cli-spawn provider=family-b ...`), not inferred from a return value
alone. 15/15 in this file, including this one (§6).

**What this does NOT prove, named honestly:** real `codex-cli`/`agy-cli`/
`agy-herdr` dispatch (this repo's actual registered executors) was not
exercised in this test — those need their real CLI binaries installed,
which this sandboxed test environment does not carry; the fake-executor
substitution is the SAME established precedent every other coordination
test in this repo already uses (`coordination-declared-consult.test.mjs`,
`coordination-run-live-proof.test.mjs`, the visibility-window fixture
cited above) to prove the MECHANISM without a real-binary dependency. The
mechanism proven — per-actor `executor` genuinely reaching
`actorPolicyFields`, genuinely producing a different `provider` per
actor — is executor-id-agnostic: nothing in `group-thinking-pack.mjs` or
`run.mjs`'s resolution path branches on WHICH executor id is named, so a
real run against `codex-cli`/`agy-cli` would take the identical code path
this test already exercises. Also NOT this cell's job (explicitly, per the
addendum itself): proving RFC-Review-Lite/Nominal-Group-Lite/
Delphi-Feedback-Lite (P10.2-P10.4) actually ASSIGN different providers to
different personas/roles — that is those cells' own responsibility; this
cell's obligation was only to confirm its own boundary does not make that
impossible, which is now proven rather than assumed.

**FlowDefinition-level per-actor policy (`spec.actors[].policy`) is
likewise untouched.** `resolvePackProtocol` reads only
`definition.metadata.version` (for drift-checking, §2) — it never reads,
copies, or overrides `definition.spec.actors[].policy` in any way, so a
protocol document's own declared per-actor `preferExecutor`/`minTier`/
`fallbackExecutors`/`preferPersona` defaults (the second of the two
levels the addendum names) flow to the engine exactly as they would
without this pack in front of them.

## 5. The five bypasses, one by one — why each is structurally impossible

Read against the real code, not asserted from design intent alone:

1. **Switch protocols silently.** `resolvePackProtocol`'s first check
   (`typeof protocolId !== 'string' || protocolId.trim() === ''`) refuses
   before the pack file is even read. `runGroupThinkingRequest` additionally
   refuses when the request body's own `protocolRef.id` disagrees with the
   caller's `protocolId` — two independent points of explicit agreement,
   never a default. Both proved directly (`resolvePackProtocol refuses an
   unset or empty protocol id`, `runGroupThinkingRequest refuses when the
   request body's protocolRef.id disagrees...`).
2. **Bypass grants.** The `authorize` step type in `run.mjs`'s vocabulary
   dispatches through `authorizeDeclaredOperation`
   (`session-engine.mjs`) — the exact same mediated door, with the exact
   same context-grant enforcement, every hand-authored request already
   uses. `group-thinking-pack.mjs` never imports `session-engine.mjs`,
   `store.mjs`, or `schema.mjs` from `src/runner/coordination/` at all
   (confirmed by its own import list) — there is no second grant path for
   it to add.
3. **Validate its own aggregate.** Confirmed by reading
   `src/verbs/coordination/schema.mjs:420-424` directly: the request
   `steps[].type` switch recognizes exactly `operation`, `fan-out`,
   `authorize`, `disposition` — nothing calls
   `validateSessionAggregation` or any aggregation-validation door. Since
   `runGroupThinkingRequest` forwards the caller's request UNMODIFIED into
   this exact validator, there is no request shape this surface can ever
   construct that reaches that capability — it is absent from the door's
   vocabulary, not merely refused by an added check.
4. **Authorize a specialist.** Same reasoning as #3: `authorizeSpecialistSlot`
   / `recordSpecialistAuthorization` are reached only from
   `session-engine.mjs`/`store.mjs` call sites this module never imports,
   and `run.mjs`'s own `authorize` step type is wired to
   `authorizeDeclaredOperation` only (confirmed by reading `run.mjs`'s
   `authorize`-branch code, `run.mjs:415-461`) — a structurally distinct
   function from specialist authorization, never a shared one.
5. **Close a session directly.** `runCoordinationUseCase` calls
   `closeSessionByQuorum` unconditionally as its own last step
   (`run.mjs:522-534`), gated entirely by the engine's own quorum/
   aggregation rules — there is no separate, caller-invocable "close" verb
   anywhere in `run.mjs`'s public surface, and `group-thinking-pack.mjs`
   introduces none. Every request through this pack closes (or does not)
   exactly as any hand-authored request already would.

The common thread: none of these five properties needed a defensive check
written INTO this cell's own code, because the ONE door this surface calls
(`run.mjs`) never exposed any of the five as a caller-invocable action to
begin with. This was verified by reading `run.mjs`/`schema.mjs` directly,
not assumed from Phase 10's own framing.

## 9. Design Notes — judgment calls made, and why

- **Whether existing `deliberation-*-chain.yaml` fixtures (P08.3) belong
  in the pack: no, deliberately excluded.** `core/coordination-protocols/deliberation-{rfc,nominal-group,delphi}-chain.yaml`
  are close in spirit to RFC-Review-Lite/Nominal-Group-Lite/
  Delphi-Feedback-Lite (confirmed by reading all three headers), but they
  are P08.3's own method-shaped PROOF fixtures for the MVP8 schema
  mechanism — named `deliberation-*-chain`, not the Phase 10 "*-Lite"
  family, and built before Phase 10's own per-protocol scope constraints
  existed (e.g. RFC-Review-Lite's "no general comments/thread service").
  Aliasing them into this pack would risk exactly what "index protocols by
  canonical id... do not create a second protocol identity" warns
  against — the pack does not get to decide a differently-scoped,
  differently-named document IS one of P10.2-P10.4's protocols. Named as
  a real interpretation call, not asserted as obviously correct.

## 11. Fix round 1 (2026-09-04) — independent Red-Team HIGH finding, closed

An independent Reviewer + Red-Team pair audited this cell in parallel
(current-cell.md's own "P10.1 Disposition" section). Reviewer found
nothing. Red-Team found and empirically proved one real HIGH-severity gap
in this cell's own headline promise; this section documents the fix,
verified against real code and real tests, not asserted from intent.

### 11a. The finding, restated precisely

`resolvePackProtocol`/`runGroupThinkingRequest`'s pre-fix self-consistency
check (`peeked.protocolRef.id === protocolId`) only verified the CALLER's
own claim was internally self-consistent and a pack member -- it never
cross-referenced that claim against the session's REAL bound protocol
(`manifest.definitionRef.id`) when `coordinationId` named an EXISTING
session. Live PoC: a session opened DIRECTLY (bypassing the pack) under a
real, non-pack-member protocol (`independent-research-fan-out-fan-in`),
then a `runGroupThinkingRequest` call against the SAME `coordinationId`
claiming a DIFFERENT, pack-registered protocol (`declared-consult`) --
self-consistent, so the pre-fix gate passed -- reached dispatch while the
session's real governing definition never changed. This falsified §5
bypass #1's proof as literally written (it only reasoned about the
FRESH-session case, never the resume case) and meant any non-pack
protocol, including `group-cognition-framework.yaml` (this track's own
permanent Do-Not-Touch), could in principle be dispatched against through
this surface today on an EXISTING session.

### 11b. The fix

`runGroupThinkingRequest` (`src/verbs/coordination/group-thinking-pack.mjs`)
now adds one additional gate, placed after the existing self-consistency
check and before the forward into `runCoordinationUseCase`: whenever the
peeked request names a `coordinationId`, the REAL manifest is resolved via
`resumeSession` (`session-engine.mjs`'s `resumeSession` -- literally
`replaySession`, re-exported, the exact same function `run.mjs`'s own
`findExistingManifest` already uses for this) and the claimed `protocolId`
is refused unless it equals `manifest.definitionRef.id`. A `CoordinationError`
with category `not-found` (no such session yet -- a genuinely fresh
`coordinationId`) is treated as "nothing to cross-check," identical to
`findExistingManifest`'s own semantics; any other error propagates
unchanged. A session whose `definitionRef` is `null` (opened as
`kind:"agent-led"`, so it has no bound protocol at all) is refused
outright against a `kind:"declared-protocol"` pack request.

**This reuses the real manifest resolver, never a second one.** No new
manifest-reading logic was written; `resumeSession` is imported once and
called with the same `{cwd, repoRoot, packageRoot}` shape `run.mjs` already
passes it.

**Import footprint, honestly updated.** This module's own header comment
previously stated it "never imports session-engine.mjs/store.mjs/schema.mjs
(runner-side) directly" -- that claim is no longer fully true and has been
corrected in the header: it now imports exactly one READ-ONLY function,
`resumeSession`, from `session-engine.mjs`, plus `CoordinationError` from
the runner-side `schema.mjs` (to recognize the "not-found" category, the
same way `run.mjs` does). This import grants no new capability relevant to
bypasses #2-#5 (bypass grants / validate its own aggregate / authorize a
specialist / close a session directly): `resumeSession` is a pure read (it
performs no dispatch, authorize, disposition, or close), so §5's reasoning
for those four bypasses is unchanged and still holds -- only bypass #1's
own proof needed correcting, which this fix round does in §11d below.

### 11c. `id` vs `id@version` — the design decision, and why

**Decision: compare by `id` alone, not `id@version`.**

The cross-check's job is to confirm the CALLER's claimed protocol IDENTITY
agrees with the session's REAL protocol identity -- not to additionally pin
an exact version match between "what the pack currently resolves for this
id" and "what version this session actually opened under."

Reasoning, checked against the real engine behavior rather than assumed:

- `resolvePackProtocol` (called earlier in the same function, unchanged by
  this fix) already refuses any drift between the pack's own pinned
  `version` and the CURRENTLY loaded FlowDefinition for `protocolId` --
  this is a version-drift gate that already exists and already runs before
  my new check. Duplicating a version compare in the resume cross-check
  would not close any additional gap that gate doesn't already close.
- Every door that actually GOVERNS a session's dispatch/authorize/close for
  its whole life -- `dispatchDeclaredOperation`, `authorizeDeclaredOperation`,
  `aggregationCloseParams` (`run.mjs`) -- resolves and version-checks
  against the session's OWN pinned `manifest.definitionRef.version`
  (confirmed by reading all three: each does
  `loadCoordinationProtocol(manifest.definitionRef.id, ...)` then compares
  against `manifest.definitionRef.version`, never against a request's
  claimed version). What `protocolId` "currently resolves to" is therefore
  irrelevant to what actually executes once a session is open -- only the
  `id` needs to agree for the caller's belief about WHICH protocol governs
  to be correct.
- A stricter `id@version` compare here would introduce a NEW refusal mode
  the vulnerability never implicated: resuming a still-open, legitimately
  older session after the pack (or the FlowDefinition file itself) later
  advances to a newer version of the SAME protocol id would then be
  refused, even though nothing security-relevant changed -- the session's
  real dispatch/authorize/close doors never cared about that newer version
  in the first place. Per this repo's own KISS/YAGNI baseline
  (`.claude/rules/development-rules.md`), adding a check that manufactures
  a new failure mode not required by the finding being fixed is the wrong
  trade.

`id`-only is therefore both sufficient to close the reported HIGH (a
protocol IDENTITY switch across a resume) and the minimal correct fix --
verified live: the new regression test in §11e fails without this check
and passes with it (confirmed by temporarily stripping the check and
re-running the test file, then restoring).

### 11d. §5 bypass #1, corrected

§5 bypass #1's original text reasoned only about the fresh-session case
(the explicit-selection checks that already existed). It is corrected here
to also cover resume, which is what this fix round actually closes:

**1. Switch protocols silently (corrected).** Two checks now run before
any request is forwarded: (a) `resolvePackProtocol`'s own checks (unset/
empty id refused before the pack file is even read; unregistered id
refused; pack-pinned version drift refused) and the request body's own
`protocolRef.id` must agree with the caller's explicit `protocolId`

has nothing to cross-check (there is no real bound protocol yet), so (a)
alone remains sufficient there, exactly as originally reasoned; an existing
session now has both (a) and (b), closing the gap Red-Team proved live.

Bypasses #2-#5 are unchanged from the original §5 text -- none of their

### 11e. TOCTOU (LOW/INFO) — closed, not merely documented

Closed, not a residual.
