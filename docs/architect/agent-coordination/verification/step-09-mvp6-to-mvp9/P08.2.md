## Finding on requirement 3 (read before assuming — the answer is "no")

`assertDispositionRefOwnedBySession` (`store.mjs:1012`) does **not** already
make a contribution-id `targetRef` safe. Reading the real code, it asks exactly
two questions per `/`-separated segment:

- does the segment name a *different* coordination session's directory on disk?
- does the segment match `/^asgn_/` **and** exist under `.fgos/assignments/`
  **and** not appear in `manifest.assignmentRefs`?

A contribution id is neither. It is pure ledger state with no `.fgos/`
directory of its own, so a bare `contrib_whatever` matches no segment rule,
resolves against nothing, and sails through unchecked. Concretely, before this
cell a disposition could target a contribution that never existed, or one
belonging to a different session, and both would be accepted. That is
literally the Bug Taxonomy entry "a disposition able to target a contribution
from a DIFFERENT session".

**An explicit check was therefore added**, mirroring the Assignment-ownership
check's own shape (prefix-keyed, then resolved against what this session
actually owns):

- `CONTRIBUTION_REF_PREFIX = 'contribution:'` (`schema.mjs`) — a reserved ref
  namespace, the same device `protocol-operation:` already establishes in this
  codebase. A ref in it must name a contribution **this session's own log
  linked**; anything else is `dangling-ref`.
- `assertDispositionRefOwnedBySession` gains a `contributionIds` set, supplied
  by `recordDriverDisposition` from a **lock-held** `readEvents`, so the answer
  is computed against the log as it is at the moment of the write. Defaulting
  to an empty set makes an unsupplied set refuse every `contribution:` ref
  rather than skip the check.
- It applies to `evidenceRefs[]` identically — same loop, same rule.

A **bare** contribution id keeps its pre-existing meaning (an opaque ref this
codebase has no registry to resolve) and can never target a contribution. That
is deliberate: inventing an id-shape constraint would have forced a naming
convention on contribution ids, which P08.1 leaves free.

## Design Notes

### Two doors, and which question each can answer

Exactly the P07.3 split. `store.mjs` has no definition and can never have one
(it sits below `session-engine.mjs` in the import graph), so it owns the
questions answerable from the manifest and the log alone: driver identity,
session membership, runId shape, artifact-ref scope, contribution-id
uniqueness, and lineage resolution. `session-engine.mjs`'s
`linkSessionContribution` owns everything that needs the bound protocol:
which operation the backing Assignment actually performed, which window gates
it, whether that window is open, and what the immutable pin is. A caller
reaching the raw door directly still cannot forge identity, membership, or
lineage — it can only bypass the *definition-aware* half, which is the same
unmediated-store-door boundary Phase 06 and Phase 07 already named.

### What the payload deliberately does not carry

Two fields from P08.1's contribution shape are absent from the event payload,
and neither is an oversight:

- **`sessionId`** is a `FORBIDDEN_FIELD_NAMES` entry (ADR-008 Decision 5),
  rejected at any nesting depth in any coordination event payload. This is a
  better answer than persisting it: the log *is* the session, so the doors
  reconstruct `sessionId` from `coordinationId` and hand P08.1's validator a
  value no caller could have set. `validateSessionMembership` therefore cannot
  fail on the mediated path — by construction, not by luck.
- **`ts`** is stamped on the event envelope by `state/events.mjs` for every
  event kind, so no kind in the Event Log table carries one as a payload
  field. The Candidate Contract's "timestamp" is that envelope stamp,
  projected back onto the record by `replay.mjs` exactly as it is for
  `aggregation-validated` and `driver-disposition-recorded`.

`linkedBy` was added beyond P08.1's field set, matching
`validatedBy`/`authorizedBy`: linking a contribution is ledger state the
session's driver writes, and replay refuses one linked under any other
identity.

### Why cycles are unrepresentable rather than merely detected

P08.1's Gaps named two P08.2 ledger-layer obligations: anchors are resolved
but never walked (so an anchor cycle or a self-anchor validates), and duplicate
contribution ids are not rejected. Both are closed here, and the anchor one is
closed structurally rather than by adding a traversal:

- `knownContributions` is built from the contributions **already linked**, and
  the candidate's own id is never in it (the duplicate-id check refuses a
  reused id first). So a self-anchor and a self-response are *dangling* refs.
- A two-node cycle needs a back edge from an older contribution to a newer
  one, which an append-only ledger cannot produce: the first would have to
  name the second before the second exists.
- At replay, the same validators run against the contributions accepted **so
  far in the walk**, so a log hand-written to contain a cycle is refused when
  the first node names a ref that has not appeared yet.

Adding an anchor-graph traversal would have been a second mechanism guarding a
state the ledger shape already makes unreachable.

### Open/resolved as a derivation

`replaySession` returns `contributions` / `ignoredContributions` (records with
no status field of any kind — asserted) plus `resolvedContributionIds` and
`openContributionIds`, computed after the walk as an intersection with the
`contribution:`-prefixed `targetRef`s of pre-terminal dispositions. The two
lists partition the linked set exactly, and a disposition naming a contribution
this session never linked resolves nothing (refused at the write door, refused
again by the intersection on a hand-written log). Post-terminal dispositions
are excluded on the same footing as every other post-terminal neutralization
here.

### Requiring a window is a real constraint, and a contract-aligned one

P08.1 made `visibilityWindowRef` **required** on every contribution, so
enforcement is unconditional rather than opt-in. Combined with deriving the
ref from the binding, this means a binding that declares no
`contextAccess.visibilityWindowRef` cannot contribute at all — refused with a
named error. That is stricter than "gate it when a ref happens to be present",
and it matches phase-08's own Exit bullet ("Contribution lineage is durable,
bounded by declared operation types, and **visibility-controlled**"). A
protocol that wants deliberation memory must gate the contributing binding.

### The disposition door has a read-side mirror, and it had to move too

`src/verbs/coordination/show.mjs` carries `isRefOwnedBySession`, a
boolean-returning duplicate of `assertDispositionRefOwnedBySession` (duplicated
rather than imported because `store.mjs` sits below it in the import graph and
the helper is unexported). Adding the `contribution:` rule to the write door
alone would have left `show` reporting a forged cross-session contribution ref
as session-owned — a silent divergence in exactly the mirror whose own comment
promised there would not be one. Both were changed in this commit, the mirror
reads its id set from `replaySession`'s accepted `contributions` (never
`ignoredContributions`), and the file's header comment now states the
obligation explicitly so the next rule added to that door does not repeat it.

### A pre-existing MVP6 residual this cell ran into (not introduced, not fixed)

`dispatchDeclaredOperation`'s visibility-window gate (`session-engine.mjs:1976`)
lives **inside the `isDriverAuthorized` branch**. A binding with
`activation.mode: required` that declares `contextAccess.visibilityWindowRef`
is therefore dispatched with **no window check at all**. This is P06 territory,
closed, and out of this cell's scope to change — but it is worth recording for
two reasons. First, it is why this cell's window test needed no hand-crafted
state: a `required` binding with a window ref can be legitimately dispatched
while its window is closed, which is exactly the state the link door must
refuse. Second, it means the link-time re-derivation is the *only* window
enforcement for that binding shape, which raises rather than lowers its value.
The refusal is proven by test, both states, in one fixture.

## Gaps

- **`contributions.allowedTypes[]` has no declaration channel, so the
  operation/type gate cannot narrow.** The headline Concern above. Closing it
  is one field on `spec.operations[]` (or on `result`) in
  `src/runner/definitions/schema.mjs` plus a one-line change to how
  `linkSessionContribution` builds `declaredOperations` — the wiring is already
  in place and pointed at the right place; only the schema field is missing.
  Assigned to whichever cell owns `src/runner/definitions/*` next (P08.3 or
  P09.2), and it should be treated as **required** for the phase's Exit bullet
  "bounded by declared operation types" to be true, which today it is not.
- **`knownAssignments` provenance checking is self-consistent, not
  independent.** `linkSessionContribution` derives `operationRef` from the
  Assignment's stamp and builds `knownAssignments` from that same stamp, so
  `validateAssignmentProvenance`'s three checks can never fire on the mediated
  path. That is not a weakness — the derivation is strictly stronger than the
  check it makes redundant — but the Proof Matrix does not claim P08.1's
  `knownAssignments` channel is doing work here, because it is not. It would
  do real work for a future caller that takes `operationRef` from somewhere
  else; none does.
- **Contract documents not updated.** `coordination-session.md`'s Event Log
  table does not yet carry `deliberation-contribution-linked`, and its
  `driver-disposition-recorded` section does not yet document the
  `contribution:` ref namespace. Following the precedent both P06 and P07 set
  (contract text promoted in the *proof* cell — P06.3, and deferred to P07.4 by
  P07.3 for the same reason), promotion belongs with P08.3. The names remain
  candidate names until then. This is the largest documentation debt this cell
  leaves.
- **`dispatchDeclaredOperation` does not gate a `required` binding's declared
  visibility window** (see Design Notes). Pre-existing P06 residual, not
  introduced here, not fixed here — but it means an ungated dispatch can occur
  for a binding whose contributions this cell then refuses. Worth a P06
  follow-up decision: either the dispatch gate should cover `required`
  bindings too, or `contextAccess` should be declared illegal on one.
- **No CLI/`show` surface.** `replaySession` now returns `contributions`,
  `ignoredContributions`, `openContributionIds`, and `resolvedContributionIds`
  ready to render; nothing under `src/verbs/coordination/` was touched, and
  `linkSessionContribution` has no production caller yet — the same "available
  API, not yet an enforced protocol property" shape P07.3 flagged for
  aggregation. P08.3's method-shaped proofs are the natural first caller.
- **`revision` currency is checked once, at link time.** A contribution links
  a pin that matched the bytes at that instant; an artifact edited *after* the
  link still leaves the link standing, with a pin that no longer matches. That
  is correct for an immutable lineage record (the whole point is that the link
  is not rewritten), but a reader who wants "is this contribution's artifact
  still current" has to recompute it, and no helper does that yet.
- **No test drives a contribution through a real `specialist-request` or
  `rank` type end to end.** All six types are proven legal at the event layer;
  the runtime layer exercises `proposal`. The method-shaped chains (RFC,
  Nominal-Group, Delphi) are explicitly P08.3's scope.
- **Impact analysis not run** (see above).
