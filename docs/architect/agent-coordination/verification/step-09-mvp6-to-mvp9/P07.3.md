## Design Notes

### `completion.aggregation` is a sibling of `mode`, not a mode value

`PROTOCOL_COMPLETION_FIELDS` gains one optional key. When it is absent,
`validateProtocolProfile` builds `{ mode }` and freezes it — the same object
the old single-line `Object.freeze({ mode: profile.completion.mode })`
produced. The regression test asserts that literally (`deepEqual`, key list,
`'aggregation' in …` false), not by inspection. `mode` stays *required*
whenever `completion` is present, which is pre-existing behavior deliberately
left alone: declaring only `aggregation` is still rejected.

### The evaluator is fed derived evidence, never caller claims

`validateSessionAggregation` has **no `outcome` parameter**. The caller
supplies identity (`aggregationId`, `validatedBy`), the aggregate's own
output refs, and `dissentRefs`; everything the verdict depends on is derived:

- *Which operations are sources* — the definition's own declaration.
- *Which Assignments answer them* — `resolveOperationOutcome`, the SAME
  stamp-verified derivation visibility windows use. An Assignment that merely
  shares an actor or a claim key answers nothing (P06.2's reserved
  `protocol-operation:` stamp is the only channel consulted).
- *Each source's artifact ref, revision pin, and disclosures* — read off the
  linked RunResult on disk.

`dissentRefs` stays a caller parameter on exactly the footing
`synthesizeResearchFanIn`'s `contradictions` and `closeSessionByQuorum`'s
`dissentingActorIds` already established: this engine has no semantic model of
disagreement and never infers one.

### The immutability pin is the settle-report sha256, and staleness is real

P07.1 flagged reconciling the evaluator's `AggregationSource` shape with the
real dispatch-side RunResult as P07.3 work. The mapping chosen:

| Evaluator field | Session-derived source |
|---|---|
| `sourceOperationRef` | the declared operation, proven by the reserved stamp |
| `assignmentId` / `runId` | `assignment-created` / latest `result-linked` |
| `artifactRef` | `settleReports[].path` (opaque identity only) |
| `revision` | `settleReports[].sha256` |
| `disclosures` | `{status, confidence}` from the RunResult, `dissent` from `status === 'blocked'` |

`settleReports` exists in `assignment-runner.mjs` for precisely this purpose —
its own comment says "a report planted or edited after settle is not in the
set (or no longer matches) and can never satisfy a report gate". So
`currentRevisions` is that same file's hash **recomputed now**, which makes
`validateSourceRevisionCurrency` a genuine tamper check rather than a
tautology. The "artifact edited after settle" test edits `agent-report.md`
after the run settles and gets `no-consensus` with one
`staleSourceKeys` entry.

**The report file is located by DERIVING its path** from the validated
`assignmentId`/`runId` (identical derivation to `readLinkedRunResultFromDisk`,
including `assertValidRunIdForAssignment`'s full-shape check), never by
joining `settleReports[].path` out of `result.json`. Joining that string would
make a hand-edited `result.json` a path-traversal surface — exactly the class
R6 closed for `runId`. The stored path is used only as an opaque map key.

Disclosures are **engine-classified, never worker-asserted**: `status` and
`confidence` are `classifyRunEvidence`'s verdict on the filesystem, not the
worker's `agentClaim`. `dissent` is a fixed marker derived from `status`, not
parsed from any prose — no text is interpreted for meaning anywhere in this
path.

A `requiredDisclosures[]` id the engine cannot derive is not silently skipped;
it fails the evaluator's disclosure coverage and forces `no-consensus`
(tested).

### All-of over bindings, at two levels

`resolveOperationOutcome` already computes `satisfied: branches.every(...)`.
This wiring honors it: when any binding of a source operation is unsatisfied,
that operation contributes **no source at all**, so the evaluator's own
coverage check fails it. The same rule applies one level deeper — if any
binding settled without a usable revision pin, none of that operation's
bindings contribute.

This was a real correction made during the cell, not a design that fell out
free. The first implementation contributed each satisfied branch
independently, which let a half-answered cohort pass coverage and reach
`consensus` — the partial-cohort bypass P06 refused one layer down. The
"half-answered cohort" test locks the corrected behavior: `research` reports
`missingSourceOperationRefs: ['research']` even though researcher-a's own
result was settled and pinned.

A consequence worth stating: this makes
`consensus ⇒ missingActors/failedActors/unresolvedContributionRefs all empty`
true by construction, which is what lets replay check it (below).

### Terminal input is refuse-only

`closeSessionByQuorum` gains one optional `aggregationId`. Inside the existing
lock, it reads the validated record from `replayed.aggregations` (the event
log — never a caller-supplied verdict, and never `ignoredAggregations`) and
**throws** when the outcome is not `consensus`. It never selects a status,
never relaxes the `partialPolicy` rules, and never closes a session quorum
would have refused. So:

- the evaluator's return value cannot drive a transition (Bug Taxonomy #1);
- "aggregation never upgrades" holds by construction — narrowing only;
- omitting the argument leaves every path byte-identical, which the
  no-`aggregationId` regression test proves by leaving a `no-consensus`
  aggregation on the log and closing `completed` anyway.

`src/verbs/coordination/run.mjs:458` is the only production caller and passes
`{}`, so it is unaffected.

### No vote/score/convergence

`validateSessionAggregation` contains no arithmetic, no threshold, no tally,
no ranking. Its control flow is list building plus `.length` emptiness checks;
the verdict comes entirely from `classifyAggregationOutcome`, whose own
three-branch boolean rule P07.2 already grep-proved free of scoring.

## The forged-aggregate boundary, precisely

The Exit bullet says replay must reject "worker-shaped/self-validated
aggregate truth". Here is exactly what is closed and what is not.

**Closed — four shapes, each with a test and a named invariant:**

1. **Worker-typed validator.** `validatedBy.type` must be `"driver"`
   (`validateAuthorizedBy`, shared with `operation-authorized`). Refused at
   shape level, therefore also at replay, since `replaySession` runs
   `validateEventPayload` on every event it walks.
2. **Wrong driver identity.** `validatedBy.id` must equal this session's
   `manifest.provenanceRoot.writerId`. Enforced at write time by the shared
   `assertDriverIdentity`, and independently at replay time by a new check
   (replay has the manifest, so it can answer the session-scoped identity
   question the pure shape validator cannot). This is the check that catches
   a hand-appended event claiming a researcher validated its own work.
3. **Fabricated evidence.** Every `sourceResultRefs` entry must have an
   accepted `result-linked` **earlier in the same log**. An aggregate cannot
   cite a result the session never produced, or one that only settles later.
   `sourceResultRefs` may also never be empty.
4. **Self-validation.** The aggregate's own `assignmentId` may not appear
   among its `sourceResultRefs` (event level), and `outputOperationRef` may
   not appear in `sourceOperationRefs[]` (schema level).

Plus: duplicate `aggregationId` refused at replay; re-recording a *different*
verdict under one `aggregationId` refused at the store door; post-terminal
events neutralized into `ignoredAggregations` exactly as post-terminal
authorizations already are.

**Partially closed — one invariant, honestly scoped:**

5. **Internally impossible consensus.** Because of the all-of rule above, a
   real validation can never produce `consensus` while naming
   `missingActors`, `failedActors`, or `unresolvedContributionRefs`. Replay
   refuses that combination. This catches an *inconsistent* forgery — someone
   copying a real no-consensus event and flipping only the outcome. It does
   **not** catch a forger who simply omits those fields.

**NOT closed, and not closable by replay:**

The session's own driver calling `recordAggregationValidation` directly with
`outcome: 'consensus'` and a set of genuinely linked `sourceResultRefs`, with
no `classifyAggregationOutcome` call behind it, produces an event replay
accepts. Replay cannot detect this, and the reason is structural, not an
oversight: **replay is definition-blind by design** (`replay.mjs` imports
nothing from `src/runner/definitions/`), so it cannot know which operations
were declared sources, cannot re-derive the evidence set, and therefore cannot
re-run the evaluator to compare verdicts. Recording an inputs-hash on the
event would not help either — anyone able to write the event can compute the
hash, so it would be theatre, not a defense.

This is the **same unmediated-store-door trust boundary** Phase 06 already
named for visibility windows (`flow-definition.md`'s Residuals 1 and 3: the
raw `createSessionAssignment` door can write the reserved stamp; the raw
`recordActorReplacement` door can collapse two cohort branches). Nothing here
narrows or widens it. What the mediated path guarantees is that
`validateSessionAggregation` — the only door that *derives* evidence — cannot
be talked into a favorable verdict, because it takes no verdict as input.
What no layer guarantees is that a driver with direct store access used that
door at all.

Stated for the record so no reader mistakes the tested refusals for a
complete guarantee: **items 1–4 hold against anything, including a
hand-written `events.jsonl`. Item 5 holds only against a careless forgery.
A careful forgery by the session's own driver identity is not detected.**

## Gaps

- **`unresolvedContributionRefs` has no end-to-end runtime test.** It is
  populated when a satisfied binding settles with no usable settle-report
  pin. Today's runner emits at most one settle report per run and always
  emits one for a substantive report, so producing that state through the
  real dispatch path would require a RunResult shape this cell has no
  legitimate way to create. The field is covered at the event-schema and
  replay-consistency layers only.
- **`aggregationSourceFrom` refuses a run carrying more than one settle
  report** rather than choosing among them. Today's `assignment-runner.mjs`
  pushes at most one (the single `agent-report.md`), so this is a guard
  against a shape with no declared rule, not a routine branch — but it means
  a future runner emitting multiple report artifacts would silently make
  every aggregation `no-consensus` until a selection rule is defined.
- **Hidden-dissent is wired but not exercised end to end.** The
  `disclosures.dissent = 'blocked'` mapping makes the evaluator's
  hidden-dissent check live on the real path, but no runtime test drives a
  branch to `status: 'blocked'` and asserts the resulting `no-consensus`. The
  mapping is asserted by design reasoning and by P07.2's own unit tests of
  `validateDissentSurfacing`, not by a session-level fixture here.
- **Nothing requires an aggregation when a definition declares one.**
  `closeSessionByQuorum` consults an aggregation only when the caller passes
  `aggregationId`; it does not hold the FlowDefinition and so cannot notice
  that the protocol declared `completion.aggregation` and no one validated
  it. A protocol author can therefore declare an aggregation and close the
  session without ever running it. Closing that needs the definition at the
  close site — plausibly P07.4 (Surface And Regression Proof) work.
- **No CLI/`show` surface.** Deliberate: `current-cell.md` names a large CLI
  surface as P07.4's job. `replaySession` now returns `aggregations` /
  `ignoredAggregations` ready for that cell to render; nothing under
  `src/verbs/coordination/` was touched.
- **Contract documents not updated.** `coordination-session.md`'s Event Log
  table and `flow-definition.md`'s `CoordinationProtocol` profile section do
  not yet carry `aggregation-validated` / `completion.aggregation`. P06's own
  pattern promoted contract text in the *proof* cell (P06.3), not the
  implementation cell (P06.2); following that precedent, promotion belongs
  with P07.4. The candidate names remain candidate names until then.
