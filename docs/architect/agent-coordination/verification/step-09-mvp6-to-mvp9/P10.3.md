## 2. The shape, and why it is genuinely new (not a P08.3 copy)

The plan's own bullet names FOUR things: private proposals, controlled
sharing, clarification, private rank. The Phase 08 proof fixture folds
"controlled sharing" into a bare visibility window (`reveal`) with no
operation of its own, and used a 2-participant cohort. This definition
takes the plan's own wording literally instead:

- **3 participants** (`participant-a/b/c`), not 2 — a real cohort-size
  difference, not cosmetic: the `shared` window's `opensAfter` now requires
  all THREE bindings of `private-propose` to settle (proven by the second
  test in this file, which shows the window still shut after only two of
  three have proposed).
- **`share` is its own explicit, driver-authorized, facilitator-run
  operation**, distinct from `clarify` — the "controlled sharing" step the
  plan names is not collapsed into `clarify` the way the MVP8 fixture did.
  This is a real schema/sequencing distinction (an independently-probed,
  correctly-refused `clarify`-before-`share` ordering check confirms it),
  but — same limitation as P08.3's own precedent, named there too — this
  cell's tests prove only grant-LEGALITY timing (can the authorization be
  recorded once the window is open), never differential content
  visibility between `share` and `clarify`, since neither this cell nor
  P08.3's fixture ever threads a non-empty `contextRefs` into the
  dispatched Assignment's own contract. Scoped correctly to
  context-injection-gate sequencing, not information-theoretic secrecy.
- **Four visibility windows**, one per phase transition, each gating a
  genuinely LATER, different operation than the one it protects — never
  self-referential:
  - `private-open` (vacuous, `opensAfter.operationRefs: []`) gates
    `private-propose`.
  - `shared` (opens once all three `private-propose` bindings settle) gates
    `share`.
  - `clarified` (opens once `share` settles) gates `clarify`.
  - `ranking-open` (opens once `clarify` settles) gates `private-rank`.

This four-window chain is not a stylistic choice. P08.3's own Design Notes
(read in full before writing this definition, per current-cell.md's Must
Read #3) proved empirically that `linkSessionContribution` refuses ANY
operation whose own contribution-bearing binding is gated by a window that
opens only after that SAME operation's own cohort settles — an operation's
Run is always AUTHORIZED before the settlement such a window would wait
for, so the position comparison `runAuthorizedSeq <= windowOpenedAtSeq` is
true 100% of the time for a self-referential shape. I read that finding
before designing this chain and built every window to open on a strictly
earlier, different operation from the start, rather than rediscovering the
refusal empirically the way P08.3 itself did on its first draft.

**No tally/winner semantics anywhere.** No `completion.aggregation` is
declared. `private-rank`'s contributions are durable, per-participant
`rank`-typed ledger entries (the closed MVP8 enum) with no reduction,
comparison, or aggregate computed over them by this definition or its test
file — proven directly by asserting `replaySession(...).aggregations` is
empty in the end-to-end test.

`metadata.id`: `core.coordination-protocol.group-thinking-nominal-group-lite`
— grepped against every existing `core/coordination-protocols/*.yaml`
before picking it (§6); no collision with
`core.coordination-protocol.deliberation-nominal-group-chain` (Phase 08) or
any other shipped id. File name (`group-thinking-nominal-group-lite.yaml`)
follows current-cell.md's own suggested example verbatim, and does not
collide with P10.2/P10.4's own sibling worktrees (checked by listing their
`core/coordination-protocols/` directories directly before writing this
file — neither had created its own new fixture file yet).

## 3. Per-actor provider/tier requirement: built and proved live

**This cell builds it.** Not left to a sibling.

`spec.actors[].policy.minTier` differs by role in the definition itself —
`facilitator-actor: standard`, `participant-a/b/c: lightweight` — a real,
portable, per-actor REQUIREMENT declared in the FlowDefinition. A literal
`preferExecutor` pin is deliberately **not** declared at any portable scope
(definition/operation/role/actor): reading
`session-engine.mjs:assertNoPortableExecutorPin` before writing this
fixture confirmed it rejects exactly that shape outright
("a portable protocol/role/actor scope must express requirements
(minTier, capabilities) only, never a concrete executor pin"), matching
`flow-definition.md`'s own PolicyPatch section verbatim.

The genuinely-DIFFERENT-EXECUTOR half of the requirement is proved live
against the real dispatch door instead, at the one scope the contract
legally allows to carry a literal pin: `dispatchDeclaredOperation`'s
`cliPolicy` parameter. The third test in
`coordination-nominal-group-lite.test.mjs` registers two real executors
(`exec-facilitator`/provider `family-facilitator`,
`exec-participant`/provider `family-participant`, the same registered-
executor shape `coordination-visibility-window-fixture.test.mjs`'s own
`fakeCohortRunnerConfig` already uses), dispatches a participant and the
facilitator each with its own `cliPolicy.preferExecutor`, and asserts the
two resulting `RunResult.policy.provenance` records carry genuinely
different `executor.value`/`provider.value`, each correctly sourced to
`{scope: 'cli', id: 'cli'}` — confirmed live in the dispatch log itself
(`executor=exec-participant ... provider=family-participant ...` then
`executor=exec-facilitator ... provider=family-facilitator ...`), not
inferred from a return value alone.

**A real finding surfaced while proving this, named honestly.** The same
test also asserts the definition's own `minTier` is genuinely read (not
merely present in the YAML) by checking the ACTUAL resolved tier value per
role (`lightweight` vs `standard`). Its provenance SOURCE label, however,
is coarser than I expected going in: `resolveAssignmentDispatchPolicy`
(session-engine.mjs) threads a resolved `minTier` into the inline
Assignment contract only when it is **strictly below** the hardcoded
`'standard'` default floor — reaching `opPolicy` scope, never the finer
`operation`/`actor` scope that actually declared it — and a resolved tier
**exactly equal** to that same `'standard'` floor is indistinguishable from
never having been declared at all (`{scope: 'default'}`), because the
raise-only comparison against the default floor is strict `>`, never `>=`.
I found this empirically (probed the real provenance object directly
before writing the final assertions, §6), traced it to the exact,
already-documented reasoning in `dispatchDeclaredOperation`'s own header
comment (not a new bug — a known resolution-granularity limit of an
existing mechanism), and wrote the test to assert the REAL observed
behavior rather than the finer attribution I originally assumed. Only a
tier declared **strictly above** `'standard'` would attribute to the real
declaring scope. Named as a Gap below for whichever future cell wants to
build a stronger per-actor-scope provenance proof.

  proving the per-actor requirement (§3).** A tier at or below the
  hardcoded `'standard'` default floor cannot be attributed, at the

  (`operation` vs `actor`) that actually declared it — only a tier
  STRICTLY ABOVE `'standard'` gets real scope attribution via the
  `cliOverride`/`resolveStrongerTier` channel. This is a pre-existing
  limit of `session-engine.mjs`'s `dispatchDeclaredOperation`
  (`resolveAssignmentDispatchPolicy`'s own default-floor comparison,
  documented in that function's own header comment), not introduced by
  this cell and out of this cell's Do-Not-Touch scope
  (`src/runner/**`) to fix. Worth a future cell's attention if a stronger
  per-actor-scope provenance proof is ever needed below/at the `'standard'`
  tier specifically.
- **No CLI/`show` rendering exercised for this definition specifically.**
  This cell proves the engine-door chain end to end (matching P08.3's own
  proof-fixture style), not a rendered replay view — the same
  "available API, not yet a rendered CLI surface" shape every prior proof
  fixture in this track has left for a later cell, if one is ever needed.
- **`share`'s own settlement carries no contribution type.** Deliberately:
