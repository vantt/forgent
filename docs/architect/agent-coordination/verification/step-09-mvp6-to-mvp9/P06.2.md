## Requirements (phase-06-mvp6-visibility-windows.md, P06.2 cell)

1. Derive milestone state (window open/closed) from listed `result-linked`
   events already in the session's event log — no new stored "window
   state" field.
2. Keep the window closed for missing, late, or failed source obligations.
3. Allow an accepted `actor-replaced` lineage to satisfy the original
   source obligation without rewriting history (the original event stays
   in the log, untouched).
4. At both `authorizeDeclaredOperation` and `dispatchDeclaredOperation`,
   require every granted context ref to satisfy BOTH existing same-session
   ownership (`assertRefsOwnedBySession`, unchanged) AND active-window
   legality (new).
5. Persist no duplicate "visibility-window-applied" truth — pure
   derivation from existing events, recomputed identically by replay.

## Design Notes (why this shape)

**One derivation function, two call sites, never cached.**
`deriveVisibilityWindowState(definition, windowId, replayed, fgosDir)` is
the ONE place window open/closed state is computed. `authorizeDeclaredOperation`
and `dispatchDeclaredOperation` both call it fresh (a new `replaySession()`
at authorize time; the SAME already-memoized `replayOnce()` reconstruction
dispatch already takes for its edge/authorization checks) — never a
cached/stored verdict from one call reused at the other, per the Bug
Taxonomy's "a window that silently stays permanently open once any single
source links (should re-check per-request, not cache/latch)". Both gates
are additive, placed alongside (never replacing) the existing
`assertRefsOwnedBySession` calls at their respective sites
(`session-engine.mjs:~1087` authorize, `~1609`/`~1639` dispatch, per
`current-cell.md`'s own citations).

**Source resolution reuses the actor-replacement pattern already proven by
`classifySessionQuorum`, not a new one.** `opensAfter.operationRefs[]` and
(structurally, though not currently enforced — see Gaps)
`permits.sourceOperationRefs[]` name `spec.operations[]` template ids, not
Assignment ids. Resolving "the Assignment that fulfils operation X" cannot
rely on `assignment-created.operationId`/`nodeId`, because those fields are
populated ONLY for a `driver-authorized` binding
(`DRIVER_PROVENANCE_COMPANION_FIELDS` in `coordination/schema.mjs` — they
"travel together" with `authorizationId` or not at all) — and the paradigm
visibility-window use case (P00.1: "private-first-pass vs.
post-independent-pass") is exactly REQUIRED source operations feeding a
later driver-authorized one. `assignment-created.actorId`, by contrast, is
always present (required field, every dispatch shape). So
`resolveOperationOutcome` resolves the operation's graph-bound actor via
`resolveDeclaredOperationActor` (the SAME resolver the function being
authorized/dispatched already uses), then follows any `actor-replaced`
lineage (`buildActorReplacementMap`, independently built here — same
semantics as `classifySessionQuorum`'s own `resolveEffectiveActor`, not a
shared helper, so this module stays a single self-contained read of the
event log per call) to the CURRENT effective actor, then classifies exactly
the way `classifySessionQuorum`/`synthesizeResearchFanIn` already classify
a settled Assignment (`missing`/`late`/`failed`/satisfied, the SAME
`status === 'failed' || confidence === 'failed' || confidence ===
'no-evidence'` vocabulary, never a second one — per the cell's own "do not
invent a second vocabulary" instruction).

**Actor-replaced test fixture uses the raw store door for the
replacement's own attempt, not `dispatchDeclaredOperation`.** A declared
operation's graph binding names a STATIC actor id
(`graph.nodes[].operations[].actor`); `replaceSessionActor` swaps who
fulfils a role SESSION-side (an `actor-replaced` event + a new
`actor-bound`) but never rewrites the FlowDefinition's own static graph, so
a subsequent `dispatchDeclaredOperation` call for the SAME `operationId`
would still resolve to the ORIGINAL actor id, not the dynamically-allocated
replacement. This mirrors reality: a replacement actor is typically a
cohort-planner allocation the static protocol never predeclared. The test
(and, by the same reasoning, any real caller materializing a replacement's
work) uses `createSessionAssignment`/`linkResult` directly — the exact
house style `coordination-recovery-and-quorum.test.mjs`'s own R1/R2
fixtures already use for this same reason — to produce the replacement's
`assignment-created`/`result-linked` events under the NEW actor id, which
`resolveOperationOutcome`'s lineage-following then picks up correctly. This
is a read-side (replay/derivation) proof, not a claim about how
`dispatchDeclaredOperation` itself routes a replacement's redispatch — that
remains out of this cell's scope.

**`permits.sourceOperationRefs[]`/`permits.delivery` are not enforced as a
per-ref filter (scope decision, see Gaps).** The cell's Goal text says
"every granted context ref must satisfy BOTH... ownership... AND
active-window legality" — implemented here as: a binding whose
`contextAccess.visibilityWindowRef` is set may not be authorized/dispatched
AT ALL unless its window is open (a binding-level gate, applying uniformly
to every ref granted to that binding, empty grant included). It does NOT
additionally filter individual `grantedContextRefs` entries against
`permits.sourceOperationRefs[]`. Reasons, stated plainly: (a) this
codebase's real `grantedContextRefs` values are frequently opaque,
non-`asgn_`-prefixed artifact strings (see
`coordination-driver-authorization.test.mjs`'s own existing
`'artifact:candidate@2'` fixture ref) that `assertRefsOwnedBySession`
itself already treats as unstructured and leaves alone — there is no
existing primitive in this codebase that maps such a ref back to "which
operation produced it", so building one would be new, untested surface
area outside this cell's Tests-First list; (b) the Tests-First list and Bug
Taxonomy for this cell test/name window open/closed gating exclusively,
never per-ref `permits` filtering. `permits.sourceOperationRefs[]`/
`delivery` stay exactly as P06.1 shipped them: schema-validated, structural
metadata describing intent, not yet a runtime filter. This is named
explicitly as a gap below for P06.3 (proof/promotion) to decide before any
contract text is promoted.

**Fan-out source operations are not disambiguated.** `resolveOperationOutcome`
calls `resolveDeclaredOperationActor(definition, operationId)` with no
`targetActorId` (first graph match only), matching that resolver's own
documented default behavior for every other omitted-`targetActorId` caller
in this file. A window whose `opensAfter.operationRefs[]`/
`permits.sourceOperationRefs[]` names an operation wired to MULTIPLE actors
(independent fan-out sharing one operation template) is not resolved
per-branch by this cell — named as a gap below.

  (P06.1) but not enforced as a per-ref delivery filter at runtime — see
  Design Notes above for the reasoning. P06.3 should decide, before any

  `permits.sourceOperationRefs[]` needs its own follow-up cell (which

  codebase does not currently have for non-`asgn_`-shaped refs).

  existing default-`targetActorId` behavior elsewhere, but not proven
