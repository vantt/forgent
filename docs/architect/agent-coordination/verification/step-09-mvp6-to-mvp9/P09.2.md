## 1. Requirements (current-cell.md's Goal / Central Design Question / Bug Taxonomy)

- Design and implement a real slot-to-actor binding mechanism: today no
  field resolves a graph operation's `actor` against a `specialistSlots[]`
  id (P09.1's own proven closure).
- Serialize slot authorization against terminal transition and competing
  slot claims.
- Atomically record authorization and session-scoped actor binding before
  any Assignment is issued.
- Reuse the existing `operation-authorized` door for each specialist
  invocation (not a new gate).
- Expiry prevents future Assignments but never erases actor/event history.
- Replacement requires a new driver authorization and remains within slot
  and session caps.
- Preserve every P09.1 closure property: a specialist may act ONLY on the
  slot's declared `operationRefs[]`, only with the slot's declared
  `role`/`requiredCapabilities`, only under the slot's declared
  `allowedVisibilityWindows[]`, never via `addSharedEdge`/topology
  mutation/undeclared expansion.
- Bug Taxonomy (pulled forward from P09.3): worker/peer authorization
  refused, unknown slot id refused, role/capability mismatch refused,
  over-cap binding refused (`maxBindings`), over-cap assignment refused
  (`maxAssignments`), foreign context refused (reusing
  `assertRefsOwnedBySession`), expired/terminal session refused with
  history preserved, the caller-supplied-definition bug class, no obvious
  non-atomic window between authorization and actor binding.

## 3. Design Notes

**The central design question: how does a slot id resolve to a dispatchable
actor?** A new optional `specialistSlotRef` field on the node-operation
binding shape (`NODE_OPERATION_REF_FIELDS`, `schema.mjs`), mutually
exclusive with `actor`, validated the same way `contextAccess` is
(`validateNodeOperationRef`) -- a slot id, never a literal actor id, exactly
as current-cell.md named as the most likely shape. Two runtime pieces
consume it:

1. `resolveDeclaredOperationActor` (session-engine.mjs) takes a new,
   optional 4th parameter `specialistBindings` (a `Map<slotId, record>` of
   CURRENTLY LIVE specialist authorizations), defaulting to an empty `Map`.
   A `specialistSlotRef` binding resolves its effective actor id by looking
   up its slot in that map; a static `actor` binding resolves exactly as
   before. With the default empty map, this function is byte-for-byte
   identical to its pre-P09.2 behavior -- verified by the full existing
   regression suite passing unchanged (no fixture anywhere names
   `specialistSlotRef`).
2. `authorizeDeclaredOperation`/`dispatchDeclaredOperation` build that map
   ONLY when the definition actually wires the operation to a
   `specialistSlotRef` (`definitionOperationUsesSpecialistSlot`, a cheap,
   I/O-free pre-check), via a new `resolveLiveSpecialistBindings(replayed,
   {round})` helper. This keeps the change a true zero-cost no-op for every
   pre-P09.2 fixture: no extra `replaySession()` call is ever made unless a
   specialist-slot binding is actually in play.

**Alternative considered and rejected: extending `actor` itself to accept
either an actor id or a slot id (single polymorphic field).** Rejected
because current-cell.md is explicit that a slot reference is "an
ALTERNATIVE to (never in addition to an unrelated) a static `actor` id,"
and a single field conflating two different resolution mechanisms (static
lookup in `spec.actors[]` vs. live session-state lookup) would make the
schema layer's own validation ambiguous about which check applies. A
second, clearly-named field with an explicit mutual-exclusion check keeps
`validateNodeOperationRef` legible and keeps the "resolves against
`spec.actors[]`" invariant P09.1's whole closure proof rests on
(`assertSpecialistSlotIdsAreDisjoint`) completely undisturbed -- `actor`
still NEVER accepts a slot id, at any point.

**One event does both jobs.** `specialist-authorized`
(`coordination/schema.mjs`'s new event kind, `store.mjs`'s
`recordSpecialistAuthorization` door) is simultaneously the authorization
record AND the session-scoped actor binding -- there is no separate
`specialist-bound`/`actor-bound` event for a specialist. This is the
mechanism, not a shortcut: the phase's own atomicity requirement
("atomically record authorization and session-scoped actor binding before
any Assignment is issued") is met structurally, because a single
`appendEventLocked` call inside one `withEventsLock` critical section has
no window between "authorized" and "bound" -- there are not two writes to
have a window between. This is a deliberate DEPARTURE from
`replaceSessionActor`'s own precedent (a `bindActor` call followed by a
separate `recordActorReplacement` call, two appends with a real window a
crash-resume claim-file has to paper over): that shape exists because
`replaceSessionActor` swaps a `spec.actors[]` SessionActor, which lives in
`manifest.actors[]` and genuinely needs a first-class `actor-bound` event
for OTHER machinery (policy stack resolution, cohort planning) to see it. A
specialist is never added to `manifest.actors[]` at all -- it is a
synthesized `{id, role}` pair (`resolveDeclaredOperationActor`'s
`specialistSlotRef` branch), resolved fresh from the live
`specialist-authorized` record every time, never a second stored structure
that could itself drift out of sync with the authorization that created it.

**"Live" occupant = last-write-wins per slot, expiry = a pure read-side
filter.** `resolveLiveSpecialistBindings` takes the MOST RECENT (log-order)
`specialist-authorized` record for each `slotId` as that slot's current
occupant -- a later authorization for the same slot IS the supersession
signal, mirroring `actor-replaced`'s own "last wins" semantics already used
elsewhere in this file (`buildActorReplacementMap`). No new
"specialist-superseded" event kind was invented. Expiry
(`expiresAfterRound`) is then a pure filter on top: a slot whose live
record's `expiresAfterRound < round` is simply ABSENT from the returned
map for that round -- `resolveDeclaredOperationActor`'s existing "no
specialist is currently bound to that slot" refusal handles it for free,
with no separate expiry-specific throw to maintain, and the expired record
itself is left completely untouched in `replayed.specialistAuthorizations`
(proven directly by the `an expired authorization...` test, which asserts
the record survives with its original `expiresAfterRound` after the
refused attempt).

**`round` reuses `dispatchDeclaredOperation`'s existing parameter rather
than inventing a session-tracked "current round" concept.**
`dispatchDeclaredOperation` already threads a caller-supplied `round`
(default 1) for topology-edge taskKey derivation; `authorizeDeclaredOperation`
gained the identical optional parameter for symmetry. The rejected
alternative was a new event kind or manifest field recording "the
session's current round" as durable state -- rejected because nothing in
the Candidate Contract names such a concept, specialist slots are
explicitly NOT topology edges (P09.1), and the existing `round` parameter
already gives a caller-supplied per-invocation numbering with exactly the
right shape for "which round is this Assignment for."

**`maxBindings` reading: cumulative-ever, not concurrent.** A slot has
exactly one LIVE occupant at a time by construction (last-write-wins,
above), so "concurrent count > 1" is structurally impossible to violate.
`maxBindings` is instead read as a hard ceiling on how many DISTINCT
`specialistActorId` values may EVER be authorized for a given slot across
the session's whole history (enforced in `recordSpecialistAuthorization`
via `opts.maxBindingsForSlot`, counting distinct actors from fresh
on-disk `specialist-authorized` events, lock-held) -- a real, monotonic,
narrowing cap on how many times a slot's occupant may be
recruited/replaced, never decremented by expiry or supersession. The
rejected alternative (a concurrency-only cap) would make `maxBindings`
unenforceable by construction under the chosen "one live occupant per
slot" model, and nothing in the Candidate Contract requires MULTIPLE
simultaneous occupants of one slot. Proven by the `replacement:...`
test, which authorizes two distinct actors against `maxBindings: 2` (both
succeed) then proves a third is refused.

**`maxAssignments` is enforced by a NEW, separate opt-in cap on
`authorizeOperation`** (`opts.maxAssignmentsForSpecialist`), not by reusing
the existing `maxInvocationsForBinding` cap. `maxInvocationsForBinding`
counts `operation-authorized` events for one exact `(nodeId, operationId,
targetActorId)` triple; a specialist's own `maxAssignments` bounds its
TOTAL invocation allowance across every operation its slot declares
(`operationRefs[]` may name more than one operation). Reusing the narrower
per-triple cap would let a specialist filling two different operations in
the same slot receive `maxInvocationsForBinding`-many invocations on EACH
independently -- silently exceeding the intended total. The new cap counts
`operation-authorized` events by `targetActorId` alone, which is safe
because a live `specialistActorId` is unique to one occupant of one slot at
a time.

**Capability check direction: superset, not exact match.**
`authorizeSpecialistSlot` requires the authorized `capabilities[]` to be a
SUPERSET of the slot's own `requiredCapabilities[]` (every required
capability present; extra ones allowed) -- the slot names a floor, not a
ceiling, matching P09.1's own "empty gate list means no gate on that
dimension" reading of `requiredCapabilities`.

## 8. Fix Round 1 (independent Red-Team, round 1) — the round-1 bypass

**Finding, in one line**: `resolveLiveSpecialistBindings` gated specialist
liveness on a bare, caller-supplied `round` parameter (default `1`), which
the ONE real production caller (`src/verbs/coordination/run.mjs`'s
"authorize" step) never forwarded at all -- since `expiresAfterRound` is
schema-validated `>= 1`, the default `round: 1` structurally never expired
anything through the real request-step path. Empirically reproduced by
Red-Team: 5 real `authorizeDeclaredOperation` calls, round omitted, all
succeeded against `expiresAfterRound: 1`.

### Blast-radius conclusion (traced before fixing, per Fixer instruction)

The bypass at the "authorize" step (`authorizeDeclaredOperation`) reached
only an OVER-BROAD `operation-authorized` grant -- it did NOT, by itself,
reach Assignment materialization. `dispatchDeclaredOperation`'s own
`resolveDeclaredOperationActor` re-resolves the live specialist bound to the
slot on EVERY dispatch, from its OWN independent
`resolveLiveSpecialistBindings` call; when the specialist is not currently
live for the slot (expired or absent), that resolution fails BEFORE the
`operation-authorized` gate is ever consulted -- even when a caller supplies
`targetActorId` naming the exact (stale) specialist id, because
`resolveDeclaredOperationActor` matches by the LIVE `effectiveActorIdOf`, not
by a caller-asserted id (`session-engine.mjs`'s `matches.find((m) =>
effectiveActorIdOf(m.ref) === targetActorId)`).

However, this containment was NOT a structural guarantee -- it depended
entirely on `dispatchDeclaredOperation`'s own `round` argument (`run.mjs`'s
"operation" step, which DOES forward `step.round`) actually being supplied
as a real, monotonic value by whoever authors the request. Nothing in the
codebase derives that round from real progress either -- `run.mjs`'s
"operation" step forwards `step.round` verbatim from the request file, with
no requirement that a caller ever populate it. A request that (like most
real usage, per the Doer's own Design Notes: "reuses `dispatchDeclaredOperation`'s
existing parameter rather than inventing a session-tracked 'current round'
concept") never supplies `round` on EITHER step type would default BOTH
calls to `round: 1`, and the specialist would never expire in practice at
all, through the real production path -- a full materialization bypass, not
merely an over-broad grant. The two call sites were not independently safe;
they shared the exact same caller-trust defect, and only the fact that
`dispatchDeclaredOperation`'s call happened to have a technically-available
`step.round` forwarding path (unlike `authorizeDeclaredOperation`'s, which
had none at all) kept the immediate empirical reproduction scoped to
over-broad grants rather than materialized Assignments.

### Fix chosen: Direction A — derive the round internally from real, replayed session state

`resolveLiveSpecialistBindings(replayed)` no longer accepts a `round`
parameter at all. It derives its own "current session round" via a new
`resolveCurrentSessionRound(replayed)` helper: one plus the count of
`assignment-created` events already in the session, session-wide. This is a
real, monotonic quantity computed purely from the replayed append-only event
log -- it can only increase, and only when a real Assignment actually
materializes, so no caller input can move it. Both call sites
(`authorizeDeclaredOperation`, `dispatchDeclaredOperation`) were updated to
stop forwarding any `round` to this function; `authorizeDeclaredOperation`'s
own dead `round` parameter (it had no other use) was removed entirely.
`dispatchDeclaredOperation`'s own `round` parameter is UNTOUCHED and remains
exactly what it was before this fix -- a per-edge taskKey/maxRounds
disambiguator, a genuinely different concept that happened to share a
parameter name with the (now-removed) specialist-liveness use. The two
concerns are now fully decoupled: specialist-slot liveness trusts no caller
input at all; topology-edge round-taking behavior is completely unchanged
(proven by the zero regressions in `coordination-driver-authorization.test.mjs`,
`coordination-recheck-disposition.test.mjs`, and every other pre-existing
fixture in the combined regression run below, none of which name
`specialistSlotRef`).

**Alternative considered and rejected: Direction B (make `run.mjs` compute
and forward a correctly-derived round, mandatory on the "authorize" step).**
Rejected for the same reason Direction A was already the phase's
recommended direction: it would have left a structurally-caller-trusted
value in place for the ONE gate this whole fix round exists to make
non-bypassable, merely moving the trust boundary from "whether `round` is
forwarded" to "whether the forwarded `round` is honest" -- no different in
kind from the bug itself, and reachable again the moment a second call path
to `authorizeDeclaredOperation`/`dispatchDeclaredOperation` is added (a CLI
flag, a retry harness, a future headless-adapter shape) without carrying the
same derivation discipline. Direction A closes the gate for EVERY current
and future caller at once, matching this track's own stated discipline
("never trusting caller-supplied state for a legality decision") and its
precedent of closing the identical bug CLASS four times already this track
(P06.2, P07.3, P07.4, P08.2).

**Why "count of `assignment-created` events" specifically, and not a
per-slot or per-actor count**: the phase's own Candidate Contract and
Acceptance text both describe `expiresAfterRound` as bounding "future
Assignments," session-wide, with no per-slot/per-actor round concept
declared anywhere in the schema. A session-wide monotonic counter is the
smallest quantity that is (a) genuinely derivable from the event log alone,
(b) impossible for a caller to manipulate, and (c) behaviorally identical to
the pre-fix default for a session's very first Assignment (round 1, before
any Assignment exists) -- so `expiresAfterRound: 1` keeps meaning exactly
what it always meant for that first Assignment, while now ALSO meaning what
it always should have: "expired the moment any further Assignment
materializes in this session."
