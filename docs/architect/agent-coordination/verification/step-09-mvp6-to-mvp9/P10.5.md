## 3. CLI/headless request-path parity — the interpretation call, made and justified

current-cell.md explicitly left this cell to decide between two readings of
"prove the same request path works through CLI and headless entry points":
(a) the skill's own `node -e "import(...)"` invocation pattern IS the
CLI-equivalent path, proven identical to the headless adapter's path; or
(b) a genuinely new `fgos group-thinking ...` CLI subcommand is required.
current-cell.md's own tentative read favored (a).

**Decision: (a).** Verified, not assumed, by reading the real code before
deciding:

- `bin/fgos.mjs` has zero `group-thinking` hits (confirmed by grep before
  this cell started) — there is no dedicated CLI subcommand for
  group-thinking today, and current-cell.md's own May-Touch section makes
  `bin/fgos.mjs` in-scope only if this cell concludes a new subcommand is
  genuinely required.
- `core/skills/fgos-group-thinking/SKILL.md` (§4 of that file, "Launch or
  resume") is this repo's own, already-shipped, already-reviewed answer to
  "how does an interactive/CLI-style caller reach group-thinking" —
  `runGroupThinkingRequest`, called via the SAME `node -e "import(...)"`
  convention `fgos-routing/SKILL.md` already established for a verb with no
  dedicated `bin/fgos.mjs` command (P10.1.md's own Design Notes, "No new CLI
  verb", independently confirmed by both P10.1's Reviewer and Red-Team
  rounds).
- `runGroupThinkingRequest` (`group-thinking-pack.mjs`) and
  `runCoordinationHeadless` (`src/runner/coordination/headless-adapter.mjs`,
  R4's real headless entry point) both import `runCoordinationUseCase` from
  the identical file, `src/verbs/coordination/run.mjs` (confirmed by reading
  both modules' import lists directly) — the ONE function `run.mjs`'s own
  header comment calls "the ONLY place a coordination request is turned into
  engine calls", used by "both the interactive CLI (`bin/fgos.mjs`) and the
  headless adapter". `runGroupThinkingRequest` adds exactly one thing ahead
  of that call (the pack-membership/identity gate, §5 below) and forwards
  the request object byte-for-byte afterward — it never rewrites, filters,
  or reconstructs it (confirmed by reading `runGroupThinkingRequest`'s own
  body: the only fields it ever reads are `kind`/`protocolRef.id`/
  `coordinationId`).

Building a genuinely new `bin/fgos.mjs group-thinking` subcommand would
therefore have added a SECOND way to reach the exact same
`runCoordinationUseCase` call this cell can already prove reaches it
identically — duplicating, not adding, proof surface, and expanding
Do-Not-Touch scope (`bin/fgos.mjs`) for no functional gain. Interpretation
(a) is both the cheaper and the more faithful reading of "prove the same
request path", so this cell built the proof, not a new subcommand.

**The proof itself** (`coordination-group-thinking-pack-registration.test.mjs`,
"the SAME RFC-Review-Lite request dispatches..."): the identical RFC-Review-Lite
request (same `writerId`, same `objective`, same two-operation `steps[]`)
dispatched through `runGroupThinkingRequest` into one temp session and
through `runCoordinationHeadless` into a second, independent temp session.
Result: **byte-identical** `steps[]` — including `assignmentId`, which
turned out to be deterministically derived from `writerId` + per-session
dispatch order rather than randomly generated, so two independent sessions
with the same writerId legitimately produce the identical id string (this
was discovered empirically: the test's first draft asserted the ids would
differ and failed — corrected once the real generation scheme was
understood, not assumed). `definitionRef`, `kind`, `closed`, `status`, and
`quorum` are all separately asserted equal as well.

## 5. Bypasses #2/#3/#4, re-confirmed against a real registered protocol's real event log

P10.1.md §5 already proved bypasses #2 (bypass grants), #3 (validate its own
aggregate), and #4 (authorize a specialist) structurally impossible by
reading `run.mjs`'s closed, four-kind step vocabulary directly — that
reasoning does not depend on which protocol is registered, so it was not
re-derived from scratch here. This cell adds one empirical layer on top: a
full RFC-Review-Lite chain (convene → propose → object×2 → **authorize**
respond → operation respond) dispatched entirely through the pack gate, then
its real, persisted `events.jsonl` read back directly (not through any
`show`/replay convenience wrapper) and checked against the FULL known event
vocabulary this codebase's coordination kernel can write
(`session-opened`/`actor-bound`/`actor-replaced`/`assignment-created`/
`result-linked`/`run-retried`/`operation-authorized`/
`driver-disposition-recorded`/`deliberation-contribution-linked`/
`aggregation-validated`/`specialist-authorized` — enumerated by grepping
`store.mjs`/`session-engine.mjs` for every `type: '...'` event literal
before writing the assertion, not assumed).

Result: `operation-authorized` IS present (the `authorize` step really
reached the mediated grant door — the driver-authorized `respond` operation
only dispatches successfully because that grant was real, not decorative);
`aggregation-validated` and `specialist-authorized` are both absent. This is
real evidence a specific registered protocol's real dispatch never wrote
either forbidden event kind, strengthening (not replacing) P10.1's
structural argument that the capability is unreachable through this door at
all.

**Bypass #5 (close a session directly) is not separately re-tested here.**

(P10.1.md §5, #5) — every dispatch test in this file (and P10.1's own suite)

## 10. Design Notes — judgment calls made, and why

- **CLI-equivalent = the skill's own `node -e` invocation pattern, not a new
  `bin/fgos.mjs` subcommand.** §3 above states the full reasoning and the
  concrete evidence checked (grep of `bin/fgos.mjs`, both modules' import
  lists, `run.mjs`'s own header comment). Building a new subcommand was
  concluded to duplicate proof surface rather than add any, and would have
  expanded this cell's Do-Not-Touch scope for no functional gain —
  current-cell.md's own text explicitly asked this decision be made and
  justified, not defaulted to either reading.
- **`assignmentId` compared for equality, not merely "present and
  different."** The test's own first draft assumed session-scoped ids would
  differ across the two independent dispatch calls and asserted
  inequality — that assertion failed on the real run, which is how the real
  generation scheme (deterministic from `writerId` + per-session dispatch
  order, never random or coordinationId-derived) was discovered. The test
  was corrected to assert equality once the real mechanism was understood,
  rather than working around the failure with a looser assertion that would
  have hidden a genuinely stronger piece of evidence (byte-identical output,
  not merely structurally-shaped output).
- **P10.1's own "ships with zero members" test was edited, not left to
  fail.** That assertion was P10.1's own explicit, correct statement of ITS
  scope ("P10.5 registers... not this cell") — once P10.5 does exactly that,
  the assertion is factually superseded, not broken by a defect. Rewritten
  to check only the registry's shape invariants, with a comment pointing at
  this cell's own registration-membership test as the one file expected to
  need editing on a future membership change, so this exact edit should not
  recur for P10.6-P10.9 or any later registration.
- **No new bypass-#5 test.** Every dispatch test in this file and P10.1's
  own suite already exercises `run.mjs`'s single, unconditional
  `closeSessionByQuorum` call — a dedicated test would duplicate existing
  coverage without adding any (per this repo's own KISS/YAGNI baseline),
  since nothing about pack membership can touch that code path (it is
  outside `group-thinking-pack.mjs`'s own import list entirely, unchanged
  from P10.1's own confirmed reasoning).
