## 1. Design Notes — the real shape, and why it differs from Phase 08's fixture

`metadata.id: core.coordination-protocol.group-thinking-rfc-review-lite`,
`version: 1.0.0`. Grep-checked before choosing it against every existing
`core/coordination-protocols/*.yaml` id (`declared-consult`,
`deliberation-{delphi,nominal-group,rfc}-chain`, `group-cognition-framework`,
`independent-research-fan-out-fan-in{,-gated}`,
`standalone-master-coordination-loop`) — no collision.

Phase 08's `deliberation-rfc-chain.yaml` (read in full as the mechanism
precedent, never cloned) has exactly **one** objector and never gates who
may see an objection before another exists — its own `rfc-open` window
governs `propose`/`object`/`respond` alike, opened once by `convene`. This
cell's own three bullets ask for something structurally different:
**independent objections before controlled reveal** is a real privacy gate,
not narrative framing. The definition built here has **two** objectors
(`objector-a-actor`, `objector-b-actor`) who each record their own objection
independently, and the proposer's `respond` binding cannot be **granted**
read access to either objection until **both** have settled — reusing the
exact MVP6 visibility-window + driver-authorized-grant mechanism P08.3's own
Nominal-Group-chain fixture already proved for an analogous shape
(`private-propose -> reveal -> clarify`), applied here to REVIEW rather than
NOMINATION semantics.

Three windows, each opening after a **different, strictly earlier**
operation than the one it gates — deliberately avoiding the self-referential
trap P08.3's Design Notes documented (a window that opens only after its own
gated operation's cohort settles can never open, since authorization always
precedes settlement):

| Window | Opens after | Gates |
|---|---|---|
| `rfc-open` | `convene` | `propose` |
| `objection-open` | `propose` | `object` (both objectors) |
| `reveal` | `object` (both, all-of) | `respond` (driver-authorized) |

`respond` is `driver-authorized` (not `required`, unlike Phase 08's own
`respond`): this is the deliberate choice that makes the privacy property
provable at the **authorization** boundary (`authorizeDeclaredOperation`),
matching Nominal-Group's own proof shape exactly, rather than only at
contribution-link time. `object` and `propose` stay `required` — nothing
needs to gate their *dispatch*, only their contribution's *lineage claim*
(`linkSessionContribution`'s own link-time re-derivation, P08.2 Fix Round
item 4), which is unconditional regardless of activation mode.

**"No general comments/thread service."** Every piece of reasoning is one of
the six closed MVP8 types — `proposal`, `objection`, `response` are the
three this chain uses (`clarification`/`rank`/`specialist-request` are not
needed by this shape and are not invented into it). No new message/thread
concept exists anywhere in this document.

**Response lineage.** The response sets `respondsTo` to one objection
(`rrl_objection_a`, the field's own required-single-target shape per P08.1)
and `anchors` to **both** objections — proving the response genuinely
engages with the full revealed set, not just the one it disposes through.
The driver disposition then resolves the response via the existing
`contribution:` ref namespace (P08.2), through the unchanged
`recordDriverDisposition` door — no new disposition mechanism.

## 2. The per-actor provider/tier requirement — real finding, not silently omitted

**`spec.actors[].policy.minTier` is demonstrated for real** — both
objector actors declare `policy: { minTier: critical }`, a genuine
elevation over the runtime default (`standard`). The provenance test below
proves this resolves to the real value with the correct scope attribution,
not merely that the schema accepts the field.

**`spec.actors[].policy.preferExecutor` is deliberately NOT declared
anywhere in this document, and cannot be.** Verified against the real
code and the real contract before writing anything, not assumed from
current-cell.md's literal wording:

- `docs/architect/agent-coordination/contracts/flow-definition.md`'s
  PolicyPatch section states it in prose: "a *portable* `CoordinationProtocol`
  or `Workflow` definition expresses requirements (`minTier`, `capabilities`),
  not literal executor/model pins."
- `src/runner/coordination/session-engine.mjs:770-788`
  (`PORTABLE_POLICY_SCOPES = new Set(['runner', 'definition', 'operation',
  'role', 'actor'])`, `assertNoPortableExecutorPin`) makes this a hard
  runtime refusal, not just documented intent: any scope in that set —
  **including `actor`** — declaring a literal `preferExecutor` throws a
  `CoordinationError` before `dispatchDeclaredOperation` resolves anything.
  Only `assignment` (a caller-supplied per-dispatch override) and `cli` (the
  trusted human/CLI scope) may legally carry one.

So current-cell.md's literal
`spec.actors[].policy.{preferExecutor,minTier}` phrasing names a field
combination that is **structurally impossible at actor scope** for the
`preferExecutor` half — a genuine finding, not a design preference, and not
something this cell invented a workaround for. The correct mechanism for
"actor A uses provider X, actor B uses provider Y" is the **request-level**
`actors[].executor` field (`src/verbs/coordination/schema.mjs`'s
`ACTOR_ALLOWED_KEYS`), which P10.1's own mid-flight addendum (§3a of
`P10.1.md`) already proved end to end, live, with two genuinely different
registered executors dispatching as two different actors in one session —
and proved it **protocol-agnostic**: "nothing in `group-thinking-pack.mjs`
or `run.mjs`'s resolution path branches on WHICH executor id is named."

**Judgment call, stated plainly:** re-proving that same request-level
mechanism specifically against RFC-Review-Lite's own actors would add no
new proof value beyond what P10.1 already established generically, and
doing so would require dispatching through `run.mjs`'s request door (a
different call path than every other test in this file, which — matching
this track's own established `dispatchDeclaredOperation`-direct pattern —
calls the session-engine functions directly). I judged the `minTier`
half — a real, legal, protocol-specific PolicyPatch declaration — worth
building here, and left the CLI-provider-diversity half to whichever cell
proves the pack end-to-end (P10.5, which already inherits P10.1's generic
proof and registers this definition through the pack). **Stated honestly
per current-cell.md's own instruction, not silently omitted.**
