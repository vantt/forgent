### Existing visibility / context-grant primitives

`grantedContextRefs` is a real, already-enforced primitive, not aspirational
substrate-proposal text:

- Schema: required on `operation-authorized` event payloads
  (`src/runner/coordination/schema.mjs:287`, `required: [...,
  'grantedContextRefs']`), and given the same-length-array validation as
  `evidenceRefs` (`schema.mjs:414`).
- Write path: `authorizeDeclaredOperation`
  (`src/runner/coordination/session-engine.mjs:1047-1116`) accepts
  `grantedContextRefs` as a parameter (default `[]`, line 1049), asserts
  every entry resolves to a ref owned by the same `coordinationId` via
  `assertRefsOwnedBySession` (line 1087, comment at line 939 quoting the
  contract's own cross-session-rejection rule), and persists it onto the
  `operation-authorized` event (line 1116). `store.mjs`'s `authorizeOperation`
  (line 914-928) is the underlying persistence door for the same payload.
- Enforcement (read path): `dispatchDeclaredOperation`
  (`session-engine.mjs:1368-1841`) re-asserts ownership at dispatch time
  (line 1609, `assertRefsOwnedBySession(authorization.grantedContextRefs,
  ...)`), builds `legalContextRefs` as a `Set` from the authorization (line
  1639), rejects any requested context ref not in that set with a named
  error (line 1645, quoting the exact "may read only the granted refs plus
  its own always-legal base context" rule), and stamps the resulting
  Assignment's `contextGrant: { refs: [...] }` (line 1655) so replay can
  explain why the worker ran.
- Replay: `replay.mjs:142` reconstructs `grantedContextRefs` as a frozen
  array on the replayed authorization, matching the write-time shape exactly
  (no divergent replay-time reinterpretation).
- CLI surface: `src/verbs/coordination/run.mjs:348,360,390` resolves
  `step.grantedContextRefs` through the same `$ref:` label-resolution the
  rest of the request-file steps use, and `src/verbs/coordination/
  schema.mjs:282,319-320` validates it as a string array of safe refs/ids at
  the request-file door, before it ever reaches the engine.

This is the exact, already-fail-closed mechanism MVP6's "fail-closed
visibility windows over exact context grants" (plan.md:23) is expected to
build on, not invent from scratch — `grantedContextRefs` already IS the
"exact context grants" half of that requirement; visibility *windows*
(legality that changes over session lifecycle phase, e.g.
private-first-pass vs. post-independent-pass) do not exist yet in any of the
modules above and are confirmed net-new MVP6 scope.
