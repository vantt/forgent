## Requirements (phase-06-mvp6-visibility-windows.md, P06.1 cell)

1. Add only `CoordinationProtocol`-profile visibility fields:
   `spec.profile.topology.visibilityWindows[]` (`id`,
   `opensAfter.milestone: listed-results-linked`,
   `opensAfter.operationRefs[]`, `permits.sourceOperationRefs[]`,
   `permits.delivery: artifact-refs`) and
   `graph.nodes[].operations[].contextAccess.visibilityWindowRef`.
2. Reject unknown window refs (`contextAccess.visibilityWindowRef` not
   resolving to a declared window id).
3. Reject dangling `opensAfter.operationRefs[]` /
   `permits.sourceOperationRefs[]` entries (must resolve to a real
   `spec.operations[]` id declared elsewhere in the same definition).
4. Reject duplicate `visibilityWindows[]` ids.
5. Reject illegal `permits.delivery` values (only `artifact-refs` is legal).
6. Reject illegal `opensAfter.milestone` values (only
   `listed-results-linked` is legal).
7. Reject any use of `visibilityWindows`/`contextAccess.visibilityWindowRef`
   on a `Workflow`-profile definition.
8. A definition with no `visibilityWindows` stays byte/behavior-compatible
   with pre-change validation (no new required field, no changed outcome
   for existing fixtures).

## Design Notes (why cross-referential checks land where they do)

`validateSpec`'s existing order is `profile -> roles -> actors -> operations
-> graph`. Window `operationRefs`/`sourceOperationRefs` must resolve against
`spec.operations[]` ids, which do not exist yet when `validateProtocolProfile`
runs. Rather than reordering the whole pipeline, `validateProtocolProfile`
validates `visibilityWindows[]` shape + duplicate-id only; `validateSpec`
runs `assertVisibilityWindowsReferenceRealOperations(profile, operationIds)`
right after `operations` is computed, mirroring the existing pattern where
`assertAdvisoryReachableFromEntry` runs as a post-check after `graph` is
built. `contextAccess.visibilityWindowRef` is checked structurally inside
`validateNodeOperationRef` (same place `actor` is checked against
`actorIds`), given `windowIds` computed once in `validateSpec` and threaded
through the existing `validateGraph` call.

`contextAccess` on a `Workflow`-profile definition is rejected explicitly
(`profileKind !== 'CoordinationProtocol'`) rather than left to fall through
to "unknown window ref" — `windowIds` is always empty for a non-protocol
profile so the fallthrough would still reject, but with a message hiding
the real reason.
