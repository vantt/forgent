**Structural findings for a future Lead (new, beyond I01/I03/I04's own documented list):**
1. A coordination session's 1-hour `aggregateBounds.wallTimeMs` budget can elapse mid-cell on a long-running track cell (this one spanned ~14 hours of wall-clock time across a user-requested pause), forcing a fresh session (`--i05b/c/d`) exactly like the quorum-closes-early gap I04 already documents — same mitigation (a fresh coordinationId, dispositions recorded in the session that actually owns the finding's assignment ref).
2. `fgos coordination run`'s own CLI process can be OOM-killed by the host while its dispatched worker subprocess keeps running to completion and lands real, uncommitted work in the cell worktree. Recovery procedure used repeatedly and successfully: `git status`/`git diff --cached` (staged work survives a killed parent), read and verify the diff line-by-line, run the declared tests, fix any small test-construction gaps found, commit. This happened 4 times in this cell alone; treat "cwd is dirty/staged after a background dispatch reports killed" as evidence to inspect, never as nothing.
3. Retrying a required-first-pass operation (`produce-candidate`) with the SAME `taskKey` after a prior call in the SAME request was interrupted mid-flight can silently return the CACHED prior result instead of dispatching fresh — always mint a new `taskKey`/`as` label for a genuine retry, even of a required (non-authorized) position.
4. A coordination-session request's own branch-guard instruction text (embedded in the objective's free-text prose, e.g. "stop immediately if it is not `<branch>`") is NOT automatically kept in sync by opening a fresh `coordinationId` for a continuation — a blanket find-and-replace of the old session id into the new one (when scripting a request file from a prior template) can accidentally rewrite the branch name too, since a track's cell branch does NOT get a matching `b`/`c`/`d` suffix the way the coordinationId does. Always verify the real git branch name separately from the coordinationId when composing a continuation request.
5. GitNexus remained unavailable for this linked worktree for the cell's entire duration (registered only for the `forgentX` main checkout, itself stale) — every round's fallback was direct source reading and reviewer/red-team's own reproduction-based attacks, consistent with every prior cell in this track.

## Deferred / residual (fix-round cap reached — not blocking, confirmed "safe direction")

- **N1 (red-team-recheck, MEDIUM): a forward system-clock step can make a live cwd-lock holder look dead.** `btime` (`/proc/stat`) is `CLOCK_REALTIME`-relative and shifts on a wall-clock step (NTP correction, VM resume-from-suspend); the lock's own `identityTs` was sampled under the pre-step clock. A forward step larger than the holder's real age plus the 5s margin would make `cwdLockHolder()`'s wall-clock comparison read a still-live holder as dead. `verifyUserHz()`'s tripwire cannot catch this specific case (both sides of ITS OWN check move together under the same step). This requires an actual host clock discontinuity, not attacker input — the Lead accepts this as a documented residual rather than opening a 3rd fix cycle: closing it fully needs a writer-side change (the lock's own acquirer recording a monotonic/tick-based identity component alongside or instead of the wall-clock timestamp), which is out of this cell's File Lease per the same "defer the writer-side change" precedent already accepted for `clear-assignment-claim`'s own standalone-claim writer gap.
- **N2 (LOW): a relative or trailing-slash `--cwd` at the real writer (`cli.mjs`) vs. this cell's `path.resolve`'d `--cwd` can name two different lock files for what a human would call "the same cwd".** Cosmetic/ergonomic, not a safety gap (worst case: `clear-cwd-lock` reports "no cwd lock exists" for a real, live lock — fails closed, never wrongly applies). Future item: normalize `--cwd` the same way at both the writer and reconcile.
- **N3 (LOW): `readRealControlEpoch` is a deliberately-not-imported copy of `recover.mjs`'s own algorithm and is not proven bit-for-bit identical** — a JSON-literal-`null` generation file is skipped by the real `run-lock.mjs` reader but counted by this cell's copy, and a non-ENOENT read error is rethrown by the real reader but swallowed here. No parity test pins the two. Both variants fail toward the same "unrelated to this action's normal path" edge case; a parity test is a good, cheap future addition.
- **N4 (LOW): thinner test coverage for the F1 fix round's own new guards** — no dedicated fixture for `verifyUserHz`'s fallback path, the exact 5s margin boundary, or F4's symlink/absolute/sibling-prefix cases specifically inside `runtime-inspection.mjs` (the `reconciliation-planner.mjs` side has broader coverage). Both HIGH-severity fixes (F1, F4) are independently probe-verified by the recheck itself even without dedicated regression fixtures for every edge; adding them is a good future item.
- **N5 (LOW): `isWithinDir` is a lexical (`path.resolve`-based) check, not a `realpath`-based one** — a symlink planted inside `.fgos/assignments/` pointing outside it is not caught. Same-trust in practice (creating such a symlink already requires write access to `.fgos/assignments/`, the same access level needed to legitimately hold/clear a claim there), but a charset allow-list on `assignmentId` (reject anything but `[A-Za-z0-9_-]+`) would close this cheaply in a future round.
- **F5 (from cycle 2's initial review, not yet addressed): the static import-graph test's detection only catches static `from '...'` imports**, missing bare `import '...'`, dynamic `import()`, and `createRequire`/`require(` forms. The exact-6-file transitive-closure assertion is still real and load-bearing for every import shape actually used in this cell's own source; this is a hardening item for the test's own robustness against a *future* change introducing one of the missed forms, not a live gap in the current, reviewed code.
