## The key architectural finding (falsified the Lead's own initial guidance)

The Lead's own pre-dispatch investigation (via `herdr --help` output alone) suggested a seam: `herdr pane run <PANE_ID> <COMMAND>...` plus `herdr pane report-agent`/`report-agent-session` to manually register a pane's agent lifecycle, since `herdr agent start --kind <enum>` cannot run an arbitrary command. **This was wrong**, and both the independent reviewer and red-team caught it with LIVE testing against the real herdr 0.8.2 gateway in the very first review round: `herdr pane run` (and the underlying `pane.send_text` socket API — confirmed via `herdr api schema --json`, which has no `pane.run` request type) **types text into the pane's shell for the shell to re-parse**, it does not exec an argv directly. A prepared `bwrap ...` invocation typed this way gets re-tokenized by the pane's own shell (zsh), losing exact-argv fidelity — confinement is lost, not preserved.

Per the confinement-adapter-contract's own explicit fallback ("If Herdr cannot start an arbitrary prepared executable while keeping readiness and session tracking, required confinement refuses before launch. It may not downgrade to partial and claim enforced."), the cell pivoted: **required/preferred bwrap confinement on herdr-spawn now fails closed with a typed refusal before any pane or agent is created.** This is the correct, contract-compliant outcome — not a failure to deliver the cell. The unconfined/legacy herdr-spawn path still gets full, correct observe/reconcile/park-by-durable-identity behavior.

- Required/preferred bwrap confinement on herdr-spawn fails closed (`confinement-adapter-unsupported`/`confinement-mode-unsupported`) before any Herdr call, zero panes created — verified live.

- New tests: `test/runner/herdr-reconciliation.test.mjs`, `herdr-round-reconcile.test.mjs`, `herdr-spawn-assignment-dispatch.test.mjs` (the last one specifically dispatches through the real `executeAssignment` door in both real executor config shapes — added specifically because 3 rounds of bugs escaped detection by tests that only called `runHerdrRound` directly).

## Fix rounds (3 rounds)

1. **Fix-1** (after the seam-pivot round's own review/red-team): 4 CRITICAL findings on the ORIGINAL (flawed) seam attempt — env stripping, false-success on supervisor death not fixed here (that was P02L's own class of bug, correctly not re-litigated), stale controller resettlement, worker-forgeable receipts — largely superseded by the seam pivot itself. Also restored a real regression (legacy kind-only herdr-spawn used to correctly refuse under required confinement; the seam attempt broke that).
2. **Fix-2**: after the fail-closed pivot, reviewer/red-team found the REAL production dispatch path never reached the new logic at all — `executeThroughConfinement`'s `adapterOpts` never carried `runId`/`preparedInvocationDigest` to the herdr adapter (the same class of dead-code bug P02L had). Also found: `agentSession` comparison logic, resumed-round reconciliation gaps, digest field-path issues.
3. **Fix-3**: the fix-2 commit's own digest-verification fix (correct field path) then over-rejected — it turned out there were THREE different, non-equivalent "workerCommandDigest" definitions in play (Authority's prepared `{command,args}` digest, the receipt's full-herdr-start-argv digest, and a reconcile-synthesized third value); fixed by picking Authority's own canonical definition and adding a POSITIVE test (a genuine receipt must be accepted, not just that a fabricated one is rejected — the earlier round's tests lacked this). Also fixed: the real root cause of "production dispatch bypasses the seam" — `assignment-runner.mjs`'s adapter-resolution code read a field (`compiledPlan.policy.adapter`) that does not exist; the real field is `compiledPlan.invocation.adapter`. Fixed for BOTH real executor config shapes (`invocations[]` and flat `adapter:`). Fixed 2 more HIGH bugs: resume re-computing and corrupting an already-published prepared-invocation digest; `agentSession` stored as a nested object instead of a flat string, causing every live worker to false-positive as an incarnation mismatch.

Final recheck (both reviewer and red-team): **PASS**, live-tested against the real gateway through the real `executeAssignment` production door in both executor config shapes, no regression in P01/P02L.

## Deferred / accepted as non-blocking

- **F-1 (MEDIUM)**: a crash exactly between outbox settlement and `result.json` publication, on resume, overwrites a reconciled command record with a fresh pending one before failing on a baseline-digest mismatch — inconvenient (loses the settlement record) but never duplicate-spawns. Fix shape is straightforward (don't overwrite a reconciled record); deferred after 3 real fix rounds already landed the safety-critical items.
- **N1 (MEDIUM)**: concurrent herdr-spawn dispatches can race on an *unrelated* file — the Claude CLI trust-store's own read-modify-rename (`trust-store.mjs`) — causing an occasional `agent_not_ready` (4/20 pairs in a live stress test). Real bug, narrow (only under genuine concurrent dispatch), not part of this cell's own lease.
- **N2 (LOW-MEDIUM)**: the pending-window reconcile path does not cross-check a receipt's own `result.outboxDigest` against the real outbox file before settling — a tampered outbox could settle once, but self-heals on the next reconcile pass per red-team's own verification.
- Cosmetic: work-label uses executor command instead of workId; no receipt published on an agent-startup timeout (command left pending, no false success either).
- **Unrelated finding, not this repo's bug**: the `agy` CLI's own `-i` flag has an argument-parsing defect (confirmed independently by the user in their own terminal) — when invoked as `agy -i --mode ... --new-project ...`, `agy` treats `--mode` as the `-i` flag's own prompt value rather than the intended prompt, and errors. This affects the `agy-herdr` executor's invocation template, not any code this cell owns.
