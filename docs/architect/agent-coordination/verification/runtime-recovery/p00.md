## Process findings worth carrying into every later cell (not P00-specific)

1. **Commit plan/contract docs to git before creating any cell worktree.** `git worktree add` only checks out committed content; this whole track's `plans/260911-2305-runtime-recovery/` directory was untracked until this cell's own docs-prerequisite commit (`b88b5097`). Every phase-design contract this track's cells read (`confinement-adapter-contract.md`, `cli-spawn-local-contract.md`, `launch-reconciliation.md`, `code-panel-cells.json`, `requirements-traceability.md`) is now on `main` — later cells do not need to repeat this.
2. **Use `contextRefs` (plain assignment ids), never raw `.fgos/...` filesystem paths, to hand evidence into a worktree-confined dispatch.** `.fgos/` exists only in the main checkout; a mutating dispatch's cwd is the isolated worktree and cannot read outside it.
3. **A stale, unconsumed `authorize` step for the same `(nodeId, operationId, targetActorId)` triple always wins over a newer one** (`resolveBindingAuthorization` picks the first unconsumed match in event order). If an early fix-round attempt crashes after authorizing but before its paired operation dispatches, do not just mint a new `authorizationId` for a later retry of the SAME position with different `grantedContextRefs` — the old one will be selected first and its (possibly empty) grants will apply instead. Safest fix: give that operation no `contextRefs` dependency at all (inline the needed evidence as objective text) rather than fight authorization ordering.
4. **A session that ever needs a `fixer`/optional-role fix round can never reach `closed: true` quorum** unless `partialPolicy` was declared at the ORIGINAL session-open call — and declaring `partialPolicy` at open triggers the separately-documented BL1 auto-close-after-first-pass bug instead, which would block any fix round from ever being authorized. There is no way to have both "the cell may need a fix round" and "the session can cleanly self-report `closed: true`" under the current kernel. This track's cells accept `status: active` as the permanent terminal state for any cell that used a fix round; the real proof of completion is the merged commit plus recorded dispositions, not the session's own `closed` field. Worth a backlog item for the coordination-engine owners, out of scope for this track to fix.
5. **`aggregateBounds.maxRounds` (default 10 in the shipped template) is easy to hit** once a cell needs 2+ fix rounds (P00 used exactly 10 Assignment-creating rounds: 1 doer + 1 reviewer + 1 red-team + 3 revise attempts (2 failed on infra, 1 succeeded) + 2 reviewer-rechecks (1 stale-bound, 1 real) + 1 red-team-recheck + 1 more revise + 1 more reviewer-recheck). A cell expecting multiple fix rounds should consider declaring a higher `aggregateBounds.maxRounds` at open, weighed against the same BL1/partialPolicy tension in point 4 (`aggregateBounds` is a separate, independent field from `partialPolicy` and does not carry the same auto-close risk — safe to raise on its own).
6. **Always dispatch through the Bash tool's own `run_in_background`, never a manual `nohup ... &`.** A manually backgrounded `coordination run` was killed mid-dispatch when its calling tool invocation ended, leaving one Assignment (`asgn_lead_runtime_recovery_op_005`) claimed-but-orphaned with a consumed authorization and no result. `run_in_background: true` survived a ~5-minute real dispatch without issue.
