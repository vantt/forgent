### Primary Scrutiny Target #2 / MEDIUM — `runMissionAssignment`'s new mission-membership check protects only the string-ID call path; the object-form path (equally documented, `@param {string|object} assignmentOrId`) has zero mission-ownership verification

**File/line:** `mission-lite.mjs:386-415` (`runMissionAssignment`'s branch

`if (!assignment) { ... }`, i.e. only when `assignmentOrId` was a string).

**Failing scenario, empirically confirmed (not just read):** built two

genuinely read-only assignment for `mission_bbb` via
`createMissionAssignment`. Called
`runMissionAssignment('mission_aaa', assignmentBObject, opts)` — passing
the OBJECT belonging to `mission_bbb` under `mission_aaa`'s missionId.
Result: **executes without error**, and `mission_aaa`'s own
`thread.jsonl` ends up with a `RESULT` message
(`assignmentId: "asgn_..."`) that has **no matching `TASK` message**
anywhere in `mission_aaa`'s thread — a self-inconsistent ledger entry.
The string-ID form of the identical scenario (`runMissionAssignment('mission_aaa',
assignmentBId, opts)`) correctly throws `assignment "..." not found in
mission "mission_aaa"`, proving the check works for that one path.

**Attribution — not a new regression, but an incomplete implementation of
this cell's own added invariant:** read the pre-cell code
(`git show HEAD:src/runner/dispatch/mission-lite.mjs:317-321`) — the
object-form path had zero mission-ownership verification before this
cell too (it always executed whatever object was passed, unconditionally).
So this is not something this diff broke that used to work. What IS new
this cell is the Doer's own unprompted rationale, stated directly in the
code comment (`mission-lite.mjs:399-406`): "a caller that mixes up an
assignmentId from a different mission... would silently execute it under
the wrong mission's thread instead of failing loudly." That rationale
applies identically to the object-form call — a caller can "mix up" an
Assignment *object* from a different mission exactly as easily as an ID
string — but the fix only covers the string form. The Gaps section's own
disclosure ("no dedicated negative test was added for a cross-mission-mismatch
assignmentId... flagged here for visibility") undersells this: it reads as
"the mechanism exists but is untested," when the actual state is "the
mechanism does not exist at all for the documented object-form call
shape."

**Violated requirement:** dispatch instructions' Primary Scrutiny Target
2(c) ("does this check apply consistently to BOTH the string-ID and
object-form call paths... or only one?") — only one.

**Practical exploitability is bounded:** no real (non-test) caller
reaches `runMissionAssignment` at all today except `mission-lite.mjs`'s
own re-export (`dispatch.mjs`), and no test or in-repo caller passes a
foreign-mission object today. The mutation-refusal gate
(`isReadOnlyAssignment`) is unconditional for both forms — this gap
cannot be used to execute a mutating operation, only to pollute a
mission's own ledger with a RESULT entry that has no corresponding TASK.

**Smallest-fix direction:** hoist the `belongsToMission` check (keyed off
`assignment.assignmentId` instead of the string `assignmentId`) out of
the `if (!assignment)` branch so it runs unconditionally for both forms,
mirroring how the `effectiveMutation`/`isReadOnlyAssignment` check below
it already does.

**What test would catch it:** a test calling `runMissionAssignment(missionA,
assignmentBelongingToMissionB, opts)` (object form) and asserting refusal
— no such test exists today, for either form (the string-ID protection
itself also has zero negative-path test coverage, per the Gaps section's
own admission).

### NEW FINDING — MEDIUM: `createMissionAssignment`'s assignment-ID allocation is a real TOCTOU race; concurrent callers under the same writer identity can collide on the same assignmentId, silently drop one caller's real Assignment content, and leave `thread.jsonl` self-inconsistent with no error raised anywhere

**File/line:** `src/runner/dispatch/assignment.mjs:89-123` (`createAssignmentId`'s scan-then-use sequence-number allocation, no exclusive-create/lock) combined with `src/runner/dispatch/mission-lite.mjs:337-342` (`createMissionAssignment`'s own `if (!fs.existsSync(assignmentJsonPath)) { write }` guard, non-atomic with the ID scan that already ran inside `buildAssignment`→`createAssignmentId`).

**Mechanism, proven in two steps:**

1. **The ID-allocation race itself, deterministic proof.** `createAssignmentId` reads existing directory entries (`fs.readdirSync(assignmentsDir)`), computes `maxSeq + 1`, then merely *checks* (`fs.existsSync`) the candidate path in a loop — it never reserves the slot. Two calls against the *same* not-yet-mutated directory state produce the identical ID:
   ```
   idA: asgn_sess_abc123_op_001
   idB: asgn_sess_abc123_op_001
   COLLISION: true
   ```
   (repro: `createAssignmentId({ caller: { writerId: 'sess_abc123' }, assignmentsDir })` called twice before either directory is created — see scratchpad `race1.mjs`). Note also: since `createMissionAssignment` never passes `stage`/`operation` to `buildAssignment` (`mission-lite.mjs:297-322`, inline shape has neither), `sanitizeToken(operation || stage || 'op')` is the **literal constant `'op'`** for every mission-lite assignment from a given writer — the sequence number is the *only* differentiator, which is exactly what this race collides on.

2. **The ID prefix is keyed on `caller.writerId` = the resolved session identity (`resolveWriterIdentity`, via `FGOS_SESSION_ID`/`CLAUDE_CODE_SESSION_ID`) — shared, by design, across every process/subprocess in one agent session.** This is precisely the shape of a real "debate" mission (this file's own stated purpose, `mode: 'debate'` is the default): multiple role assignments created for the same mission, under the same session, plausibly from parallel subprocess/worker dispatch once Phase 03's live harness exists.

3. **End-to-end empirical repro (real code path, not just the primitive), using `worker_threads` for genuine OS-thread concurrency (two JS execution contexts hitting the filesystem independently, synchronized to start via `Atomics.wait`/`notify` so both reach `createMissionAssignment` at effectively the same instant):** two workers, same mission, same session/writer identity, one creating a `researcher` assignment and the other a `reviewer` assignment. Result, reproduced on 2 of 3 runs (probabilistic, as any real race is — the collision *mechanism* itself is 100% deterministic per step 1 above; only the wall-clock overlap needed to trigger it through the real function is probabilistic):
   ```
   Result A: { assignmentId: 'asgn_..._op_001', role: 'researcher', objective: 'Investigate option A' }
   Result B: { assignmentId: 'asgn_..._op_001', role: 'reviewer',   objective: 'Investigate option B' }
   *** COLLISION CONFIRMED: both workers produced the SAME assignmentId ***
   On-disk role: researcher objective: Investigate option A   <- B's write was silently dropped
   Worker B intended role: reviewer objective: Investigate option B   <- B's in-memory return value, now divergent from disk
   thread.jsonl TASK messages:
     { assignmentId: 'asgn_..._op_001', toRole: 'reviewer',   objective: 'Investigate option B' }
     { assignmentId: 'asgn_..._op_001', toRole: 'researcher', objective: 'Investigate option A' }
   ```
   Both `createMissionAssignment` calls **returned successfully, no exception**. The canonical `assignment.json` (first writer wins, per the non-atomic `!fs.existsSync` guard) has ONLY the researcher content. `thread.jsonl` — the mission's own authoritative ledger — now carries **two TASK messages for the same assignmentId with contradictory `toRole`/`objective`**, one of which does not match what is actually persisted.

**Why this is worse than a cosmetic ledger duplicate — traced the downstream consequence, not just the corrupted write:** if B's caller goes on to call `runMissionAssignment(missionId, assignmentB /* object form, B's own in-memory result */, opts)` — the natural thing to do with the object `createMissionAssignment` just handed back — the P02.5-added `belongsToMission` check (`mission-lite.mjs:418-423`) only verifies the `assignmentId` string appears in *some* TASK message; it does not compare content, so it passes (both TASK messages share the ID). `executeAssignment` then hits its own P02.4-hardened read-back branch (`assignment-runner.mjs:583-601`) — `assignmentJsonPath` already exists (A's content), so B's in-memory `reviewer` contract is silently discarded and the **researcher's** contract is what actually executes. The "reviewer" role assignment is never genuinely run at all; the RESULT message B's caller appends is keyed to the same shared `assignmentId`, and `synthesizeMission`'s `resultByAssignmentId` Map (`mission-lite.mjs:556-561`, keyed by `assignmentId`, last-write-in-append-order wins) will silently retain only one of the two RESULT entries in synthesis input, with **zero errors, zero warnings, at any point in this chain** — exactly the multi-role "debate" consensus mechanism this file exists for silently degrades to fewer genuinely-distinct role perspectives than the mission believes it dispatched.

## Fix Evidence (Red-Team Round)

Fixer round for the Red-Team MEDIUM finding, ACCEPTED per Disposition (Red-Team Round) above: `createMissionAssignment`'s assignmentId allocation was a genuine cross-process TOCTOU race (scan-then-use sequence-number allocation, non-atomic check-then-write claim) that could silently drop one concurrent caller's real Assignment content with no error raised anywhere.

**Change:** `src/runner/dispatch/mission-lite.mjs`, `createMissionAssignment` (lines ~302-388). The single `buildAssignment(...)` call plus the `if (!fs.existsSync(assignmentJsonPath)) { fs.writeFileSync(...) }` check-then-write guard were replaced with a bounded retry loop (`MAX_ASSIGNMENT_CLAIM_ATTEMPTS = 8`, new module constant):

```
-  const assignment = buildAssignment({ ... });
-  ...
-  const assignmentDir = path.join(assignmentsDir, assignment.assignmentId);
-  fs.mkdirSync(assignmentDir, { recursive: true });
-  const assignmentJsonPath = path.join(assignmentDir, 'assignment.json');
-  if (!fs.existsSync(assignmentJsonPath)) {
-    fs.writeFileSync(assignmentJsonPath, `${JSON.stringify(assignment, null, 2)}\n`);
-  }
+  const buildCandidateAssignment = () => buildAssignment({ ... });
+  for (let attempt = 0; attempt < MAX_ASSIGNMENT_CLAIM_ATTEMPTS && !claimed; attempt += 1) {
+    assignment = buildCandidateAssignment();
+    ...
+    const assignmentDir = path.join(assignmentsDir, assignment.assignmentId);
+    fs.mkdirSync(assignmentDir, { recursive: true });
+    assignmentJsonPath = path.join(assignmentDir, 'assignment.json');
+    let fd;
+    try {
+      fd = fs.openSync(assignmentJsonPath, 'wx');
+    } catch (err) {
+      if (err.code === 'EEXIST') continue; // another writer already claimed this id -- retry with a fresh candidate
+      throw err;
+    }
+    fs.writeSync(fd, `${JSON.stringify(assignment, null, 2)}\n`);
+    fs.closeSync(fd);
+    claimed = true;
+  }
+  if (!claimed) throw new RunnerConfigError(`... after ${MAX_ASSIGNMENT_CLAIM_ATTEMPTS} attempts ...`);
```

`fs.openSync(path, 'wx')` is the exact exclusive-create primitive this codebase already uses for the identical class of problem (`main-checkout-lock.mjs`, `session.mjs`/`state/events.mjs`'s own historical use of it before both moved to a tmp-file+`linkSync` variant for a *different* reason -- see "Design note" below). On `EEXIST`, the loop calls `buildCandidateAssignment()` again rather than hand-deriving a new id: the losing writer's own `fs.mkdirSync(assignmentDir, { recursive: true })` a few lines above already left a same-named directory entry under `assignmentsDir` on disk, so the next `buildAssignment()` → `createAssignmentId()` call's own `fs.readdirSync(assignmentsDir)` scan sees it and advances `maxSeq` past it -- producing a genuinely fresh candidate id without any change to `createAssignmentId`/`buildAssignment()` (both untouched; `assignment.mjs` was not modified by this fix, per the dispatch's own preference for the narrower fix).

**Design note (openSync('wx') vs. the tmp-file+linkSync pattern):** `session.mjs`/`state/events.mjs` moved from a bare `fs.openSync(lockPath, 'wx')` + separate `fs.writeSync` to a tmp-file-then-`linkSync` pattern specifically because a *lock* file is actively read by a competing process mid-acquisition to decide "is the current holder alive" -- a window where the lock file exists but is still empty caused a competing reader to see unparseable content and wrongly reclaim a live lock (their own doc comments, `session.mjs:143-153`/`events.mjs:288-298`). That specific hazard does not apply here: no code path reads `assignment.json`'s content to make a decision *during* the race -- a competing `createMissionAssignment` call only ever attempts its own `openSync(path, 'wx')` on that exact path and either succeeds or gets `EEXIST`, never parses the winner's file mid-write. `executeAssignment`'s own later read-back (a separate, sequential call, not concurrent with creation in any scenario this fix's threat model covers) runs after `createMissionAssignment` has already returned. `fs.openSync(path, 'wx')` + one `fs.writeSync` + `fs.closeSync` is therefore sufficient to close the specific race this finding names, and simpler than introducing a second convention (tmp-file naming, cleanup) for a class of hazard this call site does not have.

**Test added:** `test/runner/mission-lite.test.mjs` — `createMissionAssignment never lets two concurrent callers under the same writer identity collide on the same assignmentId or silently drop one caller's real content` (line ~746). Two real `worker_threads`, each independently importing `mission-lite.mjs` and calling `createMissionAssignment` for the same mission/writer identity (mirroring the mission-lite "debate" shape Red-Team's own repro used). Rather than only synchronizing worker *start* time (which proved insufficiently tight to reliably force the race window in this environment -- see below), each worker patches its own thread-local `fs.mkdirSync` to pause on its first call via a shared `SharedArrayBuffer`/`Atomics` barrier: that call site is exactly the point, inside `createMissionAssignment`, right after the assignmentId candidate is computed and right before it is claimed on disk -- the TOCTOU window this fix closes. Both workers are released together once both have paused there, guaranteeing both threads computed their candidate assignmentId against the same not-yet-mutated directory state regardless of OS thread-scheduling timing. Asserts: (a) `resultA.assignmentId !== resultB.assignmentId` -- the race must be closed, not merely made less likely; (b) each result's returned `role`/`objective` match what is actually persisted in that assignmentId's `assignment.json` on disk -- no silent content divergence; (c) `thread.jsonl` carries exactly 2 TASK messages with 2 distinct assignmentIds -- never a duplicate-id entry with contradictory content.

**Revert-and-reproduce (empirical, not just read):**
1. Temporarily reverted `mission-lite.mjs`'s `createMissionAssignment` to the pre-fix single `buildAssignment()` call + `if (!fs.existsSync(assignmentJsonPath)) { fs.writeFileSync(...) }` guard (saved a copy of the fixed file first).
2. Initial attempt used only a worker-*start*-time barrier (no `fs.mkdirSync` pause) -- ran 25 times against the reverted code: **0/25 failures**. The barrier released both workers into `createMissionAssignment` close together, but each call's own `readdirSync`/`mkdirSync`/`writeFileSync` sequence completes in well under a millisecond, and real OS thread-wake scheduling jitter was enough that one worker's entire synchronous call routinely finished before the other's resumed -- confirming the race is real but timing-sensitive (matching Red-Team's own "reproduced on 2 of 3 runs" characterization), not something a bare start-time barrier reliably forces every run.
3. Rewrote the repro to pause deterministically inside `fs.mkdirSync` (patched per-worker, as described above) instead of only at start time. Re-ran the same reverted code 3 times in isolation: **3/3 failures**, each `AssertionError: two concurrent createMissionAssignment calls returned the same assignmentId` -- deterministic given the pause point, since both workers are now guaranteed to compute their candidate id against identical pre-mutation directory state before either claims it.
4. Restored the fix from the saved copy; `diff` confirmed byte-identical restoration.
5. Re-ran the same test 15 times in isolation with the fix restored: **15/15 pass** -- the guarantee is structural (an atomic claim plus a scan that always sees the prior claimant's directory entry), not merely a lower-probability version of the same race.
