# Cell P03.1 — R1+R2: Domain Harness Seam And The Non-Driving Rule

Status: doer-complete, awaiting Review/Red-Team
Phase: 03 (Domain harness seam and non-driving inline evidence, ADR-007)
Requirements: R1, R2

## Requirements

- R1: `domains/coding/harness/enrich-and-validate-contract.mjs` exports a
  pure `enrichAndValidateContract(contract, { domain, work })`. Rejects a
  contract whose `supports` field does not name an operation legal in
  `operationsForStage(domain, work.stage)`; adds `contextRefs`
  (`CONTEXT.md`/`plan.md` under `work.docsRef`); adds a repository
  read-only scope constraint; adds a concrete `agent-report.md`
  expected-output instruction when `evidence.required === 'reported'`;
  writes role→tier `policy` hints from the matched operation's own
  declared policy; never sets an executor id, never dispatches, never
  touches Work lifecycle. `buildInlineAssignment`
  (`src/runner/dispatch/assignment.mjs`) calls it between the generic
  validator (`execution-contract.mjs`) and the normalizer
  (`assignment-normalizer.mjs`), only when a domain is resolvable for the
  call. `execution-contract.mjs`'s `ACCEPTED_CONTRACT_FIELDS` accepts an
  optional `supports` field (format check only).
- R2: `findLatestAssignmentRunResult`
  (`src/runner/dispatch/operation-choice.mjs`) skips a candidate whose
  `assignment.json` carries `provenance.kind === 'inline'`, in the same
  filter chain as its existing `workId`/`stage`/`resultKind` checks — an
  inline Assignment's RunResult is never returned as `lastRunResult` to
  `chooseStageOperation`.

## Gaps

**Domain-siloing (`test/architecture.test.mjs`'s "core không import/couple
domain cụ thể" check) blocks the literal call site current-cell.md's
wording implies, and this was verified empirically, not assumed.**
`src/runner/dispatch/assignment.mjs` is core (any file not under
`domains/`), and the domain-siloing check mechanically forbids core
referencing one named domain's module — confirmed by writing a throwaway
static `import ... from '../../../domains/coding/harness/_probe.mjs'` in
`assignment.mjs` and running `test/architecture.test.mjs`: it fails with
`assignment.mjs (core) import domain cụ thể domains/coding/harness/_probe.mjs`.
A registry-field approach (a `harness` entry in `domains/coding/registry.yaml`,
read generically by `workflow-stage-graphs.mjs`'s existing `DOMAINS`
loader, mirroring how `workerContract` already works) would have been the
most consistent fix, but both files are outside this cell's "Files you may
modify" list (only `assignment.mjs`/`execution-contract.mjs`/
`operation-choice.mjs` + the new harness file). Resolution kept entirely
inside `assignment.mjs`: a domain-generic `DOMAIN_HARNESS_SEAMS` Map, built
once at module load by `fs.readdirSync`-enumerating every actual
`domains/<name>/` directory (a runtime value, never a source-code
literal) and dynamically `import()`-ing `<name>/harness/enrich-and-validate-contract.mjs`
when it exists on disk — mirroring `workflow-stage-graphs.mjs`'s own
`loadDomainsFromDisk` module-load-time-`readdirSync` precedent exactly,
just for a JS module instead of YAML. Since dynamic `import()` is
inherently a Promise, this uses ESM top-level await inside `assignment.mjs`
(legal, stable since Node 14.8) — by the time any caller can reach
`buildAssignment()`/`buildInlineAssignment()`, the module's own graph has
already finished loading, so both stay plain synchronous functions with
unchanged public signatures. Verified empirically (not just reasoned):
(a) `test/architecture.test.mjs`'s domain-siloing check passes with this
pattern in place (confirmed with a throwaway `_probe.mjs` before writing
the real seam); (b) the full narrow test battery (mission-lite,
assignment-provenance, assignment.test.mjs, assignment-policy — 85 tests)
stayed green with the top-level-await block present, proving no ordering/
timing regression; (c) a direct one-off script confirmed `buildAssignment()`
returns a fully-enriched object synchronously, not a Promise, immediately
after import resolves. A first attempt at the explanatory code comment
itself accidentally re-triggered the same false-positive detection (the
domain-siloing check's `extractImports` regex scans *raw*, uncommented
source for `import ... from '...'`-shaped text and matched a `//` comment
that used the words "import" and a later quoted example path with no
intervening semicolon between them) — caught by re-running
`test/architecture.test.mjs` before considering this done, not assumed
correct from reading the regex alone; the comment was rewritten to avoid
that literal shape.

**`buildInlineAssignment`'s new top-level `domain` supply point is
`options.domain`, not a new named top-level parameter — a deliberate
choice to avoid growing `INLINE_ASSIGNMENT_PARAM_WHITELIST`.** The
Watch-Fors section flagged this as an open call: `work.domain` alone,
`options.domain` alone, or both. Chosen: `work?.stage ? (work.domain ??
options.domain) : undefined` — i.e. the seam is a *candidate* only when a
Work with a declared `.stage` is attached (there is no Stage to validate
`contract.supports` against otherwise); among those, the domain name comes
from `work.domain` first, `options.domain` as an override/fallback when
the attached Work itself carries no `domain` field. Both `work` and
`options` were already in `INLINE_ASSIGNMENT_PARAM_WHITELIST` before this
cell, so this needed zero whitelist change and therefore breaks no
existing inline caller (`mission-lite.mjs`, the only other real caller,
passes neither `work` nor `options.domain`, confirmed by `grep`). Rejected
alternative: defaulting an attached-but-domainless Work to `DEFAULT_DOMAIN`
the way `buildDeclaredAssignment` does — current-cell.md explicitly warns
against this ("do not weaken it by making the seam call unconditional 'for
consistency'"); the inline path's whole point is proving the foundation
boundary does not itself depend on any domain, so a silent `'coding'` fold
here would undermine that evidence.

**A Work attached with a resolvable domain but no `.stage` yet skips the
seam (treated the same as "no domain resolvable"), rather than throwing.**
current-cell.md's own wording ties "domain resolvable" only to
`work.domain`/`options.domain` availability, not to stage presence — but
ADR-007 §3's entire mechanism is framed around "a Work item has a declared
Workflow/Stage." A Work mid-lifecycle with no stage yet is a legitimate
state, not a caller bug, so I chose permissive-skip (pass on generic
validation alone) over fail-closed-throw for this specific combination.
Documented as a real judgment call, not obviously the only defensible
reading — a future cell wiring a real caller through this path (Phase 03
R3's `--contract` CLI door) may find this needs revisiting once a genuine
domain-resolvable-but-stageless call actually occurs.

**`provenance.validators` gains a `'domain-harness-seam'` entry when the
seam actually fires — an addition beyond current-cell.md's literal text,
judged in-scope.** ADR-006 §1 defines `provenance.validators` as "the
validator chain that produced" the Assignment; since the harness seam is a
real validator in that chain (it can reject, per R1), recording its
participation is a direct, minimal application of that existing field's
own stated purpose, not new schema. `assignment.policy` is likewise
attached only when the seam actually produced one (mirrors
`buildDeclaredAssignment`'s own `...(mergedPolicy ? {policy: mergedPolicy} : {})`
conditional-spread shape exactly).

**`supports` is threaded through to `provenance.inline.contract.supports`
on the built Assignment, not dropped after seam validation.**
`buildInlineAssignment`'s `frozenContract` construction is an explicit
field whitelist (not a spread of the raw contract), so a new accepted
field needed an explicit line added or it would silently vanish from the
persisted record even though `execution-contract.mjs` validated it and the
seam's legality check consumed it. Added
`...(contract.supports !== undefined ? { supports: contract.supports } : {})`,
consistent with the file's own existing conditional-field style used for
`reason`/`policy`/`missionId` elsewhere in this same module.

**`enrichAndValidateContract` deliberately does not call
`src/runner/paths.mjs`'s `resolveContentRoot` for context-ref resolution,
despite current-cell.md's item 10 naming that function.** Read it in full:
`resolveContentRoot` shells out to `git worktree list --porcelain` and
reads the filesystem to find the item's real content root (crashed-mid-
session recovery, tsk-ozl D3) — a real, useful capability for a *caller*
resolving where `plan.md` physically lives on disk, but incompatible with
this module's own "one pure seam" contract (ADR-007 §1: no fs, and the
Tests First section explicitly requires "identical output for identical
input" purity, asserted by a dedicated test in this cell). Read item 10's
own framing again after finding this conflict: "see how
`buildDeclaredAssignment`'s `work.docsRef` branch already builds refs for
the pattern to mirror" — and `buildDeclaredAssignment` itself (the model
this cell is told to mirror) also never calls `resolveContentRoot`; it
just does relative `path.join(work.docsRef, 'plan.md')`/`'CONTEXT.md'`
construction with no root resolution at all. Mirrored that exact pattern
instead — confirmed correct by direct comparison of the two functions'
source before writing either one.

**Impact-analysis capability: inactive.** `fgos tool query --capability
impact-analysis --status present` was not run interactively this session
(no GitNexus MCP tools were present in this Doer's tool manifest — the
harness's own connection-failure notice confirms GitNexus failed to

`operation-choice.mjs`'s `executeDriverOperationChoice`, `cli.mjs` —
no other in-repo caller) and of `findLatestAssignmentRunResult`'s only two
real callers (both inside `chooseStageOperation`, `src/runner/loop.mjs`'s
two call sites confirmed to pass no explicit `lastRunResult`).

be prepared to catch *any* exception type, not just `RunnerConfigError` —
worth stating explicitly wherever `buildAssignment()`'s own contract is
documented, if not worth a code change.

`RunnerConfigError` with the original error chained, so every failure
mode from this call site is at least a single, catchable error type for
callers — a slightly larger but still contained change.
