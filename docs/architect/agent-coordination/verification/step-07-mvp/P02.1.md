Per-operation evidence-requirement table built into `assignment-normalizer.mjs` (lifted from `operation-choice.mjs`'s existing `interpretAssignmentRunResult` branches, ~1600-1990, read-only reference, not modified):

| Operation | `mutation` (declared, role/op-derived) | `evidence.required` | `resultKind` | `onAdvance` |
|---|---|---|---|---|
| `validate-plan` | read-only | reported | gate-verdict | `derive-plan-verdict-from-plan-md` |
| `review-item` | read-only | reported | review-verdict | (none) |
| `scout-blast-radius` | read-only | reported | advisory (fallback) | (none) |
| `scoped-subtask` | mutating | verified | work-product (fallback) | (none) |
| `implement-item` | mutating | verified | work-product (fallback) | (none) |
| `fix-verify-red` | mutating | verified | work-product (fallback) | (none) |
| any other operation | derived from role/`KNOWN_MUTATING_OPS`/`READ_ONLY_OPS` (`classifyDeclaredMutation`) | read-only → reported, mutating → verified (fallback) | read-only → advisory, mutating → work-product (fallback) | (none unless explicitly named above) |

**Default-fallback reasoning:** for the six operations R2 names explicitly, `evidence.required`/`resultKind` come straight from the lifted table. For every other declared operation (`resolve-question`, `shape-plan`, `lock-decisions`, `judge-ambiguity`, `compound-learn`, a synthesized `decompose`, `answer-question`, etc.), the fallback reuses the **just-computed `mutation` stamp** rather than a second, independently-derived role/operation check: read-only → `reported`/`advisory`, mutating → `verified`/`work-product`. This is equivalent to "read-only roles → reported, others → verified" as instructed, but routes through the single `mutation` classification this module already computes, so the two stamps for any given operation can never diverge from each other. Verified empirically against `operation-choice.mjs`'s existing branches: every operation that DOES have its own interpretation branch (`validate-plan`, `review-item`, `scout-blast-radius` accept `reported`-or-better; `fix-verify-red`, `scoped-subtask` require `verified` outright) matches this table exactly; `implement-item` has no interpretation branch yet (falls through to the generic unsupported-operation reason) but is a `KNOWN_MUTATING_OPS` entry, and R2 explicitly assigns it `verified` — folded into the explicit table rather than the fallback so it can't silently drift if `KNOWN_MUTATING_OPS` ever changes independently of this table.

**Inline provenance design decision (documented, not a spec gap):** ADR-006 R1 says inline `provenance.inline.caller.writerId` "comes from `resolveWriterIdentity()`" (`src/util/session-identity.mjs`). `assignment.mjs`/`assignment-normalizer.mjs`/`execution-contract.mjs` do NOT call `resolveWriterIdentity()` themselves — `buildAssignment()`'s inline shape accepts `caller` as a pre-built object (`{ writerId, parentAssignmentId? }`) passed in by its invoker. Reasoning: `resolveWriterIdentity()` shells out to `ps` and is a session-aware, non-pure operation, while `assignment-normalizer.mjs`/`execution-contract.mjs` are required to stay pure (R2/R3), and `buildAssignment()` itself must stay trivially unit-testable without spawning a real process tree. R4's own literal accepted shape (`{ provenance: { kind: 'inline', contract, caller } }`) already treats `caller` as caller-supplied, not internally derived. A later cell (R8, mission-lite migration) is expected to be the actual call site that runs `resolveWriterIdentity()` and passes its result in as `caller`.

### MEDIUM-1 — Dual-shape `buildAssignment()` dispatcher accepts ambiguous input silently instead of rejecting it

- File/line: `src/runner/dispatch/assignment.mjs:157-162` (`buildAssignment`
  dispatcher: `if (params?.provenance?.kind === 'inline') return
  buildInlineAssignment(params); return buildDeclaredAssignment(params);`).
- Failing scenario, empirically reproduced (not hypothetical):
  ```js
  buildAssignment({
    workId: 'tsk-1', stage: 'planning', operation: 'validate-plan',
    provenance: { kind: 'inline', contract, caller },
  });
  // -> succeeds, provenance.kind === 'inline', but stage/operation/domain
  // are silently dropped (undefined) rather than the call being rejected.
  ```
  Ran this exact case against the working tree: `AMBIGUOUS INPUT ACCEPTED
  -> kind: inline stage: undefined operation: undefined domain: undefined`.
  The reverse direction (declared fields present + a bogus/non-`'inline'`
  `provenance.kind`) is comparatively safe — it silently discards the
  caller-supplied `provenance` value and runs full declared legality
  checks — but is equally unvalidated.
- Violated requirement: ADR-006 R4 / phase-02 R4 — "`buildAssignment()`
  accepts **either** the existing declared shape ... **or** `{ provenance:
  { kind: 'inline', ... } }`" reads as mutually exclusive shapes, not "the
  inline branch wins silently when both are present."
- Impact today: none in production — grepped every caller of
  `buildAssignment()` (`operation-choice.mjs:2049`, `mission-lite.mjs:246`);
  neither passes a `provenance` key, so this path is dead code outside this
  cell's own new tests (matches the Gaps section's own claim). It also
  cannot be used to bypass either validator: when `provenance.kind ===
  'inline'` is present, declared legality (taskSpec existence, workflow
  graph) is skipped entirely regardless of what other declared-shaped
  fields ride along, and `execution-contract.mjs` still runs in full; the
  reverse never skips declared legality either. So this is a silent
  data-loss / confusing-degenerate-input bug, not a validation bypass —
  hence MEDIUM, not HIGH.
- Untested: `test/runner/assignment-provenance.test.mjs` exercises declared
  and inline as two separate calls (line 132-138) but never a single call
  carrying fields from both shapes.
- Smallest fix: at the top of `buildAssignment()`, before dispatching,
  throw `RunnerConfigError` when `params.provenance?.kind === 'inline'` and
  any of `stage`/`operation`/`domain`/`workflow` is also present (or,
  conversely, define and document the "inline wins" precedence explicitly
  and add a test asserting it — either resolution is acceptable, but the
  current silent-drop behavior with zero test coverage is not).
- Test that would catch it: a new negative test in
  `assignment-provenance.test.mjs` asserting `buildAssignment({ stage,
  operation, provenance: { kind: 'inline', contract, caller } })` either
  throws or is asserted (with a comment) to intentionally prefer inline.

### LOW-1 — `KNOWN_MUTATING_OPS`/`READ_ONLY_OPS` promoted from call-scoped to shared exported module singletons

- Files: `src/runner/dispatch/assignment-normalizer.mjs:51-63` (module-level
  `export const`), consumed by `src/runner/dispatch/assignment.mjs:49-50`.
- Before this cell, `isReadOnlyAssignment()` recreated `KNOWN_MUTATING_OPS`/
  `READ_ONLY_OPS` as function-local `const`s on every call — inherently

  pre-cell, so this isn't a wholly new pattern, but it is new for these two
  specific sets.
- Impact today: none — grepped `src/` and `test/` for `.add(`/`.delete(`
  calls on any of the three sets: zero hits. Purely a latent
  shared-mutable-global-state surface, not an active bug.
- Not blocking. Smallest fix if addressed: none required now; if wanted,
  a comment on the exports warning against mutation, or freeze-and-guard
  via a `ReadonlySet`-style wrapper if this module ever gains a test that
  needs to construct variants.

  `session-identity.mjs`'s own charset/length constants
