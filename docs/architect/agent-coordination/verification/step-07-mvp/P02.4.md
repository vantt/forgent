### HIGH — `mission-lite.mjs:runMissionAssignment`'s string-ID read-back path has the exact same unfixed "assignment.json predates the `mutation` field" bug this cell's scope-widening just fixed for `operation-choice.mjs`, and it fails in the opposite (false-refusal) direction

**File/line:** `src/runner/dispatch/mission-lite.mjs:305-310` (assignment
read-back) and `:314-318` (the `isReadOnlyAssignment` call it feeds,
unmodified by this diff).

**Failing scenario, empirically confirmed (not just read):** built a
temp-repo mission via `createMission`/`createMissionAssignment` for a
genuinely read-only op (`resolve-question`/`researcher`) — the fresh
assignment.json correctly stamps `mutation: 'read-only'`. Manually stripped
`mutation`/`resultKind`/`evidence`/`onAdvance` from the stored
assignment.json to simulate an assignment written before ADR-006 R2 added
those stamps (the exact "assignment.json predates the field" scenario this
cell's own scope-widening section names, word for word, as the reason
`operation-choice.mjs` needed a fix). Called
`runMissionAssignment('mission_gap_test', assignmentIdString, opts)` — the
documented, supported call form (`@param {string|object} assignmentOrId
Assignment ID or Assignment object`, JSDoc unchanged by this diff — this is
not a hypothetical caller). Result:

```
runMissionAssignment (by string id, legacy file) THREW:
cannot execute mutating operation "resolve-question" (role: "researcher")
in mission-lite mode — mission-lite is strictly read-only
```

The identical call with the fresh object (mutation stamped) succeeds. This
is a false-positive refusal of a genuinely read-only, correctly-declared
operation, solely because of how the assignment.json happened to be
persisted/read back.

**Root cause:** `runMissionAssignment` reads `assignmentPath` back from
disk via raw `JSON.parse(fs.readFileSync(...))` (line 310) whenever the
caller passes a string ID — bypassing `buildAssignment()`/the normalizer
entirely, identical in shape to the bug `findLatestAssignmentRunResult` had.
It then calls `isReadOnlyAssignment(assignment)` directly (line 315) on that
raw object with **no backfill** — unlike the fixed call site in
`operation-choice.mjs`, which now spreads in `fallbackMutationForAssignment(asgn)`
before calling the same function. Pre-R7, this path was accidentally safe:
the old heuristic's `assignment.missionId` clause made *any* mission
assignment (missionId is always set by `createMissionAssignment`) classify
as read-only regardless of whether `mutation` was present — so a legacy
file never hit this false-refusal. R7's field-only read removes that
accidental protection here without replacing it, unlike the one call site
this cell's scope was explicitly widened to fix. **This is a new
regression introduced by this diff, not a pre-existing issue** — confirmed
by re-deriving the pre-R7 code path: with the old heuristic, `assignment.missionId`
truthy alone would have short-circuited `isReadOnlyAssignment` to `true`
for this exact fixture.

**Why this is a real, not theoretical, caller:** every existing
`runMissionAssignment` call in `test/runner/mission-lite.test.mjs` passes an
*object* (grep-confirmed: `runMissionAssignment(mission.missionId, assignment, ...)`
at lines 117, 234, 323, 333, 461-463 — zero string-ID calls). **The
string-ID branch has zero test coverage in the entire suite**, so
"1283/1284 passing" and "mission-lite.test.mjs 6/6, zero outcome change"
provide no evidence either way for this path — it is untested before and
after this cell. The JSDoc's own contract (`assignmentOrId Assignment ID or
Assignment object`) makes this a first-class supported call shape, not a
theoretical or deprecated one; `.fgos/missions/**` state also plausibly
persists across an fgOS version upgrade on a real host project per this
repo's own mission #1/#2 framing (fgOS is installed and operating on real
projects outside this repo), so a genuinely legacy assignment.json is not
a self-hosting-only concern.

**Violated requirement:** this cell's own scope-widening note ("Everything
else in `current-cell.md`... still applies") plus its own Bug Taxonomy
("Removing the heuristic without confirming the normalizer's stamp actually
covers every real caller today... check this exhaustively, it's the crux of
this cell") and the dispatch instructions' Primary Scrutiny Target #4
("Is this the ONLY place with this latent gap?") — it is not.

**Smallest-fix direction:** mirror the exact fix already applied at
`operation-choice.mjs:374-377` — at `mission-lite.mjs:315`, replace
`isReadOnlyAssignment(assignment)` with the same derived-object pattern
(`isReadOnlyAssignment({ ...assignment, mutation: assignment.mutation === 'read-only' || assignment.mutation === 'mutating' ? assignment.mutation : fallbackMutationForAssignment(assignment) })`),
importing or re-deriving `fallbackMutationForAssignment`/`stampDeclaredAssignment`
as needed (`mission-lite.mjs` already imports from `./assignment.mjs`; would
need `stampDeclaredAssignment` from `./assignment-normalizer.mjs` directly,
same as `operation-choice.mjs` does). Add a regression test exercising the
string-ID branch with a `mutation`-less fixture, mirroring the new
`operation-choice.test.mjs` test's shape.

**What test would catch it:** a new `mission-lite.test.mjs` test calling
`runMissionAssignment` with a **string** assignmentId against a stored
assignment.json with `mutation` stripped, for a genuinely read-only
operation — asserting it succeeds rather than throwing. No such test exists

### MEDIUM — `cli.mjs`'s `execute --assignment` path never passes `opts.isMissionLite`, so `validateAssignmentLegality`'s mission-refusal gate is now unconditionally inert for this real, tested, documented caller

**File/line:** `src/runner/dispatch/cli.mjs:903-909` (the `executeAssignment`
call inside the `execute --assignment <id>` CLI subcommand) vs.
`assignment-runner.mjs:483` (`const isMission = Boolean(opts.isMissionLite);`).

Grepped every real (non-test) caller of `executeAssignment`: `cli.mjs:903`,
`mission-lite.mjs:321` (confirmed by direct read to pass `isMissionLite: true`
at line 325, matching the Doer/Coordinator's citation exactly), and
`operation-choice.mjs:2157` (the generic `dispatch: 'assignment'` branch,
which builds assignments via `buildAssignment()` with no `missionId`, so
`isMission` was never relevant to it either before or after). `cli.mjs`'s
`execute --assignment <id>` subcommand (tested at
`test/runner/assignment-dispatch.test.mjs:344`, a real documented CLI entry
point: `node src/runner/dispatch.mjs execute --assignment <id-or-path>`)
reads an arbitrary `assignment.json` by ID or literal path (including a
`.json`-suffixed path resolved relative to `root`, so it can target
`.fgos/missions/<id>/assignments/<aid>.json` directly) and calls
`executeAssignment(asgnObj, {...})` **without** `isMissionLite` — not
before this diff, and not after.

Under the pre-R7 heuristic, `isMission = Boolean(asgn.missionId || asgn.workId === null || opts.isMissionLite)`
meant a mission-shaped assignment (`missionId` set) reaching this CLI path
still tripped `isMission = true`; the refusal fired for the narrow subset of
operations in `KNOWN_MUTATING_OPS` (`implement-item`/`fix-verify-red`/`scoped-subtask`)
because for those, `isReadOnlyAssignment` short-circuited to `false` before
reaching the same `missionId` clause, so `isMission && !isReadOnlyAssignment`
was true and it threw. Post-R7, `isMission` is `Boolean(opts.isMissionLite)`
only, and this path never sets it, so the gate is now **unconditionally
skipped** for any assignment reached this way — including the 3
`KNOWN_MUTATING_OPS` operations that were previously caught.

**Practical exploitability is bounded**, which is why this is MEDIUM, not
HIGH: (1) `createMissionAssignment` — the only real producer of
`missionId`-bearing assignment.json files — already refuses to write a
mutating assignment to disk in the first place (`mission-lite.mjs:265-269`,
unmodified by this diff, still correct and in fact more correct post-R7
since it reads the properly-stamped `mutation` field on a freshly-built
object); (2) even pre-R7, an attacker/operator with the filesystem-write
access this scenario requires could already fully bypass the old heuristic
by simply omitting `missionId`/using a non-null `workId` on a hand-crafted
assignment.json, since `isMission` was false in that case regardless — so
the "protection" being narrowed here was already porous for a genuinely
adversarial input, not a hard trust boundary. This is a real, confirmed
coverage regression for a real caller (fails Primary Scrutiny Target #2's
"(b) now correctly also passes the explicit flag" test), but not an
exploitable new privilege it wasn't already possible to obtain via a
one-field omission before this diff.

**Violated requirement:** dispatch instructions' Primary Scrutiny Target #2
