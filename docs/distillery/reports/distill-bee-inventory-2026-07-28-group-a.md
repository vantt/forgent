## bee-hive

- **Skill role** (§ intro, l.18): bee-hive is a "bootstrap meta-skill", loaded first in bee repos; it verifies onboarding, reads runtime state, routes to the next skill, protects four human approval gates.
- **Progressive-disclosure pointer** (l.20): full routing table, state bootstrap, resume logic, chaining contracts, communication standards live in `references/routing-and-contracts.md`; full pipeline in `references/go-mode.md`.
- **Triage-first early exit** (§ Triage first, l.22-35): lane decided from the request text alone, before loading a second skill, using two counts — number of risk flags tripped, and number of **product files** touched. Table rows: all-knowledge-files → `docs`; 0–1 flags + ≤2 product files + one direct task → `tiny`; 0–1 flags + ≤3 product files + no gray areas → `small`; 2+ flags / story-sized / any hard-gate flag / genuine uncertainty → `standard`/`high-risk` with the normal chain incl. `bee-planning`.
- **Explicit token accounting for the triage** (l.33): the first three rows skip loading `bee-planning` — "the ~21 KB this triage exists to avoid"; the file states the triage saves nothing on bee-hive itself because "skills load whole, so `bee-hive` is already fully in context. The only saving on offer is the second load."
- **Uncertainty-resolves-downward rule** (l.35): "Uncertainty resolves downward, into loading more — never upward into skipping." One hard-gate flag = `high-risk` even at one product file; re-counting flags to land under a threshold is itself evidence you are in `standard`.
- **Onboarding protocol, 3 steps** (§ Onboarding, l.39-41): (1) `node --version`, stop below 18; (2) from bee source root run `node packages/bee/scripts/onboard_bee.mjs --repo-root <repo-root> --json`; (3) branch on `status`: `up_to_date` → continue; `changes_needed` → summarize plan, ask approval, then re-run `--apply`; `blocked_downgrade`/`blocked_no_source` → zero mutations happened, surface `versions`, resolve with user.
- **BEE markers / consent boundary** (l.41): never apply silently, and never over content outside the BEE markers without explicit consent.
- **Onboarding is a hard prerequisite** (l.43): "If onboarding is not complete, do not continue into the rest of the bee workflow." (Echoed as a one-line preamble in all 5 other skills: "If `.bee/onboarding.json` is missing or stale, stop and invoke `bee-hive`.")
- **Deferred onboarding detail** (l.45): `skills.targets` payload with `scope`/`target` fields, forced-apply transparency (D2), recheck honesty (D5), flags `--global-skills` / `--repo-hooks` / `--claude-md` — all in the reference under "Onboarding Protocol".
- **Greenfield init lane** (l.47, cited P1 / docs/09 item 6): on first onboard with no detectable build, offer an init lane before feature work; first planning slice is **one init cell** whose `must_haves` are: setup succeeds from scratch, one passing test exists, standard commands recorded in `.bee/config.json`, clean first commit. "Read what arrived; never re-fetch what it just told you."

That run adds active reservations, staleness warnings, `recommended_next`. Answering a question / reading code / explaining is explicitly **not** routing work — re-fetching then is "pure duplication".
- **Knowledge context command** (l.61, okf-foundation D38): when the active feature has a `bee.work-item` concept in `docs/knowledge/`, run `bee knowledge context --work <feature> --budget 20000` and read the manifest's files before planning/execution; the manifest **replaces** scanning `docs/history/`. No work item → offer to author one (template at `docs/knowledge/areas/okf-profile/concept-model-and-authoring.md`, Templates section), one line, user chooses, never silent/auto-written.
- **HANDOFF kinds** (l.63): `.bee/HANDOFF.json` read via `bee state handoff show --json`; missing/unknown kind reads as `pause` (fail-safe). **pause** → present phase/feature/cells-in-flight/next-action and wait for confirmation, "Never auto-resume." **planned-next** (previous cell capped green, next cell already claimed) → auto-adopted via `bee state handoff adopt`, but ONLY at a fresh-session boundary (`/clear` or freshly started session); presented as a start-now instruction. Never silently ignored, never silently dropped.

## bee-briefing

- **Frontmatter description states an anti-scope** (l.4): "Do NOT use to originate decisions, scope, or approach — those come from exploring/planning." Description encodes both use and non-use triggers.
- **Dependency `missing_effect: degraded`** (l.12) with reason "Reads cell traces and gate/status state via the vendored .bee/bin helpers" — contrast with bee-hive's `unavailable`.
- **One artifact per feature** (l.18-22): renders exactly `docs/history/<feature>/implement-plan.md`.
- **Metaphor framing** (l.18): "`bee-planning` is the waggle dance — precise, terse, bee-to-bee. Briefing translates the dance for the beekeeper."
- **Consolidator-not-planner rule** (l.24): renders FROM truth artifacts (`CONTEXT.md` decisions, `approach.md`, `plan.md`, cells, validating reports) and authors only two sections — **Technical Design** and **Rollback Plan**. Never originates a decision, approach, scope boundary, or cell. "Inventing content to fill a template section is the one failure this skill exists to prevent."
- **Lane forms table** (l.32-37): `tiny`/`spike` → **none**, "Do not create the file"; `small` → none by default, render the ~15-line **mini-brief** (Goal · Scope in/out · Affected files · Validation · one-line Risk · one-line Rollback) only when a `plan.md` exists (D4) *and* the user asks; `standard` → on-demand, full template with **empty sections dropped, never "N/A"**, only when the user asks or the slice spans multiple domains; `high-risk` → **mandatory** full template, with Rollback and Security/Permissions sections mandatory and carrying real content.
- **Conditional invocation + NOOP** (l.30): briefing is invoked conditionally per the fan-out table (decision 0009); below high-risk the caller may skip it entirely, and "briefing NOOPs when not called". "Do not treat a brief as automatic for every feature."
- **Four modes** (l.41-46): **render** (chain — invoked by `bee-planning` before Gate 2; builds `implement-plan.md`, sets `Status: Ready for Review`, Gate 2 message links it); **refresh** (chain — after Gate 2 prep and after `bee-validating` evidence; re-projects changed sections **in place**, "never a second file"); **walkthrough** (chain — after `bee-reviewing` passes Gate 4 on standard/high-risk; writes `docs/history/<feature>/walkthrough.md`, sets implement plan `status: Shipped`); **on-demand** (user asks, any phase).
- **Section → Source Map** (§1, l.52-65), 12 rows: Review Status ← `.bee/state.json` gates (never assert Approved before the gate fires); Goal/Success ← `CONTEXT.md` boundary + locked decisions (cite D-IDs); Current State ← exploring scout + `approach.md`; Scope in/out ← `CONTEXT.md` decisions + `plan.md` Out of scope (deferred ideas stay deferred); Proposed Approach + alternatives ← `approach.md` or `plan.md`'s `## Approach` (render as written, "do not substitute a 'better' idea"); **Technical Design ← authored**; Affected Files ← `approach.md` files + cell `files` (after prep, cells are authoritative); Implementation Steps ← `plan.md` shape + cells; Validation Plan ← cell `verify` commands + validating report ("never assert a result that has not run"); Risks & Mitigation ← `approach.md` risk map; **Rollback Plan ← authored**; Open Questions ← `approach.md` questions + anything uncovered.
- **Source-silent rule** (l.50): "If the source is silent, the section is an **Open Question**, never a guess."
- **Delegation split** (l.69): the section→source projection walk and walkthrough reconstruction delegate as **generation-tier I/O workers** (D2/D3); the two authored sections stay on the session model.
- **Technical Design definition** (§2, l.75): a readable narrative of flow/components/data shape/API/UI/security *the approach already implies*. A design choice the artifacts do not contain is "a proposal, not a rendering" — it goes to Open Questions, and if it should change the plan it flows back through `bee-planning`, "never smuggled into the brief".
- **Rollback Plan definition** (§2, l.76): how this specific change is undone (revert the cells' commits, disable a flag, reverse a migration). Explicitly noted: "bee has no rollback discipline elsewhere, so this is real new content." When undecided, write "Not yet decided — OPEN QUESTION: …", "never a plausible-sounding procedure nobody agreed to". `high-risk` must resolve it before Gate 3.
- **Projection Rule** (§3, l.80, extends D12): the brief is the human-layer projection; truth stays in `CONTEXT.md`/`plan.md`/cells/validating reports; the brief never overrides them.
- **Approval-site vs change-site separation** (l.82): approval happens on the brief but the brief is never the sole change site. Human feedback flows into truth artifacts first — `bee-planning` revises `plan.md`; a locked decision is superseded via `node .bee/bin/bee.mjs decisions supersede` and `CONTEXT.md` updated — THEN the brief re-renders. "Hand-editing the brief alone creates a render that disagrees with its own source."
- **Status lifecycle** (l.83): frontmatter `status` mirrors gates: `Draft` (rendering) → `Ready for Review` (presented at a gate) → `Approved` (gate passed) → `Needs Revision`, and → `Shipped` after the post-Gate-4 walkthrough. Approved at Gate 2 covers the shape; the Validation Plan section is patched with real evidence after validating, before Gate 3.
- **Drift rule** (l.84, D9): since D1 freezes `plan.md` at Gate 2, the plan can no longer drift once approved — drift now fires on **cell changes only**: if current-slice cells change after the brief was approved, set `status: Needs Revision` and re-render before the next gate. A mechanical `bee_status` warning on source-hash drift is recorded as a follow-up, not required for v1.
- **Gate ownership** (§4, l.88): briefing never presents gates — `bee-planning` and `bee-validating` do. The brief is the document their Gate 2/3 messages **link**. Three-layer doc model named: chat message = plain-language layer, brief = durable review object, mechanical reports in `docs/history/<feature>/reports/` = machine layer. "Never paste the whole brief into the gate chat message — link it."
- **Walkthrough lane scope** (§5, l.92): written after Gate 4 on `standard`/`high-risk` only; `tiny`/`spike`/`small` skip it (cap trace + commit are the record).
- **Reconstruct-from-reality rule** (l.94): sources are the capped cells' traces (outcome, `files_changed`, `deviations`, recorded `verify` output), review findings, and the UAT record — **not** `implement-plan.md`. "Where they differ, the shipped reality wins and the difference is *named*."
- **Walkthrough sections** (l.98-102): What shipped (observable outcome, present tense, from capped cells) · How it was verified (actual recorded evidence; never assert "works end-to-end" beyond the evidence; an unrun/skipped check is stated as an outstanding gap) · How to test it yourself (manual steps from UAT / SEE·CALL·RUN decisions) · Deviations from plan (from cell `deviations`; "silent divergence misleads the next reader") · Known limitations/follow-ups (deferred P2/P3 findings with backlog links). "Polished means honest, not curated to look finished."
- **Quiz offer** (l.104, P10, decision 0020): when presenting the walkthrough, offer a 3–5 question quiz on the change — what behavior changed, what each actor observes now, what was NOT verified, what deviated from plan. Questions derive only from the walkthrough's own sections; user opts in; a miss means walking that section together. Framed as mechanizing the gate litmus ("a gate the user cannot restate is dead") — never forced, never a blocker. Protocol in `references/walkthrough-template.md`.
- **Hard Gates list** (§, l.110-118), 8 items: never invent to fill a section ("a plausible Rollback or Technical Design nobody decided is a fabrication wearing a professional face"); walkthrough reconstructs from execution records not the plan; never claim broader verification than the evidence shows (unit checks passing ≠ end-to-end verified); never omit known findings or deviations to look clean; never originate; never hand-edit the brief as the sole change; never assert an unrun validation result; respect the lane (drop empty sections rather than pad); secrets and PII never appear in the brief.
- **Red Flags list** (§, l.126-135), 10 items incl.: a section filled with plausible content because "a blank section looks unprofessional"; a Validation Plan stating results ("142 passing") before anything ran; the whole brief pasted into a gate chat message; **a `-v2`/`-new`/dated implement-plan file, or a fresh brief created without checking for the feature's existing one**; `status: Approved` set before the gate passed or left stale; a walkthrough written by summarizing `implement-plan.md` in past tense; a walkthrough claiming "verified end-to-end" when UAT was skipped.
- **Handoff routing** (§, l.141-142): render/refresh → return to the calling skill (`bee-planning` for Gate 2, `bee-validating` for Gate 3); walkthrough → set `status: Shipped`, then "Invoke bee-scribing skill."
- **Reference load table** (l.144-148): a `| Reference | When to Load |` table naming `references/implement-plan-template.md` (full section-by-section template + agent writing guide), `references/mini-brief-template.md` (the small-lane ~15-line form), `references/walkthrough-template.md` (post-Gate-4 sections + reconstruct rules). This "When to Load" table pattern is a progressive-disclosure convention.

## bee-bypass-gate

- **Invocable as a command** (l.4, description): "Invocable as the command bee-bypass-gate with off / on / normal / full / total / status" — the description doubles as CLI-arg documentation.
- **Single-value scope** (l.18): the skill sets exactly one persistent per-repo value, `.bee/config.json` `gate_bypass`, a **level** (`off`/`normal`/`full`/`total`). It runs no pipeline work itself. The **behavior** of each level lives in the Gate Presentation Contract (`bee-hive/references/routing-and-contracts.md`, "Gate bypass mode") — this skill only sets the level and states what it means, "so the user opts in with eyes open".
- **Onboarding precondition** (l.20): same one-liner as the other skills.
- **Auto-approval mechanics at any on-level** (l.24): the agent stops asking at bypassed gates and takes the RECOMMENDATION option, records approval with `node .bee/bin/bee.mjs state gate --name context|shape|execution --approved true`, logs a one-line audit decision, continues, and posts a short `⚡ auto-approved Gate N` line — "not a question".
- **Named gate identifiers** (l.24): `context` | `shape` | `execution` are the three `state gate --name` values (Gate 4 has no config-settable name here).
- **Level table** (l.27-31): `off` → `gate_bypass: false`, auto-approves nothing, **every** gate stops (default). `normal` → `true`, auto-approves Gates 1-3 for `tiny`/`small`/`standard` non-hard-gate, still stops for high-risk/hard-gate Gates 1-3 · secret reads · Gate 4 UAT/P1. `full` → `"full"`, auto-approves all Gates 1-3 at every lane incl. high-risk/hard-gate, still stops for secret-file reads · a review P1 finding. `total` → `"total"`, auto-approves everything incl. secret reads, Gate 4 UAT, review P1 — "**nothing — zero stops**".
- **Hard-gate flag list, extended** (l.33): auth · authorization · data loss · audit/security · external provider · validation removal · **database migration/schema change**. (This last item does not appear in bee-hive's or bee-planning's hard-gate list — a discrepancy worth noting.)
- **Secret-file glob list** (l.34): `.env*`, `*.pem`, keys, `credentials*`, `secrets.*`. These stop under `off`/`normal`/`full`; only `total` auto-proceeds, "meaning credential contents may enter context/logs unprompted. Say this plainly when the user picks `total`."
- **Gate 4 never created by bypass** (l.35): Gate 4 exists only inside a user-started review session; no level creates one.
- **Bypass ≠ headless** (l.37): headless defers within-stage questions but still stops at every gate; bypass is the one mechanism that self-approves gates.
- **Backwards compatibility** (l.37): legacy `gate_bypass: true` is read as `normal`, so existing repos are unchanged.
- **Argument parsing** (§ Operation, l.41): `off` | `on` | `normal` | `full` | `total` | `status`; no argument → `status` then ask which level; `on` is an alias for `normal`.
- **Read step** (l.43): `node .bee/bin/bee.mjs status --json` (field `gate_bypass_level`) and `.bee/config.json`.
- **Per-argument behavior** (l.45-50): **status** = report level in plain language plus what it does/doesn't stop for, **no write**. **off** = set `false`, confirm every human gate is back, log via `bee.mjs decisions log --decision "gate-bypass set to off" --rationale "..."`. **on/normal** = set `true`, state the `normal` row, log. **full** = set `"full"`, state the row and name plainly that high-risk/hard-gate work will auto-approve without a human checkpoint, log. **total** = set `"total"`, state the row, name plainly the two things that stop being human-gated vs `full` (secret-file reads, review UAT/P1), **confirm the user wants literally zero stops**, log. Preserve every other config field; create `gate_bypass` if absent.
- **Config-write phase exemption** (l.51): `.bee/`-layer config writes are allowed in any phase, no gate, no permission needed. "Never touch `state.json` gates from this skill."
- **Persistence + visibility** (l.53): the change takes effect immediately for the current session and persists across sessions until changed. Session preamble and `bee_status` both print a loud level-specific `GATE BYPASS` banner — `NORMAL` / `FULL AUTOPILOT` / `TOTAL AUTOPILOT — ZERO STOPS` — "so the active level is never silently in effect".
- **Hard Gates** (§, l.57-59): only writes `.bee/config.json` `gate_bypass`; never approves a pipeline gate, never edits `state.json`, never runs feature work. Setting any on-level must be accompanied by stating that level's row in the same turn — "never change the level silently". `full`/`total` require the user's clear instruction; do not select them on the user's behalf.
- **Red Flags** (§, l.63-66): changing the level without telling the user what it stops covering · treating bypass as headless or headless as bypass · widening to `full`/`total` without explicit instruction or without naming high-risk/secret-read consequences · approving an actual gate from this skill instead of just setting the config value.
- **Handoff** (l.72): "Bypass level set to `<off|normal|full|total>`. Return to whatever the user was doing (or `bee-hive` if idle)."

## bee-planning

- **§1 Intake ordering inversion (D8)** (l.29): classify before you bootstrap. From the **request text plus at most 2 targeted file reads**, run a cheap intake classification to pick the lane; only then do the lane-scaled bootstrap. Rationale stated: "Tiny work must not pay full context reads before it knows it is tiny." Explicitly supersedes the old unconditional full-bootstrap-first ordering.
- **Critical-patterns digest is exempt from D8** (l.31): mandatory in every lane, tiny included; already in the session preamble so it costs no extra read. - **Risk-flag list, identical to bee-hive's** (l.35), plus the D7 narrowing spelled out (l.37): "changes behavior an existing test asserts (a covered contract must change)" replaces the old "existing covered behavior"; "the change requires weakening, deleting, or replacing existing proof" replaces "weak proof around the area". A covered bugfix that keeps existing tests green and adds a new one scores 0 on both. All other flags and thresholds unchanged.
- **Product-file caps (D6) restated** (l.39) with the same counted/never-counted split as bee-hive, plus the rationale: "Bee's own artifacts never inflate a fix past its lane."
- **Mode gate thresholds** (l.41-45): all-knowledge-files → `docs` lane, exit planning (announce one line, write, format-check, capture per bee-hive; no plan.md, no cells, no gates); 0–1 flags → `tiny` (≤2 product files, one direct task) or `small` (≤3 product files, no gray areas); 2–3 flags or story-sized → `standard`; 4+ flags or any hard-gate flag → `high-risk`; one yes/no proof decides whether the plan is real → `spike`, regardless of flags.
- **Asymmetric escalation rule** (l.47): "The mode gate **re-runs upward** the moment evidence demands escalation; de-escalation requires cited evidence."
- **Where the mode-gate record lands** (l.49): flag count + product-file count + lane choice recorded in — **tiny**: the cell itself (`action`/notes), there is no plan.md (D3); **small**: the logged scoping-synthesis decision (D4); **standard/high-risk**: `plan.md`. Above `small`, state why smaller modes are insufficient.
- **Greenfield init lane** (l.51, P1 / docs/09 item 6): first slice is one init cell with `must_haves` = setup succeeds from scratch, one passing test exists, standard commands recorded in `.bee/config.json`, clean first commit — before any feature cell. "Infrastructure first"; the init cell's verify command is the recorded `test` command itself.
- **§2 Lane-scaled bootstrap — tiny** (l.57): the targeted reads only (the ≤2 from intake) plus the mandatory critical-patterns digest; if the feature has a `bee.work-item` concept, also `bee.mjs knowledge context --work <feature> --budget 20000` and read the manifest's files.
- **§2 — small** (l.58): bounded bootstrap — `CONTEXT.md` if one exists + `decisions active --recent 3`; plus the same `knowledge context` condition.
- **§2 — standard/high-risk, 6-step ordered bootstrap** (l.59-65):
  1. **Area truth first, `bundle → decisions → history` (G4)** — with a bundle read `docs/knowledge/areas/<area>/` for every touched area plus `bee knowledge context --work <feature>`; `docs/specs/` is the read-only compatibility surface resolving a legacy `docs/specs/<area>.md#R7` citation through its pointer stub, never a read-or-write site for current truth (`scripts/okf_specs_fence.mjs`, G2). No bundle → read `docs/specs/<area>.md` before its code, `reading-map.md` before any broad grep.
  2. `docs/history/<feature>/CONTEXT.md` (or the hive scoping synthesis for surface-scope-earlier work).
  3. Critical patterns, bundle-branched, already digested from the preamble; re-read for the feature's area as needed.
  4. Recent decisions: `decisions active --recent 3`, then recall for the area through structured filters and the derived index (decision-propagation D7/D8) — `decisions search --tag <tag>` / `--scope <area>` (multi-term `--text` is **OR-ranked**; `--all` reaches the archive), plus the area's section of `docs/decisions/index.md` as "the complete-by-construction recall surface". **"Bare substring grep is the fallback, never the recall path."**
  5. Tag-matched precedent in `docs/history/learnings/` (grep the feature's domain keywords); inject hits as "we've solved X before: <file>" — **"precedent beats research."**
  6. Session scout: `bee.mjs status --json`.
- **§3 Discovery levels L0-L3** (l.71-74): **L0 skip** (pattern already exists in repo or learnings; cite it); **L1 quick verify** (confirm one API/version/behavior with a command or doc check); **L2 standard** (compare 2–3 candidate approaches, note trade-offs); **L3 deep dive** (unfamiliar territory, external systems, or hard-gate flags). "Pick the lowest level that removes real uncertainty."
- **§3 — `bee-xia` in-chain at L2+** (l.76): local truth → local reuse → upstream patterns → version-aware docs, **evidence labels on every claim**, and the **anti-reinvention ladder** (reuse → built-in → adapt upstream → build) for the recommendation; its findings merge into the approach, "never a standalone research file".
- **§3 — delegation tiers** (l.76): §2 lane-scaled bootstrap delegates as an **extraction-tier** I/O worker; other ad-hoc research dispatches during discovery (incl. bee-xia) default to the **generation** slot; **ceiling** requires the `[bee-tier: ceiling]` marker plus a one-line justification.
- **§3 — three layers of knowledge** (l.76): frame candidates through tried-and-true (what the repo/ecosystem already trusts), new-and-popular (current mainstream, verify version claims), first-principles (what the problem actually requires). "Recommend from evidence, not novelty."
- **§3 — Artifact fan-out (decision 0009)** (l.78): only **L2/L3** discovery earns a separate `docs/history/<feature>/discovery.md`; at L0/L1 record the finding in `plan.md`'s `## Discovery` note and cite it — "do not spawn a discovery file that just restates the current state `plan.md` already carries." - **Model tier assignment** (l.120, decision 0016): you may leave the model `tier` unset — the orchestrator judges each cell's difficulty and assigns the tier when it dispatches; set `tier` only as a hint when a cell is obviously mechanical (`extraction`) or obviously a hard integration/architecture call (`ceiling`), "and even then swarming may override it".
- **Verify is scoped, not full** (l.122, verify-scoping D2, decision `20534ea9`; ci-owned-verify D1/D6): a cell's `verify` is the narrowest honest check covering its change — the specific test file(s) or pattern for the touched area, never the full configured test/verify command by default. In this repo: `node scripts/run_verify.mjs --only <suite>` or the direct test file, not the full `commands.verify` chain. The full configured verify is never owed locally and never authored as a per-cell `verify` — CI runs it on the project's own cadence and auto-files a `verify-red` issue when red. The dev loop's broader check is `commands.test` (`run_verify.mjs --impacted` / `--impacted-from-git`), selected from the impact registry (`impact_registry.mjs --query`) — narrower than the full chain, wider than one `--only` suite, "and still never authored as a per-cell `verify`". Mid-iteration run the level-1 impacted run (`run_verify --impacted-from-git --level 1` — direct edges only, seconds); the transitive impacted run (`commands.test`) is the wave-close/merge gate.
- **No-test sentinel** (l.122, decision 55b951e1): a repo may declare itself no-test by setting `commands.verify`/`commands.test` to the sentinel `"none"`; there a cell's own `verify` may itself be `"none"`. "Author it only there, never invent a fake check to satisfy the field, and never carry the sentinel into a repo that has real commands."
- **§6 Prep step 3 — brief refresh** (l.123): if an implement plan was rendered at §5, invoke `bee-briefing` in refresh mode so Affected Files and Implementation Steps re-project from the created cells; if no brief exists, skip.
- **§6 Prep step 4 — handoff by lane + phase enum** (l.124): tiny/small → `state set --owner planning --phase swarming --next-action "Invoke bee-swarming (single execution worker)."`; every other lane → `--phase validating --next-action "Invoke bee-validating."` **The phase must be a real member of the enum**: `idle, exploring, planning, validating, swarming, reviewing, scribing, compounding, grooming, compounding-complete`. "Completion is carried by the approved gate, never by a phase name." `--owner` always names the selected record's pre-mutation phase and is not persisted.
- **Scope-Reduction Prohibition** (§, l.128): if the shape cannot fit budget or context, **never** quietly shrink a locked decision or drop a must-have. Answer **`SPLIT RECOMMENDED`**: propose slice boundaries, each slice honoring every locked decision it touches, and let the user choose. Cheaper alternatives found in research are *noted* alongside the honored decision — swapping them in requires the user superseding the D-ID.
- **Headless** (§, l.132): run intake classification, lane-scaled bootstrap, discovery, synthesis without questions. Standard/high-risk → write `plan.md` and stop, Gate 2 never self-approved. Tiny/small → produce the draft-cell preview + inline reality check in the structured terminal report and stop **before persisting cells** — the merged gate is never self-approved. Ambiguities (mode borderline, conflicting decisions, missing CONTEXT.md sections) go to an `Outstanding Questions` section.
- **Red Flags** (§, l.136-148), 13 items incl.: skipping the mandatory critical-patterns digest / active decisions / `CONTEXT.md` · full-bootstrapping before the mode gate picked the lane (D8 inverts this) · skipping the mode gate or choosing a mode without counting flags · counting `.bee/**`, `docs/**`, or generated projections as product files (D6) · defaulting to phases without proving the work needs them · editing `plan.md` content after Gate 2 · writing a `plan.md` for tiny, or by default for small (D3/D4) · persisting cells before the merged gate approval (persist-then-preview, D5) · cells or prep artifacts before Gate 2 · future-slice cells · pseudo-cells in markdown · vague exit states, missing deps, or a `verify` that cannot run · silently swapping a locked decision for a "better" research finding · shrinking scope instead of answering SPLIT RECOMMENDED.
