- **Reality gate — five named dimensions** (step 2): MODE FIT / REPO FIT / ASSUMPTIONS / SMALLER PATH / PROOF SURFACE, each scored PASS|FAIL with file/command evidence. Named fail triggers: nonexistent code paths, unsupported commands, stale versions, missing credentials, hidden architecture work, excess ceremony. A failed reality gate halts the pipeline and returns to bee-planning.
- **Feasibility matrix schema** (step 3): every blocking assumption gets a row `assumption | risk | proof required | evidence | result`. Plausibility language is an automatic NOT READY. - **Accepted evidence list** (§Accepted Evidence): existing implementation, file/API/type inspection, command output, build/typecheck/test result, official version/doc proof, runtime probe, or a `.bee/spikes/<feature>/` result. Evidence that is only "should work", "likely", "expected", or model knowledge → NOT READY.
- **Static evidence exemption for tiny/small (test-economy D5)** (line 49): a quoted (not paraphrased) `file:line` citation proving the code path exists and behaves as assumed is *sufficient* at these lanes; no runtime spike needed. Spike only when the assumption touches an API/library/technique with no in-repo precedent. Explicitly does not loosen `standard`/`high-risk`.
- **Spike rules** (§Spike Rules): one spike answers exactly one yes/no question; disposable code lives under `.bee/spikes/<feature>/`; NO → return to bee-planning with the failed assumption and required plan change; YES → record discovered constraints; spike code never silently becomes production code.
- **Debug discipline (test-economy D5)** (line 58): hypothesis before repro, read before rerun — record the hypothesis in one line plus the `file:line` evidence before writing any repro script ("a repro script with no prior hypothesis is not a spike, it's a guess with extra steps"). Cap the loop at **2** failed repro rounds; after the second wrong repro stop running scripts and go back to reading/instrumenting. Declared prose law; the machine-enforced proof-tier matrix lives in `bee-executing/SKILL.md`.
- **Executable code never in `docs/history/`** (line 60, GitHub #17): `docs/history/` is the tech-agnostic knowledge layer — `.md` only (CONTEXT.md, plan.md, reports, walkthrough). A cell's `verify` is a runnable command; a multi-line harness lives either in the project's own committed scripts or, if disposable, in `.bee/spikes/<feature>/` (the disposable-code half of "the one canonical scratch home", `docs/specs/doctrine-layer.md` R17). A **write-guard** denies code-extension files (`.sh`, `.mjs`, `.py`, …) under `docs/history/`, and denies any scratch-shaped write landing in a tracked directory outside `.bee/tmp/`/`.bee/spikes/`.
- **Plan checker dispatch** (§Plan Checker, line 64, decision 0021): dispatched on the **`review` slot** — `resolveTier(root, 'review', runtime)`, default opus on Claude, generation fallback; state the model explicitly; if the runtime cannot select per-agent models, cap its reads and output instead.

- **High-risk persona panel** (line 68): coherence + feasibility lenses always, plus conditional lenses (security, product, scope-guardian) chosen by the diff of concerns. Dedupe findings, then synthesize into auto-fix vs present-for-decision buckets.

Test question: "Could a worker with no session history pick each cell up cold?" **CRITICAL** flags — assumed context, vague acceptance, scope overload, unproven feasibility, broken verify — must be fixed before approval; **MINOR** flags may ship with a recorded note.
- **Decision vocabulary — exactly four verdicts** (§Decision Vocabulary): `READY`, `READY WITH CONSTRAINTS`, `NOT READY - RUN SPIKE`, `NOT READY - RETURN TO PLANNING`. READY is a feasibility verdict, not execution approval — Gate 3 still requires the user.
- **Advisor consult before Gate 3** (§Gate 3, AO2b/AO3/AO4): for a high-risk or hard-gate slice the orchestrator consults the configured advisor **before** presenting Gate 3 and before self-approving under any bypass level; bypass levels lift the human checkpoint, never this mechanical precondition. - **Staleness definition — four verbatim conditions** (AO13, lines 97–100): (1) its feature differs from `state.feature`; (2) the newest active decision id changed since the consult; (3) `sha256(plan.md)` changed since the consult; (4) the ref predates the most recent revocation of the execution gate. "Never a time-based TTL — AO13 already burned this feature on one invented number once."

- **Machine report path** (line 106): full machine report (reality gate, matrix, plan-checker findings, cell review, approval block) → `docs/history/<feature>/reports/validation-<slice>.md`.
- **bee-briefing refresh hop** (line 106): for `small`/`standard`/`high-risk`, invoke `bee-briefing` in refresh mode to patch the implement plan's Validation Plan section with accepted evidence links (and flip its `status` if a source changed) so the Gate 3 message links a current brief.

- **Optional cross-model second opinion** (line 106): agreement → mention it; disagreement → quote both positions; never auto-resolve.
- **Approval scope** (line 106): covers the **current work only**; future slices return to planning and validating.
- **On-approval state writes** (line 108): `bee.mjs state gate --name execution --approved true`, then `bee.mjs state set --owner validating --phase swarming --summary "<summary>" --next-action "Invoke bee-swarming for the validated work."` Explicit note: "`validated` is not a phase — it never was; the approved execution gate is what records that.
