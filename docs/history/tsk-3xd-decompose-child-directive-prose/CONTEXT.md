# tsk-3xd — Truyền thân mệnh lệnh xuống task con khi auto-decompose

## Feature boundary

`src/intake/plan.mjs` dispatches auto-decompose children with an EMPTY
directive: the executor only gets `title` + `refs` + `verify`, no prose
saying what to do, which files to read first, or which locked decision it
must obey. Children are stamped straight to stage `executing`
(`stageForStep(domain, 'Execute')`, decompose.mjs:940) — no clarify/decompose
gate to backfill missing context, so they run blind.

Three-layer bug (scout 2026-08-06):
- **Tầng 1** — the judge-scout LLM prompt (decompose.mjs:227) never asks for
  directive prose; schema is `children: [{title, verify, kind, ...}]`.
- **Tầng 2** — `normalizeChild` (decompose.mjs:231-255) keeps only `title`,
  `verify`, `kind`, `risk`, `refs`, `footprint`, `rawDeps` — any prose the
  model does return gets discarded here.
- **Tầng 3** — `addWork` (decompose.mjs:929-944) never passes `description`,
  even though both worker prompt templates
  (`src/runner/prompt-templates/worker-prompt-default.txt`,
  `worker-prompt-skill-pointer.txt`) interpolate `{description}`.

`buildDecomposeChildrenVerdict` (shared by both the LLM auto-decompose branch
and the native `fgos plan --children` caller-supplied branch, tsk-27y
D1) uses the same `normalizeChild` — so even a live session with full
context reasoning through its own split has no path today to hand real
directive prose to the children it creates.

## Locked decisions

| D-ID | Decision |
|------|----------|
| D1 | Two new optional fields, `action` + `read_first` (not the existing `description` field). Mirrors bee's cell shape (`upstreams/bee/skills/bee-planning/references/planning-reference.md:113`). Both are optional-additive — confirmed by precedent (`footprint`, `domain` both added under `SCHEMA_VERSION` 2 unchanged, work.mjs:422,439-460) — no `SCHEMA_VERSION` bump (currently 3, stays 3). `read_first` needs no new mechanism: `footprint` is already kept by `normalizeChild` (decompose.mjs:231-255) but never interpolated into the worker-prompt-templates — wiring `{footprint}` into both templates is the whole fix, zero LLM cost, zero schema risk. |
| D2 | `action` is generated by the LLM in the SAME judge-scout verdict call (extends tầng 1's prompt schema, no extra model round-trip) and is REQUIRED to cite a real locked-decision D-ID from the parent's own `CONTEXT.md`. `normalizeChild` mechanically checks the cited D-ID exists in the parent's decision table (reusing the existing `findUncoveredLockedDecisions` pattern already used for footprint-coverage, decompose.mjs) — extends tầng 2. A child whose `action` is missing or cites no real D-ID is invalidated, same discipline as today's missing-`verify` rejection. This was chosen over two weaker options: freeform LLM generation (nothing to check the prose against) and mechanical extraction from `plan.md` (brittle — no guaranteed 1:1 child↔phase mapping, breaks for tiny/small mode items). |
| D3 | Fix scope is `decompose.mjs` only — `normalizeChild` + `addWork`. This covers BOTH the auto-decompose LLM path and the native `fgos plan --children` path for free, since both call the same `buildDecomposeChildrenVerdict`/`normalizeChild`/`addWork` (decompose.mjs:317-318, :417-420). The manual `fgos add --parent` path is a separate CLI surface (`bin/fgos.mjs`, `src/cli/command-registry.mjs`) with zero description-shaped flag today — confirmed by reading `add`'s full parameter list. That gap is explicitly OUT of this item's scope; it is already tsk-535's own stated scope. |
| D4 | Order vs tsk-535: tsk-3xd goes FIRST, no hard dep — recorded via `fgos edit tsk-535 --merge-after tsk-3xd` (confirmed live in store: `tsk-535.mergeAfter = ["tsk-3xd"]`). `mergeAfter` (`src/state/work.mjs:256-273`) only orders at merge time, never blocks clarify/planning dispatch — both items can run in parallel. Reason: tsk-3xd patches 40/53 description-missing items via real prose through the decompose path, shrinking tsk-535 down to two smaller pieces (`fgos add` missing `--description` for 13 root items, plus backfilling the 53 already-broken items). If tsk-535 landed first with `description = title`, the 40 child items would look fixed while still being empty-meaning prompts to the executor — masking the symptom this item exists to catch. Chốt 2026-08-06, cites D1 of `docs/history/two-layer-dispatch/DISCUSSION.md` (item tsk-2t6). |

## Correction to the original bug report

tsk-3xd does **not** make tsk-535 redundant, and tsk-535 is **not**
superseded. tsk-3xd only patches forward: it never touches the 53 already-
broken items, and never touches the `fgos add` path (`bin/fgos.mjs` only
sets `description` at line 764, inside the `submit` branch — `--description`
only exists for `edit` and `tool register`).

The data-loss risk tsk-535 names is not live yet: `deriveTitle` is called
in exactly one place (`bin/fgos.mjs:748`); there is no migration or
re-derive verb anywhere in source; `docs/history/work-item-title-contract/
CONTEXT.md` still leaves "Whether D4's re-derive ships as a one-shot script
or a CLI verb" in its Deferred-to-planning section. It only fires once
someone ships that D4. The real hard constraint: both tsk-3xd and tsk-535
must land before that re-derive ships — but the item that ships it does not
exist yet, so there is nothing to attach a dependency to today.

## Pinned terms

- **Directive prose** (`action` + `read_first`): the per-child instruction
  payload a worker actually needs to act blind — `action` is why/what to do
  (citing the locked decision it satisfies), `read_first` is which files to
  read before starting (reusing `footprint`).
- **Auto-decompose**: the `judgeDecompose` LLM branch of `decompose.mjs`,
  as distinct from the native, caller-supplied `fgos plan --children`
  branch — both share the same child-validation/write path (`tsk-27y D1`).
