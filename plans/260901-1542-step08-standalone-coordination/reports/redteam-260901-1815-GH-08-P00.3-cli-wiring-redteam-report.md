# Red-Team report — P00.3 CLI wiring and live proof

Cell: P00.3 (step-08-standalone-coordination, Phase 00 R9-R11)
Verdict: FINDINGS (2 HIGH, 2 MEDIUM)

Full write-up appended under the "## Red-Team" heading in
`docs/architect/agent-coordination/verification/step-08-standalone-coordination/P00.3.md`.
This report is a condensed pointer to that write-up plus the repro method.

## Method

Read current-cell.md, P00.3.md in full (Proof Matrix, Commands, Review,
Fix Evidence), the phase-00 plan's R9-R11 text, both live-proof logs, the
full `--assignment`/`--contract` branches of `src/runner/dispatch/cli.mjs`
including `findDuplicateOverrideFlag()`, the `feature.yaml` diff, and all
touched test files. Built a standalone repro script
(`redteam-probe.mjs`, in the session scratchpad, not committed) that spawns
`node src/runner/dispatch.mjs execute ...` as a real subprocess against a
temp `.fgos/config.json` with a harmless echo executor, mirroring the
existing test suite's own `mkTempDir()`/`writeEchoExecutor()` pattern —
every finding below is demonstrated by a real CLI invocation, never a mock
or a static-analysis guess.

## Findings

1. **HIGH — `findDuplicateOverrideFlag()` misses a duplicate flag when the
   second occurrence is the very last token in argv.** The helper's loop
   bound (`i < rest.length - 1`) excludes exactly one array index — the
   literal last element — regardless of whether that occurrence "has a
   following value," contradicting the Fix Evidence's own description of
   the mechanism. Reproduced: `--executor named_executor --executor` (bare,
   trailing) dispatches successfully (exit 0) instead of being rejected.
   Practical harm is bounded (`flagValue`'s `indexOf` still picks the first
   value, so no wrong executor is silently substituted), but it is a real,
   live gap against R9's literal "reject duplicate ... before launch" text.

2. **MEDIUM — the same helper has a false-positive mode.** A value that
   happens to literally equal another flag's name string (e.g. `--tier`
   given no real value, immediately followed by a genuine single
   `--executor foo`) triggers a false "duplicate flag" rejection, because
   the checker does raw string-equality across all of `rest` with no
   concept of flag-vs-value position. Confirms `flagValue()` and
   `findDuplicateOverrideFlag()` disagree on what counts as "a flag
   occurrence."

3. **HIGH — P00.4's claimed durable tracking does not exist.** The
   Coordinator disposition says the deferred HIGH `deriveProviderFamily`
   finding "is fixed via a small dedicated follow-up cell (P00.4) ... See
   index.md for the P00.4 entry." `index.md` has zero occurrences of
   "P00.4" and zero mention of the deferred defect anywhere. The only
   record is this file's own prose. If index.md's Cell Log isn't updated
   with a real P00.4 row before this cell closes, the disclosed governance
   hole has no durable trail.

4. **MEDIUM — a third, previously-unflagged `deriveProviderFamily`-family
   bug, live-reproduced in the glm-cli proof log's own quoted evidence.**
   `transport.mjs:163`'s `provider: executor.provider ?? executor.command`
   reads a dead config field (`provider` — zero of 12 registered executors
   set it; everyone uses `providerModel`) and falls through to the literal
   command name, ignoring the already-correctly-computed
   `executor.governance.providerFamily` sitting on the same object. Live
   effect: the glm-cli proof log's own stderr banner reads
   `provider=claude` when the real provider family is `z-ai` — the
   Reviewer quoted this line verbatim without explaining the discrepancy.
   Confirmed the blast radius is confined to the stderr banner and the bare
   (non-R9) `dispatch execute <executorId>` door's own RunResult — R11's
   specific proof-required RunResult fields for the `--assignment`/
   `--contract` doors are not corrupted (`assignment-runner.mjs` never
   forwards `rawResult.provider`/`.command` into the persisted
   `result.json`, confirmed against a real result.json on disk). Predates
   P00.3 (`transport.mjs` absent from this cell's diff). Same root-cause
   family as finding HIGH already disclosed in P00.3's Review section —
   should be folded into the same P00.4 scope.

## Checked, no finding

- Ordering attack on `--contract` door's `claimAssignmentId` vs. the
  duplicate-flag check: confirmed a real empty directory is left behind on
  a rejected duplicate, but this exactly matches the Fix Evidence's own
  disclosed precedent. Not new.
- R10 completeness sweep: no stale bare `pi` executor id anywhere in the
  repo; the two `"command": "pi"` hits in `.fgos/config.json` belong to the
  legitimately-registered `codex-pi`/`pi-herdr` executors.
- `--executor=value` equals-sign syntax: pre-existing `flagValue()`
  behavior (never supported), not something this fix changed.
- New-test quality: both new duplicate-flag tests use real subprocess
  invocations with real duplicated argv, not mocks — but both only cover
  the "duplicate with a value at both positions, not last in argv" shape,
  which is exactly the gap findings 1-2 exploit.
- Focused suite (450/450) and smoke check reproduced clean, matching
  claimed evidence exactly.
- Scope: `git status --porcelain -- src test domains` shows only `cli.mjs`,
  `feature.yaml`, and 5 test files; `resolve.mjs`/`assignment-policy.mjs`/
  `config.mjs` are genuinely absent from this cell's uncommitted diff.

## Unresolved questions

- Whether `--flag=value` syntax should be added to `flagValue()` /
  `findDuplicateOverrideFlag()` at all, or whether the CLI's whitespace-
  separated convention should just be documented as the only supported
  form — a product decision, not something this red-team pass resolves.
