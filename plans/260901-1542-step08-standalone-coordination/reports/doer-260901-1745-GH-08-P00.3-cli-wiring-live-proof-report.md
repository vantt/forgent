## R11 — Live two-executor proof

Used the `--contract` door for codex-cli and the `--assignment` door for glm-cli (documented why in the proof logs: an inline `--contract` carries no `assignment.policy`, so its tier floor always defaults to `'standard'`, which `z-ai`'s single configured tier — `lightweight` — cannot satisfy; a declared `--assignment` can carry an explicit `policy.minTier` set directly on the Assignment object, a documented `buildAssignment` caller override, letting glm-cli's real tier ceiling resolve legally).

**codex-cli: DONE.** Two attempts: the first produced a technically-correct read of `package.json` ("forgent") but the executor wrote its own JSON field names instead of the required `agent-result.json` schema (a fixture-authoring gap on my end — the real system prompt only says "write structured JSON", never states the required `status`/`summary` fields, confirmed in `assignment.mjs`'s `renderAssignmentPrompt`). Second attempt, with a corrected contract, produced a schema-valid claim and the same correct answer. Both attempts proved zero mutation and accurate `provenance.executor/provider/model/tier/governance`, including `executor.source.scope: "cliOverride"` proving `--executor` reached the resolver.

**glm-cli: BLOCKED (live-executor timeout).** The config-tier mismatch above (`standard` unsupported for `z-ai`) is expected, correct R8 behavior, not a failure. The real spawn attempt via `--assignment` genuinely hung: `claude -p ... --model z-ai/glm-5.2` (glm-cli's real invocation, OpenRouter-routed) printed an "unrecognized_model" warning and produced no further output for 180s (one bounded retry, after an earlier attempt was killed prematurely by the shell tool's own 120s cap, not counted). Found and cleaned up one orphaned grandchild process (`kill -TERM`, confirmed gone) that `timeout` didn't reach transitively. The `dispatch-plan.json` written *before* the hang still proves accurate `executorId: "glm-cli"`, `governance.providerFamily: "z-ai"`, and `egress.target: "https://openrouter.ai/api"` — matching `.fgos/config.json` exactly — so R9's CLI wiring is proven on both doors even though R11's glm-cli half stopped short of a completed RunResult.

Full command transcripts, RunResult JSON, and dispatch-plan excerpts: `docs/architect/agent-coordination/verification/step-08-standalone-coordination/proofs/P00.3/{codex-cli,glm-cli}-live-proof.log`.

### Incidental finding (not fixed, out of scope)

Live evidence surfaced a real discrepancy: for `codex-cli` (no `providerModel` field in its config entry), `dispatch-plan.json`'s `governance.providerFamily` reads `"codex"` while the RunResult's `policy.providerModel` (from `resolveAssignmentDispatchPolicy`) reads `"claude"` for the identical dispatch. Root cause: `assignment-policy.mjs` calls `deriveProviderFamily(registeredExecutorEntry)` (one arg, defaults to `'claude'`) while `resolve.mjs` calls `deriveProviderFamily(executorEntry, executor.command)` (two args, yields the real CLI command string). Pre-existing in already-landed P00.1/P00.2 code (the call site carries its own "Phase 00 R6 fix F1" comment); not introduced here and outside R9-R11's scope to fix. Recorded in `proofs/P00.3/codex-cli-live-proof.log` for Reviewer/Red-Team.
