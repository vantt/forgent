## Findings

**MEDIUM — `assignment-policy.mjs`'s fix does not mirror `resolve.mjs`'s
extraction for a bare (non-`invocations[]`) executor entry with a real
non-Claude command; the two call sites still disagree for that shape.**

`src/runner/dispatch/assignment-policy.mjs:213`'s new
`registeredExecutorCommand` line only extracts from `invocations[]`. For a
bare-shape entry, `resolve.mjs`'s `byExecutor = executorEntry` branch
(L419-421) uses that entry's own flat `.command` as the real command;
`assignment-policy.mjs` leaves the second `deriveProviderFamily` argument
`undefined`, so it silently falls back to `'claude'`. Empirically
reproduced:

```js
runnerConfig.executors['bare-nonclaude'] =
  { kind: 'agent', command: 'some-other-tool', args: [], allowCrossProvider: true };
// resolve.mjs: resolveExecutorConfig(...).governance.providerFamily === 'some-other-tool'
// assignment-policy.mjs: resolveAssignmentDispatchPolicy(...).providerModel === 'claude'  <- still wrong
```

Violates P00.4.md's own Acceptance line ("mirroring `resolve.mjs:429`'s
already-correct two-argument call") and its own named Bug Taxonomy risk
("leaving the other's default parameter un-audited"). Currently latent —
verified via `.fgos/config.json` that all 12 live registered executors are
`invocations[]`-shaped, so no live dispatch is mis-tagged today — but this
is the same bug class recurring for a different shape the moment a
bare-shape executor with a real non-Claude command is registered without
`providerModel`/`provider`. Not a one-line fix: a naive full-parity
version (also reading the bare `.command`) was already tried by the Doer
and regressed ~20 tests, because several existing test fixtures register a
bare executor under id `'claude'` with `command: process.execPath` (a
swapped-in test binary, no real provider signal) and rely on the
`'claude'` default surviving that swap — read `operation-choice.test.mjs:
135-142` and confirmed this convention is real and structural, not
incidental. Smallest fix direction: document this residual gap explicitly
in P00.4.md's Gaps section (currently silent on it), and/or add a loud
guard (a `doctor` check or `validateExecutorShape`-time warning) for a
future bare-shape executor registered with a non-Claude-CLI `.command` and
no `providerModel`/`provider`.

**MEDIUM — `transport.mjs`'s banner fix is functionally correct, but the
Proof Matrix's cited test evidence for it is false; no test discriminates
the changed behavior.**

`src/runner/dispatch/transport.mjs:169`'s fix itself is correct —
independently reproduced with a `providerModel: 'z-ai'`, `command:
'claude'`, no-`.provider`-alias executor (the real `glm-cli` shape): old
fallback (`.command`) returns `'claude'` (wrong), new fallback
(`.governance.providerFamily`) correctly returns `'z-ai'`. But P00.4.md's
Proof Matrix and the Doer's report both claim
`dispatch.test.mjs`'s existing `.provider` assertions "already exercise
the transport.mjs banner-field fix... without modification" — checked
every cited line (1827, 1833, 2718, 2738, 3247, 3264, 3437, 3631, 4852,
4855, 4917, 5515): each either pins an explicit `.provider` alias
(alias-wins precedence was never touched by this fix, proves nothing about
the fallback) or has no `providerModel` at all with a command for which
old and new fallback coincidentally produce the identical string. No test
anywhere in this diff exercises "registered executor has `providerModel`
set, no `.provider` alias" — the exact shape `glm-cli` is, and the exact
bug this fix's commit message names as its own motivation. Smallest fix
direction: add one `dispatch.test.mjs` test mirroring the reproduction
above.
