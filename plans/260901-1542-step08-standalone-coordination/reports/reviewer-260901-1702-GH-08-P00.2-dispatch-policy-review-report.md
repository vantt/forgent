## Findings

**F1 (MEDIUM)** — The R6(b) exemption (`assignment-policy.mjs:154-166,169`)
lets `primaryExecutor === 'claude'` or `=== runnerConfig?.executor?.command`
skip the registry check even when neither is actually a key in
`runnerConfig.executors`. In that branch `resolvedProvider` falls back to
the raw executor-id string (`primaryExecutor`), not a value derived from any
registered entry — reproducing H2a's exact shape for this carve-out, and
contradicting R6's own wording ("explicit `claude` default only for a
**registered** executor without the field"). The exempted branch itself has
zero test coverage — no test combines a non-empty `runnerConfig.executors`
that omits `claude`/the default command with `preferExecutor` left at
default. This is the exact real-machine scenario (`.fgos/config.json`
registers only `pi`) that motivated the fix, untested.

**F2 (HIGH)** — Governance (`assignment-policy.mjs:206-211`) checks only
`resolvedProvider` (the derived provider family) against
`options.disallowedProviders`; it never separately checks
`primaryExecutor`/`executorId`. Before this cell, `resolvedProvider` was
always the executor id (H2a's bug), so `disallowedProviders` was, in
practice, keyed by executor id. After this cell, for any *registered*
executor whose `providerModel` differs from its id, the same
`disallowedProviders` config value silently stops blocking it — a real
governance-semantics regression for any existing deployment, with zero new
test covering a registered executor whose id and derived family differ
against `disallowedProviders`, and no `disallowedExecutors` (or equivalent)
added to let governance act on the executor id as R6 requires ("checks the
resolved provider family and selected executor as **distinct fields**").

**F3 (LOW)** — `provenance.*.source.scope` values (`opPolicy`, `cliOverride`,
`work`, `default`, `registeredExecutor`, `runnerConfig`) don't match the
FlowDefinition/CoordinationSession contract's documented example vocabulary
(`operation`, `cli`, `runner`, ...). Not a hard R7 violation — ADR-009
explicitly defers exact per-phase scope naming — but the Doer's claim of
matching the contract "verbatim" overstates: only the `{value,source:
{scope,id}}` object shape matches verbatim, confirmed field-by-field; the
scope vocabulary itself diverges and will need reconciling before Phase 03.

**F4 (LOW)** — `provenance.model.source` / `provenance.persona.source` can
be `undefined` (not a `{scope,id}` object) in reachable, untested states (no
`runnerConfig` passed; non-`reviewer` role with no persona override) —
contradicts the documented always-an-object shape and would throw for a
consumer that blindly destructures `.source.scope`.
