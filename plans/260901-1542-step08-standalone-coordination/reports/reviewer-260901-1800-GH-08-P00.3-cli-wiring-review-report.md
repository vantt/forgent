## Findings

**HIGH — `deriveProviderFamily` call-site disagreement is a real,
live-reproducible governance/correctness gap**, confirmed against the actual
`.fgos/config.json` registry to affect 3 of 12 registered executors
(`codex-cli`, `codex-herdr`, `herdr` — command not `claude`, no declared
`providerModel`/`provider`). `assignment-policy.mjs:201` calls
`deriveProviderFamily(registeredExecutorEntry)` (1 arg, defaults to
`'claude'`); `resolve.mjs:429` calls
`deriveProviderFamily(executorEntry, executor.command)` (2 args, real
command). Consequence 1: `assignment-policy.mjs:251`'s `disallowedProviders`
governance check operates on the wrong value — a `disallowedProviders:
['codex']` config would silently fail to block `codex-cli`. Consequence 2:
model-tier resolution silently borrows `claude`'s `modelPolicies` table for
a non-`claude` executor instead of failing closed per R8 (currently inert
for `codex-cli` only because its invocation template never substitutes
`{model}`). Pre-existing from P00.2, legitimately out of P00.3's diff to fix,
but live-confirmed by this cell's own proof and should not close Phase 00
without a tracked follow-up — Phase 00's own exit criterion asks the live
proof to demonstrate "the policy path... not only technical executor
viability," and this mismatch is exactly that kind of policy-path gap.
Smallest fix: pass the executor's real resolved command as the second arg at
`assignment-policy.mjs:201`, mirroring `resolve.mjs:429`.

**MEDIUM — R9's "reject duplicate/conflicting flags" clause unmet.** R9's
text and the cell's own Bug Taxonomy explicitly name this scenario;
`--executor` was wired using the same silent-first-occurrence
`flagValue()` behavior as the already-unvalidated `--model`/`--tier`, not the
required rejection. Existing precedent for two other unvalidated flags does
not satisfy a requirement that names this exact defect.
