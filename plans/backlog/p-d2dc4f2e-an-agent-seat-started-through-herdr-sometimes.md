# Why

Observed 2026-10-20 (owner machine, release `4efa6e15`, `forgentx-95`): xai (`grok` 0.2.101) seats failed twice in a row in the Seat Binding council (`unit-run-1792487181128-290534a4` producer: `start-refused.json` `terminal-launch-not-started` "launched root process was not identified in time", the launcher command shown typed twice in the pane with no output; `unit-run-1792495203944-8d839c6e` synthesizer: the brief landed in zsh as `quote>` lines, then cancel). The same xai seat passed at 09:06 the same day, so it is intermittent. Same family of fault as the pi brief whose Enter is lost (`plans/reports/debug-261020-1611-pi-herdr-brief-not-submitted.md`, pi still has `submit_by_prompt_door: false`). A failed launch is scored `execution-failure` with no fallback to another family, and `fgos workflow resume` does not rerun a failed step, so one bad launch costs the whole council run. Same evening: a pi seat (deepseek `v4-pro` via OpenRouter, `unit-run-1792496756320-c4e1a98b` reviewer) sat idle 20 min on a 402 shown only in its pane (pi asks `max_tokens` ≈ 911k per call; OpenRouter pre-authorises that against the balance), unseen by fgOS; resumed by typing "continue" into the pane after the owner topped up. Diagnosis `plans/reports/debug-261020-1917-herdr-seat-private-home-missing.md`: the 18:32 case is brief delivery (`delivery-unknown` → supervisor cancel; omp and pi still type the brief raw, `submit_by_prompt_door: false`; the kill landed mid-typing so the rest went into zsh); the 16:08 case is a private home whose bwrap source vanished within ms of launch, cause unproven, preflight recording proposed. Later the same evening the fault also hit codex (`openai-codex`/tetcu72, doc plan 260925 Phase 8), so it is not xai-only: `unit-run-1792509713538-50916d7b` (22:21) `terminal-launch-not-started` with the launcher command again shown typed twice in the pane, and `unit-run-1792503188381-28aaa7b2` (20:33) where codex, which already submits by the prompt door, showed the brief as an unsent `[Pasted Content 7224 chars]` until a cancel 22 s later. Panes of closed runs stay open as bare shells, which reads as a failure to the owner. 2026-10-21 00:31–02:42 (reported by session `forgentx-5f`, doc plan Phase 8): six more `terminal:delivery-unknown` → exit 11 across codex and gemini/omp. Codex: `unit-run-1792518154636-e9d4eb04` (00:43) and a 00:48 run showing an unsent `[Pasted Content 9284 chars]`, and `unit-run-1792518678834-c151429b` (00:53) with an 868-char pointer prompt, so prompt size is not the cause. omp: a 00:31 run and `unit-run-1792525295258-f400cce0` (02:42), whose screen already showed omp "Working… 2%" when the supervisor cancelled, so delivery can be judged unknown after the agent received the brief (false negative). The active release predates the omp prompt-door change (lane C, not yet activated). Relaunching the same brief usually works on the 1st–2nd retry. Side finding: a brief file under `/tmp/fgos-work` is invisible to the Doer (bwrap private `/tmp`), so a pointer prompt must reference a file inside the worktree. 2026-11-06 (HARDEN T5): a seat whose brief never reached its agent (receipt `abandoned*` or `terminal:foreground-not-agent`) is now launched once more on the same executor and account, unless a writing seat already changed the worktree, and a second loss stops it by name (`733e3a74d`, runner spec "Execution Core and Dispatch"); a brief whose delivery is unknown is not retried. Still open toward the CoS: `fgos workflow resume` does not rerun a step whose seat never started, the cause of the intermittent foreground loss, and the omp setup-wizard screen (HARDEN branch `harden/t5-seat-start`).
