The layer re-measures the baseline call classes and lands on both machines.

## Owner questions

### OQ-1. H8: cross-process addon verification needs a recorded file identity; where may it live?

**Answered 2026-10-21 16:20 (a), then superseded 17:43 by OQ-3 (c): no `activation.json` field.** The 16:20 answer was: Option (a), exactly one optional field (`nativeAddonIdentity`) in `activation.json`, its writer in `init.rs` and the loader trust rule; no cache file, no doctor row, no manifest change. Phase 2 step 2c is unblocked.

**What is happening.** Every Node process that loads the addon hashes it before `dlopen` (8.1 ms on the 11.4 MB release addon, 75 ms on the 86 MB debug addon in the suite; speed seat §0). The owner asked that this become cross-process (H8, moved from GIT to T0 at 15:55). GIT's acceptance criteria are: fail closed on any digest mismatch; any change of dev, ino, size, mtime or ctime of the `.node` invalidates; a verification is never trusted across a different manifest digest.

**Cause.** The only verified state today is the per-process `Map` in `src/git/native.mjs:11, :49-53`. Rust verifies at stage, activate and verify (`verify.rs:121-235`, `init.rs:427-456`) but records only `artifactDigest` and `activatedAt` in `activation.json` (`init.rs:96-112`); no file identity is written anywhere. A cross-process answer that satisfies criterion 2 must compare the live stat tuple with a tuple recorded by the party that verified the bytes, so the tuple must be on disk. Every viable option is new on-disk state.

**Options.**
- (a) Record `{dev, ino, size, mtimeNs, ctimeNs}` of the staged addon in `activation.json` at activate, as one optional field `nativeAddonIdentity` keyed by `artifactDigest` (Rust `publish_activation_file`, `init.rs:518-530`; ~25 Rust lines). The loader (phase 2 leaf) resolves `activation.json` through the existing `hostBinFromActivation` (`src/util/host-bin-path.mjs:41`), trusts the file when the manifest's `artifactDigest` equals the activation's and the live stat equals the recorded tuple, and otherwise hashes as today and fails closed on mismatch (~15 Node lines). Gain: the hash disappears on the activated-release channel on every CLI call. Harm: `activation.json` is Packaging's record (Packaging and GIT must be told; optional field, previous release ignores it); the three workspaces and both machines populate it only on their next activation, which the T0 landing does anyway; the dev-host and test channels have no activation and keep hashing (the suite's 75 ms is TEST H3).
- (b) A sidecar written by the loader after its first verified hash, beside the addon (`libexec/native/fgos.node.verified`, written with `durable-file::install_once`): works on every channel. Harm: a new file and a writable location inside the release tree, which the install gate says must register in `fgos setup`/`fgos doctor`; a second mechanism beside the activation record (RUL104).
- (c) Keep per-process verification, moved unchanged into the T0 leaf and loaded lazily on the first door call. Criteria 1–3 hold trivially; zero new state. Harm: 8 ms stays on every process that uses the door and did not already load the Git addon; H8 stays open.

**Recommendation.** (a). It is the smallest change that meets all three criteria, adds no file and no mechanism (the activation is already the one verified record), and the landing procedure of phase 8 re-activates every workspace anyway.

**Scope of the answer.** A "yes to (a)" authorises one optional field in `activation.json`, its writer in `init.rs`, and the loader's trust rule, all inside phase 2 step 2c, with a message to Packaging/T9 and GIT before merge. It does not authorise a cache file, a doctor row, or a change to the release manifest or the dev manifest. Until answered, phases 2a/2b ship option (c) behaviour (the existing check moved into the leaf), and phase 2c stays blocked. Choosing (b) or (c) is also inside this question's frame.

On the `npm install -g github:vantt/forgent` channel the process door fails closed by name (`process-door-not-shipped: onboard this project with fgctl init`), as Git already does. **What is happening.** Arbitration D2 made producing `native-addon.json` for the npm channel part of T0. The red-team (FM-06, AD-07, Scope-F1, Sec-F9) showed that the first draft's shape, a `--npm-descriptor` flag plus two `package.json` `files` entries, cannot ship it.

**Cause.** `package.json` `files` is walked by the release build (`scripts/build-rust-distribution.mjs:172-182`), which throws when a declared entry is absent from the checkout (`:144-146`), so the entries would break every release build and `fgos doctor`'s `active-release-matches-checkout` (`src/setup/registrations.mjs:5153`); the pre-commit root allowlist refuses `native-addon.json` at the repository root (`.githooks/pre-commit:39-43`); `npm pack` runs from the checkout with no `prepack` step (`package.json:30-49`; `test/install-packaging.test.mjs:85`); the loader resolves `entries.fgos` to a file (`src/git/native.mjs:56-61`) that an npm tarball does not carry; and one tarball would have to carry a `.node` per release target. This is a packaging route (a staged tarball directory with per-target addons and a descriptor, and its own pack → install proof), not a flag.

**Options.**
- (a) Hand the npm channel to Packaging/T9 (the parent plan's phase 07) with the evidence above. In T0 the unactivated npm and direct-`node` channels fail closed by name for process facts (`process-door-not-shipped: onboard this project with fgctl init`), exactly as Git already does on those channels (`CHANGELOG.md` `[Unreleased]`, "On the npm/GitHub install channel, `fgos init` … refuses"); an activated workspace is unaffected because the host passes `FGOS_HOST_BIN` (`apps/fgos/src/legacy_exec.rs:246-248`). Cost in T0: 0 lines. Harm: the owner's 12:05 "ship the addon for the npm channel" is delivered later, by the lane that owns packaging.
- (b) Build the route in T0: the release build stages an npm payload directory (`libexec/native/<target>/fgos.node`, `native-addon.json` without `entries`, the Node sources), `npm pack` runs from that directory, and `test/install-packaging.test.mjs` is extended to call the process door from the installed package. Cost: ~120 lines in `scripts/`, a change to how the package is published, a per-target artifact policy, ~40 test lines; T0 grows by a packaging mechanism (RUL104) and touches Packaging's files.
- (c) A `prepack` hook writing into the checkout: refused by the pre-commit allowlist and by the release build's file walk; not viable.

**Recommendation.** (a). It keeps T0 on its own components, costs nothing now, and the npm channel is already closed for Git on the same terms; the T9/Packaging council designs the tarball route once for both addons' consumers.

**Scope of the answer.** A "yes to (a)" authorises phase 2 step 2b to record the hand-off (H14) and the one-door close criterion to stay as written; it does not change the process-observe route deletion (its only caller was hot-lock on Windows, served by the door on the activated channel).
