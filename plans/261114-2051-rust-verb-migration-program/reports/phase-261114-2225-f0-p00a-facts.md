## 2. Open facts

**U1. Node seal coalescer vs native writers.** No native Rust writer appends Work events: `packages/work-state/rust/src/event_reader.rs:2` only reads. The Rust appenders are mailbox (`apps/fgos/src/wiring/mailbox_remote.rs:672`, `mailbox_ingest.rs:508`, stream `project:mailbox`) and identity (`identity_log.rs:189`); both stream contracts mark every type `sealOnWrite: false` (`packages/mailbox/contracts/event-streams.v1.json:9,16`, `packages/identity/contracts/identity-event-streams.v1.json:9,16`). Only `decision` and `work.*` lifecycle types carry `sealOnWrite: true` (`packages/work-state/contracts/event-streams.v1.json:9`), consumed by Node (`src/state/work-event-store.mjs:12`, `src/state/consumer-event-gate.mjs:84`). The crate's `append` never seals (`packages/event-store/rust/src/append.rs`, no seal reference); sealing is caller policy. Rust seals inline only inside `sync` (`packages/event-store/rust/src/sync.rs:12`, `seal_guarded`), reached from the mailbox-sync child (`apps/fgos/src/wiring/mailbox_sync.rs:241-258`, `publish`). No Rust code calls `seal_if_due` or `seal_all` outside the crate and the addon (`rg seal_if_due apps` is empty). So the coalescer hand-off (`seal-coalescing.mjs:42-46`) has no native counterpart and none is needed until a native Work writer exists (S7).

**U2. `prepareStore` beyond the addon, and the Rust calls that give the same facts.** `src/event-store/native.mjs:57-71` adds: Linux-only refusal (`available`, `:11-13`), config validation through `eventStoreConfig` (`config.mjs:8-27`, minimums and a remote name check), a hot-lock-depth refusal (`outsideState`, `:24-26`), the required `trustedMain`, a default state root (`resolveStateRoot()`), the `detached` flag mapped to `new_if_root_exists` and error `state-root-gone` (`packages/git/node-addon/src/lib.rs:36-45`), the consumer registry file list (`consumers.mjs:43`), and a per-key memo. The Rust equivalents from `(cwd, trusted_main)`:
- `maintenance` facts: `fgos_event_store::diagnostics::maintenance(&layout)` (`packages/event-store/rust/src/diagnostics.rs:56-69`), returns `streams[].oldestUnsealedAgeSec`, `lastPush`, `lastAttempt{time,remote}`.
- `seal_if_due`: `seal::seal_if_due(driver, repo, SealRequest{.., opportunistic: true}, interval)` (`seal.rs:596`); `seal_all`: `seal::seal_all` (`seal.rs:554`).
- To get `driver, repo, layout, machine, registry`: `apps/fgos/src/wiring/event_store_clone.rs:35-70` (`open(dir)`), which already feeds identity and mailbox.
Gaps in that Rust opener versus `prepareStore`: it passes `(dir, dir)` as `(cwd, trusted_main)` (`:44`) instead of the main checkout; it calls `GitDriver::new` (creates the state root), so there is no detached `state-root-gone` mode; it does not validate `eventStore.remote` (identity does its own, `identity_log.rs:129`); the registry is `Registry::shipped()` built from the same `consumers.v1.json` (`packages/event-store/rust/build.rs:58`), so no drift.

**U8. Root policies, Node door vs the two Rust walks.** Node door: `src/runner/paths.mjs:145-182`. Only `caller-tree` (all verbs) and `strict-cwd` (`init`) are used by `main()` (`bin/fgos.mjs:4244`); `main-checkout[-only]` are for other callers. Host walk: `apps/fgos/src/cli_projector.rs:17-58` (called at `apps/fgos/src/main.rs:452`). Work-state walk: `packages/work-state/rust/src/lib.rs:55-66`, caller `:118`. Differences:
1. Policies: Node has four (`caller-tree`, `main-checkout`, `main-checkout-only`, `strict-cwd`); the host has one (the walk); work-state has one (a different walk). Distribution has a fifth, unrelated: trusted main checkout via Git (`workspace.rs:30`), and the mailbox a sixth: main checkout from `CLAUDE_PROJECT_DIR`/cwd (`apps/fgos/src/wiring/mailbox_root.rs`).
2. Git ceiling: Node never walks above the Git top level of cwd's checkout (`paths.mjs:117-123`, `:176-178`); host and work-state walk to the filesystem root.
3. Home exclusion: Node stops at the realpath of home, compared with realpath of every step (`:117-120`, `:179`); host compares the raw `cwd` chain to home and to canonical home (`cli_projector.rs:23-25,48-50`, so a symlinked cwd can slip past); work-state has no home exclusion at all (`lib.rs:55-62`), so from under the home directory without a project it can land on the machine's global `~/.fgos`.
4. Nothing found: Node returns `{root: gitTop ?? cwd, found: false}` and lets admission decide (`:181`); the host returns a refusal `not-in-project` that only project-reading verbs consume (`cli_projector.rs:53-57`; consumed with `root?` at `:106,113,156`); work-state silently falls back to cwd (`lib.rs:55-62`).
5. `--dir`: Node validates a non-empty value and `path.resolve`s it, an empty or missing value is exit 4 (`paths.mjs:148-162`); `--dir` naming home is accepted. Host scans every argv token for the first `--dir`/`--dir=`, returns it unresolved (relative stays relative), refuses home, and a trailing `--dir` with no value is ignored and the walk runs (`cli_projector.rs:26-41`). Work-state ignores `--dir` entirely (`lib.rs:117-118`, uses cwd).
6. Git facts: Node reads Git (`readRepoFacts`) and refuses a repository Git will not trust under every policy (`:49-52`); the host walk reads no Git, so no trust refusal.
7. Home source: Node `os.homedir()` (`:145`); host `fgos_config::machine::home_dir` (`HOME`/`USERPROFILE`, `main.rs:451`); work-state via `project_snapshot` lookup.
8. Linked worktrees: `.fgos` is wiped from fresh worktrees; Node stops at the worktree's top (not found), the host would continue to a parent directory that holds a `.fgos` (for example a worktree placed under a project directory).

**Also: the host's mailbox sync-due rule against Node's `syncDue`: not the same job.**
- Host (`apps/fgos/src/wiring/mailbox_hook.rs:185-224`, `mailbox_sync.rs:123-129,179-193`): started only from the mailbox hook (`:151`) when `mailbox.crossMachine.enabled` and `eventStore.sync.intervalSec > 0`, the clone has a `.git` directory (a gitfile is skipped) and a store or migrated-events fence; due when the stamp file `.fgos/mailbox/mail-taken` (`packages/mailbox/rust/store/src/record/paths.rs:27,82-84`) has another remote as content or is older than the interval. ## Impact on phases

- **Phase 01 (manifest artifact).** The byte target is the worktree payload, 231844 bytes, SHA-256 `5d9c41f8...ade7`; the installed release differs and must not be used (baselines). Nothing needs to change in `scripts/explain-command-route.mjs`: it reads routes only. `HELP_SELECTORS` is read by the generator alone, so the manifest projection row's `allowed` list needs no extra script.
- **Phase 02 (host help door).** No Rust help renderer ever existed, so nothing to reuse (prior art). Order in the host today: `native_kind && !wants_help_token` first (`main.rs:282`), then help forces `legacy-cli` (`main.rs:345`); `wants_help_token` skips the selector itself (`main.rs:69-71`), while Node special-cases `hook` help (`bin/fgos.mjs:4196-4201`) and treats help as an exact token even as a flag value (`:4227-4231`); the Rust helper must keep both. Help answered by the host skips payload re-verification, which is the whole 2.3 s of the dev door; add a latency case against the installed-release baseline (117 ms) and keep the dev number only as a note.
- **Phase 03 (declarations as data).** Eight `mutatesStore`, one `landsWork` and one `eventStoreChild` declarations are JS predicates over `positional`/`flags` (`command-registry.mjs:1433-1434,1627,1726-1727,2147,2211,2240,2269,2469`); all are "first positional is one of a set", except `:1627` (`flags.action !== undefined`) and `:1727` (`flags.opportunistic === true`). ## Lessons

- The one-door scan compiles Rust. Shell state does not persist between tool calls, so `CARGO_TARGET_DIR` set in an earlier call was gone and the scan built a stray `target/` inside the worktree (gitignored). Export it in the same command as any cargo-driven script.
- A timing through the dev door is dominated by payload verification in a debug build (2.4 s per legacy call); the installed release gives the user-visible number. A phase that times help should say which door it used.
- `zsh` does not word-split `$var`; a loop over `"a b"` strings silently passed one argument and produced a plausible exit 4. Use `${=var}` or arrays.
- The brief's literal help-token `rg` finds 1 of the ~16 files that run help; the others spawn through helpers. Search by the token alone and classify by hand.
