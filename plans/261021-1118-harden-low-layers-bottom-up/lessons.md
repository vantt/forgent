# HARDEN lessons ledger

Living ledger of what the HARDEN program learned. The owner decided on 2026-11-09 that these lessons become a reusable skill, `cs-hardening`, in the skillstation hub, in the style of the `cs-*` code standards (rules with ids and MUST / SHOULD / MAY, `common/`, `references.md`, `templates/`). This file is the source the skill will be distilled from. It is not the skill.

**Kind of record.** Stateful. It ages. Written 2026-11-09 from the sources named at the end. Layers T0 to T6 and T8 are closed (T8 added HL-15 to HL-20 and OL-19 to OL-24, 2026-11-09). Add a line when a new lesson is proven; do not rewrite old evidence.

**How to read it.** Every rule has a stable id. `HL-` is a rule that held in the work. `OL-` is an operational lesson from running many leads at once. `Q-` is an open question for the skill. Evidence is a decision number (plan.md "Owner decisions"), a report under `plans/reports/`, a commit, or a memory file. Where a claim has no record in the repo, the row says "owner-reported". Nothing here is invented.

## 1. What HARDEN is

HARDEN hardens an existing, running system layer by layer, bottom-up. It fixes real bugs, moves lower-layer decisions into one authority, and deletes what is dead. The system must end better, not bigger (RUL104, D-ADR0062). A layer closes before the next opens. Source: `plan.md` "Goal" and "The per-layer loop".

In fgOS the layers are T0 process facts, T1 holder-lock and identity, T2 Git and terminal-control, T3 agent protocol, observe and Event Store, T4 run supervisor, T5 execution core, T6 workflow, T8 skill and domain (T7 Work was held back, decision 78). T7 Work and T9 host and surface come after.

## 3. The per-layer loop

Source: `plan.md` "The per-layer loop" and proposal §4. Each step lists what it caught.

1. **Baseline** (read-only, measured, on current main, with the SHA and load).
   - Catches stale assumptions. T5 baseline found dead doors `executeThroughConfinement` and `finalizeConfinementResources` (`research-261104-1755-harden-t5-baseline`). T4 baseline fixed the methods the close later reused.
   - Trap: a baseline taken under heavy load is only an upper bound (T6: load 34 to 39).
2. **Council of four seats**: correctness, red-team, speed, simplicity. Each seat reads every line of the layer and returns a migration table, a delete list, a doctor table and a tests table. The red-team hunts what the others missed.
   - T0: 7 High, 0 Critical; for example `gateway stop` killed a foreign pid, and `LinuxPgroup` made its caller a subreaper (`council-261021-1507-harden-t0-arbitration`).
   - The speed seat predicted the canonical JSON cost of N-API; the red-team disputed it; the measurement sided with the speed seat (closing T0 §3).
3. **Arbitration** by the big lead, with a source for every accept or reject, plus one small owner ask in the decision-question template: what is happening, cause, options with cost, recommendation, scope of the answer. The ask batches target shapes, Criticals, proposed additions and the landing slot.
   - Prevents a second round trip. A reply such as "1a 2a 3a" settles a layer (decisions 5, 9, 59, 61, 71).
4. **Sub-plan** with a file-ownership table and parallel groups, red-teamed and validated. Each phase lists Create / Modify / Delete / Tests to retire and a net-size line.
   - T0 sub-plan red-team: 38 findings to 19, 16 accepted. T1 sub-plan: 24 findings, 22 accepted (board 2026-10-21 17:45 and 2026-10-22 10:12).
5. **Leads with a standard brief**, one lead per worktree, cheapest model that fits. The brief carries the delete list, the rule "find the owning test before writing a new one", a lane branch pushed often, and a lessons section at the end (`.fgos/runtime/tmp/t6-phase-lead-brief.md`, items 0 to 9b). The brief is untracked, so section 6 of this ledger carries its rules.
6. **Gate** before landing.
   - Focused tests, plus every test that reads or calls a touched file.
   - `test/architecture.test.mjs`, `test/scripts/doc-health.test.mjs`, `test/scripts/check-decision-citation-drift.test.mjs`.
   - One-door census: `node scripts/git-one-door-scan.mjs --root .`, count must not rise, regenerate with `--write-census`.
   - Rust: `cargo fmt --all --check`, clippy with `-D warnings`, and `cargo check` for `x86_64-pc-windows-msvc` and `aarch64-apple-darwin`.
   - Full `npm test` through the queue. Read the fail count and every `run-tests: ERROR` line.
   - What it caught: T0 phase verify, five regressions; T1 phase verify, six regressions (a hook paying a Node start per commit, 1.08 to 5.4 s; the identity cache removal tripled `withStateTx`) (closing T0 §5, closing T1 §4). Land gate misses of 2026-10-22: a Linux-only helper broke the Windows build; a nested `match` hid a bwrap probe from the census (memory `land-gate-checks`). `docs/` change turned citation drift red (T5 docs land).
7. **Review by the owning lane.** OPC reviews every Git, process, Event Store and install diff (decision 14). HARDEN reviews OPC's. Small diffs are read in person; big diffs go to an out-of-process reviewer. Spot-check every High in source before relaying.
   - T2 5A: OPC reproduced a `resolve_head` that could pair one branch's commit with another's name; fixed with a two-step read and `tests/head_switch.rs` (closing T2 §7).
   - `worktree remove --discard-ignored`: CHANGES at 23:14 (bind the choice into the evidence, refuse nested repositories), MERGE at 23:39 (`lead-261108-2323`).
   - `fgctl` self-update: CHANGES, because `current_exe()` could write into a sealed release dir. `t9-shim-root`: CHANGES, because a relative store root resolved inside a hostile repo. Lesson recorded: a mirrored path formula is fine for reads, not for what gets executed (memory `git-reviewer-role`).
8. **Self-land.** `git diff --stat origin/main...HEAD` for unexpected deletions, rebase, rerun the focused set, push main only with a clean status and no rebase in progress. The big lead lands on the machine it runs on once gates pass; the owner machine follows a guide at a time the owner names.
9. **Board line, report, owner guide in Vietnamese.** One line on the program board per landing. A closing report with before and after, net size, acceptance and open items. A guide the owner machine follows (for example `plans/reports/guide-261108-1230-owner-machine-harden-t6-workflow.md`).
10. **Close with re-measurement** on the activated release, against the budgets, at the same load class as the baseline. A layer closes only when the loop conditions hold, no High is left unreproduced, and net lines are at most zero or each increase names its payer. Only then does the next council open.
   - Catches the lead's own optimism. T0: the full run exited 1 and the lead blamed two flakes; a leak-check ERROR line was unread (closing T0 §5b). T2: the delta table showed every ceiling missed after the merge.

## 7. Open questions for the skill

These need the owner. Each is a question about what the skill should keep, not an answer.

- **Q-01 Generic or fgOS-specific.** The method (loop, HL-01 to HL-14) looks generic. fgOS names (`fgos worktree`, census, COOK, OPC, `run-tests`, V7n red) are not. Proposal: the skill keeps the loop and rules in generic words and moves fgOS commands to `references.md` as "proven ways", as `cs-packaging-distribution` does.
- **Q-02 What "layer" means outside fgOS.** The skill assumes the system already has layers with a lower and an upper. Does `cs-hardening` need a section on how to find the layers first?
- **Q-03 Language overlays.** HARDEN moved decisions into Rust (design principle 4). Is "Rust first" a rule, or a `languages/rust.md` overlay with a Node overlay beside it?
- **Q-04 Budgets.** Many budgets were missed and accepted after the fact (T0, T2, T4, T6). Should the skill require the owner to approve size budgets before the sub-plan, and treat a missed budget as a stop, not a note? (HL-14 says so; practice did not follow it in T2.)
- **Q-05 Council seats.** Four seats ran on different models. Is the seat list fixed, or a template with the red-team seat mandatory?
- **Q-06 Operational lessons.** OL-01 to OL-18 are mostly multi-agent hygiene, not hardening. Do they belong in `cs-hardening`, or in a sibling skill for running many agent leads? Several (OL-01, OL-03, OL-04) are agent-safety rules with their own hooks.
- **Q-07 Evidence gaps to close before distilling.** No repo record was found for: the first pgrep self-match incident (OL-04; OL-19 records a recurrence on the big lead's word only), the "149 commits" number (OL-10), the late opening of T9 (OL-09), the relayed-review limit (OL-12), and the exact prune race (OL-11). The owner can confirm each or drop it. Leads were asked to end reports with a `## Lessons` section from 2026-11-09; none of the reports read for this ledger had one yet, so future reports should be added here.
- **Q-08 Where the ledger lives.** It is a plan-folder artifact now. Should it stay beside the plan, or move into the skill's `references.md` once distilled?
