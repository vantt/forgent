## What was implemented, per requirement

### R5 — `invocationKey` consumed exactly once, session-scoped

Two enforcement points, both lock-held on a fresh from-disk read:

- **Issuance** (`authorizeOperation`): a second `operation-authorized` whose
  `invocationKey` already appears anywhere in this session's
  `events.jsonl` is refused. The scan is over the WHOLE session's
  authorizations, with no binding-triple filter — this is the contract's
  "checked against that session's own `events.jsonl`" read literally.
  Ordering matters and is deliberate: the pre-existing `authorizationId`
  idempotency early-return runs BEFORE the key check, so re-issuing an
  identical authorization is still a no-op rather than colliding with itself.
- **Consumption** (`assertAuthorizationSpendable`): an `assignment-created`
  carrying an `invocationKey` some OTHER Assignment already carries is
  refused, with the same `ownAssignmentId` exemption the sibling
  `authorizationId` check uses.

Plus read-time parity in `replay.mjs`, at exact structural parity with the
duplicate-`authorizationId` check three lines above it (`duplicate-ref`).

The crash/resume requirement is covered by the shape the contract actually
describes: the authorization lands, the process dies before any Assignment
exists, and on resume the driver's attempt to re-issue the same logical
invocation under a new `authorizationId` is refused as already issued — so
the resume spends the crashed attempt's own authorization and exactly one
Assignment materializes.

### R6 — context grant enforced at dispatch

`assertRefsOwnedBySession` is called in two places, and the second is the one
that makes this a gate rather than advice:

- In `authorizeDeclaredOperation`, so an out-of-session grant never reaches
  the log at all.
- In `dispatchDeclaredOperation`'s driver-authorization block, because the
  raw `store.authorizeOperation` door has no session-membership awareness and
  can put such a record on the log anyway. A test drives exactly that path.

The ceiling itself sits in that same block, between resolving the
authorization and `buildReadOnlyContract` — inside the ONLY producer of
`authorizationProvenance` in the codebase. Every resolved `contextRef` must
be in `grantedContextRefs`, with the single exception of the declared-edge
`fromAssignmentId`, which is structurally imposed by the topology and already
validated against the edge's declared `from` actor. There is no caller-facing
parameter that reaches the contract past this check.

### R7 — binding `maxInvocations`, counted fresh from disk

`activation.maxInvocations` is read only where the FlowDefinition is in hand
(`session-engine.mjs`) and enforced only where the lock is held
(`store.mjs`) — the same split the existing `maxAssignmentsForSession` /
`maxRoundsForSession` / `maxConcurrencyForSession` opts already use, extended
with the binding triple because a scalar cannot identify a binding.

Both layers count from the contract's named source — this session's on-disk
`operation-authorized` events for the exact `(nodeId, operationId,
targetActorId)` triple — inside the held `withEventsLock`. Issuance refuses
the (N+1)th authorization; dispatch refuses the (N+1)th materialization by
counting only authorizations already SPENT by an `assignment-created`,
excluding this call's own. The dispatch check is placed AFTER every
session-wide cap, so a stricter aggregate bound always refuses first — that
is what makes "binding caps narrow, never widen" true by placement rather
than by comment, and there is a test asserting the aggregate message fires
and the binding message provably does not.

### R8 — driver authority

`authorizedBy.id === manifest.provenanceRoot.writerId`, enforced lock-held in
`authorizeOperation`. See the interpretation section below.

## How P02.1's exact bug class was avoided

P02.1's HIGH-1 was: an invariant enforced in ONE of `createSessionAssignment`'s
two writing branches, so a crash into the self-heal shape reached around it.
The fix was a single shared helper, `assertAuthorizationSpendable`, called
from both branches inside the one `withEventsLock` critical section.

R5's dispatch-side check was therefore added **inside that same helper**, on
its existing single `readEvents`, carrying its existing `ownAssignmentId`
exemption — not as a parallel check somewhere else in the function. Concretely:

- There is still exactly one `assignment-created` append site
  (`completeAssignmentRegistration`), and still exactly two callers of it.
- Both callers still run `assertAuthorizationSpendable` first — the self-heal
  branch with `ownAssignmentId: claim.assignmentId`, the genuinely-new-taskKey
  branch with `undefined`.
- The new `invocationKey` check reads the same `events` array the
  `authorizationId` check does and applies the same exemption, so it cannot
  diverge from it and cannot be true on one branch and false on the other.
- The new R7 dispatch check deliberately runs only on the genuinely-new-taskKey
  path, alongside every other cap, so an idempotent resume is never counted as
  a fresh invocation — the same reasoning the existing caps document.

The regression test for this is driven on **both** writing paths explicitly
(`coordination-store.test.mjs`, "refuses provenance whose invocationKey
another Assignment already consumed, on BOTH writing paths"), built by
construction from P02.1's own crash-state helper rather than by concurrency,
exactly as P02.1's own regression tests were.

For R7, the analogous "second, differently-shaped check" trap would have been
a process-local counter. It is closed by test, not by claim: replacing the
disk count with a `Map` in the isolated copy left the in-process R7 test
PASSING and was caught by exactly one test — the cold-process one.

## R8 interpretation (the cell asked for this explicitly)

The accepted text gives two identities and no third: `authorizedBy` is
`{type: "driver", id: <driver-identity>}` where "the driver is not a
`spec.actors[]` worker", and the manifest's `provenanceRoot` is the "Caller
identity that opened the session (writer identity)". The phase file's R8 says
the authorization writer identity "must be tied to session driver/provenance
root", and warns that "`writerId` alone is not enough if the existing API
cannot distinguish an arbitrary event writer from the driver."

**Implemented: `authorizedBy.id === manifest.provenanceRoot.writerId`,**
checked lock-held in `store.mjs`'s `authorizeOperation` — the single door
every authorization passes through, including the raw one, so there is no
lower-level door that skips it.

I did not treat the contract as insufficient (so this is not a BLOCKED
report), but I am flagging the limit rather than papering over it:

- This DOES close what P02.1 recorded. "Any caller able to reach
  `authorizeDeclaredOperation` can name an arbitrary driver id" is no longer
  true — the id is pinned to a value the session recorded at open time.
- This does NOT make the identity unforgeable. `writerId` is a self-declared
  string at every entry point in this repo. A caller who knows which identity
  opened the session can still present it. Making that impossible needs an
  authentication/attestation primitive that exists nowhere in this codebase,
  and adding one would be inventing contract semantics rather than
  implementing the accepted text — so I did not.

**Recommendation:** Review/Red-Team should rule explicitly on whether
pinning-without-attestation satisfies R8, or whether a follow-on phase owes a
real writer-identity primitive. The R8 text anticipates this question; I do
not think the Doer should answer it unilaterally.

Fixture consequence, which the cell predicted: `coordination-store.test.mjs`'s
`issueAuthorization` wrote a synthetic `driver-1` against sessions opened as
`writer-1`. Changed to `writer-1` — one line plus a comment. That is exactly
the "existing test fixtures need updating to use a real, checkable driver
identity" case the Bug Taxonomy named as expected and fine.

## Left open

Nothing in R5-R8 was deferred, and none of `index.md`'s three inherited
forward gaps was touched (`cohort-planner.mjs`, `resolveDeclaredOperationActor`
node selection, `replay.mjs` read ordering — all at zero diff). Two things a
Red-Team should probe rather than take on trust, both recorded in P02.2.md's
Gaps:

1. **No real multi-process reproduction was run.** Every new check is
   lock-held on a fresh from-disk read inside the existing critical section,
   and R5's dispatch check was folded into the same shared helper P02.1's
   HIGH-1 fix built so it cannot be reached around via the self-heal branch —
   but that is an argument from construction plus deterministic
   both-paths tests, not a race reproduction. The cold-process R7 test is the
   only genuinely multi-process evidence here, and it is sequential (a cold
   reader after a settled writer), not concurrent. Given this track's own
   history (P01.2/P03.1/P03.2, and P02.1's HIGH-1), that is the gap most
   likely to hide something.
2. **R7's two layers count differently on purpose** — issuance counts all
   `operation-authorized` events for the binding, dispatch counts only the
   spent ones. The contract's own phrase ("the binding's *consumed*-invocation
   count is counted fresh from the on-disk `operation-authorized` events")
   carries the same tension. Worth an explicit ruling that this reading is
   intended.

Three further interpretations are recorded in P02.2.md's Gaps rather than
silently taken: what "resolve to a ref owned by this coordinationId" means for
a ref that resolves to nothing on disk; which base context stays legal under
R6 (and that R6 is a ceiling, not an injection); and that
`maxInvocations` is forwarded regardless of activation mode, staying inert on
a `required` binding.
