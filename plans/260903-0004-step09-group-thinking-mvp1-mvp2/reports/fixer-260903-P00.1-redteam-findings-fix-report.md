## Fixes applied

1. HIGH — Recheck/taskKey collision: added a clause to "Recheck Is Not
   Retry" (`coordination-session.md`) requiring a recheck's `taskKey` to
   incorporate the new artifact/evidence revision or the authorizing
   `invocationKey`/`authorizationId`, explicitly naming the
   `nodeId`+`operationId`+`actorId`-only derivation as the forbidden case.
2. MEDIUM — `invocationKey` scope: added a sentence to the
   "`invocationKey` Idempotency" subsection stating scope is the
   CoordinationSession (checked against that session's own
   `events.jsonl`); cross-session reuse is out of scope.
3. MEDIUM — atomicity for `operation-authorized` vs terminal transition:
   added point 5 to the Recovery Rule requiring the active-status check and
   `operation-authorized` append to share the same atomic/serialized write
   path as `assignment-created` (point 2), plus a replay-side fail-closed
   rule for any `operation-authorized` event found after a terminal event.
4. MEDIUM — `maxInvocations` resume-counting: added a clause to
   `flow-definition.md`'s Activation table `maxInvocations` row requiring
   the consumed-invocation count to be counted fresh from on-disk
   `operation-authorized` events (never in-memory), mirroring
   `aggregateBounds`'s existing freshness guarantee.
5. LOW — `grantedContextRefs` cross-session scope: added a clause to
   "Context-Grant Enforcement" (`coordination-session.md`) requiring every
   `grantedContextRefs` entry to resolve to a ref owned by the same
   `coordinationId`; cross-session grant authority stated as out of scope.
6. LOW — `mode` default: clarified in `flow-definition.md`'s Activation
   table `mode` row that `required` is the default whenever `mode` itself
   is absent, regardless of whether the parent `activation` object is
   present (e.g. `activation: {maxInvocations: 3}` with no `mode` key also
   defaults to `required`).
