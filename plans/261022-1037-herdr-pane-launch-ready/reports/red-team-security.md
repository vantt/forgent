# Red team (security adversary + fact checker + contract verifier): herdr pane launch ready

Plan: plans/261022-1037-herdr-pane-launch-ready/plan.md, phases 01-04. Evidence is from the working tree on 2026-10-22.

## Finding 1: The probe is typed into whatever holds the pane foreground, up to ten times, with no foreground check
- **Severity:** High
- **Location:** Phase 1, Requirements ("types probe ... through driver.pane_run ... retypes the probe if not seen within 1.5 s; stops at shell_ready_timeout_ms"); plan.md Chosen design 1 ("the send gate is not involved and not weakened").
- **Flaw:** The plan uses `pane_run` as a side door around the `foreground-not-agent` rule. It never checks that the pane's foreground is the bare shell before typing. The gate is not edited, but the property the gate protects ("nothing is typed unless the foreground is the expected process") is dropped for a new typed line. That line is also repeated: 15 s / 1.5 s is about 10 lines.
- **Failure scenario:** The user's rc starts something interactive that is not a shell prompt: `sudo -v`, an ssh-agent or gpg passphrase prompt, `nvm`/`conda` confirmations, a tmux/fish exec, or a pager. The core types `printf ... fgos-ready- 1729...` plus Enter every 1.5 s into it. A password prompt receives about 10 bogus attempts, which can lock the account or trip PAM faillock. A line-mode confirmation that treats non-`n` as yes receives affirmative answers. Nothing stops this and no receipt says it happened.
- **Evidence:** core.rs:453-475 (`send` checks `process_info` and `foreground_of` before typing); terminal-control.port.v1.json:59 ("nothing is typed unless a process other than the pane's shell ... holds the foreground"). Only `launch` (core.rs:389-424) is left to type with `driver.pane_run` and no foreground check. `identity::is_bare_shell` (identity.rs:42) already exists, and the launch path already `need`s `process.info` (core.rs:396).
- **Suggested fix:** Before each probe (and before each retype), read `process_info` and require `is_bare_shell`. If a non-shell process holds the foreground, return `NotStarted("pane foreground is not a shell")` and type nothing. Cap the retypes at 2 or 3, not 10. Add a MemDriver test with a non-shell foreground that asserts zero `pane.run` calls.

## Finding 2: "The probe can never answer yes" is proven only for the one omz prompt, and retyping defeats it
- **Severity:** High
- **Location:** plan.md Chosen design 1 ("starts with `p`, never `y`/`Y`/Enter, so it can never answer an update prompt yes"); Phase 1 Requirements and step 4 test 4 ("probe never begins with a key that answers an update prompt").
- **Flaw:** The claim rests on omz `read -r -k 1` (check_for_upgrade.sh:281-286: the first key is consumed, the rest of the line goes to the shell). The plan itself says the real target class is "any start prompt" (p10k wizard, fish, nvm in "Rejected options"). Those read a whole line, or several keys, or run several prompts in a row. The probe line ends with a newline, so a line-mode `read` takes `printf '%s%s\n' ...` as the answer and Enter submits it. The retype then answers the next prompt in the chain the same way. The planned test asserts only the first character of the string.
- **Failure scenario:** A wizard or hook reads a line and treats any answer other than `n` as yes (typical for `[Y/n]` helpers, because default-yes is the convention). Probe 1 answers prompt A "yes". Probe 2, 1.5 s later, answers prompt B "yes". Since the token is never printed, the loop continues until timeout. The side effects (update, install, config overwrite) happen on the user's machine, which is exactly what plan.md rejects `DISABLE_UPDATE_PROMPT` for.
- **Evidence:** check_for_upgrade.sh:281-286 (first-key read, `[yY$'\n']` means update; a different key prints a reminder). Phase 1 test 4 pins only the string prefix. plan.md Rejected options list non-omz prompts as the reason env alone is not enough, so the plan admits non-omz prompts exist.
- **Suggested fix:** Drop the "never answers yes" claim, or restate it as true for omz only. Send the first probe without a trailing Enter, so a line-mode prompt is not submitted. For example type `printf ...` and Enter only after the prompt is known gone, or send a no-op control key such as `C-c`. Limit retypes to the single first-key-swallow case: retype once, then fail closed with `NotStarted`.

## Finding 3: The readiness proof is a guessable, time-derived token read from screen scrollback
- **Severity:** Medium
- **Location:** Phase 1 Requirements ("nonce from `self.now()` (digits)"; "polls `read_screen(... recent-unwrapped)` for the joined text"); plan.md Risks row 1.
- **Flaw:** `self.now()` is epoch milliseconds (core.rs:57, 88-90), so the nonce is the wall clock and carries no entropy. The proof is "this text is somewhere in the last 40 lines". Anything that writes to the pane before the launcher line can forge it: a per-prompt hook in the cwd (direnv `.envrc`, a `.zshenv`/`chpwd` hook that prints a line), the user's prompt, or a retained earlier probe. The plan's stated strength ("a half-eaten or still-queued line cannot fake it") covers only accidents, not an adversary.
- **Failure scenario:** The pane starts in `request.cwd` (core.rs:277-283). A hostile or compromised repo hook prints `fgos-ready-<ms>` (it can guess the window or enumerate 15 s of values) while the shell is still at a start prompt. The core then types the launcher line into the prompt, the same failure the plan set out to fix. The spoof also turns the readiness proof into an attacker-controlled "go".
- **Evidence:** core.rs:57,88-90 (`now` is ms since epoch). The plan names no source of randomness. Phase 1 uses the same nonce for all retypes.
- **Suggested fix:** Use at least 64 bits from the OS RNG, hex-encoded, and state it in the code comment as the invariant. Choose a nonce per probe. Accept the token only on a line that is not the typed echo (the line that contains the `printf` text). Record in the spec that the proof is anti-accident, not anti-hostile-rc.

## Finding 4: Phase 1's "needs read.screen" can fire after the one-shot `launch-requested` marker, and the port contract is not updated
- **Severity:** High
- **Location:** Phase 1 Requirements ("needs capability `read.screen` ... in that path"); Files list (contract edited: internal-route only); plan.md Backwards compatibility ("A driver that lacks `read.screen` can no longer launch").
- **Flaw:** (a) The plan places no order on the capability check. In the existing `launch`, all `self.need(...)` calls come before `publish_marker` (core.rs:396-400 versus 402). If the new `need("read.screen")` is added in `wait_for_shell` after the marker, a driver without `read.screen` burns the slot (relaunch is refused forever) and returns `Unsupported` for a launch that never typed anything. (b) The plan adds a requirement and a new observable (`not-started` with the new reason, `unsupported` for `read.screen`) but the Files list does not touch `terminal-control.port.v1.json`'s `launch` block (lines 37-56). Its `effects` list does not mention a probe line typed after the marker, and `results` gives no cause for `unsupported`. The plan's non-goals list the port contract at `:58,103` for the gate, but the launch block at `:37-56` is a different part and it does change.
- **Failure scenario:** A future second driver, or herdr degraded without `read.screen`, passes the supervisor's capability preflight. `launch` publishes `launch-requested`, then refuses at `wait_for_shell`. The supervisor reports `terminal-mode-unsupported` (terminal.rs:570) with the slot permanently consumed. A reader of the port contract learns nothing about the probe, the new `read.screen` need or the reasons for `not-started`.
- **Evidence:** core.rs:392-402 (needs, then marker); terminal-control.port.v1.json:37-56; terminal.rs:569-570 (`NotStarted` and `Unsupported` mapping).
- **Suggested fix:** Put `self.need("read.screen")` next to `need("pane.run")` in the `None =>` arm at core.rs:395, before the marker. Add `contracts/terminal-control.port.v1.json` (launch `effects` plus the unsupported condition) to Phase 1's Files and Verify. The `read.screen` row in the driver-capabilities contract (driver-capabilities.v1.json:11) needs no change.

## Finding 5: The start-banner dismiss (`esc`) may run ahead of the blocked-dialog check and cancel the trust prompt
- **Severity:** Medium
- **Location:** Phase 3, Requirements ("on each poll, if the profile has banners, read the screen ... send dismiss_key") and "await_ready" placement; plan.md Chosen design 3.
- **Flaw:** The phase does not say where the banner step sits relative to the existing early exits in `await_ready`. Today `visible_blocker` / `state == "blocked"` return `blocked_readiness` at once, and the idle branch calls `classify_blocked` (trust markers) before anything else (mod.rs:309-321, 322-323). The plan says the banner check is done "on each poll" and resets the settle clocks, but not that blocked states win. Pressing `esc` on an agent trust or login dialog normally means "no". For agy, the trust marker is `do you trust the contents of this project`.
- **Failure scenario:** The banner step is inserted at the top of the poll loop. agy shows the startup banner together with, or immediately followed by, the trust dialog, and the bottom 20 lines contain both. The marker matches, and `esc` goes to the dialog, which is dismissed or declined. The agent exits or runs untrusted, and the supervisor then types the brief into a shell or an unexpected state. The plan's own guard ("never ready while a marker is on screen") does not cover this.
- **Evidence:** mod.rs:309-313 (`blocked` returns first), mod.rs:322-324 (`classify_blocked`); agy trust marker from scout/agy.rs; `bottom_lines(screen, 20)` is a wider window than the 12 (`mod.rs:221`) and 6 (`common.rs:204`) used by the existing classifiers.
- **Suggested fix:** State in Phase 3 that the banner step runs only after the blocked check passes, and skip it entirely if `classify_blocked(screen)` is non-empty. Match the marker on the same narrow window as the blocked check. Add a vector for banner plus trust dialog on one screen that asserts `sentKeys` is empty and readiness is `blocked`.

## Finding 6: `DISABLE_AUTO_UPDATE` reaches the sandboxed agent tree, and "inert" is asserted without any check
- **Severity:** Medium
- **Location:** plan.md Chosen design 2, Risks ("`DISABLE_AUTO_UPDATE` leaks to the agent's process tree: Inert for every tool in the tree except oh-my-zsh"), Open decision 2; Phase 2 Requirements.
- **Flaw:** The plan states the env is inert for everything but oh-my-zsh and offers no grep or doc evidence. The supervisor's launch path has no env scrub (the launch spec carries `env: Default::default()` at terminal.rs:240 and the bwrap prefix is a pass-through; no `--clearenv`/`--unsetenv` exists in packages/run-supervisor). So the variable is inherited by the agent CLI, its tools and user scripts. The generic name `DISABLE_AUTO_UPDATE` is read by unrelated tooling. It is an unregistered env var surface, and the install/setup/doctor gate says a new env var must be registered or justified; the plan waves the gate away with "no user config key".
- **Failure scenario:** A coding-agent task runs a repo script or package tool that honours `DISABLE_AUTO_UPDATE`, for example a dev-tool wrapper. The task behaves differently inside fgOS than outside (updates silently skipped). This is a hidden behaviour difference with no setup/doctor trace and no way for the caller to opt out other than overriding the env key per request.
- **Evidence:** terminal.rs:238-241 (`env` empty, no scrub); core.rs:722-724 (`env_pairs` is the only door, applies to every created pane); plan.md Risks row 7 (the claim has no source).
- **Suggested fix:** Either scrub the variable in the launch line (`env -u DISABLE_AUTO_UPDATE` in `launch_line`, which the plan's own owner question 2 calls out of scope but is one token in the code the plan already edits) or weaken the claim to "unverified" and record the grep. Do not mark the gate as not applicable without naming the variable in the spec's config-registry area.

## Finding 7: Phase 1's file list misses a `CoreConfig` literal; the phase gates would not catch it
- **Severity:** Medium
- **Location:** Phase 1, Files (write paths) and Verify; Phase 4 Files.
- **Flaw:** Adding a field to `CoreConfig` breaks every struct literal. Phase 1 names `tests/common/mod.rs`, `herdr_driver_fake.rs:401` ("only if ... needs the new field") and `terminal_slot.rs:52-56`, but not `packages/run-supervisor/rust/tests/support/herdr.rs:84`, which builds `CoreConfig { ... }` directly. Phase 1 Verify never compiles run-supervisor tests (only `cargo build -p fgos-run-supervisor`, which excludes test targets). The break surfaces only in Phase 4, whose file list names `support/herdr.rs` "only for a helper".
- **Failure scenario:** Phase 1 commits green on its own gates, and Phase 4 (or a worktree split by file ownership, which the plan allows) then fails to compile. The "each phase is one commit; revert in reverse order" rollback stops being true for phases 1-3. Reverting phase 1 alone is impossible while phase 4's fixture changes remain.
- **Evidence:** packages/run-supervisor/rust/tests/support/herdr.rs:84; packages/terminal-control/rust/tests/common/mod.rs:232; terminal_slot.rs:52-56; herdr_driver_fake.rs:401 (grep of `launch_identify_timeout_ms`, 5 literal sites plus route.rs:143).
- **Suggested fix:** Add `packages/run-supervisor/rust/tests/support/herdr.rs` to Phase 1's write paths, and use `cargo test --workspace --no-run` in Phase 1's Verify. Better: give `CoreConfig` a `..Default` or builder so literals stop breaking.

## Finding 8: The one-pane `pane.run` count change silently weakens the double-launch proof and the supervisor wiring proof does not exercise the gate
- **Severity:** Medium
- **Location:** Phase 1 step 4 ("update the two assertions that count `pane.run == 1` ... the relaunch case adds no `pane.run` at all"); Phase 4 Requirements (fake start-prompt mode, `sh -c` of the typed line).
- **Flaw:** (a) The existing test says "second launch must not reach the driver" and asserts `pane.run` length 1 after two launches (core_failures.rs:60-63). With probes the first launch makes at least 2 `pane.run` calls, so the plan rewrites the assertion to "last `pane.run` is the launch line". That no longer proves a second launch does not type: the relaunch is refused only if the count is compared before and after, and the plan's wording ("adds no `pane.run`") is vague about the baseline. The plan has no test that a `NotStarted` timeout leaves the marker so that a retry never reaches the driver. (b) The Phase 4 fake shell runs the first typed line through `sh -c` with the first character removed. That is a model of omz `read -k 1` only; it never exercises a non-bare-shell foreground or a line-mode prompt (Findings 1-2), so the wiring proof gives confidence about a case that is already easy and none about the dangerous ones.
- **Failure scenario:** A later refactor makes `launch` retry the probe after the marker, or lets a second `launch` call probe again. The weakened assertion (`last pane.run is the launch line`) still passes while a probe is being typed into a pane that already has an agent.
- **Evidence:** core_failures.rs:60-63, 88-93; fake-herdr-pane.py:144-158 (plain `script -c <line>`, no interactive shell); Phase 4 Requirements.
- **Suggested fix:** Assert exact `pane.run` counts before and after the second launch (equal), and keep a "launch refused after a timeout does not type" test. Add a MemDriver scenario with a line-mode prompt and one with a non-shell foreground to the owning proof in phase 1.
