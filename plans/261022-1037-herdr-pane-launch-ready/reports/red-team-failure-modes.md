# Red team: failure modes (plan 261022-1037-herdr-pane-launch-ready)

## Finding 1: Phase 1 breaks every fake-herdr supervisor test until phase 4, and phase 1's verify cannot see it
- **Severity:** Critical
- **Location:** phase-01 "Verify" and "Files"; phase-04 "Requirements" bullet 1 (fake gets a start-prompt mode only)
- **Flaw:** Phase 1 makes `read.screen` plus a visible probe token a hard precondition of every plain launch. The two fakes that the supervisor/Node suites drive never show typed-line output on `pane read`. Phase 1 changes neither fake and only runs `-p fgos-terminal-control` and `cargo build -p fgos-run-supervisor` (build, not test). Phase 4 changes the Python fake only in a new start-prompt mode, so the default mode stays unable to show the token.
- **Failure scenario:** After phase 1 lands, `supervise_terminal_fake_herdr.rs` (6 tests) and the Node suites `terminal-crash-matrix`, `terminal-cutover`, `terminal-fallback`, `terminal-groups` (they use FAKE_HERDR / fake-herdr-pane.mjs) launch, never see `fgos-ready-<nonce>`, burn 15 s, and return `terminal-launch-not-started`. Phase 1 is "green" by its own verify, the serial cook run proceeds on a red tree, and the break only appears at phase 4 (or at the full gate). The probe also clobbers fake state: the Python fake overwrites `script.pid` / `typescript.log` per `pane run`, and the Node fake overwrites `pane.pid` and `pane.runCommand`, so the launch line's bookkeeping now depends on probe ordering. The plan never names the Node fake at all. Worse, the Python fake serves per-command screens `screen.run<N>.txt` keyed by `runs_started()` (fake-herdr-pane.py:66-69); the probe is now run 1 and the launch line run 2, so every existing test that scripted `screen.run1.txt` for the launcher silently gets the wrong screen.
- **Evidence:** fake-herdr-pane.py:143-153 (`pane run` -> `script -qefc`, writes script.pid), :170-172 (`pane read` returns only the scripted `screen` file); test/helpers/fake-herdr-pane.mjs:143-157 (`pane run` overwrites pane.pid/runCommand), :216-223 (`pane read` prints `''` or a scripted screen); phase-01 "Verify" lines; phase-04 "Files"; test/run-supervisor/terminal-crash-matrix.test.mjs, terminal-cutover.test.mjs, terminal-fallback.test.mjs (grep for fake-herdr/FAKE_HERDR).
- **Suggested fix:** Move the fake-shell capability (echo the output of a `pane run` line into the served screen by default) into phase 1, add `cargo test -p fgos-run-supervisor --test supervise_terminal_fake_herdr` and the Node terminal-* suites to phase 1's verify, and list `test/helpers/fake-herdr-pane.mjs` among write paths. Phase 4 then keeps only the start-prompt flag. The slicing is otherwise not shippable one commit at a time.

## Finding 2: Up to 20 s of uncancellable, heartbeat-less blind time inside `launch`
- **Severity:** High
- **Location:** plan.md Design "Chosen design" 1; phase-01 Requirements (`shell_ready_timeout_ms = 15_000`)
- **Flaw:** `launch` is a synchronous call made before the supervisor main loop exists. That loop is what polls stop requests, writes `supervisor-heartbeat.json` and runs the carrier check. The new wait adds up to 15 s before the existing 5 s `identify_root`. The plan never sums it against `HELLO_LIMIT` (15 s, started only after `launch` returns), the heartbeat period (5 s), or the cancel path. It cites none of run-supervisor spec §5.3's timing rules.
- **Failure scenario:** The controller cancels or hits a stop while the shell is slow. Nothing reads `stop-requested.json` until the loop starts, so the stop is honoured about 20 s late, then the gate starts anyway and gets GO. During those 20 s no heartbeat is written, so an adopt scan can judge a live supervisor dead and race it. A pane that vanishes (carrier gone) mid-probe is only noticed as `pane_not_found` errors in a 100 ms poll loop (spawning a `herdr pane read` process each), where the plan says nothing about turning a `Gone` pane into an early exit rather than a 15 s spin.
- **Evidence:** terminal.rs:561-577 (`core.launch` then `accept_gate(.., HELLO_LIMIT)`, no stop poll before), terminal.rs:387-389 (heartbeat only in the loop), supervise.rs:167-170 (TICK 50 ms, HEARTBEAT_EVERY 5 s, HELLO_LIMIT 15 s), core.rs:426-447 (identify_root 5 s), run-supervisor spec.md §5.3 "carrier" paragraph.
- **Suggested fix:** Make the budget explicit (handshake + identify <= one stated bound, e.g. below HELLO_LIMIT), have the handshake abort on `pane_liveness == Gone` and on a stop signal passed in by the supervisor (a callback or deadline), and write a heartbeat before `launch`. Or drop the timeout to the order of a few seconds and say why.

## Finding 3: The probe turns a slow-but-working shell into a burned, unrecoverable slot (regression)
- **Severity:** High
- **Location:** phase-01 Requirements (timeout -> `NotStarted`); plan.md Risks row "Handshake timeout burns the slot"
- **Flaw:** Today the launch line is typed at once and the tty queues it until the shell finishes its rc, so a slow rc (nvm, conda, corporate profile; the plan itself says "slow rc (seconds)") still works. After the change, an rc slower than 15 s (or a herdr whose first `pane read` lags) ends `NotStarted`, and because `launch-requested` is already durable the slot can never be relaunched. The plan's mitigation says "nothing was typed that could execute", which is false: the probes are typed and execute once the shell wakes.
- **Failure scenario:** rc takes 20 s on a loaded CI box. By t=15 s, ~10 `printf` probes sit queued in the tty. The attempt ends `terminal-launch-not-started`; the receipt steps run; `release-slot` finds a shell that later runs ten probes (a retained pane full of noise). The old path would have launched. No fallback relaunch exists because the marker is "never retried".
- **Evidence:** core.rs:393-424 (marker published before the driver call; `publish_marker` false -> "already requested"), terminal-control spec.md:152-154 (kept/abandoned handling), plan.md Risks rows "Slow rc" and "Handshake timeout burns the slot".
- **Suggested fix:** Publish `launch-requested` only after the handshake succeeds (the marker's meaning is "the launch line may be typed"), so a handshake timeout leaves the slot relaunchable and leaves the existing "bare shell past grace -> doctor finding" path intact. If the marker order must stay, state the regression as an owner decision (Open decisions currently omits it) and size the timeout against real rc times.

## Finding 4: Probe retry every 1.5 s double-types into slow shells and into line-reading prompts
- **Severity:** High
- **Location:** plan.md Chosen design 1 and Risks row "Slow rc ... Extra printf lines are harmless"; phase-01 Requirements (retype within 1.5 s)
- **Flaw:** The retry interval (1.5 s) is shorter than many normal rc durations, so a merely slow shell receives N queued probes with the same nonce, and the first one satisfying the poll does not cancel the rest. Safety against "answers yes" is argued only for the first byte. Any prompt that reads a whole line (not `read -k 1`) consumes an entire probe line plus its Enter, and for `[Y/n]`-style prompts Enter is "yes", which the plan's own omz facts say starts an update. Each retry is another chance to hit that.
- **Failure scenario:** A prompt that appears after probe #1 was consumed by an earlier `read -k 1` now meets probe #2's trailing `\n`-bearing line. With line-read semantics the default (Enter) answer fires. Or: p10k/zsh-newuser menu loops on invalid input while fgOS keeps typing a new probe every 1.5 s for 15 s.
- **Evidence:** plan.md omz facts row (`read -r -k 1`, "Only y/Y/Enter start an update"), plan.md Design bullet 1 ("starts with p, never y/Y/Enter"), phase-01 Requirements ("retypes the probe if not seen within 1.5 s"), core.rs:506-509 herdr `pane run` types a line plus Enter.
- **Suggested fix:** Do not retype blindly. Type the probe once, then poll with a longer window. Retry only after the screen shows the shell consumed input (a changed screen) and cap at 2 probes. Pin in a test that no retry is typed while the first is still queued and unsettled. State the whole-line prompt case as a known limit in the spec.

## Finding 5: Crash or adopt mid-handshake is unspecified
- **Severity:** High
- **Location:** plan.md Rollback/Risks; terminal-control spec failure table; phase-01 has no crash test
- **Flaw:** The handshake adds a long window between the `launch-requested` marker and the `launched` marker, and none of the plan's tests covers a supervisor death there. The spec's table covers death "before launch" and "after launch returned", and a `launch-requested` slot is always kept. A probe-only pane (no launcher typed) with a `launch-requested` marker and no `launched` marker is a new, common state.
- **Failure scenario:** The supervisor dies at t=8 s of the handshake. Adopt finds `launch-requested`, no gate ever connected, pane holds a bare shell plus probe lines. Per spec, `launch-requested` is kept and never reported as the `AllocatedNotLaunchedBareShell` finding, so the pane leaks indefinitely (kept by "unknown or already launch-requested is kept"), and adopt concludes `abandoned`. Nothing in phase 1 or 4 adds or runs a crash-matrix case for this.
- **Evidence:** terminal-control spec.md:152-154 and :59; core.rs:407-412; test/run-supervisor/terminal-crash-matrix.test.mjs (existing crash coverage that will not exercise the new window).
- **Suggested fix:** Either move the marker (Finding 3) so a pre-launch death leaves a plain allocated slot, or add one crash-matrix proof (die during handshake) and state the expected adopt outcome in the spec.

## Finding 6: Phase 3 banner step does not cover the paths the real loop takes, and the key can hit a live agent
- **Severity:** High
- **Location:** phase-03 Requirements (`await_ready` "on each poll"), Steps 2 and vectors
- **Flaw:** In the current loop, `inspect()` failure (NoDetector), `visible_blocker` / `state == "blocked"`, and non-idle states return or skip before the idle branch. A banner shown while the detector reports `working` (animated TUI), `blocked`, or no detector is never dismissed, or ends the wait as `Blocked` (the brief never typed, but the run is lost). The plan's text says "on each poll" but gives no insertion point, and its vectors cover only the idle-state paths. Pressing `esc` once per banner at most twice also assumes the screen refreshes between presses: a stale `pane read` right after the first press re-matches the marker and sends the second `esc`, which in agy/most TUIs interrupts or clears the first real prompt. The unruled 15 s clock (`UNRULED_READY_MS`) is reset on each banner, so a flapping banner can extend the wait to the full 30 s `READY_MS` and still fall to `NotReady`.
- **Failure scenario:** agy prints the banner while the detector says `working`; the loop never reaches the banner check, waits until `NotReady`/`Unverified` and types the brief at the banner, which is exactly the original bug. A stale frame after the first `esc` triggers a second `esc` on the live prompt.
- **Evidence:** terminal/mod.rs:300-350 (early `return` on NoDetector/Blocked before idle branch; `Unverified` at 15 s), common.rs:11,16 (PROMPT_SETTLE_MS 1500, UNRULED_READY_MS 15000), terminal.rs:43 (READY_MS 30 s), phase-03 Requirements bullet 3.
- **Suggested fix:** Specify the banner check as the first action of each loop iteration, before `inspect`, independent of detector state. Require one screen change (or a settle) between presses. Add a vector for banner-under-`working` and for a stale frame after a press.

## Finding 7: One-owning-proof and verify gaps: contradictory counts, the wiring proof tests a model the fake invented
- **Severity:** Medium
- **Location:** plan.md Test matrix; phase-04 Requirements and Risks; phase-01 Step 4
- **Flaw:** (a) Phase 4's start-prompt mode feeds the fake a first-character-swallow that the fake itself implements; it proves the fake, not the probe, since `pane read` serves a file in default mode. It is a second copy of phase 1's swallowed-key case (design principle 8). (b) Phase 1 says the relaunch case "adds no `pane.run` at all", yet `launch` types the probe after the marker only; the relaunch refusal path returns before it, so this is fine, but the "launch line is the LAST `pane.run`" assertion is a weak substitute for the old count. It does not prove the launch line is typed after a *seen* token versus after a timer. (c) Phase 1 timing tests with a 15 s default and real `Instant`/`sleep` in `identify_root`/the new loop will take 15 s per never-ready test unless the timeout is injected; the plan only adds a config field, so a loaded CI run will either be slow or flaky at the 1.5 s retry boundary.
- **Failure scenario:** The never-ready test either sleeps the full timeout (suite slow) or sets a tiny timeout so the retry (1.5 s) never fires, leaving the retype-after-swallow case unproven or racy.
- **Evidence:** phase-01 Steps 3-4; core.rs:21 (`IDENTIFY_POLL` real sleep), core.rs:426-447 (real `Instant`, not the injected clock `with_clock`); phase-04 Requirements bullet 1-2; AGENTS.md design principle 8.
- **Suggested fix:** Make retry interval and poll step part of the config (or use the injected clock) so tests run in milliseconds; drop the phase 4 swallow case or reduce it to "supervisor reaches delivered with a fake that echoes output", and say which phase-1 test owns the swallow.

## Finding 8: Quiet env applies to more than attempt panes and its "no persisted change / no registration" claim is unproven
- **Severity:** Medium
- **Location:** phase-02 Requirements; plan.md Backwards compatibility
- **Flaw:** `env_pairs` is the single door for every pane the core creates (tab create and split), including non-run panes created by other callers of `allocate`. The plan states the env "reaches the agent's process tree (inert)" but ships no check that no other tool in that tree reads `DISABLE_AUTO_UPDATE`, and no doctor/setup note even though it injects a new environment default into user-visible panes (the install/setup/doctor gate asks exactly "does this add an env var"). It reasons it away as "no user config surface", but the var is read by the user's own shell and changes the user's pane behaviour.
- **Failure scenario:** A user who relies on omz auto-update prompts or runs another updater keyed on `DISABLE_AUTO_UPDATE` silently stops getting them in fgOS panes, with no doctor line or CHANGELOG-scope note beyond the one run-failure line.
- **Evidence:** core.rs:278,283,722-724; plan.md "Backwards compatibility" and "Open decisions" 2; AGENTS.md "Install/setup/doctor gate".
- **Suggested fix:** Record the decision in the spec, mention the env in the CHANGELOG line, and add a doctor-visible note. Or restrict the default to attempt panes by passing it from the supervisor's `allocate` caller instead of the core.
