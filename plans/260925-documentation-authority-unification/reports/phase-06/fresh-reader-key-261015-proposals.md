## 1. Scoring rule

Same shape as `reports/phase-05/pilot-b-fresh-reader-key.md`, the root-authorities key and the whole-system key (`reports/phase-06/fresh-reader-key-261015-whole-system.md`): a scenario answer (one of six questions) is correct when it names an acceptable owner below with a `path#anchor` that exists and whose text supports the claim. Per reader, per scenario: at least 5 of 6 correct; 0 non-existent anchors (any one fails the whole run); at most 8 files opened before the first correct owner; 0 legacy-authority answers.

Adaptation for this batch (nothing here is promoted). All 20 Step 7 files are candidate or history carriers; each header says `Design status: Candidate`, `Canonical: No`, `Canonical for: Nothing; non-canonical candidate conservation carrier`, `Supersedes: None; legacy source remains intact`, and names the legacy source under `docs/architect/**` in `Related` and `Source relationship`. The switchboard (`docs/platform/documentation/switchboard.md#2-area-authority-routes`) has no row for proposals, redesigns, or `docs/architect/proposals/**`. A correct answer therefore does all of:

1. cites the in-scope `path#anchor` as evidence;
2. says the cited file is a candidate carrier (or, for the portal, navigation), that its text is source text carried verbatim for review, and that the legacy source file it names is the same text retained intact, not a more binding design;
3. separates three things, wherever the scenario touches a claim: a proposal (non-canonical option, `docs/platform/governance.md#3-document-types`), an accepted design (an Architecture, Contract or Decision owned elsewhere), and implemented code or behavior (a Spec; not readable in scope);
4. where a binding owner is needed, names the owner the switchboard row gives for that topic and does not invent a proposals row.

Legacy-authority answer (fails the answer): citing a legacy `path#anchor` as the evidence (readers cannot open it); treating a candidate or history carrier as binding; treating a status word inside carried source text as binding or current (`Design status: Accepted` in `documentation-system-design.md`, `accepted-prerequisite` or `implementation-ready` in `step-10-coding-domain-adoption.md`, "Option C (accepted, revised)" in `group-thinking-plan-loop.md`, `Status: partially implemented` in `doing-coordination-redesign.md`); saying a proposal is accepted, or code exists, because the file says so.

Missing the proposal versus accepted design versus implemented code distinction, the candidate versus binding-owner distinction, or the history-is-not-current distinction, where the scenario rests on it, is partial, not correct.

Anchors verified at the worktree (HEAD 4ee263d09, docs unchanged since) with `node scripts/list-doc-anchors.mjs --check <path#anchor>`; every anchor cited below returned exit 0 (42 anchors in one batch run). Equivalent supported anchors are acceptable. Several support claims live in blocks without a heading; those are cited as `unheaded-block-N` (printed by the tool) and are fragile: a block anchor that does not exist is a fabrication, a different heading anchor with the same support is fine.
