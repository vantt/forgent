- Q2: Client feature work (a write operation in a separate client project that calls the gateway from outside), with a possible gateway change depending on the answer below. cites: docs/platform/herdr-web-dashboard/spec.md#purpose
- Q3: The gateway API contract (CTR010, `fgos-gateway.v1`): `PATCH /work/{id}` (`editWork`, wraps `fgos edit`) and the `EditableWorkFields` body, plus the one-door-write rule that every write goes through an fgOS verb run by the gateway. cites: docs/platform/herdr-web-dashboard/contracts/fgos-gateway-api-v1.yaml#unheaded-block-11, docs/platform/herdr-web-dashboard/contracts/fgos-gateway-api-v1.yaml#unheaded-block-33, docs/platform/herdr-web-dashboard/spec.md#business-rules

The contract file has a `patch` operation `editWork` on `/work/{id}`. I cannot verify from in-scope files which is current, nor whether the daemon implements the route (the contract says it was "written before the daemon is implemented"). Contracts outrank guides and current specs outrank stale wording only about present behavior, and the governance doc says a conflict is a documentation defect to surface, not to resolve silently. Also the spec's "18 paths" count looks stale against the contract, which lists 19 paths by my count. cites: docs/platform/herdr-web-dashboard/spec.md#open-gaps, docs/platform/herdr-web-dashboard/contracts/fgos-gateway-api-v1.yaml#unheaded-block-11, docs/platform/governance.md#4-authority-matrix

Reasonable proof is that the client's call hits the real `PATCH` route, the engine's own validation and "no field changed" refusal reach the user verbatim, and the route's presence in the gateway is checked against its registered routes (the check itself I could not verify in scope). cites: docs/platform/herdr-web-dashboard/README.md#added-in-candidate-verification-and-change-boundary, docs/platform/herdr-web-dashboard/contracts/fgos-gateway-api-v1.yaml#unheaded-block-11

## Scenario B: dashboard off by default, loopback only

- Q1: The spec's Entry Points (availability trigger) and Business Rules R5 and R8, then the contract's `servers` block. cites: docs/platform/herdr-web-dashboard/spec.md#entry-points-triggers, docs/platform/herdr-web-dashboard/spec.md#business-rules
- Q2: A change to a recorded product-owner decision (default configuration of an exposed surface), not a bug fix. The spec states the product owner chose on-by-default with a non-loopback bind after being shown the exposure consequence, so reversing it is a user decision to bring back to the owner, not to apply silently. cites: docs/platform/herdr-web-dashboard/spec.md#business-rules
- Q3: The dashboard's config toggle (defaults ON), bind address (0.0.0.0 by default, configurable, warns when not loopback) and port 8788; the token auth rules R3/R4. The contract's `servers` entry says `http://localhost:{port}`, port 4170, "not always-on by default", which disagrees with the spec's on-by-default and 0.0.0.0 statement. These may describe different things (gateway API shape versus dashboard process), and I cannot verify that from in-scope files, so I do not choose one. cites: docs/platform/herdr-web-dashboard/spec.md#entry-points-triggers, docs/platform/herdr-web-dashboard/contracts/fgos-gateway-api-v1.yaml#unheaded-block-5
- Q4: High if left as the spec describes: R8 says first run exposes a trunk-changing surface on the network, and the token is the only thing holding it closed. Making it off and loopback-only lowers that exposure. Whether the config actually supports this today cannot be verified from these files. cites: docs/platform/herdr-web-dashboard/spec.md#business-rules, docs/platform/herdr-web-dashboard/spec.md#actors-access
- Q5: Not defined in scope. A reasonable proof is a fresh first run showing nothing listening, then enabling it and confirming it binds loopback only, with the doctor check and the owner's decision recorded. The platform's own "install/setup/doctor" requirements live outside what I may read. cites: docs/platform/herdr-web-dashboard/spec.md#business-rules
- Q6: A decision record and a spec update in the owning spec (R5, R8, entry points) so the changed default and its rationale are not lost. cites: docs/platform/herdr-web-dashboard/spec.md#business-rules, docs/platform/governance.md#4-authority-matrix
