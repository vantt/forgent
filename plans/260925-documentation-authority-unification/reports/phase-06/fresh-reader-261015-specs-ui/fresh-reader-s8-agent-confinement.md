## Scenario A: add a container-based isolation backend

- Scenario: A
- Q1 What to read first: Enter at `docs/platform/README.md`, then the switchboard row for Agent confinement. That row sends a maintainer to the legacy owner, `docs/specs/confinement-authority.md`, which is binding. Orientation reading in the candidate area is the area README, then `spec.md` §9 (default implementation and support matrix), then the contract §6.2 (backend registry shape) and §6.5 (backend port). cites: `docs/platform/documentation/switchboard.md#2-area-authority-routes`, `docs/platform/documentation/switchboard.md#4-resolution-algorithm-for-readers-and-writers`, `docs/platform/agent-confinement/README.md#added-in-candidate-read-this-area`
- Q2 What kind of work is this: A feature extension of an existing runtime contract (a new backend driver type), not a doc-only change. The candidate spec lists container backends as not needed in the default and as future extension. The rollout table lists "S6 - Extend: macOS/container/remote/network/secret backend khi có nhu cầu" as future, beyond v1. cites: `docs/platform/agent-confinement/spec.md#9-default-implementation-đầu-tiên`, `docs/platform/agent-confinement/history/rollout-and-settled-facts.md#10-lộ-trình-rollout-và-trạng-thái-hoàn-thành`
- Q3 What contract it touches: `ConfinementBackendDriverV1` / backend port, and the machine registry `confinementBackends`. The candidate contract already sketches a `type: 'container'` entry (runtime docker or podman, image, pullPolicy) and says a new driver type registers with its own schema without changing `ConfinementPolicyV1`. Constraints that bind the design (as stated in the candidate text): drivers are an allowlist in code; exactly one backend instance per dispatch; the driver must not branch on executor id, provider model, Codex or Claude; unsupported surfaces return `unsupported` with a reason; the machine registry is not part of project-over-global merge. A detached container is the "remote/container detached" profile, which the candidate spec says needs allocation journal, lease and recovery before it may be accepted as `required`. cites: `docs/platform/agent-confinement/contracts/confinement-authority-v1.md#62-nơi-đặt-policy`, `docs/platform/agent-confinement/contracts/confinement-authority-v1.md#65-backend-port`, `docs/platform/agent-confinement/contracts/confinement-authority-v1.md#621-trust-boundary-của-backend-registry`, `docs/platform/agent-confinement/spec.md#86-crash-và-cleanup`
- Q4 How much risk: High. It adds a security-enforcement backend, needs recovery semantics for resources living outside the local process, and may change component ownership, so the area README says to read `docs/platform/component-boundary.md` first (I did not open it, so whether this is a boundary change is unverified). The spec says the driver version change forces golden tests, probes and doctor to be re-run. cites: `docs/platform/agent-confinement/README.md#added-in-candidate-verification-and-change-boundary`, `docs/platform/agent-confinement/contracts/confinement-authority-v1.md#610-version-và-evolution`
- Q5 What proof means done: The candidate spec's definition of done: contract tests (closed schema rejects unknown driver type or bad driver config, backend that does not cover a required control must refuse), one-door tests (zero spawn on throw in resolve/assess/compile/prepare, crash replay idempotent, collect failure keeps resources), repo-committed behavior probes that are independent of declarative claims, and a doctor check per driver and per registry instance (`configured`, `disabled`, `unavailable`, `ready`). Whether the legacy test suite names exactly these gates is not verifiable from files in scope. cites: `docs/platform/agent-confinement/spec.md#11-proof-và-definition-of-done`, `docs/platform/agent-confinement/spec.md#111-contract-tests`, `docs/platform/agent-confinement/spec.md#113-behavior-probes`, `docs/platform/agent-confinement/spec.md#115-doctorsetup`
- Q6 What learning gets left behind: A decision row in the confinement decisions record (the existing table shows the pattern: one owner per decision, no auto-fallback between backends) and a settled-fact note in the history, plus the new support-matrix row. Edits must land once, in the declared current owner (the legacy spec), never dual-authored in the candidate files; edits under legacy roots need a reviewed exception. cites: `docs/platform/agent-confinement/decisions/confinement-authority-decisions.md#12-quyết-định-của-proposal`, `docs/platform/documentation/switchboard.md#1-operating-invariants`, `docs/platform/documentation/switchboard.md#4-resolution-algorithm-for-readers-and-writers`

## Scenario B: strict by default, and live executors onto the backend-reference shape

- Scenario: B
- Q1 What to read first: The switchboard row (legacy owner binds), then the area spec's status block and §9 items 3 and 6, the contract §6.2 (strict flag and invariants), and the open deferred items. Read the history S4 row for what was already tried. cites: `docs/platform/documentation/switchboard.md#2-area-authority-routes`, `docs/platform/agent-confinement/spec.md#9-default-implementation-đầu-tiên`, `docs/platform/agent-confinement/spec.md#tồn-đọng-mở-open-deferred-items`, `docs/platform/agent-confinement/history/rollout-and-settled-facts.md#10-lộ-trình-rollout-và-trạng-thái-hoàn-thành`
- Q2 What kind of work is this: A rollout step that the text calls S4 "Enforce" (strict flip) plus a live config migration, both described as deferred, not new design. It reverses a current default (`runner.confinement.strict: false`), which is an explicit prior decision, so a maintainer should treat it as a user/owner decision, not a drive-by edit. The text says strict stays `false` until the open deferred items are finished, and that an operator may set `strict: true` once `fgos doctor` is satisfied. cites: `docs/platform/agent-confinement/spec.md#tồn-đọng-mở-open-deferred-items`, `docs/platform/agent-confinement/contracts/confinement-authority-v1.md#62-nơi-đặt-policy`
- Q3 What contract it touches: The config contract `runner.confinement.strict` (a distribution-registered config; contract says setup registers the default and doctor check `confinementPolicies-declared`-style readiness lists missing anchors), the one-capability-one-policy and one-executor-one-backend invariants, and the executor `confinement: { backend: bwrap }` reference shape. In strict mode a capability with no explicit policy is a config error, and every committed capability must declare a policy ID or `unconfined` first; the spec adds that execute/implement capabilities must be moved to a suitable backend profile first and must not be switched to `unconfined` just to pass the gate. cites: `docs/platform/agent-confinement/contracts/confinement-authority-v1.md#62-nơi-đặt-policy`, `docs/platform/agent-confinement/spec.md#9-default-implementation-đầu-tiên`
- Q4 How much risk: High. Strict makes unmapped capabilities fail closed, and the history records that a live migration was tried once (P06) and reverted to the original bytes, with the fixture-only migration the only one that landed. The deferred items (inherited-unconfined overclaim, thin `enforced` attestation body, no production caller for the reaper) are listed as reasons strict has not been enabled. Discrepancy to flag: the spec status block says the real `.fgos/config.json` still has hand-rolled `command:"bwrap"` argv and no `confinement` key, while spec §14 and history §13.1 say the bwrap invocations in `.fgos/config.json` declare `confinement.backend` (and herdr ones add `resourceBindings`). I cannot verify the live file from the files in scope, so which is current is unresolved. cites: `docs/platform/agent-confinement/history/rollout-and-settled-facts.md#10-lộ-trình-rollout-và-trạng-thái-hoàn-thành`, `docs/platform/agent-confinement/spec.md#14-pointers-hiện-tại`, `docs/platform/agent-confinement/spec.md#tồn-đọng-mở-open-deferred-items`
- Q5 What proof means done: Per the candidate spec: every capability resolves to a policy ID or explicit `unconfined`; doctor readiness check lists no missing anchors before the flip; posture pinned for all current executors with exact write grants of the bwrap ones; a red falsifier when an undeclared bwrap executor is added; probes pass. The history names the earlier real proof (live cross-provider dogfood) but says it does not depend on the migration. cites: `docs/platform/agent-confinement/spec.md#111-contract-tests`, `docs/platform/agent-confinement/spec.md#114-observability`, `docs/platform/agent-confinement/contracts/confinement-authority-v1.md#62-nơi-đặt-policy`
- Q6 What learning gets left behind: Update the spec status block and the S4 row so the "fixture only, live deferred" claim is replaced by what actually landed, resolve the status-block vs §14 contradiction, and record the strict-default decision in the decisions record. The `strict` default and any new config key also fall under the install/setup/doctor registration rule, which is in repo instructions I was told not to open, so I only note it as unverified here. Edit only the legacy owner, once. cites: `docs/platform/agent-confinement/decisions/confinement-authority-decisions.md#12-quyết-định-của-proposal`, `docs/platform/documentation/switchboard.md#1-operating-invariants`

## Scenario C: a new CLI release changes how its TUI starts sessions; change one executor invocation and record why

- Scenario: C
- Q1 What to read first: The switchboard row (legacy owner binds), then the decisions record §13.3, which is a direct precedent: the Codex TUI moved to a shared app-server daemon, and the executor `codex-herdr-fgovn` was given `--no-daemon` next to `-s danger-full-access -a never`. Then history §13.1 for the pane recipe and for why this kind of fix was previously forgotten. cites: `docs/platform/agent-confinement/decisions/confinement-authority-decisions.md#133-pane-codex-chạy---no-daemon-sandbox-riêng-của-codex-phải-tắt-suốt-phiên`, `docs/platform/agent-confinement/history/rollout-and-settled-facts.md#131-pane-herdr-bị-confine-cho-agent-không-phải-claude-công-thức-lịch-sử-vì-sao-từng-bị-quên`, `docs/platform/documentation/switchboard.md#2-area-authority-routes`
- Q2 What kind of work is this: A small operational fix to one executor invocation (data in executor config), not a contract change, as long as it stays in the invocation and in the provider-side recipe. The binding rule from the contract is that the backend driver must not branch on provider or agent type; provider-specific need is expressed by the invocation and by resource bindings. So the fix belongs in the invocation, not in a driver `if`. The precedent also says a second defense (writing the sandbox mode into the private-home config) was not done for exactly that reason. cites: `docs/platform/agent-confinement/contracts/confinement-authority-v1.md#65-backend-port`, `docs/platform/agent-confinement/decisions/confinement-authority-decisions.md#133-pane-codex-chạy---no-daemon-sandbox-riêng-của-codex-phải-tắt-suốt-phiên`
- Q3 What contract it touches: The executor invocation entry (`confinement.backend`, `resourceBindings`, CLI flags), at the config-normalization boundary. It does not change `ConfinementPolicyV1`, the backend port or the attestation shape if nothing else moves. Under the support matrix, the posture the invocation must still honor is `hostWrite: deny` with the declared write grants; a sibling path (`codex exec`, `codex-cli-bwrap`) is stated to be unaffected, so check which other invocations share the changed behavior. cites: `docs/platform/agent-confinement/spec.md#91-support-matrix-của-default`, `docs/platform/agent-confinement/spec.md#85-adapter-mới`
- Q4 How much risk: Low to moderate. The blast radius is one executor, but the failure mode in the precedent was silent in the worst way (every command failing at runtime inside the sandbox) and caused by an upstream default change, so the real risk is mis-attributing the cause. The precedent also states what was never proven (what event re-opened the thread under the other sandbox mode), which a maintainer should copy as an explicit "not proven" line rather than overclaim. cites: `docs/platform/agent-confinement/decisions/confinement-authority-decisions.md#133-pane-codex-chạy---no-daemon-sandbox-riêng-của-codex-phải-tắt-suốt-phiên`
- Q5 What proof means done: Follow the precedent's evidence shape: reproduce the failure under the exact mount layout fgOS builds (read-only root, tmpfs /tmp, writable private home and outbox), show the new invocation avoids it, then run a real dispatch of that pane and confirm the run settles with the expected outbox files and no stray daemon files in the private home. Add or keep the posture pin for the executor (spec §11.4). Whether the precedent's reproduction commands are still runnable is not verifiable from the files in scope. cites: `docs/platform/agent-confinement/decisions/confinement-authority-decisions.md#133-pane-codex-chạy---no-daemon-sandbox-riêng-của-codex-phải-tắt-suốt-phiên`, `docs/platform/agent-confinement/spec.md#114-observability`
- Q6 What learning gets left behind: A dated decision entry in the decisions record in the same four-part form the precedent uses: Decision (with date), Why (mechanism of the upstream change), Evidence (real run id and reproduction), Not proven (open hypothesis). If the change adds or alters a pane recipe step, also update the pane recipe and history facts so a later agent does not re-derive it; the history says the recipe was lost once because it lived only in commits under a different label and old executor ids. As the files are candidate carriage, the write belongs in the legacy owner; do not dual-author. cites: `docs/platform/agent-confinement/decisions/confinement-authority-decisions.md#133-pane-codex-chạy---no-daemon-sandbox-riêng-của-codex-phải-tắt-suốt-phiên`, `docs/platform/agent-confinement/history/rollout-and-settled-facts.md#131-pane-herdr-bị-confine-cho-agent-không-phải-claude-công-thức-lịch-sử-vì-sao-từng-bị-quên`, `docs/platform/documentation/switchboard.md#1-operating-invariants`
