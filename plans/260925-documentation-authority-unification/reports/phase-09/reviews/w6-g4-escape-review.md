# w6-g4 escape review: refuse declarations for escaping wrapper callers (1c64b1904), at 87c4f5f7a

Verdicts: 6 APPROVE, 1 REWORK (Medium, documentation only). The full rows are in w6-g4-escape-review.json.

The code fix is correct. All nine escape shapes from the earlier review now make the scan refuse on the real files, and so do several shapes the tests do not list. The one REWORK is about wording. The new spec sentence says every caller the value-flow scan cannot follow refuses the declaration. That is false for an aliased export, which the scan cannot follow and does not report as an escape. A new caller reached that way still inherits a declared wrapper silently.

## REWORK

1. **Medium: the spec sentence claims more than the code does.** The sentence in `docs/platform/git/spec.md` (section 12, line 638) says: "A caller the value-flow scan cannot follow (including `.call`/`.apply`, `Reflect.apply` and array-slot calls) refuses the wrapper declaration rather than inheriting its exemption." I tested this on a `git archive` copy of 87c4f5f7a. I added `export { git as gitAlias };` to `scripts/check-evidence-relocation.mjs` and a new `scripts/zz-probe.mjs` that runs `gitAlias('.', ['reset', '--hard', 'HEAD'])`. Result: **0 sites, no throw**, and the declared `git:79ebd2a9…` still matches. The control case with a plain `export { git }` does throw `stale or ambiguous`. This is the known export-alias gap from the earlier review. It is not fixed here, and the brief says not to fix it. But it means the new general claim in the spec is untrue. The open item in `git-owner-review-request.md` also undersells the gap. It says the alias "yields zero sites even with no declarations". It does not say that the alias also lets a new caller inherit a **declared** wrapper's exemption.
   **Fix (docs only):** narrow the spec sentence to what the code checks. For example: "A caller the value-flow scan reports as an escape (`.call`/`.apply`, `Reflect.apply`, array slots, or a value passed to an unresolved callee) refuses the wrapper declaration rather than inheriting its exemption. A caller reached through an aliased export (`export { fn as alias }`) is not yet followed; it is an open Git-owner item." In the OPEN paragraph of `git-owner-review-request.md`, add: "It also lets a new cross-file caller inherit a declared wrapper's exemption: `export { git as gitAlias }` in `scripts/check-evidence-relocation.mjs` plus a caller `gitAlias('.', ['reset','--hard','HEAD'])` in another file leaves the declaration matching with 0 sites." The scanner comment talks about "unresolved caller escapes", which is the scanner's own term, so it is accurate and can stay. The census does not need to be regenerated.

## Informational (not blocking)

- **Configured-binary class membership is self-asserted, not proven.** The guard `site.family === 'unresolved-binary'` also accepts a wrapper whose program is a caller parameter. On the copy, I changed one word in the declaration: the class of `scripts/verify-phase-02.mjs` `verifyForbiddenPhase02Diff:b73042bb…`, from tooling to `configured-binary`. Together with a new `run.call(null,'git',['push','--force',…])`, the scan then showed **0 sites, no throw**. This needs a reviewed edit to the declarations file, so it is not a silent inheritance. Still, the CHANGELOG's "configured-command provenance" and the spec's "their program comes from parsed configuration" describe what the declaration claims, not something the scanner checks. A possible later hardening is for the Git owner to decide: refuse configured-binary when any resolved caller supplies a literal program argument.
- `src/runner/merge.mjs`'s configured row inherits any future escape. The census records `escapes`, so a reviewer diffing the census can see a new escape. Once the census is regenerated, nothing rejects it: `verifyCensus` checks file digests and `sites`, and the payload digest covers only the file list, not class rows.
