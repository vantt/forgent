### Why `cargo test -p fgos --test authority` still fails, and what it needs

`fgos: error: admission refused: caller admission denied: operation 'authority.locate' not found in catalog`.

The provider is now registered, so the command reaches the composition root, but `InvocationService::new` builds its
admission gate from `CATALOG` (`CallerAdmission::allow_catalog_policies(snapshot.catalog())`), and
`authority.locate` has no `OperationDescriptor` there. `CallerAdmission::admit` step 1 refuses with
`AdmissionRefused::OperationNotFound` before any provider is consulted.

The fix is one `OperationDescriptor` row for `authority.locate` in
`packages/host-runtime/rust/src/catalog.rs` (owning component `component-authority`, effect `Read`, idempotency
`Safe`, `authority_policy_id` `authority.read`, `allowed_host_kinds` `&["cli"]`, the two contract refs the descriptor
already declares) plus the `CATALOG.len()` bump and the new id assertion in that file's
`catalog_contains_required_operations` test (`53` → `54`).

I verified this is the whole gap, not a guess: I patched exactly that row into `catalog.rs`, re-ran
`cargo test -p fgos --test authority` → pass (both sentences rank `durable-file` first, `matchedOn: "alias"`, which
is the assertion the task named), and `cargo test -p fgos-host-runtime --locked` → green. I then restored
`catalog.rs` to `HEAD`, because that file is not in this assignment's write scope. It is listed in
`needsWrites`.

The behaviour itself is already proven end to end: `cargo run -p fgos -- authority locate "atomic file write" --json`
against this checkout answers `total: 157` with `{"kind":"component","id":"durable-file","canonical":"durable-file",
"matchedOn":"alias","score":2003}` as the first match — that run carried the temporary catalog row too.
