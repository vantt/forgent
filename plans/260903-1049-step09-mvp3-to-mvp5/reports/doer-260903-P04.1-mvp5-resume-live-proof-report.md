## Summary

Closed R1-R7. R4 (resume) was the one genuinely new capability required:
confirmed by reading (not assuming) that `resumeSession`
(`session-engine.mjs:376`) is literally a `replaySession` alias, and that
the real gap was `src/verbs/coordination/run.mjs` unconditionally calling
`openStandaloneSession`/`openDeclaredProtocolSession` and refusing with
"already exists" on any repeat `coordinationId`. Also confirmed (by reading
`dispatchDeclaredOperation`/`authorizeDeclaredOperation`'s bodies) that both
are genuinely session-state-driven — a fresh `readManifest(coordinationId,
opts)` on every call, no in-memory call-sequence state — so the fix could
stay a small, surgical `run.mjs`-level branch, exactly as the cell brief
predicted.

Fix: a new `findExistingManifest(coordinationId, engineOpts)` helper in
`run.mjs` that calls `resumeSession` (the SAME blessed resume door
`session-engine.mjs` already exports for this exact purpose, per its own
doc comment) and, on a `not-found` `CoordinationError`, falls through to the
existing open call unchanged. Used at both open call sites
(`agent-led`/`declared-protocol`). No new dispatch/authorize/disposition
call site was added — resume reaches the SAME doors every fresh-open
request already used.

Live-proved R4 with two real `fgos coordination run` CLI subprocess
invocations against the same `coordinationId`, split right before the last
required actor (`fixer`) runs (so the session is genuinely still `active`,
not accidentally already-quorum-satisfied, when Call 2 starts) — no
duplicate Assignment, no reconsumed invocationKey, no lost disposition, no
hidden-context leakage, all measured, not argued. A third invocation
against the now-`completed` session is refused for the correct reason
(`not active`), proving terminal-absorbing still holds through the new
door. R1/R2/R3/R7's underlying single-call mechanics are unchanged from
P03.2 and re-verified passing, not re-litigated.

R5's negative battery: cross-referenced the existing 17-bullet
`coordination-session.md` list and P03.2's own tabulation first; all 17
stay proven at the engine level with zero diff. Wrote exactly 3 new tests
for the genuinely-new-because-of-resume gaps: invocationKey reuse across
the resume boundary, terminal-session refusal through the resume door
specifically, and confirming a session-wide cap (`aggregateBounds.
maxAssignments`) declared at open time still governs on resume and cannot
be silently loosened by a resuming request's own (inert) `aggregateBounds`
field.

Full detail, code citations, the live trace (including a real standalone
reproduction outside the test runner), and the Proof Matrix are in

## Gaps (see P04.1.md's own Gaps section for full detail)

- **Concurrent RESUME of the same session** (two real processes both
  resuming/dispatching into the SAME already-open `coordinationId` at once)
  is argued from construction (the SAME lock-held doors P03.1 already
  proved crash-resume-safe), not from a real multi-process reproduction —
  handed to Red-Team as this cell's own concurrency target, matching this
  track's established Doer/Red-Team division of labor.
- The pre-existing `writerId`-identity asymmetry on ordinary (non-driver-
  authorized) dispatch — never checked against `manifest.provenanceRoot.
  writerId`, only `authorize`/`disposition` are identity-gated — is now
  PRACTICALLY reachable via a second request under resume (before, one
  request always supplied one writerId for everything, by construction).
  Confirmed this is not a NEW gap (`thin-launcher-surface-readiness.md`'s
  own hole #4 already named the underlying asymmetry as an accepted,
  pre-existing property, no driver-handoff story exists yet) — flagged for
  whoever eventually designs multi-operator resume, not fixed here.
- Request-shape fields that only ever describe session-OPEN-time properties
  (`aggregateBounds` beyond the tested `maxAssignments`, `partialPolicy`,
  `objective`, `primaryRole`, `workRef`) are all inert on a resumed request
  (never reach the skipped `openParams`/open call) — confirmed safe (never
  a widening risk, the original open's value always stays authoritative)
  but not individually tested one-by-one beyond the `aggregateBounds` case,
  since the reasoning is identical for all five (same skipped code path).
