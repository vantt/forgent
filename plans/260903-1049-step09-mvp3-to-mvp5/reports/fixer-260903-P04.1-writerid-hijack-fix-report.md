# Fixer report — P04.1 writerId hijack (HIGH-1) + resume-against-broken-session (LOW)

Track: step-09-mvp3-to-mvp5. Cell: P04.1. Branch: step-09-mvp3-to-mvp5.

## What changed

`src/verbs/coordination/run.mjs` only:

- `findExistingManifest(coordinationId, engineOpts)` became
  `findExistingManifest(coordinationId, writerId, engineOpts)`. After
  resolving an existing manifest via `resumeSession`, it now asserts
  `manifest.provenanceRoot.writerId === writerId` before returning that
  manifest to either call site. On mismatch it throws
  `CoordinationError('validation', ...)`, mirroring `assertDriverIdentity`'s
  existing message shape (store.mjs), naming both the request's writerId and
  the session's own `provenanceRoot.writerId`.
- Both call sites (`agent-led` and `declared-protocol` branches) now pass
  `request.writerId` as the new second argument.
- Doc comments updated at the top of the module and directly above
  `findExistingManifest` to record the identity-gate rationale (why ordinary
  dispatch had no per-call identity check before resume, why resume made
  that reachable, why the check belongs at the resume boundary rather than
  inside `session-engine.mjs`/`store.mjs`).

No change to `session-engine.mjs`, `store.mjs`, `replay.mjs`, or
`schema.mjs` — confirmed by `git diff --stat` (see Scope below). The fix
stayed exactly where both the Red-Team's and Reviewer's independent fix
directions pointed: `run.mjs`, at the point `findExistingManifest` resolves
an existing manifest, before any step in the request dispatches.

## Before / after

**Before:** a second, independent `fgos coordination run` request naming an
EXISTING `coordinationId` with a `writerId` of the caller's own choosing
could reach `dispatchDeclaredOperation` for an ordinary `operation`/`fan-out`
step and silently consume the original driver's still-unconsumed
`driver-authorized` grant — no `authorizationId`/`invocationKey` knowledge
required, only the `coordinationId` and the protocol's public operation/actor
names. `authorize`/`disposition` steps were already correctly gated
(`assertDriverIdentity`); only plain dispatch through the resume door had no
gate.

**After:** any resumed request (one naming an existing `coordinationId`)
whose `writerId` does not match `manifest.provenanceRoot.writerId` is
refused at the resume boundary, before a single step is processed — for
every step kind, not only `authorize`/`disposition`. A resumed request under
the session's own real `writerId` is unaffected (same doors, same behavior
as before this fix).

## Tests added

Both in `test/verbs/coordination-run-driver-steps.test.mjs` (in-process,
deterministic fixture — same pattern the existing R4/R5 resume tests already
use), inserted between the existing `aggregateBounds` resume test and the
"two runs under one writer identity" test:

1. **HIGH regression** — "R5 (resume-specific, HIGH): a SECOND request
   naming an EXISTING coordinationId with a DIFFERENT writerId is refused
   before any step dispatches...". Reproduces the exact Red-Team attack
   shape: Call 1 (real driver) produces, reviews, and authorizes a
   driver-authorized recheck, leaving one unconsumed grant. Call 2 (foreign
   `writerId: 'attacker-writer-id-not-the-original-driver'`, same
   `coordinationId`) attempts the ordinary `recheck` operation step.
   Asserts:
   - `assert.rejects` on a `CoordinationError` with `category === 'validation'`
     and a message naming both the session id and both writerIds.
   - **No side effect**: `manifest.assignmentRefs.length` unchanged (2, not
     3), `.fgos/assignments` directory entry count unchanged (2), and the
     `operation-authorized` event count unchanged (1) — i.e. the rejected
     attempt consumed nothing and dispatched nothing.
   - A follow-up legitimate resume under the SAME real `writerId` still
     reaches and completes the recheck normally (confirms the fix only gates
     the foreign identity, not resume itself).

2. **LOW regression #1** — "R5 (resume-specific, LOW): resuming against a
   session with a malformed session.json fails closed with a corrupt-log
   error...". Hand-writes an invalid-JSON `session.json` for a fresh
   `coordinationId`, then asserts `runCoordinationUseCase` throws
   `CoordinationError` with `category === 'corrupt-log'` rather than falling
   through to a fresh open; confirms the manifest file is untouched and no
   `.fgos/assignments` directory was ever created.

3. **LOW regression #2** — "R5 (resume-specific, LOW): resuming against a
   coordinationId whose session directory exists but has no session.json...".
   Reproduces P00.1's Gap #15 crash shape (dir created, `session.json` never
   written). Confirms `findExistingManifest` correctly falls through
   (`not-found`), and the fallback `openSession` attempt then fails closed at
   its own pre-existing `EEXIST` "already exists" guard — no `session.json`
   ever gets written and no Assignment is created.

(#2 is the exact shape the LOW finding named; #3 covers the sibling
Gap #15 shape Red-Team also exercised live, for completeness — both are
small and directly adjacent, not scope creep.)
