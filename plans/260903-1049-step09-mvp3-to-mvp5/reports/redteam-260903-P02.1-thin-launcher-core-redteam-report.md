## Findings

- **MEDIUM (live-reproduced): `--plan` path resolves against the wrong
  base when `--dir` is passed.** `launch-master-loop.mjs`'s
  `assertPlanPathExists` resolves the relative `--plan` path against
  `ctx.cwd` (`repoRootForCoordination`, derived from `--dir`), while the
  sibling `run` sub-verb eagerly resolves `--file` against
  `process.cwd()` (`bin/fgos.mjs:3122`) before the use-case ever sees it.
  Reproduced live: a real, existing `plan.md` in the caller's own working
  directory is reported as "does not exist" once `--dir` is supplied,
  while an equivalent `run --file` invocation with the same `--dir` and a
  same-named relative file in `process.cwd()` correctly finds it. This
  contradicts the Doer's own design claim that the launcher "mirrors that
  exact pattern" as `run`/`show`, and produces a false-positive rejection
  of a valid path — the opposite of R4's "bad file path... fails with an
  actionable error" intent (a *good* path must not fail). The Reviewer's
  parallel pass flagged the same code fact but rated it LOW as
  "untested... neither behavior is obviously wrong"; this red-team pass
  actually ran the repro, which is why the severity here is raised to
  MEDIUM. Fix: resolve `--plan` against `process.cwd()` in
  `bin/fgos.mjs`'s `launch-master-loop` branch, matching `run --file`
  exactly, plus a `--dir` + relative `--plan` regression test.

- **LOW (informational, not a bug): the "unknown fixture id" R4 test is
  unreachable through the real CLI.** `protocolRef.id` is a pinned
  constant with no caller-facing override, so the corresponding test only
  proves `run.mjs`'s reused gate via direct object mutation
  (defense-in-depth), not a launcher-reachable input path. Consistent
  with R1's single-fixture-launcher design; flagged only so the trace
  doesn't overstate what that specific test demonstrates.
