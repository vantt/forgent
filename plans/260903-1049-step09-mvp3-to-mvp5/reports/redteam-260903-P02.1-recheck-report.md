## 1. Side-by-side code read

`bin/fgos.mjs`:
- `run --file` (line ~3123 + call site): `const filePath =
  requireField(flags.file, ...)` (raw), then at the call site:
  `requestPath: path.resolve(process.cwd(), filePath)`.
- `launch-master-loop --plan` (line 3153, post-fix): `const planPath =
  path.resolve(process.cwd(), requireField(flags.plan,
  'coordination launch-master-loop requires --plan <path>'))`.

Both now resolve a relative `--plan`/`--file` against the identical base
(`process.cwd()`) using the identical function (`path.resolve`). The only
difference is where in the code the resolution happens (at the call site
for `run`, at the declaration for `launch-master-loop`) — functionally
equivalent, not just superficially similar. Confirmed by direct read, not
inferred from the report.

Downstream, `launch-master-loop.mjs:53`'s `assertPlanPathExists` still
does `path.resolve(cwd, planPath)` where `cwd` is `ctx.cwd` =
`repoRootForCoordination` — but since `planPath` now always arrives
already absolute from `bin/fgos.mjs`, `path.resolve(anything, absolutePath)`
returns `absolutePath` unchanged (Node semantics) regardless of `ctx.cwd`.
No change to `launch-master-loop.mjs` was needed, matching the Fixer's
claim.

## 2. New edge cases attempted (live, not theorized)

All three run against a two-directory setup (`caller-cwd` vs. a separate
`--dir`-named `other-repo`, mirroring the original repro), executor
config modeled exactly on the test harness's `writeFakeExecutorConfig`.

**A. Absolute `--plan` path.** `--dir /tmp/.../other-repo --plan
/tmp/.../abs-plan.md` from `caller-cwd`: exit 0, `coordinationId` and all
three steps (`produce`/`review`/`red-team`) dispatched correctly.
`path.resolve` on an already-absolute path is confirmed a no-op in
practice, not just by API contract.

**B. Relative `--plan` with `..` traversal, combined with `--dir`.** From
a `nested/caller-cwd` subdirectory, `--dir other-repo --plan

(finds the file one level up from the caller's actual cwd), unaffected by
`--dir`. No path-escape/security concern — this is a trusted-operator CLI
flag resolved via ordinary `fs.existsSync`, not a boundary crossed by
untrusted input.

**C. Missing/empty `--plan`.** Both `--plan` omitted entirely and `--plan
""` (empty string) fail at the pre-existing `requireField` check
(`fgos: coordination launch-master-loop requires --plan <path>`, exit 4)
— before `path.resolve` is ever reached. Confirms the fix did not touch
or weaken the existing missing-value validation path.
