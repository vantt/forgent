# Lane sync — runner merges a base ref, worker only edits files

Worktree `/home/vantt/projects/forgentX-worktrees/rununit-sync`, branch `feat/rununit-sync`. Rule number: **RUL97**.

## Motive

- **PROVEN** (Doer feedback, reproduced by reading the code): a confined worker cannot write the gitdir, so it cannot run `git merge`. A merge someone left half done in the worktree is then refused by the preflight `foreign-staged-index` (`run.mjs` before the change). So `fgos run` had no way to do an end-of-batch main sync.
- **Also found:** on main, a writing unit started over someone else's open merge that staged nothing would conclude that merge with the agent's files: `commitUnitWork` → `git commit` with MERGE_HEAD present. The red-team confirmed this against main's tree. This lane refuses it with `merge-in-progress`.

## Design (Lead's choice: the runner merges, the worker only edits files)

1. **Unit fields.**
   - `syncBase: <ref>`. Allowed characters are `[A-Za-z0-9._/-]`, with no leading `-` or `/`, no `..`, no trailing `/` and no `.lock`, so `@{`, `^`, `~`, `:` and spaces are refused.
   - `syncBase` needs `writes`.
   - A Unit with `syncBase` and **no objective** is sync-only (`syncOnly: true`), with objective `Merge <ref> into this branch.`.
   - **How sync-only is recognized:** by the missing objective. The Unit says so explicitly; no prompt text is guessed at.
   - One-liner: `fgos run --sync <ref> --writes … [--worktree …]`. With a prompt it means sync then the task; without one it is sync-only. `--sync` is refused with `--unit` or `--resume`.
   - A units file (`workflow start --units`) that names `syncBase` is refused instead of silently dropping it.
2. **Before any seat runs.**
   - `seedSync` resolves the ref to a sha before the unit run exists. It refuses a ref naming no commit, and a run from the main checkout.
   - `runPendingSync` → `startSyncMerge` runs with trusted git (RUL85 `gitContext`: gitdir from the main checkout, hooks from main, `GIT_*` dropped, fsmonitor off), with `merge --no-commit --no-ff`, rerere off and autostash off.
   - **up-to-date:** nothing changes.
   - **Clean merge:** the runner commits `chore(sync): merge <ref>` and checks the parents and the committed set. The unit then runs its pattern, or passes at once if it is sync-only, with `results: [{role:'sync', round:0, commit}]`.
   - **`.fgos/**`** (Lead decision Q1, 2026-10-15): every path the merge staged or left conflicted, clean or not, is put back to the branch side (HEAD). A path the base deleted is kept; a path only the base has is not taken. This applies on every branch, not only `fgw/*`. It matches approve: `merge.mjs:1425-1450` resolves a `.fgos/` path the branch left unchanged since take to the target, so keeping ours does not block approve later.
   - **A refusing pre-commit hook** (clean or concluding commit) gives `hook-refused` with the hook's stderr. git 2.34 has no `git hook run`, so when `git commit` fails the runner runs the trusted pre-commit hook again the way git runs it (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`) to tell the two apart. Clean merge: the merge is aborted and the outcome is `policy-refusal`. Concluding commit: the merge is kept and the round fails; each resume tries once.
   - **Other conflicts:**
     - The merge stays open (`unit.json#sync.status = conflicted`).
     - Conflicted paths not already covered are added to `writeScope` (`sync.scopeAdded`).
     - The producer's brief gets a `## Merge to finish` section that lists the files and says never to run git.
     - The assignment carries `syncConflicts`.
3. **Preflight.**
   - `preflightUnitWorktree({sync})` treats an open MERGE_HEAD equal to `sync.sha` over `sync.head` as the run's own. Its conflicted and merge-staged paths count neither as foreign-staged nor as `preExistingInScope`.
   - Any other open merge gets `merge-in-progress`.
   - `commitUnitWork` also refuses to commit over an open merge.
4. **After a passing round.** `commitRoundWithSync` → `finishSyncMerge` runs first:
   - **Marker left** (7 or more `<`, `|` or `>`, including a larger conflict-marker-size): `conflict-markers` with `paths`. Nothing is staged and the merge is kept. This is a commit-pending failure, so `fgos run --resume` only commits (RUL86).
   - **No marker left:** the conflicted paths are staged. An index holding paths the merge did not stage gets `staged-set-mismatch`, and the runner takes back what it staged itself. Otherwise the runner commits with MERGE_HEAD as second parent, checks parents and set, narrows the scope back, and then makes the round's normal commit (`commitUnitWork`).
   - `results[i].commit.sync` holds the merge's own record.
5. **Fail, abort and resume.**
   - **Round not passed:** the merge stays open. On resume `assertSyncResumable` decides:
     - still open: the seat runs again.
     - concluded by hand: `merged` (`commit.by: 'outside'`).
     - aborted, HEAD moved, or a clean merge commit that holds the wrong set: the resume is refused with a clear message.
   - **Crash between git and writing `unit.json`:** `sync.started` lets a resume adopt its own open merge. A first start never adopts a merge someone else opened.
   - **Refusals:** a refused start leaves no merge open. `merge-in-progress`, `foreign-staged-index`, `merge-refused` and `unscopable-conflict-path` end as `policy-refusal`; `git-error` and `committed-set-mismatch` end as `execution-failure`.
6. **Settlement.** A conflict-resolving worker only edits files that were dirty at launch, so it was scored `verdict-inconclusive`. Now the files in `assignment.syncConflicts`, inside its scope, whose content changed during the turn count as evidence (`evidence.editedSyncConflicts`). Units without a sync are unchanged; a regression test covers this.

### Prior art (`fgos catchup`, `git log -S catchup`, `-S syncBase`, `-G 'merge --no-commit'`)

- `performCatchUp` (`src/runner/merge.mjs`, tsk-4ax) and `resolveFgosOnlyConflict` merge a target into an item branch in a **detached ephemeral worktree**, with plain git and a Work-layer `runGoalCheck`.
- **Reused (shape):**
  - `merge --no-commit --no-ff`, then list `--diff-filter=U`, then commit or abort.
  - `.fgos/` conflicts take the target side.
  - abort only when MERGE_HEAD is present (`abortMergeIfPossible`).
- **Not reused (code):**
  - `src/runner/execution/**` must not import `merge.mjs` (RUL73 and the A4 guard in `run.mjs`).
  - Its git reads the worktree's gitdir, which breaks the RUL85 trust boundary.
  - Its goal check belongs to the Work layer.
- **What was missing:** a merge the worker finishes. Catchup aborts on any conflict.
- `syncBase` had no prior art.

## Open questions

1. **[DECIDED by Lead 2026-10-15: keep ours for `.fgos/**`, `hook-refused`, applied]** **(Lead) `.fgos/` and the repo hook.** This repo's `.githooks/pre-commit` refuses staged `.fgos/` changes on `fgw/*` branches and staged `.fgos/` deletions on every branch. A sync from main that brings such changes is therefore refused. This is from reading the hook; it was not reproduced with the hook installed.
   - Catchup avoids the hook because it commits from a detached checkout.
   - **Options:**
     - (a) Commit the sync merge from a detached checkout plus a CAS `update-ref`, like catchup. This is costly: the worker's worktree is on the branch.
     - (b) Let the hook accept a `.fgos` path whose index blob equals MERGE_HEAD's. This changes the AGENTS.md rule "MERGE_HEAD skips only the root guard".
     - (c) Keep it as is. It does not affect `feat/*` branches, which is the main use case, except when main deletes `.fgos` files.
   - **Recommendation:** (c) now. Choose (a) or (b) if the runner loop (`fgw/*`) is ever given a sync.
2. `fgos run --sync` requires `--writes`. A sync-only unit has to name a scope even though only conflicted paths get written. Should it default to `writes: []` plus conflicts? Not done, to follow the brief ("only with writes / a linked worktree").
3. **An inline producer over an open merge.** An inline round has no runner commit, so the merge stays open until a resume. It is documented under "Not done".
