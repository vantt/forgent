## Medium

### M1. `usesSymbol` loses calls after `//` or `/*` inside a string, and after an unpaired backtick. It duplicates `test/helpers/js-source-lexer.mjs`.

- Location: `test/architecture.test.mjs:365-376`.
- Cause: comments are stripped with `/\/\*[\s\S]*?\*\/|\/\/.*/g` before strings are recognised.
  - `//` inside a string removes the rest of that line.
  - `/*` inside a string removes everything up to the next `*/`, which may be many lines later (the next JSDoc).
  - A single-quoted string with an odd number of backticks pairs with a later backtick, and the template rule then blanks the code between them.
- Failure scenario (each case run against a copy of the function):
  - `const g = 'docs/*.md';\nawait executeExecutorCli('x');\n/** doc */` returns **false**.
  - `const u = 'https://x'; await executeExecutorCli('x');` returns **false**.
  - `const m = 'use \`fgos run';\nexecuteExecutorCli();` returns **false**.
  - A new production caller written this way passes the guard. The guard is the lock this phase exists to add ("Lần này guard khoá lại").
- Existing alternative: `test/helpers/js-source-lexer.mjs` (`lexSource`) is documented as "Shared by the source-text guard tests". `dispatch-reconciliation-import-graph.test.mjs` and `assignment-enumerator-guard.test.mjs` already use it. Its `shape` view returns **true** for all three cases above.
- Fix:
  - Build `usesSymbol` on `lexSource(raw).shape`, so literals are blanked and `${}` code is kept.
  - Do the definition and re-export stripping on that view. For `export {…} from` detection, read the specifier from the `code` view at the same offsets.
  - Add the three cases above to the fixture test at `:395`.
- The same reasoning applies to `extractImports` (`:56-70`), which `findWorkLayerReach` uses. Its regexes run on raw text, so an import named in a comment or string produces a spurious hit. Those are false positives, so they fail loudly, but they share the same hand-rolled parser. Consider `moduleSpecifiers` from `dispatch-reconciliation-import-graph.test.mjs:58`.

### M2. The redirect names `--provider <executorId>`, which `fgos run` refuses for a non-agent executor. The new test asserts that refused output.

- Locations: `bin/fgos.mjs:4731` (agy hook), `scripts/dispatch-decide-hook.mjs:57,70`, `bin/fgos.mjs:962-963` (`dispatch execute <executor>`), `cli.mjs:310-311` (`readOnlyDoors`).
- Cause: `adhocUnitFromPrompt` (`bin/fgos.mjs:451-458`) accepts `--provider` only for executors with `kind === 'agent'`. `decide` can resolve to a `kind: 'tool'` executor. The real config has two: `gitnexus` and `herdr`.
- Failure scenario (reproduced in a temp repo):
  - With the fixture from `test/cli/dispatch-retired-doors.test.mjs:115-130`, the hook denies with ``Run it through `fgos run "<prompt>" --provider tool-only` ``. The test pins that string.
  - Running that command gives `fgos: unknown --provider "tool-only"; valid providers: pi, openai`, exit 4.
  - So a blocked agent follows the redirect and hits a second refusal.
- Second problem: `--provider` is a soft preference, not a pin. Before, `dispatch execute codex` always ran codex. Now `fgos run --provider codex` may bind another candidate, and the message does not say so.
- Fix:
  - Name `--provider` only when the resolved executor is `kind: 'agent'`. Otherwise say `fgos run "<prompt>"` (or `--unit`) without `--provider`.
  - Change the fixture to an agent executor and assert the message's command is accepted by `adhocUnitFromPrompt`. For example, spawn `fgos run "<prompt>" --provider X` up to its validation step, or unit-test the parser.
  - When the old call carried `--for <capability>`, include `--capability <capability>`. `fgos run` already accepts that flag.
