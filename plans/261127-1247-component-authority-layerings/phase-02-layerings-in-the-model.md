# Phase 2: Layerings in the model, fields renamed

The model declares `hexagon`, `stack` and `domain-scope` as `layerings` rows; component rows
use `hexagon` and `stack` in place of `layer` and `tier`; schema, Rust and the Node loader read
every value list from the model. The `hexagon` values keep today's order in this phase (entry,
use-case, infra, domain, kernel) so the checks stay green; phase 4 changes the order together
with the data. `orchestration-ring` is declared in phase 5 with its values.

## Steps

1. Schema: `$defs.layers` becomes `{contract, layerings, domains}`; add `$defs.layering` with the
   CAS-D8 fields (`values` items `{id, meaning}`; `rules` items from `order-downward`,
   `isolation`, `port-wiring`; `source` one of `declared`, `fromPaths`; `granularity` one of
   `component`, `path`; optional `debt` items `{component, reason, backlog}`). Component and
   exception rows drop `layer` and `tier` and accept layering-id keys through
   `patternProperties` (string values); the Rust check decides which keys and values are allowed.
   Contract rows get an optional `port: {kind: driving | driven, implementers: [string]}`.
2. Rust `model.rs`: the layers struct holds `layerings` and `domains`; add a `Layering` struct;
   `Component` and `Exception` carry the layering values as a map flattened from the
   layering-id keys; delete `TierException`. A row that still carries `layer` or `tier` is
   refused with a message naming `hexagon` or `stack`.
3. Rust `declare.rs`: delete `LAYER_NAMES` and `TIER_RANGE`; `check_component` requires, for
   every layering whose source is `declared`, a value from that layering's `values`; refuses a
   key that is neither a known field nor a declared layering id; checks exception values the
   same way. `EMPTY_LAYERS` seeds `layerings: []` and `domains: []`. `COMPONENT_ORDER` writes the
   layering fields after `parent`, in the model's layering order. The schema-enum test reads its
   expected values from the model.
4. `render.rs`: the two component tables print one column per declared layering, headed by its id.
5. Data. `layers.yaml` gets three `layerings` rows, every CAS-D8 field filled from DISCUSSION §6
   and §3 rows 11a and 18:
   - `hexagon`: values in today's order, rules `[order-downward]`, granularity `path`,
     source `declared`;
   - `stack`: values `T0-native` to `T9-surface` with CAS-D13's `T7-domain` and `T8-work`, each
     value's meaning taken from today's `tierNames`, rules `[order-downward]`, granularity
     `component`, source `declared`;
   - `domain-scope`: values `core` and `domain`, rules `[isolation]`, granularity `path`,
     source `fromPaths`.

   In `components.yaml` rename `layer:` to `hexagon:` and `tier: N` to `stack: T<N>-<name>` on
   every row and exception, applying the CAS-D13 swap: Work rows (`work-state`, `runner` and its
   8 subcomponents, `supervision`) take `T8-work`; Domain rows (`domain-components`,
   `coding-domain`, `group-thinking`, `domain-registry-loader`, `enduser-docs-*`) take
   `T7-domain`; the `src/report/knowledge-resolver.mjs` exception moves to `T8-work`. Do the
   rename with a script under `.fgos/runtime/tmp/`, never by hand, and compare the row count
   before and after.
6. Node: `loadModel` reads `layerings`, ranks each layering's values by position, and maps files
   to their `hexagon` and `stack` values from the renamed fields; the tier tests compare value
   positions, not integers; the `tierExceptions` handling is deleted.
7. Update `model_checks.rs`, the `locate.rs` and `render.rs` fixtures and the
   `decision-index.test.mjs` fixture to the new shape.
8. Regenerate the views: `npm run fgos:dev -- authority render`.
