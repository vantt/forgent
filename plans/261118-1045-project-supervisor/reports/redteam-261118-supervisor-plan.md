# Red team: project supervisor plan (2026-11-18)

Plan read: `plan.md` + 19 phase files at `f1cd5635e`. Design input: shaping report "SETTLED DESIGN", "Round 8". Code facts checked at the same tree. Tag **[OWNER]** = needs an owner decision (five-part form at the end);
**[PLANNER]** = the planner can fix inside the plan's frame. Counts: 3 critical, 8 high, 9 medium, 7 low.

## Critical

**C1. The supervisor never leaves, so after the first wake no event is ever handled again.** [PLANNER]
Scenario: the watcher wakes the supervisor; it drains the queue and calls `supervisor done` -> `{done:true}`. The pane stays open and idle. Next tick: new event, `wake` sees holder `Live` -> `already-live` (phase-12:29). The idle LLM never reads the queue again. Events pile up forever; nothing alerts.
Evidence: PS-9 says `done` "ends the session" (plan.md:133), but phase-12:38-39 only answers `{done:true}`, phase-10:51 just forwards it, and the skill ends at `done` (phase-18:18). No phase retires the supervisor's own placement.
Fix: `supervisor done` on an empty queue calls the phase-10 `stopHeadSession` on the caller's own role (already allowed at phase-10:49-50). Add a test to phase 12: done -> placement retired -> the next wake reports `started`.

**C2. `head:supervisor-main` is shared by every project on the machine.** [PLANNER]
Scenario: forgent's supervisor is live. Project B on the same machine (mission #1) raises `plan-became-ready`. Its wake resolves `head:supervisor-main` -> Live -> `already-live`, so B is never supervised. A manual `session start supervisor --name main` in B fronts forgent's pane (head-start.mjs:204-212).
Evidence: `identityHolder` runs `fgos identity resolve <role>` and uses `projectRoot` only as the cwd (head-start.mjs:65-77). The Identity directory is per user, "so every project on the machine sees it", and folds remote holders (identity/spec.md:115,129). Lead and planner names (PS-11) have the same problem.
Fix: name the supervisor after the project handle (`fgos identity project`, cut to 32), not `main`. Lead and planner names also need a project discriminator, or the wake/grant must check `projectId` from the resolve answer. Update PS-8 and PS-11.

**C3. A lead's footprint-derived writes can open the sandbox to unconfined execution.** [OWNER: D1]
Scenario: a planner (an LLM with `plans` writes) puts `.githooks/pre-commit`, `.git/hooks/x` or `./**` in a plan's footprint. The lead's grant then makes those paths writable (phase-09:34-38). A hook written there runs, unconfined, at the next commit in the main checkout by a person or agent. This plan's own footprint already lists `.githooks/pre-commit` (plan.md:72). `validateWorkspacePaths` refuses only absolute paths, `..`, `.fgos` and globs (workspace-paths.mjs:20-33): `.` (the root), `.git` and `.githooks` pass. A lead can also edit its own `plan.md` footprint and widen it at its next rotation.
Smallest fix: the lead writes only its plan dir. The footprint becomes the bound on `run --writes` and on `land` (H4), not a sandbox write grant. This changes settled item 4, hence D1. If the owner keeps footprint writes, at least deny `.`, `.git`, `.githooks`, hook paths and `Cargo.toml`/`build.rs`-class entries, and read the footprint from `main`, not from the working tree.

## High

**H1. Publish-then-push leaves local `main` ahead of origin when the push is rejected; every later land jams.** [PLANNER] Branch flow publishes to local main, then pushes (phase-07:25-26). On a rejected push it retries from prepare against the fetched target, but local main already holds the unpushed merge, so publish is stale or mismatched three times, then `land-retries-exhausted`. The `--paths` flow keeps the local commit and refuses `land-remote-diverged` (phase-07:27). Likely trigger: the owner pushes from another machine. A person must repair main.
Fix: push the candidate OID first (a non-forced push is a CAS on the target), then fast-forward local main. For `--paths`: fast-forward the main checkout to the fetched origin before `scoped_commit`. Add a fixture test where the remote moves after the local commit.

**H2. Edge-only detection loses plans for good.** [PLANNER] (a) Records are windowed `since lastTick` (phase-11:33). Plan and discussion records carry the commit time. A merged branch's status commit, or another machine's push that arrives minutes late, has `ts < lastTick` and is never raised. (b) Nothing fetches: the sources read local `main`, so a plan set `ready` from another machine is invisible until someone pulls. (c) A lost `state.json` (the ignored-file wipe of 2026-11-08) makes the next tick "first": raise nothing (phase-11:30-31). In all three the plan sits `ready` and is never admitted.
Fix: window by a cursor on main's first-parent OID, not by time. Fetch the target through the Remote port each full tick. Add one level-triggered definition: a `ready` and admissible plan, or a `running` plan with no live lead, with id = dir + the status commit OID.

**H3. Pace rows and live-projection rows cause wake and mail storms.** [PLANNER] `watcher-active` sits in the same `--def` directory (phase-13:32-39). Every tick its row is raised with the default action `wake-supervisor` (`actions` is empty, phase-04:22), so a supervisor starts every 60 s while any plan runs. `supervisor-wake-failed` and `head-gone` rows sit over aggregates or live projections. If their `ts` is "now" or the latest failure, the id `kind|subject|ts` (phase-11:35) changes each tick, which means a new mail and a new wake every minute.
Fix: keep pace definitions in their own directory that is never raised. Each aggregate or projection definition names a stable `ts` (the first failure since the last `started`, or gone-since). Add one test: three ticks of the same outage -> one event.

**H4. Request verbs are not bound to the caller's grant or plan.** [PLANNER] `land {branch}` takes any branch. Every head with `land` (secretary, shaper, planner, supervisor) can land another plan's branch or a half-reviewed one. `land {paths}` commits any dirty main-checkout path, including a person's unfinished edits. `run {writes}` lets a lead's workers write outside its footprint (phase-10:36-37, phase-09:31-33). The Land port already carries `footprint` (git land.rs:23-24), but `LandCommand` never sets it (phase-07:18).
Fix: the route child refuses `paths` outside the caller's grant writes and `writes` outside the lead's plan footprint. Branch `land` is lead-only, and the lead passes its plan footprint as `LandRequest.footprint`. Other personas get `land` with `paths` only.

**H5. Nothing wakes the supervisor after the owner answers its question, and a stuck supervisor is invisible.** [PLANNER] The supervisor asks via a plan's owner-question section (`fgos questions --open` is read-only, command-registry.mjs:1417-1419). It must mark the event handled to reach `done`. No definition fires on an answer (phase-13:26-35), so the answer waits until an unrelated event. This contradicts "no person sitting by". A live but stuck supervisor (context limit, a hung tool) returns `already-live` forever.
Fix: add `question-answered` on `fgos.plan.activity` for plans with an open question section, and `supervisor-stuck`: an event unhandled for longer than k × the active interval while the supervisor is live -> notify.

**H6. Arming the lane pool breaks running work from wave 1.** [PLANNER] (a) Phase 4 makes `workerSlots.ceiling` default 4 and claims that "nothing reads these keys before phase 6" (phase-04:37). But `claimWork` reads that key today (claim-port.mjs:29-30,145), and null currently means unarmed (workerSlots.yaml). So the old per-item gate arms at 4 as soon as phase 4 lands. (b) Lane files sit under the machine-wide lock root (state_root.rs:77), while the ceiling is per project (schema has no scope), so project A with 4 and project B with 8 split one pool unevenly. (c) `take` is `Wait::Try` (phase-06:23). Phase 17 removes the fanout and loop trims, so a 6-way fanout gets 2 `abandoned-not-started`, and Work items claimed for refused seats churn. This plan's own wave 3 has 5 phases, and other lanes on fg-server2 share the 4 seats.
Fix: keep the standard at `null` through phase 18 and arm 4 in phase 19 (CHANGELOG). Make `workerSlots.ceiling` `global-only` (it is a machine pool). Make the loop and fanout pre-trim on `lanes.free` (a read) instead of deleting the trim. Give `take` a bounded wait.

**H7. No phase writes this repo's `land.gates`, and empty gates disable the loop in every other project.** [PLANNER] `.fgos/config.yaml` is tracked (config spec:61) but is in no phase footprint. After phase 19, `land.gates` is `[]`, so every `fgos land`, including the supervisor's `--paths` status edit, refuses `land-gate-missing`, and acceptance 8 fails. In other projects (mission #1) the whole loop is dead until someone configures gates. `--paths` also runs the full gate on the main checkout's working tree, so other people's dirty files decide the result (phase-07:27).
Fix: add `.fgos/config.yaml` (gates + `regenerate` from `land-branch.sh`) to phase 19, or to phase 4. Gate a `--paths` land only by `when` matches, and gate the committed tree, not the working tree. Add a doctor row for `land.gates empty while watcher.enabled`.

**H8. A head started from a `Type=oneshot` unit can die when the tick exits.** [PLANNER] `render_systemd` writes `Type=oneshot` with the default `KillMode=control-group` (timer.rs:356). Any run supervisor, multiplexer server or detached child that the head start forks inside the unit's cgroup is killed when the tick returns. The spike checks only exit codes (phase-02:20-22), not whether the head survives the unit's exit or a logout without linger.
Fix: in phase 2, assert the head is alive 2 minutes after the unit exits. Phase 15 then renders `KillMode=process`, or starts the head through `systemd-run --user --scope`, whichever the spike proves.

## Medium

- **M1. Double supervisor on a slow start.** [PLANNER] `startHeadSession` checks Identity, then places, with no lock (head-start.mjs:202-218). The placement is written only after launch, so if a start takes longer than the 60 s interval, or a manual wake runs at the same time, the next wake starts a second one. Fix: the wake door treats a recent placement whose host reports alive as `starting`. Add backoff after `start-failed`, because an absent herdr today means one start attempt per tick forever.
- **M2. A supervisor crash mid-drain leaves a plan `running` with no lead** (landed `running`, then died before `session start`). Only ops-metrics `plan-no-progress` catches it, and much later. [PLANNER] Fix: `supervisor plans` reports `running ∧ !leadLive` (the H2 level definition covers it).
- **M3. Token burn: every `lane-freed` (one row per worker end) and every `plan-priority-changed` cold-starts an LLM even when nothing is admissible.** [PLANNER] Fix: a no-LLM prefilter in `wake.rs`: capacity-kind events with no admissible plan are marked handled by the watcher.
- **M4. Lead stalls and duplicates.** A lead cannot be woken when a ticket ends, so it polls `request result` (60 s cap) or idles. A restarted lead does not know its ticket ids and re-runs a phase, giving two workers on one worktree. Leads also race for freed lanes with no priority. [PLANNER] Fix: `request result` without an id lists the role's tickets, plus a long-poll `--wait`. Let the lead skill read its tickets on start.
- **M5. Two planners for one discussion.** Round 8 makes the secretary start the planner (shaping:303-309), and the plan keeps `discussion-settled` -> the supervisor starts one too. Two plans get written. [PLANNER] Fix: the supervisor skips a discussion that some plan's `source` already names, or a live `planner-*` holds.
- **M6. Branch-only census exemption misses detached worktrees.** `worktree create` defaults to `--detach` (command-registry.mjs:128), and phase 5 keeps refusing detached HEAD (phase-05:22), so p-t55xjys4u5 stays open for default seats, and `land <branch>` needs a branch. [PLANNER] Fix: refuse only when the committing toplevel is the main checkout on trunk. The lead skill always creates worktrees with `--branch`.
- **M7. One door, broken twice (L10, principle 1).** `landRunnerItem` (merge.mjs:870) stays a second landing door next to `fgos land`, and `run` tickets duplicate the `.fgos/assignments/<unitRunId>/` result store. [PLANNER] Fix: the `run` ticket returns the unitRunId and reads the existing record. Open a backlog item to move `landRunnerItem` onto the use case.
- **M8. The gate runs branch code unconfined** (`sh -c` in the candidate worktree, phase-07:28). A confined worker can get code run outside its sandbox through a test file or `build.rs`; review is the only control. [OWNER: D2]
- **M9. A crash mid-land has no named recovery.** A `fgos land` killed between publish and push, or holding the rank-20 slot, leaves WAL intent (land.rs:101-103). The plan names no recovery and has no test for it. The full gate also runs while holding the slot, so all lands queue behind one test suite, and each retry re-gates. [PLANNER] Fix: add a phase-7 test where a killed land is followed by a recovered or named-refused land. Say what the operator runs.

- L2 PS-11 collisions count `done`/`withdrawn` plans; over time a live plan's lead cannot restart (`plan-ambiguous`). Exclude closed plans.
- L3 Rollback "revert the merge commit": a re-land of the fixed branch then reports `land-already-merged`; say to revert the revert.
- L4 Inconsistencies: phase-11:12-14 says no phase owns the `watcher` lock row, but phase 6 adds it, and 11 omits 6 and 13 from depends-on. Phase 1 records PS-1..16 and misses PS-17/18. "Owner questions: none" (plan.md:242), yet spike verdicts 2/3 create one.
- L5 Windows has no timer scheduler, so supervision silently never runs; say so in doctor and docs. macOS is render-only (no live proof).
- L6 The Event Store queue is read whole and never compacted (phase-08:40). With H3 unfixed it grows each tick. Across machines, a handle on one machine is invisible to the other until sync.
- L7 Idle leads and planners are never stopped after `done` or after their plan is written. Add `session stop` to the close duty.

## Owner decisions (five-part form)

**D1. Lead write grant (C3).**
1. What is happening: settled item 4 gives a lead its plan footprint as sandbox writes. A footprint can name `.`, `.git` or `.githooks`, and this plan's own footprint holds `.githooks/pre-commit`.
2. Cause: checked `validateWorkspacePaths` (workspace-paths.mjs:20-33): it denies only `.fgos`, `..`, absolute paths and globs. Leads never need to edit code in the main checkout; workers write in worktrees.
3. Options: (a) Lead writes = its plan dir only; the footprint bounds `run --writes` and `land` (+~40 lines in phase 9/10; safest; the lead cannot hot-fix a file in place). (b) Keep footprint writes plus a deny list and a read of the footprint from `main` (+~30 lines; leaves the class of "LLM writes its own grant"). (c) Keep as is (0 lines; sandbox escape stays).
4. Recommendation: (a). It removes the escape and the dirty-main-checkout land refusals together.
5. Scope: a yes changes phases 9, 10 and 18 and amends settled item 4. It does not change any other persona's grant.

**D2. Unconfined gates (M8).**
1. What is happening: `fgos land` runs the configured gates with `sh -c` outside any sandbox, on the code it is landing.
2. Cause: p-dkkodseo63 (a sandboxed seat cannot run Node tests) is why gates leave the sandbox (phase-07:28, PS-5).
3. Options: (a) Accept, and document the trust boundary in `routing-handoff.md`: landing runs reviewed branch code as the owner (0 code, ~10 doc lines). (b) Run gates through a confined seat with candidate-worktree writes and no network, once p-dkkodseo63 is fixed (a new item, days). (c) Restrict gates to the main checkout's scripts (it still runs the branch's tests; small gain).
4. Recommendation: (a) now, (b) as a separate backlog item.
5. Scope: a yes adds a doc line and a backlog row. It does not block this plan.
