# HARDEN T6 council, SPEED seat: Workflow (guide and case)

Seat lens: wall time a project using fgOS pays for workflows (Ship Faster, owner priority 1 of the product order), measured. Main `e8b5abc21` (baseline taken at `0291d40ed`), machine fg-server2, 2026-11-08 09:01 to 09:40 (Asia/Saigon). Every number below says the load average (1 minute, 24 cores) it was taken under. Load was not quiet: it was 2 to 4 at 09:01 to 09:05, then 10 to 38 from 09:06 on (another lane's full suite), so the numbers taken after that are marked "loaded" and are shape only. Nothing was dispatched to a real provider; the only fixture seats are the test suite's fake agents. No repo file changed except this report.

Citations used (glossed): RUL104 (rule "better, not bigger": every change makes the existing thing better without growing it); D-ADR0070 (decision: Workflow is a guide plus an admission ledger, the agent picks the order); owner decision 70 (2026-11-08: HARDEN runs T6 Workflow through the same per-layer loop); design principle 8 (one owning proof per behaviour, at the lowest layer that can observe it).

## Part A: target shape per component (speed view)

Rust: none of Workflow's components has a speed reason to move. Every measured cost is bytes read and parsed (97 percent of them copies), a duplicate read, or a seat launch; none is interpretive cost a language change would remove. Node cpu self time of `propose`: 731 ms inside `readSeatDirectory` (parsing result files), 563 ms in `readFileSync`, 338 ms parsing ledger lines. Removing the bytes removes 98 percent of it; a Rust parser would only make parsing the copies faster.

## Part B: findings

Severity bar: High = a measured cost that a user pays on every use of a route and that has a small local fix; Medium = measured and bounded, or High cost with a policy choice in the fix; Low = measured and small.

**W-1 (High, reproduced): `workflow propose` spends 83 percent of its time reading finished runs, twice.**
`createProposePorts.findInherit` (`propose.mjs:602-612`) walks every directory of `.fgos/workflow-runs` (the `.bindings` directory included), calls `readCaseProjection` as a guard (`:606`, result discarded), then calls `inheritFrom`, whose first act is the same `readCaseProjection` (`case-inherit.mjs:39`). Each call parses the whole ledger and then re-digests the reports of every completed step by reading unit-run result files (`playbookSubjectDigests`, `case-close.mjs:18`). Measured with the real functions, load 2.5: 985 ms per pass over 54 ledgers (345 ms parse, about 640 ms digests); two passes 1.97 s. cpu profile of the real route, load 4: `findInherit` 1 836 of 2 223 ms. Only 9 of the 54 ledgers have `case.opened`; the other 45 cannot be a source and still pay full cost.
Fix, in order of size: (a) delete the guard call at `:606` (inherit already throws the same refusal): -0.99 s, minus one line. (b) In `inheritFrom`, read the events and fold without digests, run the four events-only checks (closed, guide digest, request digest, base commit) first, and compute the digests only for a case that passes them (they are needed only to judge a milestone stale): about -0.64 s; the change moves a call, it does not add a path. (c) The ledger fix W-2 takes the remaining 345 ms parse to about 10 ms. Expected `propose` after (a) to (c): about 0.3 s (floor 0.21 s plus 0.1 s); not measured after, read-only seat.

**W-2 (High, reproduced): the ledger stores a second copy of every seat's run result, and 97 percent of that copy is one field nobody reads.**
`runner.mjs:505-520` writes `results: unitRunResult.results` into `unit.complete`; each result carries `runResult.evidence.attribution` (3 559 entries, 0.34 MB per seat) that no code in `src/workflow` reads (grep `evidence` and `attribution` in `src/workflow`: only guide text and an integrate digest). The full result already lives in `.fgos/assignments/<unitRunId>/<seat>/<n>/runs/<run>/result.json`. Evidence: 86 `unit.complete` lines hold 107.1 of the 110.3 MB of all ledgers; one live 4-seat unit this morning is 1.31 MB; removing `runResult.evidence.attribution` from each stored result gives 3.1 MB for all 54 ledgers (offline rewrite, python over the real files). What it costs a user: every `status` prints the copy (3.0 to 23.3 MB, W-4), every `advance.log` ends with a pretty print of the same state (326 MB, W-5), every append and `reread` parses it, the doctor row and `propose` read it (W-1, W-8), and it is why the retention row `p-tslryr3buq` keeps growing.
Fix: drop `evidence` from the stored result at the one writer (a `results.map` that omits one key, replacing the raw copy; about +3 lines in `runner.mjs`, no new mechanism). Consumers keep working: the fields they read (`seat`, `role`, `round`, `outcome`, `binding`, `commit`, `refused`, `runResult.executorId`, `runResult.policy`, `runResult.agentClaim.summary`, `runResult.settleReports`, `runResult.settledAt`, the verify and verdict markers) stay. Old ledgers stay readable (the new shape is a subset); their copies leave with retention (W-3). The simplicity seat's finding 6 proposes the larger change (per-seat summaries only); this smaller cut gets 97 percent of the bytes without touching any reader and is compatible with it. Not measured after the change.

**W-3 (Medium, reproduced): resolving one unit-run report parses every seat's result file, once per seat, on every `reread`.**
`resolveUnitRunRef` (`handoff-refs.mjs:100-117`) calls `readUnitRunHistory(unitDir)`, which parses every seat's `result.json`, to find the one report path of one seat; `digestUnitRunReports` asks once per seat, so a 4-seat unit parses 16 result files (about 0.5 MB each) to digest 4 small report files. `playbookSubjectDigests` does this for every completed step on every `reread` (about 4 per Unit) and in every admission read. Measured: 67 ms per full digest pass on the biggest real run (load 9.8, so an upper bound); 640 ms of the propose cost (W-1). The code lives in two T5-owned files (`unit-run-history.mjs`, `handoff-refs.mjs`), so the fix is one for T5's door with Workflow as the payer: read only the wanted seat's directory (`readSeatDirectory` already takes a seat id; it is not exported) instead of the whole unit run: 4x fewer parses, about -3 lines at the call site. With W-1(b) most of the pass disappears from `propose`; inside a run it is 67 ms per reread at worst, not a wall-time issue next to a Unit (see W-6), so I rank it Medium.

**W-4 (Medium, reproduced): `workflow status` prints the ledger's results, so an agent that checks progress reads megabytes.**
`statusWorkflow` returns `{ ...state, ... }` and `projectWorkflowState` copies `p.results` into every unit (`store.mjs:329`). Output sizes at this checkout: 3.0 MB (today's live run, one unit), 10.4, 18.9, 20.4, 23.3 MB. Time 0.47 s and 334 MB resident on the 10 MB ledger against 0.19 s and 107 MB on a small one (load 5.7). W-2 removes 97 percent of it (the 23.3 MB run becomes about 0.7 MB). Whether `status` should print per-seat results at all, when `seatProviders` already gives one row per seat, is a contract choice for the owner (Proposed 2); I do not cut it here.

**W-5 (Medium, reproduced): the detached advance logs its final state, which is the same copy a third time.**
`advance.log` of a run ends in the whole result of the foreground advance, pretty-printed (66 000 lines for the live run, 20 MB for the three October runs with real panels). It is 326 MB of the 435 MB under `.fgos/workflow-runs`, and `status` tails only the last 20 lines of 300 characters. W-2 shrinks it with the state (the final state is what is printed); nothing else to change, and I do not propose to stop printing it.

**W-6 (Low, reproduced): the Playbook runner's own overhead per step is small; do not move it or cache it.**
Counted in a two-step, two-Unit run (strace, load 11, shape only): 20 ledger appends (each one open, write, fsync), 43 whole-ledger reads (about 2 per append, because `appendWorkflowEvent` re-reads the ledger to number the line, `store.mjs:155`, and each `reread` reads it again), 0 process spawns and 16 fsyncs between Unit 1 and Unit 2, about 0.15 s. The Execution Core's Unit run in the same test: 39 to 68 spawns and 75 to 82 fsyncs, 1.5 to 2.6 s. So of a step with a 1.3 s fake seat, the runner is about 10 percent; against a real agent it is nothing. The only way the runner overhead grows is the ledger size (W-2): at 10 MB a read is 38 ms, so about 20 reads per Unit is 0.8 s late in a run. Fix: none beyond W-2. If a later change still wants the re-read gone, the hold (which proves the writer is exclusive) can carry the last number, about +4 -2 lines; not proposed now because W-2 makes it unnecessary.

**W-7 (Low, measured loaded): `loadTests` reads every test file of the checkout on every `propose` with a code slice.**
`createRepoPorts` (`propose-validate.mjs:110`) walks the tree and reads each test file under 512 KB the first time `findTests` is asked, once per process, so once per `propose`: 1 158 such paths in this repo. 886 ms at load 25 (loaded), 204 ms cold and 12 ms warm in the simplicity seat's run, and a code-slice proposal was 0.25 s slower than a docs-slice one at load 3.5. This is bounded by the checkout, so it is not growing with usage; leave unless the owner wants `propose` under 0.2 s.

**W-8 (Low, reproduced): the doctor row `workflow-case-bindings` reads every ledger, even with no binding record.**
`casesWithBindings` (`workflow-case-checks.mjs:32-48`) parses all ledgers to find those with a `binding` event: 345 ms warm over 54 ledgers (load 2.5), cold more. With W-2 it is about 10 ms. Keep every condition of the row (Doctor table).

**W-9 (Medium, reproduced): `.fgos/assignments` and `.fgos/workflow-runs` have no retention.**
1 405 MB in 529 assignment directories and 435 MB in 54 runs. Everything older than 7 days is 1 312 MB of the assignments and 356 MB of the runs (50 terminal runs); older than 14 days 1 193 MB and 356 MB. Reads that walk these trees (propose W-1, doctor W-8, `closedCaseIds`) grow with their count, and a tidy-up is the only thing that bounds them. This is the T5 arbitration's carry `p-tslryr3buq` (assigned to Workflow). A rule needs a number of days and a "never a run with a held lock" guard, which is policy, so it is in Proposed 1, not here.

**W-10 (Medium, reproduced): Workflow's test time is seat launches, and most of the launches prove something a pure function owns.**
Per-test times of `workflow-runner.test.mjs` (66 tests, 158.9 s duration, load 2.2 at start, 7.7 at end, one run): 23 tests over 3 s are 132 s. By behaviour:
- What a Unit is handed (`buildUnitHandoff`, pure over the folded state and the definition): tests at lines 304 (7.4 s), 873 (4.0), 938 (7.3), 985 (7.2), 1044 (14.1), 1346 (4.1), 1702 (4.2) = about 48 s. The copy and anonymize and own-seat resolution behaviours they also assert are owned by `test/runner/execution/handoff-refs.test.mjs` (about 22 tests, milliseconds). `buildUnitHandoff` has no direct test of its own.
- Persona and seat expansion (`seats.mjs` pure plus a dry bind): lines 1899, 1957, 1981, 2084, 2149, 2170 = about 38 s.
- The order every preset runs in: `playbook-observable-order.test.mjs` runs 8 presets and a units wave through 62 real fake-seat runs for 78.8 s (baseline, 1.27 s per seat) while `discussion-workflows`, `group-cognition-debate`, `business-discussion-workflow`, `architecture-advisory-workflow` and `advisory-m-contracts` run the same presets end to end again (57.6, 20.8, and the rest of the baseline's 78.0 and 15.4 s).
- Option flow (`--effort`, `--timeout`, `--account` reach the Unit): `units-runner.test.mjs` 24 tests, 85.8 s (baseline); `unitOverridesOf` is pure and already has `unit-handoff-raise-door.test.mjs`.
- Real clock waits: `playbook-proposer.test.mjs` sleeps 2.5 s inside the fake worker and then waits a fixed 3.5 s for it (`:247`); `waitForStatus` polls every 200 ms in `workflow-runner.test.mjs:419,442`. About 6 s of fixed clock in the first, the rest are polls.
Fix: move each of those behaviours to its owning pure function (Tests table) and keep one real-seat wiring proof per engine path; this does not weaken an assertion (the text assertions move with the case). Arithmetic estimate, not measured: about 40 s of 48 s, about 30 s of 38 s, and most of 78.8 s (an order guard that runs on a stubbed Unit run, Proposed 3) leave `workflow-runner` and `order-guard` time. The multiplier for every remaining launch is T5's 1.27 s per attempt (fsync, spawns, the test-only debug addon hash measured by the T5 speed seat); that layer is closed, so it is a carry, not a T6 change.

## Proposed additions (kept separate; owner picks; each names what it replaces)

1. **Retention rule for finished runs and their assignment trees** (W-9). Problem: 1.84 GB under `.fgos`, growing with every run, and every walk of it growing too. Evidence: 1 312 MB of assignments and 356 MB of runs are older than 7 days and terminal. Benefit: bounds disk and the cost of every read of those trees.
