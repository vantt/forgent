# HARDEN re-check, new component: Config door (`packages/config`) and `packages/herdr-fgos-common`

Pinned tree: `/home/vantt/projects/forgent-worktrees/harden-recheck-new` at `a5358f127`. Read-only audit by code-reviewer, 2026-10-29 (Asia/Saigon). Scope: the `fgos-config` crate, its addon namespace `packages/git/node-addon/src/config.rs`, `src/config/facade.mjs`, `src/setup/config-checks.mjs`, the Rust in-process readers that build a snapshot themselves, and `herdr-fgos-common`. I re-reviewed the pattern-catalog runner config only where it goes around the config door. I ran nothing: no cargo, no npm test.

**Verdict: DRIFT (16 small, 0 large). High 0, Medium 10, Low 6.** The crate itself is sound. It has no unsafe code, every write takes the holder lock and goes through Durable File, there are no panics on input, and the Windows gates refuse by name. The drift is in how other code reaches the crate. The same snapshot request is built in five places that disagree. The addon and the CLI give different answers for the same key, through two different trusted-root paths and two different detector sets. One Node setup module reads, and backs up, the config file by hand. The doctor reports legacy JSON twice. `herdr-fgos-common` keeps a second copy of the gateway's `fgos` command builder, and that builder falls back to a hard-coded `bin/fgos.mjs`.

## Layer placement, and why config depends on git

- **Core crate, default features: T2.** Its dependencies are `yaml-doc` (no fgos dependencies), `durable-file` and `canonical-json` (T0), and `holder-lock` and `identity` (T1; identity is built with `default-features = false` and only its writer-id types are used) (`packages/config/rust/Cargo.toml:6-16`). Nothing in a lower layer imports config. `fgos-git` depends on write-scope, durable-file, holder-lock and process (`packages/git/rust/Cargo.toml:7-13`). The edge `packages/git/node-addon/Cargo.toml:24` belongs to the combined addon crate, not to the git crate.
- **`host-provider` feature (only `apps/fgos` turns it on, `apps/fgos/Cargo.toml:15`): T3**, because it adds `fgos-git` (T2) and `fgos-host-runtime`.
- **The git edge is real but points down, so it is not an upward dependency (refuted).** Config uses git for one thing: finding the trusted main checkout. Spec §5 rule 6 says a `command` value comes from the main checkout's file, not from a linked worktree's copy. The CLI provider does this at `provider.rs:253` (`GitDriver::trusted_root_at`), and the addon does it at `node-addon/src/config.rs:190-198`. The edge sits behind the feature, so the addon, the gateway and work-state build config without git.
- **Upper-layer knowledge, as data only.** `bundle.rs:17-26` lists the sections that upper components own (runner, mailbox, gateway, herdr…), and `contracts/detected.v1.json` carries the claude executor template from the runner standard. Spec §4 and §8 make the section owner write that data, so I do not count this as drift.
- **`herdr-fgos-common` is a T9 surface client, outside the HARDEN layer table.** It depends only on config (`herdr-fgos-common/rust/Cargo.toml:13`). The crate does two unrelated jobs: it reads settings (`settings.rs`), and it is a CLI client that spawns `fgos` (`fgos.rs`). Its consumers are `herdr-dashboard` and `fgos-gateway`.

## Verified

- `#![forbid(unsafe_code)]` is set (`lib.rs:10`). Config files are opened no-follow through Durable File (`files.rs:65`, `machine.rs:19-25`). Writes take `project-config` or `global-config` through Holder-lock (`locks.rs:36`). Canonical JSON comes from the T0 crate (`migrate.rs:305`, `relocate.rs:11`). YAML comes only from `yaml-doc`. The crate has no hand-written atomic writer, no `/proc` read and no pid logic.
- No production code in `packages/config/rust/src` calls `unwrap`, `expect` or `panic!` on input. The one index on input, `kinds[0]` at `provider/unix_verbs.rs:239,245`, is safe because `patch_edits` refuses an empty list (`:141-142`). The two `unreachable!` calls (`provider.rs:294`, `unix_verbs.rs:343`) follow from the routing in `answer` and `run`.
- Windows and macOS: `write`, `doctor`, `migrate`, `repair` and `relocate` are `cfg(unix)`. Each has a non-Unix stub that refuses with `config-platform-unsupported` (`lib.rs:40-55`, `files.rs:98-108`, `provider.rs:36-45`, `node-addon/src/config.rs:398-408`).
- `src/config/facade.mjs` (75 lines) makes one door call per function. It has no JavaScript merge, no cache and no fallback, and objects come back without a prototype (`facade.mjs:42`).
- The doctor rows have one source, `packages/config/contracts/doctor-rows.v1.json`, read by both Rust and Node. That file is shipped in `package.json` `files`. Every registered check is wrapped, so a throw becomes a failed row (`registrations.mjs:191-196`).
- `herdr-fgos-common/settings.rs:54-63` reads only through `fgos_config::machine::project_snapshot`. Its fail-closed toggles and its fail-open `staticServing` are documented and tested (`:122-205`).
- `gateway.rs:106-134` reads the gateway section through the machine view and the token through `machine::token::read`. It reads no config file itself.
- The Node files that open a config file directly are limited to the one set in finding C5, plus the spec-sanctioned legacy `.fgos/gate-bypass.json` reads (`src/state/gate-bypass.mjs:78-100`, `work-state/rust/src/lib.rs:89-98`).

## Proposed additions (owner decides)

- **Bound the CLI spawns in `herdr-fgos-common` and the gateway.** Problem: `Command::output()` has no deadline (`fgos.rs:403,410`, `gateway.rs` `spawn_fgos_verb`), so one hung verb freezes the dashboard pane or holds a blocking-pool thread. Evidence: C12. Benefit: the dashboard stays live, and a stuck verb surfaces as `last_error`. Cost: a wait with a deadline, plus a kill through the process door.
- **Have the config door make the backup itself for `patch`.** Problem: C5 shows a caller wanting a pre-image before a bulk patch and producing it by hand. Benefit: a backup under `.fgos/runtime/config-migrate/`, created through Durable File's create-only install, exactly as migration does. Only worth it if the owner wants a pre-image for patches at all; the transaction already writes nothing on failure.
- **Teach the config-door guard about function-returned paths.** Problem: the guard does not see C5. Benefit: the next bypass is caught at commit time. Cost: more lexer logic in `architecture.test.mjs`. Alternatively, add the module to an explicit allowlist with its reason.
