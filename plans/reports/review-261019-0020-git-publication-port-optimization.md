# Review: Git Publication port optimization (b54842799..91aa212cf)

Read-only review of branch `git/p01-publication-perf` (worktree `.claude/worktrees/git-perf-review`, detached at `91aa212cf`), 21 files. I read the E3 report (`plans/reports/experiment-261019-0018-git-e3-after-port-optimization.md`), the full diff, the holder-lock spec §1/§5/§8 text, git spec §10 (rules 4a/4b, compaction line 346), plan rule 12a, and the surrounding code that the diff calls into (`control::unix_spawn_with_fds`, `Linux::lock_holders`, `durable-file::write_durably`, `Wal::scan`, `git_gate::check_wal`, `publication_preflight`). I checked two Git behaviours against Git 2.53.0 directly (in a scratch repo outside the workspace). I did not build or run the test suites, and nothing in the workspace was changed. This review is not in `plans/reports/` because the execution contract is read-only. The brief allowed that path only "if you can", so the full review is here instead.

**Verdict:** no Critical findings. There is one High: the Windows build breaks. There are seven Mediums. The most important ones are a durability regression in the WAL begin fast path, a Git candidate-check "optimization" that never fires on a changing CAS, and the drain reach assumptions that the holder-lock spec doesn't record. Fix the High and the Mediums before merge, or record owner decisions for M1 and M6.

## Critical

None.

## High

**H1. Windows build broken: `#[cfg(unix)]` now gates `std::time` imports.** `packages/holder-lock/rust/src/port.rs:16-17`.
The diff removed `use std::process::{Command, Stdio};` but left the `#[cfg(unix)]` attribute above it. The attribute now applies to `use std::time::{Duration, Instant};`. `Instant`/`Duration` are used in unconditional code: `BorrowIo::deadline` (line 376), `acquire` and `lock_until` (lines 498-523), and `acquire_traced` (lines 556-600). On `x86_64-pc-windows-msvc`, a native release target under RUL16, the crate therefore fails to compile. I verified this by reading the code. I could not compile it because the Windows target is not installed here. The E3 report's test and clippy runs were Linux-only, so they would not catch it.
Fix: delete the stray `#[cfg(unix)]` line. Add `cargo check --target x86_64-pc-windows-msvc -p fgos-holder-lock` (or the existing Windows CI job) to the lane's proof.

## Medium

**M1. The drain reach can miss holders that the spec still requires to be killed, and its assumptions are not in the spec.** `packages/holder-lock/rust/src/driver/flock.rs:243-262` and `:316-346`, `packages/process/rust/src/platform/linux.rs:639-681`, `packages/holder-lock/rust/src/port.rs:204-228`.
Spec §1 (line 27) says "no decision anywhere in the component is derived from a pid, a TTL, a start time". The §5 rule (2026-10-18) says "Any other holder of the description … is killed". The drain's candidate set now comes from pid allocation order, start time, and an allocation-rate bound (`ALLOCATION_RATE_BOUND = 4,000,000/s`). Answers to the brief's questions:
- *Fork without exec, setsid/double-fork escapees, pid namespaces nested below ours:* not missed. Each one is a new process after the mark, with a pid in our namespace past `ns_last_pid` and `start_ticks ≥ mark`. The test `setsid_escapee_after_an_earlier_proven_drain_is_still_killed` covers the setsid case.
- *Pid wraparound:* the span arithmetic handles wrap, and a full wrap is excluded only by the time bound (`pid_max/4e6` s, about 1.05 s at `pid_max=4194304`, about 8 ms at 32768). This is a heuristic, not a kernel guarantee. Pids allocated out of order are also missed: `clone3` `set_tid` and writes to `ns_last_pid` (both need `CAP_CHECKPOINT_RESTORE` or `CAP_SYS_ADMIN`) can place a new process below the floor. That is Low on its own.
- *Clock/boottime granularity:* sound. `boot_ticks_now` truncates and subtracts one tick, `starttime` truncates `start_boottime` in the same `USER_HZ` and time namespace, and since Linux 5.5 `start_boottime` is set after `copy_files`.
- *A holder that got the description before the floor point:* missed by design. The premise "a description is only ever copied across fork" is false while a borrowed child runs arbitrary code (git, hooks). That code can pass the description by `SCM_RIGHTS` to a process that already existed, or a same-uid process can take it with `pidfd_getfd`. The old full fd scan found and killed such a holder. The new drain returns `Ok`, so the holder releases while a foreign process still shares the locked description. The same failure happens if the rate bound is ever exceeded.
- *Proof-boundary race (new, and now permanent):* a holder created after the old floor forks a child. `copy_files`, `alloc_pid` and `start_boottime` all happen before the next proof's mark, but `attach_pid` happens after that proof read the range. Meanwhile another thread of the holder closes its fd. The proof then sees no holder and moves the floor past the child's pid and start, and every later drain excludes the child. Under the old full scan this miss was transient. The window is narrow, and a SIGKILLed parent aborts the fork, but the floor turns a one-time miss into a permanent one.
Fix (owner decision): record the inheritance premise, the rate bound and the `SCM_RIGHTS`/`pidfd_getfd` exclusion in holder-lock spec §5 as a decision that supersedes the line-27 wording. If the owner wants the old guarantee, keep `Reach::Since` for per-spawn drains but use `Reach::Everyone` at the two points that decide safety: `validate_quiescent` before Intent, and the last drain before release. For the race, lag the floor by one proof: set `since` to the start mark of the previous successful proof, not the current one. A process in flight during proof N is then created after proof N-1's mark and is read by proof N+1.

**M2. The `rev-list` candidate fast path never runs on a changing CAS.** `packages/git/rust/src/publication.rs:1029-1044`.
The arguments are `rev-list --objects --missing=error --end-of-options <oid>^{commit} --not <expected>`. Git 2.53.0 refuses that order: `fatal: option '--not' must come before non-option arguments` (exit 128, checked against this repository). The fallback hides the error, so every candidate check with `expected = Oid` (every CAS after a ref's first) spends one failing Git child and then runs the old type read and full history walk. Correctness holds, but the report's claims are wrong: the census says CAS changing went 18 → 10, and the report says walk cost "follows the new objects, not the length of the stream". In fact a walk still grows with the stream, and the extra child costs latency on the failing budget line.
Fix: use `"--end-of-options", &peeled, &format!("^{expected}")`. `^`-revisions are allowed after `--end-of-options`. Alternatively, put `--not <expected> --not` before `--end-of-options`; I verified that order works. Add a test that asserts the fast path decides, for example by checking the child count or by asserting the fallback is not taken for an intact candidate. Separately, record in the spec that the check trusts the history at the expected tip, as Git's connectivity check does (Low).

**M3. The WAL begin fast path returns `Existing` without making record zero durable.** `packages/git/rust/src/wal.rs:660-674`, with `:626-630` and `packages/durable-file/rust/src/lib.rs:256-261`.
Before this change, a same-id caller that lost the install still reached `write_durably`'s directory sync, with the WAL root added for record zero. The code says why: "a preceding failed creator may have installed the name without ever syncing it". The new path checks `try_exists()`, calls `inspect`, and returns `Existing` with no fsync. Operation directories are now also created without a sync. Under the seal, a live concurrent creator is impossible, but a creator that died between `link` and the directory fsync is possible. The next caller (`publication.rs:1389`, which calls `recover`) can then append `AbandonedBeforeAttempt`, which fsyncs only the operation directory and not the WAL root, then compact and return a receipt. A power loss can still drop the operation directory, so the id binding is lost and a later same-id request would execute. That breaks §10's rule that a record is durable before the next effect, and rule 1's id binding.
Fix: in the fast path, call `sync_directories(&[dir, root])` before returning `Existing`. That costs one journal commit and only on the replay path. Add a crash-boundary test for this case.

**M4. The floor-verdict record's key is incomplete and is built differently from the existing config-path discovery.** `packages/git/rust/src/driver.rs:772-815` (reader `:216-249`).
(a) The key guesses system-config paths (`/etc/gitconfig`, `<git prefix>/etc/gitconfig`). The existing `publication_preflight` (`driver.rs:403-405`) says "a custom Git prefix must never be guessed" and asks `git var GIT_CONFIG_SYSTEM/GLOBAL`. That gives two sources of truth (design principles 1 and 7).
(b) `include`/`includeIf` targets of those files are not stamped.
(c) `PATH` is not in the key. `PATH` is inherited (`Scrubbed` drops only `GIT_*`), and the `hook-run` probe runs a hook through it.
(d) The key has no fgOS build or probe-code identity, but the state root is machine-scope and shared across releases. A record from a release with different probe code and the same probe names is reused. The reader also accepts any probe set where every probe passed, without checking it equals the contract's `requiredProbes`.
Fix: add the host build version and a probe-code version constant to the key. Require the record's probe names to equal `requiredProbes`. Take config paths from the `git var` answer when it is cached, and stamp include targets or say why they don't matter. Add `PATH`. Document `git-floor-verdict.json` in the git spec's state-root section.
*Doctor:* not required by the install/setup/doctor gate. The file is an optional cache, and missing or different means "probe again", so nothing expects it to exist. No new doctor check is needed. A spec line and the CHANGELOG are enough.

**M5. A C5 scan during compaction refuses with `git-wal-unreadable` because the scan treats a compacted id as an error.** `packages/git/rust/src/wal.rs:1452-1531`, reached from `packages/distribution/rust/src/git_gate.rs:22-30`.
`entry.metadata()?` (`:1473`) and `fs::read_dir(operation.path())?` (`:1517`) abort the whole scan when the operation directory disappears. When compaction is partly done, `inspect` on a chain that is losing its records fails and becomes an entry error, and `check_wal` refuses on any entry error. Refusing on unknown state is correct, but this state is not unknown. Under plan 12a, the ledger entry is installed and fsynced before the directory removal starts, so an id with a ledger entry is terminal whatever its directory looks like.
Minimal fix, in `Wal::scan` only, with no C5 policy change: when any error or `NotFound` occurs for a root entry, read `self.compacted(&id)` again. If it returns `Some`, record the entry as terminal with no error and skip the byte count; the ledger pass counts it. Otherwise keep the error. Add a test that runs a scan against a concurrent compaction loop.

**M6. `recover` of a compacted id now refuses, which is a contract change the spec does not record.** `packages/git/rust/src/publication.rs:871-888` and `:376-420` (`RECENT_TERMINAL = 4`), `wal.rs:1082-1130`.
Spec §10 (line 346) says compaction retains the "durable terminal receipt". The ledger entry keeps an outcome summary (`r`) but not the expected value, so `recover(id)` cannot rebuild a receipt. Compaction now runs at every admission, so `recover` stops working for an id after four more publications on its ref. The phase 06 `inspectOperation` builds on this behavior. Compaction itself is correct: it touches only terminal chains (`outcome().is_some()`), the id stays bound (`begin` consults the ledger), and a replay with the same request returns the receipt while a different request is refused (tested).
Fix (owner choice): store `expected` (and `next`) in the ledger entry, which fits within 512 B even for two sha256 oids, so `recover` returns the full receipt. Otherwise amend spec §10 and the Publication API doc to say that a compacted id answers only to a replay. Separately, 12a requires compaction "inside a later Publication call", not on every call. Batching (compacting only when more than N chains are retained) is allowed and is an owner trade-off against the 60 ms budget; the report presents it as a contract change.

**M7. The loose-object durability memo can skip a needed directory fsync after inode reuse.** `packages/git/rust/src/publication.rs:770-819`.
The memo key is `(dev, ino)` of the loose file, kept for 600 s. Suppose an object is removed (gc, `prune-packed`) and the same oid is written loose again within that time. ext4 readily reuses the freed inode number, so `durable()` answers true and the fan-out and `objects/` fsyncs are skipped. A ref can then be published that points at an object whose directory entry is not durable. The WAL memo (`wal.rs:1023-1038`) adds birth time to its key for exactly this reason.
Fix: add birth time (or ctime with nanoseconds) to the key and share one identity helper with `durable_key` (DRY).

## Low

- **L1** `port.rs:205-213`: `declare_domain`'s doc comment is now attached to the new `fn since()`, so `declare_domain` has no doc.
- **L2** `wal.rs:1040-1041`: empty `impl Directory {}` left behind.
- **L3** `durable-file/src/lib.rs:101-106`: every record install spawns a thread, even when `alongside` is the no-op. Taking an `Option` and spawning only when there is work would be simpler and cheaper.
- **L4** `process/src/mapped.rs:451-473`: PATH lookup with `access(X_OK)` accepts directories. It also resolves empty or relative PATH entries against the parent's cwd, not the requested child cwd, and does not fall back to `/bin/sh` on `ENOEXEC`. That differs from `Command`/execvp, so a spawn can fail spuriously. Borrowed argv is normally an absolute git path, so the impact is small.
- **L5** DRY: `Tree::in_borrow_domain` duplicates `in_borrow_domain`, `capture_available` duplicates `capture_chunk`, and `read_relation_and_leader`'s stat parsing sits beside `parse_proc_stat`/`parse_relation`.
- **L6** The pid-order path (`linux.rs:639-681`) and the start-time path (`flock.rs:1510-1525`) disagree on the owner's direct children: only the start-time path includes `parent == owner`. The two reaches should match, or the difference should be explained.
- **L7** `publication.rs:418-420`: compaction errors at admission are discarded. A compaction that keeps failing costs every call and is visible only as retained bytes. Surface it in a trace or doctor fact.
- **L8** Test gaps: the start-time fallback (a mark older than the window, an unreadable range), the proof-boundary floor, the begin fast-path durability, whether the rev-list fast path is taken, and a scan racing compaction.
- **L9** Docs (L5 q6): there are no spec or CHANGELOG updates for the new persistent `git-floor-verdict.json`, for `recover` refusing compacted ids, or for the holder-lock reach rule.
- **L10** `scripts/git/e3-bench.mjs:466-473`: the rollback check now verifies by replaying `compareAndSwap`, which writes WAL records, instead of a read-only `recover`. It still counts a lost id as a Loss and therefore as lost, but the verifier is no longer read-only.

## Focus items answered

1. **Drain floor:** see M1. It is exact for fork, setsid, double-fork and nested namespaces. It is not exact for fd passing to existing processes, out-of-order pid allocation, or a breach of the rate bound. The proof-boundary race becomes permanent. The clock handling is sound.
2. **posix_spawn path (`mapped.rs`):** at parity with the old `Command` path. No new fd leak: the close list comes from the same `inheritable_fds()` snapshot taken in the parent, just as before. Sources and pipe ends are `O_CLOEXEC`. Stdio dup2s come before slot dup2s, and sources sit above every slot. The signal mask is emptied and `SIGPIPE` reset to default, as `Command` does. The process group is set with `SETPGROUP 0`, and neither path creates a session. Exec failure is reported synchronously by glibc's `CLONE_VFORK` posix_spawn (tested). Containment is unchanged, since the borrow path had none before either. glibc 2.29 `addchdir_np` is within the 2.35 ceiling. Non-gnu targets use the `Command` path. Only L4 differs.
3. **WAL:** each record still gets a file fsync, a no-overwrite install and a directory fsync before the next effect. The ref chain synced "alongside" is ordered correctly: the name is installed only after both syncs finish. The skeleton memo is per-process and keyed with birth time, so it cannot skip a sync after a rename, unlink or recreate, or across processes. The exception is M3, the begin fast path.
4. **Compaction:** terminal chains only, and ids stay bound. Replay returns the receipt and a different request is refused. `recover` of a compacted id differs from spec line 346 (M6). The C5 scan failure is a scan bug with a minimal fix inside `Wal::scan` (M5).
5. **Git child reduction:** no TOCTOU or ABA weakening. The target and pin CAS are still exact-old, no-deref, single-ref, with read-back. The preflight read happens right after the TargetAttempt record. `show-ref --exists` returns 0 for a dangling symref and 2 for a missing ref (verified on 2.53.0). The listing-first `read_ref` still finds dangling symrefs. Transfer reads the ref once. The rev-list path is broken but fails safe (M2).
6. **Floor cache:** the key is incomplete (M4). It needs no doctor check, only spec and CHANGELOG lines.

Tests are real: I found no environment switches or test-only branches. Windows: see H1.

## Unresolved questions

- M1: does the owner accept the fork-only inheritance premise and the rate bound as recorded holder-lock law, or should release and admission keep a full scan?
- M6: should `recover` of a compacted id return a full receipt (with expected stored in the ledger), or should the spec say that only a replay answers?
- Should compaction stay per-call (12a allows batching), given that it alone puts CAS changing over its 60 ms budget?
