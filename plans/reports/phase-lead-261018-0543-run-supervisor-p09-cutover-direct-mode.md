# Phase report: run-supervisor p09, cutover of the direct mode

Status: DONE_WITH_CONCERNS. Branch `run-supervisor/p09-cutover`, merged into `run-supervisor/integration` (see the done file for the head).

## What changed
- `executeAssignment` (cli-spawn) follows the 9.4 order: attempt lock (rank 15), cwd lease for a writing agent (rank 30) in one `LockScope`, then prepare, immutable envelope v3 + 0600 side file, `fgos internal supervise` spawned detached with the lock descriptions at fd 3/4 (`spawnWithLocks`, new in the holder-lock facade), wait for `supervisor-binding.json`, close the controller's copies at once and in `finally`. After the binding the controller only reads: live output from the capture files, the answer from `result.json` written by the settle step. No `settleRunOutcome`, no `finalizeConfinementResources`, no signal in the controller. New module `src/run-supervisor/direct-launch.mjs`.
- Removed: `detached-run-supervisor.mjs` (Node supervisor, IPC, `process.send`), `reconcile-cli-spawn.mjs`, `bindConfinedHomesToSupervisor`, `legacySpawn`, `useSupervisorRecovery`, the envelope branch of `cliSpawnAdapter`, `settleReceiptRunFromOutcome`/`settleFailedRunFromOutcome`, the cwd heartbeat, the old `scripts/bench-receipt-latency.mjs`. `rg 'startDetachedRunSupervisorProcess|runDetachedRunSupervisor|bindConfinedHomesToSupervisor|legacySpawn|useSupervisorRecovery|process\.send' src` is empty; `reapOrphanedConfinementResources` is called only from `src/run-supervisor/sweep.mjs`. Both are asserted by `direct-cutover.test.mjs`.
- Rewired: admission (`isCliSpawnRunStillWorking` = adopt probe, fails closed), resume (an attempt with an envelope goes to `adoptRun`, never a second agent), `fgos dispatch reconcile` (prints the adopt answer), `visibility-session`, `runtime-inspection` (bound = binding file).
- Marker v2 is written by the bwrap driver at prepare (`attemptId` reaches the driver through the confinement request; new request keys `attemptId`, `launchMode`, `gateCommand`, `attemptBinds`). P10's pane-less writer is gone (P10 and P09 land together).
- Carry-over items: step env (PATH, HOME, `FGOS_*`, state root) in every `steps[].env`; `createdAt {bootId, boottimeNs}` and `cwdLeaseFile` in the Windows envelope; `dispatch.gateKillGraceMs` and `lock.predecessorKillWaitMs` written into the envelope (`gateKillGraceMs`, new `deadlines.killWaitMs`); `supervise` refuses a second supervisor for an attempt that has a binding or receipt (exit 71 `attempt-already-bound`, before any lock) ; run.json, assignment.json (effective), evaluator baseline and capture paths exist before spawn.
- Rust: `ContainmentDomain::set_empty_wait` replaces the fixed 5 s of the three drivers; gate writes a pre-bound empty `gate-exit.json` in place; gate ends a missing agent as exit 127/126 with the reason in the capture stderr; supervisor enforces `launch.maxOutputBytes` (the old `maxBuffer`) with stop cause/receipt outcome `output-limit`; gate starts the agent at `/` when the sandbox hides its cwd.

## Facts found while running the real thing (not in the plan)
1. The gate runs inside the sandbox and the sandbox root is read-only: it could not create `gate-exit.json` or open the capture files (every confined run settled `gate-lost`). Fix: the controller creates the three files empty, the driver binds exactly those files writable, the gate fills `gate-exit.json` in place. Spec section 3/4 and the envelope contract say so.
2. The driver's `bwrapPrefix` carries no program, while the Rust `BwrapPidns` takes `bwrapPrefix[0]` as the bwrap path. The controller puts the sandbox program first.
3. The settle step needed what only the controller knows (effective assignment, policy, provider account evidence, fallback, stray-write baseline of the main checkout, run-control token). New `controller/settle-context.json` and `runs/NN/assignment.json`; the step reads them.
4. The supervisor still runs the steps (and holds the attempt lock) after `result.json` appears. The controller now waits for `closed.json` (bounded, 60 s) so the next dispatch never meets a step in flight; without it admission read `running` and a resume raced `finalize-home`.
5. P10 regression found and fixed: `runUnit` ran the orphan sweep after `resolveGitRoots`, so a directory that is no checkout skipped the reap (`fgos run reclaims a private home ...` was red on the integration tip).
6. Payload check: a host with no release manifest next to it (a raw `FGOS_HOST_BIN`, every dev and test host) made every step exit 66. A host that exists but has no manifest is now a development host: the payload that started the controller is the one the envelope names and the step accepts only its own root. A release host stays held to its manifest. Decision, recorded in the spec's known limits.

## Callers of cliSpawnAdapter's non-envelope branch (kept, r6 9.9)
`rg -n "cliSpawnAdapter|EXECUTOR_ADAPTERS\[" src`: the adapter is registered in `transport.mjs`, looked up only in `confinement/authority.mjs:1007` (`executeThroughConfinement`). Its callers: `executeExecutorCli` (cli.mjs: account probe, goal-check, judge, task executors), whose agent lives and dies with the calling process. Every agent of a unit goes through the supervisor, including the loop's `spawnWorker` (it runs `runUnit` -> `executeAssignment`). The adapter docstring says so.

## Decisions
- Controller waits for `closed.json` after the result (fact 4); supervisor-less attempts are waited for through adopt.
- Payload check relaxed for a development host (fact 6).
- Attempt files bound into the sandbox instead of moving the contract paths (fact 1): smallest change, no reader moves.
- `launch-unknown` is thrown as `RunnerConfigError` (`code: launch-unknown`); a supervisor that ended early is first offered to adopt and its settled answer is returned when there is one.
- Control token: kept (not released) once the supervisor owns the attempt, released when the result was seen or nothing was handed over; a settle refused for a superseded token is reported as `run-control-superseded`.

No production caller reaches the envelope writer any more; tests still drive it. Removal is a separate cleanup (needs the herdr reconcile tests moved first).

Not caused by this phase (red on the integration tip with the same host binary): `test/state/hot-lock-host-judge.test.mjs` and `test/setup/skill-wrappers.test.mjs`. `test/rust-host/fgctl-upgrade.test.mjs` timed out once (600 s) in the first run: the fgctl trap of the common rules (shared `target` link), not reproduced later. The full suite was never green in a single run on this loaded machine; every failure of the last run passes alone.
3. Matrix cases 4-6 are timing-heavy under load; they were hardened (longer waits, 12 s deadline) but a very loaded machine can still stretch them.
4. Windows controller path (release locks after spawn, `cwdLeaseFile`) is untested; macOS likewise. The Windows lease window is a documented known limit.
5. Red-first: the nine matrix cases were written alongside the code and their failures drove the fixes (gate-lost on a read-only root, stale control, unfinished steps); there was no separate red run against the old code, which no longer exists on this branch.
