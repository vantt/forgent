### contributor-guidelines-pr-rejection

Skill content changes require using `superpowers:writing-skills`, adversarial pressure testing, and before/after eval results — the project has "carefully-tuned content (Red Flags tables, rationalization lists, 'human partner' language)" that resists modification without evidence.

### porting-to-a-new-harness-guide

- **What:** `docs/porting-to-a-new-harness.md` is a long (~828 line) prescriptive guide for adding a new coding-agent runtime (harness) to Superpowers, teaching invariants over specific mechanisms since "the integration mechanism differs across harnesses, and it will keep changing."
- **Where:** `docs/porting-to-a-new-harness.md`.
- **Notable:** Defines the core architecture as three components: (1) **Skills** (harness-agnostic, in `skills/`, written to name *actions* not tools — "invoke a skill", "dispatch a subagent" — never a specific tool name); (2) **Tool mapping** (per-harness, in `skills/using-superpowers/references/<harness>-tools.md`); (3) **Bootstrap** (per-harness, injects the full `using-superpowers/SKILL.md` wrapped in `<EXTREMELY_IMPORTANT>` tags at every session start — "The bootstrap is the entire integration. Without it, the skill files are inert"). Defines a **hard requirement**: automatic session-start injection with no per-session human opt-in — "If the only way to get Superpowers in front of the model is for your human partner to opt in each session... the harness cannot be properly supported." Three named integration "Shapes": **Shape A** (shell-hook, e.g. Claude Code/Cursor — a command run at session start whose stdout is read as JSON, dispatched via a polyglot `run-hook.cmd` wrapper), **Shape B** (in-process plugin/extension with lifecycle callbacks, e.g. OpenCode/Pi — bootstrap injected as a user-role message, never a system message, to avoid token bloat and multi-system-message model breakage), **Shape C** (instructions-file, e.g. Gemini — an extension-declared always-loaded context file, never a user's own global config file). A definition of done (6 numbered criteria) and an acceptance test identical to the one in CLAUDE.md ("Let's make a react todo list" must auto-trigger `brainstorming`). Appendix A is a living reference table of all 8 current harness integrations (Claude Code, Codex, Cursor, Copilot CLI, Gemini CLI, Kimi Code, OpenCode, pi) with entry point / bootstrap mechanism / tool mapping / tests / distribution channel columns. Appendix B lists 12 "Gotchas that have bitten porters" (e.g. "Opt-in isn't a port," "Wrong JSON field → silent failure or double injection," "Editing skills to fit the harness. Never.").
- **Keywords:** Shape A/B/C, bootstrap injection, tool mapping, `EXTREMELY_IMPORTANT` wrapper, acceptance test, polyglot hook, session-start hook.

### windows-polyglot-hooks

- **What:** `docs/windows/polyglot-hooks.md` documents the cross-platform hook dispatch mechanism (`hooks/run-hook.cmd`) that lets one hook script work identically on Windows CMD/PowerShell/Git-Bash and Unix shells.
- **Where:** `docs/windows/polyglot-hooks.md`; implementing file `hooks/run-hook.cmd` (declared authoritative — "When this document and the code diverge, trust the code").
- **Notable:** `run-hook.cmd` is a **polyglot script** — one file valid as both a Windows batch script and a Unix shell script simultaneously, using a `: << 'CMDBLOCK'` heredoc trick so Unix shells skip the batch block as a no-op while CMD.exe executes it directly. Windows tries three bash locations (`C:\Program Files\Git\bin\bash.exe`, `(x86)` variant, then PATH) and exits silently (code 0) if none found — degrading gracefully rather than breaking the plugin. Hook scripts are deliberately **extensionless** (`session-start`, not `session-start.sh`) because Claude Code's Windows handling auto-prepends `bash` to any command containing `.sh`, which would double-invoke the wrapper. Documents that Claude Code as of v2.1.81 supports a `"shell": "bash"` hook config key forcing the Git-Bash route (older versions silently ignore the unknown key) — this was introduced in v6.2.0 per RELEASE-NOTES to fix PowerShell parser errors (#1751) and CMD.exe quote-stripping around metacharacters (#1918).
- **Keywords:** polyglot script, extensionless hook script, Git-Bash resolution, `hookSpecificOutput`, `.sh` auto-prepend bug.

### testing-split-tests-vs-evals

- **What:** `docs/testing.md` documents a deliberate two-tier test architecture: `tests/` (plugin-infrastructure, non-LLM code) vs `evals/` (LLM skill-behavior compliance, via the "drill" harness).
- **Where:** `docs/testing.md`; supporting spec `docs/superpowers/specs/2026-05-06-lift-drill-into-evals-design.md` and its paired plan `docs/superpowers/plans/2026-05-06-lift-drill-into-evals.md`.
- **Notable:** `tests/` = bash+node+python integration tests for brainstorm-server JS, OpenCode plugin loading, codex-plugin sync, analysis utilities — run via `run-*.sh` or `npm test`. `evals/` = Python harness ("drill") that drives **real tmux sessions** of Claude Code / Codex / Gemini CLI / Copilot CLI, with an LLM actor simulating the user and an LLM verifier judging transcript compliance; scenarios live in `evals/scenarios/*.yaml`; quick-start is `cd evals && uv sync --extra dev && export ANTHROPIC_API_KEY=... && uv run drill run <scenario> -b claude`. Drill scenarios are explicitly "slow (3-30+ minutes each)" and real-money LLM runs, "not part of CI today." The `evals/` directory used to be a git submodule pointing at a separate `obra/drill` repo, then (per the 2026-05-06 spec/plan) was fully absorbed ("lifted") into the superpowers repo proper via `rsync` with explicit excludes (`.git`, `.venv`, `results`, `.env`, `__pycache__`, `*.egg-info`) — the standalone `obra/drill` repo is slated for post-merge archival, and the Python package internally kept the name `drill` even though the directory is `evals/`. A **deletion gate** protocol: an old bash test is only deleted if a subagent, given both the bash test's assertions and the candidate drill scenario's YAML, verifies every assertion has a matching drill check — output is a per-assertion PASS/FAIL table, and the subagent's verdict is quoted in the deletion commit message as an audit trail.
- **Keywords:** drill harness, LLM actor/verifier, tmux-driven session testing, subagent-gated test deletion, submodule-to-monorepo lift.

### subagent-driven-development-evolution

- **What:** `subagent-driven-development` (SDD) is the most heavily iterated skill in the corpus — at least 5 major redesigns are documented across plans/specs spanning 2026-01 through 2026-07: document review system (Jan), task-scoped review dispatch (Jun 9), strict-cost experiment ladder (Jun 10), plan-scoped workspace (Jul 6), fix-loop redesign (Jul 15).
- **Where:** `docs/superpowers/specs/2026-01-22-document-review-system-design.md` + paired plan; `docs/superpowers/specs/2026-06-09-sdd-task-scoped-review-dispatch-design.md` + paired plan; `docs/superpowers/specs/2026-06-10-strict-cost-sdd-design.md`; `docs/superpowers/specs/2026-07-06-sdd-plan-scoped-workspace.md` + eval-results doc + paired plan; `docs/superpowers/specs/2026-07-15-sdd-fix-loop-redesign-design.md` + paired plan.
- **Notable — chronological arc:**
  - **Jan 2026 (document review system):** added spec/plan document reviewer subagents with iterative review loops (5-iteration escalation cap) — this was later **reversed**: RELEASE-NOTES v5.0.6 (2026-03-24) replaced the subagent review loop with an "inline Spec Self-Review checklist" because regression testing showed identical quality scores at ~1/50th the time (30s vs 25min).
  - **Jun 9, 2026 (task-scoped review dispatch):** root-caused per-task quality reviewers doing "branch-review-scale work on single-task diffs" (7/8 quality reviewers in one real session ran repo-wide greps; one ran 50+ Bash commands over ~200s) because the quality-reviewer prompt inherited a merge-readiness template ("Ready to merge?"). Fix: made `code-quality-reviewer-prompt.md` self-contained and diff-scoped, added a third spec-reviewer verdict channel (`⚠️ Cannot verify from diff`), added controller guidance against writing open-ended reviewer directives or pre-judging findings.
  - **Jun 10, 2026 (strict-cost ladder, `2026-06-10-strict-cost-sdd-design.md`):** an explicit **experiment ladder** (L1-L5) targeting dollars-per-run with a stated "Hard invariant: quality" and "Judgment guardrail: cheapen mechanics, never judgment." Documents real gate outcomes: L2 (cheap controller model) **died at the gates** — under a sonnet controller, the per-task quality gate "collapsed into plan-compliance advocacy," a planted defect shipped in 4/5 runs; L3 (cheap reviewer model) also **died** — haiku reviewers "cleanly flagged 0 of 10 planted defects at correct severity." Final adopted config cut go-fractals scenario cost from ~$16/run baseline to ~$12-14/run (~20-25% typical savings) via: merging spec+quality reviewers into one `task-reviewer-prompt.md` with two verdicts, required explicit `model:` line on every dispatch, task-brief/report files instead of pasted text, a progress ledger surviving compaction, one omnibus final-fix dispatch instead of per-finding fixers.
  - **Jul 6, 2026 (plan-scoped workspace):** fixed a structural bug where `.superpowers/sdd/progress.md` had no plan identity, so a follow-up plan in the same working tree would read a *different* plan's ledger as its own progress (observed in the wild: a worktree accumulated 68 files across 3 plans, requiring ad-hoc side-band filenames like `progress-p2.md`). Fix: workspace becomes `.superpowers/sdd/<plan-basename>/`, ledger's first line names its plan (`# SDD ledger — plan: <path>`), workspace is `rm -rf`'d once final review is clean. **Notable finding in the eval-results doc:** the RED baseline test (25 fresh-subagent reps across 3 fixture framings) found controllers **never actually adopted a stale foreign ledger blindly** — they always caught it via forensic git-log cross-checking, at a measured cost of 6-13 tool calls per resume (mean 9.0). The maintainer signed off on shipping the fix anyway on **structural grounds** (the fixture-iteration process itself is a documented case study: fixture v1 had fabricated commit hashes agents dismissed on sight, v2 had matched task counts but stub-code implementations agents ruled as "false records," only v3 — real implementations, rotating commit authors, resolvable hashes — produced a valid test).
  - **Jul 15, 2026 (fix-loop redesign):** resolved a **three-way self-contradiction** in the skill about who fixes review findings (process diagram said dedicated fix subagents; Red Flags said "Implementer (same subagent) fixes them"; implementer-prompt.md assumed re-engagement). Final design: resume the original implementer for fix rounds 1-3, escalate to a fresh implementer on a more capable model for rounds 4-5, five-round circuit breaker with controller adjudication at the cap (never earlier — "Adjudicating earlier to end a loop is pre-judging with a different name"), scoped re-reviews (verify findings + check only the fix diff, not a fresh full review). New file `re-review-prompt.md`. Ledger line formats become a strict grep-able contract (`Task <N>: complete (commits <base7>..<head7>, review clean)`, `Task <N>: fix round <R>/5 (...)`, `Task <N>: parked — <finding> — ruling: <why>`, `Task <N>: BLOCKED — <reason>`).
- **Keywords:** SDD, review-fix loop, circuit breaker, progress ledger, plan-scoped workspace, task-reviewer-prompt.md, resume-the-implementer, judgment guardrail, RED/GREEN eval gate.

### visual-brainstorming-companion-evolution

- **What:** The "visual companion" (a local browser UI the brainstorming skill can open alongside the terminal) went through at least 4 major design iterations, moving from a blocking architecture to a hardened, authenticated, zero-dependency server.
- **Where:** `docs/superpowers/plans/2026-01-17-visual-brainstorming.md` (original, in `docs/plans/`), `docs/superpowers/specs/2026-02-19-visual-brainstorming-refactor-design.md` + plan (non-blocking refactor), `docs/superpowers/specs/2026-03-11-zero-dep-brainstorm-server-design.md` + plan (dependency removal), `docs/superpowers/plans/2026-06-09-visual-companion-issues.md` (issue/PR triage catalog), `docs/superpowers/specs/2026-06-10-visual-companion-auth-hardening-design.md` + plan, `docs/superpowers/specs/2026-06-11-visual-companion-final-hardening-fixup-design.md` + plan.
- **Notable — arc:**
  - **Original (Jan 2026):** Express/ws/chokidar-based server, blocking `TaskOutput(block=true, timeout=600s)` feedback pattern, `sendToClaude()` JS function posting user choices back.
  - **Feb 2026 refactor ("Browser Displays, Terminal Commands"):** removed the blocking pattern entirely — "Claude Code's execution model is turn-based. There is no way for Claude to listen on two channels simultaneously within a single turn." Replaced with: browser = interactive display only, terminal = conversation channel; user interactions recorded to a per-screen `.events` JSONL file that the agent reads on its *next* turn. Deleted `wait-for-feedback.sh` entirely.
  - **Mar 2026 (zero-dep rewrite):** replaced ~1,200 lines of vendored `node_modules/` (Express/ws/chokidar, "714 tracked files") with a single ~250-300 line `server.js` using only Node built-ins (`http`, `crypto`, `fs`, `path`), including a **hand-rolled RFC 6455 WebSocket implementation** (handshake via SHA-1 + magic GUID, 3-tier frame length encoding, opcodes TEXT/CLOSE/PING/PONG only — binary frames/fragmentation/extensions deliberately unsupported). Motivation stated as supply-chain risk reduction, not a functional bug.
  - **Jun 9, 2026 (issue catalog, `docs/superpowers/plans/2026-06-09-visual-companion-issues.md`):** a single triage document distilling every open GitHub issue/PR touching the companion into "the underlying problem and the change we'd make," each grounded against actual code with file:line references. Explicit **decision**: reject a Host-allowlist security fix in favor of a per-session secret-key model, because "A direct remote client just sends the expected `Host`... the allowlist is theater for remote exposure" — documents the project's threat model reasoning directly in-doc (superpowers is used with remote binds, SSH tunnels, Tailscale). One item explicitly dropped: vendoring Alpine.js for interactive mockups (PR #1639) — "we are not taking on a vendored third-party dependency in the companion runtime," consistent with the project's zero-dependency stance.
  - **Jun 10-11, 2026 (auth hardening + fixup):** implemented the per-session key: URL carries `?key=<token>`, sets an HttpOnly/SameSite=Strict/per-port cookie, WebSocket upgrades require both valid auth AND same-origin `Origin` header (browser confused-deputy defense), `/files/*` uses realpath containment against symlink/hardlink escape, added a stop-server "instance-id" ownership proof (`--brainstorm-server-id=<id>` passed as inert argv, verified via `/proc/<pid>/cmdline` before signaling) so `stop-server.sh` never kills an unrelated `node` process. Explicit **out-of-scope boundary** stated in the auth spec: malicious *agent-authored screen HTML* is out of scope — "Companion screens are part of the agent UI surface... may use inline scripts today and may someday use same-origin vendored libraries" — full sandboxing would need a separate iframe+postMessage architecture, deliberately deferred.
- **Keywords:** blocking-vs-non-blocking turn model, `.events` JSONL, zero-dependency rewrite, hand-rolled WebSocket/RFC 6455, per-session secret key, confused deputy, realpath containment, instance-id ownership proof.

- **Notable:** Core detection primitive is a stable git internal, not environment-variable sniffing: `GIT_DIR != GIT_COMMON` (git ≥2.5, 2015) means "already inside a linked worktree," with a submodule guard (`git rev-parse --show-superproject-working-tree`) to avoid false positives, since submodules also produce `GIT_DIR != GIT_COMMON`. Documents a real **TDD validation failure and fix cycle**: the first draft of "Step 1a" (prefer native tools) used deliberately abstract language ("you know your own toolkit") and scored only 2/6 pass rate — agents anchored on the concrete git commands in the fallback Step 1b instead. Root causes identified: (1) vague guidance loses to concrete guidance, (2) Claude Code's `EnterWorktree` tool description itself says "ONLY when user explicitly asks," which silently overrides skill instructions per a cited Claude Code issue (#29950) — "Tool descriptions override skill instructions." Fix: explicit tool naming (`EnterWorktree`, `WorktreeCreate`, `/worktree`, `--worktree`) turning the decision into a factual lookup, plus a "consent bridge" sentence framing user consent as the tool's own required authorization. Result after 3 REFACTOR iterations: 50/50 pass across GREEN+PRESSURE tests. Ownership/cleanup heuristic: "whoever creates the worktree owns its cleanup" — if the worktree lives under `.worktrees/` or `worktrees/`, superpowers created and cleans it up; anything else (`.claude/worktrees/`, `~/.codex/worktrees/`) belongs to the harness and is left alone. Bundles 3 named bug fixes (#940, #999, #238) around cleanup ordering (merge→verify→remove-worktree→delete-branch, never delete-branch-before-worktree-removal) and CWD safety before `git worktree remove`.
- **Keywords:** `GIT_DIR != GIT_COMMON`, native-tool preference, TDD gate failure/fix, tool-description override, provenance-based cleanup, consent bridge.

### positive-instruction-doctrine

- **What:** A design-methodology spec proposing (and testing) a general rule for when negative/prohibition-phrased skill instructions work versus backfire, derived from micro-testing.
- **Where:** `docs/superpowers/specs/2026-06-10-positive-instruction-redesign-design.md`.
- **Notable:** States a 5-point "doctrine" from measured micro-tests (opus, 5 reps/phrasing, programmatic scoring): (1) tripwires (phrase-level self-checks on concrete tokens) work reliably; (2) recognition tables (Red-Flags/rationalization tables read at decision time) work; (3) discrete-directive prohibitions ("do not ask X to do Y") hold when the model has no competing incentive; (4) **composition prohibitions backfire** when the model has its own agenda for the output — measured example: telling a controller "don't restate the brief" produced *worse* results (4.4 spec-values re-typed) than giving no guidance at all (3.6), while a positive recipe ("your dispatch should contain: (1)...(5)") produced 3.0 with zero variance; (5) ties go to the shorter phrasing (cites that Codex re-reads SKILL.md ~500× per long session, making prose length a real cost). Documents an audit of ~30 skills classifying every negative instruction found (3 tripwires, 14 recognition tables, ~20 policy gates, 5 true composition-prohibitions) with a per-item keep/replace disposition table. A named "micro-test harness" methodology is described for reuse: one API call per sample, system prompt = the guidance variant, user = realistic scenario, ~$0.15-0.30/sample vs $12/50-min full eval run — "iterate phrasings here; confirm winners in full runs only when the change is structural." The doc's own concluding "Result" section records a negative outcome as a first-class finding: a follow-up micro-test on `writing-plans`' banned-placeholder-list found current-gen opus produces zero placeholders with or without the list (40/40 clean across two pressure stages) — conclusion: "leave the section as-is... do NOT open the follow-up PR," explicitly modeling that not shipping a change is a valid, documented outcome.
- **Keywords:** prohibition vs recipe, tripwire, rationalization table, micro-test harness, instruction-design doctrine, negative-result documentation.
