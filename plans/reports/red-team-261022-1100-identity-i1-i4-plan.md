# Red-team and validation: Identity I1-I4 plan (2026-10-22)

Plan: plans/261022-1100-identity-i1-i4-project-machine-session-directory/. Reviewed against repo main @ 71b321787. Spec sections 4, 5, 7, 10 treated as fixed. 12 findings, ordered by severity.

## Critical

### 1. Phase 01 deletes `fixEventStoreMachineId`, which `events migrate` calls today
- Evidence: phase-01 Design "Delete the dormant `fixEventStoreMachineId`". `src/verbs/events/migrate.mjs:10` imports it and `:72` calls it (`fixEventStoreLockDirs(cwd, base); fixEventStoreMachineId(cwd, base); fixEventStoreRefspec(cwd, base);`). Tests: `test/setup/event-store-fixes.test.mjs:7,11-13,26,38`; `test/setup/event-store-checks.test.mjs:37` asserts the `event-store-machine-id` missing-id branch the plan also deletes. `test/architecture.test.mjs:1309` allowlists `mintEventStoreMachineId`. None of these are in the phase-01 Files list. Scout §1 calls the fix "dormant", which is true of registration, not of callers.
- Impact: either `events migrate` breaks (the WORK lane's ES cutover runs it) or the plan leaves two mint doors, which violates L10. `migrate.mjs` is also on the board's collision list (HARDEN T1 H18, GIT/ES review).
- Fix: do not delete it. Re-point `fixEventStoreMachineId` to call the identity mint door (one line), keep its tests, and drop only the registered `identity-machine-id` fix's duplicate. Or move `migrate.mjs` to the identity fix in the same change and say so on the board for GIT/ES. Add the three test files and `migrate.mjs` to the Files list.

### 2. Bare `fgos identity` becomes fallible and heavier on the git-commit-hook path
- Evidence: phase-02 Design "Bare `fgos identity` keeps `{id, source}` and adds `machine` and `session` objects"; phase-04 "the first identity read of a session writes its entry". `.githooks/pre-commit:32,555` refuses the commit when `resolveWriterIdentity` fails. The plan never says what the bare verb does when `<stateRoot>/machine-id` is absent, which is the state of every machine until `doctor --fix` runs (scout §1: no machine-id on this machine). Board row 5.1 holds a cold-start gate of at most 10 ms for this verb; the plan adds sha256, a `/proc` read and a file write to it and does not re-measure.
- Impact: on a machine that has the new release but no minted id, either every commit is refused, or the answer silently omits fields and the doctor row `writer-identity-resolvable` shows a changed shape. A read verb that writes (phase 04) also runs in every hook and every worker subprocess.
- Fix: state the rule. The bare verb and `probeIdentity` stay `{id, source}` plus optional additive fields; a missing machine id yields `machine: null` plus a warning, never an error or a mint. Registration into the directory happens only in `identity session` (explicit), never in the bare verb. Add a test that runs bare `fgos identity` with an empty state root and proves it still returns `{id, source}` with exit 0. Re-measure the cold start.

### 3. Project id minted by `doctor --fix` on three machines diverges before the first commit is pushed
- Evidence: phase-03 Design "Mint: setup fix `identity-project-id` on the main checkout when the file is absent". Spec section 4 wants one id for every clone. The three machines each hold their own clone of this repo. The first machine to run setup mints and commits; any other machine whose clone has not pulled that commit mints a different id. The result is an add/add conflict on `.fgos/project.json`, or two ids already published. The doctor warning for this arrives only in phase 05. `.fgos` files are excluded from worker commits (`.githooks/pre-commit:222-246`, scout §4), so only a main-door commit can fix it.
- Impact: the property the rung exists for (one id on every clone) is broken on the first landing.
- Fix: the setup fix does not mint in a clone that has a remote with a newer tip. Concretely: mint only through `fgos identity project --init` (explicit), and the doctor check reports "absent" as a fail with the instruction "run it once on one machine, commit, pull elsewhere". For this repository, commit the id by hand once before the release lands, so no machine ever mints it. Test: two temp clones, both run the fix without a pull, and the fix refuses on the second when `git ls-remote` shows `.fgos/project.json`.

## High

### 4. The identity route is declared Read/Safe, but the plan adds writers to it
- Evidence: `packages/host-runtime/rust/src/catalog.rs:51-60` registers `session-identity.resolve` with `OperationEffect::Read`, `OperationIdempotency::Safe`, authority policy `session-identity.read`, outcome contract `1.0.0`. The plan adds writers under the same route: `project --new` (phase 03), `session --role`, `--take` and `list --prune` (phase 04), directory registration (phase 04). `catalog.rs` is not in any phase's Files list. `command-routes.json:405-420` has no `subcommands`/`subcommand_flags`; the plan adds them in one line without naming flags per subcommand (compare `convention` at `:121-136`).
- Impact: the host's authority and idempotency declaration is false for the new writers; the route test `test/rust-host/command-routes.test.mjs` and the `command-routes-drift` doctor row depend on exact flag lists.
- Fix: split the descriptors. Reads (`machine`, `project`, `session`, bare, `resolve`, `list`) stay Read/Safe; writes (`project --new`, `session --role/--take`, `list --prune`, and the mint) get a second operation with `Write` effect and a `session-identity.write`-style policy under the identity owner. Add `catalog.rs`, the authority-policy table and per-subcommand `subcommand_flags` to the Files list. Decide whether the operation id keeps the name `session-identity.resolve` or is renamed; if renamed, move the Rust, JSON, doctor and docs uses in the same change (L10).

### 5. The outcome schema forbids the additive fields phase 02 promises
- Evidence: `packages/session-identity/contracts/session-identity.resolve.v1.json:~22-40` gives both outcome branches `"additionalProperties": false, "required": ["id","source"]`. Phase 02 says the bare answer adds `machine` and `session` objects, "additive", and that "`session-identity.resolve.v1.json` gets the additive fields under the identity crate's contract". The Node reader at `src/util/session-identity.mjs:60-67` tolerates extras, but the contract and `golden.v1.json` (via `golden.rs`) do not. Contract is `1.0.0` (`catalog.rs:54-55`).
- Impact: the golden test fails, or someone silently weakens the schema. The doctor probe and the schema then disagree.
- Fix: bump to `1.1.0` (or add the new keys as optional properties in both branches), move the contract file under `packages/identity/contracts/`, rename in `catalog.rs` and the descriptor, and make `golden.rs` own the vectors for both shapes. List `session-identity.resolve.v1.json` and `session-identity.golden.v1.json` in phase-02 Files.

### 6. `fgos-identity` makes Event Store (and the node addon) depend on host-runtime and Convention
- Evidence: phase-01 puts the mint, the reader and `IdentityProvider` in one crate `fgos-identity`, and makes Event Store `pub use fgos_identity::machine::*`. `IdentityProvider` needs `fgos-host-runtime` (as in `packages/session-identity/rust/src/provider.rs:5`, `Cargo.toml:6`). The crate also needs `fgos-convention` (phase 01, "checks the id through `RuleSet::identifier`"), `fgos-session-identity` (phase 02), `fgos-process` and `fgos-git` (phase 03 trusted main root, `workspace.rs:28`). `packages/event-store/rust/Cargo.toml` today has no host-runtime or convention dependency, and the addon `packages/git/node-addon/Cargo.toml:17` pulls `fgos-event-store`. Design principle 2 (strict bottom-up): the leaf the event log depends on must not carry the CLI adapter.
- Impact: tokio and the host runtime land in the Node addon through Event Store; `test/architecture.test.mjs` and `docs/architecture-manifest.json` likely refuse the edge, and the phase never runs that check before the move (step 2 runs only `cargo test`).
- Fix: split the identity crate in two layers inside the same package, or two crates. The lower library (`machine`, `session`, `project`, `directory`; deps `fgos-durable-file`, `fgos-process`, `fgos-session-identity`, `fgos-holder-lock::state_root`) has no host-runtime. The provider and route live in a thin adapter module or feature that only `apps/fgos` enables. Event Store depends on the lower layer only. Run `test/architecture.test.mjs` in step 2, not step 5.

### 7. The mint "moved verbatim" cannot move verbatim; the extra dependencies and the duplicate proofs are not planned
- Evidence: `packages/event-store/rust/src/identity.rs:187-210` `mint_machine_id` calls `crate::layout::branch_key` (`layout.rs:122`), the private `random_id()` (`identity.rs:74`, Linux-only, `ErrorCode::EventStoreUnsupportedPlatform`) and `Error::from_install_error`/`ErrorCode::EventStoreMachineId`. Result codes are pinned in `packages/event-store/contracts/result-codes.v1.json:26,31`. Phase-01 Design: "moved verbatim ... same errors mapped to identity error codes". Proofs: `packages/event-store/rust/tests/registry_identity_layout.rs:127-139` (`valid_machine_id` cases) and `review_fixes.rs:136-140` stay in Event Store while phase 01 adds the same validity cases to `tests/machine.rs` and Convention `machine-id` goldens. That is three owners of one behaviour (principle 8) and two validators (`valid_machine_id` and the Convention row) with no rule for which wins.
- Fix: state that `branch_key` (slug rule) and `random_id` are either duplicated (principle 1 violation) or moved down to a shared leaf (for example `fgos-durable-file` or the identity library) and that Event Store keeps `ErrorCode` mapping by wrapping. Pick one validity authority: `valid_machine_id` stays the only implementation and the Convention kind either calls it or is dropped for machine-id (the format has an owner already). Name the single owning test, and delete the other two in the same change.

### 8. The machine handle can be invalid under its own Convention kind and is not unique at the first landing
- Evidence: phase-01 "Machine handle = the hostname slug part of the id" with Convention `machine-handle`: first `a-z`, rest `a-z0-9-`, max 40. `mint_machine_id` (`identity.rs:187-190`) allows a slug up to 56 characters and a first character that is a digit (`valid_machine_id` accepts digits first, `identity.rs:18-24`). So `3d-printer-abc234` or a 50-character hostname produces a handle that fails the plan's own check. The alias file `<stateRoot>/machine-alias` has no writer in any phase (no verb, no fix). Uniqueness across machines is deferred to phase 05, but plan.md's landing section has each of the three machines post a roster line right after phases 01-02, with generic hostnames (`ubuntu`, `localhost`) giving identical handles.
- Impact: the first roster (the product of this plan) can contain duplicate or invalid handles.
- Fix: derive the handle by truncating to 40 and prefixing a letter rule (or widen the Convention kind to match `machine-id`'s alphabet). Add `fgos identity machine --alias <name>` (with write operation, see finding 4) in phase 01, since the board needs it right away. Make the roster step check uniqueness by hand (three machines) and have the board row refuse a duplicate handle.

## Medium

### 9. Convention cannot express `cli-name` or `@`-bearing handles as the plan says
- Evidence: plan phase-02 "Convention kinds: `cli-name` (fixed set: claude, codex, ...) and `session-suffix` (first/rest `a-z2-7`, max 4)". `packages/convention/contracts/convention.rules.v1.json` `identifiers[]` rows carry only `id, description, first, rest, maxLength, reserved[]` (seat-id, workflow-name, agent-name). `reserved` is a denylist; there is no allow-list or separator. The handle `<cli>-<chars>@<machine-handle>` and phase-04 `role-alias` (`lead:<LANE>`) contain `@` and `:`, which no single `rest` class can accept. Also `session-suffix` max 4 while phase 02 mints 3 and phase 04 lengthens to 4, and spec section 4 allows 2-4.
- Impact: phase 02 ends with Convention kinds that either do not validate what Identity prints or need an extension of `rules.rs`, `operations.rs` and `convention.golden.v1.json` that the plan does not scope (scout §3 flagged this gap, and the plan does not carry it).
- Fix: either scope the Convention extension explicitly (a `pattern`/`parts` identifier shape plus goldens, in phase 02 Files), or register only the part kinds that fit (`machine-handle`, `session-suffix`, `lane-id`) and compose in Identity, recording that composition is Identity's and tested once there. Drop `cli-name` as a Convention kind and make the set a constant in the crate with its own test.

### 10. Phase 02 handle and id derivations are unstable or ambiguous in three places
- Evidence: (a) Handle chars come from 3 base32 characters (15 bits) of sha256(local id). Phase 04 lengthens both handles on collision, so a handle already pasted into the board (phase 06, step 2) stops resolving when a second session collides; the plan's resolve rule is exact-match. (b) Phase 02 "`pid-<pid>-<start time>` from `identity_of`": `facts.rs:285` `identity_of` returns `ProcTuple` with `start_time` as the raw string; on Linux it is `stat.start_ticks.to_string()` (`packages/process/rust/src/platform/linux.rs:62`), ticks since boot, with no boot id in the id. A daemon started at boot with the same pid after a reboot yields the same full id. `ProcTuple.boot_id` (`facts.rs:36`) exists and is not used. (c) For `source: unresolved`, `WriterIdentity::unresolved(caller_pid)` returns the caller's own pid (`resolve.rs` `tree_identity`), which changes on every call (the caller is the transient `fgos` child), contradicting "the same every time the same session asks".
- Fix: (a) mint 4 characters from the start (or resolve by prefix and report ambiguity), and never change a printed handle. (b) hash `boot_id` into the pid-derived local id. (c) for `unresolved` print no session handle (`session: null`, reason `unresolved`) and fail `identity session` with exit code 65-style refusal.
- Also, the "env var that won" fallback ("`ENV_ORDER` is public"): `ENV_ORDER` is public (`lib.rs:22`) and `WriterIdentity{id,source}` fields are public (`resolve.rs:46-49`), but `usable()` (`resolve.rs:69`) is private. Re-deriving the winning variable by calling `std::env::var` over `ENV_ORDER` needs a copy of the charset/length/trim rule, which is a second implementation of the session rule (principle 1, spec decision 1 "reverse if one authority forces two copies"). Recommended instead: compare the returned id string against each `ENV_ORDER` value after `resolve_current`, or add the additive `env_var` field now and tell HARDEN (the field touches `resolve.rs` only, not the T1 phase-6 files `Cargo.toml` and `proc_tree.rs`).

### 11. Phase 04 liveness has no process to judge, and the directory grows without bound
- Evidence: phase-04 "Each entry: ... a `fgos_process::facts::Record` for liveness" and "`judge_here(&Record)`". A session resolved through an env id (Claude, Codex) has no pid in `resolve_current`; the only process the verb knows is its own short-lived parent (`default_caller_pid`, `provider.rs:36-46`), not the agent head. The plan does not say which pid becomes the Record. Registration happens on "the first identity read", so every hook, worker subprocess and test that runs `fgos identity` (including `source: pid` sessions) creates an entry; the only cleanup is the manual `list --prune`. Concurrent first reads race on `<session-hash>.json`: `install_once` keeps one, but with different Records (different caller pids) the stored one may be the transient child.
- Fix: capture the Record from the tree walk (the highest tty ancestor that `tree_identity` already finds, via `fgos_process::facts::identity_of`), register only on explicit `identity session`/`--role` (see finding 2), prune dead entries on every write with a bounded scan, and cap the directory size. Name the test that proves a Claude-style env session is judged by its ancestor pid and not the transient child.
