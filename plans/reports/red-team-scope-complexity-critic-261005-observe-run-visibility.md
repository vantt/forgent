## Finding 1: Phase 6's decision ledger and A/B routine conflict with the case journal's own invariants
- **Severity:** Critical
- **Location:** Phase 6, "Requirements" (decision ledger verdicts `confirmed|revised|reversed|inconclusive`; one decision case left open until a review date), "Implementation Steps" 3-4 ("open case per setup"); plan.md D4
- **Flaw:** The case journal allows **one open case per project**, and `close` accepts only `usable|fixed|discarded`. A case is also a time window (`since`/`until`) that `metrics runs --case` and the snapshot use to bound measurement. The plan changes only the contract fields (`scores`, `rubric`, `judge`). It does not change the verdict enum, the one-open-case rule, or the meaning of the window, and it never says that it leaves them alone.
- **Failure scenario:** (a) The step 4 dogfood opens "one decision-ledger case (this plan's D1, to be reviewed at a named date)". While that case is open, every later `metrics case open` in the repo fails with `AlreadyOpen`. Any other measurement case, including the A/B cases in the same step, is blocked until the review date. (b) If the decision case is closed straight away so others can open, closing it with `confirmed`/`revised` fails with `invalid verdict ... Allowed: usable, fixed, discarded`. (c) A decision case left open for weeks makes `metrics runs --case <decision>` measure every run in that span. The window has nothing to do with the decision. Success criterion "One decision case opened with a prediction and a review date" either blocks all other cases or cannot be closed.
- **Evidence:** `packages/observe/rust/src/case_journal.rs:266-269` (`find_currently_open` -> `AlreadyOpen`), `case_journal.rs:100,330-331` (verdict whitelist), `packages/observe/rust/src/metrics_cli/case.rs:89` (close usage `--verdict usable|fixed|discarded`), `packages/observe/rust/src/metrics_cli/runs.rs:76-84` (a case is a window for `metrics runs`).
- **Suggested fix:** Phase 6 needs one of two options. (1) Explicit contract and behavior changes: a verdict vocabulary per harness, and a rule that windowless or `decision` cases are exempt from the one-open rule and from window semantics. Every consumer of `find_currently_open` and `CaseWindow` must be listed. (2) Drop "decision ledger on the same mechanism". **Question for the user (requested item):** the repo already keeps decisions in `docs/decisions/` plus the per-spec "Lịch sử quyết định" sections, projected by `fgos decision-index` (AGENTS.md L5 Q6). Should a second decision store really live in the Observe case journal? Or should the ledger be a review-date/prediction field on the existing decision records?

## Finding 2: The "one layout rule" is specified two contradictory ways, so the coverage invariant cannot hold
- **Severity:** Critical
- **Location:** Phase 1, "Architecture" (D1: `<assignmentDir>` is recognised by holding `assignment.json`) and Step 4 ("a dir named `runs` that is not a run (no `assignment.json` above it)"), against Phase 2, Step 3 ("nested with missing `assignment.json`: all three observed; the third has `role: null`")
- **Flaw:** In the Node lister, a `runs/` directory with no `assignment.json` above it is **not** a run. In the Rust walker, the same directory **is** a run, with a null role. Phase 3 compares Node's disk count with Rust's observed count and says "never loosen the comparison". The rule that both languages are supposed to "implement the same" way differs in its main edge case.
- **Failure scenario:** On a store with a `runs/NN/result.json` whose parent has no `assignment.json`, Rust observes N+1 and Node counts N. The doctor check passes only because its comparison runs in one direction ("fewer observed fails"), so a real double-count or over-walk is never caught. If the edge goes the other way (a deeper `runs/` under a directory that does hold `assignment.json`), Node counts it and Rust does not, and doctor goes red on a healthy store. This edge exists on the real store today: `asgn-deepseek-1791185611935/runs/01/` has no `assignment.json`. The current Rust source does not require `assignment.json` either. It falls back to `(Null, Null, None)`.
- **Evidence:** `packages/run-result/rust/src/lib.rs:390-404` (the `assignment.json` read is optional); `.fgos/assignments/asgn-deepseek-1791185611935/` (contains only `runs/01/run.json`); `scripts/regenerate-observe-fixtures.mjs:112-129` (the golden writes `assignment.json`, so goldens will not catch the divergence).
- **Suggested fix:** Write one normative predicate in the spec, with that edge case decided either way. Give both languages a single shared conformance fixture (one directory tree plus the expected `{assignmentId, attempt}` list) that a Node test and a Rust test both assert against. Make the doctor comparison two-sided (`observed == disk`, with skipped counts reported separately).

## Finding 3: Phase 3 cannot tell an "old host" from a blind one, and doctor runs all sources
- **Severity:** High
- **Location:** Phase 3, "Requirements" ("a host that predates the fix ... yields a passing-but-degraded result"; "the check reads directory names only; no JSON parsing"), Success Criteria ("degrades with the old staged host")
- **Flaw:** No step defines how the check detects "predates the fix". The old host answers `metrics runs` normally with a smaller total (887 here). It does not error. A smaller number is exactly the failure the check is meant to raise. Separately, `metrics runs` calls `observations()` on **every** wired source, including `ClaudeTranscriptsSource` (scans `~/.claude/projects`) and `WorkSource`, and the run-result source parses every `result.json`. The "no JSON parsing in doctor" requirement holds only for the Node half.
- **Failure scenario:** After phases 1-3 merge and before a release is cut, every `fgos doctor` on every project using the installed staged host reports `observe-run-coverage` FAILED with "N runs missing". That is the false failure the plan says it prevents. On machines with large transcript stores, doctor also slows down by the full transcript scan.
- **Evidence:** `packages/observe/rust/src/metrics_cli/runs.rs:89-96` (iterates every source), `apps/fgos/src/wiring/metrics_sources.rs:9-14` (three sources wired), `packages/observe/rust/src/metrics_cli/mod.rs:14-16` (no capability/version field exists to probe).
- **Suggested fix:** In phase 2, add an explicit capability marker to the `metrics runs` envelope, for example `coverage: {walk: "recursive-v1", onDisk, observed, skipped}`. Absence of the marker is how phase 3 identifies an old host. Better still, have the host compute and return its own on-disk count, so doctor reads one answer and never runs the transcript source. Then no walk is re-implemented in Node for this purpose.

## Finding 4: The plan misses the existing nested-layout authority and re-derives it a fourth time, in Observe
- **Severity:** High
- **Location:** plan.md "Problem" table ("Three independent flat walkers", "no spec describes the layout"); Phase 1 "Related Code Files" audit list; Phase 4 "Architecture" (fallback `<round>-fb<n>` handling, seat `outcome`)
- **Flaw:** Both factual claims are false. `src/runner/execution/unit-run-history.mjs` already walks `<unitRunId>/<role>/<round>[-fb<n>]/runs/<NN>/`. It owns the "latest fallback wins" rule and maps RunResult to the unit outcome vocabulary (`outcomeOfRunResult`). `docs/specs/runner.md` already describes the nested layout and names that module as the single reader. Phase 1's new `assignment-layout.mjs` does not absorb it, and phase 1's guard ("readdir over the assignments root") is scoped so it will not catch it. Phase 4 then re-implements fallback precedence and seat outcome in Rust. That makes three layout readers and two outcome mappings: the root-cause pattern the plan itself names, and a RUL11 violation. Computing seat outcome in Observe also touches observe.md "Must Not Own": Observe must not re-classify RunResult.
- **Failure scenario:** The next change to fallback naming or outcome mapping (for example, a new `paused-limit` handling) lands in `unit-run-history.mjs`. `metrics discussions` silently disagrees with what the pattern actually decided. This is the same failure as the 10-01 blind spot, one level up.
- **Evidence:** `src/runner/execution/unit-run-history.mjs:14-23` (`outcomeOfRunResult`), `:25-62` (role/round/`-fb<n>` walk and precedence), `docs/specs/runner.md:1427` ("Một chỗ duy nhất phân giải ... đọc lịch sử qua `unit-run-history.mjs`"), `docs/specs/runner.md:3077` (`<unitRun>/<role>/<round>-fb<n>` layout), `docs/specs/observe.md:21`.
- **Suggested fix:** Correct the Problem table. In phase 1, make `assignment-layout.mjs` the base that `unit-run-history.mjs` composes (or merge them), and extend the existing runner.md text rather than adding a parallel subsection. For phase 4, have the execution core persist the settled per-seat outcome and the fallback chain in `unit.json` or a unit result record when the unit settles. Observe then reads that one owned record instead of re-deriving it.

## Finding 5: A passive stance sensor that can fail a panelist's run
- **Severity:** High
- **Location:** Phase 5, "Architecture" (D2 `stance` in `agent-result-claim`), Step 2 ("invalid `choice` type rejected"), Requirements ("Never blocks")
- **Flaw:** Validation failures in `validateAgentResultClaimContract` are not soft. An invalid claim makes confidence `failed` and policy `refuse` (`invalid-agent-result-claim`). That maps to seat outcome `policy-refusal`, and the unit and workflow step then fail. Making a malformed `stance` invalid turns the passive sensor into a gate on every panelist. The validator also already ignores unknown fields, so a contract change is not needed for a claim carrying `stance` to be accepted. The only real change is the instruction text. The planned validation change adds risk and no capability.
- **Failure scenario:** A model writes `"stance": "B"` (a string) or `{"choice": 2}`. The claim is refused, the panelist seat fails, the Delphi step fails, and the workflow stops. That is a behavior change on runs where `stance` is optional.
- **Evidence:** `src/runner/dispatch/run-result.mjs:505-512` (invalid claim -> `confLvl = 'failed'`), `:524-527` (policy `refuse`), `src/runner/execution/unit-run-history.mjs:20` (`policy` -> `policy-refusal`), `src/runner/dispatch/agent-result-claim-contract.mjs:51-89` (no unknown-field rejection; an extra `stance` is already accepted).
- **Suggested fix:** Leave the claim validator unchanged. Do the stance shape check in the Observe reader: a malformed stance counts as `stancesMissing`/`stanceInvalid` and never invalidates the claim. Add only the instruction line, gated on unit params. **Question (requested item):** the porting-log row this phase implements specifies a `STANCE:` line, and its kill criterion K2 needs 30 runs measured. With options-only measurement, most real questions read `unmeasured` (the plan admits this). Will K2 ever accumulate? Also, `core/workflows/delphi.yaml` is a generic template with no question. Should options be declared per run request rather than in the workflow YAML?

## Finding 6: Phase 1 changes the behavior of dispatch reconciliation, and the plan does not list that consumer
- **Severity:** High
- **Location:** Phase 1, "Requirements" and Step 5 ("keep return shapes"); "Related Code Files" (only `runtime-inspection.mjs`, `show-run.mjs`)
- **Flaw:** `allRuns` feeds more than `dispatch inspect`. `reconciliation-planner.mjs` uses the `--cwd` view's `activeRunIds` (run.json present, result.json absent) and `inspectionStatus` to decide whether a dead cwd-lock may be removed. After phase 1, every crashed or orphaned nested run (no `result.json`) becomes an active run bound to its cwd. Nested runs also go through `owner()`/`assignmentEvidence()`, whose admission and coordination logic was written for flat assignments. Reaching nested runs makes "partial"/"needs-input" states possible where today there are none.
- **Failure scenario:** There are four orphaned nested runs today (`unit-run-1791169494102…`, `…1791174736476…`, `…1791192177634…`, `…1791192481353…`, all `run.json` with no `result.json`). After phase 1, `fgos dispatch reconcile` for any cwd they are bound to returns `blocked: active Run(s) still bound`, permanently. In this repo the main checkout is already blocked by 5 flat orphans. The new regression lands on workflow unit worktrees and on other projects (mdview), where nested runs are the majority.
- **Evidence:** `src/runner/dispatch/reconciliation-planner.mjs:561-566`, `src/runner/dispatch/runtime-inspection.mjs:153-170` (`owner`/`authority`), `:290` (`active = found.filter(!result.present)`).
- **Suggested fix:** Add `reconciliation-planner.mjs` (and `dispatch recover` via `authority()`'s `observeCommand`) to the consumer list. Add a test: a nested orphan under a worktree cwd, then reconcile, with the expected outcome stated. Decide explicitly whether orphaned unit seats count as "active" or are classified as abandoned.

## Finding 7: Phase 4's source location and subject choice cross boundaries and duplicate an existing slot
- **Severity:** Medium
- **Location:** Phase 4, "Architecture" (D3 `UnitRunSource` in the `run-result` crate; subject kind `run` with id = unit run id; join on `unitRunId`), "Risk Assessment" ("if red-team objects, move")
- **Flaw:** (a) The `run-result` crate is the Run Result Evaluator boundary. Reading `.fgos/workflow-runs/*/events.jsonl` (Workflow-owned) and `unit.json` (Execution-Core-owned) from it adds a cross-area dependency. `docs/platform/component-boundary.md` §3 requires either updating the map or recording "No component-boundary change", and the plan does neither. (b) The subject table says `run:<runId>` is owned by `packages/run-result` and names RunResult runs. Reusing kind `run` for unit-run ids puts two entity types in one namespace. (c) The harness already has a slot for workflow discussions: `compute_sessions` accepts `source == "workflow"` with subject kind `session`. That slot was added when the coordination engine was retired. The plan ignores it and builds a parallel `metrics discussions` view. (d) The join is weaker than stated: `unit.scheduled` carries no `unitRunId`, and a unit whose `runUnit` throws emits no `unit.complete` at all. Crashed units can never be linked to their workflow.
- **Failure scenario:** The harness `sessions` section stays at zero forever while `metrics discussions` reports the same runs, giving two dashboards that disagree. A crashed Delphi unit (the one the acceptance criterion wants to see "fail with the gemini/xai fallback chain") shows `workflow: null`.
- **Evidence:** `packages/run-result/rust/Cargo.toml` (deps: host-runtime, observe only); `docs/platform/component-boundary.md:46-54`; `docs/specs/observe.md:29`; `packages/observe/rust/src/scorecard.rs:347`; `src/workflow/runner.mjs:377-382` (no `unitRunId` in `unit.scheduled`), `:387-407` (`unit.complete` only after `runUnit` returns).
- **Suggested fix:** Decide D3 now rather than deferring it to "if red-team objects". Either have the Workflow component expose a `workflow` source (subject `session`, filling the existing `compute_sessions` slot), or record the boundary change. Have the workflow runner write `unitRunId` at schedule time, or emit `unit.failed` on throw, so the join is complete.

## Finding 8: Phase 2 reports skipped counts through a trait it does not list as changing, and its real-store invariant is racy
- **Severity:** Medium
- **Location:** Phase 2, "Architecture" ("Skipped-unparseable and skipped-missing-timestamp counts are returned alongside observations"), "Related Code Files" (lists only `lib.rs` and tests), Step 4 (real-store `observed == on_disk`)
- **Flaw:** `ObservationSource::observations` returns only `Vec<Observation>`. Returning counts "alongside" requires changing the trait in `fgos-observe`, and four implementors would need updating (RunResult, Work, ClaudeTranscripts, InvocationFaults). Neither the trait nor those implementors are listed. Separately, the replacement smoke test compares two walks of the **live** repo store. Any dispatch that settles between them (common inside an agent session, where `npm test`/`cargo test` runs alongside panes) makes the test flaky.
- **Evidence:** `packages/observe/rust/src/contract.rs:81-84`; implementors at `packages/work-state/rust/src/work_source.rs:436`, `packages/observe/rust/src/sources/claude_transcripts.rs:130`, `packages/observe/rust/src/sources/invocation_faults.rs:25`, `packages/run-result/rust/src/lib.rs:330`; `packages/run-result/rust/tests/smoke_real_store.rs:7-11` (reads `../../..` live store).
- **Suggested fix:** Expose coverage as an inherent method on `RunResultSource` (or as observation-kind `run.skipped` records) instead of changing the shared trait. Keep the invariant hermetic on the fixture, and run the live comparison only in the doctor check.
