## Part B, findings

Counts: High 2, Medium 8, Low 6. Fixes sized in lines.

### High

**F1. High. `npm run build:skills` exits 1 after it has already written the skill surfaces, in any plain checkout.**
Evidence: `scripts/build-skill-wrappers.mjs:21-40` writes `.agents/skills`, `.claude/skills`, the plugin mirror, then at `:41` calls `materializeInstructionProjection`, whose first step `computeInstructionProjection` (`instruction-projections.mjs:239-246`) reads instruction sources through `discoverInstructionSources`, which parses YAML through the native door. The script never calls `ensureAddonForScript`; both siblings do (`build-domain-registry.mjs:62`, `project-agents.mjs:256`, defined `scripts/lib/git-addon-stage.mjs:78`). Baseline measured exit 1, `git-addon-unavailable`, after 22 skills, 125 wrappers and 20 plugin files were written.
Scenario: a maintainer edits `core/skills/x`, runs `npm run build:skills && git add ...`. Surfaces are written, the projection step throws, `&&` stops. The managed AGENTS.md block, `.fgos/instructions/effective/repo.json` and the ledger are not regenerated, so a lane that changed `core/instructions` lands with stale projections and `instruction-projections.test.mjs` goes red later in main. The half-written state also hides the cause: the log ends with `mirrored ...` lines and a stack.
Fix: import and call `ensureAddonForScript()` first, and compute the projection (`computeInstructionProjection`) before the first write so any refusal leaves the tree untouched. About +3 lines in the script, 0 in the module. Prove with one test that runs the script with no staged addon in a temp copy and asserts either exit 0 or an unchanged tree.

**F2. High. The wrapper step rewrites vendor skills it does not own, in this repository and, through `fgos setup`, in every project it sets up.**
Evidence: `generateAllSkillWrappers` (`skill-wrappers.mjs:168-195`) enumerates `readdirSync(agentsSkillsRoot)` and writes `.claude/skills/<name>/SKILL.md` plus copies every sibling file for every directory that has a `SKILL.md`. The only ownership test, `isGeneratedWrapper`, guards the orphan prune at `:198-205`, never the write. `assembleSkills` is the one that knows the owned names (it prunes only entries carrying the assembled header, `:1198-1219, 1303-1311`). The sibling step ignores that set. External path: `materializeSkillsIntoProject` (`:1328-1362`) runs `generateAllSkillWrappers(targetAgentsSkills, targetClaudeSkills, { keep })`; `keep` (`createProjectSkillGuard`, `:261-305`) refuses only a target that is tracked and dirty, or whose `SKILL.md` has a newer `version`. AgentKit dirs are git-ignored, so `dirtyPaths()` (status with `untracked: 'none'`) never lists them and they are overwritten. A dev-checkout `packageRoot` with 104 vendor dirs also copies them into the target (`:1349`).
Scenario (this repo, from the code and the baseline's staged run): after `build:skills` with the addon, 104 `.claude/skills/ak-*/SKILL.md` become 16-line fgOS wrappers marked "generated ... do not edit"; AgentKit's next update sees files it did not write. Today in main the originals equal the `.agents` copies, so no instruction text is lost, but the next AgentKit version bump will make wrapper and original diverge silently. Scenario (other project): `fgos setup` in a project with AgentKit installed replaces its `ak-*` entries in `.claude/skills`. The mission is fgOS working in other projects (D-ADR0035, #1); touching another tool's files there is the worse half.
Fix: `generateAllSkillWrappers` takes the owned names (`discoverCanonicalSkills` already returns them; `_shared` is excluded already) and skips everything else; `materializeSkillsIntoProject` passes the names `assembleSkills` produced for the package plus the target. About +8/-4 lines. The same set replaces the ignore-list knowledge in `.gitignore` (second place that hard-codes it is `worktreeSetup`'s `ak-*` glob, F11).
