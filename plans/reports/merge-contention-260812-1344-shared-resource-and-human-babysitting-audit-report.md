# Merge contention — shared-resource + human-babysitting audit

Scope: contention design, not merge algorithm correctness. Read-only investigation.

## 1. Shared-resource inventory

| Resource | Acquired by | Hold duration | Loser's fate | Bounded wait? |
|---|---|---|---|---|

Net: every *write* to shared state funnels through exactly 3 fs-lock primitives (main-checkout, events, sessions) plus one un-lockable git artifact (`MERGE_HEAD`). Claims/execution are cheap and fast against these locks; **merge is the one operation that holds the heaviest lock (main-checkout) for the longest time (up to 3+ minutes)**.

## 2. Serialization width — merging is single-threaded today, proven from code

- `mergeRunnerItem` acquires `main-checkout.lock` before its first git call and holds it through `mergeRunnerItemLocked` — including the full `runGoalCheck` verify run (`merge.mjs:679-756`). No merge caller ever runs without this lock; there is no alternate/parallel merge path (merge-next SKILL.md: "never a parallel merge path").
- `/fgOS:merge-next` picks exactly one top-ranked id per call (`merge-next/SKILL.md:11-13,24-25`: "still takes no id... always picks the single top-ranked item"). `/fgOS:merge-list` computes a full `ready` ranking (`mergeReadiness`, `graph-harness.mjs:109-258`) but nothing ever consumes more than `ready[0]` per merge attempt.
- `/fgOS:merge-loop` is literally `/loop` wrapped around `/fgOS:merge-next`, iterating **sequentially**, one `/fgOS:merge-next` call fully resolving (done/blocked) before the next fires (`merge-loop/SKILL.md:12-16` steps 3-4).
- Contrast with **claiming/execution**, which is already N-wide: `dispatch.mjs`'s default runner config allows `parallel: { maxRoots: 4, maxLeavesPerRoot: 4 }` (`dispatch.mjs:247-249`) — up to 16 concurrent claimed/executing items. Merge is the single-lane funnel downstream of a 16-lane production pipeline.

**Minimum critical section a merge truly needs** vs **what it holds today**:
- Truly needs the lock only for: `git merge --no-commit --no-ff` staging + the final `git commit` (the actual mutation of the shared checkout's index/HEAD) — a few seconds.
- Holds the lock for: staging **plus the entire verify run** (`runGoalCheck`, up to 185s measured) that happens on the merged-but-uncommitted tree, because verify must run against the post-merge tree and there is currently no isolated place to run it once merged into the shared checkout (`merge.mjs:665-677` comment explicitly documents this tradeoff and the heartbeat hack needed to survive it).
- The heartbeat renew (`HEARTBEAT_INTERVAL_MS`, `merge.mjs:677,745-748`) is a **symptom fix**, not a scope-narrowing fix: it exists purely to keep an already-oversized critical section from expiring under its own TTL while it holds the lock nobody else can touch.

## 3. Failure-on-contention modes — grounded in code

1. **`lock-held` (claim or merge)** — clean, typed error with holder pid + remaining TTL (`claim-port.mjs:99-108`, `merge.mjs:721-729`). CLI layer retries with bounded backoff by default (`lock-wait.mjs`). This is the **well-behaved** case.
2. **`lock-ambiguous`** — unparseable lock file, fails closed, **never retried** even under `withLockRetry` (`lock-wait.mjs:27-29`). A losing session gets an immediate hard failure with no self-heal; recovery requires `fgos-unlock`/`forceReclaimAmbiguousLock` (`main-checkout-lock.mjs:594-615`), a human-triggered action (`fgOS:unlock` skill).
3. **Stale MERGE_HEAD misattributed as conflict (tsk-4hj)** — a crashed/exited session's abandoned merge leaves `MERGE_HEAD` on disk *after* releasing `main-checkout.lock` (the lock and the git artifact are two separate resources with two separate lifetimes). A second session's own valid merge attempt reads that leftover as its own conflict, and — before the fix — called `git merge --abort`, **destroying the first session's real, possibly-uncommitted, manually-resolved conflict fix**. Fixed by checking `mergeHeadExists` *before* the merge attempt and returning a distinct `merge-blocked-other-item` outcome instead of `conflict`, never calling abort on state this call didn't create (`docs/history/tsk-4hj-.../CONTEXT.md` D1-D3, `merge.mjs:960-974`). This is the sharpest illustration in the codebase that **the lock and the git state it's meant to protect can desync** — the lock is scoped to fgOS's own primitive, not to git's own merge-in-progress state, which has no TTL and no owner-tracking at all.
4. **events.lock flake under real concurrency (tsk-3wn)** — not a production bug: the *test* that stampedes 20 processes × 40 appends (800 serialized holders) against a 2000ms budget sized for "dozens" of holders was over-scaled relative to its own documented envelope (`events.mjs:44-48`), and got fixed by right-sizing the test (8×15=120), not the lock. Real finding for this audit: `EVENTS_LOCK_TIMEOUT_MS`=2000ms is a genuinely tight budget once dispatch parallelism (16-wide, §2) is pushing that many concurrent session/runner writers at once — the same envelope math that broke the test can plausibly break for real at full dispatch width, and there is no backoff/retry wrapper around `withEventsLock` today the way `lock-wait.mjs` wraps `main-checkout.lock`. Two unrelated items (`tsk-104`, `tsk-4qu`) were pushed to `blocked` purely by this flake, not their own content — a real cost of a losing session's exit-7-shaped failure being indistinguishable from a real regression until someone diagnoses it.
5. **`lock-held` exit 7** — `bin/fgos.mjs` maps `lock-timeout`-category errors through `EXIT_CODES` (codes 2-5,7-9; `bin/fgos.mjs:9,4689`). A losing CLI invocation (not wrapped in `withLockRetry`, or past its budget) exits non-zero with a machine-readable code — clean, not silent, but still a hard stop a human or script must notice and re-drive.
6. **Silent false-block via unclassified merge outcome (adjacent, tsk-4hj D4)** — found during that same item's validating pass: `fgos sync-root`'s own call site had **no branch** for any outcome besides `merged`/`conflict`/`fgos-write-rejected`/`verify-fail`; a new outcome (`merge-blocked-other-item`) would have silently fallen through to the **success** block and reported `synced` when nothing actually synced. Fixed with a defensive catch-all `else` (`CONTEXT.md` D4). This class of bug — a losing/blocked outcome silently misreported as success — is exactly the shape a "human babysitting the merge queue" exists to catch by eyeballing output; every new outcome variant is a fresh opportunity for it to recur at a call site that hasn't been audited yet.

## 4. Human-in-the-loop audit — is each stop load-bearing?

| Stop point | Where | Load-bearing (real judgment) or mechanical gap? |
|---|---|---|
| Iron Law trip (`--acknowledge-iron-law`) | `bin/fgos.mjs:2985-2990`, merge-loop step 4 "never on this skill's own authority" | **Load-bearing.** Explicitly named in `AGENTS.md`/`docs/specs/runner.md` (RUL34/RUL37) as requiring a real human confirming failing-test-first proof for a self-modifying diff. This is the one stop this audit found zero grounds to soften. |
| `merge-conflict` block | `approve`'s genuine-conflict branch (`merge.mjs:990-1000+`, tsk-18a classification) | **Load-bearing when genuine content conflict** — but note `mergeReadiness` already excludes footprint-declared conflicts from `ready` (§5), so a `merge-conflict` outcome that still occurs means either a declared footprint missed real overlap, or content-level conflict within disjoint footprints. Worth a footprint-accuracy audit (out of this item's scope) since every occurrence currently burns a full human stop. |
| `merge-blocked-other-item` | tsk-4hj's new outcome, catchup-retryable | **Mostly mechanical** — the doc itself frames this as "the blocking item's own merge will eventually finish or get aborted by a person" and routes it through `fgos catchup`, i.e. **self-heals without a human** once the other session's merge resolves. Only escalates to a human if it recurs/stalls — already the cheapest tier of stop in the system. |
| `verify-fail-post-merge` | merge-loop step 4, `docs/how-to/diagnose-a-verify-fail-post-merge-block-on-approve.md` | **Already machine-driven, not a human stop** — this is the one block reason the merge-loop skill agent-diagnoses itself: reads output, checks whether the failing test is in the item's own diff, reproduces in isolation, fixes pre-existing bugs directly on `main` if genuine, retries once. Only escalates to a human if the retry makes no progress. This is the template the rest of the table should be measured against — it proves the loop *can* absorb a block reason without a person, when someone has bothered to write the playbook. |
| Plain `verify-fail` (not post-merge) | merge-loop step 4's generic "any other reason" bucket | **Currently mechanical-gap, not load-bearing** — treated identically to merge-conflict/Iron Law (stop after 2 consecutive same-id blocks) even though it's the *same class* of "some test failed" as `verify-fail-post-merge`, which already has a playbook. No stated reason this reason couldn't reuse the same diagnose-and-retry-once flow; it currently doesn't only because nobody extended the playbook to cover it. |
| `integration-drift` | merge-loop's generic block bucket | Not investigated in the files read for this audit — flagged as an open question below rather than guessed at. |
| `lock-ambiguous` | `withLockRetry` never retries this (`lock-wait.mjs:27-29`); recovery is `fgOS:unlock` | **Currently a hard human stop by design** (fail-closed, D5) — but the underlying cause (corrupt/unparseable lock content) is itself always machine-detectable and the `forceReclaimAmbiguousLock` re-read-before-reclaim logic already exists (`main-checkout-lock.mjs:594-615`). The `fgOS:unlock` skill already automates the mechanical part (re-read, refuse only if a live holder is confirmed) — so the human step here is arguably just "run the skill," not real judgment, except in the genuine case where a live different session is confirmed holding it. |
| Same-id blocked twice → hard stop | merge-loop step 4's final bucket, step 6 report | **Load-bearing as a circuit breaker**, but its trigger threshold (any 2 consecutive blocks, even two *different* reasons) is conservative by design, not tuned — every block reason that already has (or could have) a self-resolve playbook shouldn't count toward this counter the same way an untriaged one does. |

**Overall pattern**: of the enumerated stop points, only Iron Law is unambiguously required to stay human. `merge-blocked-other-item` and `verify-fail-post-merge` already got machine playbooks (the newest two items in the merge classification lineage). The remaining reasons (`merge-conflict`, plain `verify-fail`, `integration-drift`) are still lumped into the generic "stop after repeat" bucket mostly because nobody has written their playbook yet, not because they're inherently unresolvable by a machine — the trend line in this codebase's own history (tsk-18a → tsk-4hj → the verify-fail-post-merge playbook) is toward narrowing what needs a human, one classified outcome at a time.

## 5. Parallelism opportunity

- `mergeReadiness` (`graph-harness.mjs:109-258`) already computes exactly the data a concurrent merge scheduler would need: a `ready` set with footprint conflicts (`footprintOverlapAmong`) and dependency/mergeAfter ordering (`waiting`) already excluded, plus `mergeSets` grouping same-root siblings and conflict components for explicit serialization. **The hard part — knowing which merges are mutually safe — is already solved and pure (no fs, no git shell) in this function.** What's missing is a caller that merges more than `ready[0]` per pass.
- Two `ready` items with disjoint footprints and no shared root are, by this function's own contract, safe to merge in either order — nothing currently stops them from merging into main **concurrently** except that `merge-next`/`merge-loop` never ask for more than one at a time, and `main-checkout.lock` would serialize their actual commit step anyway (which is correct and cheap — see §2's "truly needs" scope).
- The real lever: shrink the critical section (§2) so verify runs **outside** the lock (e.g. verify the merged tree in a disposable clone/worktree, only reacquire the lock for the final fast commit), then a `merge-next`-style caller could pop N mutually-conflict-free `ready` candidates and run their (now-decoupled) verify phases concurrently, funneling only the short commit step through the existing single lock. This mirrors exactly the shape `dispatch.mjs` already uses for claim/execute parallelism (`maxRoots`/`maxLeavesPerRoot`) — the pattern exists in this codebase already, just not applied to the merge stage.
- `mergeSets` with `reason: 'shared-root'` already documents which `ready` items must serialize relative to each other (informational only today) — a parallel merge scheduler would read this bucket as its serialization constraint and everything else in `ready` as parallelizable.

## Open questions

- `integration-drift` block reason: not traced to its source in this pass — worth confirming whether it already has (or could get) a diagnose-and-retry playbook like `verify-fail-post-merge`.
- Whether footprint declarations (the `mergeReadiness` conflict input) are accurate enough in practice that `merge-conflict` outcomes are rare "real" conflicts vs. frequent footprint-declaration misses — this determines how much of that stop is fixable by better footprint tooling vs. inherent content risk.
- No file found showing `events.lock` has ever actually timed out in production dispatch (only the test-scale flake, tsk-3wn) — the 16-wide dispatch concurrency concern in §3 point 4 is a plausible risk, not an observed incident; worth a real measurement before prioritizing a fix.

Of the human stop points, only Iron Law is genuinely load-bearing — merge-blocked-other-item and verify-fail-post-merge already got machine playbooks, and merge-conflict/plain verify-fail/integration-drift are lumped into a generic repeat-stop mostly for lack of a written playbook, not inherent unresolvability.
