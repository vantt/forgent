# Review: docs/platform/config/spec.md, standard + only-differences + machine files

Line numbers are of the current working-tree file. Read-only review; owner decisions 1-4 not reopened.

## High

**H1. Migration drops values that currently shadow a differing global (L63, L246, A19).** Today project beats global. A project value equal to the standard but sitting over a different global value is a pin. Dropping it flips the effective value on that machine to the global one. The equivalence check ("effective value read through the new files", L244) will either fail or, if run without the global file, pass while behaviour changes.
Wording (L246): "drops every value equal to the standard unless a global file on this machine holds a different value for the same path; those are kept with `@fgos:why [migrate] pins the standard over a machine override` and listed in the report. The equivalence check reads the machine's own global file in both views."

**H2. The "1290 lines are copies of the setup seed" claim is false for capabilities (L63, L326).** I compared `DEFAULT_CAPABILITY_SLOTS` (`src/setup/registrations.mjs:2262`) with `runner.capabilities` in `.fgos/config.json`: 0 of 36 seed entries are equal (the file has 42 entries, 6 not in the seed). The file entries carry `prefer` pools and `confinement: required/host-write-denied` where the seed has `unconfined`. `modelPolicies`, `tierFallback`, `patterns` and `defaults` also differ from `DEFAULT_RUNNER_CONFIG`. Only `confinement` is equal. `runner.executors` has no seed in `DEFAULT_RUNNER_CONFIG`; the seed is `PI_EXECUTOR_DEFAULT`. The line counts are right (capabilities 22-780, so 759 lines), but "copies" is not. Consequences: (a) the evidence line of the decision is wrong; (b) A19 "drops every value equal to the standard" will drop almost nothing from this file unless the standard descriptors are authored from this repository's current catalog, which is a decision the spec does not name.
Wording: replace "are copies of the setup seed" with "were seeded by setup and since edited by hand; whether an entry equals the new standard is decided when the standard is authored (section 4)". Add to section 13 who authors the first standard and from which source.

**H3. "Hidden from every confined worker" is not what the confinement code can do (L201, A18).** `resolveBlindHiddenRoots` (`resources.mjs:197-217`) keeps only directories (`isDirectory()`), and bwrap hides them with `--tmpfs` (`drivers/bwrap.mjs:584`). Hiding runs only in the `blind` branch (`requestIsBlind`), and `{fgosDir}` is the project's directory, not `~/.fgos`. So "both paths join the hidden set" is not an addition of two strings: it needs file masking (for example `--ro-bind /dev/null <file>`) outside the blind branch, plus a home-directory token. The spec also does not say the owner of that change: `docs/platform/secrets/spec.md` L231 gives confinement to the confinement owner, and L204 and L306 keep the extension as an open question 4, with the live-probe result in L334 (a worker read `secrets.local.env`).
Wording: "This needs a confinement change the Config slice depends on: an unconditional file mask for these two paths in the bwrap driver and a `{homeFgosDir}` token. It is owned by the confinement spec (`docs/specs/confinement-authority.md`) and cross-referenced from secrets spec section 15 question 4. Until it lands, the accounts and token files are no better protected than `config.json` is today." Also add this row to gate list (section 16) and to the six questions Q3.

**H4. Backups and leftovers defeat the hiding (L252, section 13).** The global backup (old `config.json` with accounts and token) goes to `~/.fgos/runtime/config-migrate/`, which is not hidden. A stale `~/.fgos/config.json.bak-20261021-llmaccounts` exists today on this machine. Hiding only the two named files leaves the same secrets readable.
Wording (section 9): "The hidden set is `~/.fgos` minus the paths a worker needs (listed), not two file names; a global backup holding accounts or the token is mode 0600 and lies under the hidden set. Doctor reports `config.json.bak-*` files in `~/.fgos` that still hold an account pool or token."

## Medium

**M1. Redundancy is judged against what? (L63, A5, L172).** For a project file the inherited value includes the machine's global file, so the verdict varies by machine, and a project value equal to the standard over a differing global is a legitimate pin. "No door writes a value equal to the one it would inherit" would refuse that pin.
Wording: "Redundancy is judged per file against the layers below it that every teammate shares: a project value is redundant when equal to the standard, never judged against the global file (machine-local); a global value is redundant when equal to the standard. A value equal to a `detected` value is never redundant (the detected value varies by machine)." Also state what `set` does with an equal value (no-op with a named notice, or `unset` if the key exists) and that `config-redundant-value --fix` on a key with `@fgos:why` needs the `comment-would-be-lost` acknowledgement (L178).

**M2. Where `detected` sits in the ladder (L61, L120, L188, L63).** Section 3 lists project > global > standard; section 5 adds `detected` as a provenance without a rank. Is it below global, above standard? Does a standard value for `runner.executor` exist? Wording: "`detected` ranks between global and standard, and applies only to keys whose descriptor says `absent: detected` (no standard value). A project or global value always wins over it." Add `detected` to the `absent` field (L91).

**M3. Renamed or removed standard entries stay forever (L98).** An entry a project copied (a capability, executor, tier name) that a later standard renames or deletes remains as a valid `<any>` key; `config-unknown-key` does not see it because `<any>` matches everything. This is the exact failure the revision cites (`rigorToTier`). Also the spec says "copies that one entry" (L98), but the merge is deep by default (yaml-document L118), so a copied whole entry freezes the fields the standard may later change.
Wording: "A file writes only the fields it changes (`runner.capabilities.code:review.confinement.mode`), never the whole entry; an entry that the standard lacks and no descriptor owns is reported `config-unknown-key`. A descriptor may list `retired` entry names; a file entry under a retired name is an error naming the replacement." (the second sentence is a new mechanism, see list below.)

**M4. How a file removes or disables an inherited entry (L98).** Under per-entry deep merge, a file cannot delete a standard capability or executor. YAML Document L119 says a present `null` wins as null, but Config says nothing on whether `null` is a legal entry value. Wording: "To switch off a standard entry a file sets it to `null`; the descriptor of a `map of T` states whether `null` is allowed; an entry set to `null` is not a redundant value."

**M5. Account and token moves are two files, not one transaction (L142, L254, L190).** Moving a pool from `config.json` to `accounts.yaml` is a write to two files; the spec states the one-source rule (L148) but not the order or the crash state. Also the token file is not YAML, so steps 3 and 4 of the transaction (YAML Document, schema, comments, `@fgos:why`) do not apply to it, and its creation needs a create-only 0600 open.
Wording: "Migration and `config-key-in-wrong-file --fix` write the destination first, verify it, then remove the key from the source; a crash between the two leaves the key in both, reported as `config-key-in-wrong-file`, and the destination wins. The token file is written by Durable File create-only with mode 0600 at creation, content one line and a final newline, no comment grammar."

**M6. Confined snapshot and the accounts layer (L201, L249-L250).** `config-accounts-unavailable-confined` is defined for "a verb that needs the pool", but `snapshot()` itself has no stated behaviour for a confined caller: is the `accounts` layer empty, an error, or absent with a provenance note? Nested `fgos dispatch decide`/`explain` inside a worker would diverge from the outer view. Wording: "A snapshot taken by a confined session has no `accounts` layer and says so in its provenance (`accounts: unavailable-confined`); only verbs that lease an account fail by name."

**M7. Descriptors have no way to say which file a key lives in (L89, L61).** `scope` is `both|project-only|global-only`. `config-key-in-wrong-file` "naming the file it belongs in" needs a `file` field (`config`, `accounts`, `token`). Wording: add a row `file | config (default), accounts or token; a key of another file is refused in config files by name`.

**M8. Stale remnants of "init writes keys / defaults get materialized".**
- L116: "its callers receive the in-memory defaults and the list of keys a newer release describes but the file lacks". A file never lacks a standard key now. Delete the second half.
- L227 end: "`doctor --fix` for missing keys". Same. Say: "`init` for missing files; `doctor --fix` applies the fixes it reported (redundant values, wrong-file keys, permissions, doc drift)".
- L39 `suggestion` "written only when setup materializes the key": section 6 says init writes "any value setup chose". State once who writes a suggestion and when (init only, with `[setup:suggested]`).
- L176 and L323 history, "departs from the default" for missing-why: with only-differences every value departs. Say `config-comment-missing-why` applies to every value in a file.
- L172: "departs from the default or inherited value and no reason is given": same simplification (every `set` needs a reason, except the no-op case of M1).
- L190 "the key is `sensitivity: secret-value` (section 9) while it is read" and L197 "(only `gateway.token`, until it moves)": say "until it moves into Secrets".

**M9. Section 9 safety bullets still mention only the global file (L198, L199, L200, A7).** The no-echo fixture breaks "the line next to the token in a global file": the token is no longer there. The no-follow rule says "the global file inside `~/.fgos`". Mode 0600 says "the global file". Account entries can hold login-store paths (see `src/runner/dispatch/llm-accounts.mjs` shape, not read in full by me), and the spec gives accounts no `sensitivity`, so `show` prints them. Wording: extend the three bullets and A7 to "the global, accounts and token files"; move the fixture to the token file and to an accounts file with a broken adjacent line; give the account keys a sensitivity (state which, and whether `show` prints them to unconfined users).

## New mechanisms, listed separately (not recommended unless owner picks them)

1. A `retired` list on a catalog descriptor (M3). Problem: stale copied entries silently survive; evidence: `rigorToTier` (`registrations.mjs:637`) needed a one-off check. Benefit: one generic doctor error instead of a hand-written check per retirement. Alternative without a mechanism: write only changed fields and let doctor warn on keys not in the standard (needs a descriptor-owned name list for `<any>` maps).
2. A file-mask path in the confinement driver (H3). It is required by decision 3, so it is a dependency rather than an option; flagged because the spec treats it as a one-line change.

Status: DONE_WITH_CONCERNS
Summary: The revision is mostly consistent, but four high issues remain: migration can flip behaviour against a differing global, the "copies of the setup seed" evidence is false (0 of 36 capabilities equal the seed), the confinement hiding is not a drop-in (directory-only `--tmpfs`, blind-only), and migration backups leave the secrets readable. Several stale old-model sentences (missing keys, missing-why wording, section 9 fixtures) and one wrong symbol name (`stripDollarComments`, really `stripConfigComments` at config.mjs:280) need fixing.
