# Inventory of Git Harness Lessons for Rust Component Migration

**Date**: 2026-10-17  
**Role**: Researcher  
**Scope**: Read-only inventory of all git harness lessons recorded across repository documentation (`docs/`, `plans/`, `archive/plans/`, `doc-registry.json`).

---

## 1. Executive Summary

fgOS is preparing to unify and replace its fragmented git harness implementations (which currently span `src/runner/merge.mjs`, `src/runner/worktree.mjs`, `src/runner/main-checkout-lock.mjs`, `src/runner/main-checkout-activity.mjs`, `.githooks/pre-commit`, `src/runner/execution/commit-unit-work.mjs`, `src/runner/execution/unit-sync.mjs`, `src/workflow/integrate.mjs`, and `packages/distribution/rust/src/lock.rs`) into a single, cohesive, high-performance Rust git component.

Over the evolution of fgOS, git operations—specifically around **locks, concurrency races, worktree isolation, merge gates, commit scoping, and crash recovery**—have been the single most frequent source of subtle, high-severity bugs, silent data-loss incidents, and inter-session deadlocks.

This document synthesizes an exhaustive inventory of **55 concrete lessons** extracted from historical post-mortems, architecture decision records (ADRs), journals, design reports, and doc-registry entries. Particular scrutiny is applied to `lock` and `race` categories, followed by an audit of areas where current code has drifted from or failed to implement documented lessons.

## 3. Lessons Claimed in Docs but No Longer (or Never) Implemented in Code

The following 8 concrete gaps were discovered where documentation, specifications, or historical decision records assert invariants that current codebase either **no longer implements** or **never implemented** in newer subsystems:

### 1. Workflow Runner `integrate` Step Violates Core Platform Merge Laws
* **Doc Claim**: Platform Laws L10 (`docs/platform-foundations.md`), `docs/specs/runner.md:3030-3038` (D-ADR0042), and `docs/specs/runner.md` state:
  1. The runner *never* merges directly into the main checkout (`unit-sync.mjs:24`).
  2. All lands into target trunk must use isolated worktree verification and atomic CAS commit trees (`git write-tree`, `git commit-tree`, `git update-ref`).
  3. Merges must be executed `--no-commit --no-ff`, verified on the staged tree, and aborted if verify fails.
* **Actual Code State in `src/workflow/integrate.mjs:99-130`**:
  - In `mergeWorkflowBranch`, when `currentBranch === targetBranch` (the main checkout is on trunk), the code directly executes `git merge --no-ff` **inside the main checkout itself** (`integrate.mjs:113-114`).
  - It acquires **no lock** (`main-checkout.lock` or target slot lock).
  - It performs **no pre-commit test verification** and has no abort on failure.
  - In the temporary worktree branch (`integrate.mjs:116-126`), it runs bare `git merge` with immediate commit, bypassing CAS (`git update-ref`), and swallows removal errors in `cleanupWorkflowWorktree`.
* **Risk**: High risk of corrupting trunk or clobbering concurrent developer edits when running workflow integrate steps.

### 2. Workflow `createWorkflowWorktree` Omits Isolation, Provisioning, and Setup Commands
* **Doc Claim**: ADR0020 (`docs/specs/runner.md:1692`) and tsk-2vd (`docs/history/worktree-dependency-provisioning/CONTEXT.md`) require that every worktree stood up for execution/verification must:
  1. Have `.fgos/` stripped immediately to prevent state pollution.
  2. Have dependencies provisioned (`npm ci` / `npm install`).
  3. Run declared project setup commands (`runWorktreeSetupCommands`, e.g. `cargo build`).
* **Actual Code State in `src/workflow/integrate.mjs:33-63`**:
  - `createWorkflowWorktree` only executes bare `git worktree add [branch] [path]`.
  - It does *not* strip `.fgos/`.
  - It does *not* provision dependencies (`node_modules` is absent).
  - It does *not* run worktree setup commands.
* **Risk**: Any workflow step attempting verification or compilation in this worktree will fail due to missing dependencies/binaries rather than code defects.

### 3. Hardcoded 60s Verify Timeout in `run.mjs` Diverged from Configurable Goal-Check
* **Doc Claim**: `docs/specs/runner.md` and `src/runner/goal-check.mjs` state that verification commands execute with configurable timeouts (`runner.goalCheck.timeoutMs`, default 180s-300s) to support real test suites.
* **Actual Code State in `src/runner/execution/run.mjs:909`**:
  - Verification is invoked via `execSync(verifyCmd, { timeout: 60000 })` with a hardcoded 60-second deadline.
* **Risk**: Complete test suites (which take ~185s on this repo) are unconditionally killed at 60s and scored as verify failures, breaking automated unit runs.

### 4. `dispatch.claim` Lockfile Claimed in Runner Spec but Writer Deleted
* **Doc Claim**: `docs/specs/runner.md:29` specifies that an assignment run creates a lockfile named `dispatch.claim` in the run's outbox directory to enforce single-live-worker admission.
* **Actual Code State**:
  - The writer was completely deleted during the Coordination Engine (L4) retirement (`2180b4e72` / D-ADR0050).
  - Only cleanup code in `src/verbs/dispatch/recover.mjs:239` unlinks `dispatch.claim` if found. No producer ever creates it.
* **Risk**: Spec drift; a component relying on `dispatch.claim` for mutual exclusion will find it absent.

### 5. Coordination Session Claims (`.fgos/coordination/sessions/*.claim`) in Doctor Checks
* **Doc Claim**: Setup and doctor registrations (`src/setup/registrations.mjs:5919`) still retain checks scanning for and repairing `.fgos/coordination/sessions/*.claim`.
* **Actual Code State**:
  - The entire coordination subsystem was retired in commit `2180b4e72` per D-ADR0050. No writer creates these files anymore.
* **Risk**: Dead checks running in `fgos doctor` looking for relics of an obsolete architecture.

### 6. Rust `lock.rs` is Read-Only and Missing Composite / Beacon Protocols
* **Doc Claim**: Architecture documentation for host runtime and distribution (`docs/platform/host-invocation-routing/architecture/node-to-rust-migration.md`) frames Rust as the native foundation for platform operations.
* **Actual Code State in `packages/distribution/rust/src/lock.rs`**:
  - `lock.rs` only implements read-only inspection of `main-checkout.lock`. It cannot acquire, renew, or release locks.
  - It does not parse composite identities (`pid:ts:rand` used by dispatch locks).
  - It does not support `merge-slot` or the `main-checkout-activity.json` beacon protocol.
* **Risk**: Any attempt to move lock management to the existing Rust crate without implementing write/renew/beacon logic will fail.

### 7. Historical `approve --verify-only` Mode No Longer Implemented
* **Doc Claim**: Knowledge base articles (`docs/knowledge/fgos-approve-s-verify-only-mode-checks-the-current-cwd-not-the-item-s-real-branch/`) describe an `approve --verify-only` mode that runs checks against cwd rather than the item branch.
* **Actual Code State**:
  - In `src/verbs/merge/approve.mjs`, no `--verify-only` mode or flag exists. Verification is strictly executed as part of the full approval and merge pipeline.
* **Risk**: Documentation describes an obsolete CLI flag that was retired.

### 8. Whole-Tree Status Check Fallback in `approve`
* **Doc Claim**: D-ADR0042 and tsk-598 assert that clean tree checks are scoped strictly to `ownFileSet` (committed diff + declared footprint) so unrelated dirty files never block merges.
* **Actual Code State in `src/verbs/merge/approve.mjs:320-335`**:
  - The initial check calls `isMainTreeClean(repoRoot)` which scans the whole main tree unless an explicit `ownFileSet` is constructed and passed down to `mergeRootIntoMainCas`.
* **Risk**: Unrelated dirty files in the main checkout can still block approvals on paths where `ownFileSet` is omitted.

## 4. Key Architectural Prescriptions for the Unified Rust Git Component

When designing and compiling the single Rust git component to replace the Node git harness, the implementation must adhere to these 6 non-negotiable architectural invariants:

1. **One Atomic CAS Landing Door**:
   All merges into target branches (both trunk and integration branches) must use isolated detached worktrees, `git write-tree`, `git commit-tree`, and `git update-ref <ref> <new> <old>` compare-and-swap. Never merge directly into a shared checkout.
2. **Unified Holder-Lock Primitive**:
   Consolidate the 14 duplicate lock implementations into one robust primitive supporting Mutex, Lease (with background heartbeat renewal), and Beacon semantics, recording `ttlMs`, process start time, and token-based re-entry.
3. **Strict Worktree Lifecycle & Isolation**:
   Every created worktree must have `.fgos/` stripped, dependencies provisioned, and project setup commands run. Worktree removal must verify the checkout is not dirty and not currently occupied by the calling process (`cwd`).
4. **Enforced Commit Scoping**:
   Workers must have read-only access to `.git`. The runner alone stages and commits declared `writeScope` paths, excluding pre-existing dirty files and foreign staged changes, using literal pathspecs and null-delimiters.
5. **Pre-Merge Concurrency Discipline**:
   Always verify `MERGE_HEAD` does not exist before attempting a merge. Guard all aborts with `mergeHeadExists`. Skip no-ops when already an ancestor (`is-ancestor`).
6. **Contiguous Event-Log Merge Driver**:
   Maintain the custom merge driver for `.fgos/events.jsonl` that reconstructs sequence contiguity over the union of content lines rather than textual line diffing.
