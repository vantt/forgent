## B. Lock order and lock inventory (what the old code actually does)

Locks and lock-like objects, all file-based, all in `.fgos/` unless noted:

| Object | Identity and judging | Held by | Notes |
|---|---|---|---|
| `main-checkout.lock` | `{pid, ts, ttlMs?}`; numeric pid (liveness + ttl) or string id (ttl only) | claim, a non-slot merge (root-to-main with a lock, sync-root onto trunk), the CAS land step, the checkpoint writer | Default ttl 3 min; heartbeat for long holders; `v` or marker means newer protocol (held, never touched). |
| `merge-slot--<encoded target ref>.lock` | same record; always `process.pid`, no self-recognition benefit needed | `withMergeTargetSlot` around a leaf-into-root or nested sync-root merge | Per target ref; held across the target-tip read, catch-up, ephemeral merge and ref CAS. |
| `dispatch--<encoded cwd>.lock` | composite `pid:ts:rand` identity | dispatch (outside the assigned files) | Dead embedded pid = free at once. |
| `main-checkout-activity.json` (beacon, `runtime/`) | `{v, writer, writtenAt, windowMs}`; a hint, not a lock | pre-commit hook only | 20 s default window; same writer allowed; corrupt or future-dated fails open. |
| `events.lock` / `claims.lock` | outside the assigned files | durable writers / claim writes | `claims.lock` is taken inside `events.lock`. |
| git's own `index.lock` | git | every git index writer | The hook runs while git holds it, so the hook never waits on the mutex. |

Observed acquisition order (outer to inner), reconstructed from the code:

1. Claim: `main-checkout.lock` → (checkpoint under the same hold) → `events.lock` → `claims.lock` (claim-port.mjs:116,165,302-328). The writer identity is resolved before either inner lock (claim-port.mjs:304). The main lock is released before dependency install (claim-port.mjs:360).
2. Leaf-into-root and nested sync-root: target slot → (checkpoint: `main-checkout.lock` taken and released inside, skipped when held) → ephemeral worktree → ref CAS (merge.mjs:804-807,770-827; worktree.mjs:1334-1394). `main-checkout.lock` is NOT taken for the merge itself.
3. Non-slot merge (sync-root onto trunk): `main-checkout.lock` for the whole merge, verify and commit, with heartbeat (merge.mjs:898-967).
4. Root-into-main CAS: no lock during merge and verify; `main-checkout.lock` only for the land (re-check own files → `update-ref` CAS → `read-tree`), acquired with a 60 s wait (merge.mjs:1865-1935). There is no per-trunk slot, so two concurrent root approvals both pay a full verify and the loser fails at `update-ref` (see G-11).
5. Hook: reads `main-checkout.lock` once, never waits (a land takes the mutex before git's `index.lock`).

Self-recognition, TTL, heartbeat, held/ambiguous: see C-009 to C-033. Heartbeat status reaches the commit step through `AsyncLocalStorage` (merge.mjs:60,949-963,1537-1546).

## C. Gaps and latent defects seen while reading (observations, not lessons)

These are facts a Rust rewrite must decide on; none is recommended or decided here.

- **G-1 Residual TOCTOU in compare-then-unlink and compare-then-replace.** Stale reclaim, release-if-own and renew all re-read, compare, then act (main-checkout-lock.mjs:423-442,669-683,733-744). Between the second read and the unlink or replace another process can finish its own reclaim and write a new live record, which this process then unlinks or overwrites. The old code narrows the window but does not remove it, and no test exercises it.
- **G-2 The hook's `.fgos` guards parse newline-separated, C-quoted git output.** `stagedFgosDeletions`, `stagedFgosChangesOnWorkerBranch` and the line-count guard split `diff --name-only` on newlines without `-z` (.githooks/pre-commit:211-248,284-316). With quoting on, a `.fgos/` path holding a non-ASCII byte, tab or quote arrives as `".fgos/…"` and fails the `.fgos/` prefix test, so the guard does not see it. The root-file guard in the same file already uses `-z`.
- **G-3 Two env-trust models.** The unit commit path scrubs every `GIT_*` variable but the identity and config ones (commit-unit-work.mjs:31-41). `merge.mjs`'s `git()` merges the whole `process.env` (merge.mjs:96-105) and the CAS land and worktree calls pass no env at all, so an inherited `GIT_DIR` or `GIT_INDEX_FILE` would redirect them.
- **G-4 The workflow integrate path has no lock, no clean-tree gate and swallows failures.** `mergeWorkflowBranch` merges in the main checkout when the target is its current branch (integrate.mjs:111-113) without `main-checkout.lock`, and on a conflict never runs `merge --abort`, leaving `MERGE_HEAD` behind. Its caller catches every error and then records the step as passed (src/workflow/runner.mjs:496-510, read for context). The `squash` option replaces `--no-ff` with `--squash` (integrate.mjs:106-108), which stages but never commits, yet the function returns `merged: true`; no caller passes `squash` today. The temp-worktree branch fails when the target is checked out in a worktree other than the main checkout. A detached HEAD makes `symbolic-ref` throw. Only the clean current-branch path is tested (WR:200).
- **G-5 Hardcoded `main` beside `detectTrunk`.** `approve.mjs:886` reads `resolveRefSha(repoRoot, 'main')`; `catchup.mjs:112` targets `'main'`; several approve friction texts and return shapes say `main`. `detectTrunk` is used elsewhere. Only `reviewDiff`, `createBranchRef` and the ephemeral fallback have master-trunk tests (MT:2159, MT:2164, WT:441, WT:460).
- **G-6 `refreshUnstartedBranch` is not a CAS.** It checks "branch is an ancestor of target" and then runs `branch -f` or `merge --ff-only` (worktree.mjs:1224-1244); a commit landing between the check and the move is discarded. Every other ref move uses `update-ref` with the old value.
- **G-7 A record stamped in the future never expires.** `judgeRecord` computes `now - ts <= ttl`, which is true for any future `ts` (main-checkout-lock.mjs:280-281). A clock stepped backwards therefore keeps a string-identity or live-pid lock held until the clock catches up; only the beacon clamps a future-dated record (main-checkout-activity.mjs:72-84).
- **G-8 Verify kill is SIGTERM only.** `runCommand` sends SIGTERM on timeout and never escalates, and resolves on the shell's `exit`, so a grandchild the shell spawned can outlive the call (goal-check.mjs:67-72,94-116).
- **G-9 `releaseOnExit` listeners end the whole process.** The SIGINT/SIGTERM handler releases the lock and then `process.exit(1)` (main-checkout-lock.mjs:525-534), so any library caller that opts in takes over process termination.
- **G-10 Some readers still parse non-`-z` output.** `isCheckoutDirty` (worktree.mjs:394), the resync dirtiness and stray-dirt checks (worktree.mjs:898,1066), the `.fgos` sweep in the merge (merge.mjs:1575) and `findCheckoutPath` (worktree.mjs:362-375) read newline-separated text; they only test emptiness or `??`/column prefixes, except `findCheckoutPath`, which cannot represent a worktree path holding a newline.
- **G-11 No per-trunk slot for root-into-main.** Two concurrent root approvals both run the full detached merge and verify; the second fails at `update-ref` and parks as `merge-failed-unclassified` (catchup-recoverable) after paying a full verify (merge.mjs:1767-1921).
- **G-12 `review --github` pushes only the leaf's head branch.** The root base branch is never pushed, so a real PR for a leaf would fail on a missing base; recorded in the code as an accepted limitation (review.mjs:81-88). Not exercised by any real-gh test.
- **G-13 No test for lock recovery after a partially failed reclaim race.** The reclaim path's `retry` statuses (C-005, C-006, C-007, C-008) are exercised only by the happy reclaim and the two-process create race.
