## Mechanisms I had to choose (none were fully specified upstream)

1. **Dev-manifest env var contract (P04)**: named `FGOS_ACTIVE_RELEASE_PATH` (release root) + `FGOS_ACTIVE_MANIFEST_PATH` (path to the generated manifest JSON). Chose two separate env vars rather than one combined value so `legacy_exec.rs` (P07) can validate them independently and so a later staged-release activation binding (P09) can set the same two names without inventing a new mechanism.
2. **`RegistrySnapshot` construction / dependency direction (P05→P08)**: the kernel doc says "compile-time constant" but `fgos-distribution` (a leaf provider crate) must not be a dependency of `fgos-host-runtime` (the kernel), per the architecture's stated layering ("provider adapters depend on component protocols, not host presentation"). I resolved this by making `registry.rs` export a public `build_snapshot(catalog, providers, fingerprint)` constructor rather than a single hardcoded `const`; `fgos-host-runtime`'s own tests use it with only in-crate fixtures (P05/P06), and the *production* snapshot is assembled once at the `apps/fgos` composition root (already path-depending on both crates since P04), which is the only place allowed to know about both. P07 assembles it with just the echo fixture (proving `version` fails closed pre-P08 with `no binding`); P08 extends the same call site to add the real distribution provider. I flagged this explicitly inside P05's requirements so the Doer doesn't build a single opaque `const` that P08 can't extend. This is a real design decision, not just a formatting choice — worth the Lead's eyes if they'd rather have host-runtime own the full binding differently.
3. **Fixed fingerprint instead of a runtime hash**: since R1's catalog/provider set never changes at runtime, I specified a fixed `&'static str` fingerprint literal rather than a computed hash, so `RegistrySnapshot` can stay genuinely `const`-friendly in the test-only path. Flagged as a documented trade-off, not silently assumed.
4. **Module-graph assertion (P06)**: chose a source-text `include_str!` + `use`-line scan integration test (`tests/module_graph.rs`) over a clippy `disallowed_types`/lint-list approach, since the constraint is about which modules `use` which others, not which types are constructed — a lint list would need per-symbol maintenance as the crate grows, while the source scan directly encodes the two forbidden edges named in the task (kernel modules never importing invocation/authority modules; the two test-only projector shims never importing each other).
5. **Recorder sink (P07)**: `FGOS_INVOCATION_RECORD_PATH` env var, JSON-lines append, no-op when unset. Chosen because the P02 harness needs a deterministic, inspectable file to assert "one invocation record per exec" against, and because it lets `legacy_exec.rs` and `InvocationService`'s own `record` stage share one recorder entry point (P07 requires calling the *same* function P06 defined, never a second logging path) without needing a running collector process.
