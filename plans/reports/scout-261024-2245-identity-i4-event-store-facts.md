## 3. Reading events

- Rust `read(...)` in `packages/event-store/rust/src/read.rs:424`; `ReadRequest {layout, origin, streams, cursor, folded, project}` (line 39). It discovers tips for own refs and mirrors (`Tip {name, oid, machine, scope, mirror}`, line ~50). Node: `store.read({streams, cursor, folded, project, checkpoint}, heldRanks)` (`native.mjs:~92`), answer includes `sequence`, `cursor`, `deferred`, `missing`, `legacy`.
- Mirrors: fetch refspec `+refs/fgos/events/*:refs/fgos/remotes/<remote>/events/*` installed by setup (spec lines 417-424). Readers accept only `events/`, `branch-events/`, `local-events/` and exact `legacy` below `refs/fgos/remotes/<remote>/` (spec line 452). Each foreign mirror is verified on its own; a bad one keeps its last good tip and yields a typed warning (spec line ~437). Remote events arrive in the same ordered `sequence` as local ones, so a consumer reading `streams:['project:<name>']` sees every machine's events of that stream after sync. Events with unfetched predecessors are `deferred` (consumer refuses with `event-store-incomplete-history`, as `porting-store.mjs:~63`).
- Cursor: `rebuildRequired` unless new events are own-stream and cover the cursor (spec lines 462-470).
- `fgos rebuild`: the existing door, drops every registered consumer cache and refolds (`src/verbs/events/rebuild.mjs`; spec line 495).
- View location: `<main .fgos>/cache/<name>.json` untracked, rebuildable (spec line 460; `src/state/fgos-file-registry.mjs:35-37`). The history checkpoint is `.fgos/cache/event-history.json`.
- Machine-level consumer: NOT possible as designed. The open root is `<git-common-dir>/fgos/events` (spec line 205 area, section 8), refs live in the clone, mirrors come from the project remote, `rebuildFromStore` is per repo (cwd or repoRoot), and the cache sits under the repo's `.fgos`. A user-level consumer would need its own store/remote design (not found anywhere). So I4's shared directory is per project (repository), fits the existing filter by project id, and a machine with sessions in several projects must append in each project's clone. `eventStoreFacts(cwd,...)` etc. all take a repo cwd (`native.mjs:~150`).
- Reads run outside the gate (`event-store-full-read-under-state` if `hotLockDepth()>0`).

Dependency rule: Event Store never imports a consumer (spec line 135).

## 6. Retention, size, superseding

- Payload size limit: none found. `envelope::line` (`envelope.rs:23`) only serializes; append checks non-empty batch, valid ts, valid cursor keys (`append.rs:160-183`). Only size cap seen: `checkpoint.rs:88` "checkpoint too large" (the cache file). Counters limited to 2^53-1.
- Event count / compaction: none. Spec section 22 (lines 650-652): ref-chain snapshot and compaction is "a later item", opened when a full rebuild exceeds 2 s on the slowest machine; out of scope, section 25 (line 745: hard deletion and ref-chain compaction out). "There is no tombstone protocol" for erasing secrets (line 651). A leaving machine's ref is kept forever (line 450); no retire or delete verb.
- Superseding: the store has no notion of it; the consumer owns the fold. Existing "first wins / last wins per key" precedents: `porting.add` keeps the first add per id (`porting-store.mjs:26-33`); `porting.move` sets status (last in canonical order wins). Order is a deterministic total order with `seen`-based causality (spec section 12); concurrent events from different machines are ordered deterministically, not by wall clock alone (`ts` is informational and a last tie-break only, line 173). A "latest wins per (machine, session key)" view for identity entries must be written by the I4 consumer (add / drop event types, or republish snapshot events); nothing generic exists. Note cost: every republish stays in the chain forever, so publishing should be on change, not on a timer.
