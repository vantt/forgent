## Earlier findings: verification

- **C1 and H1 (ancestor and descendant collisions): fixed.** `restore_checks` (`restore.rs:176-231`) builds a protected set made of every target leaf plus every ancestor. A non-directory ancestor counts as a collision. A target leaf that sits on an existing directory contributes every leaf beneath it, found by a no-follow `symlink_metadata` walk. Any collision path that is not in the index refuses with `restore-untracked-target-collision`, whatever the `reapplyLocalDelta` setting, unless that exact path is listed in `allowedReplacements`. Listed paths are added to the capture set. The test `ancestor_and_directory_collisions_require_exact_permission_and_retain_bytes` covers ignored and untracked, both reapply settings, an ancestor file and a descendant file, refusal, permitted replacement, extraction and acknowledgement. Symlinked parents are refused by `safe_path` for target paths, allowed replacements and captured paths. Submodules (`160000`) and sparse or skip-worktree flags (`ls-files -v` must be all `H`) still refuse. Tracked directories that the target removes leave ignored content in place, because Git only removes directories that are empty.
- **H2 (capacity): fixed.** Only paths that are not in HEAD, or are dirty, staged or untracked, go through `capture`. Clean HEAD paths store only `clean_modes`. Their bytes stay reachable through `expectedHead`, an ancestor of the new HEAD. Local edits made after capture show up as dirty on the drift re-capture, change the digest and refuse before `TargetAttempt`. Test: `clean_large_tracked_bytes_do_not_use_snapshot_capacity`, with a 33 MiB clean file and a snapshot under 100 KB.
- **M1 (corrupt or missing snapshot): fixed.** `restore_observe` (`restore.rs:868-892`) closes an active chain with `AbandonedBeforeAttempt` before an attempt and `recoveryRequired` after one. The warning names the exact cause, and the damaged file is not touched. Because the snapshot now includes `operation_id`, a fresh operation never has the same digest as the damaged evidence. Test: `missing_or_corrupt_active_snapshot_closes_with_evidence_and_allows_fresh_operation`.
- **M2 (incoming executable bit): fixed.** A competing local executable-bit change refuses before the snapshot is stored (`restore.rs:472-484`). Otherwise the incoming executable bits are combined with the saved non-executable bits (`:591-600`). Test: `incoming_executable_mode_and_local_content_survive_and_local_mode_conflict_refuses`.
- **M3 (retention): fixed as the coordinator decided.** Acknowledgement needs a terminal outcome. It durably appends `RestoreAcknowledged`, then releases the snapshots, then compacts through the normal ledger with an explicit `restore_ack` gate (`wal.rs` `compact_restore_ack`). The tests show that an interrupted release can be retried and that an uncompacted acknowledged chain still admits new work.
- **M4 (extraction): fixed.** `listSnapshot`, `extractPath` and `acknowledge` go through the existing port. They pass through Rust, the addon and Node, and use the same custody/writer authority.
- **L1-L4: fixed.** The `unwrap` is gone. L2 compares full blob ids (`--no-abbrev`) and refuses any overlap between local content and destination content before an effect (test `overlapping_offset_hunks_refuse_before_effect`). L3 preserves intent-to-add (test `intent_to_add_survives_reapply`). L4 reports `restored` with a `restore-post-check-failed` warning.

## The specific questions

- **Can the seven-day expiry delete a snapshot that is still needed?** No. `prune_restore_orphans` treats every snapshot referenced by any uncompacted chain that has an intent as referenced. That covers active chains, terminal-but-unacknowledged chains, and acknowledged chains not yet compacted (`retained` skips only compacted ids). It removes only files that are older than seven days, unreferenced, and either parse as valid snapshots or are recognised `.durable-file-*.tmp` files. Corrupt and unknown files are never removed. The one unbound window lies between storing a snapshot and calling `begin`. A snapshot in that window is fresh, unless it is a deduplicated file left by a crash under the same operation id. Even then, the `read_restore_snapshot` at `restore.rs:529` runs before `TargetAttempt`, so the worst case is an abandoned chain, never a reset without a snapshot.
- **Can extractPath write outside the directory or follow a symlink?** No. It writes only `destination/<basename>`, and `file_name` can never be `..` because the name passes `fgos_scope_literal`. The destination must be an existing directory. It is canonicalized and checked against the canonical checkout, main and common-dir roots. The file is opened with `create_new` (O_EXCL), which does not follow a symlink at the final component and never overwrites, at mode 0600, and is fsynced.
- **Does acknowledgement bind the right identity?** Yes. It requires the held checkout scope and goes through `restore_evidence_authority`, which matches worktree root, writer identity, resource set and the custody lock-file dev:ino. It refuses a non-Restore id and an already-compacted id, and needs a terminal outcome. The digests it releases come from that operation's own chain. Since every digest includes the operation id, one operation's acknowledgement cannot release another operation's bytes.
- **Any new permanent block?** None found. Expiry runs only inside `store_restore_snapshot`, so its failure modes refuse a new restore and never affect admission. A corrupt snapshot now closes its chain instead of blocking.
- **Glob-character paths.** The new `add --intent-to-add -- p` and `diff --raw HEAD -- p` calls do not pass `--literal-pathspecs`. A probe with an intent-to-add file literally named `n*` next to an untracked `nX` showed the whole operation refused up front with `unscopable-conflict-path`. Pathspec magic therefore cannot reach these calls, and this is not a finding.

## Findings

**Critical: none. High: none. Medium: none.**

**Low**

- **N-L1. On case-insensitive filesystems, a case-only rename is falsely refused** (`restore.rs:217-231`). Example: HEAD tracks `Readme` and the target renames it to `README`. `symlink_metadata("README")` resolves to `Readme`, which is not in the index under that spelling, so restore refuses with `restore-untracked-target-collision: README`. This is fail-closed, not data loss, and listing `README` in `allowedReplacements` is a way out. Fix: before declaring a collision, compare the on-disk name with the index case-insensitively (or with a `core.ignorecase` lookup). Alternatively, document the workaround. I inferred this from the code and could not probe it on Linux.
- **N-L2. extractPath is only blocked from three roots** (`restore.rs:704-709`). It refuses this checkout, the trusted main root and the common dir. A sibling linked worktree outside the main root, or the fgOS state root, is accepted. A canonicalize-then-open TOCTOU also exists when someone else can write to the destination's parents. `create_new` prevents overwrites, so no bytes can be lost. Fix, if wanted: also refuse every registered worktree root and open the final file through a directory fd (`openat`).
- **N-L3. The spec says more than `listSnapshot` does.** Spec §SafeRestore says "clean paths are reconstructed from the expected commit". In fact `listSnapshot` returns only captured paths, and `extractPath` on a clean path returns `restore-path-has-no-retained-bytes`. Fix: change the wording to "clean paths are not listed; read them from `expectedHead`". Separately, every snapshot store re-reads every old unreferenced snapshot file (each up to 128 MiB) and two full `retained(100_000)` scans run per acknowledge/store. This is performance only.
