## 3. Convention: registering a new kind

- Single source: `packages/convention/contracts/convention.rules.v1.json` (embedded by Rust via `include_str!`; spec `docs/platform/convention/spec.md:60`). Top-level keys: `contract, errorCodes, rules, identifiers, definitionFiles`. Rust: `packages/convention/rust/src/rules.rs` (`IdentifierRule` `:43`, `identifier(id)` `:276`), `operations.rs`, `provider.rs`; goldens `packages/convention/contracts/convention.golden.v1.json` + `packages/convention/rust/tests/golden.rs`.
- Admission (spec section 1, `:22`): a rule enters only when it is a deterministic generate/resolve/check of a name or repo-relative path, backed by golden cases for generation or resolution plus checking. "A deterministic format used by a state owner may become a later convention kind; allocation and uniqueness remain with that state owner" (`:34`). So id/handle SYNTAX goes to Convention; minting and uniqueness stay with Identity (consistent with spec section 4 rule 5).
- Two existing shapes: `name-template` (kinds `report`, `plan`, `journal`; operations name/path/check/classify, `convention.rules.v1.json` rules array) and `placement-glob`. Neither fits an id-syntax kind.
- The shape that fits: `identifiers[]` entries `{id, description, first, rest, maxLength, reserved[]}` (a character-class identifier). Example: `seat-id` = first `a-z`, rest `a-z0-9-`, maxLength 40, reserved [runs, outbox, inbox, inputs, unit-control, control, sync, verify, verifier]; also `workflow-name` (64), `agent-name` (64).
- **Gap:** an `IdentifierRule` has no separators beyond one `rest` class, so `<cli>-<chars>@<machine-handle>` (contains `@`) and a hex-128 project id / `<machine-slug>-<base32x6>` with fixed length are not expressible as is. Either register separate identifiers (`machine-id`, `project-handle`, `cli-name`, `session-suffix`) and compose in Identity, or extend Convention (rules.rs + operations + goldens + doctor). Whether `check` exposes identifiers by CLI should be verified in `operations.rs` before planning (not read here).
- Convention doctor row: `convention-conformance` (`docs/specs/distribution.md:77`). Convention route: `command-routes.json:121` (`convention`, native, `convention.query`), `apps/fgos/src/main.rs:110,120,247`.

## Contradictions and risks vs the spec

1. Spec section 3 says Event Store "minted by setup" and section 4 says the machine id lives in "user state root (`~/.fgos`)". Real code uses `<stateRoot>/machine-id` (`~/.local/state/fgos` here, not `~/.fgos`); the setup fix is dormant (not registered). Spec section 7 I2 "Event Store reads it through this component; suite unchanged and green" is about a dormant crate and no machine id exists on this machine yet; I2 can define the mint door without disturbing Event Store only if `identity::machine_id` stays the reader path or is re-pointed in one change (L10).
2. Spec section 3 "Store id ... fits as the clone id; no human short form": `store.json` is created only at the first append (`initialize_under_append_lock`, `identity.rs:165`), so a clone has no store id until Event Store is active; "clone" identity cannot be minted by setup on this repo today. Verify before promising `<project-handle>@<machine-handle>` in I1/I2.
3. Spec section 4 "Project id ... minted once by the first `fgos setup` in a repository without one" in a tracked file: setup can only write it from the main checkout; worktrees do not carry `.fgos/` (strip, ADR0020), and worker branches cannot commit under `.fgos/` (pre-commit tsk-5pb). The file must be created via a main-door commit.
4. Handle shape contains `@`; Convention identifiers have one `first`/`rest` charset (no separators), so section 4 rule 5 needs either composed identifiers or a Convention extension (rules.rs, operations, goldens). The mailbox name alphabet `[A-Za-z0-9._-]` does not allow `@`, so mailbox address and handle cannot be the same string without changing one alphabet.
5. `fgos identity` has no subcommand support in its route (`command-routes.json:405-420`); `resolve` and `list` need `subcommands: true` + flags and a projector change, and the output contract `{id, source}` is version 1.0.0 with `golden.v1.json`.
6. Phase 6 of HARDEN T1 is pending and edits the session-identity crate, node-addon `lib.rs`/Cargo, `src/util/session-identity.mjs`, `facts.rs`, `architecture-manifest.json`, `component-boundary.md`: serialize any I1-I4 edit to those after it lands, or build the new crate (`packages/identity/rust`) without touching them. `docs/platform/component-boundary.md` and `docs/architecture-manifest.json` are shared files in the board's collision list; edit the board row first.
7. I4 depends on Event Store publication, which is dormant and has an empty consumer registry; adding the identity event type means adding the first consumer to `consumers.v1.json` (needs `cachePath` and `rebuildModule`, i.e. a rebuildable local view) and an Event Store cutover decision from the EVENT-STORE/WORK lanes.
8. `.githooks/pre-commit` only checks root files with no `/`; `.fgos/project.json` is safe, but `fgos doctor`'s `event-store-legacy-layout` (post-cutover) inspects tracked `.fgos/events*` families only, so no conflict with a new `.fgos/project.json` name; avoid any name under `.fgos/events*`.
