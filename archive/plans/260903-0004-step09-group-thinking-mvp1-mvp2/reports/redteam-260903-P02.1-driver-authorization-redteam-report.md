## Verdict

**BLOCK — one HIGH finding.**

`createSessionAssignment`'s self-heal fast path skips the lock-held
"one authorization materializes at most one Assignment" check. A real crash
followed by real concurrency makes ONE `operation-authorized` event
materialize TWO Assignments — the exact double-dispatch hole this cell's Bug
Taxonomy names — and the resulting event log is then permanently unreadable
(`replaySession` throws `duplicate-ref` on every subsequent read, including
the session's own recovery path).

Reproduced end to end with **no file surgery at all**: a genuine `SIGKILL`
produces the crash state, then two real OS processes both dispatch
successfully against the one authorization. 2/2 reproductions once the crash
state was reached; 10/20 and 7/12 in the higher-throughput variant that
constructs the same crash state directly.

Everything else held. Attacks 1, 2, 5, 6, 7 and 8's gate-bypass question
turned up no additional defect across 100+ real multi-process trials.

## Findings

### HIGH-1 — the self-heal path double-consumes one authorization, then bricks the session

**Where.** `src/runner/coordination/store.mjs`:

- `createSessionAssignment`'s lock-held consumption check sits at
  `store.mjs:557-567`, *after* the `if (fs.existsSync(taskClaimPath))` branch
  at `:517` has already `return`ed or self-healed.
- The self-heal branch at `:532-546` calls `completeAssignmentRegistration`
  and forwards `authorizationProvenance` into it — and
  `completeAssignmentRegistration` (`:354-367`) appends `assignment-created`
  with that provenance. It never runs the consumption check.

So the check guards the genuinely-new-taskKey path only. The self-heal path
writes a consuming `assignment-created` with no consumption check at all.

**Why the pre-lock gate does not save it.** `dispatchDeclaredOperation`'s
gate (`session-engine.mjs:1358-1400`) reads via an unlocked `replaySession`,
resolves an unconsumed authorization, and only later takes the lock inside
`createSessionAssignment`. Two processes can both pass that unlocked gate on
the same authorization; the lock-held check exists precisely to break the tie,
and the self-heal path bypasses it. This is the same pre-lock-advisory /
lock-held-authoritative split the file's own comments describe for
`maxRoundsForActor` and the aggregate bounds — with one branch missing.

**Reproduction A — end to end, no file surgery**
(`probe-endtoend-kill-then-race.mjs`):

1. Real session, real `authorizeDeclaredOperation` (`auth_recheck_1`).
2. A real dispatching process is `SIGKILL`ed at a jittered time; rounds are
   discarded unless the kill landed in the window store.mjs documents
   ("crashed at or after `assignment.json` was written but before the
   `assignment-created` event / `assignmentRefs` update completed") — claim
   file + `assignment.json` present, no `assignment-created`, no ref.
3. Two real OS processes then dispatch the same driver-authorized binding:
   one with a genuinely new `taskKey`, one resuming the crashed `taskKey`.

Result, both times the crash state was reached:

```
round 2: genuine crash state reached by SIGKILL (claim -> asgn_coordinator_1_op_001, no assignment-created, no ref)
  new taskKey T1 -> Assignment asgn_coordinator_1_op_002
  resume  taskKey T2 -> Assignment asgn_coordinator_1_op_001
  assignment-created events consuming auth_recheck_1: 2 ["asgn_coordinator_1_op_002","asgn_coordinator_1_op_001"]
  replaySession afterwards: THROWS duplicate-ref: authorization "auth_recheck_1" is claimed by more than one "assignment-created" event
round 17: (identical)
crash-states reached=2 double-consumption reproductions=2
```

**Reproduction B — crash window reachable by a real kill**
(`probe-genuine-crash-window.mjs`, 24 kill attempts, log padded with valid
non-matching `operation-authorized` lines only to widen the target window;
no code path altered):

```
{ "CRASH-WINDOW HIT: claim + assignment.json, no assignment-created, no ref": 3,
  "fully registered": 5, "killed before any claim": 16 }
ATTEMPTS=25 GENUINE-CRASH-WINDOW-HITS=3
```

**Reproduction C — rate, with the crash state constructed directly**
(`probe-selfheal-double-consume.mjs`; the parent holds the session's real
`events.lock` so both children clear their unlocked pre-lock gate, then
releases): **10/20** and **11/20** in two independent runs (7/12 in an earlier
shorter run). Both children returned success in every double-consumption trial.

**Damage, measured** (`probe-selfheal-evidence.mjs`):

```
  A: {"ok":true,"assignmentId":"asgn_coordinator_1_op_002","resumed":false}
  B: {"ok":true,"assignmentId":"asgn_coordinator_1_op_001","resumed":true}
  asgn_coordinator_1_op_002: runs=1 withAgentResult=1
  asgn_coordinator_1_op_001: runs=1 withAgentResult=1
  replaySession:        THROWS duplicate-ref
  subsequent dispatch:  THROWS duplicate-ref
```

Two distinct Assignments, each with a completed executor run, against one
driver authorization — then every later read of that session fails.

**What it violates.**

- store.mjs's own invariant text: "one authorization materializes at most one
  Assignment".
- `current-cell.md`'s Bug Taxonomy: "the R4 gate itself must not accidentally
  let a SECOND dispatch reuse a FIRST authorization silently".
- `P02.1.md`'s Gaps claim that consumption is "enforced in TWO places —
  advisory pre-lock … and AUTHORITATIVELY lock-held inside
  `createSessionAssignment`". The authoritative half has a hole.

**Relation to Review LOW-1.** The Reviewer traced this exact path and
concluded it was unreachable because "the pre-lock gate would already have
refused, since the authorization it needs is by then consumed". That holds
only if the gate's view is still valid at lock time. It is not — that is the
TOCTOU the lock-held check exists for. The LOW-1 fix (replay failing closed on
double consumption) did not make this safe; it converted a silent
double-dispatch into a **permanently unreadable session**, which is worse for
recovery. Fixing the write path is what makes the LOW-1 read-time check
unreachable, as intended.

**Smallest fix.** Run the consumption check before/inside the self-heal
branch, exempting only the case where the already-consuming event belongs to
this same claim (a genuine idempotent resume of its own authorization):

```js
// inside the fs.existsSync(taskClaimPath) branch, before completeAssignmentRegistration
if (authorizationProvenance?.authorizationId !== undefined) {
  const consumer = readEvents(eventsPath).find(
    (e) => e.type === 'assignment-created' && e.payload?.authorizationId === authorizationProvenance.authorizationId,
  );
  if (consumer && consumer.payload.assignmentId !== claim.assignmentId) throw new CoordinationError('validation', ...);
}
```

Equivalently: hoist the existing `:557-567` check above the claim branch and
add the `!== claim.assignmentId` exemption. One condition either way.

**Regression test direction.** A test that (a) builds the crash state
(claim + `assignment.json`, no `assignment-created`, no ref), (b) consumes the
authorization with a different `taskKey`, (c) resumes the crashed `taskKey`,
and asserts the resume is refused with zero second consumer — no concurrency
needed once the ordering is fixed by construction.

### MEDIUM-1 — the write path accepts driver-authorization provenance it never verifies

`createSessionAssignment` validates only that an `authorizationId` is not
already consumed. It never checks that the id names a real
`operation-authorized` event, and it never requires an `authorizationId` at
all for the other provenance fields. Probed with a REAL contract captured from
a real dispatch (`probe-bypass-forged-provenance.mjs`):

```
[authorizationId that was never issued]  write: ACCEPTED
                                         replay: THROWS dangling-ref (session permanently unreadable)
[no authorizationId, but operationId/nodeId/invocationKey/contextGrant present]
                                         write: ACCEPTED
                                         replay: clean
```

Two distinct problems:

1. A fabricated `authorizationId` is a second, concurrency-free route to the
   same permanent-unreadability poison pill. Fail-closed on read, but the
   failure lands on the whole session instead of on the bad write.
2. An `assignment-created` can carry `contextGrant: {refs: [...]}` with **no**
   `authorizationId`, and both the write path and replay accept it. R3's
   stated purpose ("so replay can explain why the worker ran and which grant
   made its context legal") is not actually enforced, and R6 (P02.2) is
   designed to enforce reads against exactly this record.

Not exploitable from outside `src/runner/coordination/**` today (Review LOW-3
established there are no external importers), which is why this is MEDIUM and
not HIGH.

*Smallest fix:* (a) in the same lock-held section, require that a provenance
`authorizationId` matches an `operation-authorized` event in this log —
turning the read-time brick into a write-time refusal; (b) in
`schema.mjs`'s `validateEventPayload`, reject an `assignment-created` that
carries any of `operationId`/`nodeId`/`invocationKey`/`contextGrant` without
`authorizationId`.

### LOW-1 (observation, pre-existing — not a P02.1 defect)

`replaySession` reads `session.json` **before** `events.jsonl`
(`replay.mjs:52-58`), while `completeAssignmentRegistration` appends the event
before writing the manifest. An unlocked reader whose two reads straddle a
concurrent commit therefore sees a new `assignment-created` with a stale
`assignmentRefs` and throws a spurious `dangling-ref`. Measured with a reader
loop against 2 concurrent dispatchers: 4-12 spurious `dangling-ref` errors per
3-second window in 18/20 trials (thousands in 2 of 20), with the final replay
clean every time.

Both the read ordering and both dangling-ref checks predate this diff, so this
is not this cell's defect. It is noted because the R4 gate adds another
unlocked `replaySession` consumer on the dispatch path, so a legal
driver-authorized dispatch can now also abort for this reason under
concurrency. Belongs in the forward notes with MED-2, not in this cell's fix
round.

## Attack 4 — is `nodeId` not being independently load-bearing safe as shipped?

**Independent conclusion: yes, safe as shipped — and the comparison must be kept.**

Two things are true at once, and the Fix round's table conflates them:

1. **`nodeId` can never be independently discriminating through the engine
   doors, by construction.** `authorizeDeclaredOperation`
   (`session-engine.mjs:963-983`) ignores the caller's `nodeId` for selection
   and writes `node.id` from
   `resolveDeclaredOperationActor(definition, operationId, targetActorId)` —
   the same deterministic resolver, with the same inputs, that the gate uses
   at dispatch. `nodeId` is therefore a pure function of the other two
   components, so two records agreeing on `(operationId, targetActorId)`
   always agree on `nodeId`. No fixture can make it discriminate. That is why
   the mutation sweep cannot catch dropping it, and no amount of test-writing
   short of MED-2's change will.
2. **It is nevertheless load-bearing at runtime**, against a record written
   through the raw `store.authorizeOperation` door, which has no definition
   awareness. Proved (`probe-nodeid-load-bearing.mjs`): an authorization with
   the real `operationId` + real `targetActorId` but the wrong `nodeId`
   (`phase-first-pass` instead of `phase-recheck`) is written to the log, and
   the dispatch is **refused**. Review LOW-3's "a direct-store authorization
   naming a nonexistent binding is inert" depends on this comparison.

The MED-2 shape itself is fail-safe, confirmed empirically: a definition with
one operation bound to one actor at two nodes (`required` at A,
`driver-authorized` at B) validates; `authorizeDeclaredOperation({nodeId:'node-b'})`
is refused ("that binding lives at node node-a"); the dispatch resolves node
A's `required` binding and dispatches with no authorization at all. Node B's
`driver-authorized` activation never gates anything, but nothing is
*wrongly* authorized: the binding the runtime actually resolved had its own
declared mode honoured. No authorization for one binding can authorize
another today.

**Recommendation (documentation only, no code change):** record reason (1) next
to `resolveBindingAuthorization`, so a future cleanup does not delete the
`record.nodeId === nodeId` comparison as "proven non-load-bearing by
mutation testing" — it is load-bearing against the store-level door, just not
reachable-to-discriminate through the engine door.
