## What was built, per requirement

**R1 — artifact refs.** No new artifact mechanism, deliberately: artifact refs
already exist end to end as `runResult.evidence.artifacts` (produced by
`dispatch/assignment-runner.mjs`, returned to every caller by
`dispatchDeclaredOperation`), rooted under the producing Assignment's own run
directory. The session's job is to LINK them, which
`operation-authorized.targetArtifactRef` and `contextGrant.refs` already do.
The only code R1 needed was making `targetArtifactRef` obey the same
same-session rule the grant does, at both doors — which also closes P02.2's
Red-Team LOW-1 at exactly the moment it said to ("Phase 03's recheck semantics
are what will start reading it"). The test asserts the session directory is
still exactly `{events.jsonl, session.json, tasks}` before AND after a full
grant-plus-recheck cycle, so "not a second artifact authority" is proven, not
asserted.

**R2 — recheck is a new Assignment.** This is the real fix for the
taskKey-derivation gap P02.2 recorded. A driver-authorized invocation's
DEFAULT claim key now carries the id of the authorization it spends:
`declared:<operationId>[:round-N]:auth:<authorizationId>`. Because
`authorizeOperation` already refuses to issue two authorizations under one id
(and one `invocationKey`), two invocations at one binding structurally cannot
be claim-equal — and neither can ever equal a key derived from
`nodeId`+`operationId`+`actorId` alone, which is the shape the contract's
"Recheck Is Not Retry" clause names as forbidden. That forbidden shape is
tested literally: a recheck dispatched with the ORIGINAL review binding's own
default key is REFUSED (by P02.2's silent-discard guard, unchanged), the
original Assignment untouched, the authorization left unconsumed.

The ordering problem this had to solve: the taskKey is what a claim record is
looked up BY, so the authorization cannot be resolved the usual way (which
needs the resumed Assignment id) before the key exists. Resolved with a
separate, small selector (`resolveTaskKeyAuthorization`): prefer an unconsumed
authorization (the invocation being spent), else the most recent consumed one
(a repeat/crash resume, which must land on the key its own invocation first
claimed). The dispatch gate below is untouched and re-resolves exactly as
before. Both resume shapes are covered by test — an idempotent repeat and the
crash-recovery self-heal Red-Team built for P02.2 — and both still pass.

Recheck never supersedes: the original's `result.json` is compared
byte-for-byte before and after, `run-retried` count is asserted 0 (so
`linkResult`'s `allowSupersede` path is provably never entered), and each
Assignment has exactly one `result-linked`.

**R3 — disposition.** A new store door, not a RunResult field and not a worker
Assignment. It mirrors `authorizeOperation` structurally, and its identity
check is literally the same function as R8's — extracted and shared rather
than copied, which is what the Bug Taxonomy asked for. The "never a worker
result" property is shown two ways: the worker's own `result.json` is asserted
not to contain the string at all, and `validateEventPayload('result-linked',
{..., disposition})` is asserted to REJECT the field, so there is no
result-shaped event a worker could smuggle one through.

**R4 — replay.** `replaySession` now also returns `assignments`, `results`,
and `dispositions`. Recheck lineage is the join
`assignments[].authorizationId → authorizations[].targetArtifactRef` (which
artifact revision each Assignment ran against; the original first-pass review
carries no `authorizationId` at all). "From `events.jsonl`/`session.json`
alone" is asserted literally: every answer is re-derived a second time
straight from `readSessionEvents` + `readManifest` and asserted equal.

## The one behavior change, and the two tests it re-pointed

Making the default taskKey carry the authorization id means the two collision
shapes P02.2's silent-discard guard was built for are no longer reachable by
OMITTING a taskKey — which is the root-cause fix P02.2 explicitly deferred to
this phase. Two of its tests drove the collision that way and would otherwise
have failed for the right reason.

Both were re-pointed to a caller-supplied shared `taskKey`, the one way the
collision is still reachable, so the guard keeps exactly the coverage the
Reviewer and Red-Team mutation-verified (mutation-checked again here: both
still fail if the guard is disabled). Nothing was weakened — a NEW test proves
the default path now SUCCEEDS where it used to be refused: a fan-out with no
explicit taskKey materializes two Assignments, one per authorization, each
carrying its own `authorizationId`.

## Open / for the Coordinator to rule on

Everything below is recorded in full in `P03.1.md`'s Gaps section; these are
the ones worth a decision rather than a read.

1. **`disposition` is validated as a non-empty string, not a closed enum.**
   The contract says "e.g. `accepted | rejected`" and also describes "closing
   a round," so shape-only is the literal read. One line to close if Review
   wants a fixed vocabulary. Note this is a DIFFERENT mechanism from
   `session-engine.mjs`'s pre-existing `DISPOSITION_VALUES`, which governs the
   Phase 04 consult-disposition Assignment, not this event.
2. **No session-scope check on a disposition's `targetRef`/`evidenceRefs`.**
   Inert today — nothing reads them into a contract, prompt, or gate — so this
   follows the same "close it when it is read" posture that
   `targetArtifactRef` was held to (and which this cell now discharges for
   that field). If any future surface renders dispositions into worker-visible
   context, the check belongs there first.
3. **Post-terminal dispositions are refused at write time but not neutralized
   at read time**, unlike `operation-authorized`. Deliberate: Recovery Rule
   point 5's neutralization exists so a post-terminal authorization can never
   satisfy the dispatch gate, and a disposition has no gate and materializes
   nothing — discarding a durable driver decision found on the log would lose
   information for no safety gain.
4. **Concurrency is argued from construction plus deterministic tests, not a
   real multi-process reproduction** — the class this track's history says
   sequential tests miss. The specific race worth attacking: two concurrent
   dispatchers with ONE unconsumed authorization now derive the SAME taskKey
   (they must — that is the resume property), so they collide on one claim
   exactly as two same-taskKey callers always have; expected outcome is one
   Assignment plus one refusal/resume, never two.
5. **The shipped-fixture fan-out HIGH is NOT covered by this fix.** The
   authorization-derived suffix applies only to `driver-authorized` bindings;
   a `required` topology-edge dispatch has no authorization to key on, so
   `independent-research-fan-out-fan-in.yaml`'s collision still needs
   `targetActorId` threaded into the topology-edge derivation, exactly as
   `index.md` records. Said explicitly here so nobody reads this cell as
   having closed it.
6. **R5-R7 remain P03.2's**, by this cell's own Non-Goals: no live CLI/no-Work
   run, no consolidated negative-proof battery, no surface-readiness doc.
   `replaySession`'s new return shape is what `show.mjs` will read.
