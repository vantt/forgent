## How the disambiguation requirement was handled

The gate matches an `operation-authorized` record to a dispatch by the
**full `(nodeId, operationId, targetActorId)` triple** — never by `actorId`
alone, never by `operationId` alone. `resolveBindingAuthorization` filters
on all three simultaneously; `nodeId` and `targetActorId` both come from the
binding `resolveDeclaredOperationActor` already resolved, so the gate can
never disagree with the dispatch about which binding it is gating.

Both under-disambiguation failure modes are real in this codebase, not
hypothetical, and the pattern reference was
`resolveDeclaredOperationActor` itself (already correctly keyed by
`operationId` with an optional `targetActorId` disambiguator):

- **One actor, many operations/nodes.** `standalone-master-coordination-loop.yaml`
  binds `reviewer` to `review-candidate` at `phase-first-pass` AND to
  `reviewer-recheck` at `phase-recheck`. Matching by actor alone would let a
  recheck authorization silently materialize the first-pass review.
- **One operation, many actors/nodes.** An independent fan-out cohort shares
  one operation template across N branch actors (the Phase 04 `targetActorId`
  case). Matching by operation id alone would collapse them.

The proof is `coordination-driver-authorization.test.mjs` →
"an authorization for (phase-recheck, reviewer-recheck, reviewer) does NOT
authorize the SAME actor at a DIFFERENT binding". Its fixture reproduces the
`standalone-master-coordination-loop.yaml` shape with BOTH bindings marked
`driver-authorized`, so only correct triple matching can tell them apart:
authorizing just the recheck binding leaves the first-pass review binding
refused with zero Assignments on disk, and the recheck binding then
dispatches. `cohort-planner.mjs` was not touched (Non-Goal).

## How the atomicity requirement was achieved — concretely

Recovery Rule point 5 requires that checking session-active-status and
appending `operation-authorized` share the **same atomic/serialized write
path already used for `assignment-created`**, not a separately-named
lookalike.

The shared path is literal. `store.mjs`'s `authorizeOperation` does its
manifest read, `schemaVersion` check, `status !== 'active'` check,
idempotency read and `appendEventLocked` all inside ONE
`withEventsLock(eventsPath, …)` call. `withEventsLock` derives its lock file
from `path.dirname(logPath)` — the session directory — so this is the exact
same on-disk `events.lock` hardlink mutex that:

- `createSessionAssignment` holds around `completeAssignmentRegistration`'s
  `assignment-created` append + `assignmentRefs` write (Recovery Rule
  point 2, the precedent point 5 names), and
- `transitionSessionStatus` / `transitionSessionStatusLocked` hold around the
  terminal event append + `session.json` status write.

A concurrent `transitionSessionStatus` therefore cannot interleave between
this status check and this append: whichever call wins the lock runs to
completion first, and the loser re-reads the manifest the winner already
wrote.

**This was proven discriminating rather than asserted.** The test
"the active-status check and the operation-authorized append share ONE held
events-lock critical section" spawns a worker thread that acquires the
session lock via `withSessionLock`, posts `locked`, sleeps 400ms, then calls
`transitionSessionStatusLocked(…, 'cancelled', …)` inside that same held
lock. The main thread waits for `locked`, asserts the manifest still reads
`active`, then calls `authorizeOperation` — which blocks on the lock,
acquires it after the transition, and must refuse.

I then mutated `authorizeOperation` into a check-then-act (manifest read and
status check hoisted above `withEventsLock`) and re-ran: the naive test
("an operation-authorized append is refused once the session has left
active") still PASSED, while this test FAILED. The implementation was
restored from a byte-copy and the file went back to 16/16. So the atomicity
proof is not satisfiable by a comment or a convention.

The replay side is covered separately and independently of write-time
ordering: "replay ignores an operation-authorized event that appears AFTER a
terminal event" appends such an event directly to `events.jsonl` (bypassing
the store entirely, simulating a hand-crafted log) and asserts it lands in
`ignoredAuthorizations`, never in `authorizations`.

## What was deliberately left for P02.2 (R5-R8)

Recorded in full in `P02.1.md`'s Gaps section; summarized here.

- **R5 `invocationKey` idempotency.** The field is threaded end to end
  (authorize → event → `assignment-created` provenance → replay record) but
  its uniqueness is enforced nowhere. Two authorizations may carry the same
  `invocationKey` under different `authorizationId`s today.
- **How much idempotency P02.1 DID build** (so no double-dispatch hole is
  left undocumented): exactly one invariant — `authorizationId` is consumed
  at most once — enforced advisory pre-lock in the gate and authoritatively
  lock-held in `createSessionAssignment`. Consumption is derived from disk,
  never memory. A same-`taskKey` resume prefers its OWN already-consumed
  authorization so an idempotent retry never spends a second one. NOT
  covered: a crash between `authorizeOperation` and `createSessionAssignment`
  leaves an unconsumed authorization a later DIFFERENT `taskKey` may
  legitimately spend — safe under R4 (nothing dispatched), but R5's
  `invocationKey` rule is what makes that resume-identical.
- **R6 context grant at dispatch.** `grantedContextRefs` is recorded and
  copied onto `assignment-created` as `contextGrant: {refs: [...]}`, but the
  dispatched contract's `contextRefs` are still built exactly as before —
  nothing filters or validates them against the grant. The contract's
  same-`coordinationId` ownership rule for grant entries is also unchecked at
  authorize time.
- **R7 bounds interaction.** `activation.maxInvocations` is validated and
  carried but read by nothing at dispatch. No new bounds logic was added and
  no existing `aggregateBounds` enforcement was changed or regressed.
- **R8 driver authority.** `authorizedBy` is shape-validated only; its `id`
  is not tied to `provenanceRoot` or any writer identity.
