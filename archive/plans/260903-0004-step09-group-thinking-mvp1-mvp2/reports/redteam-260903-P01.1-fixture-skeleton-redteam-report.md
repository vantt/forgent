## Findings summary

- **HIGH-1**: `src/runner/coordination/cohort-planner.mjs:307-316`
  (`resolveActorOperation`) resolves an actor's wired operation by first-match
  scan over `graph.nodes`, keyed on `actorId` alone. This new fixture is the
  first one in the repo where a single actor (`reviewer`, `red-team`) is bound
  to two *different* operation ids at two different graph nodes
  (`review-candidate`/`reviewer-recheck`, `red-team-candidate`/`red-team-recheck`).
  `resolveActorOperation` can structurally never return the second binding.
  This is the exact "Edge disambiguation" gap the substrate proposal's own §9
  table names, and the vulnerable function is not hypothetical — it is already
  imported and called by `session-engine.mjs:1631` inside
  `dispatchResearchFanOut`, and covered by a real passing test suite
  (`cohort-planner.test.mjs`). Currently masked only because the two paired
  operations happen to share identical `role`/no `policy`/no `capabilities` —
  the first divergence (e.g. a stricter `minTier` on a recheck op) will cause
  a **silent wrong-value substitution** the moment `planCohort` is pointed at
  this fixture. Correctly out of scope to fix in this cell (no `src/` diff
  required, Do-Not-Touch respected); the gap is that this cell's own Gaps
  section discusses the adjacent `activation` gap but never names this
  concrete, already-live landmine that its own new fixture shape triggers.
- **MEDIUM-1**: no test in
  `test/runner/flow-definition-standalone-master-coordination-loop.test.mjs`
  asserts the `actor` field of any `graph.nodes[].operations[]` binding — only
  operation-to-node placement is checked. A swapped/wrong actor binding (e.g.
  `red-team-recheck` accidentally bound to `reviewer`) would validate under
  schema (no actor.role == operation.role cross-check exists) and pass every
  existing test silently. The shipped fixture's actual bindings are correct
  (verified by direct read); this is a coverage gap, not a live bug.
- **LOW-1**: no test asserts `graph.entry`, total node count/id set, or the
  concrete `transitions` edges — only operation-to-node placement. An orphan
  node or wrong entry point would validate under schema (no
  all-nodes-reachable check exists outside the `completion.mode: synthesize`
  path, which this fixture doesn't use) and pass unnoticed. Fixture's actual
  graph is correct (manually re-derived); test-robustness note only.
- Attack angles that found nothing: raw YAML typo/shape risk; loader test
  ordering fragility (the "finds all shipped core fixtures" test sorts both
  sides before comparing, not order-fragile); `result.kind: work-product`
  misread-as-mutation-authority risk (already covered generically by the
  substrate's own §10 stance, no fixture-specific vector found).
