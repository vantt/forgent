# Constraint Advocate Report — Dispatch Operability Design

**Assignment:** asgn_codex_lead_op_005  
**Scope:** design package `plans/260914-dispatch-operability-evidence-attribution/`; canonical coordination/runner contracts inspected read-only.  
**Verdict:** design is directionally sound and should remain **design-only** until the listed migration gates are proven through production doors.

## Risk scale

Magnitude is the credible harm if the risk escapes implementation: Critical = unsafe authority or irreversible false terminal truth; High = blocked or misleading recovery/operations; Medium = compatibility or diagnosability regression. Reversibility concerns the harm after a bad production write, not the ease of editing code.

## Locked-law and authority constraints

- **L1/L3/L7:** `result.json`, immutable Run evidence, action audit, and mutable projections must retain clear log/state and durability classification. Do not create a shadow Dispatch outcome ledger or a new truth store.
- **L4:** external/CLI consumers require typed outcomes and exit-code/contract discipline; no recovery decision may depend on prose or timeout alone.
- **L5:** implementation completion needs reproducible proof and canonical documentation, not a `READY` design verdict.
- **ADR-011 / current Assignment–Run contract:** Dispatch owns lifecycle truth; herdr/provider state is transport/liveness evidence, not completion receipt. Existing partial admission/fencing implementation raises the bar for the reconcile rollout.
- **DOEA-03/07/10/12:** terminal truth, recovery separation, narrow CAS repair, and full production-door proof are non-negotiable design constraints. Reopening them for implementation convenience is a sink-the-decision failure unless direct contrary evidence triggers the documented lock process.

## Sink-the-decision concern

**Open concern: material.** The design is marked READY and a planned-design pointer is already present in `docs/specs/runner.md`, but the decision lock says DOEA labels are not platform-wide ADRs, while the promotion manifest only schedules a RunResult contract addendum and runner/reading-map pointers. Before source mutation, the implementation track must create a decision-to-canonical-target checklist with owners and evidence links for: (1) the exact RunResult v2 migration contract, (2) inspect/reconcile operation catalog and effect authority, (3) recovery-owner boundary, (4) adapter coverage/attestation declaration, and (5) operator-facing ambiguity/refusal behavior. If any item changes L1/L3/L4/L7 or an accepted cross-area contract, it needs a formal superseding decision rather than another track-local lock.

## Bottom line

Proceed only as a separately authorized implementation track, in the prescribed order: claim/effective contract → result normalization/compatibility → read-only inspection → CAS reconcile → production-door proofs. Gate all writes and all recovery-adjacent behavior on typed ambiguity/corruption/refusal, and do not claim operational value until downstream workflow proofs traverse the selected adapter and persistence path.
