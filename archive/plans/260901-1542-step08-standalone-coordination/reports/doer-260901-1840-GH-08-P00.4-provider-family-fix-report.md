# Doer report — P00.4: provider-family derivation disagreement fix

Branch: `step-08-standalone-coordination`, base `75505c75812703b355f1291d618244c75a5d7b09`, HEAD after fix `454ecb56`.

## What was fixed

**Fix 1 — `src/runner/dispatch/assignment-policy.mjs:~213`** (`resolveAssignmentDispatchPolicy`'s `resolvedProvider` computation): the single-argument `deriveProviderFamily(registeredExecutorEntry)` call silently defaulted its `resolvedCommand` parameter to `'claude'`, disagreeing with `resolve.mjs:429`'s correct two-argument call for any registered executor with no `providerModel`/`provider` field whose real command isn't a Claude CLI command (live-confirmed: `codex-cli`, `codex-herdr`, `herdr`).

Fix extracts the real command the same way `resolve.mjs`'s `resolveExecutorConfig` does — `registeredExecutorEntry.invocations.find(inv => inv.via === 'cli')?.command` — and passes it as the second argument. Every currently-registered production executor (`.fgos/config.json`'s `runner.executors`) is `invocations[]`-shaped, so this covers the real bug fully. A bare (non-`invocations[]`) entry shape has no such structured signal, so `registeredExecutorCommand` stays `undefined` there and `deriveProviderFamily`'s own default parameter (`'claude'`) applies — byte-identical to the pre-fix behavior for that shape. This mattered: an initial version of the fix that also read a bare entry's flat `.command` field regressed ~20 tests across `test/runner/assignment-runresult.test.mjs`, `operation-choice.test.mjs`, `mission-lite.test.mjs`, etc. — those fixtures register a fake executor under the id `claude` with `command: process.execPath` (a locally-swapped-in Node binary standing in for the real CLI, common test convention), which is not a real provider signal. Restricting the extraction to the structured `invocations[]` shape avoided that regression while still fixing the real bug and preserving the deliberately-different `custom-claude-executor` test (bare shape, `command: 'claude'`, expects family `'claude'` via `deriveProviderFamily`'s own default).

**Fix 2 — `src/runner/dispatch/transport.mjs:~169`** (`resolveExecutorCommand`'s returned `provider` field, consumed by `cli.mjs`'s stderr dispatch banners and `loop.mjs`'s `executor.dispatch` audit event): was `executor.provider ?? executor.command` — for every currently-registered production executor (no top-level `.provider` alias declared anywhere in `.fgos/config.json`), this always fell through to the raw `executor.command`, ignoring `providerModel` entirely (e.g. `glm-cli`, routed to `z-ai`/OpenRouter via env override, would show `provider=claude` in the banner — actively misleading).

Fix changes the fallback to `executor.governance.providerFamily` (`resolveExecutorConfig`'s own already-computed `deriveProviderFamily(executorEntry, executor.command)` result). An explicit `executor.provider` display alias still wins first — this is a deliberate, separately-tested concept distinct from the model-routing family (`dispatch.test.mjs:3230`, "D9's reported agy/Gemini bug" regression test: an executor can alias to `"agy"` for display while its real family/model-routing `providerModel` is `"gemini"`). An initial version that unconditionally used `governance.providerFamily` broke that alias test and one other (`dispatch.test.mjs:1830`) — restoring the alias-first precedence fixed both while still correcting the dead-fallback case.

## Regression test

Added to `test/runner/assignment-policy.test.mjs` (also imports `resolveExecutorConfig` from `resolve.mjs` now): a `codex-cli`-shaped executor entry (`invocations: [{via:'cli', command:'codex', ...}]`, `allowCrossProvider: true`, no `providerModel`/`provider`) run through `resolveAssignmentDispatchPolicy`, asserting `effective.providerModel === 'codex'` and `effective.provenance.provider.value === 'codex'` (pinning the fix — pre-fix this was `'claude'`), plus a direct cross-check that `resolveExecutorConfig(...).governance.providerFamily` equals the same value, proving the two previously-disagreeing call sites now agree.
