## Files Changed

- `src/runner/dispatch/resolve.mjs` (+63/-9)
  - New `resolvePolicyTierModel(cfg, policyTier, providerModel = 'claude')`
    — direct policy-tier resolver (R5). Reads `MODEL_POLICY_TIERS` values
    (`lightweight|standard|creative|analytical|critical`) directly against
    `cfg.modelPolicies.<providerModel>`, with no `DEFAULT_TIER_TO_POLICY`
    indirection. Mirrors `modelForTier`'s own legacy-flat-`cfg.models`
    fallback (the two tables are mutually-substitutable per this module's
    existing D9 precedent) so callers that configure only a legacy
    `models` map are unaffected. Fails closed with a named
    `RunnerConfigError` (names provider + tier) — never swallowed.
  - New `deriveProviderFamily(executorEntry, resolvedCommand = 'claude')`
    (R6) — extracted (pure move) from `resolveExecutorConfig`'s own inline
    provider-family ternary (was lines 368-375). `resolveExecutorConfig`
    now calls it with the same two inputs it always used
    (`executorEntry`, `executor.command`) — byte-identical behavior for
    that existing caller. `assignment-policy.mjs` calls it with just
    `executorEntry` (no resolved command exists yet at policy-resolution
    time), which resolves through the `CLAUDE_CLI_COMMANDS` branch to
    `'claude'` by default — matching R6(c)'s simpler rule exactly.
  - `modelForTier` itself: **untouched**. Verified via `git diff` and
    GitNexus `impact` (upstream) — 5 direct callers/processes
    (`dispatchClaimedItem` in `loop.mjs`, `executeAssignment`,
    `spawnWorker`, `fanoutBatchExecutorCli`, `runMissionAssignment`), all
    still green.

- `src/runner/dispatch/config.mjs` (+14)
  - New `supportsPolicyTier(cfg, providerModel, policyTier)` (R8) — pure
    boolean query, `typeof cfg?.modelPolicies?.[providerModel]?.[policyTier]
    === 'string'`, no I/O. `resolvePolicyTierModel` calls it for its
    modelPolicies-table branch.
  - `validateModelPoliciesShape` (R8's other half): confirmed **already**
    accepts a partial per-provider tier table at load time (its own doc
    comment already documented this); already rejects an invalid tier key
    (not in `MODEL_POLICY_TIERS`) and an invalid model value
    (non-string/empty). No code change needed there — added tests instead
    (below) to prove it.

- `src/runner/dispatch/assignment-policy.mjs` (rewritten resolution body)
  - R5: tier resolution (`effectiveTier`) unchanged; step 4 (provider
    model & literal model resolution) now calls `resolvePolicyTierModel`
    directly, no `try/catch` — an unsupported provider/tier pair now
    throws all the way up instead of silently setting `resolvedModel =
    null` (the exact B1 swallow, removed).
  - R6: added a registered-executor lookup (`runnerConfig.executors[primaryExecutor]`)
    before deriving provider/model. Throws a named `RunnerConfigError`
    when `primaryExecutor` is not found there — but ONLY when
    `runnerConfig.executors` is itself present as an object (a real
    registry to check against; `runnerConfig` and `runnerConfig.executors`
    both stay optional, matching every other place in this file). The
    literal `'claude'` identity and whatever `runnerConfig.executor.command`
    already is are exempted from that "must be registered" requirement —
    see Gaps below for why this was necessary (a real regression, not a
    speculative carve-out). `providerModel` (governance-checked field) now
    comes from `deriveProviderFamily(registeredExecutorEntry)` when the
    executor is registered, not the raw executor id string. Added a new
    `executorId` field (= `primaryExecutor`) distinct from `providerModel`,
    so a future governance check can inspect the two independently.
  - R7: added `effectivePolicy.provenance` — a new, additive field (every
    pre-existing flat field — `role`, `persona`, `executorPreference`,
    `providerModel`, `tier`, `model`, `visibility`, `constraints` — is
    unchanged in shape/value). Shape is
    `{field: {value, source: {scope, id}}}` for
    executor/provider/model/tier/persona/visibility/constraints/governance,
    matching ADR-009's FlowDefinition PolicyPatch provenance contract
    verbatim. Scopes used: `cliOverride`, `opPolicy`, `work`, `default`,
    `registeredExecutor`, `runnerConfig`, `assignment`, `governance`.

3. **R6(b) exemption, worth flagging to Review/Red-Team explicitly**: the
   "unregistered `preferExecutor` throws" check exempts the literal
   `'claude'` identity and whatever `runnerConfig.executor.command`
   already is from the "must appear in `runnerConfig.executors`"
   requirement. This was **not** a speculative design choice — a naive
   "must always be listed" version of the check broke a real, pre-existing
   green test (`assignment-dispatch.test.mjs`'s CLI-subprocess test),
   because this machine's own `~/.fgos/config.json` registers only `pi`
   under `executors` (not `claude`), and `mergeWithGlobalConfig` pulls
   that in for any project config that doesn't declare its own
   `executors` map. Root-caused and fixed by scoping the exemption
   narrowly to the implicit-default identity (no silent substitution
   occurs there — the value asked for and the value used are identical).
   See the code comment at `assignment-policy.mjs:156-163` and the new
   regression test `resolveAssignmentDispatchPolicy never validates
   preferExecutor registration when runnerConfig declares no executors
   registry at all`.
