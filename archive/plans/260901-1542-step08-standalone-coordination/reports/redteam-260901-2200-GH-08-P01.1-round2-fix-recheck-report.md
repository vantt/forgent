# Red-Team re-check: P01.1 round-2 crash-safety fixes

Scope: focused re-verification of `createSessionAssignment` /
`completeAssignmentRegistration` in `src/runner/coordination/store.mjs`,
after the round-1 (write-order) and round-2 (self-heal + taskKey hashing +
inner-crash-window) fixes. Did not re-run the original full attack list
(contract fidelity, session-blindness, etc.) — already covered twice.

## What was verified

1. **Re-derived the crash-point induction independently.** Listed every
   sequential on-disk write `createSessionAssignment` performs (5 writes:
   directory claim, claim-file, `assignment.json`, event append, ref
   update), then hand-traced the actual code (not the doc comment) for
   every crash point between them. All converge to one of: true existing
   Assignment, safe loud `CoordinationError`, or completed self-heal. None
   produces a silent duplicate Assignment, silent duplicate event, or a
   permanently session-invisible Assignment.
2. **Reproduced 2 novel crash windows independently**, via a standalone
   script (`/tmp/.../redteam-recheck-p01-1.mjs`, not the shipped test
   file) calling the real exported functions against hand-constructed
   on-disk state:
   - Inner self-heal crash window (event appended, ref missing, inside
     `completeAssignmentRegistration`): self-heals correctly, no
     duplicate event. Also proved a genuinely duplicated event line IS
     detectable via `readSessionEvents` (so the "stays at 1" result is
     the guard doing real work, not a blind spot).
   - taskKey-hash mismatch/collision throw path (`store.mjs:389-394`):
     **zero coverage in the shipped test suite** — independently
     constructed a decoy claim file and confirmed a named
     `CoordinationError` (`category: "validation"`), no side effects.
3. Confirmed `completeAssignmentRegistration` is unexported and only
   called from the two sites inside `createSessionAssignment`'s own held
   `withEventsLock` — genuinely never reachable outside the lock.
4. Confirmed the taskKey-hashing function (`hashTaskKey`, SHA-256 prefix)
   and independently confirmed `"primary-round-1"` / `"primary_round_1"`
   hash to distinct values — the MEDIUM fix's regression test is not
   self-defeating.
5. Ran the full required test command (758 pass, 0 fail) and the smoke
   check (`mechanism` field present). Confirmed the contract doc's
   Storage Layout table lists `tasks/<hash>.json`. Confirmed
   `git status --porcelain -- src test domains
   docs/architect/agent-coordination/contracts/` shows only files this
   cell's full history (both fix rounds) claims.

## New finding (LOW, informational, not blocking)

`store.mjs:388`'s claim-file `JSON.parse` is unguarded — unlike its
sibling `readAssignmentJson` (`store.mjs:254-262`), which wraps its own
`JSON.parse` and rethrows `CoordinationError('corrupt-log', ...)`. A crash
mid-write of the claim file itself (a torn `fs.writeFileSync` on
`tasks/<hash>.json`) leaves a claim file that exists but fails to parse.
Independently reproduced: a truncated claim file causes
`createSessionAssignment` to throw a raw, unwrapped `SyntaxError`
(`instanceof CoordinationError` is `false`, `category` is `undefined`),
not the module's own error taxonomy. This is still a safe loud (and
permanent, same as the already-accepted claim-only crash window) failure
— never a silent duplicate or further corruption — so it doesn't violate
the specific safety bar this re-check was scoped to, but it breaks the
module's own fail-closed `CoordinationError` convention. Smallest fix:
wrap `store.mjs:388`'s `JSON.parse` the same way `readAssignmentJson`
already does.

Also noted (informational only): the inter-write window between the
Assignment-directory claim and the claim-file write can leave a harmless
orphaned *empty* directory on retry (never becomes a real Assignment, not
referenced anywhere) — safe, but not named in the function's doc comment
alongside its two sibling crash windows. And `completeAssignmentRegistration`'s
duplicate-check does a full `readEvents` scan on every call (including the
common first-time path), a mechanism deviation from `state/store.mjs`'s
incremental-view convention (tsk-49e) — low practical risk since a
session's own event log is scoped to that session, not the whole
platform's history.
